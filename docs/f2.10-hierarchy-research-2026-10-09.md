# F2.10 — a configurable, any-depth site hierarchy: research (2026-10-09)

*Input to the `F2.10` ADR. Prepared because the client's site list (question
`C22a`, [handover 2026-08-17](./ion-exchange-client-handover-2026-08-17.md))
has had no answer since 2026-08-17, and the owner asked how a product should
make the hierarchy fit any customer as data. Two parts: how standards and
products model it, and what our code would need. Base: `main` at `6a184d48`.*

## Summary

- **No surveyed product or standard uses a fixed ladder.** They store a tree of
  typed nodes: each node has a parent and a type, the tenant's catalogue names
  the types, and the depth is free (AWS IoT SiteWise caps it at 30).
- **"Subsystem" is not a location level.** ISO 14224, ISA-95, Haystack and Brick
  all model it as equipment composition or a system grouping under the site.
  Our asset groups already play that role (ADR 0040 ruling 5, ADR 0053
  decision 9).
- **Our schema is close, the consumers are not.** One self-referencing column,
  `locations.parent_id`, makes the tree; existing rows become roots and no data
  moves. About eight consumers assume one flat location level. Effort **8–12**,
  above the row's 4–8, which assumed one campus tier rather than a general tree.
- **Everything structural can be built without `C22a`.** The client's list
  becomes data an admin enters; it still decides the real nodes and names,
  whether a campus needs its own control room, and per-campus tariffs.

### Recurring patterns

1. **Typed adjacency list plus a type catalogue** (Brick, Haystack, SiteWise,
   Azure Digital Twins, SAP): node + parent + type; the catalogue holds labels and
   allowed parent/child types. Fits when depth and names differ per customer —
   our case.
2. **Naming separate from structure** (SAP): a code mask or label template is
   presentation and validation; the parent link is stored data. Never derive a
   parent from a code.
3. **A precomputed ancestor index** — a closure table (Maximo `LOCANCESTOR`) or
   a materialized path (Postgres `ltree`) — when subtree reads, roll-ups and ACL
   checks dominate and moves are rare. *No direct benchmark of the two found.*
4. **Parallel hierarchies over the same nodes** (Maximo systems, Desigo views,
   Niagara hierarchies, Haystack `systemRef`, Brick `feeds`): physical
   containment, electrical feed and organisational grouping as separate edge
   sets.
5. **Location separate from composition** (Brick `hasLocation` vs `hasPart`,
   RealEstateCore same-type `isPartOf`, ISO 14224 levels 1–5 vs 6–9) — where a
   subsystem or skid sits between asset and site.
6. **Tag- or query-defined virtual hierarchies** (Niagara, PME templates) for
   navigation views per user group, not for authoritative roll-ups.

### Reported pitfalls

- **Ancestor-index drift on a move:** Maximo APAR IJ45613 lost `LOCANCESTOR`
  rows on a re-parent, IJ37745 on an undelete
  (https://www.ibm.com/support/pages/apar/IJ37745).
- **Reports hard-wired to a level shape** return nothing on other structures
  (Schneider PME FAQ, https://www.se.com/au/en/faqs/FA241688).
- **One-level aggregation** (SiteWise): a deep roll-up chains metrics.
- **Recursive cost:** products avoid a recursive query on every read with a
  path or closure index; nested sets make moves linear in the whole tree
  (https://docu.ilias.de/go/wiki/wpage_255_1357).
- *Inference, unsourced:* a grant on a node implies its descendants, so a move
  changes visibility at once; historical roll-ups after a re-parent show the
  current tree unless the parent link is effective-dated.

## 2. Our code (at `6a184d48`)

### Current model

`Organization → Location → Asset → Point`, fixed (ADR 0008:1, :20-24). ADR 0008
forbids no depth; the holds are elsewhere:

- ADR 0018 decision 6 deferred `locations.parent_id` and `parent_asset_id` to a
  companion ADR that was never written (0018:123-126), and already ruled that
  *a grant on a parent location does imply access to its descendants … must be
  explicitly tested: it silently widens access* (0018:150-155).
- `assertLocationManagementIsFlat`
  (`apps/api/src/auth/access-control.integration.spec.ts:640-700`) enforces
  flatness on purpose: *"Do not relax it to make depth compile"*.
- `bms.locations` (`packages/db/src/schema/bms-schema.ts:100-126`): no parent
  column; `type` → `location_types.code` (:108-112); `latitude`/`longitude`
  NOT NULL (:116-117; also the API, `locations.schema.ts:23-24`,
  `contracts/admin.ts:45-46`).
- `bms.location_types` (:92-98) is **global** — ADR 0077 decision 1 rejected a
  per-organization table (0077:68-71); only a global admin edits it
  (`location-types.service.ts:180-187`).
- `asset_groups` are per location (:345-368), with `asset_group_members.role`
  (ADR 0049, :370-385) — the "subsystem".
- `assets.location_id` NOT NULL, the column every scoped check filters on
  (:293-301). No `parent_asset_id` anywhere.
- `map_locations` (:735-750) has no `organization_id`; F3.79 makes every active
  location a pin (`apps/api/src/map/map.service.ts:84-107`).

### Implementation shapes

1. **`locations.parent_id` self-reference + recursive CTE (recommended).**
   Composite FK `(parent_id, organization_id) → (id, organization_id)` with a
   unique `(id, organization_id)` (precedents `asset_groups_id_location_key`,
   `bms-schema.ts:367`; the `dashboard_tabs` composite FKs,
   `dashboard-schema.ts:281-288`). `WITH RECURSIVE` needs no dependency gate;
   `ltree` is an extension (migrations carry no `CREATE EXTENSION`,
   `drizzle/0075_location_timezone.sql:32`; `btree_gist` had to go through
   `roles.ts`), and a closure table needs triggers — neither pays off at tens to
   hundreds of nodes per organization. Level naming, one of:
   - (i-a) depth from the tree, the label from the global type; add `campus`,
     `township`, `plant` by `INSERT`;
   - (i-b) a new org-scoped RLS table `location_levels(organization_id, depth,
     label)`, which must amend ADR 0077.
   Keep **type** (what the place is) separate from **level** (where it sits).
2. **A fixed-depth `location_groups` tier:** 3–5 points; fails "any depth" —
   every further tier is code again.
3. **Tags only:** 2–3 points; no containment, and ADR 0018's descendant rule
   would need a tag-grant table, so no saving.

The asset tree (`parent_asset_id`) is not needed for the ladder: *"one asset per
plant for v1 … the group is the train … a train of unit assets with a
parent-child link is a v2 shape, available once F2.10 lands"* (ADR 0040:168-176;
ADR 0053:160-166).

### Risks

- **RLS does not cover the scope walk:** scope reads run on `fleetDb`, which
  bypasses RLS (`access-scope-sources.ts:106`, `:149`, `:190`). Containment is
  the composite FK plus an org predicate inside the recursive CTE; a cross-org
  parent edge would leak a subtree.
- **Scope widening:** 28 + 18 call sites widen at once (ADR 0018:150-155); the
  tripwire must be re-pointed at the exact closure and prove a sibling subtree
  is refused.
- **Inactive ancestors:** per-row `active` filters would hide a campus but keep
  its children visible — the ADR must rule it.
- **Coordinates:** interior nodes need a centroid, or `latitude`/`longitude`
  become nullable, which reaches the map and the timezone logic.
- **Reports** with stored `location_ids[]` silently miss new children.
- **ADR 0055:** any aggregate above a site re-opens decision 12.

## 3. Recommendation (for the ADR's decisions)

| Decision | Recommended |
|---|---|
| Shape | `locations.parent_id` + recursive CTE; composite same-org FK; cycle guard; depth cap |
| Level names | New global types (campus, township, plant) by `INSERT` (i-a); a per-org label table only when a client asks (ADR 0077 amendment then) |
| Where assets attach | Any node; `@site` stays the asset's own node (ADR 0055 unchanged) |
| Access | A grant on a node covers its subtree (ADR 0018); a deactivated node hides its subtree; re-pointed tripwire with sibling denial |
| Subsystem | Asset groups, as today; `parent_asset_id` stays v2 |
| Reports and dashboards | Store a node, expand at read time; never name a level in code |
| Moves | Allowed within one organization; audit-logged; a consistency check in the suite |

### Buildable without `C22a`

The migration and composite FK; cycle and same-org guards; subtree scope and
the re-pointed tripwire; the `parentId` contract field; the tree picker and
admin form; subtree filters in health, sustainability and reports; the level
naming.

### Needs `C22a` (data or a later option, not a design block)

The real nodes, depths and names per tenant; whether a campus needs its own
control room or `@`-selector; whether interior nodes carry coordinates;
per-campus tariffs.

### Not verified

The ISO 14224 text; Area optional in ISA-95; Brick location depth; the Honeywell
Forge model; the Desigo physical view; Maximo after 7.6; an `ltree` vs closure
benchmark; ACL and re-parenting roll-up behaviour (inference).
