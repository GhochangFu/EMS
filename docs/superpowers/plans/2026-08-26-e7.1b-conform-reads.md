# E7.1b — conform the deviating decision-1 LIST reads to ADR 0043 (decisions 1+3)

Follow-up to `2026-08-26-e7.1b-tenant-columns-policies-write-path.md`. That work
reclassified several decision-1 **user-facing LIST reads** onto *unconditional*
`fleetDb` (BYPASSRLS). ADR 0043 decision 1 says those reads run **inside
`withTenant` by default**; only a genuinely fleet-wide admin view (decision 2) or
a multi-org actor at run time (decision 3) falls back to fleet. The compliance
review caught the deviation; the human chose **conform**.

## Scope

**In — six user-facing LIST reads, four services:**

| Service | Read | Table(s) |
|---|---|---|
| `alarms` | `list` | `alarms` |
| `work-orders` | `list` | `work_orders` |
| `maintenance` | `list` (+ its `getActiveWorkOrdersBySchedule` guard read) | `maintenance_schedules`/`_history`, `work_orders` |
| `rules` | `listRules` (via `ruleRows`) | `automation_rules` |
| `rules` | `listExecutions` | `rule_executions` |

**Out — stays on fleet, unchanged (write-path resolution / not decision-1 /
decision-2):**

- Pre-write org resolution: `resolveAlarmOrg`, `resolveWorkOrderOrg`,
  `resolveScheduleOrg`, `resolveWriteOrg`, `reorder`'s `currentRows`,
  `validateRuleDraft`'s code scan, `nextRuleCode`, every `resolveActorId`.
- **Post-write read-backs** (`work-orders.getById`, `maintenance.getScheduleItem`
  /`getWorkOrder`, `rules.getRuleRow`): these *are* the org-discovery step (they
  cannot take a known org — finding it is their job), and read
  `WHERE id=<just-written> AND assetId IN assetIds` — the same protection as the
  blessed `resolveWorkOrderOrg`. Pulling them in forces a 13-method write-path
  redesign. **Excluded, with the residual named** (comment + backlog follow-up:
  *single-org post-write read-backs on decision-1 tables still resolve to fleet*).
- `rules.getBuilderCatalog` reads `assets` (master data, **not** a decision-1
  table) — excluded.
- `rules.evaluateEnabledRules` / `ruleRows` cross-org sweep — decision 2
  (ADR 0033), stays fleet.
- `admin/audit` (decision-12 global-admin view) and `notifications`/`channels`
  (E7.1c per decision 7) — excluded, unchanged.

## Design — one shared helper

`apps/api/src/database/tenant-read-scope.ts` (new), beside `tenant-context.ts`:

```ts
export type ReadScopeResolution =
  | { kind: "empty" }
  | { kind: "single"; organizationId: string }
  | { kind: "fleet" };

// Reads DISTINCT assets.organization_id on fleet (master-data resolution,
// pre-tenant — the established access-control pattern).
resolveTenantReadScope(fleetDb, assetIds): Promise<ReadScopeResolution>
//   null/undefined (admin)      -> { fleet }        decision 2 admin view
//   []                          -> { empty }
//   0 matching assets           -> { empty }        (vanished/foreign ids)
//   1 distinct org              -> { single, org }  decision 1 (RLS backstop)
//   >1 distinct org             -> { fleet }        decision 3 run-time fallback
// assets.organization_id is NOT NULL since 0047, so a resolved org is never
// null — no backfill branch here (it would be unreachable and untestable).

// The single seam. fn ALWAYS receives a BmsTx.
withReadScope<T>(tenantDb, fleetDb, assetIds, onEmpty: () => T,
                 fn: (tx: BmsTx) => Promise<T>): Promise<T>
//   single -> withTenant(tenantDb, org, fn)   (GUC set, RLS scopes)
//   fleet  -> fleetDb.transaction(fn)         (BYPASSRLS, no GUC)
//   empty  -> onEmpty()                       (fn never called, no query)
```

- `fn` is typed `(tx: BmsTx) => …` only — **no `BmsDb | BmsTx` union, no cast**.
  Write-path callers of `ruleRows`/`getActiveWorkOrdersBySchedule` wrap in
  `fleetDb.transaction(...)`; the default param keeps them terse.
- Every downstream read inside `fn(tx)` MUST use `tx`. A stray `this.fleetDb`
  inside a tenant tx compiles, runs on a second connection, and silently
  unscopes — the one thing to grep for after each edit.

## Build order (helper-first — get Layer 1 green before touching a service)

### 1. Helper + its own integration test (Layer 1)

- Write `tenant-read-scope.ts`.
- `apps/api/src/database/tenant-read-scope.integration.{spec,test}.ts` — real
  `bms_tenant`/`bms_fleet` pools, a probe `fn` running
  `select current_user, current_setting('app.current_organization', true)`:
  - single-org assetIds → `current_user` = tenant role **and** GUC = that org;
  - two-org assetIds → fleet role, GUC empty;
  - `null` (admin) → fleet role;
  - `[]` → `onEmpty`, probe never runs;
  - a NULL-org asset in scope → throws.
- This asserts the ADR decisions verbatim, with zero production instrumentation.
  Get it green first.

### 2. The six reads (TDD per service; alarms first as the pattern)

For each: move the query builder into `fn(tx)`, call through `withReadScope`,
preserve the **exact** empty shape via `onEmpty`
(`{items:[],nextCursor:null}` for alarms; `{items:[]}` elsewhere).

- `alarms.list` — pattern-setter, hands-on.
- `work-orders.list`.
- `maintenance.list` — also thread the scoped `tx` into
  `getActiveWorkOrdersBySchedule` (add a `db: BmsTx` param; `convertToWorkOrder`
  keeps calling it via `fleetDb.transaction`, write-path). **Reword its
  `:233-238` comment** — it now has two modes (scoped tx / fleet).
- `rules.listRules` — give `ruleRows(db: BmsTx = <fleet tx>)` a handle param;
  `listRules` runs it via `withReadScope`, keeps the `filterRuleRows` post-filter
  as sub-org narrowing. `evaluateEnabledRules`/`getRuleRow` still call the fleet
  default. Confirm `mapRuleRow` NULL tolerance (asset-less rules already null;
  rule.org == asset.org so no *new* nulls).
- `rules.listExecutions` — `withReadScope` around the `rule_executions ⋈
  automation_rules` read.

### 3. Per-service tests (Layer 2) — two assertions each

- **Decision-3 (ADR-mandated):** one `list({assetIds:[inScope, foreign]})`
  returns **both** orgs' rows (a wrongful `withTenant(one org)` drops the other).
- **Mechanism — `.transaction` counter:** wrap injected dbs, assert a single-org
  list called `tenantDb.transaction` once and `fleetDb.transaction` zero. A revert
  to `this.fleetDb.select(...)` drops the tenant count to 0 → fail.
