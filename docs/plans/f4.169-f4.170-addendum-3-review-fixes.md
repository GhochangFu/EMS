## 1. The canonical location lookup (security M-1, code-review C1/F1, migration Low)

Candidates for an identity (ESKOM org only):
- K: rows whose `meta->>'seedKey'` equals this key;
- S, C: rows matching the canonical slug / code whose key is NULL or equals this
  key (a row keyed for another identity is never a candidate).

Rule:
- no candidate → INSERT (holder pre-reads as today);
- every candidate is the same row → adopt it;
- else, if K has a row and that row is the oldest candidate (`created_at`, then
  `id`) → adopt it;
- else → adopt nothing, write nothing for this identity, log one line naming every
  candidate id.

`created_at` is not writable through any admin path (checked: locations schema
and service, onboarding, template instantiate).

Required cases (integration, one each, each with the precedence mutation that
reddens it):
- (a) C's key wiped, newer X has a forged key → nothing adopted, X unchanged
  (name, meta, key), one line.
- (b) no keys; C's slug renamed; admin Z takes the canonical slug → nothing
  adopted, Z unchanged, C unchanged.
- (c) no keys; two canonical rows swap slugs → no cross-identity overwrite.
- (d) C keyed; C's code renamed; Y takes the canonical code → C adopted, code
  write skipped and logged.
- (e) C keyed; C's slug renamed; Z takes the canonical slug → C adopted, slug
  write skipped and logged.
- (f) row A keyed `a` holds B's slug → A is not a candidate for B.
- S4 must also assert the holder Z is unchanged (null key, name, meta).
