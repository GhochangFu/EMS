## 3. Refinements (each is a call inside the amendment; veto at skim)

- **R1 — "current" is the newest succeeded run that holds the current hour's bucket.** C3 says "a bucket at or after the current hour". A run's buckets are consecutive, so the two agree for every run whose first bucket is not in the future. Equality makes the one-point probe three equalities on `forecasts_pkey` and the list one row per run per point. A run started with a future `--as-of` is not current until its first hour arrives.
- **R2 — one clock.** The API reads `new Date()` once per request. The current hour is that instant floored to the UTC hour in TypeScript and bound as a parameter (the same value as C4's `date_trunc('hour', now(), 'UTC')`). Stale is `currentHour − firstBucket > 3 h` (C3). Tests inject the clock.
- **R3 — a 64 h look-back.** `FORECAST_MAX_HORIZON_HOURS = 64` in the contract file mirrors the scorer's upper bound. It bounds the search for a run's first bucket and the list's run window. A case in `tests/e1.1-ml-readiness-single-source.test.ts` holds it equal to `config.py`'s bound.
- **R4 — the list SQL is a per-run `LATERAL` with `OFFSET 0`, and a test holds it.** See section 2. An integration case plants about 150,000 rows in a rolled-back transaction, runs `ANALYZE`, and fails if `EXPLAIN (FORMAT JSON)` shows a `Seq Scan` on `forecasts` for either read.
- **R5 — wire shape.** `GET /ml/points/:pointRef/forecast` answers `{ asOf, forecast }`; `asOf` is the server instant, used for the "now" marker and the live-range rule, so no screen trusts the browser clock. The first bucket is not on the wire; `stale` is. `GET /ml/forecasts` answers `{ items }`.
- **R6 — the guard moves unchanged; the cap is a second function.** `decodeGuardedPointRef` moves to `apps/api/src/common/guarded-point-ref.ts` byte for byte. `decodeBoundedPointRef` in the same file adds the 1–128 character check on `pointKey` (S2) and is what the `ml` route calls. The telemetry routes keep their behaviour.
- **R7 — the chart draws a forecast only when the page function is `avg`.** The forecast is of the hourly mean. Beside a `sum` or `max` line it is a different quantity and would wreck the axis.
- **R8 — the exact axis rule (C2).** `span = to − from`. `cap = span ≥ 24 h ? 48 h : span`. `xMax = max(to, min(lastForecastBucket, to + cap))`. Forecast points after `xMax` are dropped, except the first one, so the line runs to the edge and ECharts clips it. With no forecast drawn, `xMax = to` as today.
- **R9 — legend.** The option gains `legend` (type `scroll`) whenever a series is plotted. It lists the actual series, "Forecast p50" and "Forecast p10–p90", never the hidden lower band series. With forecasts for more than one point the names are suffixed ` · <pointKey>`.
- **R10 — the widget's actual line.** The widget reads the aggregate route for 1,440 minutes with `bucketFunction=avg&bucketStats=true` (the read the history page's 24 h preset makes) and averages the 1-minute buckets to whole UTC hours in the browser, weighted by `sampleCount`. That equals `_1h`'s `sum / count`. No API change.
- **R11 — the widget's config is `{}`.** C1 leaves `config` for renderer options and none is needed yet: the unit comes from the bound point.
- **R12 — `forecast` is refused in both template surfaces** (asset templates and dashboard templates), so "builder palette only" holds after C1. ADR 0048 Amendment 1's derived rule would make it authorable; Amendment 3 R-f ("builder palette only", newer) already decides against that, so R12 implements an accepted ruling. Q1 confirmed it.
- **R13 — `/forecasts` is declared in a new `apps/web/src/pages/extra-routes.tsx`.** `app.tsx` has one free line. The legacy `/assets/:assetId/history` redirect moves to the same file, which frees about seven lines. `EXTRA_ADMIN_ROUTES` and its two gates are untouched.
- **R14 — tab-state helpers move out of `dashboard-builder-form.ts`** (lines 896–999) into a new `apps/web/src/lib/dashboard-builder-tabs.ts`, re-exported, as a move-only commit. The spec file of that name already exists.
- **R15 — model label.** The web maps `amazon/chronos-2` → "Chronos-2" and `amazon/chronos-bolt-small` → "Chronos-Bolt"; an unknown name is shown as stored.
- **R16 — the mirror declares CHECKs with Drizzle's `check()`**, the first schema file here to do so, because R-a says "checks". An integration case compares the mirror's columns with `information_schema.columns` (C9: nothing else would notice drift).
- **R17 — response types are exported from the contract file** (`packages/shared/src/contracts/ml-forecasts.ts`), the `maintenance-windows.ts` precedent. `index.ts` is not touched.
- **R18 — the three C5 edits stop naming a version.** The `e1.1` integration test and the Python test assert `≥` the expected version; only the new `e1.4a` test asserts `= 2`.

One-point read (parameters: `$1` asset, `$2` point key, `$3` and `$4` the current hour, `$5` the current hour − 64 h; the 64 h lower bound matches the list, review N1). The pure step takes the first row's bucket as the first bucket, computes `stale`, and returns buckets `≥` the current hour (C4):

```sql
WITH current AS (
  SELECT f.model_run_id, f.issued_at, r.model_name, r.model_version
    FROM ml.forecasts f
    JOIN ml.model_runs r ON r.id = f.model_run_id AND r.organization_id = f.organization_id
   WHERE f.asset_id = $1 AND f.point_key = $2 AND f.horizon_bucket = $3
     AND r.status = 'succeeded' AND f.issued_at >= $5
   ORDER BY f.issued_at DESC
   LIMIT 1
)
SELECT f.horizon_bucket, f.p10, f.p50, f.p90, c.issued_at, c.model_name, c.model_version
  FROM current c
  JOIN ml.forecasts f ON f.asset_id = $1 AND f.point_key = $2
                     AND f.model_run_id = c.model_run_id AND f.horizon_bucket >= $4
 ORDER BY f.horizon_bucket
```

```sql
WITH recent_runs AS (
  SELECT r.id, r.organization_id, r.model_name, r.model_version
    FROM ml.model_runs r
   WHERE r.status = 'succeeded' AND r.started_at >= $since
), covering AS (
  SELECT f.asset_id, f.point_key, f.model_run_id, f.issued_at, rr.model_name, rr.model_version
    FROM recent_runs rr
   CROSS JOIN LATERAL (
     SELECT f0.asset_id, f0.point_key, f0.model_run_id, f0.issued_at
       FROM ml.forecasts f0

        AND f0.horizon_bucket = $current_hour
        AND f0.asset_id = ANY($ids)          -- present whenever ids is not null (S1)
     OFFSET 0                                -- keeps the per-run index path (R4)
   ) f
), current AS (
  SELECT DISTINCT ON (asset_id, point_key) asset_id, point_key, model_run_id, issued_at, model_name, model_version
    FROM covering ORDER BY asset_id, point_key, issued_at DESC
)
SELECT c.asset_id, c.point_key, c.issued_at, c.model_name, c.model_version,
       agg.first_bucket, agg.p50_min, agg.p50_max, agg.p50_peak_at,
       a.code AS asset_code, a.name AS asset_name,
       l.id AS location_id, l.name AS location_name,
       l.timezone AS location_time_zone, o.timezone AS organization_time_zone,
       ap.unit
  FROM current c
 CROSS JOIN LATERAL (
   SELECT min(f.horizon_bucket) AS first_bucket,
          min(f.p50) FILTER (WHERE f.horizon_bucket >= $current_hour) AS p50_min,
          max(f.p50) FILTER (WHERE f.horizon_bucket >= $current_hour) AS p50_max,
          (array_agg(f.horizon_bucket ORDER BY f.p50 DESC, f.horizon_bucket)
             FILTER (WHERE f.horizon_bucket >= $current_hour))[1] AS p50_peak_at
     FROM ml.forecasts f
    WHERE f.asset_id = c.asset_id AND f.point_key = c.point_key
      AND f.model_run_id = c.model_run_id AND f.horizon_bucket >= $since
 ) agg
  JOIN bms.assets a ON a.id = c.asset_id
  JOIN bms.locations l ON l.id = a.location_id
  LEFT JOIN bms.organizations o ON o.id = a.organization_id
  LEFT JOIN bms.asset_points ap ON ap.asset_id = c.asset_id AND ap.point_key = c.point_key
 ORDER BY l.name, a.code, c.point_key
```
