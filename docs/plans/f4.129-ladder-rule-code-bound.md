# F4.129 — bound the ESKOM ladder rule code (hash-suffix cut)

Plan by `plan-architect` (Fable), 2026-09-27, from the `F4.129` row (`docs/BACKLOG.md`, ⬜, P2, effort 1, Wave 1, Depends —, not an enabler). Measured read-only at `01a3640f` (branch `fix/F4.129-ladder-rule-code-bound`). Owner-gated scope (2026-09-27): **hash-suffix cut** — no ADR, no schema change, the column stays `varchar(64)`. Skip-with-warning and widening the column were rejected. Merge approval (step 7) is owed.

## Goal

`seedEskomLadderRules` (`packages/db/src/automation-rules-seed.ts:557`) writes five rules per ESKOM electrical asset with code `ESKOM_${asset.code.replaceAll("-", "_")}_${rule.suffix}` (line 604). `bms.automation_rules.code` is `varchar(64)` (`schema/alarms-schema.ts:189`) and `bms.assets.code` is `varchar(64)` too, so one asset code of 42+ characters aborts `pnpm db:seed` with `22001 value too long`, and `compose up` re-seeds on every boot. A pure helper `ladderRuleCode(assetCode, suffix)` returns the current code unchanged whenever it fits in 64, and otherwise cuts the asset part and inserts an 8-hex uppercase SHA-256 prefix of the full asset code, so the result is exactly 64 and two long codes that share a prefix stay distinct. Existing seeded rule codes do not change by one byte.

Out of scope: widening the column; skipping with a warning; migration `0033` (frozen; its INSERTs only hit empty tables); the other five seeders in the file (fixed catalog codes, longest `CR-ENV-BATTERY-ROOM` at 19 characters); an `A-B`/`A_B` collision in the unchanged short path (pre-existing); the backlog closure (a separate `docs(backlog):` PR).

## Facts the plan rests on

- Line 604 is the only producer of the ladder code; no consumer parses it (`tests/rule-vocabulary.test.ts:323` reads migration 0033's text).
- Idempotence keys on the condition tuple `(asset_id, point_key, operator, threshold_value)` (lines 579–600), not on the code.
- `upsertRuleByCode` compares `rule.code.trim().toUpperCase() === code`, so the hash segment is uppercase hex.
- Charset: migration `0070_catalog_code_charset.sql` puts `CHECK (code ~ '^[A-Za-z0-9_-]+$')` on `bms.assets`, so every code the ladder reads is ASCII; `slice()` on code units is exact (the `F4.104` surrogate lesson does not apply). The helper docblock cites `0070`.
- Arithmetic: the template is `7 + n + s` long; it fits iff `n + s <= 57`. The overflow shape `ESKOM_<cut>_<8 hex>_<suffix>` is `16 + k + s` long, so `k = 48 − s` fills 64 exactly.
- `packages/db` has a vitest project (`src/**/*.test.ts`, no database). DB-backed seed tests live in `tests/*.integration.test.ts` with inline assertions, gated by `requireIntegrationDb`. Precedents: `tests/f3.68-point-key-headline-ranks-seed.integration.test.ts`, `tests/f3.67-site-control-room-views-seed.integration.test.ts`.
- `bms.assets` and `bms.automation_rules` are `FORCE ROW LEVEL SECURITY`; the seed runs as `bms_owner` inside `withOrganization` (`seed-tenant.ts:122`).
- Coverage `include` does not cover `packages/db`; thresholds do not move.

## Decisions (the plan's three open questions, settled at build)

- **D1 — hash the raw asset code**, before the `-`→`_` fold, so `A-B…` and `A_B…` overflow to different rule codes. *Corrected at review:* case 9's fixture holds no `-`, so it pinned only the "full" half; `assertAHyphenAndAnUnderscoreDiffer` (added after review) pins the "raw" half.
- **D2 — the overflow fills 64 exactly**: keep as much of the asset code as fits. Case 4 pins it.
- **D3 — export `ESKOM_LADDER_RULES`** itself, so the spec iterates the five real suffixes. `packages/db/src/index.ts` does not re-export the module, so no public surface changes.

## Tasks

### Task 1 — unit spec pair (red)

Create `packages/db/src/automation-rules-seed.spec.ts` (exported `assert…` functions, one claim each, no vitest import) and `packages/db/src/automation-rules-seed.test.ts` (one `it` per function; model `pue-demo-seed.test.ts`). Fixtures: `A40`, `A41`, `A42` (`"A".repeat(n)`), `LONG60 = "F4129-" + "X".repeat(54)`, `P60 = "P".repeat(60)`, `P61A = P60 + "A"`, `P61B = P60 + "B"`.

1. `assertAShortCodeIsUnchanged` — `("ESK-MANUAL-01","PF_LOW") → "ESKOM_ESK_MANUAL_01_PF_LOW"`, `("UPS-A","DEMAND_HIGH") → "ESKOM_UPS_A_DEMAND_HIGH"`.
2. `assertTheBoundaryFitsUnchanged` — `A41` + `VOLTAGE_CRITICAL` equals the raw template, length 64. Reddens `<=` → `<`.
3. `assertOneBelowTheBoundaryFitsUnchanged` — `A40` → raw template, length 63.
4. `assertAnOverflowFillsTheBoundExactly` — `A42` → length `=== 64`.
5. `assertTheOverflowShape` — matches `/^ESKOM_A{32}_[0-9A-F]{8}_VOLTAGE_CRITICAL$/`.
6. `assertTheCutIsDeterministic` — two calls on `LONG60` are `===`.
7. `assertTwoLongCodesWithACommonPrefixDiffer` — `P61A` vs `P61B` differ.
8. `assertEverySuffixStaysInsideTheBound` — `ESKOM_LADDER_RULES.length === 5`; for each rule with `LONG60`: length 64, ends `_<suffix>`, starts `ESKOM_<folded LONG60 cut to 48 − s>_`; the five results are pairwise distinct.
9. `assertTheHashIsOfTheFullCode` — `P61A` + `PF_LOW` contains the first 8 uppercase hex of `sha256(P61A)`.

Both files land in one commit (`tests/repo-invariants.test.ts` requires the wrapper).
