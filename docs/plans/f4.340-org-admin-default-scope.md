# F4.340 — a new organization admin gets its organization's scope

> **For agentic workers:** this plan follows the `superpowers:writing-plans`
> format. Build it unit by unit under TDD (red test first, then the code).
> **ADR 0128 is accepted, and the owner said "yes" to this plan on
> 2026-11-11. The build is recorded at the end.**

**Row:** `F4.340` (P1 defect) in `docs/BACKLOG.md`.
**Base:** `main` at `9c8c6f1`.
**ADR:** [ADR 0128](../adr/0128-organization-admin-home-organization-grant.md)
(Accepted 2026-11-11; all six questions ruled as recommended). It is needed because the fix changes what ADR 0089 decision 3's
create transaction writes and decision 14's "one audit event per write".
**Goal:** an `organization_admin` created (or promoted) on Users & Access can
sign in and see its organization's sites with no manual Grants step; a scoped
role created without a grant is warned about, not silently left empty.

---

## 1. Root cause (verified against source)

| Where | What it does |
|---|---|
| `apps/api/src/admin/users/users.service.ts:389-404` | `create` inserts the `bms.users` row (with `organizationId`) and one `master.user.create` audit row. **No grant is written.** |
| `apps/api/src/admin/users/users.service.ts:473-492` | `update` can change the role to `organization_admin`; also writes no grant. |
| `apps/api/src/auth/access-scope-sources.ts:59-66` | `directOrganizationIds` reads only `bms.user_organization_access`. |
| `apps/api/src/auth/access-control.service.ts:216-217` | `writableOrganizationIds` for `organization_admin` = `directOrganizationIds` → `[]`. |
| `apps/api/src/auth/access-control.service.ts:245` | `writableLocationIds` → `[]` for the same reason. |
| `apps/api/src/auth/access-scope.ts:92-93` + `access-scope-sources.ts:152` | read scope source is only `"organization"`; with no grant it yields no locations and no assets. |
| `apps/api/src/admin/users/users.service.ts:691` | `requireManager` uses `writableOrganizationIds`, so the new admin cannot manage users either. |
| `apps/web/src/pages/control-room/organizations-page.tsx:82` | renders "No sites in your access scope". |

`bms.users.organization_id` is read for scope nowhere. So the defect is a
missing write, not a wrong read.

**The reproducing test (written first in U1, red on `main`):** in
`apps/api/src/admin/users/users.integration.spec.ts` (+ its `.test.ts`
runner), create an `organization_admin` through `UsersService.create` with a
fake `IdentityAdminClient` and `organizationId = X`; then, as that user,
`AccessControlService.writableOrganizationIds` returns `[]` and
`readableLocationIds` returns `[]` while organization `X` has active
locations. After the fix both contain `X` / `X`'s locations.

## 2. Options and recommendation

| Option | Change | Verdict |
|---|---|---|
| **A. Server writes the home grant on create (and promotion)** | `users.service.ts` only; same transaction; audited | **Recommended** (ADR 0128 Q1) |
| B. Home organization is an implicit scope | `directOrganizationIds` and ~6 readers | Rejected: wide blast radius; a revoked home grant would stop working, against the F3.78 ruling "a grant an admin removed stays removed" |
| C. The wizard sends `POST …/grants` after create | web only | Rejected: two requests, a failed second call leaves the defect; the copilot `user.create` path misses it |

Option A needs no migration, no new grant or policy: create already runs in
`withTenant(home)` (`users.service.ts:767` `inExecutor`), and the `0040`
`tenant_isolation` policy on `user_organization_access` admits a row whose
`organization_id` is the GUC organization. The caller's own scope check on
the home organization (`users.service.ts:344-349`) already holds, so the
grant widens nothing.

## 3. Units (tests first in each)

### U1 — API: create and promotion write the home grant (ADR 0128 decisions 1–3)

Files:
- `apps/api/src/admin/users/users.service.ts` — in `create`, when
  `body.role === "organization_admin"`, inside the existing `inExecutor`
  callback after `insertUserRow`: insert
  `user_organization_access (user_id, organization_id)` and write a
  `master.user_grant.add` audit row (`payload: { userId, kind:
  "organization", targetId, reason: "home_organization" }`). In `update`, when
  `newRole === "organization_admin"` and the role changes, insert the same row
  `ON CONFLICT DO NOTHING` and audit only when a row was inserted.
- Reuse `insertGrant` from `user-grants.service.ts` (export it if needed) —
  do not copy the SQL.
- Keep the file under the §4.5 1000-line cap; if it crosses, move the helper to
  a small `home-organization-grant.ts`.

Tests (red first):
- Unit `users.service.spec.ts`: create `organization_admin` → grant insert +
  two audit rows in one executor call; create `operator` → no grant; a grant
  insert failure rolls back and runs the Keycloak undo (existing path);
  promotion to `organization_admin` → grant; promotion when the row exists →
  no duplicate, no extra audit; demotion → grant kept.
- Integration `users.integration.spec.ts` (real RLS, tenant pool): the
  reproducing test from §1; the grant row lands under `bms_tenant` with the GUC
  set to the home organization; a forced grant failure leaves no user row and
  no audit row; the new admin passes `requireManager` and lists users of its
  organization.
- Integration `access-control-rls.integration.spec.ts` or
  `multi-org-scope.rls.integration.spec.ts`: after create, `readableLocationIds`
  (which goes through the private `scopeForUser`) returns X's active locations and nothing from another organization.

### U2 — Shared contract: `hasEffectiveGrant` on the user DTO (ADR 0128 Q6)

- `packages/shared/src/contracts/users.ts` — add
  `hasEffectiveGrant: z.boolean()` to `adminUserDtoSchema`.
- `users.service.ts` list query — compute it on `bms_fleet` per row with
  `selectReadScopeSourceFor` semantics (the same rule as the grants DTO
  `effective`, `user-grants.service.ts:234-269`), `true` for `admin`. One
  query, not one per row.
- Tests: contract spec; unit for each role with and without grants.

### U3 — Web: Review warning and Users-list flag (ADR 0128 decision 4)

- `apps/web/src/components/admin/user-wizards.tsx` — Review step:
  for `organization_admin`, one line "Gets access to <organization> on
  create"; for `location_admin`, `asset_group_admin`, `operator`, `viewer`,
  a warning "This user will see nothing until you add a grant."
- `apps/web/src/pages/admin/users-page.tsx` — a "No access" badge on an
  active row with `hasEffectiveGrant === false`.
- Tests: `users-page-wizards.spec.tsx` and `users-page.spec.tsx` assert the
  exact strings (jsdom), per role.

### U4 — Runbook: one-off backfill for existing users (ADR 0128 Q5)

- `docs/runbooks/keycloak-user-administration.md` — a new section:
  1. a read-only listing query (active `organization_admin` with no
     `user_organization_access` row: id, email, home organization);
  2. the fix is the Grants drawer in the UI (audited), not SQL — so there is
     no direct-write command to misuse.

**Why not a migration:** a migration runs on every host and would re-add a
home grant an admin removed on purpose, against the F3.78 owner ruling; it
also cannot write a real actor into the audit row. On AWS the one known case
(`bcpl-admin`) was already fixed by hand, so the listing is expected to be
empty; the owner runs it once after deploy.

## 8. Build record (2026-11-11)

Built in the same pull request as this plan, after the owner's "yes".

**Units.** U1–U4 as planned. The §1 reproducing test (create an
`organization_admin`, read its scope) failed on `main` with `[]` and passes
after U1.

**Where the build departs from the plan:**

1. **U1 — the grant insert is not `insertGrant`.** `insertGrant`
   (`user-grants.service.ts`) throws on an empty `RETURNING`, so it cannot say
   "skip a held grant". `home-organization-grant.ts` writes its own Drizzle
   insert with `ON CONFLICT DO NOTHING` on `(user_id, organization_id)`, the
   `user_organization_access_user_org_unique` index. No SQL is copied.
2. **U1 — the scope readers in the reproducing test.** It calls
   `directOrganizationIds` and `scopeFromSource(…, "organization")` on the
   rollback transaction, not `AccessControlService`, because the service reads
   through its own pool. The two are the same rule while
   `readScopeSourcesForRole("organization_admin")` is `["organization"]`.
   A forced-grant-failure rollback is covered by the unit suite only.
3. **U2 — a list-row schema, not a field on the user DTO.**
   `adminUserListItemSchema = adminUserDtoSchema.extend({ hasEffectiveGrant })`
   (ADR 0030): only the list needs it, so the write responses keep the plain
   DTO.
4. **U2 — what "in effect" means.** A grant counts when it reaches an active
   location, the same rule as `readScopeSourceYields` and the Grants drawer's
   `effective`, computed for all listed users in one `UNION` query on
   `fleetDb`.
5. **U3 — the Grants drawer refetches the users list** after an add or a
   remove, so the "No access" pill follows the grants (code review).

**Tests.** Unit (`users.service.spec.ts`: create, promotion, demotion from
`admin`, an `organization_admin`'s promotion, failure undo, list flags);
integration on the real pool roles (`users.integration.spec.ts`: create,
promotion, held grant, demotion, list flags per grant kind and the
active-site rule); shared contract; jsdom (Review note per role, the pill,
the drawer refetch). Mutations checked: removing the drawer's refetch, renaming
the `asset_group` kind, and dropping the active-site join each fail a test.

**Reviews.** `security-reviewer`: no critical, high or medium findings; its

closure items.
