# F4.107 — bound the draft forwarded to the model

**Provenance.** Written on Fable (`claude-fable-5-1`) as the step-3 plan for
backlog row `F4.107`, and revised once after the dispatching session measured the
merge expression at `onboarding-chat.service.ts:702–713` and found this plan's
first flag wrong (§0). The numbers in §1's size table come from this plan's own
fixtures, except the 0.40 MB live upload figure, which is the dispatching
session's measurement against `bms-api-1`.

Two owner rulings stand and are not re-opened: **(1)** build it, re-scoped to the
measured ~0.7 MB per turn; **(2)** when the forward budget is exceeded, shed
values and keep the JSON valid — the four free-form records first, then
over-long strings — with every code, name and protocol kept. The six decisions
this plan owed are recorded in §8.

---

## 0. Correction to the first draft of this plan — `location.meta` is replaced on merge, not accumulated

The first draft of this plan claimed the forwarded payload grew without limit
across turns through `location.meta`, and argued the budget partly from that.
**The claim was wrong, and it is recorded here because `docs/BACKLOG.md`'s
`F4.116` row currently makes the same claim and will be corrected against this
document.**

What was measured, by replicating the merge expression at
`onboarding-chat.service.ts:702–713` verbatim and running ten 100,000-byte
PATCHes through it per shape:

| Shape | After ten patches | Behaviour |
|---|---|---|
| `location.meta`, same key | 100,032 B | replaced |
| `location.meta`, distinct keys | 100,033–100,042 B | replaced |
| `onboardingMeta`, same key | 100,029 B | replaced |
| `rtus` | 100,085 B | replaced wholesale |
| a patch omitting `meta` | keeps the stored one (100,041 B) | kept, not grown |
| a patch sending `meta: {}` | 24 B | shrinks it |
| `location.<new top-level key>` | 1,000,105–1,000,134 B | **accumulates — schema-unreachable** |
| `onboardingMeta`, distinct keys | 1,000,120 B | **accumulates — schema-unreachable** |

`{ ...base.location, ...patch.location }` spreads one level, so a patch carrying
`meta` replaces the whole object; distinct keys inside `meta` do not help,
because `meta` is a single key of `location`. The two shapes that do accumulate
cannot be reached: `draftLocationSchema` (`onboarding.schema.ts:48–67`) has
neither `.strict()` nor `.passthrough()`, so zod strips an unknown top-level
location key; `onboardingDraftMetaSchema` (`:145–150`) is a closed three-field
object and its docblock at `:213–221` says so — *"it is a closed three-field
object and cannot nest."* The rule-based chat branch and the workbook upload
write fixed shapes and no free keys. The first draft's fixture F was a ten-key
`meta` object built by hand; it never ran the merge.

**Conclusion: no field accumulates across turns through any parsed path.** The
forwarded payload is bounded per turn at the producer-reachable ~0.68 MB (§1,
fixture D), which is what the row and ruling 1 already say.

What survives of the flag: **this row's cap is still the only size bound on the
prompt.** `F4.103`, `F4.104` and `F4.115` bound the draft's parts — item count,
string length, depth — and nothing measures the serialised whole before it is
embedded at `:294`. The per-turn ceiling is a consequence of those three bounds
meeting a 102,400-byte body limit, not a check anything performs.

Two smaller corrections to the brief this plan was written against, both
immaterial: one 102,400-byte body holds 239 max-width asset points under the
`{"draft":{"assetPoints":[…]}}` envelope, not 238; and a synthetic at-caps upload
with every cell at its column width is 473,816 B (0.45 MB) rather than the live
0.40 MB, because the synthetic fills `domain`, `rtuCode`, `stationCode` and
`stationName`, which the upload never writes. The live figure stands.

## 1. Goal

Bound the bytes of draft context that `handleOpenAiTurn` embeds in the system
prompt on every turn. Today
`Draft context (redacted): ${JSON.stringify(redactDraftForLlm(draft))}`
(`apps/api/src/admin/onboarding/onboarding-chat.service.ts:294`) forwards the
whole redacted draft: up to ~0.68 MB per turn at the caps, **bounded per turn**
by the producers' own limits and re-sent on every turn, with no check on the
serialised size anywhere. When the serialised draft exceeds a budget, shed values
in a fixed order — the four free-form records (`rtus[].config`, `rtus[].meta`,
`assets[].meta`, `location.meta`), then strings longer than any code/name column
— replacing each with one fixed marker, so the JSON stays valid and every code,
name and protocol survives (ruling 2). The walk is iterative and is
`rebuildDeep`, not a fourth traversal (`F4.115`, §4.8).

**Sizes measured for this plan** (`Buffer.byteLength(JSON.stringify(draft))`,
built from `ONBOARDING_DRAFT_STRING_MAX` and the `F4.103` caps; node v24.17.0 —
byte counts do not move with the runtime):

| Fixture | Bytes | Reading |
|---|---|---|
| A — the shipped template (2 RTUs, 3 assets) | 1,108 | what an operator is handed |
| **B — demo estate, 10 RTUs / 99 assets / 40 point keys / 495 asset points, realistic strings** | **71,035 (69.4 KiB)** | **the floor** |
| E3 — upload at both caps, realistic cells | 81,336 (79.4 KiB) | a large legitimate upload |
| C — upload at both caps, every cell at its column width | 473,816 (462.7 KiB) | the live figure is 0.40 MB; see §0 |
| D — C + one PATCH body of point keys (40) + one of asset points (239) | 678,062 (662 KiB) | **the row's "~0.7 MB per turn" — the per-turn producer maximum** |
| F — ten 100 KB values in one `location.meta` | 1,000,830 | **not producer-reachable.** Built by hand, not by the merge: one PATCH of this size is refused by the 102,400-byte body limit, and across PATCHes `mergeDraft` replaces `meta` (100,042 B measured after ten). Retained only as the magnitude the one-level spread would reach if `draftLocationSchema` ever gained `.passthrough()` — 1,000,105 B measured with the schema bypassed (§0) |
| G — 20,000-deep `rtus[0].config` (`F4.115` fixture) | ~180,022 | `JSON.stringify` throws at 4,174 in `bms-api-1` |
| E — all four arrays at caps, realistic, nothing shedable | 692,056 | not producer-reachable (≤ ~1,000 asset points per body); the *shape* of the residual in §3.5 |
| one max-width point key / asset point | 2,539 / 427 | 40 / 239 fit one 102,400-byte body |
| the marker `[omitted: over prompt budget]` | 31 | |

**Out of scope, explicitly:** bounding `location.meta` or any `z.record` field by
key count at its write site (`F4.116`, whose premise §0 corrects); logging in the
`catch {}` at `:270`; the rule-based branch (untouched, and the only branch the
running stack executes); the raw user turn going to OpenAI unredacted (ADR 0022
gap 4, a different row); any API response contract — nothing here reaches a
client, so §4.8 / ADR 0030 does not apply.

## 3. Decisions this plan owes

### 3.1 Where the cap lives — a new module, returning the JSON text

`apps/api/src/admin/onboarding/onboarding-prompt-budget.ts`, exporting
`serialiseDraftForPrompt(draft: unknown): string`. The chat service embeds the
returned string at `:294`.

Why a string and not an `OnboardingDraft`: the budget is measured on serialised
bytes, so the function must `stringify` to decide; returning the text avoids a
second `stringify` at the call site and gives the honest type. A shed draft is
**not** an `OnboardingDraft` — `rtus[].config` becomes a `string` where the type
says `Record<string, unknown>`, and `location.meta` likewise. Returning
`OnboardingDraft` would need a cast that lies at exactly the field the row is
about. `redactDraftForLlm` keeps its contract and its assertions; it gains one
caller (this module) and loses one (the chat service).

Why a new file: `onboarding-redaction.ts` is 438 lines and its spec 592; the
derivation docblocks and ~9 assertion functions here are ~170 + ~420 lines.
`onboarding-draft-caps.ts` is the precedent for "the number, its derivation and
its sentence live in their own module".

### 3.2 The traversal — `rebuildDeep` with one minimal extension

Stage 1 (records) needs only the existing key visitor:
`(key) => key === "config" || key === "meta" ? { value: MARKER } : null`. It
matches at any depth; for a schema-shaped draft that is exactly the four fields
(no other `config`/`meta` key exists — `onboardingMeta` is a different name), and
for anything else it sheds more, never less, which is the safe direction under
§4.3.

Stage 2 (long strings) decides on a **value**, which `KeyVisitor` cannot see. The
minimal shared extension: an optional fourth parameter `visitLeaf?: LeafVisitor`
where `type LeafVisitor = (value: unknown) => { value: unknown } | null`,
consulted for every non-container child in **both** branches (array elements
included — a string in an array is a value, not an index, so the `KeyVisitor`
docblock's "object keys only" stays true). It runs after the key visitor declined
and after the container check; a bare non-container root is returned unvisited,
as today. `cloneJson` and `scrubSecrets` pass nothing and are byte-for-byte
unchanged.

`isJsonContainer` (`stack-safe-json.ts:111`) is exported for this third consumer.
The shed's input is always post-scrub plain JSON, so the JSON-only predicate is
the right one; the "two predicates stay different" pair tests are untouched.

### 3.3 Order of operations, and why depth comes first

```
1. redacted = redactDraftForLlm(draft)                         // iterative already
2. if exceedsDepth(redacted, MAX_ONBOARDING_DRAFT_DEPTH): redacted = shedFreeFormRecords(redacted)
   // stringify's own ceiling is 4,173 on node v20.20.2 in bms-api-1 (F4.115); the four
   // records are the only fields that can carry depth, so shedding them makes the
   // ruler safe to apply. Without this the budget cannot be measured on the draft
   // that most needs it, and the RangeError is swallowed by the catch at :270.
3. json = stringify(redacted); if byteLength(json) <= BUDGET: return json
4. redacted = shedFreeFormRecords(redacted); json = stringify; if under: return json
5. redacted = shedOverLongStrings(redacted); return stringify(redacted)   // see §3.5
```

The input to step 1 is bounded per turn at ~0.68 MB by the producers; the steps
exist because that bound is a consequence of three per-field limits, not a
measurement anything makes on the serialised text. Whole-stage, not per-value
(decision 3): minimal shedding would show the model RTU-1's config and not
RTU-2's depending on key order, which is arbitrary and unexplainable. Three
stringifies of ≤ 0.7 MB is milliseconds.

### 3.4 The three numbers

**`PROMPT_DRAFT_BUDGET_BYTES = 262_144` (256 KiB) — decision 2.**

- *Floor — 69.4 KiB (B).* A session's estate at the demo's scale with every array
  populated and realistic strings: the two anchors `F4.103` used (template, demo
  estate), applied to bytes. Task 0 re-measures it through the real producers.
- *Bound — 256 KiB.* 3.8× the floor; 2.5× one 102,400-byte body, the largest
  single write any producer makes, so an at-caps upload with realistic cells
  (79 KiB) plus one body of mappings fits without a shed.
- *Ceilings, for contrast — two, and both are per-turn.* **678,062 B** (D): the
  producer-reachable maximum one turn can forward, reached only with every
  workbook cell at its column width plus one body each of point keys and asset
  points; the bound sits 2.6× below it. And the model's context window — 128k
  tokens for the default `gpt-4o-mini`, a property of `OPENAI_MODEL` and asserted
  by nothing — roughly 350–450 KB of JSON, above which OpenAI refuses the request
  and the `catch {}` degrades the turn to rule-based silently. The bound sits
  below that window with room for the reply. A consequence worth stating: a draft
  at D cannot reach the model at all today, so on such a draft the shed does not
  only bound the forward, it is what makes the LLM turn answer.

**The 128 KiB alternative, considered and declined.** What it would buy: 128 KiB
less per turn of secret-scrubbed opaque data forwarded unshed (2.5 bodies' worth
becomes 1.25), and roughly 35k fewer tokens at the worst under-budget case. What
it would cost: a legitimate estate between ~130 KB and ~250 KB — an at-caps
realistic upload plus one body of mappings is ~180 KB — loses `config` (host,
port, topic) from the prompt in the `rtu` phase, a functional loss with no
security gain since `config` is already secret-scrubbed. Under a per-turn ceiling
of 678 KB either number is a real bound; 256 KiB is the one that does not shed a
legitimate estate. This paragraph goes in the constant's docblock so a later
reader sees the trade.

**`PROMPT_STRING_MAX = 255`** — the widest code/name column in
`ONBOARDING_DRAFT_STRING_MAX`; only `pointKeys.description` (2,000) is wider, and
it is opaque operator data under ruling 2 — neither a code, a name nor a protocol
(decision 4). Counted in UTF-16 code units, the unit `.max()` uses (`F4.104`).
Pinned by an assertion, not derived by filtering the record — see Task 2.

**`PROMPT_OMITTED_MARKER = "[omitted: over prompt budget]"`** — a fixed literal.
§4.3: no key, no size, no fragment of the value it replaces.

### 3.5 The residual — option (a), the owner's ruling (decision 1)

After both stages, what remains is codes, names and protocols, and the rulings
shed none of it. A draft of those alone reaches 678 KB at the caps with max-width
cells (D) and ~280 KB with realistic ones (E3 plus two bodies). **The budget is
therefore a shedding threshold, not a hard limit,** and the docblock says so with
these numbers. `serialiseDraftForPrompt` returns the shed JSON even when it is
still over budget — valid, untruncated — and
`assertAResidualOverBudgetPayloadIsValidJson` pins that it neither throws nor
cuts. What this leaves open, stated in the docblock rather than implied: **a
hostile draft of 255-character names still forwards in full** — 600 such
`displayName`s are "names the model reasons about" by the ruling's letter, and
go. The declined alternatives were returning `null` to take the rule-based branch
(a hard cap, but it removes a working LLM turn for any estate between the budget
and the model's window) and a third stage shedding array items (contradicts
ruling 2).

### Task 3 — the call site, and the assertion on what is forwarded

**Modify** `onboarding-chat.service.ts`: `:25–29` import
`serialiseDraftForPrompt` from `./onboarding-prompt-budget` and drop
`redactDraftForLlm`; `:294`
`Draft context (redacted): ${serialiseDraftForPrompt(draft)}`. Kept
(decision 6): one sentence in the prompt at `:293` — *"A value shown as [omitted:
over prompt budget] was withheld; do not copy it into draftPatch."* Without it a
model echoing `config: "[omitted…]"` fails `onboardingDraftSchema.safeParse` (a
string is not a record) and the whole turn is dropped silently — the producer-3
discard `onboarding.schema.ts:266–276` rules acceptable, but this would be a new
way to reach it.

**The review added a control beside that sentence, and it does not re-open
decision 6.** An instruction is not a control, and the case decision 6 argues is
the *harmless* one: an echoed `config: "[omitted…]"` is a string where `z.record`
is required, so the parse refuses it. Measured against the compiled schema, the
