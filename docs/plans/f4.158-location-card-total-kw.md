# F4.158 — a location card's Total kW must not multiply over the RTU and alarm joins

Plan by the session, 2026-09-25 (owner ruling the same day: a short plan, no
`plan-architect` dispatch, for an effort-1 row). No ADR (owner-gated
2026-09-25): a defect inside the existing `LocationKpiSummary` contract, with no
scope, dependency or schema change. ADR 0075 decision 2 kept `total_kw`
unchanged for `F3.30` only.

## Goal

`DashboardService.locationKpis` (`apps/api/src/dashboard/dashboard.service.ts`)
computes `COALESCE(SUM(latest.kw), 0)` over `bms.locations` LEFT JOIN
`bms.rtus` LEFT JOIN `bms.assets` LEFT JOIN `bms.alarms`. Each asset's latest
`kw` is summed once per RTU at the location times once per alarm row on the
asset. The counts beside it survive only because they are `COUNT(DISTINCT …)`.

Measured on the shared dev database 2026-09-25 before the fix (card against
the per-asset sum): CSMOC Gauteng 35,441.5 against 294.0; RSMOC KwaZulu-Natal
42,174.9 against 157.1; every two-RTU site with no alarm exactly 2×.

`locationDashboard` spreads the same card, and the web's
`location-kpi-groups.ts` sums the cards into the organization header, so both
take the fix with no change of their own.

**Out of scope.** `latest` stays unbounded in time (ADR 0075 decision 2: a
stale `kw` still sums). No contract, web, migration or AGENTS.md change.
`kpis.totalKw` (`kw_latest`) already sums one row per asset and is not touched.

## Fix

Pre-aggregate `kw` per location in a CTE, before the joins:

```sql
kw_by_location AS (
  SELECT a.location_id, SUM(latest.kw) AS total_kw
  FROM bms.assets a
  INNER JOIN latest ON latest.asset_id = a.id
  WHERE ($2::uuid[] IS NULL OR a.id = ANY($2::uuid[]))
  GROUP BY a.location_id
)
```

`LEFT JOIN kw_by_location kl ON kl.location_id = l.id`, read as
`COALESCE(MAX(kl.total_kw), 0)` — one row per location, so `MAX` is that row.
The outer `LEFT JOIN latest` goes. **The CTE carries the same asset predicate
as the outer `bms.assets` join** (`location_id` plus the `$2` scope), so
`totalKw` and `assetCount` describe one asset set; without `$2` the card sums
assets outside the caller's scope and no count shows it.

Rejected: `SUM(DISTINCT latest.kw)` removes the fan-out but merges two assets
with equal readings.

## Tests first (the `F3.30` freshness integration spec, rolled-back transactions)

1. **No fan-out.** Two RTUs at one location; asset X on RTU 1 and asset Y on
   RTU 2, each `kw = 21`; two alarms on X (one open, one cleared). Expect
   `{ totalKw: 42, rtuCount: 2, openAlarms: 1 }`. Today: 126. `SUM(DISTINCT)`
   and `MAX` give 21, so the one assertion also rejects both wrong fixes.
2. **Scope.** An in-scope asset `kw = 42` and an out-of-scope asset
   `kw = 100` at the same location, `assetIds` = the in-scope one. Expect
   `totalKw` 42. Mutation: remove the `$2` predicate from the CTE → 142.

Update the spec's docblock: its *Fan-out* paragraph says a second RTU would
double `totalKw`, which stops being true.
