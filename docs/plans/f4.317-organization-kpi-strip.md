# F4.317 — plan: an organization KPI strip from the template system

Draft, 2026-11-06, against `main` `a2ec5a4d`. **Step 2 (scope gate) is open.** This
plan needs a new ADR (proposed number 0112) before any build. Nothing here is
built, and nothing merges before the owner accepts the ADR and says "yes" to this
plan.

## 1. Goal

The organization level of the Control Room, `/control-room/org/:organizationId`,
shows a KPI strip at the top, like the estate level does, but scoped to that
organization. The strip comes from a template: every organization gets a default
strip with no admin action, and an organization admin can change its own strip
later through the template and the dashboard builder.

Today the page shows only `LiveStatusStrip` (live / not-live site counts,
`F4.259`). The estate shows four `KpiTile`s: Total load, Sites online, Open
alarms, PUE (`apps/web/src/pages/dashboard-page.tsx:137-187`).

**Out of scope.** The estate strip stays coded (it spans organizations, and a
template belongs to one organization). The rest of the organization page (map,
site groups, alarms rail, health, load trend, dashboard list) stays coded. The
site level is not changed.

## 2. Facts measured from the code

- **The estate strip reads one coded endpoint.** `useExecutiveDashboard`
  (`apps/web/src/hooks/use-executive-dashboard.ts`) polls `GET /dashboard/kpis`
  every 4 s and sums live `kw` from the telemetry socket. The controller passes
  `readableAssetIds(user)` (`apps/api/src/dashboard/dashboard.controller.ts:27-30`);
  `DashboardService.kpis(assetIds)` (`dashboard.service.ts:461`) returns
  `totalKw`, `sitesOnline`, `sitesTotal`, `alarmsOpen`, `alarmsCritical`,
  `pueEstimate` and `prior` (24 h back, ADR 0074 decision 5). Contract:
  `dashboardKpisSchema` (`packages/shared/src/contracts/dashboard.ts:123`).
- **An organization scope for that read already exists.** `GET /dashboard/load-trend`
  takes `organizationId` and uses
  `accessControl.readableAssetIdsInOrganization(user, organizationId)`
  (`dashboard.controller.ts:72-80`). The same intersection can feed `kpis()`.
- **"Sites" means two different things today.** `kpis()` counts
  `DISTINCT bms.assets.site_name` (`dashboard.service.ts:511-513`). The
  organization page counts `LocationKpiSummary` rows from
  `GET /dashboard/locations` (`organization-page.tsx`, `splitByLiveTelemetry`).
  The estate shows "4 / 17" while its organization cards hold 10 + 6 = 16 sites.
  An organization strip that reuses `kpis()` as it is can disagree with the
  "6 sites" in its own header.
- **Templates have two targets.** `bms.dashboard_templates.target` is
  `'asset_group' | 'site'` (`dashboardTemplateTargetSchema`,
  `packages/shared/src/contracts/dashboard-templates.ts:333`; ADR 0087
  Amendment 1 ruling Q3a). Templates are per organization (`organization_id`
  NOT NULL), versioned, published, stock-importable, and stamped on the copy
  (`dashboards.template_id`). **No organization target exists.**
- **An organization-wide dashboard already exists as a shape.** A `bms.dashboards`
  row with `location_id` and `asset_group_id` both NULL is organization-wide
  (`dashboards.service.ts:212`, `dashboards-list-location.integration.test.ts:157`).
  The metric catalog resolves its widgets over the organization's assets,
  intersected with the caller's readable set (`metric-catalog.service.ts:69-73,
  136`).
- **The site level has a pointer table; the organization level has none.**
  `bms.site_control_room_views` (one row per location: `kind`, `dashboard_id`,
  `builtin_key`) tells the site page which dashboard to draw. There is no
  equivalent for an organization.
- **The metric catalog is closed and held by a database CHECK.**
  `metricCatalogKeySchema` (`dashboard-builder.ts:641`) has ten keys; migration
  `0096` holds the same list in `dashboard_widget_sources_catalog_key_check`.
  A new key is a migration (the `0079`, `0081`, `0096` precedent).
- **What the catalog can already give at organization scope:**
  `alarms.active.count`, `workorders.open.count`, `assets.health.score`,
  `assets.offline.count`, `sustainability.total` (`{pointKey, aggregate}`, with
  `coverage {fresh, carrying}`), and the dataset `water.balance`.
- **What it cannot give:** sites live / total, PUE, a critical-only alarm count.
  `value_tile.compareToPrevious` exists, but I did not confirm that the catalog
  resolver computes a prior value for a catalog source (the readers found are
  in `apps/web/src/lib/widget-value.ts` and `dashboard-widget-data.ts`). Step 3
  must confirm this before it promises a "vs yesterday" line on a catalog tile.
- **Point keys that exist in the seed:** `kwh_today`, `kl_today` (15 uses),
  `kl_this_month`, `run_hours_h`, `flow_klh`. I did not count which PHEWB assets
  carry `kwh_today` against the live database. The `coverage` field labels a
  partial roll-up, so a partial value is never shown as a whole one.

## 3. The KPI set

Row 1 is the estate's four tiles, scoped to the organization. Row 2 holds the
organization tiles. Each tile names its source. A tile with no data shows "—"
and the reason, as the estate PUE tile does today (`pueTileProps`).

| # | Tile | Value | Sub-line | Source |
|---|---|---|---|---|
| 1 | Total load | Σ latest `kw`, kW | vs yesterday | `sustainability.total {kw, sum}` |
| 2 | Sites live | live / total locations | "reporting in the last ~150 s" | **new** `sites.live.count` (value + `coverage`) |
| 3 | Open alarms | count | vs yesterday · "N critical" | `alarms.active.count` + **new** param `tone: "critical"` |
| 4 | PUE | Σ `site_kw` / Σ `it_kw` | "Not configured …" when null | **new** `pue.ratio` |
| 5 | Energy today | Σ `kwh_today`, kWh | coverage "x of y assets" | `sustainability.total {kwh_today, sum}` |
| 6 | Water today | Σ `kl_today`, kL | coverage | `sustainability.total {kl_today, sum}` |
| 7 | Assets offline | count | of N assets | `assets.offline.count` |
| 8 | Asset health | score | — | `assets.health.score` |
| 9 | Open work orders | count | — | `workorders.open.count` |
| 10 | Energy cost today | Σ `energy_cost_today`, org currency | coverage | `sustainability.total {energy_cost_today, sum}` |
| 11 | Water cost today | Σ `water_cost_today`, org currency | coverage | `sustainability.total {water_cost_today, sum}` |
| 12 | Energy cost this month | Σ `energy_cost_this_month` | coverage | `sustainability.total {energy_cost_this_month, sum}` |
| 13 | Water cost this month | Σ `water_cost_this_month` | coverage | `sustainability.total {water_cost_this_month, sum}` |
| 14 | Availability (24 h) | avg `availability_pct_24h`, % | coverage | `sustainability.total {availability_pct_24h, avg}` |

**Owner ruling 2 (2026-11-06):** all nine, plus the cost KPIs. Tiles 10–13 are
the cost tiles. The cost point keys carry unit `""` on purpose
(`packages/db/src/point-key-units.ts:728-731`, ADR 0070 decision 8): the
currency is the tenant's, so the tile reads `organizations.currency`
(`bms-schema.ts:49`) for its unit. Tile 14 is added because the point key
exists; it is in the open questions.

**Not proposed, because the data does not support them now:**

- **Worst site.** No catalog entry ranks sites. The site cards and the map
  already show each site's state. A new dataset key can come later.
- **Total cost (energy + water) on one tile.** `sustainability.total` takes one
  point key. One sum over two keys is a new catalog param. Tiles 10–13 give the
  parts.
- **Data freshness** as its own tile. Tile 2 (live / total) and tile 7 (assets
  offline) carry it. A third tile repeats them.

## 4. The template design

1. **A third target, `organization`.** `dashboard_templates.target` gains
   `'organization'`. Its content is the existing flat `widgets` list, with no
   `tabs` (an organization has no asset group to bind a tab to). The write
   schema refuses `tabs` on this target and refuses widget types other than
   `value_tile` in this phase.
2. **A stock template, "Organization standard"** (`stock_code`
   `organization-standard`), in `packages/shared/src/site-templates/` beside
   `smoc-standard.ts`, with the tiles of §3 as the owner rules them. It imports per organization
   through the existing stock import.
3. **The default needs no row.** With no organization view row, the page draws
   the strip from the stock content in `@bms/shared`, resolved through the
   catalog at organization scope. This is the fail-safe of ADR 0076 decision 5,
   one level up. So every organization, new ones too, gets the strip at once.
4. **A pointer table, `bms.organization_control_room_views`**
   (`organization_id` PK, `dashboard_id` ON DELETE SET NULL, `updated_at`,
   `updated_by`), FORCE RLS on own organization, the same shape as
   `site_control_room_views`. A row points the page at an organization-wide
   dashboard that was copied from a published `organization` template.
5. **How an organization changes its strip.** An admin edits the
   organization's `organization` template (draft → publish), then uses
   "Make organization layout" on the organization page. In one transaction the
   action copies the published template into an organization-wide dashboard and
   writes the pointer row. After that, the admin can edit that dashboard in the
   builder. "Reset to default" deletes the pointer row.
6. **Who may change it.** *Superseded by owner ruling 5 (§8): a
   `location_admin` may change it too. ADR 0112 decision 5 holds the rule.*
   The original proposal was: the roles that write dashboard templates and
   organization-wide dashboards today (ADR 0049, `F3.1d`): an organization
   admin of that organization and a global admin. A `location_admin` or an
   asset-group-scoped user may not: an organization-wide dashboard spans sites
   they cannot all read. Every user who can open the page can read the strip,
   and each tile resolves over that user's readable assets only.
7. **The renderer.** A new `OrganizationKpiStrip` replaces `LiveStatusStrip` on
   the organization page. It draws value tiles in the `KpiTile` style, four per
   row at `lg`, as the estate does. `LiveStatusStrip` is removed because tile 2
   carries the same two numbers.

## 5. Scope gates

**An ADR is needed (AGENTS.md §10, §9.4).** Proposed ADR 0112, "Organization
control-room layout from a template". It amends ADR 0087 (Amendment 1 ruling
Q3a: the target enum; decision 7: the fail-safe) and ADR 0048 (the closed
catalog). It records:

- a new template target (contract enum and, if one exists, the DB CHECK);
- a new table, `bms.organization_control_room_views` (migration, RLS);
- three catalog changes: keys `sites.live.count`, `pue.ratio`, and a `tone`
  param on `alarms.active.count` (migration of the catalog CHECK);
- new routes: `GET/PUT/DELETE /control-room/organizations/:id/view` (or the
  name step 3 picks), and the instantiate arm for `target: "organization"`;
- the "sites" definition for the strip: locations, as the organization cards
  count them.

No new dependency. §6 does not list this work. The build follows the owner's
standing rule: plan, then "yes", then build.

## 7. Verification (for step 3)

- Integration: each new catalog key at organization scope, intersected with a
  `location_admin`'s set (the strip of a scoped user counts only their sites).
- RLS: the pointer table refuses another organization's row (FORCE RLS legs).
- Web spec: no view row → the stock strip; a row → the copied dashboard; the
  "Sites live" tile agrees with the header's site count.
- Browser (DOM asserts, not screenshots): PHEWB shows "4 / 6" in tile 2, and the
  open-alarm count equals the header's alarm count.

## 8. Open questions for the owner (asked one at a time)

1. **Strip only, or the whole organization page from the template?**
   **Ruled 2026-11-06: strip only first, the whole page later** (a later row).
2. **Which tiles are in the default?** **Ruled 2026-11-06: all nine, plus the
   cost KPIs** (tiles 10–13 of §3).
2b. **Availability (tile 14) in the default too?** **Ruled 2026-11-06: yes.**
   The default is tiles 1–14.
3. **"Sites" means locations** (agrees with "6 sites" in the header), not
   `site_name`? This also asks whether the estate tile ("4 / 17") moves to the
   same rule. **Ruled 2026-11-06: locations, the estate tile too.** The estate
   "Sites online" tile moves to the location count in this row (expected
   "4 / 16"); `kpis()` changes, and the ADR records it.
4. **Default without a row** (stock content drawn at once for every
   organization), or a seeded copy per organization? **Ruled 2026-11-06:
   stock content, no row** (§4 item 3). PR 5's seed copies are then optional
   demo data only.
5. **Who may change the strip:** organization admin and global admin only?
   **Ruled 2026-11-06: also location admins.** This replaces §4 item 6's
   proposal. Consequence for the ADR and the build: today a `location_admin`
   cannot write an organization-wide dashboard (the `F3.1d` HIGH review fix,
   `dashboards.service.rls.integration.test.ts:578`). So the build needs a
   narrow grant: a `location_admin` of that organization may write the
   organization `organization` template, the organization view row and the
   dashboard the row points at, and nothing else organization-wide. The
   security reviewer must check that grant. The tiles still resolve over each
   viewer's readable assets, so the edit changes which tiles others see, not
   which data they can read.
6. **Does "vs yesterday" stay on Total load and Open alarms?** If the catalog
   resolver has no prior value for a catalog source, this adds a `prior` to the
   resolve response. **Ruled 2026-11-06: yes, add it if it is missing**, on the
   ADR 0074 decision 5 rule (the same instant 24 h back). Step 3 confirms the
   resolver first.
7. **Accept ADR 0112** as §5 describes, before the build plan? **Ruled
   2026-11-06: draft it.** Drafted as Proposed:
   `docs/adr/0112-organization-control-room-layout-from-a-template.md`.
   **Accepted by the owner 2026-11-06.** Step 2 is closed. The build waits for
   the owner's "yes" to the step-3 plan.
