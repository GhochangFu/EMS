## 1. Goal

Author the five electrical asset classes the tag list describes and `F2.13` did not ship — **transformer, DG set, UPS, solar PV, APFC** — as five more `StockAssetTemplateEntry` values in the electrical pack, so that every organization can import a real, complete class template through the mechanism `F2.13` built. Each entry declares its class table from `docs/electrical-derived-taglist-v1.md` as template points (`C` rows required and `meta.tier: "core"`, `X` rows optional and `"extended"`, `M` rows optional and `"manual"`), carries the file's alarm bullets as **pair-absent philosophy rows** (a meaning and a severity, never a number — ADR 0019 Amendment 2), carries its **maintenance plans** as `content.maintenance`, and carries its **KPIs** as `content.kpis` `bms-calc-v1` expressions. Five of the tag list's derived codes turn out to be genuinely expressible over measured points in their own class; per ADR 0051 Amendment 6 decision 8 those five are **promoted into `ELECTRICAL_CLASS_POINT_KEYS` and authored as `kind: "derived"` template points with real formulas**, and the other thirty-two are **deferred and named, never placeholdered**. The pack file crosses the §4.5 1000-line cap on the way, so it splits one module per class, and the build-time vocabulary guard gains the `pointKeys:` scan `F2.13` wrote an instruction for and could not write a check for.

When this lands, `F3.2` (per-asset-type default dashboards) has authored content to draw from for six electrical classes instead of one, and the SOW page-9 *Electrical Distribution Overview* and page-10 Utilities node have their asset classes defined in the product rather than in a document.

## 2. Out of scope

- **The feeder/incomer class stays at `stockVersion: 1` and its content is not edited.** §5.6 records the four candidate reasons to bump it and rejects all four. The only change it takes is a **text-only move** into its own file (Task 1), which is not a content change and therefore not a version bump.
- **Every KPI that needs an asset attribute or a cross-asset value**, each named with its reason in §5 and asserted absent by the build spec:
  - `load_pct` (feeder, transformer, DG) — measured kVA or kW ÷ **rating**, an asset attribute.
  - `demand_vs_contract_pct` — **contract demand**, an asset attribute (the page-9 KPI).
  - `pf_penalty_flag` and `pf_penalty_hours` — the **tariff PF band**, a site attribute, plus accumulation.
  - `performance_ratio_pct`, `specific_yield_kwh_kwp_day`, `capacity_utilization_pct` — **installed kWp**, an asset attribute.
  - `losses_pct` — incomer − Σ feeders, a **cross-asset sum** `bms-calc-v1` cannot name.
  - `lv_load_pct` (§2, in-table `D`) and `grid_export_kw` (§5, in-table `D`) — both read a **different asset's** §1 meter.
  - `hot_spot_estimate_c`, `loss_of_life_pct_day`, `duval_triangle_zone` — models the grammar has no functions for (IEC 60076-7 exponents, the C57.91 exponential ageing factor, a triangle-zone lookup).
  - `tap_changes_per_day`, `starts_per_day`, `steps_per_day`, `availability_pct`, `underload_hours`, `battery_events_per_month`, `charge_cycle_count` — every one needs a **time window** the grammar has no state for.
  - `fuel_hours_remaining_h` — the tag list writes it "level ÷ rate", but `fuel_level_pct` is a **percentage**; converting it to litres needs the tank capacity, an attribute.
  - `runtime_margin_min` (site minimum), `battery_age_months` (attribute), `capacitor_health_pct` (rated kVAr per step), `pf_correction_kvar` (needs `tan`/`acos`), `string_current_deviation_pct` (needs the whole string set), `self_consumption_pct` (site load), `co2_avoided_kg` (`E4.2`'s, plus an emission factor), `kwh_per_unit_output` and `specific_energy_kwh_kl` (production / KL from another asset).
- **`F3.2` default dashboards.** No `content.dashboards` key on any entry. A dashboard is that row's shape to choose.
- **Any seed-time import** — ADR 0052 decision 9. `db:seed` gains nothing; `BASELINE-*` untouched.
- **Any change to the catalog mechanism** — no route, no service, no DTO, no migration, no web change. `asset-templates-stock.service.ts`, `asset-templates.controller.ts`, `packages/shared/src/contracts/admin.ts` and `asset-templates-page.tsx` are not opened.
- **`content.health`** (ADR 0050 / `E1.3`) — weights and bands per electrical class are a health-model decision, not a tag-list transcription.
- **The water, mechanical and facility packs** (`E5.1`/`E5.2`/`E5.3`). Do not create `water.ts`, `mechanical.ts`, `facility.ts`.
- **`dga_lab_result`.** ADR 0051 Amendment 6 decision 7 excluded it (unit `text`; `telemetry.point_values.value` is a finite double), so it is in the tag list's §2 table and in **no** `*_POINT_KEYS` array. The transformer entry does not declare it, and Task 5 adds the assertion that says so.

## 3. Serial or parallel, and the model per pass

**Serial, one branch, three consecutive `implementer` passes. Do not fan out.**

The five classes *look* like five independent siblings, and they are not. Every one of them writes the same three shared files — `stock-catalog/electrical.ts` (the pack index), `stock-catalog/stock-catalog.spec.ts` (the build spec) and `tests/f2.13-asset-stock-catalog-vocabulary.test.ts` (the guard, whose anti-vacuity bounds are a single number per file) — plus `packages/shared/src/constants.ts` and `packages/db/src/point-keys-seed.ts` for the promotions. §3 of `docs/build-operating-model.md`: *"Anything two agents would edit the same file for — they will conflict."* Five worktrees would produce five conflicting edits to one guard bound and five conflicting appends to one array, and the merge would be done by hand anyway. The row is also not a ⭐ enabler: `F2.13` already froze the seam (`StockAssetTemplateEntry`, the DI token, the two routes), so nothing here defines an interface later work hangs off.

Three passes on `feat/F2.12-electrical-class-templates`, each starting only when the previous is green:

| Pass | Tasks | Model | Why, against the §2 ladder |
|---|---|---|---|
| **A** | 1–2 — the six-file split, the five vocabulary promotions, the three `185 → 190` bound moves | **Sonnet** | *"A well-specified, self-contained, mechanical unit."* Task 1 is a text-only move with the destinations named; Task 2 is five array lines, five `UNIT_BY_KEY` lines and three numbers. Nothing here is a judgment call — the plan supplies every literal. |
| **B** | 3 — the guard's `pointKeys:` scanner and the build spec's generalised checks | **Opus** | *"Units that need judgment in the execution."* A second regex over the same files that must **not** re-match `pointKey:`, plus turning four feeder-specific assertions into catalog-wide ones without weakening any of them. A wrong regex here makes 248 references pass while checking 234, silently — the exact failure mode the file exists to prevent. |
| **C** | 4–8 — the five entries, tests-first, one class per commit | **Opus** | *"Ordinary multi-file feature work against the plan where judgment is needed in the execution."* 138 point rows, 52 alarms, 6 KPIs and 21 maintenance plans transcribed from a document, where a wrong tier, a wrong unit spelling or a dropped row is silent until an import fails on a client's site. **Not Fable** — this defines no seam and touches no auth or RLS surface. |

**One escalation rule, stated so it is reviewable rather than improvised.** Pass C ships the transformer first (Task 4) precisely because it is the hardest entry — 31 table rows across four tiers, the only `manual` rows in the row, the only excluded code, and the only class whose headline number cannot be expressed at all. If the transformer commit comes back with a tier, unit or count that disagrees with §5's tables, **re-dispatch Tasks 5–8 at Fable** and say so in the dispatch. If it matches, the remaining four are the same shape at lower difficulty and stay on Opus.

Step 5's review agents (`code-reviewer`, `security-reviewer`, `agents-compliance-reviewer`, and **no `migration-reviewer` — this row writes no SQL**) run in parallel as always; step 6's browser half goes to `browser-verifier` by default.

### 4.2 Which derived codes have a `bms-calc-v1` formula, and which do not

The grammar (`packages/shared/src/calc-dsl/`) is `+ - * /`, unary `-`, `{point_ref}`, number literals, and exactly five functions with fixed arity (`abs` 1, `round` 1, `min` 2–20, `max` 2–20, `clamp` 3). No exponentials, no trigonometry, no time, no state, no aggregation across assets. `MAX_FORMULA_POINT_REFS = 20`, `MAX_FORMULA_LENGTH = 1000`. A derived template point's formula must additionally resolve every `{ref}` to a **measured** point declared in the same template (`templatePointsBodySchema`'s `superRefine`), and a derived point requires `formulaDialect: "bms-calc-v1"` plus a `calcTrigger`.

**Five are expressible. These are the five this row promotes and authors** (ADR 0051 Amendment 6 decision 8: *"`F2.12` promotes each derived code it can actually author a formula for, in its plan"*):

| Code | Class | Formula | Unit | Refs, and their tiers |
|---|---|---|---|---|
| `oil_rise_over_ambient_c` | §2 transformer | `{top_oil_temp_c} - {ambient_temp_c}` | `°C` | `top_oil_temp_c` C, `ambient_temp_c` X |
| `specific_fuel_l_kwh` | §3 DG set | `{fuel_rate_lph} / {gen_kw}` | `L/kWh` | `fuel_rate_lph` X, `gen_kw` C |
| `unplanned_run_flag` | §3 DG set | `{dg_status} * {mains_available}` | `` (0/1) | `dg_status` C, `mains_available` C |
| `load_headroom_pct` | §4 UPS | `100 - {load_pct}` | `%` | `load_pct` C |
| `inverter_efficiency_pct` | §5 solar PV | `{ac_power_kw} / {dc_power_kw} * 100` | `%` | `ac_power_kw` C, `dc_power_kw` C |

**Thirty-two are not**, every one for a reason that is a property of the grammar or of the data model, not of effort — the full list is §2 above, and each appears again in its class's docblock in §5.

**Two consequences of the formulas that must be written into the module docblocks, not discovered later:**

- **Division by zero is not an error the author can prevent, and the engine already handles it.** `evaluate.ts` returns `non_finite` for any node whose result fails `Number.isFinite` — *"`non_finite` covers division by zero and any non-finite intermediate"* — so `specific_fuel_l_kwh` with `gen_kw = 0` (the DG is running unloaded) and `inverter_efficiency_pct` with `dc_power_kw = 0` (night) produce **no value for that reading** rather than a wrong one. That is the correct behaviour and it is visible in the engine's skip count. Do not add a `clamp` or a `max(…, 0.001)` guard: a fabricated denominator turns "no data" into a plausible number, which is worse.
- **`oil_rise_over_ambient_c` needs an explicit `maxInputAgeSeconds`.** `DEFAULT_MAX_INPUT_AGE_SECONDS` is 300 s. `ambient_temp_c` on a transformer is typically a slow-updating site sensor; at the default the formula silently never fires, which reads as "the feature is broken" and is the harder failure to diagnose. Set `maxInputAgeSeconds: 3600` on that point and say why in the row's comment. The other four take both inputs from the same controller at the same scan rate and take the default (`null`).

## 5. The five entries, authored

Common to all five: `domain: "electrical"` (the code `assertAssetDomain` checks against `bms.asset_domains`), `stockVersion: 1`, and a `description` that **cites `docs/electrical-derived-taglist-v1.md` and its section by name** — ADR 0052 decision 6, the stamp plus the citation is the provenance, and there is no `meta.provenance`. `assetType` is snake_case, matching the `feeder` / `ro_skid` / `test_rig` convention already in the repository.

Point-row conventions, unchanged from the feeder and restated so nobody re-derives them:

- `sourceDataKeyPattern: null` on **every** point, measured and derived alike. The pattern is the site's telemetry wiring, which the tag list does not know and the catalog must not guess.
- `unit` is `null` wherever `UNIT_BY_KEY` holds `""` — the `0/1` flags, the `enum` and `code` rows, `tap`, `count`, and the dimensionless PF rows. A template `unit` is an override; `null` defers to the catalog's own unit.
- `label` is the Description column with the tag list's editorial remarks dropped (`(existing key)`, `(SunSpec St enum: …)`, `(per string, combiner box)`).
- `sortOrder` is the index, and the index is the tag list's own row order. Derived points are appended after the table rows, in the order they appear below.
- **`meta.tier` is present if and only if `kind === "measured"`.** `core` ↔ `required: true`; `extended` and `manual` ↔ `required: false`. A derived point carries **no** `meta.tier`, because the C/X/M column says what the plant has *fitted* and a computed point is fitted by nobody. Derived points carry `required: false` — which is inert at instantiation (§4.3) and avoids implying a mapping obligation that can never be met.
- Derived points carry `kind: "derived"`, `formula`, `formulaDialect: "bms-calc-v1"`, `calcTrigger: "streaming"`, `calcIntervalSeconds: null` (a streaming point must not carry one), and `maxInputAgeSeconds: null` except where noted.

Alarm-row conventions: every alarm is **pair-absent** — no `thresholdValue`, no `operator` — per ADR 0019 Amendment 2 decisions 1 and 2 and B7's *"limit values are set per site at commissioning"*. The meaning is carried by `message`. Every `pointKey` is a key the same entry declares (`assertContentRefsResolve`), and binding an optional `X`-tier point is legal because the check requires the key to be *declared*, not required.

### 5.5 `electrical-apfc` — Capacitor bank / APFC panel

### 5.6 The feeder stays at `stockVersion: 1`

Four candidate reasons to bump it were considered, and all four fail:

1. **KPIs from the SOW page-9 row.** *Total Power*, *PF* and *Energy Today* are each a bare point (`kw`, `pf`, `kwh_today`); the only true ratio in that row, `demand_vs_contract_pct`, needs the contract demand and is deferred. ## 11. Open questions — answer these before the first line of Task 4

**1. Provenance for content the tag list does not carry: the 21 maintenance plans and the 6 KPI codes.**

Both are authored from published practice rather than transcribed from `electrical-derived-taglist-v1.md`, which has no maintenance section and names none of `winding_to_oil_gradient_c`, `monitored_gas_sum_ppm`, `failed_start_ratio_pct`, `battery_cell_spread_v`, `module_temp_rise_c` or `pf_gap`. ADR 0052 decision 6 says the stamp plus the citation is the provenance, and the citation currently points at a document that does not contain this content. It is one question, not two, because it is the same gap.

- **Recommended:** author them, mark them **PROVISIONAL — derived from published practice, not client-confirmed** exactly as the tag list marks itself, and put the derivation basis in each class module's docblock the way the tag list puts its own at the top (IEEE C57.106 / IS 1866 for transformer oil; OEM 250-hour service intervals for the DG; IEEE 1188 / 450 for UPS batteries; the standards are already named in §5's tables). The asymmetry that makes this safe for KPIs and not for point keys: **a KPI code is per-entry template content, changeable by a version bump; a point key is seeded into `bms.point_keys`, foreign-keyed by `0058` and permanent.** This plan applies that asymmetry consistently — it invents no point key and does invent six KPI codes.
- **Alternative:** ship the five classes with points and alarms only, and defer KPIs and maintenance to a follow-up row gated on a derived maintenance/KPI document, the way the point set was gated on the tag list. Cost: `F3.2` still has nothing named to draw a tile from, and the guard's `pointKeys:` scan has nothing to scan, so the `F2.13` instruction stays owed.

**2. Promote `cell_voltage_spread_v` as a sixth derived point?**

§4's *"cell voltage spread high (weak block)"* alarm has no parameter to bind to: the tag list gives `cell_voltage_min_v` and `cell_voltage_max_v` and names no spread code in its Derived: list. `{cell_voltage_max_v} - {cell_voltage_min_v}` is expressible. As planned, it is a **KPI** and the alarm binds `cell_voltage_min_v` with the pair named in the message.

- **Recommended: yes, promote it** — an alarm whose parameter is not a point is an alarm nobody can rationalize, and this is the one place in the row where that is true. It would make six promotions (`vocabulary.size ≥ 191`), the UPS entry 31 points, and the `battery_cell_spread_v` KPI redundant (drop it).
- **Against:** it is a code the source document does not name, and a point key is permanent. ADR 0051 Amendment 6 decision 8 authorizes promoting the tag list's *named* derived codes; this one is unnamed, which is why it is asked rather than assumed.

**3. `assetType` values — `dg_set`, `ups`, `solar_pv`, `apfc`, `transformer`. Confirm.**

`assetType` is free text (max 64) with no vocabulary behind it, and `F2.2` instantiation copies it onto every asset the template creates. The repository's four existing values are `feeder`, `test_rig`, `test_skid`, `ro_skid` — snake_case, singular, no prefix — and the five above follow that. If the client's own asset taxonomy uses different words (`dg`, `inverter`, `capacitor_bank`), changing them later is a version bump on five shipped entries, so it is cheaper to confirm now than to correct.

**One thing flagged and deliberately not asked, because it is not this row's to decide:** §2 of the tag list has no current, kVA or kW row and §4's derived list has no spread code — both are **v2 redline candidates for `docs/electrical-derived-taglist-v1.md`**, and the document's own instruction to the client is *"strike what is not fitted, add what is missing, correct names and units."* This plan records both in the class docblocks and changes the document not at all.
