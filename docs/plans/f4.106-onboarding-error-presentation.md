# F4.106 — the onboarding wizard presents a sentence, not an envelope

Plan for backlog row `F4.106`. Branch `F4.106-onboarding-error-presentation`,
off merged `main` at `2a6144b6`. Planned on Opus after Fable hit its rate
limit; built per unit per `docs/build-operating-model.md` §2.

## Goal

The onboarding wizard is the only admin screen in `apps/web` that renders a
server refusal by reading `err.message` straight into a red box. Seven failure
surfaces on `apps/web/src/pages/admin/onboarding-chat-page.tsx` do this, and
two of the seven render nothing at all.

This row makes every one of them present a sentence: five existing
`err.message` reads move to `apiErrorMessage`, `validateMutation` gains the
`onError` it has never had, the template-download button gains the `.catch` it
has never had, `apiErrorMessage` learns the one body shape it does not
currently unwrap (a Zod `flatten()`, which four of these routes throw
verbatim), the 413 "file is too large" sentence is extracted to one shared
helper instead of a third copy, and `uploadOnboardingExcel` /
`downloadOnboardingTemplate` gain the `clearSessionOnAuthFailure` call both of
their telemetry siblings have had since `F1.9`.

**Effort is 2, not the 1 the row was filed at.** Ruling 1 widened it from two
things to a whole surface plus two auth gaps plus a shared-helper extraction.

### Out of scope, explicitly

- The ~30 identical raw-`err.message` sites on the other twelve admin pages
  (owner ruling 1 — a separate row is filed; do not open those files).
- Any `apps/api` change: no controller, no schema, no migration, no seed, no
  query.
- Any `packages/shared` change. No response type moves, so ADR 0030 / §4.8

- Closing the API↔web duplication of `MAX_IMPORT_FILE_BYTES` (residual).
- No new npm dependency (§9.4). No ADR — `F4.103` owner ruling 1 covers the
  whole `F4.103`–`F4.107` batch.

## Owner rulings

1. **The row reaches the onboarding screen's whole error surface**, not only
   the two things the row names. The ~30 sibling sites on other pages stay
   open and get their own row.
2. **Extract the 413 sentence once; keep each feature's own fallback wording.**
   A third copy of the helper is §4.8 drift. Because this touches the two
   existing files, their false docblock claim is corrected in the same pass.
3. **The seventh surface is caught, and it reads the server's body.** The
   template-download button gains a `.catch`, and `downloadOnboardingTemplate`
   stops discarding the response body — keeping its current line as the
   blank-body fallback. Without this, ruling 1 would introduce a regression: a
   401 would silently clear the session while the operator saw nothing.

Four smaller questions settled by the author with the plan's recommendations,
recorded so a reader can see they were decided rather than missed:

- **Flatten wording** — `formErrors` first and unlabelled, then each
  `fieldErrors` key as `` `${field}: ${messages.join(" ")}` ``, parts joined
  with a space.
- **No length cap on the flatten output.** Capping the new branch while the
  identical `return trimmed` path in the same function stays uncapped is
  harder to defend than either extreme, and the number would be invented in a
  repo that derives every number. Recorded as a residual with a new row.
- **`role="alert"` on both banners** — matches the repo idiom.
- **The commit refusal's `errors[]` stays discarded** — out of scope, residual.

## Facts this plan is built on, each verified in source

`node_modules/.pnpm/@nestjs+common@10.4.22/.../exceptions/http.exception.js`
— `HttpException.createBody` returns `arg0` **verbatim** unless it is falsy, a
string, or an array. `@nestjs/core`'s `BaseExceptionFilter` then sends
`isObject(res) ? res : { statusCode, message: res }`. `apps/api/src` registers
no global exception filter.

Measured directly by building the real exceptions
(`scratchpad/f4106-probe-envelope.mjs`), not reasoned from the source:

| Refusal | Wire body | What `apiErrorMessage` yields today |
|---|---|---|
| `PATCH /draft` over `F4.103`'s cap | `{"formErrors":[],"fieldErrors":{"draft":["Array must contain at most 100 element(s)"]}}` | the raw JSON, unchanged |
| `POST /chat` missing message | `{"formErrors":[],"fieldErrors":{"message":["Required"]}}` | the raw JSON, unchanged |
| `F4.102`/`103`/`104`'s string guards | `{"message":"…","error":"Bad Request","statusCode":400}` | the sentence ✅ |
| multer `LIMIT_FILE_SIZE` | `{"message":"File too large","error":"Payload Too Large","statusCode":413}` | `File too large` — no size figure |

So the row's own description is right for the string guards and **wrong for
the four Zod sites**: they carry no `message`, `error` or `statusCode` at all.

## The assertion rule this row must not get wrong

The mutation for a page site is "revert `apiErrorMessage(err)` to
`err.message`". For the **envelope** sites that mutation renders the whole
JSON — which *contains* the sentence. `findByText` with a substring match and
`toHaveTextContent(/…/)` both still pass. A presence-only assertion there is
decoration, and shipping one is the exact §4.6 failure `F4.105` recorded.

So every envelope-shaped page claim gets **two halves in the same assertion**:
the sentence is present **and** the banner text contains none of `statusCode`,
`"error"`, `errors`, and does not start with `{`. Reuse the leak-loop idiom
already in `apps/web/src/lib/api-error-message.spec.ts:25-27`.

The four **flatten** sites carry no human sentence at all, so presence alone
does redden there. Do not let one assertion shape cover both classes — you get
two claims where only one is alive.

### Unit 2 — `apiErrorMessage` learns the Zod `flatten()` shape

`apps/web/src/lib/api-error-message.ts` is the right unwrapper and there must
not be a second one (§4.8). But it does not handle the shape four of these
routes actually produce. Moving those sites to `apiErrorMessage` without this
unit changes nothing for them.

**Files:** `api-error-message.ts` (93) — extend `ErrorEnvelope` with
`formErrors?: unknown; fieldErrors?: unknown` and add one branch;
`api-error-message.spec.ts` (112) — four new exported functions;
`api-error-message.test.ts` (27) — four new `it()`s.

**Where the branch goes, and why that placement is the whole safety
argument.** After the `message` and `error` branches, immediately before the
final `return trimmed`. It therefore fires **only on bodies where the function
currently returns raw JSON**, so it is a strict improvement for all callers and
regresses none. That is a claim about a function 22 components import, so it
gets its own assertion (C3) rather than a sentence in a docblock.

**Wording.** Collect non-blank `formErrors` strings first, unlabelled. Then
each `fieldErrors` key in `Object.keys` order that has at least one non-blank
string message, as `` `${field}: ${messages.join(" ")}` ``. Join all parts with
a space. If nothing usable survives, fall through to `trimmed` unchanged.

**The docblock must state the limit rather than imply precision.**
`z.flatten()` collapses a nested path to its top-level key, so `PATCH /draft`
names `draft` and cannot name the offending array element. That is `F4.103`'s
recorded residual, and naming `draft` is the most this shape can give.

§9.6: this text is rendered, never logged. Add no logging.

| # | Claim | Mutation that must redden **this** assertion |
|---|---|---|
| C1 | The verbatim `F4.103` `PATCH` refusal body renders `draft: Array must contain at most 100 element(s)`, and the output contains none of `fieldErrors`, `formErrors`, `{` | delete the branch → raw JSON returns, absence half fails |
| C2 | A `formErrors`-only body renders its sentence | drop the `formErrors` half → only C2 fails |
| C3 | A body carrying **both** `message` and `fieldErrors` returns the `message` and does not contain the field name — the "regresses none" claim | move the new branch above the `message` branch → only C3 fails |
| C4 | `{"formErrors":[],"fieldErrors":{}}` and `{"fieldErrors":{"a":[]}}` still return the raw body | return `"The request failed."` when parts are empty → only C4 fails |
