# F4.357 — a persistent alarm bar on every page, with a popup and a tone

> **For agentic workers:** this plan follows the `superpowers:writing-plans`
> format. Build it unit by unit under TDD (red test first, then the code).
> **ADR 0130 is accepted (2026-11-12). The build waits for the owner's "yes" to
> this plan, and for the answers to §2.**

**Row:** `F4.357` (P1, 4–6 days, in progress) in `docs/BACKLOG.md`.
**Base:** `origin/main` at `ccc5cd13`.
**ADR:** [ADR 0130](../adr/0130-persistent-alarm-bar.md) — every line is a ruling. No migration, no dependency.
**Suggested path:** `docs/plans/f4.357-persistent-alarm-bar.md`.

**Goal.** Every authenticated page and the control room wall carry one bar fixed
to the bottom edge. It shows the active alarm count per severity in the page's
scope, the newest unacknowledged alarm of the highest rank, Acknowledge, mute and
an "All alarms" list that opens upward. A new alarm of rank >= 20 opens one popup
(critical first, newest first; Acknowledge per row or all with one reason; Close).
An unseen unacknowledged alarm of rank >= 30 blinks at 1 Hz and plays a Web Audio
tone every 30 s until acknowledged or muted. The API gains `locationId` on
`GET /api/v1/alarms` and `GET /api/v1/alarms/summary`, and `alarmListItemSchema`
gains `severityRank`.

**Out of scope (ADR non-goals, plus this plan's).** Shelving; browser
`Notification`, SMS, push; server-side mute or sound settings; any change to
rules, severities, the lifecycle or the acknowledge route; a site selector
(`F3.29`); a bulk acknowledge endpoint; moving the four existing
`useAlarmsSocket` callers onto the shared socket (decision 13 allows it, does not
require it); `alarmDetailsResponseSchema` (it gains nothing).

**Serial, hands-on.** One implementer at a time, PR 1 to PR 4 in order. The units
share the feed, the store and the contract, so no fan-out and no worktrees.

**CodeGraph was not available** for this plan (`.codegraph/` holds no index, the
CLI is not on PATH, no MCP tool). The blast radius in §6 is from `git grep` on
`origin/main`. The local checkout differs from `origin/main` in none of the files
below (checked with `git diff --stat HEAD origin/main`).

## 2. Plan-gate questions (owner, before the first line of code)

Each has a recommendation. None reopens a decision; each names a point where the
ADR's words and the code do not meet.

1. **"and N more" and the 50-row window (decisions 7, 10, 16).** The store's list
   is the 50 newest *active* alarms of the scope, acknowledged ones included. So
   (a) the popup can never hold more than 50 rows, and the exact number of unseen
   alarms beyond them is not in either read; (b) an unacknowledged critical alarm
   older than those 50 rows gets no popup row, no blink and no tone (the counts
   stay exact).
   **Recommended:** build as written. N = (summary total of rank >= 20) minus
   (rank >= 20 rows in the list), worded "and N more active alarms", linked to
   `/alarms`. Record (b) in the bar's docblock. An `acknowledged=false` filter is
   a follow-up row if the owner wants it.
2. **A device alarm's location label (decision 17, second sentence).** The list
   item carries no location for an `rtu_comms` alarm, so the label needs a field.
   **Recommended:** add `locationName: z.string().nullable()` to
   `alarmListItemSchema` beside `severityRank` — the asset's location for a rule
   alarm, the RTU's for `rtu_comms`, `null` for `ingest_host`. Additive, same PR.
3. **The store fetches (decision 16) against AGENTS.md §4.2** ("data fetching via
   TanStack Query hooks"). **Recommended:** follow the ADR. The store's feed calls
   the `api/alarms.ts` functions (they keep `checkResponse`), because the list,
   "seen", the mute and the tone cadence must outlive `AppShell`. Record the
   exception in the `chore(agents):` catch-up.
4. **Where "Control Room · Estate" shows (decision 5).** The string is on no
   screen today. **Recommended:** the `/control-room` page's KPI ribbon reads
   "Control Room · Estate" (`pages/control-room/organizations-page.tsx:72`), and
   the bar's list header names its scope: "Estate", "This organization", "This
   site and its sub-locations", "All alarms you can read".
5. **Layering (decision 3).** **Recommended:** the bar and the popup are `z-40`.
   A modal dialog or drawer (`z-50`) covers them while it is open; the tone still
   plays. "Cannot be hidden" means the bar has no hide control.
6. **The wall (decision 12).** **Recommended:** the bar renders inside the zoomed
   `[data-wall-root]`, so it scales with the wall; it carries `data-wall-bar`, so
   a click on it (Acknowledge, "Sound blocked — click to enable") does not pause
   the rotation; dialogs opened from it portal to `document.body` at 1x.
7. **The popup's reason form (decision 8) against ADR 0106 ruling Q9** (operations
   writes on `WizardShell`). **Recommended:** the popup has its own one-field
   reason form (one reason, N calls, "This cannot be undone" on it). The bar's
   single Acknowledge button reuses the existing `AlarmAckWizard`.

**Gates still owed:** the owner's "yes" to this plan; the merge gate per PR
(step 7); the `e2e` label on PR 2 and PR 3 (about 4 billed minutes each — GitHub
Actions minutes are short, so run `pnpm test:e2e` locally first and push once).

## 3. Design decisions (no ruling needed)

| # | Decision | Why |
|---|---|---|
| D1 | `severityRank` (and `locationName`) are **scalar sub-selects inside `alarmListItemColumns`**. | No consumer adds a join, so the five producers cannot drift. |
| D2 | The location predicate is one function of self-contained sub-selects, used in `list`'s `WHERE` and the summary's `ON`. | The `alarmVisibleTo` shape; the counts agree with the list. |
| D3 | The subtree comes from `expandLocationSubtrees`; the P2 rule is applied first. | `tests/f2.10` allows no new CTE; one rule for `locationId` across the API. |
| D4 | The feed is a **module singleton installed in `main.tsx`**. Not installed, `AlarmBar` renders nothing and starts nothing. | Survives `AppShell` remounts; `app.tsx` is untouched; the 34 shell specs stay inert. |
| D5 | "New" = in the list, unacknowledged, rank >= 20, id not in `seenIds`. | Same behaviour as decision 16's list diff: the set is empty after a load (decision 21), Close adds the shown ids, a session end clears it. |
| D6 | Refetch: the first socket event arms a 1 s timer; later events do not re-arm it; a fetch in flight is followed by one more. | A pure debounce never fires in an alarm storm. |
| D7 | Every response carries its request number and scope key; a late one is dropped. | A scope change must not be overwritten by the old page's answer. |
| D8 | Tone cycle: wanted = an unacknowledged rank >= 30 alarm whose id is not muted. Wanted and no cycle: play now, repeat every 30 s. Wanted and a cycle runs: nothing extra. Not wanted: stop. The cycle survives a scope change. | Decisions 10, 11. |
| D9 | Mute is a set of ids, not a flag. | "Never the next one." |
| D10 | The bar is one row, `3rem` high. No `vh` unit in the bar, the list or the popup. | The wall resolves `vh` wrongly inside the zoomed box. |
| D11 | The blink is plain CSS in `index.css`, not a Tailwind animation. | MG1 pins the four `mimic-*` animations. |
| D12 | `--alarm-bar-h` is declared on `html {}` in the plain-CSS tail, not in the `:root` token block. | The token-set gates parse `:root`. |
| D13 | The page clearance is the class `alarm-bar-clearance` on the two shell roots and the wall root. | Z2 forbids `pb-[…]`. |
| D14 | `canAcknowledgeAlarms(role)` in `apps/web/src/lib/admin-access.ts` mirrors the `operational` class (`role !== "viewer"`). | The matrix is API-only. |
| D15 | Fetch failure: keep the last list, mark the feed stale ("Alarms not updating" on the bar), retry every 30 s. | A monitoring bar must not show stale counts silently. |

## 9. Risks

1. **The 50-row window** (Q1): an old unacknowledged critical alarm behind 50 newer active alarms is silent. Recorded; the counts stay exact.
2. **Read load:** each socket event costs two scoped reads per open tab, at most once a second. Check the `F4.17` buckets for `GET /alarms` against two requests a second per tab; a 429 marks the feed stale and retries at 30 s.
3. **The wall's fixed bar inside CSS `zoom`:** the layout rests on Chromium's zoom, as the wall already does. Browser check 10 is the gate; if the fit loops, the fallback is the bar outside the zoomed root with the fit height reduced by its pixels.
4. **Autoplay:** a wall nobody touches shows "Sound blocked — click to enable" and plays nothing until one click. A kiosk flag (`--autoplay-policy=no-user-gesture-required`) is a deployment note, not code.
5. **The e2e suite:** the popup can cover a target at the bottom centre. Local run first; one helper if needed.
6. **`checkResponse` in production logs and passes:** a web bundle newer than the API would read `severityRank` as `undefined` and show no popup. The deploy ships both together; PR 1 merges first.
7. **Three producers run in other processes** (the worker's sweep, `api-replica`): rebuild and restart `worker` with `api`, or the `cleared` event lacks the new fields and fails the socket payload's shape in dev.
8. **`seenIds` and `mutedIds` grow for the life of a tab** (one uuid per alarm seen). No pruning; a shift is a few thousand ids at most.
