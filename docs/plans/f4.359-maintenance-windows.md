**Base:** `main` at `615c1d8c` (`git diff --stat HEAD origin/main` is empty).
**ADR:** [ADR 0131](../adr/0131-maintenance-windows.md). One migration, no dependency.
**Suggested path:** `docs/plans/f4.359-maintenance-windows.md`.

**Goal.** An admin creates a maintenance window (reason, start, end at most 7
days later, targets: assets, locations with their subtree, single rules; an
optional work-order or schedule link) and can extend, end early or cancel it.
While a window covers an alarm, the alarm is **suppressed**: the row is written
and listed, but it has no bar count, popup, blink, tone, notification or
escalation. An alarm active at the start is suppressed too; `rtu_comms` alarms
are covered, `ingest_host` alarms never. At the end every still-active
suppressed alarm returns as a normal alarm: the bar treats it as new, its raise
notification is sent, and its escalation clock starts then. The web gains a
"Maintenance" badge, a "Maintenance N" pill in the ADR 0130 bar, and an admin
page "Maintenance windows". The Copilot can propose the four window writes
(ADR 0099 Amendment 19).

**Out of scope (ADR non-goals, plus this plan's).** Repeating windows; a
per-alarm shelve; `ingest_host` suppression; any change to telemetry, calcs,
KPIs or health scores — so the KPI ribbons, the map, the mimic node colours, the
site-widget summary, `asset-role-summary` and `alarm-stats` **still count a
suppressed alarm** (§1, last row; §9 risk 2); the rule `enabled` switch; a window
made from a work order or schedule; a delete route for windows;
`alarmDetailsResponseSchema`; moving `acknowledged`/`cleared`/`suppression` broadcasts onto `bms_alarms`
(`F4.133`).

**Serial, hands-on.** PR 1 to PR 7 in order, one implementer at a time. The
units share `bms.alarms`, the list-item contract and the lifecycle sweep.
Nothing fans out: PR 7 needs PR 5 (`useActiveMaintenance`) and PR 6, and PR 6
waits for Amendment 19.

## 2. Plan-gate questions (owner, before the first line of code)

None reopens a decision. Each names a point where the ADR's words and the code
do not meet.

1. **Where the raise path decides (decision 10).** The ADR says the engine reads
   the windows "with the enabled rules (the same cache)". That cache serves one
   of four raise callers, in one of two processes.
   - **(a) Recommended:** `AlarmRaiser` decides inside its raise transaction,
     after the insert returned a row: one keyed read of the organization's
     active windows, then the stamp, then `pg_notify`. No cache, so nothing to
     invalidate; exact on all four paths in both processes; cost is one indexed
     read per **real** raise (a dedupe hit pays nothing). The sweep still applies
     decisions 7 and 8 within one tick. This refines decision 10's mechanism and
     keeps its two promises (no 60 s lag; decided before any notification).
   - (b) As written: a window cache beside the rule cache, plus one for the
     worker's sweep, Evaluate now and the device sweep; invalidation crosses
     processes by a new `NOTIFY` channel with a `LISTEN` client in the worker
     (it has none today); a lost notification leaves a gap of up to 60 s.

   **Ruling (owner, 2026-11-13): (a)** — `AlarmRaiser` decides in the raise
   transaction.
2. **A third column and a contract field (decisions 8, 17, 19).** "The escalation
   clock starts from that moment" needs the moment stored: `raised_at` makes a
   returned alarm's steps `skipped_stale`, and with overlapping windows
   (decision 9) the first window's end is not the moment. "The bar treats it as
   new" needs a discriminator that survives a missed socket event.
   **Recommended:** `bms.alarms.unsuppressed_at timestamptz NULL` in the same
   migration, and `unsuppressedAt: z.string().nullable()` on
   `alarmListItemSchema`. Alternative for the web only: key "seen" on
   `id + maintenanceWindowId` (no field; wrong if one window suppresses the same
   alarm twice).
   **Ruling (owner, 2026-11-13): as recommended** — the `unsuppressed_at`
   column and the `unsuppressedAt` field.
3. **An alarm notified or escalated before the window (decision 8).**
   **Recommended:** the ledger answers. At the return, a channel of the rule
   that holds **no** row under the alarm's raise key is owed the raise (the
   withheld one); a channel that already holds a `sent` row gets nothing more. A
   step sent before the window is not sent again; the steps not yet sent follow
   the new clock. An acknowledged alarm gets neither (ADR 0057 Amendment 5
   ruling 4). Alternative: a new "still active after maintenance" event with a
   key epoch — a `buildDedupeKey` change, about 1 more day.
   **Ruling (owner, 2026-11-13): as recommended** — the ledger answers.
4. **`state=active` and `state=unacknowledged` (decision 19 names only `all`
   and `suppressed`).** **Recommended:** `unacknowledged` excludes suppressed
   alarms (it is the bar's announcing read, and its 50 rows must not fill with
   them); `active` keeps them, badged (rails, the Copilot's `list_alarms`);
   `suppressed` = active and suppressed, so its length equals the pill's N. The
   bar's "All alarms" panel drops suppressed rows on the client and shows "N
   suppressed by maintenance". Consequence: `summary.total` can be less than the
   `active` list's length. Alternative: `active` excludes them too.
   **Ruling (owner, 2026-11-13): as recommended** — `active` keeps suppressed
   alarms, `unacknowledged` excludes them.
5. **`asset_group_admin` (decision 13 says "organization and site admins"; the
   named check also admits `admin` and `asset_group_admin`).** **Recommended:**
   follow the named check — the rule toggle already lets that role disable every
   rule of its assets. The admin page is unreachable for it (`AdminRoute`), so
   in practice it writes through the API only. Alternative: refuse it in the
   service.
   **Ruling (owner, 2026-11-13): as recommended** — follow the named check;
   `asset_group_admin` is admitted.
6. **The form (decision 16) against ADR 0099 decision 6.** A `WizardShell` takes
   a Copilot catalog entry (`tests/f3.85-stepper-coverage.test.ts`; the `F3.86`
   plan's ruling Q9 is the precedent for wizards in place of dialogs), which
   makes each window write a Copilot write and needs an ADR 0099 amendment.
   Recommended was: plain dialogs, no catalog entry. Alternative: four catalog
   entries now, with an amendment, about 2 more days.
   **Ruling (owner, 2026-11-13): the alternative** — `WizardShell` and four
   catalog entries (create, extend, end, cancel), under **ADR 0099 Amendment
   19**. PR 6 and PR 7 wait for its acceptance.
7. **Which surfaces carry the asset badge (decision 14: "the asset page", "the
   asset's dashboard tiles").** **Recommended:** `AssetDetailPanel`
   (`/asset-browser`), the header of `/asset-history/:assetId`, the generated
   site asset card (`components/control-room/generated-site-asset-card.tsx`),
   and the header of an asset-scoped dashboard on `/dashboards/:slug` (one
   badge, not one per widget). A rule-only target shows the badge on its alarm
   rows only. Alternative: every dashboard-builder widget bound to the asset —
   wider, about 1 more day.
   **Ruling (owner, 2026-11-13): as recommended** — the four surfaces.

## 3. Design decisions (no ruling needed)

| # | Decision | Why |
|---|---|---|
| D1 | The window's organization is **derived from its targets**; the create body has no `organizationId`. Targets of two organizations are a 400. | Nothing to mismatch; the composite FKs say the same in SQL. |
| D2 | Window state is derived, on the database clock: future `ended_at IS NULL AND starts_at > now()`; active `ended_at IS NULL AND starts_at <= now() AND ends_at > now()`; past otherwise. `end` and `cancel` both write `ended_at`/`ended_by`. | One rule for the route, the raiser and the list. |
| D3 | The 7-day rule is the service's (a pure `validateWindowPeriod`), not a table CHECK. | An extension may carry the total past 7 days (decision 2). |
| D4 | The window routes write **no alarm row**. The raiser stamps at the raise; the sweep stamps and lifts. | Two writers of the stamps, both gated (U10). |
| D5 | The sweep is a **reconciler**: each tick, for every active alarm, covered and not stamped → stamp; stamped and not covered → lift. | Heals a raise-path miss, clock skew and a missed tick; needs no event from the routes. |
| D6 | One pure function `firstCoveringWindow(windows, subject)` (earliest `starts_at`, then id) used by the raiser and the sweep. Location cover = a target location is in the subject location's ancestor-or-self set (`locationAncestors` / `locationAncestorChains`). | Decision 9's "first window"; no new CTE; per-window membership without one walk per window. |
| D7 | `rtu_comms` cover: the RTU's `location_id` is under a target location, **or** the RTU has at least one bound asset and every one is an asset target of the same window. | Decision 5; K4 makes the location arm cover the "all its assets are under the location" case. |
| D8 | The stamp is an `UPDATE` in the raise transaction right after the insert, before `pg_notify`. | Outside observers never see the row unstamped; the cover read is paid only on a real raise. |
| D9 | `AlarmRaiseResult` gains a required `suppressed`; `notifyOnRaise` returns early on it. | One choke point for three callers (decision 10). |
| D10 | The return notification is the **raise-retry phase's**: for an alarm with `unsuppressedAt`, a rule channel with no ledger row is owed (Q3). | State-driven and crash-safe: a restart between the lift and the send loses nothing; no new dispatch site. |
| D11 | Escalation reads `escalationStart(alarm) = unsuppressedAt ?? raisedAt` for `dueSteps`, `stepIsTooLate` and the message's minutes. | Decision 8. |
| D12 | A cleared-while-suppressed alarm keeps `suppressed_at`; `notifyCleared` is skipped for it. `suppressed_by_window_id` is kept after a lift (history) and replaced by a later window's id on a new suppression. | Decisions 8, 9; the contract's `maintenanceWindowId` stays truthful. |
| D13 | A fourth socket event `{ type: "suppression", alarm }` for a stamp or a lift by the sweep. | `created` would read as a second raise; every consumer refetches on any event, so none changes. |
| D14 | The new module lives in `apps/api/src/maintenance-windows/`; contracts in `packages/shared/src/contracts/maintenance-windows.ts`; both new tables in `alarms-schema.ts`. The directory joins `CATALOG_DIRS` in PR 6. | `operations.ts` and `index.ts` are at the cap; no schema import cycle; the service audits through the funnel from PR 2, so the `via: "copilot"` mark needs no later change. |
| D15 | Extend, end and cancel need **every** target of the window inside the caller's read scope. | A site admin must not end a window that also covers another site. |
| D16 | `GET /maintenance-windows` items of an active window carry `assetIds`: the caller-readable assets it covers as assets (asset targets, and assets under location targets), inside the request's filter. | One read per page answers every asset badge (decision 14) with no per-asset call. |
| D17 | The pill's N is `summary.suppressed` (the feed); the pill's visibility and its panel are a TanStack Query read of `state=active` windows for the page scope, refetched every 60 s, in a child component that mounts only when the feed is installed. | The summary gains exactly one count (decision 19); a window that starts by time emits no alarm event, so the pill may lag by up to 60 s — stated, not hidden. |
| D18 | The Maintenance badge is `StatusPill` with `tone="info"`. | No new colour token (`tests/f3.65-colour-roles-gate.test.ts`). |

## 9. Risks

1. **A window hides a real fault** on its targets (ADR). The 7-day rule, the reason, the badge and the pill are the mitigation; nothing more is built.
2. **The bar and the other counts disagree by design.** KPI ribbons, the map, mimic node colours, the site-widget summary and health scores still count a suppressed alarm (non-goal). An asset can show "Alarm" beside "Maintenance". Tell the owner at the PR 5 review; a change is a new row.
3. **Two clocks.** The raiser reads the database's `now()`; the sweep takes the API process's tick. A skew stamps or lifts one tick early or late; D5 corrects it on the next tick.
4. **A stamp write that fails** leaves an alarm covered and unstamped: the bar announces it until the next tick lands the write. The later phases still treat it as suppressed in that tick.
5. **Timing.** A window takes effect on already-active alarms, and ends, within one sweep interval (30 s plus the sweep's own run time). The pill can lag a time-based start or end by up to 60 s (D17).
6. **Two API processes** (`api-replica`, profile `realtime-smoke` only) both sweep: the guarded writes make one of them the writer, but only that process's sockets get the `suppression` event (the `cleared` event has the same limit, `F4.133`), and both could offer a withheld raise in the same instant. **Unverified** that the AWS demo runs one API process.
7. **A cleared-while-suppressed alarm sends no "Cleared" message**, also when its raise was sent before the window (decision 8's last sentence, as written).
8. **Cost.** One small window read per tick, and one per real raise; ancestors and bound assets are read only while a window with such a target is active. A returned alarm whose rule joins no enabled channel costs one batched channel read per tick while it stays open and unacknowledged.
9. **The composite FKs** refuse a hard delete of an asset, location or rule that was ever a target. No route does that today; a future one must decide.
10. **`checkResponse` logs and passes in production:** a web bundle older than the API ignores `suppressed` and shows no badge. The deploy ships both; PR 3 merges before PR 5.
11. **The worker must be rebuilt with the API** from PR 4, or its raises carry no stamp until the next sweep and their notifications leak for that raise.
12. **The e2e suite:** the new admin tab and the pill are on covered paths; run `pnpm test:e2e` locally before each labelled push.
13. **The Copilot can silence alarms.** A proposed create or extend is red, is offered only on the user's own words, and is one Confirm (Amendment 19). The route's role and scope checks run again at Confirm.
14. **The propose budget** passes 103,000 with four more tools; the bound rises by the release-4 rule and the owner confirms it with PR 6.
15. **`copilot-target-resolver.ts` is at 989 lines** and PR #1039 is open on it; PR 6 rebases on it or keeps its edit to ten lines.
16. **Amendment 19 is not accepted yet.** If the owner changes a ruling at acceptance, U14 changes before PR 6 starts; PR 1 to PR 5 do not.
