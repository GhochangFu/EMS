## 1. Goal, and what is explicitly out of scope

Give the three tables migration `0050` created a surface a human can use. Two halves on one branch:

- **The builder.** An authoring page where an administrator composes a dashboard: places widgets of the four catalog types, arranges them on the 12-column canvas (position **and** size), binds points, picks a chart's series from the four plain labels, edits each type's config, saves, and duplicates an existing dashboard into a scope they may already write to. Role-gated the ADR 0038 decision 10 way — the **forms**, not merely the buttons.
- **The viewer.** A route that reads and never writes: a list of the dashboards the caller may read, and a detail route that renders one with live values. Every mutating affordance stays on the builder.

**Explicitly out of scope.**

- **No new API route, no schema, no migration.** `GET /dashboards`, `GET /dashboards/:slug`, `POST /dashboards`, `PATCH /dashboards/:id`, `DELETE /dashboards/:id` and `PUT /dashboards/:id/widgets` all exist (`apps/api/src/dashboard-builder/dashboard-builder.controller.ts:59,65,71,78,84,92`). The one `apps/api` **behaviour** change this plan proposes is a `23505` → 409 rewrite inside `create`/`update` — see open question 2.
- **No new widget renderer.** `apps/web/src/components/widgets/dashboard-widget.tsx` exports `DashboardWidget({widget, data, now})` behind an exhaustive dispatcher and `WidgetData`. Its docblock states that `F3.1d` maps `F3.1b`'s response into `WidgetData`; that mapping is this row's, the drawing is not.
- **No new label, anywhere.** `WIDGET_CATALOG`, `CHART_SERIES` and `WIDGET_TONE_COLOR` live in `apps/web/src/lib/widget-catalog.ts`; `CHART_SERIES_OPTIONS` and `WIDGET_TYPE_LABELS` in `apps/web/src/lib/template-dashboard-form.ts` already derive from them. Import; never restate. The four series labels are *Trend* / *Trend (filled)* / *Comparison bars* / *Scatter*, and `tests/f3.1c-widget-series-mapping.test.ts` fails a second copy.
- **No drag-and-drop or grid-layout dependency.** ADR 0047 §Dependencies makes it a *conclusion* of this build, not an input. §4 names the arrange mechanism and the exact §9.4 stop condition.
- **No collision avoidance and no auto-reflow.** `0050` permits two widgets to occupy the same cells and nothing forbids it. See open question 3 — this is the §9.4 trigger.
- **No `F3.2`.** Instantiating a template's dashboard into `bms.dashboard_widgets` stays `F3.2`'s. The viewer renders rows that already exist.
- **No `F3.28`.** The alarms rail, the KPI period-delta, the status legend and the Diagram/List toggle are decision 6's, and `F3.28` composes *on top of* the page this row ships.
- **Not the dark canvas.** `docs/BACKLOG.md` §5's *Reference layout language* ⚠ stays open and stays the owner's; this ships in the light palette.
- **No bulk telemetry endpoint.** See open question 4.

## 2. Serial or parallel — **serial, one branch, one PR**

`F3.1d` is **not** ⭐, so "never fan out an enabler" is not what decides this. Three things do:

1. **There is a spine every later unit imports.** Units 1–3 (the grid constant, the rewiring, the source scan) are consumed by units 4, 7 and 9. A worktree that starts the builder before `DASHBOARD_GRID` is on the branch invents the fourth copy this row exists to prevent.
2. **The file sets overlap.** Builder and viewer both edit `apps/web/src/app.tsx`, both import `apps/web/src/lib/dashboard-widget-data.ts`, both render `DashboardWidget` through the same canvas component, and both consume the same `apps/web/src/api/dashboards.ts`. That is the opposite of `build-operating-model.md` §3's "non-overlapping in files".
3. **The fan-out unit is a backlog row.** Splitting one row across two worktrees produces two branches and spends the owner's step-7 merge gate twice — and ADR 0047 Amendment 4 explicitly **declined** making the viewer a sixth child, on the release rather than on the paperwork.

**Build order inside the branch is spine-first**: shared constant → source scan → pure `lib/` modules with their specs → API client → viewer → builder → duplicate. The viewer precedes the builder deliberately: it is the smaller consumer of `WidgetData`, so the seam is exercised and corrected before the larger surface is written on top of it.

## 4. The arrange/resize mechanism, and the §9.4 stop condition

**What is built: two affordances over one CSS-grid canvas, no dependency.**

- **Four number inputs per widget** (`gridX`, `gridY`, `gridW`, `gridH`) in the widget inspector. Always available, keyboard-accessible, and the `F3.1e` precedent (`apps/web/src/components/asset-templates/dashboard-widget-editor.tsx:81-104`). This is the affordance that must work; the pointer layer is the one that must not be worse.
- **A pointer-events drag and resize layer.** `onPointerDown` + `setPointerCapture` + `onPointerMove` on the tile (drag) and on a bottom-right handle (resize), converting pixel deltas to column/row deltas through a measured cell size, clamped by `DASHBOARD_GRID`.

`apps/web/src/pages/work-orders-page.tsx:654` is the in-repo drag precedent and it is **HTML5 `draggable` for list reorder only — it gives no resize**, so it is a shape reference and not a reusable implementation. Pointer events over CSS grid is the no-dependency route to both.

**The geometry is pure and lives in `apps/web/src/lib/dashboard-grid-geometry.ts`.** Cell size is an *argument*, never read from the DOM inside the pure module. That is what makes the arrange rules testable without layout — and it is necessary, because **jsdom implements no layout: `getBoundingClientRect()` returns zeros.** Consequence, stated plainly so a reader does not assume otherwise: the pointer handlers themselves are verified **only in the browser pass** (§10), never by the suite.

**The §9.4 stop condition — the one that can actually fire.** "The pure geometry is testable" is a design constraint the implementer can always satisfy, so it is not a stop condition. This is:

> **Stop and raise the §9.4 gate if collision avoidance or auto-reflow is required.** `0050` permits overlapping widgets. This build lets an author place two tiles on the same cells; the canvas draws them stacked and the save succeeds. If the owner rules that tiles must push each other out of the way, or that a moved tile must compact its neighbours upward, **that is exactly what a grid-layout library buys and the hand-rolled route stops being the cheaper answer.** Do not write a compaction algorithm inside this row: raise it, take its own ADR on the ADR 0042 precedent (four test-only devDependencies, ruled mid-build rather than assumed at the start), and check the Node floor first — ADR 0042 Amendment 1 records `jsdom@30` requiring Node 22 on a Node 20 repository, and `.github/workflows/ci.yml` pins `node-version: 20`.

A second, weaker trigger worth naming: if `dashboard-grid-geometry.ts` passes ~250 lines of pointer arithmetic, the no-dependency claim has stopped being true in substance. Raise it rather than continuing.

## 5. The grid-bounds single source — extract, and why nothing else works

**Today the bounds are four sites in three files:**

| Site | Literals |
|---|---|
| `packages/db/drizzle/0050_configurable_dashboard_tables.sql`, `dashboard_widgets_grid_bounds_check` | `grid_x + grid_w <= 12`, `grid_h <= 24`, … |
| `packages/shared/src/contracts/dashboard-builder.ts`, `dashboardWidgetIdentitySchema` | `.max(11)`, `.max(12)`, `.max(24)`, and the `.refine` `gridX + gridW <= 12` |
| `apps/api/src/dashboard-builder/dashboards.schema.ts`, `widgetIdentityWriteFields` | `.max(11)`, `.max(12)`, `.max(24)` |
| `apps/api/src/dashboard-builder/dashboards.schema.ts`, `eachWidgetFitsTheGrid` | `widget.gridX + widget.gridW > 12` |

*(The brief said "three places"; that is three **files**. `dashboards.schema.ts` carries two independent sites and both must be rewired, or the array-level cross-field check keeps a private `12`.)*

**Ruling: extract named constants into `packages/shared/src/contracts/dashboard-builder.ts` and rewire the two TypeScript schemas.** The migration keeps its literals — SQL cannot import a TypeScript constant, and that is a permanent, principled exception rather than an oversight, exactly as ADR 0047 decision 2 accepts one forward migration per widget type.

```ts
/**
 * The canvas, declared once. `F3.1d`'s builder clamps to these numbers rather
 * than restating them, and `apps/api`'s write schema reads them too — the same
 * discipline `WIDGET_POINT_CARDINALITY` established (Amendment 2 §1): a bound
 * enforced only by the surface that happens to be convenient is not enforced.
 *
 * `0050`'s `dashboard_widgets_grid_bounds_check` is the fourth site and cannot
 * import this — SQL has no imports. `tests/f3.1d-grid-bounds-single-source.test.ts`
 * is the scan that keeps a FIFTH from appearing in TypeScript.
 */
export const DASHBOARD_GRID = {
  columns: 12,
  minWidgetW: 1,
  minWidgetH: 1,
  maxWidgetH: 24,
} as const;
```

**Why "import differently" is not available.** `apps/web` carries no `zod` (F3.1c's recorded constraint — `widget-catalog.ts:10-14`), and adding it is a §9.4 gate this row is not entitled to open. Without `zod` the builder cannot read a bound *out of* `dashboardWidgetIdentitySchema`; a plain exported constant is the only value both packages can consume. `packages/shared` is already a runtime dependency of `apps/api` and `apps/web` (`widget-catalog.ts:2` imports `WIDGET_POINT_CARDINALITY` at runtime today), so this costs nothing new.

**It trips no existing scan.** `as const` is not a Zod combinator, so neither `tests/adr-0030-contract-derivation.test.ts` nor `tests/f3.1a-dashboard-schema.test.ts`'s combinator scan sees it. Confirmed by Task 0.1 that the grid assertions read the migration, not this file.

### 6.1 Routes (`apps/web/src/app.tsx`)

**The page is named `dashboard-viewer-page.tsx`, not `dashboard-view-page.tsx`** — `apps/web/src/components/asset-templates/dashboard-view-editor.tsx` already exists and is `F3.1e`'s template-content editor. **Navigation:** one entry, `{ label: "Dashboards", path: "/dashboards" }`, added to the *Monitoring* group of `apps/web/src/layouts/app-shell.tsx`. The builder gets **no nav entry**; its entry point is a "Manage dashboards" link on `/dashboards`, rendered only when `canAuthorDashboards(user.role)`. This keeps `masterDataTabs`/`visibleMasterDataTabs` untouched (zero blast radius on eleven other admin pages) and means the route reachability question lives in exactly one predicate.

### 6.2 The gating shape — ADR 0038 decision 10, applied

Decision 10 (`0038-template-authoring-ui.md:241-259`) splits the check in two, and this row mirrors it exactly.

**Pure role checks — computed client-side from `user.role` and used to decide whether a form is rendered at all.** `GET /api/v1/auth/me` returns `user.role` in `sessionUserSchema` (`packages/shared/src/contracts/auth.ts:35-40`) and the app already stores it (`apps/web/src/stores/auth-store.ts:6-11`). Two new predicates in `apps/web/src/lib/admin-access.ts`, each its own function with a docblock naming the API method it mirrors — the idiom `canManageNotificationChannels` (`admin-access.ts:27-43`) established, and the reason it gives applies here too: two predicates whose bodies read alike today answer different questions and are gated by different API methods.

```ts
/** Mirrors `canPerformOperationsWrite(role, "configuration")` — `apps/api/src/auth/operations-write.ts:23-31`. */
export function canAuthorDashboards(role: UserRole): boolean { … }   // admin, organization_admin, location_admin, asset_group_admin

/** Mirrors ADR 0047 Amendment 2 ruling 2, enforced by `AccessControlService.canManageDashboard`. */
export function canCreateOrganizationWideDashboard(role: UserRole): boolean { … }  // admin, organization_admin
```

**What "forms, not buttons" means concretely.** For a `location_admin` or an `asset_group_admin`, `apps/web/src/components/dashboards/dashboard-scope-fields.tsx` **does not render the organization-wide radio option at all**, and the Duplicate dialog does not offer it as a target. Not disabled, not hidden by CSS — absent from the DOM. The backlog row states the reason: gating only the buttons ships a page that looks editable and loses the work to a 403.

**Scope checks that need the server fall through to the API's refusal, rendered inline.** `accessibleScopeSchema` carries no organizations, so "may this user write in organization X" is not derivable on the client — the same residual decision 10 accepts. The 403 body (`"You may not create a dashboard with this scope"`, `dashboards.service.ts:295`) is rendered next to the form. `clearSessionOnAuthFailure` is **401-only** since `F4.52` (`apps/web/src/api/http.ts`), so the inline render actually runs and the user's typing survives — that file's docblock names ADR 0038 decision 10 as the thing this made reachable.

## 7. The point picker — how it is populated and why it cannot offer a foreign point

`F3.1b`'s `assertBoundPointsInOrganization` (`apps/api/src/dashboard-builder/dashboard-point-scope.ts`) refuses any `pointId` outside the dashboard's organization with a 400. The picker must not be able to produce one.

**Neither points endpoint carries an organization id.** `adminAssetPointDtoSchema` (`packages/shared/src/contracts/admin.ts:92-107`) has `assetId`, `locationId`, `pointKey`, `unit` and no `organizationId`; `adminAssetDtoSchema` has `organizationCode` and no id. So the picker cannot filter by organization directly.

**It filters by location instead, and the containment is structural.** `adminLocationDtoSchema` **does** carry `organizationId` (`admin.ts:26-43`), and `bms.locations.organization_id` is `NOT NULL` — one location belongs to exactly one organization. So the chain is:

1. The dashboard's `organizationId` is known (the create form chose it; an existing dashboard carries it in its DTO).
2. `GET /admin/locations` → keep only rows whose `organizationId` matches.
3. The author picks a location.
4. `GET /admin/asset-points?active=active&locationId=<id>` → every returned point belongs to an asset in that location, therefore to that organization.

A point reached this way cannot be one `assertBoundPointsInOrganization` refuses. That guard stays the enforcement; the picker is the second line of defence, exactly as `F3.1b`'s 403 is the second line behind the hidden org-wide form.

**Cardinality is enforced from the shared map, never a literal.** `WIDGET_CATALOG[type].points` already imports `WIDGET_POINT_CARDINALITY` (`widget-catalog.ts:79-80,93`), so the picker reads `min`/`max` from the catalog entry. A gauge accepts one binding and the *Add point* control disappears at the maximum; the same numbers `apps/api`'s `pointsFieldFor` refuses with.

**`min` is an authoring rule and never a read rule.** `dashboard_widget_points.point_id` is `ON DELETE CASCADE`, so a retired sensor can legitimately take a live gauge to zero bindings. Amendment 1 and `contracts/dashboard-builder.ts:232-236` both rule that this state stays readable and renders as *"no data bound"* — the **viewer must never hide or refuse a widget below `min`**, or a retired sensor becomes a missing dashboard. The builder's form warns; the viewer does not filter.

### Unit 9 — `feat(web)`: duplicate this dashboard

**New `apps/web/src/components/dashboards/duplicate-dashboard-dialog.tsx`.** The composition, client-side, per Amendment 2 ruling 3:

1. `GET /dashboards/:slug` (with `?organizationId=` when the caller is multi-org) → the full DTO.
2. `freeSlug(source.slug, takenSlugs)` from the already-fetched list — `<slug>-copy`, `<slug>-copy-2`, …, bounded at 50 attempts. §Task 0.2 is what makes that list collision-complete.
3. `POST /dashboards` with `{organizationId: source.organizationId, slug, name: "<name> (copy)", description, …scope}`. **The organization is never offered as a choice** — the copy stays inside the source's organization by construction, which is what keeps `assertBoundPointsInOrganization` satisfiable. 4. `PUT /:id/widgets` with the source widgets mapped DTO→write body: **drop every `id`** (those belong to the source rows), keep `widgetType`, `title`, the four grid fields, `config`, and `points: [{pointId, role, sortOrder}]`.

**Two behaviours to state rather than hide.**

- **It is not atomic.** If step 4 fails, an empty dashboard exists. The dialog then navigates into the builder on the new dashboard and renders the error inline, rather than issuing a compensating `DELETE` — a second failure path that can also fail. The operator sees a half-made copy, which is recoverable; a silent rollback that half-worked is not.
- **A copy carries the source's bindings.** `0050` does not constrain a dashboard's bindings by its scope, so a site dashboard copied into another site keeps the first site's points. Retargeting them is manual, and the dialog says so.
