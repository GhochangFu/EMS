# F3.69 — the dashboard site view (`SiteDashboardView`, `DashboardLiveCanvas`, the site page branch)

Plan by `plan-architect` (Fable), 2026-09-26, from ADR 0076 decisions 5 and 8
and the `F3.69` row. Measured read-only at `dd89de9f`. Scope gate: passed —
ADR 0076 is *Accepted* and names this row; no new ADR is owed, no migration is
needed (migration 0085 stays free). Merge approval (step 7) is still owed.

## Owner rulings (2026-09-26)

- **OQ1 → (a).** One `Open in Dashboards` link to the viewer. No Edit link on
  the site view; the viewer holds it behind `canAuthorDashboards`.
- **OQ2 → (a).** A failed dashboard read renders an inline `role="alert"` card
  with the API's message and a `Try again` button that refetches both the
  resolve read and the dashboard read. The fail-safe rule stays in the API
  (decision 5); no client copy of it.

## Goal

Replace the `F3.66` OQ2 interim card ("This site shows the dashboard {slug}" +
a link) in `SiteViewBody` with the configured dashboard rendered inline on
`/control-room/site/:locationId`: the same widgets, the same live socket
overlay, the same reads the dashboard viewer uses, hosted under the site
page's own breadcrumb, header and fail-safe banner. Nothing new is served: the
resolve DTO already carries `dashboardId` and `dashboardSlug`, the viewer
already reads by `(slug, organizationId)`, and the resolver already proved the
dashboard belongs to the site's organization.

**Out of scope.** No API route, no contract change, no migration, no seed. No
site target for section templates, no `F3.32` mimic (it arrives as a widget
type and renders here unchanged). No change to `/dashboards/:slug` behaviour,
to `app.tsx`, `app-shell.tsx`, `lib/smoc-pages.ts`, the `builtin` branch,
`control-room-route.tsx`, `use-control-room-access.ts`,
`lib/control-room-access.ts` or `tests/f4.156-*` (all `F3.70`'s). No
`AGENTS.md` edit in this branch.

## Measured facts the plan rests on

- **The resolve DTO is enough.** `resolvedSiteControlRoomViewDtoSchema`
  (`packages/shared/src/contracts/site-control-room-views.ts:49`) carries
  `dashboardId` and `dashboardSlug`; `resolveSiteControlRoomView`
  (`site-control-room-view.pure.ts:109-127`) sets both only after it compared
  `dashboard.organizationId` with the site's organization and re-checked the
  scope. `LocationKpiSummary.organization.id` on the page is therefore the
  organization id the viewer read needs. The dashboard's name comes from the
  `DashboardDto`. **No DTO growth, no contract edit.**
- **The viewer read.** `fetchDashboard(slug, organizationId?)`
  (`apps/web/src/api/dashboards.ts:109`) → `GET /dashboards/:slug?organizationId=`;
  throws `ApiError` with the status, so `lib/query-retry.ts` stops retrying a
  404/403 at once. `DashboardsService.getBySlug` routes by
  `readableOrganizationIds` and filters by the passed organization id.
- **Access follows from site read.** The resolve read admits a global scope or
  a scope that lists the location. `readableOrganizationIds` derives a
  non-admin's organizations from the same grants (`organization`, `location`,
  `asset_group`), so a user who can read the site normally holds its
  organization and `getBySlug` answers. **One exception (step-5 security
  review, Low 1; owner ruled a separate row, `F4.161`):** the two walks stop on
  different conditions — `scopeForUser` at the first source with a location or
  asset, `readableOrganizationIds` at the first source with any organization.
  A `viewer`/`operator` with an organization grant on an organization that has
  no sites or assets, plus a site grant in a second organization, reads the
  site but gets a 404 on the dashboard read: the OQ2 error card, closed, no
  leak. Widget values still go through `readableAssetIds`.
  **No new access rule on the web; no client-side gate.** A positive control at
  the API layer is missing today — U4 adds one.
- **The viewer is a page, not a component.** `DashboardViewerPage`
  (`apps/web/src/pages/dashboard-viewer-page.tsx`) owns `useParams`,
  `useSearchParams`, `AppShell`, `PageHeader` and the Edit link; the
  `useDashboardTelemetry` call, `now`, the tiles map, the empty-state line and
  `DashboardCanvas` + `DashboardWidgetLive` are the embeddable half.
  `useDashboardTelemetry` opens one `/ws/telemetry` socket, seeds from
  `fetchTelemetryRecent`, reads `fetchPointAggregate` and polls
  `fetchDashboardCatalogValues` — every one must be mocked in a jsdom spec,
  plus `socket.io-client` (precedent `generated-site-view.spec.tsx`).
- **The fail-safe is already end to end** (`F3.67` S9/S10,
  `assertSiteMovedToAnotherOrganizationIsOutOfScope`; `F3.66` V2/V3). Those
  cases answer `kind: "generated"`, so the dashboard branch never runs. The only
  new failure surface is the dashboard read failing after the resolve said
  `dashboard` (OQ2).
- **The page today.** `site-page.tsx:142-156` is the branch to replace; the
  null-slug fallback to `GeneratedSiteView` (V13a/V13b) stays. `site-page.spec.tsx`
  V7 asserts the interim card; V13b's `waitFor` reads `/This site shows the dashboard/`.
- **Silent gates.** `tests/repo-invariants.test.ts` fails a `.spec` without its
  `.test` wrapper; the jsdom docblock goes on the wrapper. No new file under
  `tests/`. No dashboard is seeded anywhere, so the browser run creates one.

## Decisions (engineering; reviewable at step 7)

- **D1 — no API or contract change.** Slug + the site's organization id address
  the read; the name comes from the answer.
- **D2 — extract the viewer's live canvas, byte-moved.** New
  `DashboardLiveCanvas({ dashboard: DashboardDto })` in
  `apps/web/src/components/dashboards/dashboard-live-canvas.tsx` holds
  `useDashboardTelemetry`, `now`, the tile map, the "This dashboard has no
  widgets yet." line and `DashboardCanvas` + `DashboardWidgetLive`.
  `DashboardViewerPage` renders it below its header, keeping its own query,
  loading and error lines.
- **D3 — `SiteDashboardView({ slug, organizationId })`** in
  `apps/web/src/components/control-room/site-dashboard-view.tsx`: `useQuery`
  with the viewer's key `["dashboards","detail",slug,organizationId]`. No
  refetch interval. Renders a `SectionCard` titled with the dashboard's name
  (the slug while pending), an `Open in Dashboards` link to
  `/dashboards/${encodeURIComponent(slug)}?organizationId=${encodeURIComponent(organizationId)}`,
  `<p role="status">Loading dashboard…</p>` while pending, the OQ2 error card,
  else `<DashboardLiveCanvas dashboard={data} />`. No `AppShell`, no
  breadcrumb, no notice, no Edit link.
- **D4 — the page edit is one branch.** `site-page.tsx:142-156` becomes
  `<SiteDashboardView slug={view.dashboardSlug} organizationId={site.organization.id} />`
  plus the import. Nothing else in the file moves.
- **D5 — chrome.** The site page keeps its breadcrumb, `PageHeader` and ribbon;
  the dashboard's name is the section title, not the page title.
- **D6 — access is not re-decided on the web.** A refusal renders as the OQ2
  error card.
- **D7 — live updates** are `useDashboardTelemetry` inside
  `DashboardLiveCanvas`, unchanged.
