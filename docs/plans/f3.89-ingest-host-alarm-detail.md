# F3.89 — The ingest-host alarm names the host, sites and RTUs; a deploy restart raises none

> **For agentic workers:** `superpowers:writing-plans` format. Build under TDD
> (red test first). **Not approved.** ADR 0127 Amendment 2 is *Proposed*; no
> code is built until the owner says yes to the amendment and this plan.

**Row:** `F3.89` in `docs/BACKLOG.md`. **ADR:** [ADR 0127 Amendment 2](../adr/0127-device-health.md).
**Base:** `main` at `479979d`.

**Goal.** An operator who gets "Ingest host not reporting" can read which host
stopped and which of their organization's sites and RTUs it took down, and a
normal deploy restart of the ingest host raises no alarm at all.

**Out of scope.** A deploy marker (ADR 0127 Amendment 2 Q5 option b). Any migration. The alarm grid's
subject and Site column. Notification transports.

---

## 1. Mechanisms, verified against source

- The text is the constant `INGEST_HOST_ALARM_MESSAGE`
  (`apps/api/src/device-health/device-alarm-rule.ts:38`), raised in
  `runDeviceHealthSweep` (`device-health-sweep.service.ts:126-141`), once per
  organization from `byOrganization(rows)`.
- `organizationHostReporting` uses `hostSummaryFor` over the hosts the
  organization's monitored RTUs name (`device-state.ts:84`).
- `RtuHealthRow` (`device-health.reads.ts:60`) has `code`, `displayName`,
  `hostKey`, `edgeServed`, `monitoredSinceMs` — **no location**. The read
  (`readRtuHealthRows`) joins `bms.rtus` but not `bms.locations`.
- `AlarmRaiser.raiseDevice` (`alarm-raise.service.ts:368`) inserts with a bare
  `ON CONFLICT DO NOTHING` arbitrated by `alarms_open_per_device_uidx`. An open
  alarm keeps its first message; a new text does not update or re-raise.
- Notifications send `input.message` as the body (`notifications.service.ts:585`);
  the dedupe key is the alarm, not the text (`notifications/dedupe-key.ts`).
  The clear text is `Cleared: <message>` (`alarm-lifecycle.ts:362`).
- The clear path (`alarm-lifecycle-device.ts:96`) reads host freshness only,
  never the message. Unchanged.
- Web: `alarm-source.ts` labels the subject "Ingest host"; the message renders
  as text in the grid, rail and details panel. No change needed.

## 2. Units (tests first in each)

### Unit 1 — `locationName` on `RtuHealthRow`
- **Test (integration, `device-health.integration.spec.ts`):** a monitored RTU
  read with `kind: "monitored"` carries its location's name; an RTU whose
  location name is empty reads `""`.
- **Code:** `readRtuHealthRows` joins `bms.locations l ON l.id = r.location_id`
  and returns `location_name` → `locationName: string`. Other readers of the
  row type ignore it (`tsc` lists them).

### Unit 2 — `ingestHostMessage` (pure, `device-alarm-rule.ts`)
- **Tests (`device-alarm-rule.spec.ts`, new):**
  1. one stale host, 3 Online RTUs at 2 sites → `Ingest host not reporting: cloud — 3 RTUs at 2 sites stopped: A, B; RTUs: R1, R2, R3`;
  2. 7 sites / 8 RTUs → 5 names each, `+2 more sites`, `+3 more`;
  3. an Offline RTU is left out; a Stale one is in;
  4. edge-served RTU counts; an RTU with no `monitored_since` does not;
  5. display name blank → code;
  6. RTUs of a fresh second host are left out; two stale hosts → `a, b`;
  7. a rowless host key (`never`) is named;
  8. no active RTU → `… cloud — no active RTUs`;
  9. a 255-character name is cut to 64; the message never passes 500;
  10. sorting is stable (same input in any order → same text);
  11. singular forms (`1 RTU at 1 site`).
- **Code:** `ingestHostMessage(rowsOfOrganization, hostsByKey, dbNowMs)`, using
  `hostStateAt` and `stateOf`. `INGEST_HOST_ALARM_MESSAGE` stays as the prefix.

### Unit 3 — the sweep uses it
- **Test (`device-health-sweep.service.spec.ts`):** the `ingest_host` raise
  carries the built message; two organizations on one host each get only their
  own names (no name of org B in org A's message); the warn log on a failed
  raise holds no site or RTU name (§9.6).
- **Integration (`device-health-sweep.integration.spec.ts`):** a stale host
  over seeded rows stores the built message on `bms.alarms`; a second tick with
  a changed RTU state leaves the message and the alarm id unchanged.
- **Code:** `message: ingestHostMessage(ofOrganization, hostsByKey, dbNowMs)`.

### Unit 4 — the raise hold (`INGEST_HOST_RAISE_AFTER_SECONDS` = 120)
- **Tests (`device-health-sweep.service.spec.ts`):**
  1. host last beat 119 s ago (a restart shorter than the hold) → no
     `ingest_host` raise **and** no `rtu_comms` raise (decision 6 hold);
  2. 120 s → one `ingest_host` raise with the unit-2 text;
  3. a rowless host key (`never`) raises at once;
  4. 45 s stale then fresh again on the next tick → nothing raised over both
     ticks (the AWS restart shape).
- **Tests (`device-alarm-rule.spec.ts`):** `ingestHostDue(rows, hosts, dbNowMs)`
  — `false` when reporting, `false` under 120 s, `true` at 120 s, `true` for
  `never`; `null` with no monitored RTU.
- **Clear path stays the same:** the existing `alarm-lifecycle-device` specs
  run unchanged (an open host alarm clears after 120 s fresh); add one that an
  alarm opened past the hold still clears on that rule.
- **Integration (`device-health-sweep.integration.spec.ts`):** a host row with
  `last_beat_at = now() − 60 s` raises nothing; `now() − 150 s` raises one with
  the new text.
- **Code:** `organizationHostReporting` stays (the clear uses it);
  `runDeviceHealthSweep` skips the RTU loop when not reporting (unchanged) and
  raises only when `ingestHostDue`. The constant sits beside
  `RTU_COMMS_RAISE_AFTER_SECONDS`.

## 5. Verification (§4.6)

- **API/unit + integration:** above.
- **AWS (owner, after deploy):** the next ingest restart raises one alarm per
  organization whose text names `cloud` and only that organization's sites;
  over the next 8 days the deploy restarts raise ~0 host alarms (was ~20 a day
  per organization); `bms-ctl ingest stop` for 3 minutes raises one per
  organization after ~120–150 s.
- **Browser:** skipped — the web renders the stored text unchanged; the jsdom
  specs already gate that the message shows.
