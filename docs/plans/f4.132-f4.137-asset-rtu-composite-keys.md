## 1. Goal and out of scope

**Goal.** Four constraints make the database hold what `AssetsService`, `RtusAdminService`, instantiation and the onboarding commit already derive in code: an asset's `organization_id` equals its location's, an RTU's `organization_id` equals its location's, and a wired asset's `rtu_id` names an RTU at the asset's own location. Migration `0113` refuses with counts if live data disagrees and never repairs. The Drizzle schema mirrors the keys, a `tests/` spec pins the migration text and the schema slices, a `tests/` integration file proves each key refuses a disagreeing write as `bms_tenant`, `bms_owner` and the superuser and accepts a consistent one, and the five fixture suites that plant a now-forbidden row plant it with constraints off.

**Out of scope.** Removing the service pre-checks (`assertRtuLocation`, `resolveLocationOrg`, `resolveAgreedOrg`, `locationBelongsToOrganization`) — they stay as the first refusal, the key is the backstop. Dropping the single-column FKs `assets_location_id_locations_id_fk`, `assets_rtu_id_rtus_id_fk`, `rtus_location_id_locations_id_fk` (the API maps 23503 on the last by name, `rtus.service.conflict.spec.ts:134,151`). `asset_points.rtu_id` (a different column, its own `assertRtuLocation` at `asset-points.service.ts:639`). Any API, contract or browser change — there is none, so §4.8 contract work is N/A. An RTU at an ancestor node serving child-node assets (not a shipped feature; see decision 6).

## 2. The constraint set and why

| Key | Table | Definition | Holds |
|---|---|---|---|
| K1 `rtus_id_location_key` | `bms.rtus` | `UNIQUE (id, location_id)` | target for K4; never refuses a row (`id` is the PK), the `asset_groups_id_location_key` reasoning |
| K2 `rtus_location_id_organization_id_fkey` | `bms.rtus` | `FOREIGN KEY (location_id, organization_id) REFERENCES bms.locations (id, organization_id) ON DELETE NO ACTION ON UPDATE NO ACTION` | RTU org = its location's org (the F4.138 drift becomes impossible) |
| K3 `assets_location_id_organization_id_fkey` | `bms.assets` | `FOREIGN KEY (location_id, organization_id) REFERENCES bms.locations (id, organization_id) ON DELETE NO ACTION ON UPDATE NO ACTION` | **F4.132** |
| K4 `assets_rtu_id_location_id_fkey` | `bms.assets` | `FOREIGN KEY (rtu_id, location_id) REFERENCES bms.rtus (id, location_id) ON DELETE NO ACTION ON UPDATE NO ACTION` | **F4.137**, location half; MATCH SIMPLE skips `rtu_id IS NULL` |

Target `locations_id_organization_key` exists since 0103 — reuse it. **Not added:** `assets(rtu_id, organization_id) -> rtus(id, organization_id)` (the F4.137 row's form) and its `rtus(id, organization_id)` unique. With K2 + K3 + K4 it is implied: asset.org = loc(asset).org (K3); asset.loc = rtu.loc (K4); rtu.org = loc(rtu).org (K2) = loc(asset).org = asset.org. A fifth key would add a unique index on `rtus` and no claim. K4 is the location form because every writer already enforces location equality (`assets.service.ts:532` refuses an RTU at another location; `asset-templates-instantiate-core.ts:428` puts the asset at the RTU's node; `hierarchy-seed.ts:357` picks the RTU at the asset's node), and the location form is the one that makes the org form redundant — the reverse is not true. K2 is required: without it K4 holds the location and nothing holds the RTU's own org (schema scout §1 confirmed no key exists).

```sql
SET ROLE bms_owner;

-- 1. K4's target. DDL only, no row read, so it may run as the owner (0103 §2).
DO $$
BEGIN
  IF NOT EXISTS (
    SELECT 1 FROM pg_constraint
    WHERE conname = 'rtus_id_location_key'
      AND conrelid = 'bms.rtus'::regclass
  ) THEN
    ALTER TABLE bms.rtus
      ADD CONSTRAINT rtus_id_location_key UNIQUE (id, location_id);
  END IF;
END $$;

RESET ROLE;

-- 2. Refuse, never repair. As the migrator's superuser: bms.rtus and bms.assets
--    carry FORCE ROW LEVEL SECURITY, so bms_owner under SET ROLE with no GUC
--    would count 0 and report success (0085 header).
DO $$
DECLARE
  rtu_org_drift   bigint;
  asset_org_drift bigint;
  asset_rtu_drift bigint;
BEGIN
  SELECT count(*) INTO rtu_org_drift
    FROM bms.rtus r JOIN bms.locations l ON l.id = r.location_id
   WHERE l.organization_id <> r.organization_id;
  SELECT count(*) INTO asset_org_drift
    FROM bms.assets a JOIN bms.locations l ON l.id = a.location_id
   WHERE l.organization_id <> a.organization_id;
  SELECT count(*) INTO asset_rtu_drift
    FROM bms.assets a JOIN bms.rtus r ON r.id = a.rtu_id
   WHERE a.location_id <> r.location_id;

  IF rtu_org_drift > 0 OR asset_org_drift > 0 OR asset_rtu_drift > 0 THEN
    RAISE EXCEPTION
      'migration 0113: live data disagrees — rtus_location_id_organization_id_fkey: % row(s), assets_location_id_organization_id_fkey: % row(s), assets_rtu_id_location_id_fkey: % row(s)',
      rtu_org_drift, asset_org_drift, asset_rtu_drift
      USING HINT = 'Repair the rows by hand (ADR 0102 decision 3): the asset or RTU takes its location''s organization, and a wired asset''s rtu_id must name an RTU at the asset''s own location. This migration never rewrites a row.';
  END IF;
END $$;

-- 3–5. The three keys, each behind its pg_constraint probe (ADD CONSTRAINT on a
--      populated table validates every row; §2 reported any failure first).
```
