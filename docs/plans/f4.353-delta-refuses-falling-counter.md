## 1. Goal

`delta({kwh_total}, today)` is last sample minus first sample. When the
cumulative register sends one bad `0` (the AWS demo, `PHE-MFM-000000004` on
2026-11-08 and `PHE-MFM-000000003` on 2026-11-10), the `0` is the window's last
sample for a few ticks, and `kwh_today` / `_this_month` / `_this_year` and the
three `energy_cost_*` points are written as large negative numbers (down to
−74,067 kWh and −555,502 in cost).

After this row, `deltaOf` refuses with a new reason **`window_decreasing`**
when `last < first`. The formula writes nothing for that tick; the skip counter
and `CalcStatusRegistry` record it, as for `window_empty`. When the register
comes back, the next tick writes the right value again.

## 2. Out of scope

- A reset-aware `delta` (declined at the gate: needs a range scan).
- A bad sample as the window's **first** sample (Amendment 8 "What this
  costs"; the ingest `eng_min` / `eng_max` band is the cover, an owner
  configuration step).
- Recomputing or deleting stored rows (no backfill job; the owner's AWS step
  is written in the PR body and the closure record).
- Any change to `avg`, `min`, `max`, `sum`, `hours`, the planner or the SQL.

## 5. AWS repair (the owner's step; nothing is run from the session)

Stored negative rows stay until removed. Run as the **superuser**
(`DATABASE_URL_SUPERUSER`): `bms.assets` is under FORCE RLS, so as
`bms_owner` the asset lookup returns nothing; and the aggregates belong to
`bms_rollup`. All instants are written in UTC on purpose: a bare
`'2026-11-08'` is read in the session's zone.

1. **Preflight** — see every derived key that went wrong, not only the six
   energy keys (the stock feeder also derives `co2_kg_*` and
   `energy_saving_vs_baseline_pct` from the same `delta`; a saving goes above
   100, not below 0):

   ```sql
   SELECT a.code, v.point_key, count(*), min(v.value), max(v.value),
          min(v.time), max(v.time)
     FROM telemetry.point_values v
     JOIN bms.assets a ON a.id = v.asset_id
    WHERE a.code IN ('PHE-MFM-000000003','PHE-MFM-000000004')
      AND v.time >= '2026-11-08T00:00:00Z' AND v.time < '2026-11-11T00:00:00Z'
      AND ((v.point_key <> 'energy_saving_vs_baseline_pct' AND v.value < 0)
           OR (v.point_key = 'energy_saving_vs_baseline_pct' AND v.value > 100))
    GROUP BY 1, 2 ORDER BY 1, 2;
   ```

2. **Compression.** Raw rows compress after 7 days, so the 2026-11-08
   chunk (1-day chunks, `compress_after` 7 days) becomes eligible to compress
   around 2026-11-16 00:00 UTC. Run the delete before then if you can.
   After that, check `timescaledb_information.chunks` (`is_compressed`) for
   the range first: a delete on a compressed chunk is slower and may need the
   chunk decompressed.
3. **Delete**, in one transaction, the keys the preflight listed:

   ```sql
   BEGIN;
   DELETE FROM telemetry.point_values v
    USING bms.assets a
    WHERE a.id = v.asset_id
      AND a.code IN ('PHE-MFM-000000003','PHE-MFM-000000004')
      AND v.time >= '2026-11-08T00:00:00Z' AND v.time < '2026-11-11T00:00:00Z'
      AND v.point_key IN ('kwh_today','kwh_this_month','kwh_this_year',
                          'energy_cost_today','energy_cost_this_month','energy_cost_this_year')  -- + any others from step 1
      -- a saving % is legitimately negative (consumption under baseline); a bad
      -- delta pushes it ABOVE 100, so that key gets its own test
      AND ((v.point_key <> 'energy_saving_vs_baseline_pct' AND v.value < 0)
           OR (v.point_key = 'energy_saving_vs_baseline_pct' AND v.value > 100));
   -- the row count should match step 1's total (about 8 ticks × each key); ROLLBACK if not
   COMMIT;
   ```

4. **Refresh** the four aggregates over the same range, each `CALL` on its own
   (never inside a transaction block), in this order:

   ```sql
   CALL refresh_continuous_aggregate('telemetry.point_values_1m', '2026-11-08T00:00:00Z', '2026-11-11T00:00:00Z');
   CALL refresh_continuous_aggregate('telemetry.point_values_5m', '2026-11-08T00:00:00Z', '2026-11-11T00:00:00Z');
   CALL refresh_continuous_aggregate('telemetry.point_values_1h', '2026-11-08T00:00:00Z', '2026-11-11T00:00:00Z');
   CALL refresh_continuous_aggregate('telemetry.point_values_1d', '2026-11-08T00:00:00Z', '2026-11-11T00:00:00Z');
   ```

   The range is far inside raw retention (730 days), so this repairs and does
   not drop (ADR 0024). Use these targeted calls, not
   `pnpm db:refresh-aggregates`.
5. **The raw `kwh_total = 0` samples are left in place** by this plan: they
   are what the meter sent, and they show as a dip on a `kwh_total` trend.
   Deleting them too is the owner's choice (add `kwh_total` and
   `v.value = 0` as a second delete before step 4).
6. **Recommended:** set an engineering floor on `kwh_total` for the PHE
   meters (`eng_min = 1`) so a bad `0` is dropped at ingest. This also covers
   the first-sample case this rule cannot see (Amendment 8, "What this
   costs").
