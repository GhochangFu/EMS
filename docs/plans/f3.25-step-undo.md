## 1. Goal

Each chat turn that changes the onboarding draft records a checkpoint of the seven draft sections (`location`, `rtus`, `pointKeys`, `assets`, `assetPoints`, `templates`, `onboardingMeta`) taken **before** the write, in a new nullable `bms.onboarding_sessions.checkpoints jsonb` ring of the last 10. The user undoes the last step with the exact phrase `undo`, or rolls back to a named checkpoint through `POST /api/v1/admin/onboarding/sessions/:id/rollback` bound to the checkpoint id and the draft hash the client last saw (409 on a mismatch, nothing written), with a web Undo control. A rollback assigns the seven sections wholesale, keeps `_secrets` and runs `reconcileSecrets`, clears `_commitProposal`, re-derives the phase with `inferPhase`, cuts the ring to the entries before the restored one, and appends a code-written `Undid: <label>` action line. The `confirm <step>` labels (F4.199) are answered by `confirmStepTurn` on the agent path too, never reaching the model. A 25th tool `suggest_replies` lets the model offer up to 4 chips; code drops `confirm commit`, `undo` and anything that `looksLikeCredential`, adds the current step's label and `View draft`, and replaces the hardcoded `["View draft"]`. Checkpoints never reach the client or the prompt: the session DTO carries summaries (`id`, `seq`, `label`, `takenAt`) and `draftHash` only. The ADR 0090 commit model does not change.

**Out of scope.** Per-step commit to master data; rollback after commit; staged edits; redo; checkpoints for the Excel upload, `PATCH` draft or the credential route (they clear the ring — Q3); a model undo tool; any `AGENTS.md` edit (the "24 tools" line at `AGENTS.md:1439` and the §6 wording are a separate `chore(agents):` PR, §9.10); `F3.23`'s Q&A text (it reuses the primitive).

## 3. Open questions (the owner rules before U1; the plan assumes the recommendation)

- **Q1 — how the client gets the hash and the list (ADR *Left to the plan* 1).** *Recommended:* `onboardingSessionDtoSchema` gains `checkpoints: z.array(onboardingCheckpointSummarySchema)` and `draftHash: z.string().nullable()`, filled by `mapSession`. The summary schema is `.strict()` so a leaked `sections` key fails the web's parse. `draftHash` is SHA-256 of the stored draft minus the proposal; it reveals nothing. Gated by the shared contract spec and the `mapSession` cases in U3.
- **Q2 — a byte bound on the ring (point 2).** *Recommended: yes.* The draft caps allow 5,000 asset points, 500 assets, 100 RTUs with open `config` records, so one snapshot can reach about 1 MB; ten of them ride in the row every `loadSession` reads. `MAX_CHECKPOINT_RING_BYTES = 2_000_000` on `JSON.stringify(ring)`: evict the oldest until under; a single snapshot over the bound is not recorded, and `chat` logs `{ sessionId, dropped: "too_large" }` (counts only, decision 9 of ADR 0090). Gated in U2.
- **Q3 — `PATCH` draft and the Excel upload versus the ring (point 3).** *Recommended: both clear the ring (`checkpoints: null`); `POST :id/credentials` leaves it.* This departs from the Phase A draft plan ("record nothing, clear nothing"). Reason: the hash binding protects a stale tab, not the same tab — add an asset by chat, then rename the location in the preview (PATCH), then type `undo`: with the ring kept, the restore brings back the old name and the PATCH is lost silently. A rollback must never cross a write it did not checkpoint. Cost: a manual edit ends undo history until the next chat step. Gated in U3.
- **Q4 — redo (point 4).** *Recommended: no.* A rollback records no checkpoint; the ring is cut to entries with `seq` below the restored one. Gated in U4.
- **Q5 — tool or reply field (point 5).** *Recommended: a 25th tool `suggest_replies`.* A field on the provider's final reply needs structured output in both adapters and the port; a tool is one registry entry, one `ToolState` field, and it is classified `agent_only` in `GUIDED_TOOL_COVERAGE` (reason names ADR 0094, which the coverage spec's regex accepts). Pins 24 → 25 at `onboarding-agent-tools.spec.ts:82`, `onboarding-template-tools.spec.ts:70`, `onboarding-template-tools.test.ts:62` and the docblock `onboarding-agent-tools.ts:204`. `AGENTS.md:1439` is the sweep's. Gated in U5.
- **Q6 — where the step-label intercept sits.** ADR 0094 decision 8's plan detail says "the match moves from `handleRuleBasedTurn` to `handleTurn`, before the mode choice". On the stack head `confirm point keys` at the point-key step **writes** `use_existing_point_keys` on the guided path when the organization has keys (`onboarding-chat-rule-based.ts:233-236`, F4.195, pinned by `onboarding-chat-point-keys.spec.ts:487-495` and offered by `excelImportFollowUp` at `onboarding-chat.service.ts:190-194`). An intercept before the mode choice shadows that write. *Recommended:* the intercept runs in `handleTurn` on the **agent path only** (after the `resolved.kind === "guided"` return, before `runAgentTurn`); the guided path keeps its own match. Net behaviour is the ruling's: both modes answer by code and no label reaches the model. Residual: `confirmStepTurn`'s prompt text is guided wording ("say **kw**") in both modes — by decision 8, recorded in the closure.
- **Q7 — the web chip filter.** *Recommended:* `offeredReplies` drops `undo` as well as `confirm commit` (defence in depth; ADR 0094 decision 9 names the server filter as the guard). Two lines in U6.
- **Q8 — the commit-close gate.** `onboarding-commit.service.ts:577` gains `checkpoints: null`. Its unit harness (`onboarding-commit.service.spec.ts:54 buildService`) may not record `set` values; if it does not, the assertion goes to `onboarding-commit-templates.integration.spec.ts` (DB-gated; a local skip is reported as a skip, never as green).
