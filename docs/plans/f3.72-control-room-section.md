# F3.72 — One Control Room section (ADR 0087 decisions 1–3): step-3 plan

Plan written on Fable (`plan-architect`) on 2026-09-30 against `e46d04cb`;
owner rulings OQ1–OQ9 taken the same day, one at a time, and folded in below
(§8 records them; where a ruling changed the drafted design, the design text
here is the ruled one). ADR [0087](../adr/0087-one-control-room-and-smoc-standard-site-template.md)
is merged (#660, `182cd460`). In the first stable version by owner ruling
(ADR 0087 gate question 9; merge cutoff 2026-09-30 end of day).

## 1. Goal

One sidebar entry, **Control Room**, replaces **Dashboard**. Its levels:
**Estate** (today's `/` content, plus organization cards) → **Organization**
(ADR 0076 decision 2, plus Asset health and the 60-minute load trend for that
organization) → **Site** (today's site view, plus a fixed **Assets & RTUs**
tab holding today's `/locations/:id/dashboard` content). `/` renders the
caller's entry level in place (no redirect); `/locations/:id/dashboard`
redirects to the site's Assets & RTUs tab; each level lists the library
dashboards for its scope with an Open link. The level-skip rule of ADR 0076
decision 2 stays.

**Out of scope:** `F3.73`–`F3.75`; any schema change; the `/dashboards`
library page itself; the "Domain-first navigation IA" decision; the
`chore(agents):` sweep.

## 2. Measurements that shape the plan

- `GET /dashboard/kpis` and `GET /dashboard/load-trend` take no organization
  filter (`apps/api/src/dashboard/dashboard.controller.ts`: `readableAssetIds(user)`
  only). `GET /asset-health/summary` takes `locationId` only
  (`asset-health.schema.ts` says "no `organizationId`, deliberately"). The
  narrowing precedent is `F3.66` step 5: `organizationId` on `/alarms` and
  `/alarms/summary`, ANDed onto the readable set
  (`AccessControlService.readableAssetIdsInOrganization`, `[]` for an
  unreadable organization → empty, never 403). Both services already take
  `assetIds`.
- `GET /dashboards` filters by `organizationId | assetId | section`; no
  `locationId` filter. The summary DTO carries `locationId`, `assetGroupId`,
  `assetId`, but not the group's location. OQ6 ruled: add the API filter now.
- `apps/web/src/lib/landing-route.ts` sends a one-location user to
  `/locations/:id/dashboard` after login (`login-page.tsx`, `auth-callback-page.tsx`).
  With `/` rendering the entry level it is dead: delete it; both callers
  `navigate("/", { replace: true })`.
- `LocationKpiCard.to` default is `/locations/:id/dashboard`. OQ3 keeps the
  estate accordion, so the default stays and changes to the site view (OQ7).
- `world-map.tsx` links "Dashboard →" to `/locations/:id/dashboard` — link it
  straight to the Assets & RTUs tab (OQ9).
- `ControlRoomScopeRoute` sends a `none` scope to `/`. **`/` must not be
  wrapped in it** (a loop). The entry page handles `none` itself: the KPI read
  answers `{ items: [] }` and the "No sites in your access scope" card renders.
- `tests/f3.66-control-room-routes.test.ts` fails closed on any
  `<ControlRoom…Page` use outside the three wrapped routes and requires each
  scope page exactly once in `app.tsx`. The `/` route breaks both claims by
  construction; the gate is updated to claim `/`.
- SMOC tab keys are `overview|sld|ups|battery|hvac|env|it` (`lib/smoc-pages.ts`);
  the new key `assets` collides with none.
- Spec files export functions; the `.test.tsx` wraps them. New cases follow.

## 3. Design decisions

- **D1 `/` and `/control-room`.** `ControlRoomOrganizationsPage` gains a
  boolean prop `entry`. Without it (at `/control-room`) it keeps today's
  behaviour, except that the organizations level renders `<DashboardPage user />`
  (the estate) instead of its own card grid. With `entry` (at `/`,
  **unwrapped**) it renders the target level **in place**: organizations →
  `<DashboardPage user />`; organization → `<ControlRoomOrganizationPage user organizationId={id} />`;
  site → `<ControlRoomSitePage user locationId={id} />`; empty → the no-sites
  card without the "Back to the dashboard" self-link. Pending/error states
  unchanged. The URL stays `/` (OQ2). `ControlRoomOrganizationPage` and
  `ControlRoomSitePage` each gain an optional id prop that overrides
  `useParams()`.
- **D2 Estate = `DashboardPage`** (file and name kept). Title
  **"Control Room · Estate"**, eyebrow "Control Room" (OQ4) — the ribbon text
  follows. Order: KPI tiles; an **"Organizations"** `SectionCard` holding
  `OrganizationCardGrid` (the grid extracted from `organizations-page.tsx`,
  cards link to `/control-room/org/:id`); **the existing "Location performance"
  section stays unchanged** (org filter tabs + accordion + filtered grid, OQ3),
  its cards now open the Control Room site view (OQ7); `HealthSummarySection`;
  the load trend; a "Dashboards" section (`ScopedDashboardsList`).
- **D3 Organization level** adds, under the site grid: `HealthSummarySection organizationId`,
  an `OrganizationLoadTrend organizationId` card (plain `useQuery` on
  `fetchLoadTrend("60m", organizationId)`, `refetchInterval: 60_000`, no
  socket and no stale pill — the socket sum is estate-wide), and
  `ScopedDashboardsList organizationId`. Not rendered for the `empty` target.
- **D4 Site tab.** Key `assets`, label **Assets & RTUs**. The site page renders
  its own two-entry strip above the body: **Site view** (bare path,
  `aria-current` when `tabParam !== "assets"`, OQ5) and **Assets & RTUs**
  (`/control-room/site/:id/assets`). The SMOC seven-tab strip stays inside
  `SmocSiteView` under "Site view". Redirect rule (F3.70 D5) becomes:
  `tabParam !== undefined && tabParam !== "assets" && (!showsSmocTabs || tab === null)`.
  `assets` renders for every kind and every site the caller can read; a
  rejected resolve read still shows the not-available card.
- **D5 `SiteAssetsView`** (`components/control-room/site-assets-view.tsx`,
  `{ locationId }`): `location-dashboard-page.tsx`'s state, query and body
  moved verbatim; the `AppShell`, `PageHeader` and ribbon are not moved. One
  prose change: the "Access denied" link `Return to Main Dashboard` →
  **"Back to the Control Room"** to `/control-room` (OQ8).
  `LocationDashboardPage` is deleted; `/locations/:locationId/dashboard`
  renders `<LocationDashboardRedirect />` inside `ControlRoomScopeRoute`.
- **D6 Sidebar.** Remove `{ label: "Dashboard", path: "/" }`; the Control Room
  item is `aria-current` at `/` too. Top-nav "Overview → /" stays.
- **D7 `ScopedDashboardsList`** (`{ organizationId?: string; locationId?: string }`):
  reads `fetchDashboards` with the organization filter, and with the new
  `locationId` filter when given (OQ6); a `SectionCard` "Dashboards" with rows
  `name` + `Open` link to `/dashboards/${slug}?organizationId=${dashboard.organizationId}`;
  loading / error / "No dashboards for this scope." states.
- **D8 API** — three reads, controller/service only, response shapes unchanged:
  - `organizationId` on `/asset-health/summary` and `/dashboard/load-trend`
    (OQ1): when present, `readableAssetIdsInOrganization(user, organizationId)`
    replaces `readableAssetIds(user)`; malformed → 400. The "deliberately no
    organizationId" docblock is rewritten to the `F3.66` narrowing rule.
  - `locationId` on `GET /dashboards` (OQ6): matches a dashboard whose
    `location_id` is that location **or** whose `asset_group_id` is a group of
    that location (`bms.asset_groups.location_id`). ANDed beside the
    organization conditions — narrows within the read scope, never widens; an
    unknown or unreadable id answers `[]`, never 403 (ruling 4 of ADR 0068).
    Register the field where `listDashboardsQuerySchema` is registered
    (`openapi-registry.ts` `REQUEST_SCHEMAS`, `strict-body-ledger.spec.ts`
    `QUERY_SCHEMAS`).
- **D9 Gates.** New `tests/f3.72-control-room-entry.test.ts` (inline
  assertions, listed in the root `typecheck:tests` script).
  `tests/f3.66-control-room-routes.test.ts` updated to claim `/`.
