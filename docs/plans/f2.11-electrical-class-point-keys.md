## 1. Goal, and what is out of scope

**Goal.** `docs/electrical-derived-taglist-v1.md` is the v1 point basis for the six electrical asset classes (feeder/incomer, transformer, DG set, UPS, solar PV, APFC). 139 of its codes exist nowhere in the platform's vocabulary. Migration `0058` gives `bms.template_points.point_key` a foreign key to `bms.point_keys(code)` (ADR 0051 Amendment 3), so `F2.12` cannot author a single class template until those codes are in the table. This row puts them there: **one array, `ELECTRICAL_CLASS_POINT_KEYS`, of exactly 139 codes in `packages/shared/src/constants.ts`; 139 explicit `UNIT_BY_KEY` entries in `packages/db/src/point-keys-seed.ts`; one `keysForDomain(..., "electrical")` line appended to `GLOBAL_CATALOG`; three guard numbers moved to their new actuals.** It is `F3.41`'s shape at ten times the size. `bms.point_keys` goes 49 → **187** on a cold start (§3.1 — not 188).

**Explicitly out of scope.**

- **Any class template.** `F2.12` authors those and now waits on `F2.13` (ADR 0052, Accepted 2026-09-02 — the stock asset-template catalog). This row authors zero template content.
- **The prose "Derived:" paragraphs under each class table.** Amendment 6 decision 8: `load_pct` on a feeder, `demand_vs_contract_pct`, `hot_spot_estimate_c`, `performance_ratio_pct`, `specific_fuel_l_kwh`, `duval_triangle_zone` and the rest are derived points needing a `bms-calc-v1` formula, and most reference an asset attribute the grammar cannot name (ADR 0036; the fork `F2.9` records). **Only table rows are promoted.** `F2.12` promotes each derived code it can actually author a formula for, per formula.
- **`dga_lab_result`.** Decision 7: its unit is `text` and `telemetry.point_values.value` is a finite `double precision` (`F4.32`). It stays a lab record for `F1.13`/a maintenance note. The four numeric DGA rows carry what a point can.
- **Merging into `ELECTRICAL_POINT_KEYS`.** Decision 2. That array's own docblock says "keep in sync with simulator" and nothing simulated writes these. Merging would also break `tests/f3.39`'s clash check, which needs the arrays disjoint.
- **Six per-class arrays.** Decision 2. Three codes recur across classes (`ambient_temp_c` §2/§4/§5, `thd_v_pct` §1/§6, `battery_v` §3/§4) and all 25 reused codes would clash against the existing arrays. Class membership is `F2.12`'s content.
- **No migration and no SQL file.** Decision 6. `bms.point_keys` has been seed-seeded since `0057`; this stays on that side.
- **The water/process vocabulary.** `flow_rate`, `ph`, `cod`, `dissolved_oxygen` stay on `KEYS_AWAITING_A_VOCABULARY` in `tests/f3.38-stock-catalog-vocabulary.test.ts` and its `stillOutside` test stays green untouched. **Verified by set intersection: none of the four appears in any of the six class tables.** They land when `E5.1` promotes its own array, on this row's path.
- **`rule-points.ts`, `control-room-bindings.ts`, `contracts/dashboard.ts`.** Each names its arrays explicitly; an eighth is invisible to all three. No new `z.enum`, no `electricalClassPointKeySchema` — nothing consumes one. See §6.
- **No `AGENTS.md` §6 edit and no `docs/BACKLOG.md` ✅ mirror in this branch** — §9.10, separate `chore(agents):` PR.

### 3.1 The cold-start count is **187**, not 188 — and `battery_charge_pct` is why

The ADR's Consequences bullet and the backlog row both say "49 to 188", which is `49 + 139`. That arithmetic assumes all 139 codes are new **rows**. One of them is not.

`battery_charge_pct` is §4's *"Battery charge remaining, %, C"*. It is in no `*_POINT_KEYS` array, so by the ruling's own measurement rule it is one of the 139. But it **already occupies a row in `bms.point_keys`**, arriving by the two paths `constants.ts` cannot see — `bmsPointKeyForSensor`'s `BC: "battery_charge_pct"` in `packages/db/src/phe-pilot-seed.ts:64`, and migration `0057`'s orphan sweep. ### 3.2 Three further effects of that one code, all determined by decisions 3 + 7

`seedPheCatalog` runs at `packages/db/src/seed.ts:186`; `seedPointKeyCatalog` runs at `:217`, **after** it. The catalog upsert is

```sql
ON CONFLICT (code) DO UPDATE SET
  name = EXCLUDED.name,
  domain = EXCLUDED.domain,
  unit = COALESCE(bms.point_keys.unit, EXCLUDED.unit)
```

So once `battery_charge_pct` joins `GLOBAL_CATALOG` under `electrical` with unit `"%"`:

1. **`domain` flips `environment` → `electrical`.** `domain` is assigned outright, not `COALESCE`d. Consistent with decision 3, which is unconditional. **Owner ruling 2026-09-02 (§9 Q3): the flip is accepted.** Note this happens on the **next `pnpm db:seed` on any database**, not only a cold start — so it is observable in the API layer without the scratch DB.
2. **`unit` fills `NULL` → `"%"`** through the `COALESCE`. An improvement (the code carried no unit at all), and the only value this row can ever write for it — see §7.2.
3. **No test fails on either.** `tests/f3.39`'s clash check compares only the `*_POINT_KEYS` arrays; `phe-pilot-seed.ts`'s inline registration is invisible to it. That is the same blind spot `F3.41` discovered from the other side, so the plan states it rather than relying on a guard.

**Two documented statements go stale in this commit and must be corrected in it** — F3.41's own rule, in its words: *"that comment becomes stale in this commit and must be corrected in it."* Task 2, step 4.

### 3.3 Why the array stays in `constants.ts` — the guards decide it, not the line count

Constraint: AGENTS.md §4.5 caps a file at 1000 lines. `constants.ts` is 173 today; +139 code lines, +1 `export const`, +1 `] as const;`, +2 for the type alias, +~45 docblock ≈ **365 lines**. The cap is not in play.

But the real reason is stronger and must go in the plan so a future §4.5 split does not break it silently. **Both guards read `packages/shared/src/constants.ts` as text:**

- `tests/f3.38-stock-catalog-vocabulary.test.ts:130` — `pointKeyVocabulary` matches `/export const [A-Z_]*POINT_KEYS = \[([^\]]*)\]/g` against `CONSTANTS_REL`.
- `tests/f3.39-global-point-key-vocabulary.test.ts:453` — `arraysByName` matches the same shape against the same file.

A sibling `packages/shared/src/electrical-class-point-keys.ts` re-exported from `index.ts` would be **invisible to both, with nothing failing**: the array would be neither clash-checked nor unit-coverage-checked, and `tests/f3.38`'s vocabulary would silently not contain the 139 codes. **The array goes in `constants.ts`. State that reason in the docblock.**

Two corollaries for the array's shape:

- **The name must match `/[A-Z_]*POINT_KEYS/`** — uppercase and underscore only, no digits. `ELECTRICAL_CLASS_POINT_KEYS` satisfies both regexes.
- **The array body must contain no `]` character** — both regexes use `[^\]]*`. 139 quoted snake_case strings and comments without brackets are fine; **do not put a `[…]` citation inside the array literal.**
