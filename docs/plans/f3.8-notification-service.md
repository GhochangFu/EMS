## 1. Goal, and what is out of scope

**Goal.** Give the platform one way to tell a human that an alarm opened, and
make the *absence* of that path visible instead of silent. Concretely: one
additive migration adds a channel vocabulary, a channel table, a
rule↔channel join and a delivery ledger; a `NotificationTransport` interface
gets three implementations (log, email, webhook) chosen by configuration; a
`NotificationService.dispatch()` records one `bms.notification_deliveries` row
for every attempt *including every skip*, bounded by a transition dedupe and a
per-channel hourly ceiling; the webhook transport refuses its own network
before it sends; and two browser surfaces plus a readiness banner make all of
it operable without reading a log file.

**Explicitly out of scope.**

- **The two `AlarmRaiser` call sites.** See §2 — this is the one boundary the
  ADR states twice and it belongs to `F3.7`. `F3.8` ships
  `NotificationService.dispatch()` and nothing calls it from the raise path.
- **No queue, no worker, no Redis, no `apps/worker`** (decision 1). AGENTS.md §6
  puts job queues out of scope until `F4.24` promotes them, and `F3.8`'s
  `Depends` cell is `—`. If your diff imports `bullmq` you have left the item.
- **No SMS, no push** (`F3.9`). A fourth transport, later, with no schema change.
- **No escalation, no auto-clear** (`F3.10`). It reads
  `bms.notification_deliveries`; it does not extend it here.
- **No change to `automation_rules.action`** (decision 3). Same three values,
  no new column, no backfill.
- **No widening of `AlarmRaiseRule` and no edit to `alarm-raise.service.ts`**
  (decision 9). ADR 0033 made `AlarmRaiser` the one writer of `bms.alarms`;
  it does not become the notifier.
- **No role-derived or default recipients** (decision 11). Reopening that needs
  a new ADR, not a flag.
- **No template engine.** Message bodies are string composition off the fields
  `composeAlarmMessage` already produces.
- **`SMTP_HOST` gets no default in `docker-compose.yml`** (decision 12). This is
  an out-of-scope item in the strongest sense: adding one is the failure the
  decision exists to prevent, and an invariant test asserts its absence.

### The boundary: `F3.8` stops at `dispatch()`

ADR 0041 decision 9 is titled *"Both raise paths dispatch"* and names
`RulesService.evaluateEnabledRules` and `AlarmEngineService`. Read alone it
sounds like `F3.8` work. It is not, and the ADR says so twice:

- decision 9's own last paragraph — *"`F3.7` must therefore add `action` to that
  cached `SELECT`"*;
- Consequences — *"`F3.7` becomes buildable: it wires `action.type === 'notify'`
  to `NotificationService.dispatch`"*.

**So decision 9 is a constraint on where dispatch may sit, not a work item in
this row.** Its purpose is to stop `F3.8` from hiding dispatch inside
`AlarmRaiser` where `F3.7` could not reach it, and to record — before anyone
builds `F3.7` — that `CachedThresholdRule` carries no `action` today.

**This plan therefore assumes:** `F3.8` delivers
`NotificationService.dispatch(input)` with the signature U6 fixes, plus its own
tests against a fake transport, and **no caller in the raise path**. Absorbing
the wiring would merge `F3.7` into a 7–9 item and leave the board saying two
rows are open when one piece of work exists.

If the owner reads decision 9 the other way, the correction is small and
additive — two call sites and one widened `SELECT` — but it is theirs to make,
not this plan's.

### Decisions this plan makes (not questions — do not escalate them)

**D1. A rule joins its channels through `PUT /api/v1/rules/:id/notifications`.**
Decision 3 creates `bms.rule_notifications` and decision 11 says a rule notifies
exactly the channels joined to it, but ADR 0041 names no route that writes that
join. Without one, migration `0038` ships a table nothing can populate and the
whole item sends nothing by construction. The route takes
`{ channelIds: string[] }`, replaces the set for that rule, and is authorised
like every other rule write (`assertOperationsWriteRole(user, "configuration")`),
because attaching a recipient to a rule is rule authoring. It lives in
`rules.controller.ts` beside the other rule writes rather than in the
notifications controller, so the scope check that already guards rule writes
guards it too.

**D2. The webhook HMAC secret goes in dedicated ciphertext columns, not inside
`config` jsonb.** Decision 8 says the secret goes through
`CredentialCryptoService`; that service returns
`{ ciphertext: Buffer, iv: Buffer, keyVersion: number }`
(`apps/api/src/security/credential-crypto.service.ts`), which is three values,
not one. Putting them in `secret_ciphertext bytea`, `secret_iv bytea`,
`secret_key_version integer` — the shape the RTU credential columns already use
— keeps `config` free of anything secret, which is what makes decision 8's
"never log `config`" cheap to hold rather than a rule someone has to remember.

**D3. `notification_deliveries.status` gets a CHECK constraint, not a lookup
table.** ADR 0031 Amendment 1 and ADR 0032 make *domain* vocabularies open
(severity, category, asset domain) because a domain pack extends them with an
INSERT. These five statuses are produced only by `NotificationService` and by
nothing else, ever; an operator cannot add a sixth without new code to emit it.
`notification_channel_kinds` **is** a lookup table, per decision 3 and the
`prefer-dynamic-vocabularies` pattern, because a fourth kind (`F3.9` SMS) is a
data + transport addition. The line is the same one `alarm_severities.tone`
draws: open where the domain grows, closed where the code owns it.

**D4. Rate-limit default lives in config as `NOTIFY_RATE_LIMIT_PER_HOUR`,
default 60.** Decision 7 names the number but not where it lives. Environment,
read once at module init like the SMTP settings (decision 8), so a noisy pilot
can be turned down without a deploy of new code.

**Interfaces produced:** Drizzle tables `notificationChannelKinds`,
`notificationChannels`, `ruleNotifications`, `notificationDeliveries`, exported
from `@bms/db`.

**Step 1 — write the migration.** Follow `0030_alarm_severity_vocabulary.sql`'s
shape exactly: a leading comment block that argues the design, `CREATE TABLE IF
NOT EXISTS`, seeds with a bare `ON CONFLICT DO NOTHING` (no conflict target —
0030's comment explains why a named target aborts the transaction when a second
unique constraint collides), and every `ADD CONSTRAINT` wrapped in a
`DO $$ ... IF NOT EXISTS (SELECT 1 FROM pg_constraint WHERE conname = ... AND
conrelid = 'bms.x'::regclass) ... END $$;` block.

```sql
-- 1. The channel-kind vocabulary, as data (ADR 0041 decision 3).
CREATE TABLE IF NOT EXISTS bms.notification_channel_kinds (
  code varchar(64) PRIMARY KEY,
  label varchar(128) NOT NULL,
  active boolean NOT NULL DEFAULT true,
  created_at timestamptz NOT NULL DEFAULT now()
);

INSERT INTO bms.notification_channel_kinds (code, label) VALUES
  ('email',   'Email'),
  ('webhook', 'Webhook')
ON CONFLICT DO NOTHING;

-- 2. Channels. `config` holds NOTHING secret (plan D2): the webhook HMAC
--    secret is in the three ciphertext columns, so a log line or an API
--    response that carries `config` cannot leak a credential.
CREATE TABLE IF NOT EXISTS bms.notification_channels (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  code varchar(64) NOT NULL UNIQUE,
  name varchar(128) NOT NULL,
  kind varchar(64) NOT NULL,
  config jsonb NOT NULL DEFAULT '{}'::jsonb,
  secret_ciphertext bytea,
  secret_iv bytea,
  secret_key_version integer,
  enabled boolean NOT NULL DEFAULT true,
  created_at timestamptz NOT NULL DEFAULT now(),
  updated_at timestamptz NOT NULL DEFAULT now()
);

-- 3. The join. CASCADE from the rule only: deleting a channel that rules
--    still reference must fail loudly, the same NO ACTION reasoning
--    `alarms_severity_fk` records in 0030.
CREATE TABLE IF NOT EXISTS bms.rule_notifications (
  rule_id uuid NOT NULL,
  channel_id uuid NOT NULL,
  created_at timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (rule_id, channel_id)
);

-- 4. The delivery ledger. Every attempt, INCLUDING every skip (decision 4).
--    `alarm_id` is nullable: a "send test" delivery and a
--    `skipped_unconfigured` recorded before any alarm exists both have none.
CREATE TABLE IF NOT EXISTS bms.notification_deliveries (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  rule_id uuid,
  alarm_id uuid,
  channel_id uuid NOT NULL,
  status varchar(32) NOT NULL,
  dedupe_key varchar(255),
  attempted_at timestamptz NOT NULL DEFAULT now(),
  error text,
  CONSTRAINT notification_deliveries_status_check
    CHECK (status IN ('sent','failed','skipped_unconfigured',
                      'skipped_deduped','skipped_rate_limited'))
);

-- 5. The rate-limit read (decision 7) is "how many deliveries on this channel
--    in the last hour", so it wants (channel_id, attempted_at DESC).
CREATE INDEX IF NOT EXISTS notification_deliveries_channel_time_idx
  ON bms.notification_deliveries (channel_id, attempted_at DESC);
CREATE INDEX IF NOT EXISTS notification_deliveries_dedupe_idx
  ON bms.notification_deliveries (dedupe_key)
  WHERE dedupe_key IS NOT NULL;
```

Then the foreign keys, each in its own `pg_constraint` guard:
`notification_channels.kind → notification_channel_kinds(code)`;
`rule_notifications.rule_id → automation_rules(id) ON DELETE CASCADE`;
`rule_notifications.channel_id → notification_channels(id)`;
`notification_deliveries.channel_id → notification_channels(id)`;
`notification_deliveries.rule_id → automation_rules(id)`;
`notification_deliveries.alarm_id → alarms(id)`.

**Step 2 — the fresh-database trap.** ADR 0041's Consequences names this
explicitly, and it is the `F3.6` defect: `migrate` runs **before**
`pnpm db:seed`, so a migration that joins `bms.assets` or `bms.automation_rules`
is a silent no-op on a fresh database. Migration `0038` seeds **only**
`notification_channel_kinds`, which joins nothing — so it is safe by
construction. Do not add a demo channel row to the SQL file. If a demo channel
is wanted it belongs in `packages/db/src/` beside the other seeds, keyed on
`code` with `ON CONFLICT DO NOTHING`, and it must be a no-op-safe insert that
survives running twice.

**Step 3 — mirror the tables in `bms-schema.ts`,** following `ruleExecutions`
(`packages/db/src/schema/bms-schema.ts:749`) for style: `bmsSchema.table(...)`,
`uuid("id").primaryKey().defaultRandom()`, `timestamp(..., { withTimezone: true })
.notNull().defaultNow()`, `.references(() => automationRules.id)`.

**Step 4 — write the failing integration spec** in
`packages/db/src/notification-channels-seed.integration.spec.ts`, gated the way
ADR 0014 requires (`requireIntegrationDb` / `openIntegrationPool`, wrapped by a
`.integration.test.ts` — `tests/repo-invariants.test.ts` fails the build if a
`.spec` has no wrapper):

```ts
it("seeds both channel kinds and survives a second run", async () => {
  const kinds = await pool.query(
    "select code from bms.notification_channel_kinds order by code",
  );
  expect(kinds.rows.map((r) => r.code)).toEqual(["email", "webhook"]);
});

it("refuses a delivery status outside the five (plan D3)", async () => {
  await expect(
    pool.query(
      `insert into bms.notification_deliveries (channel_id, status)
       values ($1, 'delivered')`,
      [channelId],
    ),
  ).rejects.toThrow(/notification_deliveries_status_check/);
});
```

**Step 5 — verify from scratch, twice.** This is the F3.6 precedent and it is
not optional:

```bash
docker compose --profile core down -v && docker compose --profile core up -d && pnpm db:migrate && pnpm db:seed
```

Then run `pnpm db:migrate && pnpm db:seed` a second time against the same


```ts
export const notificationChannelDtoSchema = z.object({
  id: z.string(),
  code: z.string(),
  name: z.string(),
  kind: z.string(), // a code from bms.notification_channel_kinds, not a union
  config: z.record(z.unknown()),

  createdAt: z.string(),
  updatedAt: z.string(),
});

export const notificationDeliveryDtoSchema = z.object({
  id: z.string(),
  ruleId: z.string().nullable(),
  ruleCode: z.string().nullable(),
  alarmId: z.string().nullable(),
  channelId: z.string(),
  channelCode: z.string(),
  status: z.enum([
    "sent", "failed", "skipped_unconfigured",
    "skipped_deduped", "skipped_rate_limited",
  ]),
  attemptedAt: z.string(),
  error: z.string().nullable(),
});

export const notificationReadinessDtoSchema = z.object({
  kind: z.string(),
  configured: z.boolean(),
  detail: z.string(),
});
```

`kind` is `z.string()` and `status` is `z.enum`. That asymmetry is plan D3 made
visible in the contract: the kind vocabulary is open (`F3.9` adds `sms` as
data), the status set is closed and owned by `NotificationService`.

**`hasSecret`, not `secret`.** A channel response must never carry the HMAC
secret, encrypted or otherwise. The boolean is what the UI needs to render
"secret set / not set".

**Step 2 — write the failing test first:**

```ts
it("reports SMTP unconfigured when SMTP_HOST is unset", () => {
  expect(buildConfig({}).smtp).toBeNull();

it("does not allow insecure webhooks unless explicitly opted in", () => {
```

The second assertion is deliberate: only the exact string `"true"` opts in.

### U4 — `WebhookTransport` and the egress refusals *(highest risk — hands-on)*

**Files:**

**Step 1 — write the failing guard test.** Every one of these is a decision-6
requirement, and each is a separate `it`:

```ts
describe("assertWebhookTargetAllowed", () => {
  it("refuses http:// when insecure is not opted in", async () => {
    await expect(assertWebhookTargetAllowed("http://example.com/hook",
      { allowInsecure: false, resolve: neverCalled }))
      .rejects.toThrow(/https/i);
  });

  it("refuses loopback after DNS resolution", async () => {
    await expect(assertWebhookTargetAllowed("https://hooks.example.com/x",
      { allowInsecure: false, resolve: async () => ["127.0.0.1"] }))
      .rejects.toThrow(/private|loopback/i);
  });

  it("refuses a Compose service name that resolves into RFC 1918", async () => {
    await expect(assertWebhookTargetAllowed("https://grafana/api",
      { allowInsecure: false, resolve: async () => ["172.18.0.7"] }))
      .rejects.toThrow(/private/i);
  });

  it("refuses link-local IPv4 and IPv6", async () => {
    for (const addr of ["169.254.169.254", "fe80::1"]) {
      await expect(assertWebhookTargetAllowed("https://h.example.com/x",
        { allowInsecure: false, resolve: async () => [addr] }))
        .rejects.toThrow(/private|link-local/i);
    }
  });

  it("refuses when ANY resolved address is private", async () => {
    await expect(assertWebhookTargetAllowed("https://h.example.com/x",
      { allowInsecure: false, resolve: async () => ["93.184.216.34", "10.0.0.5"] }))
      .rejects.toThrow(/private/i);
  });

  it("allows a public https target", async () => {
    await expect(assertWebhookTargetAllowed("https://h.example.com/x",
      { allowInsecure: false, resolve: async () => ["93.184.216.34"] }))
      .resolves.toBeUndefined();
  });
});
```

The fifth test is the one a first implementation usually fails: a hostname with
several A records must be refused if *any* of them is private, not merely if the
first is. The third is decision 6's own example — `grafana` is reachable by name
on the Compose network, which is exactly why validating the *string* at write
time is insufficient.

Ranges to refuse: `127.0.0.0/8`, `0.0.0.0/8`, `10/8`, `172.16/12`, `192.168/16`,
`169.254/16`, `100.64/10`, `::1`, `fe80::/10`, `fc00::/7`, and IPv4-mapped IPv6
(`::ffff:10.0.0.1` — normalise before comparing, or the mapped form walks
straight past an IPv4-only check).

**Step 2 — the transport.** Global `fetch` (already used in
`apps/api/src/auth/jwt-auth.guard.ts`), **no new dependency**:

```ts
const res = await fetch(url, {
  method: "POST",
  headers: {
    "content-type": "application/json",
    "x-trinetra-signature": sign(rawBody, secret),
  },
  body: rawBody,
  redirect: "manual",                      // a 3xx is a `failed` delivery
  signal: AbortSignal.timeout(5_000),
});
```

- `redirect: "manual"` and then treat any 3xx as `failed` — a redirect is the
  standard way around an allowlist.
- Read at most 2 KiB of the response body for `error`. Nothing from the response
  is parsed, trusted, or acted on.
- `sign()` is `createHmac("sha256", secret).update(rawBody).digest("hex")` over
  **the exact bytes sent**, not over a re-serialised object.

**Step 3 — the transport tests** stub `fetch` and assert: a 3xx yields
`failed`; a timeout yields `failed` with a bounded message; the signature header
is present and matches an independently computed HMAC; the guard is called
**before** `fetch` (assert `fetch` was not called when the guard rejects — the

### U6 — `NotificationService`: dedupe, rate limit, and the delivery ledger

**Files:**
- Create: `apps/api/src/notifications/notifications.service.ts`
- Create: `apps/api/src/notifications/dedupe-key.ts`
- Test: `apps/api/src/notifications/notifications.service.spec.ts` + `.test.ts`
- Test: `apps/api/src/notifications/storm-control.integration.spec.ts` +
  `.integration.test.ts`

**Interfaces produced** — this is the signature `F3.7` will call:

```ts
export type DispatchInput = {
  ruleId: string;
  ruleCode: string;
  alarmId: string | null;
  severity: string | null;
  message: string;
  /** `AlarmRaiseResult.raised` — false means the dedupe already fired. */
  raised: boolean;
};

dispatch(input: DispatchInput): Promise<DeliveryResult[]>
```

**Step 1 — the dedupe, written as a test first.** Decision 7's first bound. The
signal already exists and was verified in source rather than assumed:
`AlarmRaiseResult` is `{ raised: boolean; alarmId: string | null }`
(`apps/api/src/alarms/alarm-raise.service.ts`), and `raised` is `false` exactly
when `alarms_open_per_rule_uidx` (migration 0032) caught a rule already open for
that asset.

```ts
it("sends nothing when the alarm did not transition to open", async () => {
  const result = await service.dispatch({ ...input, raised: false });
  expect(fakeTransport.sent).toHaveLength(0);
  expect(result.every((r) => r.status === "skipped_deduped")).toBe(true);
});
```

**The skip is still recorded.** A `skipped_deduped` row is the difference
between "we chose not to send" and "nothing happened", and decision 4 is
explicit that a notification never sent is a fact worth as much as one that was.

**Step 2 — the rate limit.** A `COUNT(*)` over
`bms.notification_deliveries WHERE channel_id = $1 AND attempted_at > now() -
interval '1 hour' AND status = 'sent'`, compared to
`notificationsConfig.ratePerHour`. Count only `sent`, not skips — otherwise the
ceiling fills with its own refusals and one noisy hour locks a channel out for
the next. Excess is a `skipped_rate_limited` row.

**Step 3 — the negative storm-control test.** Decision 7 names this as the
direction that costs a client an inbox, and AGENTS.md §4.6 requires proving both
directions:

```ts
it("re-evaluating every enabled rule against an unchanged plant sends zero", async () => {
  await seedEnabledRulesWithChannels();       // the live ladder, ~337 rules
  await service.dispatchAll(unchangedPlantEvaluation());
  expect(fakeTransport.sent).toHaveLength(0);
});
```

Take the rule count from the live dev database at build time rather than
hard-coding 337 — the number moves with the seed, and a test that fails because
someone added a rule is a test people delete.

**Step 4 — dispatch is fire-and-forget and can never fail a caller**
(decision 1). `dispatch()` catches every transport rejection, records it as
`failed` with a bounded `error`, and resolves. Test it: a transport that throws
must still produce a delivery row and a resolved promise.

**Step 5 — commit.**

### U7 — The notifications API

**Files:**
- Create: `apps/api/src/notifications/notifications.controller.ts`

Routes, all under `@Controller("notifications")` with `@UseGuards(JwtAuthGuard)`,
following `rules.controller.ts` for the `ZodError → BadRequestException` shape:

| Route | Authorisation |
|---|---|
| `GET /notifications/channels` | `assertAdminRole(user.role)` |
| `POST /notifications/channels` | `assertAdminRole` |
| `PATCH /notifications/channels/:id` | `assertAdminRole` |
| `DELETE /notifications/channels/:id` | `assertAdminRole` |
| `POST /notifications/channels/:id/test` | `assertAdminRole` |
| `GET /notifications/deliveries` | `assertAdminRole` |
| `GET /notifications/readiness` | `JwtAuthGuard` only — see below |
| `PUT /rules/:id/notifications` (D1) | `assertOperationsWriteRole(user, "configuration")` |

**`readiness` is authenticated but not admin-only, deliberately.** Decision 10
renders it as a banner on the rules surface, and a location-scoped operator
editing a rule marked `notify` is exactly the person who must see that no
transport is configured. It returns one boolean and one sentence per kind — no
host, no port, no credential — so it discloses nothing an admin-only gate would
be protecting.

**Every write body is a Zod schema** parsed in the controller, `ZodError` →
`BadRequestException(err.flatten())`, the pattern every route in
`rules.controller.ts` already uses. The webhook `url` is validated as a string
here; the **real** check is U4's guard at send time, because DNS can change
between write and send (decision 6).

`POST /channels/:id/test` sends one message through the channel's real transport
and records a delivery row like any other attempt — it is the cheapest way to
make U4's egress rules visible to whoever configures a webhook. It is subject to
the rate limit; it is **not** subject to the transition dedupe (there is no
alarm).

**Commit after the API tests are green.**
