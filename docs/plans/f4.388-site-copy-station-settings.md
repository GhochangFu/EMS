## 0. Why

The owner, 2026-11-19, after release B: "lota pata 1 and lota pata 2 side dashboards should be exactly like the dashboard it previously was … look out what Bilsi dashboards are having … the mimic builder is using isometric clips, whereas you divided the lota patha 1. Those are not isometric." Measured on the demo host, read-only: Lotapata I and II carry the station's 40 widgets in the same tabs, order, positions and titles, with chart bindings per site (one train, which is right). Six config keys differ:

- the 3 `mimic` widgets: the station has `"glyphSet": "iso"` (an AWS data change of 2026-11-09), the sites have none;
- the 3 `trend_strip` widgets: the station has `points`, `segments`, `styles`, `colors` (and `tabKey` on the Overview), the sites have `defaultRange` only. The points are `group code:point key`, never an asset id.

The split made each site's copy from `pump-station-standard` (DB v4), which holds neither.

Owner ruling, 2026-11-19: **"Both"** — the sites take their station's settings, and the stock template is updated.

## 1. Goal and out of scope

**Goal.** When the PHE seed makes a split site's copy, each `mimic` and `trend_strip` widget takes the config of the matching widget on its station's own dashboard, one time per copy. The same step repairs Lotapata I and II one time on the next deploy, per widget, only while the widget is as the seed made it. The stock `pump-station-standard` goes to `stockVersion` 3 with `glyphSet: "iso"` on its three mimics.

**Out of scope.** A selection in any template (Q1). A `pump-station-standard` upgrade chain. Any write to a station dashboard. Any change to template rows on AWS. Web code, contracts, migrations: none.

## 2. Design, with evidence (citations at `64fd1e10`)

- **D1 Where the copy is made.** `seedPhewbSiteLayouts` (`site-layout-seed-move.ts:364-413`) resolves unsplit stations plus split sites (`pheSiteLayoutSites`, `site-layout-seed.ts:153-165`), then `seedSiteLayouts` (`:467-548`) plans (`planSiteCopy`, `:372-403`) and writes (`writeSiteLayoutTabs`, config at `:441`). The copy is stamped with the template's stock version (`:518-526`).
- **D2 Where the station's copy is.** `bms.dashboards` with `slug = siteLayoutSlug(<station slug>)` and `location_id = <station id>`, the identity the unlink uses (`phe-site-split.ts:517-526`). The row stays after the unlink (ADR 0139 decision 7). Read it without a view row and with any template code (Lotapata's is `smoc-standard`).
- **D3 One new step, after `seedSiteLayouts`, same transaction** (`seed.ts:408-410`). For each split station: the station id and its site ids come from `resolvePhewbSiteLayoutLocations` (two calls per station; no new SQL). The site's candidate copy is the `CANDIDATE_SQL` rule (`site-layout-seed-move.ts:135-143`, with `FOR UPDATE OF d`) and template code `pump-station-standard`.
  - **Considered when:** the copy is in this run's `outcome.made`, OR its `stock_version` is NULL or below 3.
  - **Per widget (types `mimic`, `trend_strip` only):** match the station widget on tab key + widget type + rect, exactly one match. Copy the whole station config when (a) the site config equals the as-made config, which is `planSiteCopy` run with the copy's own `template_id` row (the `site-layout-seed-move.ts:300-305` method); (b) the station config parses (`mimicConfigSchema` / `trendStripWidgetConfigSchema`); (c) a mimic is `source: "preset"` with the same `preset` (a `layoutId` belongs to the station). Otherwise keep and log the reason (Q4).
  - **Write:** `UPDATE bms.dashboard_widgets SET config = $new WHERE id AND organization_id AND config = $read::jsonb`, row count checked. Then stamp the copy 3 with `COPY_STAMP_SQL` (`site-layout-seed-upgrade.ts:422-425`).
  - **Why the stamp.** The builder writes `core` as an absent key (`widget-config-form.ts:746`). Without the stamp, an administrator who goes back to core would be overwritten at each boot. `dashboards.stock_version` is read by the seed only (`site-layout-seed-upgrade.ts:683`; the smoc chain reads only `smoc-standard` copies, `:372-382`). Precedent: F4.305 owner answer C5.
- **D4 Order.** Template → smoc chain → move → make → the new step. On AWS a new site copy comes from DB v4 (stamp 1), then takes the station's settings, then stamp 3: the station wins. On a cold start there is no station dashboard and the stamp is 3 from the insert: stock applies. Run 2 writes nothing.
- **D5 A stock bump rewrites no live dashboard.** `ensureSiteTemplate` inserts v1 `ON CONFLICT DO NOTHING` (`site-layout-seed.ts:218-224`); `upgradeSeedSiteTemplate` runs for `smoc-standard` only (`:270-272`, `site-layout-seed-upgrade.ts:322`); the copy chain reads only `smoc-standard` copies (`:789-794`), and a copy stamped 5 skips its v5 step (`:683`); `moveUntouchedPheCopies` needs an exact fingerprint (`site-layout-seed-move.ts:291-308`); split stations are not in `locationIds` (`:372-376`). ADR 0052 decision 7: "Bumping `stockVersion` in the catalog touches no organization's row". **Demo host writes from this plan's PR: 12 widget configs and 2 stamps (1 → 3) at Lotapata I and II. Zero template rows. Zero station rows.**
- **D6 Boot gate.** `verify-hierarchy-seed.ts:877-881,929` counts view rows only. No effect. `tests/f4.169-f4.170-…` is not touched.
- **D7 Web.** The renderer already reads `glyphSet` for these presets (`mimic-geometry.ts:197-206,285-286`; `mimic.ts:475-476`; held by `mimic-widget-live.spec.tsx` LV-B4/B4b). The eight strip points are all seeded trend defaults (`point-key-trend-defaults-seed.ts:14-33`). A point off a list is dropped, never thrown (`trend-strip.pure.ts:177-181`).
