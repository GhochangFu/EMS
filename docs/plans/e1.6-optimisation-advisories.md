## 1. Goal

A signed-in user sees **advisories** for real energy meters they can read: a card per advisory that says what was found in the last 7 complete local days, what it is worth (kWh, kVAh, money, kg CO₂, kVAr), how sure the figure is (*Measured*, *Estimated*, *Forecast-based*) and which assumptions it rests on. Two kinds ship first: **low power factor** and **consumption above baseline**. A third, **forecast demand near contract**, follows when `kw` forecasts are live. Advisories are computed when a page asks, from tables that already exist, by pure functions in a new API module `apps/api/src/advisories/`. They appear on a new page `/advisories` (Operations, after Anomalies) and in a section on `/asset-history/:assetId`. Every card carries the *Advisory* pill and the line "An estimate from the last 7 days, not a guaranteed saving."

**Out of scope** (named so nobody builds it):
- Any migration, table, grant, index, cache, queue, worker job, environment variable or package. Any `apps/ml` change.
- Any LLM call or LLM-worded text. Any alarm, notification, work order, report, schedule, export, copilot answer or copilot tool. Any acknowledge, dismiss or "done" state. Any history of past advisories.
- A dashboard widget. An annual figure. An accuracy figure or a percentage of confidence.
- A ₹ load-shift advisory (needs time-of-day rates), water (kL), chemical dosing, HVAC or cold-room setpoint advice. A PF penalty or rebate rate. An excess-demand penalty.
- The template `optimisation` section: `RESERVED_SECTIONS` keeps refusing it (`packages/shared/src/contracts/asset-template-content-writes.ts:186`).
- Any edit to `E1.9`'s files (`apps/api/src/ml/ml-findings.*`, `apps/api/src/ml-findings/*`, `apps/web/src/components/ml/*`, `apps/web/src/lib/ml-findings.ts`, `apps/web/src/hooks/use-ml-findings.ts`) or to `apps/api/src/ml/ml.module.ts`. They are imported, never changed.
- Any threshold or detector change. `ANOMALY_UNUSUAL_SCORE`, `ABNORMAL_RATIO`, `BASELINE_WINDOWS`, `MIN_BASELINE_WINDOWS` are imported, never restated.

## 3. Refinements (each is a call inside the ADR; veto at skim)

- **R-a — one request, one clock, one window per zone.** For an asset in zone Z with local today D, the window is the local days D−7 … D−1. Baseline window k (1…`BASELINE_WINDOWS`) is the 7 days before that, shifted k × 7 days. Hours are put in a day with `localDay`.
- **R-b — "7 complete days" means coverage.** The window qualifies when it holds at least `ADVISORY_MIN_COVERAGE` (0.8, the ML readiness figure) of its 168 hourly buckets. Baseline windows use the Energy page's own counting rule through `verdictFor`.
- **R-c — the module provides its own `MlAnomaliesService`** (`providers: [MlAnomaliesService]`), the `CopilotAvailabilityService` precedent. `ml.module.ts` and its exports are not edited, so there is no shared-file edit with `E1.9` or `E1.8`.
- **R-d — anomaly context uses `forAsset` on the advisory's exact window**, for at most `ADVISORY_ANOMALY_CONTEXT_MAX` (25) `excess_consumption` advisories, taken in the response's sort order. The others carry no context line. A failed anomaly read means no context line, never a failed response. The context is added after the numbers are final.
- **R-e — the cap.** With more than 200 qualifying assets, one statement sums the last 7 days of `_1h` `kw` per asset to pick the top 200. With 200 or fewer it does not run. The web shows "Showing 200 of N meters."
- **R-f — sentences are built on the server** by pure functions; the response carries both the sentences and the numbers.
- **R-g — the comparison uses the number shown.** PF is rounded to 2 decimals first; the advisory fires when that rounded PF is below the threshold.
- **R-h — in force "at the window's end".** The PF threshold, the emission factor, the baseline parameter and the tariff version are the ones in force in the window's last hour. The money figure still prices each hour at its own rate.
- **R-i — a meter that is not a billing meter of its site's tariff is *Estimated*** when it shows money, with the assumption "Priced at the site's tariff rate; this meter is not the billing meter."
- **R-j — where no kVAh tariff applies and there is no tariff at all**, the line reads "No kVAh-billed tariff is set for this meter's site, so no ₹ is shown." The ADR's kWh sentence is used only when a kWh tariff is mapped.
- **R-k — the ₹ sign.** Money reads `₹ 12,340` for `INR` (grouped with `en-IN`) and `USD 12,340` otherwise (`en-US`). In the fixed sentences the word "₹" becomes the currency code when it is not `INR`.
- **R-l — the asset-history section is hidden when the asset has no advisory** and when the read fails. No empty sentence and no banner on that page.
- **R-m — the kind enum holds all three kinds from `E1.6a`**; the fields only `demand_near_contract` needs arrive in `E1.6c`.
- **R-n — the icon is Lucide `lightbulb`**; no navigation item uses it.
- **R-o — a module-wiring spec** holds the new module's edges, because CI does not boot the API and a merge deploys by itself.
- **R-p — `parameterRowAt`** is added beside `parameterValueAt` (which then calls it), so the assumptions can name a value's scope and date without a second loop.

## 4. The rules, exactly

Written with the recommended answers to Q1–Q7. A different ruling changes the marked line only.

### 4.1 Who is considered

An asset is a **candidate** when all hold: the caller can read it (`narrow`); it has an active `kw` point that is real by the ML rule (Q6); its organization's energy features are not off (`isEnergyShown(energy_features, true)`); its own location has a valid zone. Candidates above 200 are cut by R-e. A candidate **qualifies** when its window passes R-b.

Per qualifying asset: `E` = the window's kWh (sum of the hourly figures); `C` = the window's cost, from `foldCostByDay` + `sumCostDays` over the 7 days, used only when all days with energy are priced (else no money); `avgRate = C ÷ E`.

### 4.2 `low_power_factor` (domain `electrical`)

1. **PF**, first path that gives a value in (0, 1]: (i) registers: `kwh_total` delta ÷ `kvah_total` delta over the window; (ii) `kva`: Σ hourly mean `kw` ÷ Σ hourly mean `kva` over hours with both; (iii) `pf` (Q5): Σ `kw` ÷ Σ (`kw` ÷ `pf`) over hours with both and 0 < `pf` ≤ 1. Paths (ii) and (iii) are *estimated*. No path → no advisory.
2. **Threshold** = `tariff_pf_band` (R-h), else `ADVISORY_DEFAULT_PF_THRESHOLD` (0.95, *estimated*). Fires when rounded PF < threshold and PF < `ADVISORY_TARGET_PF` (0.99).
3. **Avoidable kVAh** = `Ek ÷ PF − Ek ÷ 0.99`, where `Ek` is the register kWh on path (i), else `E`.
4. **Correction** = mean kW × (tan(acos PF) − tan(acos 0.99)), mean kW = `E ÷ hours with data`.
5. **Money (Q1)** only when the tariff in force (R-h) has `energyUnit = "kvah"` and `C` exists: `C × (1 − PF ÷ 0.99)`. This equals avoidable kVAh × PF × `avgRate`.
6. No CO₂ line. **Confidence**: *Measured* only on path (i) with `tariff_pf_band` set and not R-i; else *Estimated*.

### 4.3 `excess_consumption`

1. **Baseline**: the `energy_baseline_kwh_per_day` row at **asset scope** (Q7) × 7 ("your baseline", *Measured*); else `verdictFor(current, windows)` on the 4 earlier windows ("own history", *Estimated*).
2. **Fires** when `E ÷ baseline >= ABNORMAL_RATIO` (Q4). "Not enough history" → no advisory.
3. **Excess kWh** = `E − baseline`. **Money** = excess × `avgRate` when `C` exists. **CO₂** = excess × `grid_carbon_factor_kgco2_per_kwh` (R-h) when set.
4. **Context** (R-d): unusual hours = distinct hours in the window with any score ≥ `ANOMALY_UNUSUAL_SCORE`; none → no line.

### 4.4 Common

- **30-day figure** = unrounded 7-day figure × 30 ÷ 7, then rounded. **Rounding**: money, kWh, kVAh, kg CO₂, kVAr to whole numbers; PF to 2 decimals.
- **Order**: priced before unpriced; then 30-day money, then 30-day kWh (kVAh for PF), descending; then asset label, then kind. No total across advisories is ever shown, so mixed currencies never add.
- **Sentences** (`<…>` are values; "(about <x> in 30 days if the last 7 days repeat)" is written `[30]`):

| Where | Sentence |
|---|---|
| PF headline | `Power factor averaged <pf> over the last 7 days, below <threshold>.` |
| PF lines | `About <n> kVAh could be avoided at a power factor of 0.99 [30].` · `About <money> in 7 days [30].` or `Your tariff bills kWh; a PF penalty is not modelled, so no ₹ is shown.` or R-j or `No rate is available for this meter, so no ₹ is shown.` · `About <n> kVAr of correction would bring it to 0.99.` |
| Excess headline | `Used <n> kWh in the last 7 days, <ratio> times your baseline of <n> kWh.` / `… times its usual <n> kWh.` |
| Excess lines | `About <n> kWh above the baseline [30].` · `About <money> in 7 days [30].` or `No rate is set for this meter, so no ₹ is shown.` · `About <n> kg CO₂ in 7 days [30].` |
| Context | `<h> unusual hours in this window on the Anomalies page (advisory); <b> marked by both methods.` then `MIXED_SENTENCE`, or `BASELINE_ONLY_SENTENCE` when no hour has both (both imported) |
| Assumptions | `Window: <d1> to <d7> (7 complete days), <zone>.` · `Rate: tariff "<name>", version from <date>, billed in <kWh\|kVAh>; the month's bill ÷ kWh.` / `Rate: energy_tariff_per_kwh at <asset\|location\|organization> scope, from <date>.` / `No rate set.` · `Emission factor: <f> kg CO₂/kWh at <scope> scope, from <date>.` / `No grid emission factor set.` · `Threshold: <t> (tariff_pf_band, <scope> scope).` / `Threshold: 0.95 (default; tariff_pf_band is not set).` · `Target power factor: 0.99 (fixed).` · `Power factor from the kWh and kVAh registers.` / `… estimated from hourly kW and kVA.` / `… estimated from hourly kW and PF.` · `Baseline: your energy_baseline_kwh_per_day of <n> kWh/day × 7.` / `Baseline: the median of <k> earlier 7-day windows (own history).` · R-i's line · `30-day figure: the 7-day figure × 30 ÷ 7, if the last 7 days repeat.` |

### 4.5 Contract — `packages/shared/src/contracts/advisories.ts`

```ts
export const ADVISORY_KINDS = ["low_power_factor", "excess_consumption", "demand_near_contract"] as const;
export const ADVISORY_CONFIDENCES = ["measured", "estimated", "forecast_based"] as const;
export const ADVISORY_WINDOW_DAYS = 7;
export const ADVISORY_PROJECTION_DAYS = 30;
export const ADVISORY_MAX_ASSETS = 200;
export const ADVISORY_DEFAULT_PF_THRESHOLD = 0.95;
export const ADVISORY_TARGET_PF = 0.99;
export const ADVISORY_MIN_COVERAGE = 0.8;
export const ADVISORY_ANOMALY_CONTEXT_MAX = 25;
export const ADVISORY_DISCLAIMER = "An estimate from the last 7 days, not a guaranteed saving.";
export const ADVISORY_EMPTY_SENTENCE =
  "No advisories. An energy meter gets advisories when it has real data, a tariff or rate, and 7 complete days.";

const amount = z.object({ window: z.number(), projected: z.number() }); // 7-day, 30-day
export const advisorySchema = z.object({
  id: z.string().max(80),                                   // "<assetId>:<kind>"
  kind: z.enum(ADVISORY_KINDS), confidence: z.enum(ADVISORY_CONFIDENCES),
  organizationId: z.string().uuid(), locationId: z.string().uuid(), assetId: z.string().uuid(),
  assetCode: z.string(), assetName: z.string(), assetRtuName: z.string().nullable(), assetLocationName: z.string(),
  timeZone: z.string(), windowFrom: iso, windowTo: iso,
  headline: z.string().max(300),
  lines: z.array(z.string().max(300)).max(6),
  context: z.array(z.string().max(300)).max(2),
  assumptions: z.array(z.string().max(300)).min(1).max(10),
  currency: z.string().length(3),
  money: amount.nullable(), kwh: amount.nullable(), kvah: amount.nullable(), co2Kg: amount.nullable(),
  kvar: z.number().nullable(), powerFactor: z.number().nullable(),
});
export const advisoriesResponseSchema = z.object({
  asOf: iso, candidates: z.number().int().nonnegative(), considered: z.number().int().nonnegative(),
  advisories: z.array(advisorySchema),
});
```

**Encoding (§4.8 / ADR 0030), named so a reviewer checks it:** every object is one plain `z.object`. There is no intersection and no all-readonly object, so neither `z.intersection` nor `.readonly()` applies, and nothing is flattened from two parts; no `.merge()` or `.extend()`. Not `.strict()` (responses). No `.default()`. Types are `z.infer`, exported from this file. One `export * from "./advisories";` line in `contracts/index.ts`. Both routes return `advisoriesResponseSchema`.

-- 1. Real energy meters: zone, energy setting, points, billing-meter flag
SELECT a.id, a.code, l.timezone AS location_zone, o.energy_features, o.currency,
       array_agg(DISTINCT ap.point_key) FILTER (WHERE ap.point_key IN ('kw','pf','kva','kwh_total','kvah_total')) AS points,
       EXISTS (SELECT 1 FROM bms.location_tariff_meters m WHERE m.asset_id = a.id) AS billing_meter
  FROM bms.assets a
  JOIN bms.organizations o ON o.id = a.organization_id
  JOIN bms.locations l ON l.id = a.location_id
  JOIN bms.asset_points ap ON ap.asset_id = a.id AND ap.active
  LEFT JOIN bms.rtus r ON r.id = ap.rtu_id
 WHERE o.code = :'org'
   AND (a.meta->>'telemetrySource' = 'mqtt' OR (ap.source_kind = 'measured' AND r.ingest_enabled))
 GROUP BY a.id, a.code, l.timezone, o.energy_features, o.currency
HAVING bool_or(ap.point_key = 'kw');
-- 2. Tariff mappings and their billing unit
SELECT lt.location_id, lt.tariff_key, lt.effective_from, lt.effective_to,
       (SELECT array_agg(DISTINCT c.energy_unit) FROM bms.tariff_categories c WHERE c.key = lt.tariff_key) AS catalog_unit,
       (SELECT array_agg(DISTINCT oc.energy_unit) FROM bms.org_tariff_categories oc
         WHERE oc.key = lt.tariff_key AND oc.organization_id = lt.organization_id) AS own_unit
  FROM bms.location_tariffs lt JOIN bms.organizations o ON o.id = lt.organization_id WHERE o.code = :'org';
-- 3. The five parameters and their scope
SELECT cp.key, cp.asset_id IS NOT NULL AS asset_scope, cp.location_id IS NOT NULL AS location_scope,
       cp.effective_from, cp.effective_to
  FROM bms.calc_parameters cp JOIN bms.organizations o ON o.id = cp.organization_id
 WHERE o.code = :'org' AND cp.key IN ('energy_tariff_per_kwh','tariff_pf_band','grid_carbon_factor_kgco2_per_kwh',

-- 4. Data: hours of kw in 35 days, and whether the registers report

## 18. Questions only the owner can rule (each has a recommended answer; all are needed before `E1.6a`)

1. **Money for low power factor.** The ADR multiplies avoidable kVAh by "the hourly rate". The rate the system holds is money per **kWh** (the month's bill ÷ kWh), also on a kVAh tariff. kVAh × a per-kWh rate overstates the saving by 1 ÷ PF (about 15 % at PF 0.87).
   - (a) Money = the meter's 7-day cost × (1 − PF ÷ 0.99). This is avoidable kVAh × PF × the average rate: the same blended rate, in the right unit.
   - (b) As written. The figure is too high.
   - (c) Price the avoided kVAh at the top slab's own rate. More exact; needs new bill plumbing and its own review.
   **Recommended: (a).**
2. **Which aggregate.** Decision 2 names `readLocalHourEnergy` (it reads `_5m`); decision 9 budgets 35 days of `_1h`.
   - (a) `readLocalHourEnergy` for all 35 days. One definition of kWh, exact local days, no new energy SQL; 12 times the rows of decision 9 (about 50,000 for 5 meters, about 2 million at the cap). The demo-host EXPLAIN and the stop rule in section 16 decide.
   - (b) `readLocalHourEnergy` for the 7 priced days; one new `_1h` statement for the five window totals. Fewer rows; window edges are up to 30 minutes off in a half-hour zone.
   - (c) `_1h` only, new SQL throughout.
   **Recommended: (a)**, with (b) ready if the stop rule fires.
3. **Which pool.** Decision 6 says both branches of `withReadScope`. Every reused read takes the fleet pool and an id list.
   - (a) The candidate read runs through `withReadScope` (row security backs a single-organization caller). Every later read runs on the fleet pool with those candidate ids only, never `null`; the organization equality is inside each reused statement. This is how the dashboards and reports price energy today.
   - (b) Rewrite the reads to take a transaction. New SQL, against decision 2.
   **Recommended: (a).**
4. **`>` or `>=`.** The ADR says the advisory fires above 1.5 × baseline and must never disagree with the Energy page. The Energy page fires at 1.5 or above and counts a baseline window only when it holds at least half the current period's hours.
   - (a) Call the Energy page's own `verdictFor`: `>=`, with its counting rule.
   - (b) `>` as written; the two can then disagree at exactly 1.5.
   **Recommended: (a).**
5. **A meter with `kw` and `pf` but no `kva` and no `kvah_total`.** The ADR admits it but gives no formula.
   - (a) A third path, marked *Estimated*: PF = Σ kW ÷ Σ (kW ÷ pf) over the hours with both.
   - (b) No low-PF advisory for such a meter.
   **Recommended: (a).**
6. **"Real".** The ADR says "its RTU has `ingest_enabled`, the same rule as the ML targets". The ML rule is: the asset is marked `mqtt`, **or** its `kw` point is measured through an ingest-enabled RTU.
   - (a) The ML rule word for word, held equal to `apps/ml`'s line by a test.
   - (b) Only the RTU flag.
   **Recommended: (a).**
7. **Which baseline rows count as "your baseline".** `energy_baseline_kwh_per_day` can be set for an asset, a site or the whole organization.
   - (a) Asset-scope rows only. A site or organization value is ignored for a single meter and its own history decides.
   - (b) The nearest scope, as the existing `energy_saving_vs_baseline_pct` point reads it. A site-wide value would then be compared with each single meter under it, and most would never fire.
   **Recommended: (a).** Check 3 in section 16 shows which rows exist today.
