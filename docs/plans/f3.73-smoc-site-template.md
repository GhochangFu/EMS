## 1. Goal

A dashboard can have tabs, each tab bound to at most one asset group of the
dashboard's site. A "SMOC standard" site template (target `site`) makes one
tabbed, site-scoped, template-stamped dashboard per site — Overview plus one
tab per asset domain present — that an admin edits in the builder. Five new
widget types (active alarms rail, state legend, asset-class strip, module
summary card, critical-systems list) render server-computed, role-bound
status. The copy is made by a per-site admin action, the site arm of
`instantiate`, a bulk per-template action, and the seed (seed-owned demo sites
only). The generated view stays the fail-safe, with one new notice for a site
that has no copy yet.

**Out of scope:** `RSMOC-WC` (keeps `builtin`, F3.75); live breaker state
(F3.74); a UI for authoring tabs inside a *template* (the API accepts tabbed
content; the stock template is imported, not hand-drawn); an admin editor for
`asset_groups.domain` (no route creates a group today, so every group is
seed-, migration- or action-made and gets its domain there); PHE environment
member roles (owner ruling 10 of F3.41 keeps them NULL); roles for the
`CR-LEAK-*` / `CR-SMOKE-*` sensors (no `bms.asset_roles` code exists for them —
OQ6); a "refresh copy from a newer template version" action (ADR 0049
instance rule holds by construction); `app-shell.tsx` / `admin-access.ts`
edits; a `role` column on the `assets.list` dataset (a role is a membership
property and the resolver receives only asset ids — F3.75 gap).

## 3. Design decisions

- **D0 Split `dashboard-builder.ts` before PR1.** Move the DTO block
  (`dashboardWidgetDtoSchema`, `dashboardDtoSchema`, their docblocks,
  `:865-964`) to a new `packages/shared/src/contracts/dashboard-dto.ts`,
  exported through `contracts/index.ts` and the shared index (no re-export
  from `dashboard-builder.ts` — that would be a cycle). Budget after the move:
  ≈ 865 lines; PR3 adds ≤ 45 → ≤ 910. Before moving, run
  `grep -rl "dashboard-builder" tests/ packages apps --include=*.ts` and
  re-point every path-based scan (`tests/f3.32-mimic-widget.test.ts` parses
  `widgetTypeSchema` from the file — it stays; anything that parsed the DTO
  block moves with it). Every PR states the file's line count in its
  description.
- **D1 Tabs table (ruling Q1, A-prime).** `bms.dashboard_tabs`: `id`,
  `organization_id NOT NULL`, `dashboard_id NOT NULL` (FK ON DELETE CASCADE),
  `location_id NULL`, `asset_group_id NULL`, `tab_key varchar(64)`, `label
  varchar(128)`, `sort_order int`, timestamps. **An Overview tab (no group)
  stores `location_id NULL`**, so the composite FK is inert for it and a
  dashboard with only an Overview tab can still move scope. Constraints:
  `UNIQUE (dashboard_id, tab_key)`, `UNIQUE (dashboard_id, id)` (target of the
  widgets' composite FK), `CHECK ((asset_group_id IS NULL) = (location_id IS
  NULL))`, `CHECK (tab_key ~ '^[a-z0-9-]{1,64}$' AND tab_key <> 'assets')`,
  composite FK `(asset_group_id, location_id) → asset_groups(id, location_id)
  ON DELETE RESTRICT`, composite FK `(dashboard_id, location_id) →
  dashboards(id, location_id) ON DELETE CASCADE` (a location move on the
  dashboard then fails `23503`, translated to 400). Two new unique indexes:
  `asset_groups_id_location_key (id, location_id)` and
  `dashboards_id_location_key (id, location_id)`. `dashboard_widgets.tab_id
  uuid NULL` with composite FK `(dashboard_id, tab_id) →
  dashboard_tabs(dashboard_id, id) ON DELETE CASCADE`. FORCE RLS on
  `dashboard_tabs` with three legs (own org; parent dashboard org; asset group
  org `IS NULL OR EXISTS`). The `dashboard_widgets` policy is **not**
  re-created: the composite FK pins a widget's tab to its own dashboard and the
  existing policy already checks that dashboard's organization — the header
  says so and `security-reviewer` is asked to confirm it (OQ5). The fleet-pool
  reads of tabs carry an explicit `organization_id` predicate; the gate is the
  cross-org-stamped fixture (§2), not a query-text scan.
- **D2 Widgets body.** `PUT /dashboards/:id/widgets` becomes `{ tabs?: Tab[],
  widgets: Widget[] }`; a widget gains optional `tabKey`. Rules
  (`dashboards.schema.ts`, one `superRefine`): tab keys unique; `tabs` present
  ⇒ every widget names an existing `tabKey`; `tabs` absent or empty ⇒ no
  widget names one (legacy canvas); every `module_summary_card.config.targetTabKey`
  names a key in `tabs` (from PR3 on); `MAX_DASHBOARD_TABS = 8`; the 40-widget
  cap applies **per tab** (and to the legacy canvas). Service rules: a tab
  with `assetGroupId` needs `dashboard.locationId` (else 400,
  `TAB_GROUP_SCOPE_MESSAGE`); a tab `id` that is not one of this dashboard's
  stored tabs → 400 (`TAB_ID_UNKNOWN_MESSAGE`, never echoing the id); the
  mimic guard becomes "the dashboard's group or the widget's tab's group is
  non-null". Tabs are diffed by `id` (kept), inserted by key, deleted when
  absent (widgets cascade; the service deletes them explicitly first so the
  audit `widgetCount` is honest). The DTO gains `templateId`,
  `tabs: DashboardTabDto[]`, and `tabId` on each widget.
- **D3 Per-tab resolution.** `MimicNodesService.read` selects
  `COALESCE(t.asset_group_id, d.asset_group_id)` per widget via `LEFT JOIN
  bms.dashboard_tabs t ON t.id = w.tab_id AND t.organization_id = $n` and
  resolves members per group. `resolveAssetScope` moves to
  `apps/api/src/dashboard-builder/dashboard-scope-assets.ts` (exported,
  memoised per scope key inside one call) and `MetricCatalogService`
  resolves the scope **per widget** (tab group when the widget's tab binds one,
  else the dashboard scope); the dedupe key gains the scope key. The
  `Resolver` signature is unchanged (asset ids only) — that is why
  `assets.list` carries no `role` column.
- **D4 Template target + content tabs (rulings Q3a/Q3b).**
  `dashboard_templates.target varchar(32) NOT NULL DEFAULT 'asset_group'
  CHECK IN ('asset_group','site')`; one new `dashboard_sections` row `site`
  ("Site layouts") so the NOT NULL `section` has an honest value (`target` is
  the behaviour switch; `section` stays display grouping — OQ3). Content:
  `sectionTemplateContentSchema`'s object gains `tabs: siteTemplateTabSchema[]
  .max(8).default([])`; tab = `{ key, label, sortOrder, domain: string|null,
  groupCode?: string, mimicPreset?: MimicPreset, widgets: Widget[] }`; the
  existing `superRefine` walks `widgets` **and** every `tabs[].widgets` for
  key uniqueness. Rule: `target === 'site'` ⇒ top-level `widgets` empty and
  `tabs` non-empty; `target === 'asset_group'` ⇒ `tabs` empty (a create/patch
  `superRefine` where the body carries both; `publish`/`instantiate` re-check
  from the stored row). Tab widget count per tab ≤ 40; every domain must be a
  live `bms.asset_domains` code (`assertAssetDomain`).
- **D5 Group picking (ruling Q3b + decision 4).** Pure
  `pickTabGroups(tabs, groupsAtSite, choice)` in
  `packages/shared/src/site-layout-planner.ts`: tabs resolve in order; a tab
  with `domain: null` is the Overview (no group); a tab takes the **single**
  untaken group of its domain; a tab with no candidate is **omitted** ("one
  tab for each domain present"); a tab with > 1 untaken candidates is
  **ambiguous** unless `choice[tabKey]` names one of them (a choice naming a
  group of another domain, or a taken group, is refused). Whether a template
  tab's `groupCode` may resolve a two-candidate case without a choice is
  **OQ1** — ruling Q3b says the admin picks and a bulk run skips; the planner
  ships with `groupCode` as a **hint only when OQ1 is answered yes**, and the
  seed always passes explicit choices, so the seed does not depend on OQ1.
  Returns `{ tabs, omitted, ambiguous: [{ tabKey, domain, candidates:
  [{ id, code, name }] }] }`. `planSiteLayout(...)` then **drops every Overview
  `module_summary_card` whose `targetTabKey` is an omitted tab** and reports
  them. The per-site action answers 409 with `ambiguous` (candidates
  included, so the web needs no second read); the bulk action skips and
  reports.
- **D6 Copy actions (rulings Q3a/Q4/Q4b/Q5).** New `SiteLayoutService`
  (`apps/api/src/control-room/site-layout.service.ts`) with
  `makeForSite(jwt, { locationId, templateId?, tabGroups? })` and
  `makeForOrganization(jwt, templateId)`. Three thin routes over it:
  `POST /admin/locations/:id/site-layout` (body `{ tabGroups?, templateId? }`;
  the notice button; `templateId` absent → the organization's newest
  published `target='site'` template by `published_at DESC`, none → 409
  `NO_SITE_TEMPLATE_MESSAGE` — OQ4); **the site arm of
  `POST /admin/dashboard-templates/:id/instantiate`** (ruling Q3a: when the
  template's `target === 'site'` the body is `{ locationId, tabGroups? }` and
  the call delegates to `makeForSite`; a group body on a site template, or a
  site body on a group template → 400 `TEMPLATE_TARGET_BODY_MESSAGE`); and
  `POST /admin/dashboard-templates/:id/apply-to-sites` (bulk; only a
  published `target='site'` row). Per site, one `withTenant` tx: refuse if the
  site has a `site_control_room_views` row **other than a removed copy**
  (`409 SITE_HAS_VIEW_MESSAGE` — this covers `RSMOC-WC`'s builtin row, a
  `generated` row and a live `dashboard` row). A removed copy is
  `kind='dashboard' AND dashboard_id IS NULL` (the `ON DELETE SET NULL` of
  `0082:34` leaves it when an admin deletes the copy); ruling Q4 forbids
  replacing the builtin view or an existing copy, and a removed copy is
  neither, so the action re-makes it: it **updates that row in place** with
  `WHERE location_id = $1 AND kind = 'dashboard' AND dashboard_id IS NULL`
  and asserts `rowCount === 1` (else 409), in place of the insert below;
  make groups when the site has
  none (one per domain present among the site's assets: `code = domain`,
  `domain` set, members = the site's assets of that domain, roles NULL);
  `pickTabGroups`; plan widgets with the shared planner; insert dashboard
  (`location_id = site`, `template_id`, slug `site-layout-<location slug>`;
  a `23505` on the slug → 409 `SITE_LAYOUT_SLUG_TAKEN_MESSAGE`), tabs, widgets,
  points, sources; **insert** the view row `{kind:'dashboard', dashboard_id}`
  with `ON CONFLICT DO NOTHING` and assert `rowCount === 1` (else 409 — the
  pre-check is advisory, the insert is the rule; never `onConflictDoUpdate`);
  audit `master.location.site_layout.make` + `master.location.control_room_view.set`
  + `master.asset_group.create` per group; return `{ locationId, dashboardId,
  dashboardSlug, omittedTabs, droppedCards, resolution }`. Permission, named
  exactly: `accessControl.requireMasterDataUser(jwt)` then
  `assertCanManageLocation` (the `putSetting` pair, **403** on failure —
  S6 below expects 403, not 404) then `canManageDashboard` on the location
  scope (404 on failure, the dashboards precedent); bulk needs
  `organization_admin`/`admin` (`assertCanAuthor`). The `instantiate` site
  arm inherits the group route's `assertCanAuthor` before delegating.

- **D9 Site widgets read.** `GET /dashboards/:id/site-widgets?tab=<key>` (one
  read per dashboard tab, the `mimic-nodes` pattern, declared before
  `@Get(":slug")`) answers `{ dashboardId, tabKey, resolvedAt, scope: {
  assetIds count }, alarms: { active: AlarmListItem[≤20], summary }, roles:
  AssetRoleSummaryItem[], tabs: [{ tabKey, label, assetGroupId, status: {
  worstSeverity, tone, activeAlarms, offlineAssets, assets } }] }`. Scope =
  the tab's group members (or the dashboard scope for Overview/legacy) ∩
  readable ids. `roles` comes from `AssetRoleSummaryService.summarize(assetIds,
  { groupIds: [tab group] })` — an **explicit group scope**, because a null
  scope answers `{ items: [] }`; on the Overview it passes the site's group
  ids. `tabs[]` status is computed for **every** group tab in one query
