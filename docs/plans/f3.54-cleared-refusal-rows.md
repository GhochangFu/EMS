# `F3.54` — implementation plan

**Two failed reads keep a cleared message's refusal row.**

Branch `F3.54-cleared-refusal-rows`, based on `main` at `fab37197`.
Backlog row: P2, Effort 1, Wave 2, `Depends —`. Not a ⭐ enabler.

---

## 0. Goal, and what is out of scope

ADR 0057 Amendment 2's ruling **Q-A** established a principle and applied it to
one exit. A *cleared* message is dispatched exactly once — `notifyCleared` runs
from the clear phase, and `loadActiveAlarms` filters `cleared_at IS NULL`, so
the sweep never sees that alarm again. A refusal that writes no row therefore
buys no retry while costing the only evidence it happened.

Today that principle is applied at `dispatchToChannel`'s **hourly-ceiling** exit
(`const retriable = input.event?.kind === "escalation";`) and at neither of the
two exits above it, which still discriminate on `input.event !== undefined`.

This row changes **two ternaries** so all three event-path exceptions narrow to
the escalation kind: a refused *cleared* message writes its `failed` ledger row
at the failed ledger read (plan D3) and at the failed rate-limit read (security
review H1), while an escalation step at either exit still writes nothing and is
retried on the next tick.

### Explicitly out of scope

- **The two `dispatchToChannels` pre-check refusals** (owner ruling 2). The
  alarm-less event refusal (review L2, returns `[]`) and the cross-organization
  channel filter (review M2, drops the channel) also write no row and also apply
  to a cleared message. They refuse the **pairing** before `buildDedupeKey` has
  run, so there is no key to attribute a row to — a different class from
  refusing a send — and neither is reachable from `notifyCleared`, which always
  passes a real `alarm.id` and sends only to channels already holding a `sent`
  row. **Named in the amendment** so the next reader does not re-file them.
- **A sixth, terminal status** (owner ruling 3). Accepted: the row is written
  `failed`, and the mismatch is recorded rather than fixed.
- No migration, no contract change, no dependency, no web change, no route.

## 1. Every `return` in `dispatchToChannel`, classified from source

The row asks for two branches. Enumerating the method confirms there is no
third — and that the one remaining rowless event exit is self-justifying.

| # | Exit | Reached by | Row today | After `F3.54` |
|---|---|---|---|---|
| R1 | **D3** — `eventDeliveryBlocked` threw → `failed` | event only | none, either kind | **cleared: row. escalation: none.** |
| R2 | `alreadyRecorded` → `skipped_deduped` | event only | none, either kind | **unchanged — correctly** |
| R3 | Step 1 transition dedupe → `skipped_deduped` | raise only | row unless one exists | unchanged |
| R4 | **H1** — `isOverHourlyLimit` threw → `failed` | raise **and** event | raise: row. event: none | **cleared: row. escalation: none. raise: row.** |
| R5 | Over the ceiling → `skipped_rate_limited` | raise and event | already Q-A-shaped | unchanged |
| R6 | Transport result | all | always a row | unchanged |

**R2 is the one exit that keeps writing nothing for a cleared message, and
Q-A's argument does not reach it.** `eventDeliveryBlocked` returns `true` only
because a row *already exists* under that key. The evidence Q-A protects is
already in the ledger; a second row would restate it, which is exactly what
`F3.46` closed. Nothing to do — but say so in the amendment.

**Two non-`return` exits, for completeness.** `dispatchToChannel` can leave by
**throwing** at the `channel.updatedAt.getTime()` watermark line (outside the
`try` on purpose, `F3.50`), and `dispatchToChannels` can throw at
`buildDedupeKey`. Both are programming errors over already-validated fields
rather than operational refusals, and both are caught by `notifyCleared`'s own
`try` and the escalation phase's per-step `try`. Neither writes a row and
neither should.

## 3. Tasks in build order — test first, and the line that reddens each

### Task 1 — D3, the unit gate (RED first)

`notifications.events.spec.ts`, new **case 6b** after case 6. Case 6's shape
with `eventInput({ kind: "cleared" })`:

- `results[0].status === "failed"`, `.error === "delivery ledger read failed"` —
  the result is **unchanged** by this row.
- `recorded.length === 1`, status `failed`, the error text, the dedupe key
  ending `:cleared`, the alarm id.
- `webhook.sent.length === 0` — a failed read is still never a send.
- `warnings.length === 1` — still exactly one warn line.

**Reddened by:** reverting D3's return to the bare
`return { status: "failed", error: "delivery ledger read failed" };`.

**Why this is an *attempt* claim, and why the fake can carry it.** D3 fires
because the ledger read failed; `record()`'s insert runs on the same connection
and swallows its own failure with `logger.error`. The claim is "the cleared path
calls the insert", not "a row exists" — and `fakeDb()` supports exactly that,
because `failDeliveryReads` and `failInserts` are **independent flags** and
`recorded` is populated by the `insert().values()` spy.

**One case deliberately not written.** A variant with both flags set, asserting
the result is still `failed` and nothing rejects, would **pass identically if
`record()` were never called**. That is the `F3.48` shape — an absence assertion
that cannot prove an action — and it is out.

### Task 2 — D3, the production change

Hoist a `const failed` first, as step 2 already does, then:

```ts
return input.event?.kind === "escalation"
  ? failed
  : this.record(input, channel, dedupeKey, failed);
```

`input.event?.kind` and **not** `input.event.kind`, even though `input.event` is
narrowed inside the `if`, so this line is **textually identical** to the
ceiling's. That identity is the row's closing complaint answered.

Rewrite the comment: keep the "a row would poison this key" argument for the
escalation kind, add Q-A's for the cleared kind. Cases 6 and 10 (both
escalation, both `recorded.length === 0`) stay green as free regression gates on
the escalation arm.

### Task 3 — H1, the unit gate (RED first)

New **case 10b**. Case 10's shape with `eventInput({ kind: "cleared" })`:

- `reads.deliveryExists === 1 && reads.rateLimit === 1` — the ledger, then the
  ceiling.
- `results[0].status === "failed"`, `.error === "rate-limit check failed"`.
- `recorded.length === 1`, status `failed`, key ending `:cleared`.
- `webhook.sent.length === 0`.

**Reddened by:** reverting H1's return to
`input.event !== undefined ? failed : this.record(...)`.

### Task 4 — H1, the production change

```ts
return input.event?.kind === "escalation" ? failed : this.record(input, channel, dedupeKey, failed);
```

Update the comment to name the kind, and say that this line is now structurally
identical to the ceiling's twenty lines below — the two adjacent exits no longer
discriminate differently, which is what the row asked for.

Three existing cases become free regression gates: case 10 (the escalation arm),
the unnumbered raise-path block (the raise arm survives because
`input.event?.kind` is `undefined` on that path and `undefined !==
"escalation"`), and cases 7/7b (the ceiling exit, untouched).

### Task 5 — the integration gates (RED first)

`storm-control.integration.spec.ts`, two blocks after the
`sentChannelIdsForAlarm` assertion and before the disabled-channel block, which
owns its own `finally`.

**This layer can hold both branches, and holds a stronger claim than the unit
layer.** Neither branch needs a real read failure. The four SELECTs in this
service are told apart by their **projection** — `{count}` is the rate-limit
read, `{id}` the skip read, `{status}` `eventDeliveryBlocked`, `{channelId}` the
recipients read — and those four are disjoint. So wrap the real `db` in a
pass-through that rejects **one** projection and delegates everything else, and
build a second `NotificationsService` over it:

- **D3 block** — blind `select({ status })`; only `eventDeliveryBlocked` throws,
  and the `insert` goes to real Postgres.
- **H1 block** — blind `select({ count })`; `{status}` passes through and
  returns `[]` for a fresh key, so step 2 runs and only `isOverHourlyLimit`
  throws.

Each block asserts both directions with `statusesByKey`: a **cleared** input
gives `["failed"]`; the same input as `kind: "escalation"` under its own key
gives `[]`; and `sent.length` is unchanged in both. The escalation half is what
kills the over-broad mutation "record on every event".

**The split of ownership, stated plainly.** The unit spec owns *"the insert is
attempted"*; the integration spec owns *"the row lands in
`bms.notification_deliveries` and reads back"* — against the real status CHECK,
the real `organization_id NOT NULL` and the real `alarm_id` foreign key, none of
which the fake has. The read failure is synthetic there; the **write path is
real**, so the integration wording must not be weakened to "attempts".

**Two collision hazards, both mechanical.** (a) The fixture channel already owns
the `warning` and `critical` cleared keys, and one block asserts an absolute
`countByKey(...) === 1` on the first. Because the dedupe key is
`rule:alarm:severity[:suffix]`, each new block needs its **own distinct
`severity` string** — it is free-form and is not written to the row. (b) Append
after the recipients assertion, never before the two absolute
`countDeliveries` assertions on the shared fixture channel.

carries `status`, `error`, `channelCode`, `ruleCode`, `alarmId` and

event kind a row belongs to. After this change `error === "delivery ledger read
failed"` is a *unique* discriminator for a cleared D3 refusal — D3 is event-only
and escalation stops writing it — but `"rate-limit check failed"` stays
ambiguous between a raise and a clear. Recorded in Amendment 4 §4(e); a
follow-up row is filed at closure rather than widening this one.

## 5. ADR 0057 Amendment 4 — section by section

**Title.** `## Amendment 4 — F3.54: two failed reads keep a cleared message's
refusal row (2026-09-08)`

**Lead.** Amends **decision 10** and **Amendment 2's ruling Q-A**. Unchanged:
rulings Q9, Q1, Q2, the escalation path, the raise path. State that ADR 0041
needs its own amendment and why.

**§1 — What Q-A established, and why it stopped one branch short.** Q-A's
argument is about the *cleared kind*, not about the ceiling. `F3.48` wrote it
into the exit it was looking at and left two adjacent exits discriminating on
`input.event !== undefined`. Both predate `F3.48`, which only made the
inconsistency visible by naming the principle. Both emit a `warn`, so this was
never the fully silent shape.

**§2 — Ruling 1: both ternaries narrow to the kind**, with the three-by-two
table (D3 · H1 · ceiling × escalation · cleared · raise), closing on the fact
that H1's line and the ceiling's line are now textually identical.

**§3 — Ruling 2: the two pre-check refusals stay out**, with L2's and M2's
reasons, plus **R2** in the same paragraph: it writes nothing for a cleared
message and always will, because the row that blocked the key **is** the
evidence.

**§4 — Accepted costs.**
(a) On a dead ledger the D3 path now emits a `warn` *and* `record()`'s
`logger.error` for the same event. The honest claim is that the cleared path
**attempts** the row. Argued, not gated — an Effort-1 row does not buy a
log-capture harness for a consequence nothing branches on.
(b) On a total outage the clear phase attempts one INSERT per (cleared alarm ×
channel) before giving up — bounded, on the failure path, inside a serial loop.
(c) Growth is one row per (alarm, channel), self-bounding at
`MAX_EVENT_ATTEMPTS` through R2 even though no retry drives it. In production it
is exactly one.
(d) **Ruling 3:** `failed` is retriable-shaped for a refusal that will never be
retried. Accepted. Nothing reads the key again — the dedupe key carries the
alarm id, an alarm clears once, and a re-raise is a new alarm with a new key — so
the mismatch is cosmetic. A sixth status would be a migration plus a contract
change plus every reader.
(e) The deliveries view cannot name the event kind (§4 above).

**§5 — Which layer holds which claim.** Unit: the insert is attempted, both
branches, both kinds. Integration: the row lands in real Postgres, with the
escalation half as the mutation killer, and the read failure synthesised by
projection-blinding because live induction is not available (§7).

## 6. Blast radius

`dispatchToChannel` is **private** with exactly one caller.

| Caller of `dispatchToChannels` | Reads the result? | Forced change |
|---|---|---|
| `notifyCleared` | **No** — `await`, no assignment | none |
| escalation phase | **No** — `await`, no assignment | none |
| `dispatch()` | passthrough | none |
| `rule-actions.ts` — the only production caller of `dispatch()` | **No** — `void ….catch(…)` | none |

**Can changing D3's return for the cleared kind affect the `results` array?
No — twice over.** `record()` returns its `result` argument unchanged, so the
`DeliveryResult` pushed is byte-identical either way; only a row is written
first. And **no production caller reads the array at all**.

**A `failed` row under a cleared key changes no later decision.**
`sentChannelIdsForAlarm` and `isOverHourlyLimit` filter `status = 'sent'`;
`hasRecordedSkip` filters `skipped_deduped`. `eventDeliveryBlocked` does sample
it — one `failed` row leaves both arms false, so the key is not blocked, which
is correct — and the key is never read again in any case. Within a single clear
the loop covers several channels under one key, but every read is scoped to
`(channel, organization, key)`.

**Existing tests asserting the current no-row behaviour for a cleared message:
none.** The cleared cases in the unit spec are a plain send, the ceiling refusal
(already Q-A-correct) and `sentChannelIdsForAlarm`; the integration spec's are
the Q-A ceiling refusal and the once-per-key proof. **The test layer is purely
additive**, which is itself evidence that ruling 1 is a narrowing rather than a
rewrite.

## 7. §4.6 verification — layer by layer, N/A named

**Database — covered by the integration suite; live induction is N/A with a
reason.** Run `storm-control.integration.spec.ts` with `DATABASE_URL` set
(Postgres is on **5433** here). The gate is asymmetric — unset skips locally and
throws under CI — so run it locally with the URL set or the new blocks assert
nothing. **Manual induction on the running stack is not available:** both
branches fire on a read failure, and inducing one there means revoking a grant
or terminating a backend on a database other sessions are using. The
projection-blinded wrapper is the strongest available gate on a real Postgres,
and that substitution is stated in the block's own comment, not only here.

**API — N/A.** No route reaches `dispatchToChannel`; `dispatch` is
fire-and-forget and the sweep's entry point is called from a loop. The local API
is OIDC with no password grant, so there is nothing to `curl` even if a route
existed. No image is rebuilt, so no stale-image trap applies.

**Browser — N/A, deliberately.** No file under `apps/web/` changes, the DTO is
unchanged, and the new row is the most ordinary row the deliveries view renders:
a `failed` row with an error string. Planting one by SQL and reading the page
would verify `F3.8`'s renderer, not this change — no falsifiable claim about
`F3.54`, at the cost of a human sign-in, since the browser tools never type a
password.

**Cold start — N/A.** No migration, no seed change, no role change.

**Gates.** Root `pnpm test` and `pnpm test:coverage`, plus `pnpm typecheck` and
`pnpm typecheck:tests`. No coverage threshold moves. No assertion touches a
lifetime counter: the fake's counters are per-fake and the integration
assertions are per-key reads.
