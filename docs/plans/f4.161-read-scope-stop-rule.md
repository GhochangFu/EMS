## Goal

One function decides which grant source a user's read scope comes from, and both `scopeForUser` (locations/assets) and `readableOrganizationIds` (organization ids) resolve from that one choice. A `viewer`/`operator` whose organization grant reaches no active site, and whose site grant sits in a second organization, then reads that site's dashboard by slug (200) instead of a 404 — the `F3.69` site view stops showing the error card for that user. An operator/viewer whose grants reach no active site anywhere gets `[]` (the last source, `none`). `admin`, `organization_admin`, `location_admin` and `asset_group_admin` keep today's results and today's query count.

**Out of scope.** No API route, no contract change (no `packages/shared` edit; §4.8 is N/A — `readableOrganizationIds` is internal, `AccessibleScope` is unchanged), no migration, no seed, no web change, no `AGENTS.md` edit in this branch. No change to `organizationIdsFromReadScopeSource`'s per-source derivation (OQ1). No change to `writableOrganizationIds` (its own two-branch rule is not a walk). No caching of the probe.

## Measured facts the plan rests on

- **The two walks today.** `scopeForUser` (`access-control.service.ts:871-880`) loops `readScopeSourcesForRole(role)` and breaks at the first `scopeFromSource` whose `assetIds.length > 0 || locations.length > 0`; the last source's scope stays otherwise. `readableOrganizationIds` (`:745-757`) breaks at the first `organizationIdsFromReadScopeSource` with `ids.length > 0`, else `[]`. Only `operator` and `viewer` have more than one source (`access-scope.ts:64-67`: `organization, location, asset_group, none`).
- **"Yields" is "reaches at least one active location", for every grant source.** In `access-scope-sources.ts`: `organization` filters `locations.active = true` (`:101`) and derives assets only from those locations; `location` filters active (`:143`) and derives assets from those; `asset_group` keeps only groups whose location is active (`:203`, `:214-215`) and derives assets from those groups. So `assetIds` can never be non-empty while `locations` is empty. The probe in D2 is that one predicate, and the E-cases in U3 gate the equivalence on the real database.
- **An empty asset group with an active location DOES yield** (its location is in `locations`). The only asset-group case that does not yield is a group whose location is inactive. The non-yield asset-group case is a group under an inactive location (S3); the empty-group-under-an-active-location case is a residual (see U3).
- **Query cost today, per call, on `fleetDb`.** `scopeFromSource`: `organization` up to 3 queries, `location` up to 2, `asset_group` up to 3; `readableOrganizationIds`: 1 per source visited. The asset-id fetch is the heavy one. Mirroring by calling `scopeFromSource` for every source inside `readableOrganizationIds` would add that fetch to every `GET /dashboards*`, `/alarm-kb` and catalog read — so a cheaper probe is used (D2).
- **Nothing covers `readableOrganizationIds` today.** `evaluate-throttle-route.spec.ts:180` fakes it; `alarm-kb.integration.spec.ts` and `dashboards.service.rls.integration.spec.ts` drive only single-source seeded roles plus two-organization `organization_admin` fixtures. None of them reddens under the fix.
- **Fixture facts.** The seed carries one inactive location, ESKOM `ESK-DECOMM-01` (`packages/db/src/access-fixtures-seed.ts:29,66-76`). `wc-admin@bms.local` holds one active ESKOM location grant. A fresh `pnpm db:seed` gives PHEWB no asset groups. Identity and grant rows insert only through the superuser pool under `FORCE`; organizations and asset groups insert on the fleet pool. A transaction handle is `BmsTx`, not `BmsDb`, so fixtures here are committed with a per-run prefix and deleted by id in `afterAll`.
- **Who reaches each consumer.** `calc-parameters.service.ts:295-297,460-463` call `requireMasterDataUser` first (single-source roles). `rules.controller.ts:190-203` calls `assertOperationsWriteRole(user, "configuration")` first (admin + the three scoped admins). `alarm-kb.controller.ts:45`, `metric-catalog.service.ts:154`, `dashboards.service.ts:116,220` are open to `viewer`/`operator`. `canAuthorDashboards` (`apps/web/src/lib/admin-access.ts:87-94`) never admits operator/viewer, so no author path is affected.
- **Line budget (§4.5).** `access-control.service.ts` 881 (loses about 10), `access-scope-sources.ts` 249 (gains about 70), `dashboards.service.rls.integration.test.ts` 812 (gains about 60). All stay under 1000.
- **CI wiring.** `apps/api/vitest.config.ts` includes `src/**/*.test.ts`, and `ci.yml` runs `pnpm test:coverage` with `DATABASE_URL` set, so a new `*.integration.test.ts` under `apps/api/src` runs in CI with no workflow edit.

## Decisions

- **D1 — one pure selector.** `selectReadScopeSource(sources, yields)` in `access-scope.ts`: walks `sources`, returns the first for which `await yields(source)` is true; if none, returns the last source **without probing it** (exactly today's `scopeForUser`, and it keeps single-source roles at zero probes). An empty list returns `"none"`.
- **D2 — a cheap probe, one `LIMIT 1` per source.** `readScopeSourceYields(fleetDb, user, source)` in `access-scope-sources.ts` answers "does this source reach at least one active location": `organization` = `user_organization_access ⋈ locations WHERE active`; `location` = `user_location_access ⋈ locations WHERE active`; `asset_group` = `user_asset_group_access ⋈ asset_groups ⋈ locations WHERE active`; `global` = `true` (unreachable: `global` is only ever the sole source, for `admin`, and D1 never probes a sole source; `true` states that the walk would pick it); `none` = `false`. All on `fleetDb`, keyed by `user.id` (the Amendment 2/3 comment on each query). `selectReadScopeSourceFor(fleetDb, user)` = `selectReadScopeSource(readScopeSourcesForRole(user.role), s => readScopeSourceYields(fleetDb, user, s))`.
- **D3 — both service walks become one call each.** `scopeForUser` = `scopeFromSource(fleetDb, user, await selectReadScopeSourceFor(...))`; `readableOrganizationIds` = `organizationIdsFromReadScopeSource(user.id, await selectReadScopeSourceFor(...))` after the `admin → null` branch. Remove the unused `noAccessScope` import.
- **D4 — cost.** Single-source roles: 0 probes, today's cost. `operator`/`viewer`: 1–3 `LIMIT 1` probes, then one `scopeFromSource` or one org query. `readableOrganizationIds` never loads asset ids.
- **D5 — the observable `scopeForUser` result is unchanged**, gated by the existing `access-control.integration` cases plus S8/S9 and the E-rows.
