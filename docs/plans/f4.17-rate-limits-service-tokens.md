## 1. Goal

**Part A.** After this row, every `/api/v1/*` request is counted twice in
Redis:

- **Stage 1**, per client IP, before any guard.
- **Stage 2**, per identity, at the end of `JwtAuthGuard`, before any multer
  buffer.

These counts hold across `api` and `api-replica`. They are refused with one
429 shape once `RATE_LIMIT_MODE=enforce`. The Socket.IO handshake gets the
Stage 1 check.

**Part B.** An `organization_admin` (or `admin`) can do the following from
`/admin/service-accounts`:

- create a service account (`viewer` or `operator`) with grants;
- issue it an expiring `bms_sat_…` token, shown once;
- see `last_used_at`;
- revoke the token.

A revoked token stops working on every replica within one `NOTIFY` round-trip.
Every lifecycle event is in `bms.audit_log`.

**Architecture.**

- A new `apps/api/src/rate-limit/` module: store, classes, decorator, 429
  helper, Stage 1 middleware.
- A new `apps/api/src/service-accounts/` module: token codec, verifier, revoke
  listener, admin controller and service.
- One migration (`users.kind` and `bms.service_account_tokens`).
- One web screen.

No new dependency. The store uses the `redis@^5` client the Socket.IO adapter
already uses.

**Out of scope.**

- RFC 7807 bodies (`F4.21`; this row only centralises the 429 and token-error
  sites).
- Per-organization limit overrides.
- A limit-admin screen.
- Token IP allow-lists.
- Expiry-warning notifications.
- Keycloak client-credentials.
- The Traefik edge limiter.
- Moving the background sweeps (`F4.128`).
- `--requirepass` on Redis (`F3.12`).

## 11. Recorded during PR 1 (2026-11-10)

**What the build changed from §4, and why.** Recorded rather than rewritten
away.

- **Stage 1 counts every path except the three probes**, not "every path
  starting with `/api/v1/`". Express matches routes case-insensitively, so a
  prefix test let `POST /api/V1/auth/login` reach the login handler with no
  count at all. Both reviews found this (security H1, code correctness 1). The
  exemption and the login test compare a lower-cased path with its trailing
  slashes removed.
- **The HTTP client address comes from `clientAddress()`, not `req.ip`.**
  With a forwarded chain shorter than `API_TRUST_PROXY_HOPS`, Express falls
  back to the leftmost entry, which the client wrote. `clientAddress()` keys
  that request on the socket peer instead (security M2). `trust proxy` is
  still set, so `req.ip` agrees whenever the chain is the expected length.
- **`/health`'s `rateLimit` section carries `store` only, not `mode`.**
  `/health` is public on AWS (security L2). `store` reads `degraded` while the
  client is not ready, not only after a failed call (code correctness 2).
- **When the memory store overflows, it drops Stage 1 counters before
  Stage 2.** This stops an IPv6 subject flood from resetting the flooder's
  own identity budget (security L1).
- **Accepted, not changed:**
  - A Redis call that times out may still `INCR`, so it counts twice
    (security L3).
  - A Stage 1 refusal leaves no access-log line, because pino-http registers
    later, at Nest init. Only the decisions counter carries it.
- **Names as shipped:**
  - The decorator is `RateLimitClassOf('heavy')`, because `RateLimitClass` is
    the type. U6's scan looks for that name.
  - The metric label is `bucket`, not `class`, because it carries the Stage 1
    buckets too: `bms_rate_limit_decisions_total{stage,bucket,outcome}`.
  - The 429 schema lives in `packages/shared/src/contracts/rate-limit.ts`,
    not in `errors.ts`.
- **Live check in place of supertest** (the repository has none). A minimal
  Nest app followed `main.ts`'s order: CORS, trust proxy 2, then Stage 1. It
  showed:
  - `req.ip` is the client behind a forged `X-Forwarded-For` prefix;
  - the 4th request at a limit of 3 got a 429 carrying
    `Access-Control-Allow-Origin` and `Retry-After`;
  - `/health` was never limited;
  - a preflight was not counted.
- **Measured cost:** one store check on local Redis has p50 0.03 ms and p95
  0.06 ms (n = 2,000), so two checks add about 0.12 ms p95 per request.

**Gate before `RATE_LIMIT_MODE=enforce` (owner's switch, decision 7).** Both
reviews found this.

- A refused Socket.IO handshake is sent `rate_limited` and then
  `disconnect(true)`. socket.io-client never reconnects after a server
  disconnect, and nothing in `apps/web` handles `rate_limited`.
- The SPA opens one socket per live hook (about eight on some pages), and it
  opens them again on every navigation. A control room behind one NAT can
  therefore spend 30/min quickly. Its live alarm feed would then stay dead
  until a remount.

Before `enforce`, do both:

1. Size `ws` from the shadow week's `bucket="ws"` counts.
2. Either make the SPA reconnect after `retryAfterSeconds`, or refuse in a
   way the client retries.

The same lockout reasoning applies to the 10/min `login` bucket behind a
shared NAT under local auth.

## 14. Recorded during PR 4 (2026-11-11)

**U10, `service-accounts/service-token-codec.ts`.**

- The token format is `bms_sat_<12 [A-Za-z0-9]>_<43 base64url>`. The id is
  drawn with `randomInt`, so it has no modulo bias. The secret is 32 random
  bytes.
- Only `SHA-256(secret)` is stored, and the compare runs in constant time.
- A malformed token is refused before any database read.

**U11, `ServiceTokenVerifier` and the guard.**

- **The guard's route.** `JwtAuthGuard.verifyToken` sends a `bms_sat_` token
  to the verifier before any JWT parse, under both `AUTH_MODE`s. A JWT never
  reaches the verifier, and a token never reaches `jwt.verify`; both
  directions are tested.
- **The verifier's checks.** It reads on the `bms_auth` pool, which since
  `0147` sees live tokens only, and repeats the expiry and revocation tests
  in code. It then requires the owning row to be `kind = 'service'`, not
  disabled, in the token's organization, and `viewer` or `operator`.
- **The principal.** It is JWT-shaped: `sub` is the account's `users.id`. It
  is placed in the identity memo, so `resolveDbUser`, `resolveActorId` and
  RLS read the service row exactly as they read a person's.
- **Read-only tokens.** A `read_only` token gets a 403 `token_read_only` on
  any method other than GET, HEAD or OPTIONS. This runs before the Stage 2
  limit.
- **Rate-limit budget.** Stage 2 keys a token on `token:<id>`, so two tokens
  of one account are two budgets.
- **Cache.** The cache holds a verified token for at most 30 s and keeps the
  stored hash, so every request still proves its secret.
- **`last_used_at`** is touched at most once a minute per token per process.
  It is fire-and-forget, and a failure is logged once with the error's name
  only.
- **Socket.IO** accepts a token on the handshake (Q12). The socket is tagged
  `data.serviceTokenId`.

**U12, `bms_service_token_revoked`.**

- `notifyServiceTokenRevoked(tx, tokenId)` sends the NOTIFY inside the
  revoke's transaction. PR 5's revoke and disable paths call it.
- Each process's `ServiceTokenListenerService` responds by forgetting the
  token in its verifier and closing that token's sockets
  (`SocketRegistry.disconnectServiceToken`).
- On every (re)connect it clears the whole cache and closes the sockets of
  any connected token that is no longer live. This mirrors `bms_user_disabled`.
  It is a per-process fan-in, not a sweep, so it runs in every replica.

**Deviations from ADR decision 9's interface note.**

- **One code for every refused token.** A refused token gets one 401 code,
  `token_invalid`, not separate `token_expired` and `token_revoked`. The
  `0147` policy hides revoked and expired rows from `bms_auth`, so the
  verifier cannot tell them apart. One code also gives no oracle (the
  security review's own recommendation). `authFailureCodeSchema` gains
  `token_invalid`.
- **The read-only 403** carries `code: "token_read_only"` as planned.

**Tests:**

- `service-token.spec.ts`, 12 tests: the codec, every verifier refusal, the
  cache window, `forget`, the touch, and the notify handlers.
- `jwt-auth.guard.service-token.spec.ts`, 6 tests. Mutations: dropping the
  per-token key turns the budget test red; dropping the read-only refusal
  turns the write test red.
- `service-token.integration.spec.ts`, 5 tests on a real `bms_auth` pool:
  valid, revoked, expired, a disabled account, `last_used_at` stamped, and a
  committed NOTIFY reaching a real LISTEN client.
- `tests/f4.17-service-token-wiring.test.ts` pins the wiring.

The `Authorization` header is already redacted from the pino request log
(`logger.options.ts`), so a token never reaches a log line.

**What PR 4's reviews changed.** The security and code reviews found the
same three races.

- **A socket opened while a revoke landed stayed open with no time limit**
  (security M1, code C2). Fixed in `service-token-socket.ts`:
  - `tagServiceTokenSocket` stores the token id before the handshake's first
    `await`, so a NOTIFY that lands during verification finds the socket;
  - `holdServiceTokenSocket` reads the token fresh once the socket is
    registered (the `isUserDisabled` pattern), and closes it when the token
    is no longer live.
- **A forget during a verify's reads could be undone when the read finished
  and wrote the cache** (security L1, code C1). Each `forget` and `forgetAll`
  bumps a counter; a verify that sees a counter move answers from its read
  and does not cache it.
- **A token socket outlived its token's expiry** (security L2, code C3). The
  principal now carries `expiresAt`, and `holdServiceTokenSocket` arms a
  timer that closes the socket at expiry. Delays beyond Node's 24.8-day
  timer limit re-arm.
- **A forged but well-formed token cost a `bms_auth` read on every request**
  (security L4). An unknown id is remembered as unknown for 5 s. Only "no
  live row" is remembered, never a wrong secret, so nobody can lock a real
  token out.
