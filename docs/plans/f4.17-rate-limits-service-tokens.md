## 1. Goal

**Part A.** After this row, every `/api/v1/*` request is counted twice in
Redis:

- **Stage 1**, per client IP, before any guard.
- **Stage 2**, per identity, at the end of `JwtAuthGuard`, before any multer
  buffer.

These counts hold across `api` and `api-replica`. They are refused with one
429 shape once `RATE_LIMIT_MODE=enforce`. The Socket.IO handshake gets the
Stage 1 check.

**Part B.** An `organization_admin` (or `admin`) can do the following from
`/admin/service-accounts`:

- create a service account (`viewer` or `operator`) with grants;
- issue it an expiring `bms_sat_…` token, shown once;
- see `last_used_at`;
- revoke the token.

A revoked token stops working on every replica within one `NOTIFY` round-trip.
Every lifecycle event is in `bms.audit_log`.

**Architecture.**

- A new `apps/api/src/rate-limit/` module: store, classes, decorator, 429
  helper, Stage 1 middleware.
- A new `apps/api/src/service-accounts/` module: token codec, verifier, revoke
  listener, admin controller and service.
- One migration (`users.kind` and `bms.service_account_tokens`).
- One web screen.

No new dependency. The store uses the `redis@^5` client the Socket.IO adapter
already uses.

**Out of scope.**

- RFC 7807 bodies (`F4.21`; this row only centralises the 429 and token-error
  sites).
- Per-organization limit overrides.
- A limit-admin screen.
- Token IP allow-lists.
- Expiry-warning notifications.
- Keycloak client-credentials.
- The Traefik edge limiter.
- Moving the background sweeps (`F4.128`).
- `--requirepass` on Redis (`F3.12`).
