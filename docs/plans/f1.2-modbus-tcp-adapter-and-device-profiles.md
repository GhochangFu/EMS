# F1.2 — Modbus TCP read adapter and device profiles (ADR 0141)

**Status: approved 2026-11-22** (owner, in chat: "Approve the plan"; P1–P12 ruled the same day, §12). No code PR starts before the ADR amendment it depends on is accepted (§13). Written by plan-architect (Fable) against `main` at `5359e6e6`. CodeGraph was not available; every path below was checked by read and grep. **Nothing was run**: every claim that needs a database, a build or a socket is listed as a measure-first task.

**Precondition: met.** ADR 0141 is *Accepted* (2026-11-22, #1480). `F1.2` is Track A, Wave 1, P0, effort 10–12 person-weeks (`docs/BACKLOG.md:431`; the unit is at `:37`), depends on `F1.1` (done). It is **not** a star enabler; `F1.1` is. PR 1 and PR 2 still define the seam every later PR hangs off, so they are built serially and hands-on.

**Goal:** One read-only `modbus_tcp` poll adapter on `node:net`, an organization-scoped device-profile table with an admin editor, a poll interval set per organization and overridden per endpoint for every poll protocol, an edge export script, and a simulator, so that a Modbus meter is read end to end without a client's register map.

**Architecture:** The wire codec is a pure, zod-free module in `packages/shared`; the adapter, its `node:net` transport and its read planner are in `apps/ingest/src/adapters/`; the host resolves the interval in the binding plan and the reload registry replaces an endpoint whose interval or device slice changed. Profiles are rows in `bms.device_profiles`; binding copies the registers into `rtu_connection_configs.config.device`, so the host and the edge never read a profile.

**Tech stack:** Node core (`node:net`), Zod, Drizzle, NestJS, React + TanStack Query. No new dependency.

## 1. Goal and out of scope

An operator imports or writes a device profile, binds an RTU to it on the RTUs page, and the ingest host (or an edge box, from an exported file) polls the device with function codes 01–04 at the resolved interval and writes the samples through the existing normaliser. The local stack shows it with a Node-only Modbus simulator. The row closes only on a recorded read from one real bench device.

**Out of scope.** Function codes 05, 06, 15, 16 or any write (`F3.12`); Modbus RTU direct serial; any protocol library; BACnet, SNMP, OPC-UA, REST polling, DCS; a cloud-to-edge config push; re-applying an edited profile to bound devices (a later row, ADR decision 15); bridging address gaps (decision 8); discovery (`supportsDiscovery` stays `false`); a copilot catalog entry for any new route; a `bms_ingest` role; the bench device purchase; any `AGENTS.md`, `docs/roadmap.md` or `docs/BACKLOG.md` scope edit in a feature PR.

### The questions as asked

1. **P1 — unit identifier 255.** Decision 6 bounds `unitId` to 0–247. The Modbus TCP implementation guide names 255 for a directly addressed TCP device (to be confirmed in T1.0), and some Ethernet meters answer only to it. (a) keep 0–247; (b) accept 0–247 and 255. *Recommended: (b)*, as ADR 0141 Amendment 1.
2. **P2 — profile versions and `verified`.** (a) every save is a new immutable row; an edit or a copy sets `verified: false`; only a stock file can carry `true`; (b) edit in place until a device is bound; (c) draft and publish, as asset templates. *Recommended: (a)* — a bound device's `{ code, version }` then always names a row that still says what was copied.
3. **P3 — the stock meter list (Q6).** Candidates: Schneider PowerLogic PM5000 series, Secure Elite 400 series, Elmeasure LG series, Selec MFM series, L&T (the list is the owner's). The rule: a model ships only with a public manual, its revision and page numbers. Also: does the owner supply the PDFs, or approve a web fetch for the agent? *Recommended: three models first, the bench device's model among them.*
4. **P4 — intervals above 360 s** (M12). The freshness cap is 900 s, so a device polled every hour shows as not live for most of the hour. (a) keep the 1 h bound and show a warning on both forms; (b) lower the bound to 360 s (amends decision 10); (c) raise the freshness cap (amends ADR 0075). *Recommended: (a).*
5. **P5 — the simulator's network** (M13). (a) a new `modbus-sim` network joined by `ingest` and `modbus-sim` only; (b) the simulator joins `ingest`, and can then reach Postgres; (c) no compose service, the simulator runs on the host. *Recommended: (a)*; it amends ADR 0016 Amendment 8 and the `F4.61` test.
6. **P6 — which hosts the cloud host may dial** (M13). An `organization_admin` can set `host`; the ingest container reaches `postgres` and `web`, and on a shared private network any other tenant's meter. ADR 0141 says a guard is "a possible follow-up, not v1". (a) no guard in v1, as written; (b) `MODBUS_TCP_HOSTS` on the cloud host, empty by default, fail closed, the ADR 0114 pattern; the edge is not affected. *Recommended: (b)*, about 0.5 pw in PR 4, as ADR 0141 Amendment 1. The security review will raise it either way.
7. **P7 — the value of a failed read** (M10). (a) `0` with `good: false`, as decision 9 and the conformance suite require; the docs say not to set `accept_bad` on a Modbus point; (b) a failed block emits nothing and the adapter counts it itself, which loses the per-point drop record. *Recommended: (a).*
8. **P8 — registers on the edge** (M9). (a) the export writes the full list (decision 17 as written); the cloud counts unmapped keys as unresolved on every batch; (b) the export writes only registers mapped to an active point; a new mapping then needs a new export. *Recommended: (b).*
9. **P9 — two RTUs on one gateway with different intervals** (M8). (a) the shortest resolved interval wins; (b) the first RTU by id wins; (c) the second RTU is skipped by name. *Recommended: (a)* — no device is read more slowly than its own setting.
10. **P10 — reconnect after a lost socket** (M3). (a) the adapter re-dials at the start of the next `poll()`, no backoff; (b) the host restarts a poll adapter whose own health says `disconnected`, through the existing backoff, for every poll protocol. *Recommended: (b)* — it is what decision 9 states, and `F1.3`/`F1.5` get it with no further work.
11. **P11 — how far onboarding goes** (M7). (a) onboarding stores a valid Modbus connection with ingest off, and the operator binds a profile and switches ingest on from the RTUs page; (b) the draft also names a profile, and the commit copies the registers and may switch ingest on (about 1–1.5 pw more, in the chat, the Excel path and the commit). *Recommended: (a)*, with (b) as a new row.

(a) global `admin`; (b) also an `organization_admin` with a direct grant, as the energy settings. *Recommended: (a).* Decision 13 *(drafter)*: registers as table rows. (a) rows only; (b) rows plus a CSV paste. *Recommended: (a)*, with (b) as a later row.
