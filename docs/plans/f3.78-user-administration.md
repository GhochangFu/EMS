## 1. Goal and scope

Give `admin` and `organization_admin` a way to create a user (Keycloak account plus `bms.users` row, joined by `oidc_subject`), edit it, deactivate and reactivate it, set a temporary password, and manage its organization / location / asset-group grants; give every master-data role the ability to create and edit an asset group and to add and remove members. Every write runs in `withTenant` of the **target row's** organization (or on `bms_fleet` when the row's old or new role is `admin`), writes one audit row in the same transaction, and is refused outside the caller's scope without naming the hidden row.

**Out of scope (ADR *Promotion* and decision 13):** MFA (`F4.13`), SSO federation, self-service sign-up, access reviews / approvals / SCIM, deleting a user or an asset group, a reassign route for a paused schedule, local-auth user writes (read-only screen, decision 11).

## 3. Units

Conventions for every unit: tests first; assertions in `*.spec.ts` with a `*.test.ts` wrapper under `apps/**` and `packages/**`; inline assertions in `tests/`; every new `tests/*.test.ts` file appended by hand to the root `typecheck:tests` script (`pnpm pkg set`); `pnpm typecheck:tests` run before claiming a signature change is safe; one claim per `it()`; the named mutation is **run** and the failing test's name is read. Never `select()` the `users` table without a column list on a pool role — `password_hash` is not granted. **Never `tx.insert(users)` on a pool role**: drizzle-orm 0.38.4 `buildInsertQuery` (`pg-core/dialect.js:346-376`) lists every table column and sends `default` for an omitted one, so the statement names `password_hash`, and Postgres checks the column INSERT privilege on every listed column; a bare `.returning()` also selects `password_hash`. The user insert is raw `sql` with an explicit column list and an explicit `RETURNING` list.

## 8. Departures from the ADR text

1. **Where the link runs.** Decision 4 places the first-sign-in link in `resolveDbUser`; here it runs in the guard's call of the same shared function, before the `disabled_at` check (decision 8). Outcome identical and strictly safer.
2. **"It must change exactly one row" (decision 4) is read as the statement's success condition, not as a throw on zero rows.** Zero rows means no row to link — a freshly federated operator/viewer with no `bms.users` row, a row already linked to another subject, or a concurrent first request that won the link — and the request takes the ADR 0044 path (or the re-read). Only > 1 rows throws.
3. **Field name.** `emailVerified` in the contract; `email_verified` in the claim.
4. **`OIDC_CLIENT_ID` is required under OIDC**, no default (decision 5's `azp` option, fail-closed like `OIDC_ISSUER`).
5. **Realm roles are read through `role-mappings/realm/available`**, not `GET /roles/{name}`.
6. **The paused schedule is advanced to its next occurrence**, not left due and not put on the hourly poison backoff (D3).
7. **The password policy is applied by the provisioning step, not by the realm import** (decision 6 names the policy, not its carrier): the import of the seven plaintext demo credentials must not depend on how Keycloak 24 validates them.
8. **Deactivate and reactivate both write one audit row on every call** (decision 14), with `alreadyDisabled` / `clearedDisabledAt` flags, so decision 8's idempotent retry is visible in the log.
9. **PR2 adds a named volume for `/opt/keycloak/data`** (`bms-keycloak-data`) so API-created users survive a `keycloak` recreate: ADR 0089 creates users in Keycloak but did not name where Keycloak keeps them. Owner ruling 2026-10-03. It is infra, not scope, so ADR 0089 is not amended. The mount is the whole data directory because the image has no `h2` directory — a volume mounted there is root-owned and Keycloak (uid 1000) cannot write it. Moving an existing deployment onto the volume is a one-time realm re-import (new signing keys, and new user ids where the realm predates the pinned ids) — `docs/runbooks/keycloak-user-administration.md` §6.

## 9. Open questions and gates

**Q-A — Keycloak in CI. Ruled by the owner 2026-10-02: run it on every code PR.** Recommendation: run it (one `docker run -d` step, ~60–90 s inside the job that already waits for Postgres), with the `/etc/hosts` entry so the hostname rule holds. Alternative if minutes are tight: a `keycloak` label-gated job; the per-push job then sets `KEYCLOAK_INTEGRATION=skip` and the gate prints a verdict line.

**Q-B — Ruled by the owner 2026-10-02: keep decision 5's rule.** `http://localhost:8080` for a developer running the API from source. Recommendation: keep decision 5's text; the runbook documents the `keycloak` hosts entry (the same mechanism CI uses) or the API in Compose. A developer path by URL would be a one-line amendment to decision 5, not a plan change.

**Q-C — How K6 reads the realm policy. Ruled by the owner 2026-10-02 during the PR1 build: read as the master admin.** The `bms-api-admin` service account (`manage-users`, `view-users`) gets a reduced realm representation without `passwordPolicy` or `bruteForceProtected` (HTTP 200, both keys absent), so K6 reads `GET /admin/realms/bms` with the bootstrap master admin, the same identity the provisioning step uses. CI's test step gets `KEYCLOAK_ADMIN` and `KEYCLOAK_ADMIN_PASSWORD` (throwaway values). The service account keeps exactly `manage-users` and `view-users` (decision 5); `view-realm` is not added.

**Q-D — Keycloak's required `lastName`. Ruled by the owner 2026-10-02 during the PR1 build: make the names optional.** Keycloak 24's default user profile requires `firstName` and `lastName`, and the shared realm has the `VERIFY_PROFILE` required action enabled, so a user created with `firstName` only (D1) would meet an "update profile" page at first sign-in and could change the `name` claim. The provisioning step (U4) therefore also removes the `required` block from `firstName` and `lastName` in the user profile (GET, transform, PUT, as it already does for `email.permissions.edit`), and K5 gains a case for it. D1 stands.
