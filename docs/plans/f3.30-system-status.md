# F3.30 — System Status and Data Quality indicators: implementation plan

**Scope gate:** [ADR 0075](../adr/0075-system-status-and-data-quality.md), Accepted 2026-09-25 (PR #548, `b9fb6b53`). Plan written by `plan-architect` (Fable) on 2026-09-25 against `main` at `b9fb6b53`. Not a ⭐ enabler. No migration, no new dependency, no `packages/db` change, no `migration-reviewer`.

**Goal.** Two things, one PR. (1) The four `kw`-only freshness tests (`locationKpis`, `locationDashboard`'s RTU rows, `kpis.sites_online`, the map's `fresh_count`) move to the ADR 0074 any-point rule through one shared `live` CTE whose window is built from `LIVE_TELEMETRY_MAX_AGE_SECONDS`; `total_kw` does not change; the `/` tile hint follows the window; a `tests/` guard proves every freshness bound is built from the constant. (2) A new authenticated read `GET /api/v1/system/status` (Zod contract in `packages/shared`) answers three component states (`queue`, `storage`, `field_data`), one verdict, and `dataQuality` = fresh ÷ streaming assets in the caller's scope; a `SystemStatusIndicator` in the shell footer polls it every 30 s and renders the verdict and the Good/Fair/Poor band, red "Status unavailable" on a failed request.

**Out of scope.** An ingest heartbeat, drop counters, per-device last-seen (`F3.16`); gap coverage or an expected reporting interval; the sidebar placement (`F3.29`, §5 IA gate); a `database` component; queue depths, bucket names or error text in the status body; fixing the unbounded `kw_latest` read (ADR 0075 decision 2 keeps it as it is); any `AGENTS.md` edit (separate `chore(agents):` PR, §9.10); the closure edits in §"Owed after merge".

**Serial.** One branch `feat/F3.30-system-status`, one commit per unit, in the order below (ADR 0075 ruling 10). Units 5–9 touch files disjoint from units 1–4, but the whole item is ~9 small units of 30–150 lines each; the cold-start cost of a second worktree exceeds the saving. No fan-out.

## Plan decisions (ADR silent; the plan chose; the owner may veto)

1. **No `active` filter on the denominator.** Decision 1 says "an asset in the caller's scope with `rtu_id IS NOT NULL`"; `kpis`' `asset_sites` also ignores `active`. Dev has 0 inactive assets with an RTU, so the choice changes no number today.
2. **One shared CTE text**, `LIVE_ASSETS_CTE_SQL` in `telemetry-freshness.ts`: `live AS (SELECT DISTINCT asset_id FROM telemetry.point_values WHERE time > now() - interval '<N> seconds')`, fleet-wide (the 25 s window holds ~12 rows on dev; scope is applied by the join that follows). The role-summary keeps its `members`-restricted form over the same interval constant.
3. **Component order** `queue`, `storage`, `field_data` (the ADR table). **Labels** "Job queue", "Object storage", "Field data". `title` = `Job queue: ok · Object storage: not configured · Field data: degraded` (underscore → space).
4. **Loading state** renders a grey dot and "Checking status…" — neither "operational" nor "unavailable".
5. **`percent`** = `Math.round(fresh / streaming * 1000) / 10`; rendered as `Data quality 98.6 % Good` (decision 5's own spacing); `null` → `Data quality —`.
6. `StorageHealthService` is injected **required** in the new service: the module is API-only (`AppModule` always imports `StorageModule`); `HealthController`'s `@Optional()` exists only because that controller also lives in the worker.
7. **Empty scope** (`readableAssetIds` = `[]`) runs no query: `streamingAssets 0`, `freshAssets 0`, `percent null`, `field_data: not_monitored`.
8. Query key `["system", "status"]`, `refetchInterval: SYSTEM_STATUS_REFETCH_MS = 30_000`, `refetchIntervalInBackground` left `false`.
9. The `/` hint becomes `` `Sites with fresh telemetry (~${FRESH_MS / 1000}s)` `` from `apps/web/src/lib/schematic-telemetry.ts` — the web constant the `tests/` guard already pins to the API constant, so the hint cannot drift again.
