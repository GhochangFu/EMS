## 1. Goal

A signed-in user sees, for each **real** asset they can read, whether its condition is getting worse and, if the trend of the last 28 local days holds, in how many days it reaches a limit that already exists. Two indicators: **(a) health trend** — the daily health score falling toward the lower edge of the template's `fair` band; **(b) point drift** — the daily mean of a ruled ML-target point moving toward its nearest threshold rule. The answer is a **range in days**, never one date, named **"Time to limit (trend)"**, labelled *Estimated*, with the *Advisory* pill, the line "A trend from the last 28 days, not a failure prediction." and an *Assumptions* list. It is computed when a page asks, by pure functions in a new API module `apps/api/src/degradation/`, from tables that already exist. It shows in four places: a *Degradation — advisory* section on `/asset-history/:assetId`, one line on the asset health card, a *Trending toward a limit — advisory* card on the control-room organization and site pages (after *Bad actors — advisory*, never on the wall, top 10), and a display-only note beside a maintenance schedule that states two figures and no action.

**Out of scope** (named so nobody builds it):
- Any migration, table, grant, index, cache, queue, worker job, environment variable or package. Any `apps/ml` change.
- A learned RUL, the words "remaining useful life" or "RUL" on any screen, an accuracy figure, a percentage of confidence, a single date.
- Any alarm, notification, work order, report, export, copilot answer or copilot tool. Any dismiss or "done" state. Any LLM call or LLM wording. Any change to a schedule. Any history of past estimates.
- A new page, a navigation item, a dashboard widget, a tab on `/advisories`.
- Simulated assets. Lifecycle fields (`F4.386`). `last_completed_at` on work-order close (`F4.385`). Run-hours or usage-based schedules.
- Any change to the health score, its bands, its roll-up, the donut, `assets.health.score`, the alarm engine or any threshold rule.
- Any behaviour change in `apps/api/src/ml/**`, `apps/api/src/asset-health/**` or `apps/api/src/advisories/**`. Four symbols there gain visibility only (R-r).

## 3. Refinements (each is a call inside the ADR; veto at skim)

- **R-a — one request, one clock, one window per zone.** For an asset in zone Z with local today D, the window is the local days D−28 … D−1. Day index `x` is 0 for D−28 and 27 for D−1.
- **R-b — the zone** is `resolveSiteTimeZone(location zone, organization zone)`: the site chain every other page uses, ending at UTC. ADR 0138 has no "no zone, no answer" rule (ADR 0137 had one).
- **R-c — days are grouped in SQL**, `(bucket AT TIME ZONE zone)::date` with the zone bound per asset through `unnest`, as `readLocalHourEnergy` binds it. `localDay`, `shiftDay` and `windowDays` build the day labels the rows are matched to; a row outside the asset's 28 labels is dropped.
- **R-d — a day "has a value"** when, for health, `scoreAsset` answers a number for that day's counters; for drift, when the day's Σ`sample_count` is above 0. Missing days stay missing: no fill, no interpolation.
- **R-e — the current value** is the mean of the values present in the window's last 3 local days (x 25–27). None present → not reported (the data is stale).
- **R-f — the arithmetic** is section 4.3: Mann–Kendall with the tie correction and the continuity correction, normal approximation (n is always ≥ 21); Theil–Sen over all day pairs; Sen's rank interval with `scipy`'s index rule.
- **R-g — the projection** starts from the current value (R-e) at the window's end. The **median** slope decides the horizon rule. The range ends come from the interval's two ends: `min = max(1, floor(distance ÷ |steepest|))`, `max = ceil(distance ÷ |gentlest|)`, each quotient rounded to 6 decimals first; equal ends become `min` and `min + 1`; a `max` above 90 is sent as `null` and reads "to more than 90".
- **R-h — no single-day figure crosses the wire.** The contract carries `min` and `max` only, so no screen can print one date.
- **R-i — the health limit** is the band whose `code` is exactly `fair`. The sentence names the label of the next band in the template's list. No `fair` band, or `fair` last in the list → no health trend.
- **R-j — drift targets** are a constant `DEGRADATION_DRIFT_TARGETS` in the shared contract, the union of the scorer's two default lists, held equal to `targets.py` by a repo test (the `e1.1-ml-readiness-single-source` shape). The scorer's environment overrides are not followed.
- **R-k — candidates.** An active asset with at least one active point that passes the real line. A drift point is an active point of a target class that passes the real line itself and has at least one covered rule.
- **R-l — covered rules are `E1.9`'s**: `readThresholdRules`, then `covers`. No operator or unit logic is written twice.
- **R-m — sentences are built on the server** by pure functions; the response carries both the sentences and the numbers.
- **R-n — the cap.** With more than 200 candidates, `scoresInScope` ranks them (lowest score first, no score last, then id) and the first 200 go on. With 200 or fewer it does not run.
- **R-o — the schedule read is separate and quiet.** It runs after the numbers are final, only for assets with a crossing, in its own `withReadScope`. A failed read means no note, one `warn` with the error's class name, never a failed response. The note changes no number.
- **R-p — every surface draws nothing** while loading, on a failed read and when it has nothing to show: no heading, no empty sentence, no banner, no "Loading…" card.
- **R-q — the list route is `heavy`** (12 a minute), the asset route `read`: one list call recomputes up to 200 assets over 28 days with no cache, the reason `E1.6a`'s security review gave for `/advisories`. A refused call hides the card (R-p). The web keeps a list for 15 minutes per scope.
- **R-r — four visibility-only edits outside the module**: `healthForAssets` becomes public; `covers`, `toCrossingRule` and `midnightOf` gain `export`. No statement, no behaviour and no caller changes.
- **R-s — a module-wiring spec** holds the new module's edges, because CI does not boot the API and a merge deploys by itself.
- **R-t — due days** on the note use the panel's own formula, `ceil((nextDue − now) ÷ 1 day)`, so the two figures on one card agree.

### 4.3 The math file — `apps/api/src/degradation/trend-math.ts` (pure, no import)

```ts
export const Z_90 = 1.6448536269514722;          // the 0.95 normal quantile, for a two-sided 90 % interval
export function normalCdf(x: number): number;     // Abramowitz–Stegun 26.2.17, |error| < 7.5e-8
export function mannKendall(ys: readonly number[]): { n: number; s: number; varS: number; z: number; p: number };
export function theilSen(xs: readonly number[], ys: readonly number[]): { pairs: number; slope: number; low: number; high: number };
```

- `S = Σ_{i<j} sign(y_j − y_i)`, in time order.
- `Var(S) = [n(n−1)(2n+5) − Σ_g t_g(t_g−1)(2t_g+5)] ÷ 18`, `t_g` the size of each group of equal `y`.
- `Z = (S − sign(S)) ÷ √Var(S)`; `Z = 0` when `S = 0` or `Var(S) ≤ 0`. `p = 2 × (1 − Φ(|Z|))`; `p = 1` when `Var(S) ≤ 0`.
- `normalCdf`: `t = 1 ÷ (1 + 0.2316419·|x|)`; upper tail `= φ(|x|)·t·(0.319381530 + t·(−0.356563782 + t·(1.781477937 + t·(−1.821255978 + t·1.330274429))))`.
- Slopes: `(y_j − y_i) ÷ (x_j − x_i)` for every `i < j`, sorted ascending; `N` of them. `slope` is the median (the mean of the two middle values when `N` is even).
- Interval: `C = Z_90 × √Var(S)` (the same tie-corrected variance); `low = slopes[max(round((N − C) ÷ 2) − 1, 0)]`, `high = slopes[min(round((N + C) ÷ 2), N − 1)]`, 0-based.

### 4.4 The trend rule and the projection (`degradation-trend.ts`, pure)

`trendOf({ xs, ys }, limit)` where `limit` is `{ value, direction: "down" | "up" }` or a function of the current value (drift, 4.6). In this order; the first that fails ends it with a reason (reasons are for tests and logs, not the wire):

1. `n ≥ DEGRADATION_MIN_DAYS` (21), else `coverage`.
2. At least one value with `x ≥ 25`, else `stale`. `current` = their mean.
3. `p < 0.05` **and** (`low > 0` **or** `high < 0`), strictly, else `no_trend`.
4. The slope points at the limit (health: `slope < 0`; drift: 4.6 finds a rule ahead), else `not_toward_limit`.
5. `current` not already beyond the limit (health: `current ≥ limit`), else `already_past`.
6. `point = |limit − current| ÷ |slope|`. `point < 1` → `under_one_day` (not reported). `point > 90` → reported with status `beyond_horizon`, `daysToLimit: null`. Else status `crossing` with R-g's `{ min, max }`.

| P3 | V1 as health, limit 0.70 | current 0.77; `crossing`, `{ min: 14, max: 15 }` (equal ends widen by one) |

### 4.5 Health trend (`degradation-health.ts`, pure)

Input: the asset's `TemplateHealth | undefined` and its counter rows per `(day, pointKey)`: Σ`in_range_count`, Σ`sample_count`, max `rule_count`, max `skipped_rule_count` (the live read's own rule). Per day: `scoreAsset(thatDay'sTagCounts, health).score` (called, never restated). Limit: R-i. `slopePerWeek = slope × 7`. The sentence shows score points (× 100).

### 4.6 Point drift (`degradation-drift.ts`, pure)

Input: the point's daily means and its covered rules (R-l). Direction is the slope's sign. **The limit (Q2 as recommended)** is, among covered rules **ahead** of the current value in that direction (`gt|gte` with `threshold > current` when rising; `lt|lte` with `threshold < current` when falling), the one nearest the current value; ties by rule name, then id. No rule ahead → not reported.

### 4.7 Schedule note

For an asset with at least one `crossing` indicator: its **nearest** indicator is the one with the smallest `min` (then the smallest `max`, `null` last, then health before drift, then point key). For each **active** schedule of the asset with `min < dueInDays` (R-t; **Q4 as recommended**), one note: `{ scheduleId, nextDueAt, sentence }`, ordered by due date. The asset-history section shows the first; the panel shows each on its own card.

### 4.8 Order and assembly

An asset is in the response when it has at least one reported indicator. Indicators inside an asset: `crossing` before `beyond_horizon`, then 4.7's order. Assets: those with a crossing first, by nearest `min`, then `max` (`null` last), then asset label, then id; assets with only `beyond_horizon` after them, by label. The control-room card takes the first 10 assets that have a crossing.

### 4.9 Sentences (`degradation-lines.ts`; exact strings; the range dash is the en dash U+2013)

`<range>` is `<min>–<max>` or `<min> to more than 90`. Numbers: at most 2 decimals, trailing zeros dropped; health as whole percent; a missing unit leaves no gap. A rule name longer than 120 characters is cut with `…`.

| Where | String |
|---|---|
| Health, summary | `Trending down: reaches <Band> in about <range> days` |
| Health, sentence | `At the trend of the last 28 days, the health score reaches <Band> in about <range> days.` |
| Health, beyond | summary `Trending down: no limit within 90 days`; sentence `At the trend of the last 28 days, the health score falls. No limit within 90 days.` |
| Health, detail | `Now <n>% (mean of the last 3 days). Limit <n>% (the lower edge of <Fair label>). Change: <±n.n> points a week.` |
| Drift, summary | `<pointKey> trending <up\|down>: reaches <limit> <unit> in about <range> days` |
| Drift, sentence | `At the trend of the last 28 days, <pointKey> reaches <limit> <unit> (rule "<name>") in about <range> days.` |
| Drift, beyond | summary `<pointKey> trending <up\|down>: no limit within 90 days`; sentence `At the trend of the last 28 days, <pointKey> moves toward <limit> <unit> (rule "<name>"). No limit within 90 days.` |
| Drift, detail | `Now <n> <unit> (mean of the last 3 days). Limit <n> <unit> (rule "<name>"). Change: <±n> <unit> a week.` |
| Schedule note | `Trend reaches its limit in about <range> days; next service due in <n> days.` (`1 day` for 1) |
| Assumptions, in this order | `Window: <d1> to <d28> (28 local days, today not included), <zone>.` · `Coverage: <n> of 28 days have a value; at least 21 are needed.` · health `Limit: <n>%, the lower edge of the <Fair label> band of this asset's template.` / drift `Limit: <n> <unit>, from the rule "<name>" in force today.` · **Q1 line** (as the ADR: `The tag weights and rules in force today are applied to past days.`) · `Method: Theil–Sen slope over daily values; Mann–Kendall test (p < 0.05) and a 90 % slope interval that does not include 0.` · `Days to the limit: from the mean of the last 3 days, at the two ends of the slope interval.` · health `Daily value: the health score from the day's in-range counts.` / drift `Daily value: the mean of the day's hourly values.` |

### 15.1 Before the build — read-only SQL as `bms_fleet`

Not executed in this session (2.3). Statement 2's `selftest` row guards the arithmetic: if it differs from the expected row, **stop and report; do not read the other rows**. A syntax error is fixed by the local session and reported. Statements 1 to 4 each start with the same head, printed once.

```sql
BEGIN TRANSACTION READ ONLY;
SET LOCAL statement_timeout = '120s';

-- HEAD
WITH real_assets AS (
  SELECT a.id AS asset_id, a.code, a.organization_id, a.domain, t.asset_type, t.content -> 'health' AS health,
         COALESCE((SELECT n.name FROM pg_timezone_names n WHERE n.name = l.timezone),
                  (SELECT n.name FROM pg_timezone_names n WHERE n.name = o.timezone), 'UTC') AS zone
    FROM bms.assets a
    JOIN bms.locations l ON l.id = a.location_id
    JOIN bms.organizations o ON o.id = a.organization_id
    LEFT JOIN bms.asset_templates t ON t.id = a.template_id
   WHERE a.active
     AND EXISTS (SELECT 1 FROM bms.asset_points ap LEFT JOIN bms.rtus r ON r.id = ap.rtu_id
                  WHERE ap.asset_id = a.id AND ap.active
                    AND (a.meta->>'telemetrySource' = 'mqtt' OR (ap.source_kind = 'measured' AND r.ingest_enabled)))
), win AS (
  SELECT ra.*, (now() AT TIME ZONE ra.zone)::date AS today FROM real_assets ra
), targets(domain, asset_type, point_key) AS (
  VALUES ('facility','cold_room','cold_room_temp_c'),
         ('electrical','energy_meter','kw'), ('electrical','energy_meter','kva'), ('electrical','energy_meter','kvar'),
         ('electrical','energy_meter','pf'), ('electrical','energy_meter','frequency_hz'),
         ('electrical','energy_meter','voltage_l1_v'), ('electrical','energy_meter','voltage_vry'),
         ('electrical','energy_meter','voltage_vyb'), ('electrical','energy_meter','voltage_vbr'),
         ('electrical','energy_meter','voltage_vrn'), ('electrical','energy_meter','voltage_vyn'),
         ('electrical','energy_meter','voltage_vbn'), ('electrical','energy_meter','current_ir'),
         ('electrical','energy_meter','current_iy'), ('electrical','energy_meter','current_ib'),
         ('electrical','pump_breaker','breaker_main'), ('electrical','chlorine_pump','chlorine_pump_on'),
         ('environment','rtu_health','battery_charge_pct'), ('environment','rtu_health','network_strength'),
         ('environment','rtu_health','controller_power_status')
), drift_points AS (
  SELECT DISTINCT w.asset_id, w.zone, w.today, ap.point_key
    FROM win w
    JOIN bms.assets a ON a.id = w.asset_id
    JOIN targets tg ON tg.domain = w.domain AND tg.asset_type = w.asset_type
    JOIN bms.asset_points ap ON ap.asset_id = w.asset_id AND ap.point_key = tg.point_key AND ap.active
    LEFT JOIN bms.rtus r ON r.id = ap.rtu_id
   WHERE (a.meta->>'telemetrySource' = 'mqtt' OR (ap.source_kind = 'measured' AND r.ingest_enabled))
     AND EXISTS (SELECT 1 FROM bms.automation_rules ru
                  WHERE ru.asset_id = ap.asset_id AND ru.point_key = ap.point_key
                    AND ru.organization_id = w.organization_id
                    AND ru.rule_type = 'threshold' AND ru.enabled AND ru.lifecycle_status = 'published'
                    AND ru.operator IN ('gt','gte','lt','lte') AND ru.threshold_value IS NOT NULL
                    AND ru.condition ->> 'window' = 'latest')
)

-- 1. Inventory: HEAD, then
SELECT w.code, w.zone,
       EXISTS (SELECT 1 FROM jsonb_array_elements(CASE WHEN jsonb_typeof(w.health -> 'bands') = 'array'
                                                       THEN w.health -> 'bands' ELSE '[]'::jsonb END) AS b(band)
                WHERE b.band ->> 'code' = 'fair') AS has_fair_band,
       hc.first_counter_day, COALESCE(hc.counter_days, 0) AS counter_days_in_window,
       (SELECT count(*) FROM drift_points d WHERE d.asset_id = w.asset_id) AS drift_points
  FROM win w
  LEFT JOIN LATERAL (
    SELECT min((c.bucket AT TIME ZONE w.zone)::date) AS first_counter_day,
           count(DISTINCT (c.bucket AT TIME ZONE w.zone)::date)
             FILTER (WHERE (c.bucket AT TIME ZONE w.zone)::date >= w.today - 28
                       AND (c.bucket AT TIME ZONE w.zone)::date <  w.today) AS counter_days
      FROM telemetry.point_in_range_1h c
     WHERE c.asset_id = w.asset_id AND c.rule_count > 0
  ) hc ON true
 ORDER BY w.code;

-- 2. The trends under the ruled rules: HEAD, then
, health_tag_day AS (
  SELECT w.asset_id, ((c.bucket AT TIME ZONE w.zone)::date - (w.today - 28)) AS x, c.point_key,
         sum(c.in_range_count)::float8 AS in_range, sum(c.sample_count)::float8 AS samples, max(c.rule_count) AS rules
    FROM win w
    JOIN telemetry.point_in_range_1h c ON c.asset_id = w.asset_id
   WHERE c.bucket >= now() - interval '30 days'
     AND (c.bucket AT TIME ZONE w.zone)::date >= w.today - 28
     AND (c.bucket AT TIME ZONE w.zone)::date <  w.today
   GROUP BY 1, 2, 3
), health_series AS (
  SELECT 'health'::text AS kind, d.asset_id, 'health'::text AS key, d.x,
         sum(COALESCE((w.health -> 'weights' ->> d.point_key)::float8, 1) * d.in_range / d.samples)
           / sum(COALESCE((w.health -> 'weights' ->> d.point_key)::float8, 1)) AS y
    FROM health_tag_day d JOIN win w ON w.asset_id = d.asset_id
   WHERE d.rules > 0 AND d.samples > 0
   GROUP BY d.asset_id, d.x
), drift_series AS (
  SELECT 'drift'::text AS kind, p.asset_id, p.point_key::text AS key,
         ((v.bucket AT TIME ZONE p.zone)::date - (p.today - 28)) AS x,
         (sum(v.sum_value) / NULLIF(sum(v.sample_count), 0))::float8 AS y
    FROM drift_points p
    JOIN telemetry.point_values_1h v ON v.asset_id = p.asset_id AND v.point_key = p.point_key
   WHERE v.bucket >= now() - interval '30 days'
     AND (v.bucket AT TIME ZONE p.zone)::date >= p.today - 28
     AND (v.bucket AT TIME ZONE p.zone)::date <  p.today
   GROUP BY p.asset_id, p.point_key, 4
), selftest AS (
  SELECT 'selftest'::text AS kind, '00000000-0000-0000-0000-000000000000'::uuid AS asset_id, 'v3'::text AS key,
         (t.ord - 1)::int AS x, t.y::float8 AS y
    FROM unnest(ARRAY[5,5,4,4,4,3,5,2,2,1,3,1]) WITH ORDINALITY AS t(y, ord)
), series AS (
  SELECT * FROM selftest UNION ALL SELECT * FROM health_series UNION ALL SELECT * FROM drift_series
), agg AS (
  SELECT kind, asset_id, key, count(*) AS n, avg(y) FILTER (WHERE x >= 25) AS recent
    FROM series WHERE y IS NOT NULL GROUP BY 1, 2, 3
), ties AS (
  SELECT kind, asset_id, key, sum(t * (t - 1) * (2 * t + 5)) AS tie_term
    FROM (SELECT kind, asset_id, key, y, count(*) AS t FROM series WHERE y IS NOT NULL GROUP BY 1, 2, 3, 4) g
   GROUP BY 1, 2, 3
), pairs AS (
  SELECT a.kind, a.asset_id, a.key, sum(sign(b.y - a.y)) AS s, count(*)::int AS pairs,
         array_agg((b.y - a.y) / (b.x - a.x) ORDER BY (b.y - a.y) / (b.x - a.x)) AS slopes
    FROM series a
    JOIN series b ON b.kind = a.kind AND b.asset_id = a.asset_id AND b.key = a.key AND b.x > a.x
   WHERE a.y IS NOT NULL AND b.y IS NOT NULL
   GROUP BY 1, 2, 3
), trend AS (
  SELECT g.kind, g.asset_id, g.key, g.n, g.recent, p.s, p.pairs, v.var_s,
         CASE WHEN v.var_s <= 0 OR p.s = 0 THEN 0 ELSE (p.s - sign(p.s)) / sqrt(v.var_s) END AS z,
         (p.slopes[(p.pairs + 1) / 2] + p.slopes[(p.pairs + 2) / 2]) / 2 AS slope,
         p.slopes[GREATEST(round((p.pairs - 1.6448536269514722 * sqrt(GREATEST(v.var_s, 0))) / 2)::int, 1)] AS low,
         p.slopes[LEAST(round((p.pairs + 1.6448536269514722 * sqrt(GREATEST(v.var_s, 0))) / 2)::int + 1, p.pairs)] AS high
    FROM agg g
    JOIN pairs p USING (kind, asset_id, key)
    JOIN ties t USING (kind, asset_id, key)
   CROSS JOIN LATERAL (SELECT ((g.n * (g.n - 1) * (2 * g.n + 5) - t.tie_term) / 18.0)::float8 AS var_s) v
)
SELECT t.kind, ra.code, t.key, t.n AS days, t.s, round(t.var_s::numeric, 4) AS var_s, round(t.z::numeric, 4) AS z,
       t.slope, t.low, t.high, t.recent AS current, lim.limit_value, lim.source,
       CASE WHEN lim.limit_value IS NOT NULL AND t.slope <> 0 THEN (lim.limit_value - t.recent) / t.slope END AS days_to_limit,
       CASE
         WHEN t.n < 21 THEN 'coverage'
         WHEN t.recent IS NULL THEN 'stale'
         WHEN NOT (abs(t.z) > 1.959963984540054 AND (t.low > 0 OR t.high < 0)) THEN 'no trend'
         WHEN t.kind = 'health' AND t.slope > 0 THEN 'improving'
         WHEN lim.limit_value IS NULL THEN 'no limit'
         WHEN t.kind = 'health' AND t.recent < lim.limit_value THEN 'already past'
         WHEN (lim.limit_value - t.recent) / t.slope < 1 THEN 'under 1 day'
         WHEN (lim.limit_value - t.recent) / t.slope > 90 THEN 'beyond 90 days'
         ELSE 'REPORT'
       END AS verdict
  FROM trend t
  LEFT JOIN real_assets ra ON ra.asset_id = t.asset_id
  LEFT JOIN LATERAL (
    SELECT (b.band ->> 'minScore')::float8 AS limit_value, 'band fair'::text AS source
      FROM jsonb_array_elements(CASE WHEN jsonb_typeof(ra.health -> 'bands') = 'array'
                                     THEN ra.health -> 'bands' ELSE '[]'::jsonb END) AS b(band)
     WHERE t.kind = 'health' AND b.band ->> 'code' = 'fair'
    UNION ALL
    (SELECT ru.threshold_value, 'rule'::text
       FROM bms.automation_rules ru
      WHERE t.kind = 'drift' AND ru.asset_id = t.asset_id AND ru.point_key = t.key
        AND ru.organization_id = ra.organization_id
        AND ru.rule_type = 'threshold' AND ru.enabled AND ru.lifecycle_status = 'published'
        AND ru.threshold_value IS NOT NULL AND ru.condition ->> 'window' = 'latest'
        AND ((t.slope > 0 AND ru.operator IN ('gt','gte') AND ru.threshold_value > t.recent)
          OR (t.slope < 0 AND ru.operator IN ('lt','lte') AND ru.threshold_value < t.recent))
      ORDER BY abs(ru.threshold_value - t.recent)
      LIMIT 1)
  ) lim ON true
 ORDER BY 1, verdict, 2, 3;

-- 3. The cost of the two daily reads at the host's real size: EXPLAIN (ANALYZE, BUFFERS) before HEAD, then
SELECT c.asset_id, c.point_key, (c.bucket AT TIME ZONE w.zone)::date AS day,
       sum(c.in_range_count), sum(c.sample_count), max(c.rule_count), max(c.skipped_rule_count)
  FROM win w JOIN telemetry.point_in_range_1h c ON c.asset_id = w.asset_id
 WHERE c.bucket >= now() - interval '29 days' AND c.bucket < now()
 GROUP BY 1, 2, 3;
-- and again with this tail
SELECT v.asset_id, v.point_key, (v.bucket AT TIME ZONE p.zone)::date AS day,
       sum(v.sum_value) / NULLIF(sum(v.sample_count), 0), sum(v.sample_count)
  FROM drift_points p JOIN telemetry.point_values_1h v ON v.asset_id = p.asset_id AND v.point_key = p.point_key
 WHERE v.bucket >= now() - interval '29 days' AND v.bucket < now()
 GROUP BY 1, 2, 3;

-- 4. Rules that changed inside the window (for Q1): HEAD, then
SELECT ra.code, count(*) AS rules,
       count(*) FILTER (WHERE ru.created_at >= now() - interval '28 days') AS created_in_window,
       count(*) FILTER (WHERE ru.updated_at >= now() - interval '28 days') AS updated_in_window,
       min(ru.created_at)::date AS first_rule_day
  FROM real_assets ra JOIN bms.automation_rules ru ON ru.asset_id = ra.asset_id
 WHERE ru.rule_type = 'threshold' AND ru.enabled AND ru.lifecycle_status = 'published'
 GROUP BY ra.code ORDER BY ra.code;

ROLLBACK;
```

   - (b) The limit is the warning rule (critical only when there is none); once passed, nothing shows. This needs a severity read, which the `E1.9` rule read does not have.
   **Recommended: (a).**
3. **"No limit within 90 days".** The rule table says a trend is reported only inside 1–90 days, and also that beyond 90 days it "reads" that sentence.

   - (b) Show it nowhere.
   **Recommended: (a).**
4. **Which end of the range the schedule note compares.** "Earliest crossing comes before the next due date."
