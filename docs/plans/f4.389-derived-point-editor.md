# F4.389 — plan: save a new derived point through the template editor

> **For agentic workers:** REQUIRED SUB-SKILL: use superpowers:executing-plans to work this plan task by task. Steps use checkbox (`- [ ]`) syntax. Small row, built serially; do not fan out.

Written 2026-11-19 against `origin/main` = `529cc4f`. Paths are relative to the repository root. **Status: plan only. Nothing is built before the owner's yes and the rulings in section 5.**

**Goal:** An author can add a new derived point to a template draft, give it a formula and a trigger, and save it, using only the UI.

**Scope gate:** row `F4.389` is ⬜, P2, effort 0.5–1, depends on `F2.5` (✅), not a ⭐ enabler. Web only: no route, Zod contract, schema, migration or package change, so no new ADR. Option (b) changes what ADR 0038 decision 2 says the Calculations tab writes; Q2 asks how to record that.

---

## 1. The defect, measured

- **Points tab** (`apps/web/src/components/asset-templates/points-tab.tsx`): the author adds a row and sets its kind to `derived`. Save runs `pointGridErrors` (`apps/web/src/lib/template-points-grid.ts`, the block near line 400), which refuses a derived row with an empty formula: *"A derived point needs a formula and a trigger. Set them on the Calculations tab, or change this point back to measured."* The guard is correct: the server refuses a derived point without a formula with a 400.
- **Calculations tab** (`apps/web/src/components/asset-templates/calculations-tab.tsx`): its `rows` state comes from `pointRowsFrom(template)` (line 82), that is, from the **stored** points. An unsaved Points-tab row never reaches it. With no stored derived point it shows *"This template has no derived points. Add a point on the Points tab and set its kind to derived, then set its formula here."* Its docblock (lines 19–22) gives the kind switch to the Points tab only, as ADR 0038 decision 2's table does.
- **Each tab owns its own form state.** `asset-template-detail-page.tsx` (line ~160) says so, and its tab-switch guard prompts to discard a dirty tab.
- **Result:** no UI path creates a derived point. The same dead end stops a change of a **saved** measured point to derived.
- **Workaround used for `F4.387`:** a direct `PATCH /admin/asset-templates/:id` with the full `points` list. `buildPointsPayload` already omits `meta` when it is `null`, so the UI path does not hit the `meta: {}` 400.

## 2. Options

| | What changes | For | Against |
|---|---|---|---|
| **(a)** Formula and trigger fields on the Points tab for a derived row with no formula | `points-tab.tsx` gets a formula field, grammar, trigger and interval for that row | One tab, one save | A second copy of the Calculations tab's controls (grammar, trigger, interval, staleness, coverage, preview, suggestions) or a reduced copy that cannot set them all. Puts the formula on the tab ADR 0038 decision 2 keeps it off. Widens an already wide grid. |
| **(b)** An **Add a derived point** control on the Calculations tab | `calculations-tab.tsx` appends a new derived row with a point-key select, label and unit; the existing formula editor and trigger controls then show for it; the existing Save sends it | Self-contained: one tab and a lib helper. Reuses `buildPointsPayload`, the point-key query, the formula editor and every existing check. Does not touch the page's tab-switch guard. | The Calculations tab can now add a point (it writes `pointKey`, `label`, `unit`, `sortOrder` for that row), so there are two places that add points. Changing a **saved** measured point to derived still takes two saves (remove it on Points, save; add it on Calculations). |
| **(c)** One unsaved point list shared by both tabs | Point rows move up to the page (or `template-tab-body.tsx`); both tabs read and write it; the page's tab guard lets Points ↔ Calculations switch without the discard prompt | Fixes both the new-point and the change-kind cases. The existing message becomes true as written. | The largest change. It touches the page, `template-tab-guard.ts`, both tabs, `template-tab-body.tsx` and the stock-view page, and the tab-switch guard has a record of defects (comments near lines 355–390 of the page). `useFollowStoredWhenClean` must move as well. More than the row's effort. |

## 3. Recommendation: option (b)

It is the smallest change that gives a working path, and it keeps one formula editor surface. The change-kind case keeps a two-save path that works, and the Points tab message will say how to do it. If the client later needs a one-step change of kind, option (c) becomes a separate row.

## 4. Out of scope

- Any API, contract, schema or migration change.
- One-step change of a saved measured point to derived (option (c)).
- Any change to the formula editor, the calc DSL or the KPIs tab.
- Any write on the demo host.

## 5. Owner rulings needed

- **Q1.** Which option? Recommended: (b).
- **Q2.** How to record that the Calculations tab can now add a derived point (ADR 0038 decision 2 and the tab docblock). Recommended: a short ADR 0038 amendment in the build PR, plus the docblock edit.
- **Q3.** The Points tab keeps `derived` in the kind select for a new row, and its message changes to name the new control. Recommended text: *"A derived point needs a formula and a trigger. To add one, use Add a derived point on the Calculations tab. To change a saved point to derived, remove it here and save, then add it there."* The alternative is to offer only `measured` on an unsaved row; the recommendation keeps the select as it is, because a hidden option is harder to explain than a clear message.
