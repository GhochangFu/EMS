## 1. Goal

Author the six mechanical/utility machine classes of `docs/e5.2-derived-taglist-v1.md` as six more `StockAssetTemplateEntry` values, in a new **mechanical pack**, so that every organization can import a pump set, a VFD, an air compressor, a chiller, an AHU or a boiler through the mechanism `F2.13` built and `E5.1` proved a second time. Four things land:

1. **A domain.** `bms.asset_domains` gains its sixth row — `mechanical` / `Mechanical` / `sort_order 60` — through a new seed module, `packages/db/src/asset-domains-seed.ts`, the **first** domain a pack has added since migration `0029` and the first use of the path ADR 0031 Amendment 1 A1.1 prescribed (*"declaring a value is an `INSERT` a domain pack ships in its own seed"*). The seed proves the row lands (`verifyHierarchySeed` counts six), and the API integration suite proves an import depends on it.
2. **A vocabulary.** Two arrays in `packages/shared/src/constants.ts` — `MECHANICAL_CLASS_POINT_KEYS` (**68** codes: pump, VFD, compressor, boiler) and `HVAC_CLASS_POINT_KEYS` (**39** codes: chiller, AHU) — **107** codes in all: the tag list's 94 new table codes (95 as spelled — §12 ruling 1 reuses the DG set's `fuel_level_pct` for the boiler's day tank) plus the **13 derived codes this plan promotes**. 107 `UNIT_BY_KEY` entries, two `keysForDomain(…)` lines appended last, two `ARRAY_DOMAIN` entries, and every guard bound moved to its new actual. `bms.point_keys` goes **291 → 398** on a cold start. The 21 tag-list codes that already exist are **referenced, never redeclared** (§4.2).
3. **Six entries.** `mechanical-pump`, `mechanical-vfd`, `mechanical-compressor`, `hvac-chiller`, `hvac-ahu`, `mechanical-boiler`, authored in **that order** (ADR 0053 decision 1 — document order), the first two entries anywhere filed under `hvac` and the first four under a domain that did not exist on `main` this morning. Each declares its section's table rows as template points (`C` → required + `meta.tier: "core"`, `X` → optional + `"extended"`, `M` → optional + `"manual"`), carries its alarm bullets as **pair-absent philosophy rows** with a populated `philosophy` (ADR 0053 decision 5), carries **maintenance plans** (decision 8, three `safetyCritical`), and carries **no `content.kpis`** (decision 6, the same structural reason as `E5.1` §5.0).
4. **Thirteen derived promotions.** Thirteen of the tag list's **30** named derived codes are expressible in `bms-calc-v1` over measured siblings inside their own entry — including the N4 chiller KPIs (`cooling_load_tr`, `kw_per_tr`, `cop`, plus the two ΔTs) — and are authored as `kind: "derived"` points with real formulas (13 point instances, no code authored twice). The other **17 are deferred and named**, never placeholdered (§5.0).

When this lands, the 2026-08-22 sheet's row 4 (chillers, compressors, HVAC) has product behind it, form ref N4's chiller KPIs exist as reviewable derived points, and the N5 health signal (*kW/TR high vs baseline*) is a pair-absent alarm bound to a computed point — the surface ADR 0050 reads, authored here and built nowhere in this row.

## 3. Serial or parallel, and the model per pass

**Serial, one branch, five consecutive `implementer` passes. Do not fan out.**

Six machines *look* like six independent siblings and are not, for the reason `E5.1` §3 gave and one more. Every entry writes the same shared files — `stock-catalog/mechanical.ts` (the pack index), `stock-catalog-deferrals.spec.ts` (`STOCK_ENTRY_CODES`, `DEFERRED_DERIVED_CODES`), `tests/f2.13-asset-stock-catalog-vocabulary.test.ts` (`STOCK_ASSET_RELS`, one number per file), `packages/shared/src/constants.ts` and `packages/db/src/point-keys-seed.ts`. And this pack has a **hard ordering dependency the water pack did not**: `AssetTemplatesAdminService.create` calls `vocabularies.assertAssetDomain(body.domain)` (`asset-templates.service.ts:185`) against the live table, so a `mechanical-*` entry cannot be imported — and the integration suite cannot prove it — until the seed row of Task 3 has landed. Six worktrees would produce six conflicting appends, and four of them would be unimportable on their own branch.

**`E5.2` is not a ⭐ enabler and defines no seam in `apps/api`.** `F2.13` froze `StockAssetTemplateEntry`, the DI token and the two routes; `F2.12` froze the per-class split and `checkEntry`; `E5.1` froze the prefix map and the per-entry deferral record. What this row *does* do that later packs hang off is **the domain seed path** (Task 3) — the first `bms.asset_domains` `INSERT` outside a migration, which `E5.3` copies for `facility` — and that is the one unit routed up the ladder.

### 4.4 The 107 codes and their `UNIT_BY_KEY` values

Two arrays, both appended after `WATER_CLASS_POINT_KEYS`; **`MECHANICAL_CLASS_POINT_KEYS` first** (it holds §1, the document's first section) then `HVAC_CLASS_POINT_KEYS`; inside each array the sections run in document order and each section's promoted derived codes are appended at its end — `F2.11` §4.1's shape. **First occurrence wins**, and there is no cross-array recurrence to resolve (§4.1). `""` — never a missing entry — for every `0/1`, `enum` and `code` row and for the two dimensionless ratios (ADR 0051 Amendment 6 decision 4). ### 5.0 The derived-code rule, the thirteen promotions and the seventeen deferrals

**The rule is `E5.1` §5.0's, unchanged, and both halves still hold**: (a) a derived template point is `bms-calc-v1` over **measured** points the same entry declares — never another derived point, never another asset's — and its code must be promoted into the vocabulary because `assertPointKeysActive` checks it; (b) `content.kpis` buys nothing (`checkEntry` refuses `unvalidated`; `collectContentPointRefs` walks a KPI's keys regardless of dialect). **So this pack authors no `content.kpis`** (ADR 0053 decision 6): every expressible ratio the document names is a named code an alarm can bind (two do: `kw_per_tr_high`, `sat_deviation_high`), and every other named code is deferred.

**Four consequences of the formulas that go in the module docblocks, not discovered later:**

- **Division by zero is handled and must not be guarded.** `evaluate.ts` returns `non_finite`, so `specific_energy_kwh_kl` at zero flow, `load_factor_pct` at zero run hours, `specific_power_kw_m3min` at zero FAD, `kw_per_tr` and `cop` at zero ΔT or zero kW (a chiller that is off), `steam_to_fuel_ratio` at zero fuel and `excess_air_pct` at 20.9 % O₂ all produce **no value for that reading**. No `clamp`, no `max(…, 0.001)` — a fabricated denominator turns "no data" into a plausible number.
- **No `maxInputAgeSeconds` override in this pack.** Every formula's inputs arrive from the same controller or the same plant-room instrument set at the same scan rate — `E5.1`'s `approach_c` override was for a weather-station input. `cooling_kw` may come from a separate power meter, but a power meter and a BTU meter both report in seconds to a minute, inside the 300 s default. The entry specs assert `null` on all thirteen, so a "helpful" override is a test failure with a reason.
- **Six formulas reference an `X`-tier optional point** (`head_m`, `specific_energy_kwh_kl`, `specific_power_kw_m3min`, `coil_delta_t_c`, `steam_to_fuel_ratio`, `excess_air_pct`). Legal — the reference check requires *declared*, not required — and it means a site that does not fit the instrument gets no value. Do not promote the input to `C`.
- **Two physical constants and one atmospheric constant are the document's, not the plan's.** `10.2` m/bar, `4.19` and `3.517` are written in the tag list's own *Derived:* lines; `20.9` is the volume fraction of oxygen in air, the textbook simplified excess-air relation (dry basis). None is a site value and none is a limit — B7 governs alarm thresholds, not physics.

## 12. Open questions — all seven ruled by the owner, 2026-09-03, before the first line of Task 1

Asked one at a time (`AskUserQuestion`, one call per question, options plus the recommendation). Each is what ADR 0053 did **not** settle. The first three change the vocabulary, which is write-once. **Every ruling took the recommendation**; ruling 1's count changes are folded into §§1, 4, 5.6, 6, 8, 9 and 11 above, and this section is the record.

1. **Reuse `fuel_level_pct` for the boiler's day-tank level, or mint `fuel_tank_level_pct` as the tag list spells it?** The DG set already seeds `fuel_level_pct` (*fuel level, day tank*); the boiler's row is *Day-tank / bunker level*. ADR 0051 Amendment 6 decision 5 (one code, one meaning) and the tag list's own note (*"existing keys are reused, not renamed"*) both point at reuse; the ADR counted 95 new codes with the document's spelling. **Recommendation: reuse `fuel_level_pct`** and correct the tag list at closure (the `pct_recovery` precedent). Every count in §4.6 drops by one. **Ruled: reuse `fuel_level_pct`.** The boiler's row 13 binds the DG set's code; `MECHANICAL_CLASS_POINT_KEYS` is 68, the arrays hold 107, `bms.point_keys` reaches 398, and the `f2.13` distinct bound is 382.
2. **Unit spellings for the five promoted derived codes whose unit the document does not write:** `head_m` → `m`, `specific_energy_kwh_kl` → `kWh/KL`, `specific_power_kw_m3min` → `kW/(m³/min)`, `cooling_load_tr` → `TR`, `kw_per_tr` → `kW/TR`; `cop` and `steam_to_fuel_ratio` → `""`. **Recommendation: as listed** — `KL` follows `KL/hr`, `TR` is the document's own abbreviation, the parenthesised form is the one that is not ambiguous. **Ruled: as listed.**
3. **Boiler promotions at the margin: promote `excess_air_pct` (the textbook O₂ relation with the 20.9 constant), and defer `specific_fuel_kg_ton_steam` as the reciprocal of `steam_to_fuel_ratio`?** The document names `excess_air_pct` *"from O₂"* without a formula; the relation is universal, not a site value. `specific_fuel_kg_ton_steam` is the IBR log-sheet figure and would be a second code for the same information. **Recommendation: promote `excess_air_pct`, defer `specific_fuel_kg_ton_steam`** (13 promoted / 17 deferred as planned). Ruling both the other way gives 12 / 18 and 13 / 17 respectively. **Ruled: promote `excess_air_pct`, defer `specific_fuel_kg_ton_steam` — 13 / 17.**
4. **Keep `coil_delta_t_c` (AHU) as a separate code from `chw_delta_t_c` (chiller)?** Same formula string over the same two vocabulary codes; the document names them differently because one is the plant loop and one is a coil. **Recommendation: keep both as the document names them** — the handout is what the client redlines, and a merge is a one-line redline; a plan-side merge silently edits the handout. **Ruled: keep both.**
5. **Maintenance plan counts — 4 / 3 / 4 / 4 / 4 / 5 with the three `safetyCritical` plans ADR 0053 decision 8 names?** The boiler's annual IBR inspection is authored `compliance`, not `safety_critical`, so the count of critical plans stays three. **Recommendation: as §5.7** — decision 8 named three, and a statutory inspection is a compliance item with its own reference. **Ruled: as §5.7 — 24 plans, three `safetyCritical`.**
6. **Alarm categories for the comfort rows: `comfort` for `sat_deviation_high`, `return_rh_high`, `co2_high`, and `operations` for `chw_leaving_temp_high`?** `comfort` is one of `0029`'s four concerns and has never been used by a stock entry. **Recommendation: as §5.5** — the AHU serves occupants; a chiller serves a loop whose load is unknown. **Ruled: as §5.5 — `comfort` on the three AHU rows, `operations` on the chiller's.**
7. **`hvac` as the skill on `fire_trip`?** The fire system, not a trade, answers the event; the AHU is restarted by HVAC after the all-clear. The alternative is no skill, which would widen the "process-chemistry" no-skill class to a life-safety row. **Recommendation: `hvac`**, with the action text saying *do not restart until the fire system resets*. **Ruled: `hvac`.**
