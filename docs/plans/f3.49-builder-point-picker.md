# F3.49 — the rule builder's point picker offers what `assertCompatiblePoint` accepts

Branch `F3.49-builder-point-picker`, cut from `origin/main` at `4be4f153`.
Gated by **ADR 0058 Amendment 2** (owner ruling, 2026-09-10).

## 1. Goal

`GET /api/v1/rules/catalog` returns, per asset, the **union** of
`pointKeysForAsset`'s hard-coded map and the point keys the asset's pinned
template declares — the set `assertCompatiblePoint` has accepted since `E2.4`
Q1. Both sides call **one** function in `apps/api/src/rules/rule-points.ts`, so
the docblock at `rule-points.ts:17-19` (*"Both must agree, which is why it is one
function rather than two lists"*) becomes true again. The acceptance set does not
move: nothing savable becomes unsavable, and nothing unsavable becomes savable.

**Out of scope, by the owner's rulings of 2026-09-10:**

- Offering `asset_points` rows, alone or in a three-way union.
  `AssetPointsAdminService.create` gates on the fleet catalog only, so an
  `asset_points` key can be one the PATCH refuses with 400, and a `derived` point
  has no row at all.
- Any change to what `POST`/`PATCH /rules` accepts.
- Any contract change. `ruleBuilderCatalogAssetSchema.pointKeys` is already
  `z.array(z.string())`; no field is added, so no `z.intersection`/`.readonly()`
  question arises. A plan that adds a contract field here adds a field nobody
  reads.
- Any web change. `rule-builder-panel.tsx:144` reads
  `selectedAsset?.pointKeys ?? []` and `:315` maps it into `<option>`s with no
  client-side filter. Held by an existing gate rather than claimed:
  `rule-builder-panel.spec.tsx:31` feeds `pointKeys: ["supply_temp_c"]` — a key
  in none of the six constants — and `:183` selects it, so a client-side list
  would already fail that spec.
- The seed, migrations, `apps/ingest`, `apps/sim`.
- Marking or filtering a picker key the asset has no `asset_points` row for.
  Accepted in ADR 0058 Amendment 2, with a backlog row owed against the seed.

## 2. Decisions

### D1. The shared helper — signature and home

Both go in `apps/api/src/rules/rule-points.ts`:

```ts
/** Map order first, then template-only keys in template order; a key in both appears once, at its map position. */
export function mergeRulePointKeys(domain: string, code: string, templateKeys: readonly string[]): string[]

/** The point keys a rule may target, per asset id — the hard-coded map ∪ the pinned template's keys. Every input asset gets an entry. */
export async function ruleTargetPointKeysByAsset(
  fleetDb: BmsDb,
  assetRows: ReadonlyArray<{ id: string; code: string; domain: string }>,
): Promise<Map<string, string[]>>
```

`ruleTargetPointKeysByAsset`:

1. `if (assetRows.length === 0) return new Map();` — drizzle-orm 0.38.4 renders
   `inArray(col, [])` as `sql\`false\``, so this is a saved round-trip, not a
   crash guard. Say that in the comment so nobody removes it as "defensive".
2. **One** query:
   `select({ assetId: assets.id, pointKey: templatePoints.pointKey }).from(templatePoints).innerJoin(assets, eq(assets.templateId, templatePoints.templateId)).where(inArray(assets.id, ids)).orderBy(asc(templatePoints.sortOrder), asc(templatePoints.pointKey))`.
3. Seed the `Map` from the input rows (`id → []`), then push each query row into
   its entry — **ignoring** a row whose `assetId` is not an input id. That is the
   honest semantics (only input assets are answered) and it is what keeps
   `rules.service.spec.ts`'s HVAC cases green, whose fake answers every select
   with `[{ code, domain }]` rows carrying no `assetId`.
4. Replace each entry with `mergeRulePointKeys(row.domain, row.code, entry)`.

The four reasoning paragraphs of `templatePointKeysForAsset`'s docblock
(`rule-points.ts:60-76`: no `kind` filter; `innerJoin` with no null guard;
`fleetDb` because `template_points` is under FORCE RLS; the caller's scope check
is the isolation control) **move** onto this helper verbatim. The fifth paragraph
(`:78-79`, "Called only when the hard-coded lookup misses") is deleted — see D2.
`templatePointKeysForAsset` itself is deleted; its only callers are the two lines
in `rules.service.ts`.

**`template_id = NULL`:** the inner join yields no rows, the seeded entry stays
`[]`, and the union is exactly today's hard-coded list. The `rule-points.ts:67-69`
argument already says why that is the honest answer.

**`assertCompatiblePoint`** moves to `rule-points.ts` (Task 1), and after Task 2
its body is: the existing asset lookup (keeping the "Selected asset does not
exist" 400), then
`(await ruleTargetPointKeysByAsset(fleetDb, [{ id: assetId, ...asset }])).get(assetId) ?? []`,
then the existing refusal. `rule-points.ts` needs `BadRequestException` from
`@nestjs/common`, which `rule-codes.ts:1` and `rule-arming.ts:1` already import
in this module.

### D2. The laziness is dropped, consciously

Today `assertCompatiblePoint` queries `template_points` only on a map miss. After
this row every validation (`createDraft`, `updateRule`, `previewRule`,
`publishRule` — all through `validateRuleDraft`) runs one indexed query
(`assets` PK → `template_points (template_id, point_key)` unique index). Why drop
it: the ruling is one function, and a map-first short-circuit is a second code
path — the row exists because there were two. `getBuilderCatalog` cannot be lazy
at all, so keeping laziness means the validator and the picker read the map in
two places, which is the divergence Task 4's gate forbids. The cost is bounded:
these are human-paced write paths; the evaluation sweep and `AlarmEngineService`
never call it.

### D3. Order and dedupe are pinned

Map order first, so every existing `same(...)` assertion in `rule-points.spec.ts`
stays true byte-for-byte and a template-less asset's list is unchanged. Then
template-only keys ordered by `(template_points.sort_order, point_key)`.
`sort_order` because it is the author's declared order; `point_key` as the
tie-break because the health seed writes `sort_order = 0` on every row it
creates, so without it those keys get heap order that differs per database — a
picker order a browser check passes on one machine and fails on another. A key in
both sets appears once, at its map position. Dedupe inside the template side
needs no code: `(template_id, point_key)` is unique and an asset has one
template.

### D4. `rules.service.ts` — extract first, in its own commit

`rules.service.ts` is 990 lines; AGENTS.md §2 says *"extract before adding to
it"*. The feature's net delta could be kept to +1 (992), but the instruction is
explicit and the extraction is the cheap one: `assertCompatiblePoint`
(`:930-948`) has one caller (`:903`) and its only service dependency is
`this.fleetDb` — the `F3.56` `readiness()` shape. Moving it (20 lines with the
trailing blank) leaves the service at **970**, and the feature's +1 to
`getBuilderCatalog` lands at **972** — this said 971 when the plan was written;
the constructor comment took a line as well. It also puts the validator and the picker's
source in one file, which is what makes Task 4's scan a one-file claim.

### D5. `getBuilderCatalog` — one bounded `inArray`, derived from `rows`

After `rows` resolves (`rules.service.ts:132-136`):
`const pointKeys = await ruleTargetPointKeysByAsset(this.fleetDb, rows);` and
`:146` becomes `pointKeys: pointKeys.get(row.id) ?? []`. The id list comes from
`rows`, so the unfiltered branch (`assetIds == null`) and the filtered one share
one template query and cannot drift from the asset filter. The `?? []` is dead by
the helper's contract; Task 2's fold test is what makes it dead rather than a
hiding place.

**Rows 14–16 were added after review, and their absence was the defect.** The
table shipped with no mutation against the `ORDER BY` at all, so ADR 0058
Amendment 2 property 2 was decided prose with nothing behind it — the unit fakes
ignore every argument they are handed, and the fixture's three points carry
distinct `sort_order`s in insertion order, so a sequential scan returned them
sorted by accident and the `point_key` leg never executed. Both the correctness
and the compliance review found this independently.

**The first repair for the tie-break was itself dead, and running it is what
showed that.** Task 3 case 3 originally tied two fixture points at
`sort_order = 5` and deleted-and-re-inserted the alphabetically earlier one so
it was physically last, expecting the tie-break to be the only thing that could
restore the asserted order. Mutation 15 was then run and the case **stayed
green**: Postgres does not specify the order of rows tying on every `ORDER BY`
key, so removing the leg produces an arbitrary order rather than a different
one, and it coincided. No behavioural test can hold that leg. It moved to a
source assertion (Task 4 `it` 5), which mutation 15 does redden, and the case
kept only the `sort_order` leg it can genuinely hold.
