## 1. Goal, and what is out of scope

**Goal.** The four `content.alarms[].philosophy` fields — `cause`, `impact`,
`action`, `skill` — become readable by the people the alarms are for, on two
surfaces that fail in opposite conditions:

- **Surface 1 (PR 1).** `GET /api/v1/alarms/:id/details` returns a nullable
  `classPhilosophy` block, and `alarm-details-panel.tsx` renders it beside the
  instance enrichment. Resolved by exact provenance —
  `automation_rules.source_template_id` plus `source_alarm_code`, the link
  `E2.4` built in migration `0067`.
- **Surface 2 (PR 2).** A browsable knowledge base listing the current published
  version per asset class, readable by anyone who can see alarms, `viewer`
  included, scoped to the caller's organization.

Today neither exists. The only path from a philosophy row to a human is
`philosophyDescription()`
(`apps/api/src/admin/asset-templates/template-alarm-rules.ts:187`), which
flattens the four fields into prose on a seeded rule's `description` and clamps
it at 2000 characters; and the template authoring screen's Alarms tab (ADR 0038),
which is gated to the master-data roles, so the operator and the technician
cannot open it.

**Explicitly out of scope.**

- **No table and no migration.** A KB with its own table is a second copy of
  `content.alarms[].philosophy` that drifts the moment an author edits one
  (ADR 0059 decision 1).
- **No copy-to-enrichment button, and no prefill** (ruling Q1, decision 5).
- **No editing from either surface.** Authoring stays in the template screen's
  Alarms tab. Both surfaces here are reads (decision 11).
- **The three instance-only enrichment fields** — affected assets,
  energy/water/production impact, ETR. ADR 0034 puts them off the template
  contract permanently. Do not add them.
- **No cross-surface version diff.** A class whose alarm entry was dropped in a
  later version shows on the panel and not in the KB, and decision 4 states that
  this is correct. A version diff is `E2.4`'s drift job.
- **No change to `philosophyDescription()`** or to how `E2.4` seeds, re-applies
  or reports drift (decisions 10 and 11).

### Decisions this plan makes (beyond ADR 0059)

1. **PR 1's read stays inside `AlarmDetailsService.get`**, as one more `leftJoin`
   on the existing query plus a jsonb pick, not a second round trip. That method
   already composes five tables and one follow-up query; a sixth join is cheaper
   than a second call and keeps the `null` case free.
2. **The `content.alarms[]` entry is selected in SQL, not in TypeScript.** A
   `jsonb_path_query_first` (or a lateral `jsonb_array_elements` filtered on
   `code`) returns one object; pulling the whole `content` blob into Node to find
   one entry would ship a 256 KiB column per alarm read.
3. **PR 2 gets its own module**, `apps/api/src/alarm-kb/`, rather than more
   methods on `AlarmsModule` or on the admin template service. It is a read over
   template content for an operations audience — it belongs to neither existing
   owner, and ADR 0034 set the precedent by giving `AlarmDetailsService` its own
   file for the same reason.
4. **Both reads run on `FLEET_DRIZZLE`** and therefore carry a hand-written
   organization predicate (ADR 0059 decision 9). `bms_fleet` is `BYPASSRLS`; RLS
   gives these reads nothing.
5. **The KB route is `/alarm-kb`**, in the operations shell beside `/alarms`, not
   under `/admin`. It uses the ordinary authenticated route wrapper, **not**
   `AdminRoute` — ruling Q0b puts `viewer` inside.

## 3. Build order

Four units, two pull requests. Units A and B are PR 1; C and D are PR 2. Each
unit is TDD — the spec lands red before the implementation.

### Unit A — `classPhilosophy` on the alarm details read (PR 1)

**Files.**
- `packages/shared/src/contracts/operations.ts` — extend
  `alarmDetailsResponseSchema` (currently at line 502).
- `packages/shared/src/index.ts` — no new export needed;
  `AlarmDetailsResponse` already re-exports from the schema.
- `apps/api/src/alarms/alarm-details.service.ts` — the join and the mapping.
- `apps/api/src/alarms/alarm-details.service.spec.ts` — new unit spec, or extend
  the existing `alarm-enrichment.integration.spec.ts` harness.

**Tests first.**
1. `assertDetailsReturnsClassPhilosophyForASeededRule` — a rule with
   `source_template_id` + `source_alarm_code` pointing at a template whose
   `content.alarms[]` carries a matching `code` returns all four fields plus the
   resolved skill label, the template id, version and name.
2. `assertDetailsOmitsClassPhilosophyWhenProvenanceIsNull` — the 290-row case.
   `classPhilosophy` is `null`, and the rest of the response is byte-identical to
   today's.
3. `assertDetailsOmitsClassPhilosophyWhenTheAlarmCodeIsAbsentFromContent` — the
   entry was dropped in the version the rule pins. `null`, not a throw.
4. `assertDetailsRefusesATemplateFromAnotherOrganization` — decision 9. A rule
   whose `source_template_id` belongs to another tenant yields `null`, and the
   predicate is what makes it so. **This test must fail if the `eq` on
   `organizationId` is deleted** — write it as a mutation check, not a happy path.
5. `assertDetailsResolvesAnInactiveSkillLabel` — decision 7; retirement is
   `active = false` and a historic philosophy stays readable.

**Then the implementation.** One `leftJoin` to `asset_templates` on
`automationRules.sourceTemplateId` **and** the organization predicate, plus a
SQL-side pick of the `content.alarms[]` element whose `code` equals
`automationRules.sourceAlarmCode`, plus a `leftJoin` to `alarmSkills` for the
label.

### Unit B — the panel renders it (PR 1)

**Files.**
- `apps/web/src/components/alarm-details-panel.tsx`
- `apps/web/src/components/alarm-details-panel.spec.tsx` — new; the blast radius
  says this component has **no covering tests** today, so this unit adds the
  first ones.

**Tests first.**
1. The class block renders its four labelled fields, and the heading names the
   template and version it came from (decision 6).
2. The class block is absent, with no empty heading and no layout hole, when
   `classPhilosophy` is `null` — the 100% case on today's data.
3. The class block and the enrichment block are **distinguishable**: the class
   heading says class-level, and the enrichment form is unchanged. This is
   decision 5's labelling requirement, and it is the one a reviewer will call a
   bug if it is missing.
4. A `viewer` sees the class block. It is a read, and `readOnly` hides only the
   enrichment write form.
5. **No control writes the class text into the enrichment form** (ruling Q1).
   Assert the absence of a copy affordance, so a later well-meaning addition
   fails this test rather than sliding in.

## 4. Blast radius — what this change forces you to update

- **`alarmDetailsResponseSchema`** has exactly one consumer today,
  `apps/web/src/api/alarms.ts`. Adding a nullable field is additive, so no
  existing caller breaks — but the schema is `z.infer`red, so the web type moves
  the moment the contract does, and `pnpm typecheck` is the gate that proves it.
- **`AlarmDetailsService.get`** has 10 callers through
  `alarms.controller.ts` / `alarms.module.ts`, and its covering suite is
  `alarm-enrichment.integration.spec.ts`. Every existing assertion in that file
  must still pass unchanged — the new field is additive.
- **`alarm-details-panel.tsx`** has **no covering tests**. Unit B writes the
  first ones; do not treat the absence as permission to skip them.
- **`app.module.ts`** gains one module in PR 2. `fleet-read-wiring.spec.ts`
  asserts which services take `FLEET_DRIZZLE` — **the new service must be added
  to that list**, or the spec will either fail or, worse, silently not cover it.
- **Nothing in `packages/db`.** No schema file changes, no migration, no seed.

## 7. Step 6 verification, per layer

**The fixture is the gate, and it is not optional.** With 0 of 290 rules carrying
provenance, a suite that passes on the seed proves nothing about PR 1.

**What this gate became, and why it is stronger than the three steps originally
written here.** The first draft of this section asked the fixture to publish a
template, instantiate it, and raise an alarm through the rule engine. The risk
it was guarding is narrower than that ceremony: if
`AssetTemplateInstantiationService` stamped a value the read's join does not
match — a cased code, a prefixed one, one run through `seededRuleCode` — a
hand-stamped fixture would stay green while the panel showed nothing.

So the fixture does not hand-stamp. **`insertTestAlarmSeededFromTemplate` builds
its `automation_rules` row by calling `seededRuleValues`** — the production
function `instantiate` itself calls, at
`apps/api/src/admin/asset-templates/template-alarm-rules.ts:273`. Whatever
instantiation stamps, the test stamps, and a change there breaks this suite.

**Mutation-checked, not asserted.** Changing that function's
`sourceAlarmCode: alarm.code` to `` `${alarm.code}_MUTATED` `` fails two
assertions — the happy path and the retired-skill case — and reverting restores
22 of 22. The coupling is live.

**What this gate still does not cover, stated rather than implied:**

- **The HTTP instantiate path.** `instantiate` also authorizes, resolves a
  target, re-validates the catalog and the alarm vocabularies. None of that
  affects the three provenance columns, but none of it is exercised here either.
- **Raising through the rule engine.** The fixture inserts `bms.alarms` with a
  real `rule_id`. The engine's own raise path is covered by `F3.6`'s and
  `F3.7`'s suites and is not specific to `E2.2`.
- **The browser layer** (below) — owed, and not yet run.

| Layer | PR 1 | PR 2 |
|---|---|---|
| **DB** | `psql` on 5433: confirm the seeded rule carries all three provenance columns, and that the pinned template version's `content` holds the matching `code`. | Confirm the 26/21/170 counts still hold at build time; they move as templates are published. |
| **Contract** | `pnpm typecheck` — the web type follows the schema. | Same, plus the shared philosophy object is reused, not restated. |
| **API** | Integration spec against the fixture: the block resolves. Plus the four `null` cases. | Integration spec: version selection, org scoping, `viewer` access. |
| **HTTP** | `curl` cannot get a token locally — the API is OIDC with no password grant. Send the HTTP assertion to `browser-verifier` as a `fetch` from the signed-in SPA tab. | Same. |
| **Web** | jsdom spec (Unit B) covers render, absence, labelling and the no-copy rule. | jsdom spec (Unit D) covers grouping, search, empty state, `viewer`. |
| **Browser** | Only what the cheaper layers cannot hold: that the panel shows the block for the fixture alarm on the running stack. Assert with `javascript_tool` and an exact string match; **do not screenshot to find where to click.** Say which layers were skipped and why. | Same, plus that `/alarm-kb` routes for a `viewer` sign-in. **Signing in needs the human** — ask per identity before dispatching. |

Other sessions redeploy the shared stack. **Pin image ids in every
`browser-verifier` dispatch**, and re-check the container's Created time against
the commit before trusting a live response.

## 9. Serial or parallel

**Serial, and PR 1 first.** Unit C reuses the contract object Unit A introduces,
so building PR 2 first would either duplicate the schema or block on a file PR 1
owns. Within PR 1, Unit B needs Unit A's contract; within PR 2, Unit D needs
Unit C's endpoint.

**Do not fan these out to parallel agents.** Four units, two of them touching
`packages/shared/src/contracts/operations.ts`, is exactly the shape §1b calls
unsafe in parallel — same file, different units.

`E2.2` is safe in parallel with the **other session's** `F4.103`–`F4.107`, which
are onboarding-upload rows: they touch
`apps/api/src/admin/onboarding/`, `apps/web/src/api/admin/onboarding.ts` and
`apps/web/src/lib/telemetry-import-preview.ts`, and share no file with any unit
here. The shared risks are the checkout, Postgres on 5433 and the `:4000`/`:5173`
containers — hence the worktree, and hence §7's pinned image ids.
