## 1. Goal

ADR 0091 ruled two PRs. **PR 1 (decision 1, this plan's executable part)** gives template create, publish and instantiate a *transaction-aware core*: a function that takes the caller's `tx`, the actor and the body, and does every guard read — the template row and its points, the target RTU and location, the point-key catalog, the asset-code and rule-code checks — through that `tx`, so a row written earlier in the **same uncommitted transaction** is visible to the guard. The cores live in new files (the two service files stand at 940 and 996 lines against §4.5's 1,000-line cap); `AssetTemplatesAdminService.create`/`publish` and `AssetTemplateInstantiationService.instantiate` become thin wrappers that open `withTenant` and call the core; a public `*InTransaction(tx, …)` method on each service is the door PR 2's commit will use. **Zero behavior change:** routes, bodies, responses, audit rows, error texts and their precedence are byte-identical, and the existing template-domain integration suites (17 `*.integration.test.ts` pairs under `apps/api/src/admin/asset-templates/`) pass unchanged — that is the gate. **PR 2 (decisions 2–12)** adds `templates[]` and `assets[].template` to the draft, the seven tools, the one-transaction commit through the cores, the access rule, the proposal text, the bounds, the web preview and the live verification; it is outlined in §9.

**Out of scope for PR 1:** any change to the onboarding module, the draft schema, the shared contracts, the web, `packages/db`, `AGENTS.md` (§9.10 — a `chore(agents):` sweep after PR 2), the backlog row (stays 🟡 until PR 2 closes), `update`/`archive`/`createDraftFrom`/`deleteDraft`/`migrate` (they keep their `fleetDb` reads; only create, publish and instantiate gain cores), and the decision-5 access option on the instantiate core (PR 2 adds it; PR 1 keeps `canManageLocation` as today).

- **RLS facts that decide which reads can move** (verified in `packages/db/drizzle`): `point_keys` has **no** RLS since `0057` (`DISABLE ROW LEVEL SECURITY`), so a `tx` read sees every key and the tenant role may `INSERT`/`UPDATE` it (grants `0039:49`). `asset_templates`, `template_points`, `locations`, `rtus`, `assets`, `automation_rules`, `rtu_connection_configs` are `FORCE` tenant tables keyed on `organization_id`: under `withTenant(org)` a `tx` read sees that organization's rows **only** — including uncommitted ones — and never another organization's. `organizations` carries no policy and is readable on `tx` (`onboarding-commit.service.ts:541`). Consequence: two instantiate guards *cannot* be tx-only without a text change — see §11 Q1 and U4.
- **Integration fixtures that must roll back.** Every "same uncommitted transaction" claim runs inside one `withTenant(tenantDb, org, async (tx) => { …; throw new RollbackSentinel(captured) })` and asserts on the captured values outside. A callback that returns **commits** (memory: `withRollback` cases must throw). Independent reads inside the claim go through the same `tx` (a pool read cannot see uncommitted rows); cleanup of the committed fixtures (templates, point keys) runs on the owner pool before and after, as `asset-templates.instantiate.integration.spec.ts:112` does.

### The wrappers, exactly

```ts
async create(jwt, body, stamp?) {
  const created = await withTenant(this.tenantDb, body.organizationId, (tx) => this.createInTransaction(tx, jwt, body, stamp))
    .catch((err: unknown) => { throw translateDraftConflict(err, body.code); });
  return this.getById(jwt, created.id);
}
async publish(jwt, id) {
  const { template } = await this.fetchRow(id);                 // fleetDb; the organization for withTenant; the same 404 first, as today
  await withTenant(this.tenantDb, template.organizationId, (tx) => this.publishInTransaction(tx, jwt, id));
  return this.getById(jwt, id);
}
async instantiate(jwt, templateId, body) {
  await this.accessControl.requireMasterDataUser(jwt);         // today's first statement; keeps 403-before-404 for a non-master-data caller with a bad id
  const organizationId = await this.templateOrganization(templateId); // fleetDb select({ organizationId }) … limit(1); 404 "Asset template not found"
  return withTenant(this.tenantDb, organizationId, (tx) => this.instantiateInTransaction(tx, jwt, templateId, body))
    .catch((err: unknown) => { throw translateAssetCodeCollision(err); });
}
```

The guards that used to run before `withTenant` now run inside it. That is observable nowhere: `translateDraftConflict` rewrites only `constraint === "asset_templates_org_code_draft_unique"` and `translateAssetCodeCollision` only `assets_code_unique` / `automation_rules_org_code_idx`; every other error passes through unchanged, and a refused guard rolls back a transaction that wrote nothing. The wrapper's pre-read is an *organization lookup*, not a guard: the core re-reads the row through `tx` (so PR 2 sees a template the same commit created) and holds every check. Cost: one extra read of the template row per publish/instantiate.

**Q1 — two `fleetDb` reads remain inside the instantiate core.** ADR 0091 decision 1 says the core "does every guard read through that `tx`". Options: keep both (recommended; zero behavior change, the PR 1 gate); tx-only as the ADR words it, accepting the two text changes and editing the pinned spec; tx-only for the target, estate read kept for codes. **Blocks U4.**
