## 1. Goal

One function, `assetPointProblems`, decides whether a draft mapping will commit: the asset exists and is plain, the point key resolves (`unresolvedPointKey` against the draft's declared keys plus the fleet catalog `ctx.templates.pointKeys`), and the `(assetIndex, pointKey)` and `(assetIndex, sourceDataKey)` pairs are unique, compared exactly. The validator's `assetPoints` block, `map_point`, `remove_point_key` and the new `map_points` all call it, so a proposal that reads `readyToCommit` cannot fail at commit as `23503` (500, this is `F4.119`) or `23505` (409). Two batch write tools, `add_point_keys` (≤ 100 keys) and `map_points` (one `assetIndex`, ≤ 200 rows), all-or-none, join `CREDENTIAL_CHECKED_TOOLS`; one focused read `get_asset_points { assetIndex }` lists an asset's rows with their draft indexes. `use_existing_point_keys { value: true }` is refused when the catalog holds no active `kw`; the point-key and mapping action lines pass every model string through `quoteCell`. A system-prompt section drives the question loop: ask for the tag list, propose a table in text, offer "Write these mappings" / "Change the table" through `suggest_replies`, write only after the user agrees, say which keys are new to the catalog. `commitSummary` names how many declared keys are new to the catalog. The registry grows 25 → 28. No migration, no `packages/shared` change, no `apps/web` change.

**Out of scope (owner, ADR 0092).** Committed assets and the F2.7 sheet (D1); live tag discovery (`F3.24b`); suggestion and ranking (`F3.26`); guided grammar (D6 — but the guided `map_point` and `use_existing_point_keys` **do** gain the checks, through `guidedWrite`); point metadata in the draft (D4); the unit/domain contradiction pre-check (decision 8; raise a P3 row at closure); the Excel upload; `AGENTS.md`; the ADR 0090/0091 texts (ADR 0092 *Amended records* already names them).
