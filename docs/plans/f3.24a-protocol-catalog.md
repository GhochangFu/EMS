## 1. Goal

Give every onboarding chat a real protocol catalog and one config schema per protocol, shared with ingest. A code-defined catalog in `@bms/shared/ingest` — eight read-only entries, one per `onboardingProtocolSchema` value, each with a label, a description, `ingestWired`, `supportsDiscovery`, the required and optional config fields, an example config and a draft config schema — replaces `bms.protocol_catalog`, a table that no migration ever created and that `OnboardingProtocolService.listCatalog` (`onboarding-protocol.service.ts:54-70`) has been silently reading as `[]` since ADR 0011. The Drizzle declaration (`packages/db/src/schema/bms-schema.ts:671-679`) is deleted with no migration. `mqttConfigSchema`, `MqttConfig`, `mqttDeviceSchema` and `MqttDevice` move unchanged from `apps/ingest/src/adapters/mqtt.ts:28-82` to `@bms/shared/ingest`, and a looser `mqttDraftConfigSchema` (host and port optional, every present field strict) is derived beside them. `OnboardingValidateService.validate` (so `validate_draft`, the web preview and the commit's pre-check), `add_rtu` and `update_rtu` parse `rtus[i].config` with the protocol's draft schema and report paths only. `list_protocols` and the guided protocol-question intercept answer the catalog with the fields each protocol needs. An RTU on a protocol with no adapter is accepted as config only, and its action line ends with `(config only, not ingested)`. The system prompt tells the model to call `list_protocols` before it adds a non-MQTT RTU; the guided `defaultConfig` reads the catalog's example config for a non-MQTT protocol. No new tool (the registry stays 29), no migration, no new dependency, no `apps/web` change, no wire-contract change (`onboardingDraftRtuSchema.config` stays `z.record(z.unknown())`), **one PR**.

**Out of scope (owner, ADR 0093).** Live point discovery (`F3.24b`: its own ADR, after `F1.4` or `F1.5`); any `mqtt` dependency in `apps/api`; any API-to-ingest channel; a model-started connection; an admin UI or table for the catalog (gate question 3 option B needs a new ADR); a warnings channel on `validate_draft`; config schemas for `F1.2`–`F1.6`; the `F4.185` scrub widening; the `F4.223` and `F4.224` fixes; `AGENTS.md`; the ADR 0016 and ADR 0090 texts (ADR 0093 *Amended records* already names them, as ADR 0092 and 0095 did for ADR 0090).

## 3. Open questions (the owner rules before U1; the plan assumes the recommendation)

- **Q1 — a draft MQTT config that carries `rejectUnauthorized`.** `apps/ingest/src/host/bindings.ts:470-473` skips an MQTT RTU whose stored config has an own `rejectUnauthorized` key (`tls-downgrade-refused`), whatever its value. ADR decision 4 moves the schema "unchanged, with the `.default(true)`", so the shared `mqttConfigSchema` accepts the key, but a draft that passes with it commits an RTU ingest never serves — the class ADR decision 5 closes. *Recommended:* `mqttDraftConfigSchema` refuses a present `rejectUnauthorized` key with the fixed message `rejectUnauthorized is set by the ingest host's environment, not by the draft; remove it`. The alternative (accept and let ingest skip) keeps today's silent failure.
- **Q2 — F4.224's order.** Owed by the ADR. *Recommended:* F4.224 lands **after** this row as its own 0.25-effort PR (one regex on `onboarding-chat.service.ts:310`), rebased on this branch. F4.223 does not share a file (correction 2 above) and may land at any time.
- **Q3 — the catalog text.** The labels, descriptions, field lists and example configs are product text the model and the guided reply echo. The table in U2 is the proposed text; the owner approves or edits it before U2. Two rules it already meets: no key is a credential (`community` is a `SECRET_FRAGMENTS` entry, so the SNMP example carries `version`, not a community string), and every example host is a loopback or the PHE broker the guided default already names.
- **Q4 — the guided sentence for a refused config.** `guidedRefusal` (`onboarding-guided-writes.ts:75-99`) maps each registry refusal class to a user-facing sentence and fails closed on the rest. *Recommended:* a new class for the config refusal, `GUIDED_CONFIG_REFUSAL = "That RTU setting is not valid for its protocol. Open the preview to check the RTU's config."`. Reachable on the guided path only when `MQTT_PORT` is not a number (`defaultConfig`, `onboarding-chat-rule-based.ts:768`, gives `NaN`, which the schema refuses — a fail-closed guard).
