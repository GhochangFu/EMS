# Implementation plan — F3.37, the asset role vocabulary

Branch `feat/F3.37-asset-role-vocabulary`, off `main` at `d416a25`. Scope gated
2026-08-30 as ADR 0049 decision 5. No ADR is owed for the build itself; two open
questions below need a ruling before the first line of code, and one needs a
ruling before Unit A5.

---

## 1. Goal

Give `bms.asset_group_members` a `role` column that holds a code into a new
**global** lookup table `bms.asset_roles`, seed that table with the 26 role codes
the Ion Exchange mock's five trains name, expose the vocabulary through the
existing `GET /api/v1/vocabularies` response, and add the boundary check that
turns an unknown role code into a 400 naming the live values rather than letting
the foreign key surface as a 500. The role says what part a member **plays in
that group** — "the incoming supply", "a chiller" — so `F3.36` can bind a
section-template widget to a named position instead of a `uuid`, `F3.28` can
label a per-class health strip, and `F3.32` can anchor a mimic node.

**Explicitly out of scope.** Dashboards, dashboard templates,
`bms.dashboard_templates`, the stock catalog, and role *resolution* at
instantiation — all `F3.36`. The `table` widget and the metric catalog —
`F3.35`. Opening master-data administration to `asset_group_admin` — that is
`F3.34`, an authorization boundary two docblocks close on purpose, and this row
must not widen it as a side effect. Assigning roles to the seeded Eskom demo
memberships — the demo groups are
`electrical`/`hvac`/`it-rack`/`ups-battery`/`environment`, which the mock's five
trains do not map onto, so a demo backfill would be invented data. Adding `stp`
and `etp` to `bms.asset_domains` — see Open Question 1.

## 2. Contradiction in the ADR that the reader must not have to reconcile

ADR 0049's Consequences says of the two migrations: *"Both forward-only and both
tenant-scoped in the migration that creates them."*

**That sentence is true of `F3.36`'s `bms.dashboard_templates` and false of this
row's lookup table, and the plan takes the second reading deliberately.**
`bms.asset_roles` is **global**: no `organization_id`, no
`ENABLE ROW LEVEL SECURITY`, no policy. The evidence:

- `packages/db/drizzle/0047_tenant_policies_force.sql` gives none of
  `asset_domains`, `rule_categories`, `alarm_severities`, `alarm_skills` an
  `ENABLE ROW LEVEL SECURITY`. This is the fourth table of exactly that class.
- A per-org vocabulary breaks ADR 0049 decision 3's stock catalog: an imported
  stock template resolves `incoming-supply`, and the code must mean the same
  thing in every organization or the catalog resolves differently per tenant.
- A nullable `organization_id` with `NULL` meaning global is the shape decision 3
  rejected outright, on `E7.1c` and ADR 0043 Amendment 5.

The `role` column on the junction changes nothing about tenancy: `0047` lines 84
and 223–240 already give `bms.asset_group_members` a `tenant_isolation` policy
through **both** parents (`asset_groups.organization_id` and
`assets.organization_id`), with `FORCE`. Do not add an `organization_id` to the
junction — `0046`'s own text names junctions as deliberately column-free, and
`tests/adr-0043-tenant-columns.test.ts:71` asserts it.

## 3. Open questions — all three RULED by the owner on 2026-08-30

| | Question | Ruling |
|---|---|---|
| **OQ1** | `domain` column on the lookup table? | **Flat list, no `domain` column.** As recommended. |
| **OQ2** | Singular or plural role codes? | **Singular codes, the mock's labels verbatim.** As recommended. |
| **OQ3** | Does the admin surface ship in this row? | **Ship Parts A + B + C in `F3.37`.** As recommended. Effort `3–4` → `6–8`. |

The three questions as they were put, and the costs each option carried, are
kept below unedited — a ruling is worth less without the alternatives it
declined.

**OQ1 (before Unit A1). Does `bms.asset_roles` carry a `domain` column so a
picker can filter, or is it a flat list?**

The finding that decides the cost: the mock's five trains are Electrical · Water
· STP · ETP · HVAC, and `bms.asset_domains` holds `electrical`, `hvac`, `it`,
`environment`, `water` — **there is no `stp` and no `etp`**. So a
`domain varchar(64) REFERENCES bms.asset_domains(code)` on the lookup table is
not one column; it forces two new rows into `bms.asset_domains`, which is the
vocabulary `assets.domain` and `asset_templates.domain` read, so it changes the
plant-domain picker on the asset admin screen for every organization. That is a
product decision about the asset domain vocabulary, not a display tweak inside
this row.

- **Recommendation: flat list, no `domain` column.** Follow `assetDomains`
  exactly. The picker groups by a `sortOrder` banded per train (Electrical
  110–160, Water 210–250, STP 310–360, ETP 410–440, HVAC 510–550) — a
  convention, not a gate, and stated as such. The cost of being wrong is one
  forward-only migration adding a nullable column, and there is nothing to
  backfill because no membership carries a role yet.
- **What it leaves imperfect, stated so nobody is surprised:** a flat 26-option
  `<select>` offers `chillers` to a water group, and `equalization` (shared by
  STP and ETP, see below) sits at the STP position in an ETP-filtered view. The
  picker-filter question returns properly in `F3.36`/`F3.28`, when a train is
  actually rendered.

**OQ2 (before Unit A1). Are the role codes singular or plural?**

The mock's labels are plural — "HT Panels", "Chillers", "Primary Pumps" — but a
role is the part **one** member plays, and N members carry it. Recommendation:
**codes singular (`ht-panel`, `chiller`, `primary-pump`), labels exactly as the
mock renders them ("HT Panels", "Chillers", "Primary Pumps")**. Low stakes, but
forward-only migrations make it cheap now and awkward later.

**OQ3 (before Unit A5, and it is the scope question — see §7). Does the admin
read and the admin page ship inside this row, or as a new row `F3.38`?** Full
costing in §7. This one is not a preference; it decides whether `F3.37` can
honestly close.

## 4. Two findings the plan is built on, restated so they are not re-litigated

**No unique index on `(asset_group_id, role)`.** The mock's own nodes are plural
by design — `HT Panels = "2 · all good"`, `Pump House = "2 of 3 running"`,
`Chillers = "2 of 3 · 74%"`, `Primary Pumps = "3 running"`,
`Utilities = "DG · UPS · Solar"` — so a role matching several members is the
norm, not the exception. `WIDGET_POINT_CARDINALITY` in
`packages/shared/src/contracts/dashboard-builder.ts:258` already ships
`chart: { min: 1, max: MAX_WIDGET_POINTS }`. ADR 0049 decision 4 rejected binding
an *asset type* because the **widget count** would vary; one role → one widget
keeps the widget count fixed however many members match. Migrations here are
forward-only, so a constraint added and later dropped costs a second migration.

Two consequences that are this plan's to carry:

- **Resolution order must be deterministic, and the key is `assets.code`.** It is
  `varchar(64) NOT NULL UNIQUE` (`packages/db/src/schema/bms-schema.ts`), so it
  is a **total** order, not a partial one — which is what makes it safe. Ordering
  by `asset_group_members.id` or by insertion order means the same stock template
  instantiated twice in one organization yields two different tile orders with no
  visible cause. This ordering lives in the members read (Unit B2) and is gated
  there.
- **ADR 0049 decision 6 becomes a spectrum, and this plan answers it in the
  display layer.** Decision 6 ruled unresolved role → zero bindings → "no data
  bound". Zero bindings is visible. Two of three chillers carrying the role
  renders a widget that looks right and is quietly one short, which is not.
  **The answer taken here: the members read returns a per-role member count, and
  the admin page renders it beside each role.** It is a display concern and not a
  stored invariant, so it does not reopen the ADR. If OQ3 splits Part B out, this
  obligation goes with it and must be named in the new row.

**`equalization` appears in both the STP and the ETP train.** `code` is the
primary key of a global table, so it exists exactly once and both trains share
it. **Resolution is safe as-is** — ADR 0049 decision 4 resolves a role against
*the target asset group's members*, so a shared `equalization` never crosses
trains. Stated here so nobody adds an `stp-` / `etp-` prefix defensively. Only
the picker is affected, which is OQ1.

### Unit A1 — migration `0051`

**File to create:** `packages/db/drizzle/0051_asset_role_vocabulary.sql`
**File to modify:** `packages/db/drizzle/meta/_journal.json` — append
`{ "idx": 51, "version": "7", "when": <epoch ms>, "tag": "0051_asset_role_vocabulary", "breakpoints": true }`.
**Drizzle silently skips any `.sql` file missing from the journal**, so
`db:migrate` would pass with the schema short a table; that is exactly how
`0018`/`0021`/`0022` shipped to `main` without creating `bms.point_keys`.

**`0051` is free on disk today, but `F3.35`'s BACKLOG row also names `0051`** for
widening `dashboard_widgets_widget_type_check`. Whichever lands first takes it;
if `F3.35` merges first, this file becomes `0052` and the journal `idx` follows.
Say so out loud in the PR so the loser's plan text is corrected rather than the
two colliding.

Contents, in this order:

1. A header comment stating the three facts a reader will otherwise re-derive:
   the table is global and why (ADR 0049 decision 3 + the `assetDomains`
   precedent), the junction keeps no `organization_id` and why (`0046`'s junction
   rule + `0047`'s two-parent policy), and no unique index on
   `(asset_group_id, role)` and why (plural nodes, forward-only migrations).
2. **`SET ROLE bms_owner;`** — and this is load-bearing, not ceremonial. Not for
   `FORCE ROW LEVEL SECURITY` (there is none here). For
   `ALTER DEFAULT PRIVILEGES FOR ROLE bms_owner IN SCHEMA bms GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO bms_tenant, bms_fleet`
   at `packages/db/drizzle/0041_bms_owner_and_force_rls.sql:112-113`, which fires
   **only for objects created by the role it names**. `pnpm db:migrate` connects
   as `DATABASE_URL_SUPERUSER` (`bms_app`). Without the bracket,
   `bms.asset_roles` is owned by `bms_app`, the default privileges never fire,
   and `VocabulariesService` — which injects `TENANT_DRIZZLE`, i.e. `bms_tenant`
   — cannot read it. `0039`'s own comment records that this failure surfaces "one
   endpoint at a time", which here means inside `F3.36`, long after `0051`. The
   four existing vocabulary tables escaped this only because they predate
   `0039`/`0041`.
3. `CREATE TABLE IF NOT EXISTS bms.asset_roles (...)` — `code varchar(64)
   PRIMARY KEY`, `label varchar(128) NOT NULL`, `sort_order integer NOT NULL
   DEFAULT 100`, `active boolean NOT NULL DEFAULT true`, `created_at timestamptz
   NOT NULL DEFAULT now()`. Column for column with `bms.asset_domains`.
   **No `organization_id`. No `ENABLE ROW LEVEL SECURITY`. No policy. No explicit
   `GRANT`** — the default privileges do it, and a hand-written `GRANT` would be
   redundant and would hide a future breakage of the `SET ROLE` bracket
   (`0050`'s header records this exact instruction).
4. `INSERT INTO bms.asset_roles (code, label, sort_order) VALUES … ON CONFLICT (code) DO NOTHING;`
   — the 26 rows in §5.1 below. Seeded in the migration, exactly as `0029` seeds
   `bms.asset_domains` and `0034` seeds `bms.alarm_skills`.
5. `ALTER TABLE bms.asset_group_members ADD COLUMN IF NOT EXISTS role varchar(64) REFERENCES bms.asset_roles(code);`
   — **nullable**, because every existing membership has no role and a `NOT NULL`
   would need a default that is a claim. A foreign key, never a `CHECK` (§4.8,
   ADR 0031/0032). **No `ON DELETE` clause**, by design, so a delete of a role
   that plant still references fails loudly; retire with `active = false`.
6. `CREATE INDEX IF NOT EXISTS asset_group_members_group_role_idx ON bms.asset_group_members (asset_group_id, role);`
   — a plain index, **not `UNIQUE`**, and the header says why. Not
   `CONCURRENTLY`: it cannot run in a transaction block and the drizzle migrator
   wraps every file.
7. **`RESET ROLE;`** — mandatory, not symmetry. `0041`'s comment records that a
   leaked `SET ROLE` reaches the drizzle migrator's own journal write and every
   later migration in the same run.

Forward-only and idempotent (§4.4): every statement is `IF NOT EXISTS` or
`ON CONFLICT DO NOTHING`.

**The `ADD COLUMN` needs no bracket of its own** — ownership does not change on
`ALTER TABLE` — and the header should say so, or the next reader adds one by
symmetry.

## 10. Serial or parallel

**Serial, hands-on, no fan-out.**

`F3.37` carries no ⭐ in `docs/BACKLOG.md` and is not on the
build-operating-model §3 enabler list. But the §3 test that matters is not the
star — it is whether the unit defines an interface other work hangs off, and this
one defines a master-data vocabulary that **three** rows consume (`F3.36`,
`F3.28`, `F3.32`). ADR 0049's Consequences is explicit that carrying it inside
`F3.36` was declined because *"a master-data vocabulary designed inside a
dashboard row gets shaped for one consumer, and the other two then work around
it."* A subagent building that interface **cold**, without the gate
conversation, is the wrong tool. It is built one unit at a time.

Mechanically the same answer holds: A1 → A2 → A3 → A4 → A5 are strictly
sequential (migration → drizzle schema → contract → service → endpoint), and
A3/A4 touch `packages/shared/src/contracts/operations.ts` and
`apps/api/src/vocabularies/` — files `F3.35` and `F3.36` will also touch. Two
agents would collide.

**The one unit that could go to `implementer` on Sonnet is C1**, and only if OQ3
is ruled (i). It is new-files-only (`asset-groups-page.tsx`,
`api/asset-groups.ts`, the spec/test pair) plus two additive lines in `App.tsx`
and `admin-hub-page.tsx`, it is fully described by §7 above, and by then B1/B2
have frozen its contract. It still meets §3's delegation bar only because the
plan removes the cold start. Everything else is built inline with the session
model flipped.
