## Goal

`bms.location_types` (`code`, `label`, `sort_order`, `active`, `created_at`; global; no RLS; `bms_tenant` SELECT only) becomes the source of the location-type vocabulary, seeded with `smoc_campus`, `rsmoc`, `csmoc`, `pump_station`. `bms.locations.type` gains a foreign key to it. Migration `0085` moves the six `PHEWB` locations and their six map pins to `pump_station`; the two PHE seeds write the same value so a cold start agrees. Every `z.enum(["smoc_campus", "rsmoc", "csmoc"])` becomes one shared bounded-string schema; the two write paths (admin locations, onboarding commit) refuse a code that is not an active row with a 400 that names the valid codes; onboarding stops coercing to `smoc_campus` (Excel: a row error; chat: it asks, with the active labels as suggestions). The map returns the joined location's type as `kind` and the lookup's label as `kindLabel`, and "carries live health" becomes "joins a location". `GET /api/v1/admin/location-types` returns the active rows for the admin page's type dropdown. The location KPI row (`locationKpiSummarySchema`, and so `LocationDashboardDto`) gains `typeLabel`, which the location dashboard header and the KPI card show instead of the raw code (OQ4).

**Out of scope.** No create/rename/deactivate page for types (deferred, a new row when this one closes). No FK on `map_locations.kind`; `eskom_station` stays an unconstrained map-only kind. No per-organization ownership of types. No change to the Control Room views, the sim, ingest, the worker or the WebSocket protocol. No `AGENTS.md` edit in the feature branch (the post-merge `chore(agents):` sweep owns it).

## Decisions (engineering)

- **D1 — one code schema, declared once.** New `packages/shared/src/contracts/location-types.ts`: `locationTypeCodeSchema = z.string().min(1).max(32)` and `locationTypeDtoSchema = z.object({ code: z.string(), label: z.string() })` (plain object; no intersection, no readonly). `admin.ts`, `auth.ts`, `dashboard.ts` (both fields), `onboarding.ts` import `locationTypeCodeSchema` (a new file avoids an import cycle between the existing contract files). `envelopes.ts`: `locationTypesListResponseSchema = itemsOf(locationTypeDtoSchema)`. `index.ts`: `LocationTypeDto`, `LocationTypesListResponse` as `z.infer`. `contracts/index.ts` re-exports the file. `apps/api/.../locations.schema.ts` keeps the name `locationTypeSchema` but re-exports the shared one (§4.8 "re-export rather than restate"); `onboarding.schema.ts` imports it.
- **D2 — `VocabulariesService` owns the eighth vocabulary.** `listLocationTypes(): Promise<LocationTypeDto[]>` (active, `ORDER BY sort_order, code`) and `assertLocationType(code)` through the existing `unknownCodeMessage` (field union gains `"location type"`; `liveCodes` gains the table). Pool: `TENANT_DRIZZLE` = `bms_tenant`, whose SELECT the migration keeps and proves. `OnboardingCommitService` already has the service; `LocationsAdminService`, `OnboardingChatService` and `OnboardingService` gain it as a constructor dependency.
- **D3 — the read endpoint is its own controller.** `apps/api/src/admin/locations/location-types.controller.ts`: `@Controller("admin/location-types") @UseGuards(JwtAuthGuard) @Get()` → `LocationsAdminService.listLocationTypes(jwt)` = `requireMasterDataUser(jwt)` then `vocabularies.listLocationTypes()`, returning `{ items }`. Same guard pair as `GET /admin/locations`.
- **D4 — the draft can hold a location without a type.** `type` becomes `locationTypeCodeSchema.optional()` in both draft copies (`onboarding.ts:164`, `onboarding.schema.ts:64`). `OnboardingValidateService.validateCrossField` adds `{ path: "location.type", message: "Location type is required" }` when `location` exists without `type`, so `readyToCommit` stays false; `inferPhase` returns `"location"` while `type` is missing, so the chat re-asks. The commit calls `vocabularies.assertLocationType(loc.type ?? "")` before the transaction (fails closed: `""` is refused with the code list). No new phase (OQ2).
- **D5 — the chat and Excel paths get the list differently.** The chat service injects `VocabulariesService` and calls `listLocationTypes()` in the location branch and in the OpenAI branch. The Excel parser stays pure: `parseUpload(buffer, activeLocationTypeCodes: readonly string[])` is a **required** second parameter (an optional one at an adapter is invisible), and `OnboardingService.uploadExcel` fetches the codes and passes them.
- **D6 — the Excel refusal has the `parseRtus` protocol shape** (`:595-598`): "LOCATION row 1 has an empty type; use one of a, b, c, d and upload the workbook again" / "... has an unknown type of N characters; use one of ...". Fold `.trim().toLowerCase()` before the compare; never echo the cell (§4.3).
- **D7 — the chat matches on code or label, case-folded, whole-word**; on a miss it answers "Which type of location is **{name}**?" with `suggestedReplies` = the active labels and `currentPhase: "location"`, patching `name/slug/code` only. A reply that matches a label or code sets `type` and moves on to the RTU question. The OpenAI system prompt lists the active codes; a `location.type` in the model's patch that is not an active code is deleted from the patch before `finalizeTurn`.
- **D8 — the map.** SQL adds `LEFT JOIN bms.location_types lt ON lt.code = l.type` and selects `l.type AS location_type, lt.label AS location_type_label`. `kind = location_type ?? ml.kind`; `kindLabel = location_type_label ?? (ml.kind === "eskom_station" ? "Station" : ml.kind)` — the API owns every label, so the web switch goes. Live health: `loc.canonical_location_id !== null`. Web: `apps/web/src/lib/map-site.ts` exports `isOperationalSite(site) = site.canonicalLocationId !== null`; the popup line becomes `<span data-testid="site-kind">{s.kindLabel}</span>{s.organization ? ` · ${s.organization.code}` : ""} · {status}` so a joined pin shows "Pump station · PHEWB".
- **D9 — the admin page.** `fetchAdminLocationTypes()` in `api/admin/locations.ts`; `useQuery({ queryKey: ["admin", "location-types"] })`; `<option value={code}>{label}</option>` from the list; `emptyForm.type = ""`; the resolved value `form.type || types[0]?.code ?? ""` feeds both the `<select value>` and the payload; the select is disabled until the list loads. The two `AdminLocationDto["type"]` casts go (it is `string`).
- **D10 — the migration runs in three brackets.** `SET ROLE bms_owner` → `CREATE TABLE IF NOT EXISTS bms.location_types`, the four-row `INSERT ... ON CONFLICT DO NOTHING` (no target, as `0038`), `REVOKE INSERT, UPDATE, DELETE ON bms.location_types FROM bms_tenant` (the grantor revokes, as `0059`) → `RESET ROLE`. Then **as the superuser**: the two idempotent `UPDATE`s (`bms.locations` is FORCE-policied since `0041`, so `bms_owner` under `SET ROLE` would update zero rows and report success), a `DO` guard that raises when any `bms.locations.type` has no lookup row, and `ALTER TABLE bms.locations ADD CONSTRAINT locations_type_fk FOREIGN KEY (type) REFERENCES bms.location_types(code)` behind a `pg_constraint` guard (the FK validation scan must also see the rows). Then the `0059`-shape proof: `bms_tenant` holds SELECT and not INSERT/UPDATE/DELETE; `bms_fleet` holds SELECT (the map query runs on the fleet pool). No statement-breakpoint marker text anywhere in the file (the `0038` header explains why).
- **D11 — a 23503 on `locations.type` is not mapped to a 400.** The service check runs first on every write path; the FK can only fire if a `location_types` row is deleted between the check and the insert, and no code path deletes one (rows are retired with `active = false`). A 500 there reports a broken invariant (OQ1).
- **D12 — the five `'site'` fixtures become `'rsmoc'`** (the peer's code; OQ5).
