## 0. Goal and out of scope

**Goal.** Give the Energy Consumption report its third format and a history. `pdfmake` (pure JS over `pdfkit`, standard Helvetica, no font VFS) renders the same `energyTable` rows the CSV and XLSX already read; `GET /api/v1/reports/energy/export.pdf` answers beside the two export routes with the same query, scope and `no-store`. Migration `0077` creates `bms.report_files` tenant-scoped from birth; `POST /api/v1/reports/energy/files` renders under the caller's readable asset scope, stamps the readers' location scope, writes object-then-row with F3.4's commit-then-discard cleanup, and refuses with 409 at `REPORT_ONDEMAND_CAP` (50) before any storage call; `GET /reports/files`, `GET /reports/files/:id/download` (proxied, `attachment`, `no-store`) and `DELETE /reports/files/:id` follow decision 6's read rule; the object key is `org/<org>/reports/<fileId>` from a second builder in `object-key.ts`. The Reports panel gains a PDF button, a Save-to-history action and a History list.

**Out of scope (F3.5b, by the ADR's own split):** `bms.report_schedules` and migration `0078` (which is also where `report_files.schedule_id` and the `(schedule_id, period_end, format)` unique index arrive); the `reports-dispatch` and `reports-render` queues; `report-period.ts`; the email attachment and `delivery_status` transitions (F3.5a writes `none` and never changes it); `ReportsCoreModule` (decision 9 — see §2 R-10 for why it is not pulled forward); the Schedules web section; the retention helper `REPORT_RETENTION_PER_SCHEDULE` (it prunes *scheduled* files, which do not exist yet). **Named deferrals kept:** a bundled Unicode font, a presigned download, report files for asset-group-only users, the orphan sweep (ADR 0066 decision 11 says it is filed "the day the worker has a second job kind" — no row exists yet; decision 5's sentence is a note for that row, not code here).

## 2. Plan rulings (where the ADR is silent) and the questions the human must answer first

Each is marked **plan ruling** so the owner can overrule it before code; **Q-1..Q-3 need an answer before U6 starts.**

- **R-1 — `energyTable` is exported, not duplicated.** `energy-pdf.ts` imports it; `energySheetRows` stays as the XLSX reader. Decision 2's "one row source" holds by import, and the spec proves it by mutation (U1).
- **R-2 — PDF layout.** A4 portrait, 40pt margins, Helvetica 9pt body; a title line `Energy Consumption` with the period and `generatedAt` under it; then the table blocks exactly as `energyTable` yields them, each block a pdfmake `table` with `headerRows: 1` and the blank rows as block breaks; numeric cells right-aligned and formatted with `new Intl.NumberFormat("en", { maximumFractionDigits: 2 })` (deterministic on Node 20's full ICU); string cells verbatim. Money keeps the shape the table already has — the ISO code in the **Unit** column beside the amount (`5,042.12 | ZAR`, `2.15 | ZAR/kWh`) — which is how the CSV and XLSX already satisfy "never a symbol"; a null cost is the table's U+2014 (in WinAnsi). Footer: page `n / N`. **Plan ruling:** the ADR's `INR 1,234.56` describes the pair, not a merged cell; if the owner wants one cell, U1 concatenates `${unit} ${value}` for the two money rows only.
- **R-3 — `sha256` and `byte_size` are computed from the rendered `Buffer` in the service, after the render and before any storage call** (F3.4 R-4's point). The filename is server-generated: `energy-consumption-<start>-to-<end>.<pdf|xlsx>` — the same name the web's `saveExport` gives the direct download.
- **R-4 — the row's `organization_id`, and Q-1.** The ADR's save body is `{ startDate, endDate, format }`, but a global admin's `readableAssetIds` is `null` (every organization) and an organization admin may hold several grants, so the row has no single organization to carry. **Plan ruling:** the body gains **`organizationId` (uuid, optional)**. The service resolves the target: `writableOrganizationIds(jwt)` is `null` → the body value is **required** (400 "organizationId is required for a global admin"); exactly one id → that id, and a body value that differs is 403; several → the body value is required (400 naming the count, never the ids); zero → 403. The render scope is `readableAssetIds(jwt)` **intersected with the organization's assets** (`assets.organization_id = org` on `fleetDb`; `null` → all of the organization's assets), so a file never carries another organization's rows. **Q-1 (owner):** accept the optional `organizationId`, or require it always?
- **R-5 — the `location_ids` stamp, and Q-2.** Decision 6 says "from `writableLocationIds(jwt)` (`null` → `{}`)". For an `organization_admin` that helper returns **every location of every organization they hold**, which would stamp foreign location ids onto this organization's row. **Plan ruling:** `admin` and `organization_admin` stamp `{}` (whole organization — what their write *is*); a `location_admin` stamps `writableLocationIds ∩ locations.organization_id = org`, and an empty intersection is 403 "No location scope in this organization to record for the report". `asset_group_admin`, `operator`, `viewer` are refused by `assertMasterDataRole` inside `writableLocationIds` **before** any of this (decision 6's `wc-hvac-admin` case). **Q-2 (owner):** confirm `{}` for organization admins rather than the literal list.
- **R-6 — decision 6's read rule is one method, role-aware:** `AccessControlService.canReadReportFile(jwt, { organizationId, locationIds })` — `admin` → true; `organization_admin` → `directOrganizationIds` includes `organizationId`; `location_admin` → `locationIds.length > 0` and every id ∈ `writableLocationIds`; any other role → `assertMasterDataRole` throws 403. `canManageOrganization` is **not** used for this, because for a location admin it is location-derived (§1). The list route uses the same inputs as a SQL predicate (R-7). A refused download/delete answers **403** with one sentence, `"Report file is outside your access scope"`, after the row was read on `fleetDb` (the file id is a random uuid; existence is not a secret worth a 404 that lies — the asset-image routes answer 403 for the same case). **Q-3 (owner):** 403, or 404 for out-of-scope?
- **R-7 — list ordering and size.** `GET /reports/files?limit=` (`z.coerce.number().int().min(1).max(200).default(50)`, `.strict()`), ordered `created_at DESC, id DESC`, no offset — the on-demand cap bounds the set at 50 per organization until F3.5b. The SQL predicate for a `location_admin` is `cardinality(location_ids) > 0 AND location_ids <@ $writable::uuid[]`; organization admins and global admins filter by organization only, through `withOrganizationReadScope`.
- **R-8 — the DTO is a `parseStoredContract` site** (`"report_files.to_dto.row"`, the tenth literal), never a bare `.parse()` — `f4.108` is edited to count it. The DTO is a plain `z.object().strict()` — no `.merge()`, no `z.intersection`, no `.readonly()` (it is not composed and it is not the all-readonly shape; say so in the docblock as `asset-images.ts` does). **`scheduleId` is absent from the F3.5a DTO** — the column arrives with `0078`, and a hard-coded `null` would be a lie that later becomes true. `organizationId` and `locationIds` **are** carried (the web needs neither today; F3.5b's schedule section will).
- **R-9 — audit rows, `report_file.create` / `report_file.delete`** (entity type `report_file`, payload `{ fileId, organizationId, format, byteSize, sha256, periodStart, periodEnd }` / `{ fileId, organizationId }` — ids, a code and numbers, never the filename), written inside the tenant transaction through `MasterDataAuditService.write(…, tx)` exactly as F3.4 does. The ADR is silent; a stored tenant document deleted by an admin is the case the audit log exists for. **Plan ruling.**
- **R-10 — `ReportsCoreModule` stays F3.5b's.** Decision 9 needs it only so `WorkerModule` can import `ReportsService` without `CalcModule`'s loops. Nothing in F3.5a runs on the worker, `tests/f4.24-worker-imports-no-api-loop.test.ts` cannot see a split that the worker does not import, and building it now would be an untested seam. `ReportsModule` keeps providing `ReportsService` and importing `CalcModule`; F3.5b replaces that with the import.
- **R-11 — cap serialisation.** The authoritative count runs inside the tenant transaction under `pg_advisory_xact_lock(hashtextextended('report_files:' || organization_id, 0))` (no parent row to `FOR UPDATE`, unlike F3.4's asset). The cheap fleet pre-check runs before the render and before the put; both compare `!(n < cap)`. Until `0078` lands the count is *all* rows of the organization; F3.5b changes the predicate to `schedule_id IS NULL`. The cap is read once by `readReportFilesConfig(process.env)` (`REPORT_ONDEMAND_CAP`, default 50, floor 1; a non-integer value → default with one `warn` naming the variable) — the `queue-config.ts` reader shape — and provided under a `REPORT_FILES_CONFIG` symbol token.
- **R-12 — cleanup after a failed row is a private copy of F3.4's `discardObjectUnlessTheRowCommitted`**, parameterised on `reportFiles`, with the docblock naming its origin. AGENTS.md §9 rule 9 (no unrelated refactor) and the narrow F3.51 precedent decide against lifting F3.4's private method into a shared helper in this row.
- **R-13 — web role gate.** The History section and the Save action render only for `isMasterDataAdmin(user.role)`; the PDF button renders for everyone (the export routes are `readableAssetIds`-scoped, like CSV). `ReportsPanel` gains a `user: AuthUser` prop from `ReportsPage` (the store is not read inside the component, so the spec keeps its bare render plus a role). The organization select renders only when `user.role === "admin"` (fed by `fetchAdminOrganizations`); other roles send no `organizationId` and render the 400 sentence if the API asks for one.
- **R-14 — delivery status labels:** `none` → "On demand", `sent` → "Emailed", `skipped_unconfigured` → "Email not configured", `failed` → "Email failed" — pure, in `apps/web/src/lib/report-files-view.ts`, so F3.5b changes no component to light them up.
- **R-15 — no new `tests/` fence for the route headers.** The PDF route's headers are imperative and pinned by a stub-response assertion in `reports.controller.spec.ts`, the same gate the XLSX route has; the file routes' headers are pinned the same way in `report-files.controller.spec.ts`.
