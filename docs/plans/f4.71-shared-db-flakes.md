### M4 — backfill `22023 refresh window too small` in CI (live; recurs)

CI log of run 33831488312 (2026-09-04, step executed 03:01:41Z): `_1m`, `_5m`, `_1h` each
"from 2026-09-04T00:00:00.000Z"; `_1d` then failed with `22023`, detail "The refresh window
must cover at least one bucket of data", from `refreshLevel` (`:161`) via `main` (`:505`).
`main()` refreshes each level over `[sourceFloor, now()]` (`:456`, `:505`) — no bucket-width
check. Two conditions met at once:

1. The `_1h` materialization hypertable's oldest chunk started that UTC day. Chunk ranges
   are epoch-aligned multiples of the chunk interval; 2026-09-04 is day 20700 since the
   epoch, divisible by 10 — consistent with a 10-day interval (measure it on `bms_f471`:
   `SELECT hypertable_name, time_interval FROM timescaledb_information.dimensions WHERE
   hypertable_schema = '_timescaledb_internal'`). So the 1-day window `[00:00, 03:01)`
   held no complete bucket.
2. `_1h` had a row at all. CI seeds one raw row at `now() - 2 minutes` (`ci.yml:257-263`);
   `_1h` materializes it only when `floor(now, 1h) > row time`, i.e. the step ran within two
   minutes after an hour boundary (03:01:41 ✓). The 02:02Z run's step ran ~02:06 → `_1h`
   empty → "has no chunks; stopping before _1d" → green; every later run the same.

`packages/db/src/refresh-aggregates.ts` has no commit since 08-25, so this recurs for a run
whose backfill step executes at `HH:00–HH:02` UTC on a boundary day (09-14, 09-24, 10-04, …).
`refreshAggregatesFrom` is safe (its window is always ≥ 2 bucket widths, `:264-266`).

```ts

/** Runs `work`, retrying only SQLSTATE 55P03 (a concurrent refresh) — the
 *  `refreshLevel` loop in packages/db/src/refresh-aggregates.ts:143-178. */
export async function retryOnConcurrentRefresh<T>(
  work: () => Promise<T>,
  retry: { attempts: number; delayMs: number } = FIXTURE_REFRESH_RETRY,
): Promise<T>
```

5. `theDefaultBudgetIsFiveAttemptsThreeSeconds` — `FIXTURE_REFRESH_RETRY` equals
