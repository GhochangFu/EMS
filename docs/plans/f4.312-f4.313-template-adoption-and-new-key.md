# F4.312 + F4.313 — plan: adopt a template-less asset onto a template version; a new catalog key from the Add panel (ADR 0109 Amendment 1)

Written by plan-architect (Fable), 2026-11-05, against `origin/main` at `b3b886c8`. Scope: ADR 0109 Amendment 1 (accepted 2026-11-05, rulings A0–A13, decisions 1–9). Not committed yet; the owner's rulings on the open questions are appended below before any build.

## 1. Goal

**F4.312.** An administrator pins an asset whose `assets.template_id IS NULL` to one published template version of the asset's own organization and domain, in one transaction per batch of up to 25 assets, all or nothing, after a preview that names every refusal by asset code and point key. Existing measured rows the version declares stay; missing measured points get an `unmapped` row; undeclared rows stay (extra points); a standalone calculated point whose key the version declares as derived becomes that asset's override (ruling 8) with no row write; the version's seeded alarm rules and default dashboards are written as `instantiate` writes them; derived points and KPIs reach the asset through the pin. Surfaces: the points page, the asset list's bulk action, and the copilot card `assetTemplate.adopt`.

**F4.313.** The key picker of the Add calculated point panel and of the bulk wizard gains **New key** (code, label, unit — the Point keys page's own schema), shown only to a global administrator. The panel checks the formula first, then creates the key (`POST /admin/point-keys`), then writes the point. If the point write fails the key stays, the panel says so, and the next try finds it in the picker. No API change.

**Out of scope:** release back to no template; stock PHE templates; draft/archived targets; a combined copilot key-plus-point card; any change to `asset_points` columns, `CalcDefinitionsService`, `migrate`'s behaviour or the point-keys access rule.

## 2. Facts measured from the code

- `migrate` has **no plan hash**: it rebuilds the plan at apply and refuses on any refusal; `asset-templates-migrate.schema.ts` says there is deliberately no field echoing a preview back. Adoption reuses that guard.
- `instantiate` writes: the asset row, measured `asset_points` rows only, `automation_rules` via `seededRuleValues`, default dashboards via `AssetDashboardsInstantiateService.instantiateForAssets`, one audit row. It writes **no KPI rows** (read through the pin) and **no maintenance plans**.
- Reusable instantiate guards: `assertCatalogActive`, `parseTemplateContentForInstantiate`, `assertAlarmVocabulariesStillLive`, `assertBatchFits`, `assertRuleCodesFree` (widened to `{ code }[]`).
- Reusable migrate pieces: `resolveAdditionSourceDataKey`, `unresolvableAdditionMessage`, `translateAssetPointInsertUnique`, `refuseOverridesThatDoNotSurvive` (already ruling 8's "through the override's own checks"), `refuseMetadataOverridesThatDoNotSurvive`. Their `refuse` callback gains the asset as a second argument so refusals carry `assetId`/`assetCode` fields.
- Migrate's private reads `loadPoints`, `catalogUnits`, `pointIdsByKey` move to a sibling (`asset-templates-version-reads.ts`); the migrate service is 964 lines.
- Ruling 8 costs no row write: flipping `template_id` moves the computed row from the standalone read to the template read (`coalesce(asset, template)`); history continues under `(asset_id, point_key)`; runtime status restarts at the next reload.
- `asset_points_source_ref_check`: the A3 unmapped row is `{ rtuId: null, sourceKind: "unmapped" }`.
- Access (A10): migrate's chain verbatim — `requireMasterDataUser` → template in scope (403) → published (409) → `writableLocationIds` count refusal (403).
- Catalog gates: `f3.85-catalog-coverage` (every new `@Post` is an entry or on `ASSET_TEMPLATE_PENDING` in the same PR), `f3.85-stepper-coverage` (`NOT_YET`), propose budget `< 91_000` (last measured 89,599). `assetTemplateDeploy` cannot carry an adopt body, so a new target kind `assetTemplateAdopt` is needed. ADR 0099's next amendment is **12**.
- **No migration.** Adoption writes existing tables only.

## 6. Owner rulings on the open questions (2026-11-05, asked one at a time)

1. **Migrate's guard.** Apply recomputes the plan and refuses (409, nothing written) on any refusal. No plan hash.
2. **Rules + dashboards.** Write the seeded alarm rules and the default dashboards, as instantiate does. Derived points and KPIs come through the pin. No maintenance-plan write.
3. **A blank asset unit is not a mismatch.** Refuse only when both units are set and differ; the row's unit is not rewritten.
4. **An inactive catalog key does not refuse adoption** (migrate's reading).
5. **Refuse** a computed row whose key the version declares as measured (`point_key_already_mapped`).
