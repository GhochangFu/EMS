## 1. Goal, and what is out of scope

**Goal.** An escalation step that the per-channel hourly ceiling refuses is retried on a
later tick instead of being lost for the life of the ledger. Two changes in one file,
`apps/api/src/notifications/notifications.service.ts`.

**Q1** — when `isOverHourlyLimit` refuses a dispatch carrying an **escalation** event,
`dispatchToChannel` returns `{ status: "skipped_rate_limited", error: null }` to its
caller **without calling `record()`**. Nothing is written, so the event's key is never
spent, and the next lifecycle tick (30 s, sweep-then-sleep) re-dispatches the same due
step and sends it once `isOverHourlyLimit`'s trailing-hour count of `sent` rows has
fallen back under `ratePerHour`. **No caller changes**: `runEscalationPhase`
(`apps/api/src/alarms/alarm-lifecycle.service.ts:364`) already `await`s
`deps.dispatchToChannels(...)` and ignores the results, so "write no row" is by itself
the whole retry mechanism.

**Q2** — `eventDeliveryBlocked` stops treating a `skipped_rate_limited` row as blocking,
in **both** arms of its predicate, by adding `ne(status, 'skipped_rate_limited')` to the
SQL `WHERE`. This releases the keys already blocked before this row lands, including the
52 backlogged alarms ruling Q7 measured on the seeded stack. Without Q2 the row would
close while the steps it was written about stayed lost.

**Q-A** — Q1 covers the escalation kind only. The cleared message keeps its
`skipped_rate_limited` row. See C1.

**Explicitly out of scope.**

- **The raise path.** `dispatchToChannel`'s `else if (!input.raised)` branch, and
  `hasRecordedSkip` and `sendTest`, are not touched. A raise key is per transition and
  the next raise is a new alarm with a new key, so ADR 0041 decision 4's visibility
  requirement continues to be served where its growth is bounded. `hasRecordedSkip`
  already pins `status = 'skipped_deduped'`, and the two key spaces are disjoint anyway
  — `buildDedupeKey` appends `:escalation:<n>` or `:cleared` to an event's key.
- **`skipped_unconfigured`.** It blocks an event key by the same mechanism, so a step
  refused while its channel had no transport is still never retried. Amendment 2 §5
  holds it out deliberately, as its own row. This plan *adds a test that it still
  blocks* — that is not scope creep; it keeps the FG1 guard alive after the
  rate-limited case inverts.
- **Ruling Q9 and `MAX_EVENT_ATTEMPTS`.** Three `failed` rows still block a key.
- **No DDL and no migration.** `notification_deliveries_channel_key_idx`
  (`(channel_id, dedupe_key) WHERE dedupe_key IS NOT NULL`,
  `packages/db/drizzle/0066_alarm_lifecycle.sql:324-326`) still serves the read; the
  status is a residual filter over the handful of rows one key holds. `packages/db` is
  untouched, so no `migration-reviewer` and no cold-start gate.
- **No back-off stamp.** That was the board row's option (b) and it needed DDL;
  Amendment 2 chose the no-DDL form.
- **No new file anywhere** — so no `.test.ts` wrapper to create, and no line to add to
  the root `typecheck:tests` script.
- **The `docs/BACKLOG.md` ✅ row, `docs/roadmap.md`, and `AGENTS.md:450`** — the
  `chore(agents):` sweep, a separate PR, never this branch (§9.10).

### Corrections

**C1 (decided the Q-A ruling). Q1 as first written also silenced the cleared message,
which is never retried.** `input.event !== undefined` covers both event kinds. For
`kind: "escalation"` the retry premise holds. For `kind: "cleared"` it does not:

- `notifyCleared` is called **only** from `runClearPhase`, inside the loop over the rows
  `writeAlarmState` has just returned — alarms that cleared *in this tick*
  (`alarm-lifecycle.service.ts:205-214`).
- Its own doc says so: *"the clear has already committed and the next tick will not see
  this alarm again"* (`:260-262`).
- `loadActiveAlarms` filters `and(isNull(alarms.clearedAt), isNotNull(alarms.ruleId))`
  (`:483`).

Under the blanket form a ceiling-refused clear gets no send, no row, no retry and no log
line — the silent-loss shape §4.6 names, and worse than today's visibly-lost row. The
owner ruled Q-A on 2026-09-08: **escalation only**.

**C2. `notifications.service.spec.ts:458-486` is the raise path, and it stays.**
`service.dispatch(input())` uses `input()`'s defaults — `raised: true`, no `event` — so
it enters step 2 on the raise path, and its assertion that the rate-limited skip *is*
recorded is exactly what Q1 preserves. **Do not touch it**; it becomes the unit-level
guard that Q1 did not leak into the raise path.

**C3. Amendment 2 §3's worked example is not reachable in production, and the amendment
now says so.** Today's predicate blocks on the first non-`failed` row, so at most **one**
`skipped_rate_limited` row can exist per event key; after Q1 the escalation path writes
none. The SQL form is still right, for the reason that survives: the predicate must stay
exact **by construction**, and the comment at `:448-451` must stay true.

**C4. If the unit fake is left blind, the events spec's rate-limited case keeps passing
while encoding a falsehood.** `fakeDb` tells the four `SELECT`s apart by projection and
sees nothing of the `WHERE` (`notifications.service.spec.ts:80-95`). After a correct
SQL-only Q2 the fake still returns the queued `skipped_rate_limited` row and the
predicate still blocks, so
`notifications.events.spec.ts:322`'s `{ ledger: ["skipped_rate_limited"], want: "skipped_deduped" }`
stays **green** while asserting the opposite of production. That row is **deleted**, not
inverted, and replaced by (a) an assertion on the rendered SQL and (b) the real-database
case in storm-control.

**C5. Storm-control's FG1 block exists to catch a read narrowed to `status = 'sent'`**
(`storm-control.integration.spec.ts:378-401`, its own comment). The rate-limited row is
the only non-`sent`, non-`failed` row it plants, so inverting the block deletes the
guard. A `skipped_unconfigured` case replaces it — a status Amendment 2 §5 keeps
blocking.

**C6. `storm-control.integration.spec.ts:399`'s `countByKey(...) === 1` passes before and
after, for different reasons.** Today the refusal writes one row; after Q1+Q2 the retry
writes one `sent` row. Split it into *0 after the refusal* and *1 `sent` after the
retry*, and assert the status.

**C7. Two stale names to fix while in these files.** `dedupe-key.ts:37` and
`storm-control.integration.spec.ts:239` both name `NotificationsService.hasRecordedDelivery`,
a method that does not exist — it is `eventDeliveryBlocked`.

**C8. The board row's proposed fix (a) is falsified** — Amendment 2 §1 records why.
Dropping the status from the `.some(...)` arm alone leaves `rows.length >= MAX_EVENT_ATTEMPTS`
standing, and three rate-limited rows land within 90 s while the ceiling needs up to an
hour to lift.

### Decisions

**D1.** Q1 is one named local and one ternary, in the shape H1 already uses two lines
above. Not a new method, not a config flag — the reader must see the two ceiling-refusal
exits side by side and see that they treat the escalation path the same way.

**D2.** Q2 is `ne()` in the `WHERE`, never a `.filter()` on `rows`. `ne` joins the
existing `import { and, eq, gte, sql } from "drizzle-orm";`.

**D3. No new log line on an escalation-path ceiling refusal.** Amendment 2 §2 accepts
the lost visibility and names the operator's signal — the raise path's own rate-limited
rows on the same channel. A `warn` per refusal per tick would be 52 lines every 30 s in
the exact burst this row exists to survive. If the owner wants a signal it belongs on
the channel (a health field), not in the sweep, and that is a separate row.

**D4. The unit layer proves the *shape* of the read; the real database proves the
*behaviour*.** Unit: the rendered SQL names `"status" <> $n` with `skipped_rate_limited`
bound, via `PgDialect().sqlToQuery` — the same conversion drizzle's `PgSession` runs, an
idiom already used in `apps/api/src/asset-health/health-rollup-sql.spec.ts`. Integration:
the retry, the release and the surviving blockers, against Postgres. A filtering fake was
rejected: it would rewrite the invariant `fakeDb`'s header documents and two spec files
depend on, to discriminate a state C3 shows is unreachable.

**D5.** One PR, two commits, each with its own green run.

### The accepted cost, with the number

On a channel held over its ceiling, every due step is re-dispatched every tick and
reaches **two** reads instead of one — the ledger read plus `isOverHourlyLimit`. At
ruling Q7's measured burst (52 backlogged alarms, one step each) that is ~104 reads per
30 s tick against ~52 today, both single-digit-millisecond indexed reads on the fleet
pool, and it stops the moment the ceiling lifts or the alarms are acknowledged or
cleared. The retry is deliberately **unbounded in time** — Q9's three-attempt bound
counts `failed` rows and this path writes none — so a channel held permanently over a
misconfigured ceiling retries for the life of the alarm, writing nothing. Amendment 2 §2
accepts exactly this.
