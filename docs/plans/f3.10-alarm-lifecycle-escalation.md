## 1. Goal, and what is out of scope

**Goal.** Give an alarm a lifecycle. Today `bms.alarms` has one closure —
acknowledgement — so a transient breach stays "open" until a human clicks, and
an acknowledged alarm whose condition still holds **re-raises as a new row on
the next evaluation** (measured on the `F3.46` stack run). After this row:
`bms.alarms` carries `cleared_at` and `normal_since`; *active* means
`cleared_at IS NULL`; acknowledgement is an annotation; one 30 s sweep in the
API process clears an alarm once fresh samples have stayed non-matching for the
rule's hold (`clear_hold_seconds`, default 120 s) and, for alarms that are
active and unacknowledged, sends each step of the organisation's per-severity
escalation profile once, to the step's channels, through the existing
`NotificationsService` and its ledger. Four tenant tables hold the profiles, a
`configuration`-class admin API and page administer them, the alarms page
shows the four states, and the rules card gets one number field.

**Explicitly out of scope.**

- **The `/cr-overview` Active Alarms rail** — stays `F3.28` (decision 11). The
  `ActiveRulesPanel` in `control-room-overview-page.tsx:433,701` reads rule
  states, not alarms, and is not touched.
- **No new column on the deliveries page** (decision 11). The event kind lives
  in `dedupe_key`; `GET /notifications/deliveries` and its DTO are unchanged.
- **No per-rule profile override, no shelve action** (Consequences).
- **No deadband and no change to the condition grammar** (decision 3).
  `rule-evaluation.ts` is imported, not edited.
- **No queue, no worker, no per-alarm timers** (decision 4). The ledger and the
  two stamps are the state.
- **No seed** (decision 8). Nothing escalates until an operator configures a
  profile; the migration seeds no row in any of the four tables.
- **No retry of a step whose delivery failed** — decision 10's literal text; see
  Q7 for the one case worth a ruling.
- **`POST /api/v1/alarms/:id/ack` is unchanged** (decision 1). It never clears,
  and it still accepts a *cleared, unacknowledged* alarm — that press is the
  transition to *closed*. `alarms.service.ts:205-219` filters on
  `acknowledged_at IS NULL` only, which is exactly right, so it is not edited.
- **The `chore(agents):` sweep** — §9 lists it; it is the caller's separate PR.

### What the unit-spec fake can and cannot see (the `F3.46` lesson)

`notifications.service.spec.ts`'s `fakeDb` distinguishes `select()` chains by
**projection**: `{ count }` is the hourly ceiling, `{ id }` is
`hasRecordedSkip`. Every new ledger read in U2 must use a projection the fake
has not seen — `{ status }` for the event-idempotency read, `{ channelId }`
for the cleared-recipient read — or the fake's boolean queue feeds the wrong
branch and the spec passes for the wrong reason. The real `WHERE` is proved
against Postgres in the storm-control and lifecycle integration suites.

### Decisions this plan makes (not questions — do not escalate them)

**D1. Two PRs; PR 1 is the loop helper and the notification split, and it is
worth its own review cycle.** Both units touch live production paths — the two
loops that drive `bms-calc` and the health roll-up, and the one dispatch entry
point with the storm-control gate — so a small, separately-reviewed diff is
exactly where a regression there is cheapest to catch. Both are independent of
any DDL, and they merge while `0063`/`0064` land. **The contracts do not go in
PR 1**, against decision 12's candidate list: `clearedAt` and
`clearHoldSeconds` are required keys, and `checkResponse` throws in dev on a
missing key, so a contract shipped before the column it reports would redden
the SPA on `main`; and the escalation DTOs have no consumer until U8 — inert
schemas buy a reviewer nothing. They ship with their consumers in PR 2.

**D2. The shared loop is `runSweepLoop(deps, signal)` in
`apps/api/src/scheduling/sweep-loop.ts`.** `deps` = `{ sweep(nowMs), sleep,
now, baseTickMs, label, logger }`. `runSchedulerLoop` and `runHealthRollupLoop`
keep their exported signatures and become one-expression wrappers (the calc
one owns `previousCyclic` in its closure). The warn text stays
`` `${label}: sweep failed: ${cause}` `` so `health-rollup.spec.ts:236-240`'s
"the warning must carry the cause" holds unchanged. `sleep` stays in
`telemetry/sleep.ts` — moving it touches four importers for nothing.

**D3. Event idempotency lives inside `dispatchToChannel`, keyed on any ledger
row.** Decision 10 says the ledger is asked before a step or a cleared message
is sent; the place that asks is the per-channel path both entry points already
funnel through — `F3.8`'s own reason ("a second entry point would be a second
place for the dedupe to be forgotten"). When `input.event` is set the service
reads `(channel_id, organization_id, dedupe_key)` for **any status**, returns
`{ status: "skipped_deduped", error: null }` **without writing** when a row
exists (the original row is the record), and otherwise proceeds through the
hourly ceiling, the transport and `record()`. A failed idempotency read returns
`{ status: "failed", error: "delivery ledger read failed" }` with **no row and
no send**: writing a row would poison the key for every later tick, and
sending would risk the duplicate the read exists to prevent; the next tick
retries, and the warn line carries channel code, rule code and reason (§9.6).
The raise path (`raised: false` → `hasRecordedSkip`) is untouched.

**D4. Both sweep phases select `cleared_at IS NULL AND rule_id IS NOT NULL`;
the escalation phase adds `acknowledged_at IS NULL`.** A rule-less alarm (ADR
0033 decision 5's historical case — the three seed rows) has no condition to
return to normal against and no rule code for a subject line. The rule's
`enabled`/`lifecycle_status` does **not** gate the clear: the alarm is a fact
about the plant and the rule's operator and threshold still define "normal";
a rule that has lost its asset, point, operator or threshold is skipped with
no change. Stale or missing sample → no change (decision 5, ADR 0027).

**D5. `0065`'s backfill runs in the `0046` per-organisation GUC loop, the
index is dropped and re-created after it in the same transaction, and
`alarms_open_rule_idx` is left alone.** `bms_owner` under `FORCE` with no GUC
sees zero `alarms` rows, so a bare `UPDATE` would silently backfill nothing
(`tests/adr-0043-tenant-columns.test.ts:169-178` records the trap, and ADR 0045
§4 forbids the superuser bypass). Index DDL is not subject to RLS. Drizzle runs
the file in one transaction, so no raise can land between `DROP INDEX` and
`CREATE UNIQUE INDEX`; if a database somewhere holds two `cleared_at IS NULL`
rows for one `(asset_id, rule_id)`, the `CREATE` fails loudly, which is the
right outcome. The legacy `(asset_id, rule_key)` partial index has no reader;
dropping it is a scope the row was not given, so the migration header records
it as dead weight for a later sweep.

**D6. Policy shapes.** `alarm_escalation_profiles` and
`alarm_escalation_defaults` carry `organization_id NOT NULL` with an own-column
`tenant_isolation`; `defaults` adds a parent leg on `profile_id`
(`EXISTS (... alarm_escalation_profiles p WHERE p.id = profile_id AND
p.organization_id = current)`), because a foreign key is checked with row
security off (`0056:279-291`) and without the leg a tenant could map its
severity to another tenant's profile. `alarm_escalation_steps` and
`alarm_escalation_step_channels` are junction-shaped (no column; the
`rule_notifications` precedent, `0047:262-272`): steps police through their
profile, step channels through step → profile. The channel leg is **not** in
the policy — `rule_notifications` does not check the channel's organisation
either, because a fleet-wide (`NULL`-org) channel is a legitimate target; the
service gates channel scope in code (D8). FK actions: `steps.profile_id` and
`step_channels.step_id` `ON DELETE CASCADE` (configuration cascades with its
parent); `step_channels.channel_id` and `defaults.profile_id` `NO ACTION`
(deleting a channel a step still names, or a profile a severity still maps
to, fails loudly — `0038`'s reasoning for `rule_notifications.channel_id`).
Uniques: `(organization_id, code)` on profiles, `(profile_id, step_no)` on
steps, PK `(step_id, channel_id)`, PK `(organization_id, severity)`.

**D7. `clearedAt` goes on the details response and a `cleared` arm goes on the
socket event.** Decision 11 says "the alarm response gains `clearedAt`";
`alarmDetailsResponseSchema` is an alarm response and `alarm-details-panel.tsx:229`
prints `Open` for anything unacknowledged, which would be wrong for a cleared
alarm. The sweep runs in the API process beside `AlarmsGateway`, so
`broadcastCleared` is fifteen lines and is what makes the alarms page move
without a reload (it already invalidates on any `alarm` event,
`alarms-page.tsx:98-102`). The owner can strike the broadcast; the plan then
loses only live updates, not correctness.

**D8. Escalation-profile administration uses the channel-admin gate.** Decision
11 says "`configuration` role, like the channel admin"; the operative clause is
"like the channel admin", because a profile binds channels and must not be
editable by someone who cannot manage them. So: `requireMasterDataUser` +
`canManageNotificationChannel(jwt, organizationId)` (`admin`,
`organization_admin` over writable organisations), and every channel id in a
body is checked through `ChannelsService.loadById(jwt, id)`, which throws
`ForbiddenException` outside scope. **Q6 asks the owner to confirm this
reading.**

**D9. One column list for `AlarmListItem`.** Three selects build it today
(`alarms.service.ts:126-142,239-257`, `alarm-raise.service.ts:216-234`), and
the sweep needs a fourth for the broadcast. All four must add `clearedAt`, so
U5 extracts `alarmListItemColumns` and `toAlarmListItem(row)` into
`apps/api/src/alarms/alarm-list-item.ts` and uses it in all four places.

**D10. `channels.service.ts` gains nothing.** It is at 986 lines. The sweep's
"enabled channels by id" read is `loadEnabledChannelsByIds(fleetDb, ids)` in a
new `apps/api/src/notifications/channel-reads.ts`, returning raw rows the
caller maps with the already-public `ChannelsService.toChannelRow`
(`channels.service.ts:906`). `loadForRule` is not moved.

**D11. Severity is validated by the foreign key, not by `VocabulariesModule`.**
`NotificationsModule` declares no `imports` and `alarms.module.ts:17-19`
records that this is what keeps the edge acyclic. `alarm_escalation_defaults
.severity → alarm_severities(code)` is enforced by Postgres; the profiles
service translates the FK constraint name into a 400 the way
`channels.service.ts:327-333` does for `ORGANIZATION_ID_FK`.

**D12. Organisations on the dispatch input follow `F3.7`.** The escalation and
cleared `DispatchInput.organizationId` is the **rule's** organisation
(`rule-actions.ts:55-71`); the alarm writes run under the **alarm's**
organisation (`AlarmRaiser`'s GUC); a rule with no organisation is skipped with
a warn, as `toDispatchInput` returns `null`.

**D13. The escalation catalogue is read every tick, not cached.** Four small
tables, one join, on `fleetDb` with a recorded reason (a system sweep with no
JWT spanning every tenant — the same reason `AlarmEngineService` and
`HealthRollupService` give). Correctness over a 60 s cache: an operator who
maps a severity sees it act on the next tick.

**D14. Message text is string composition, no template.** Subject prefix by
event: `` `escalation ${step} · ${severity}: ${ruleCode}` `` and
`` `cleared · ${severity}: ${ruleCode}` `` (today's subject is
`` `${severity}: ${ruleCode}` ``, `notifications.service.ts:182`). Body:
`` `${alarm.message} — unacknowledged for ${minutes} min (escalation step ${n})` ``
and `` `Cleared: ${alarm.message}` ``.

**D15. Every new request body is `.strict()`.** One producer (the SPA), so
ADR 0029 Amendment 3's question has one answer; recorded by registering each
schema in `openapi-registry.ts` so `strict-body-ledger.spec.ts` walks it.

**D16. `clearHoldSeconds` follows the `F4.46` null discipline.** Nullable in
the schema, `null` round-trips as "the default", `mergeRuleDraft` preserves an
absent key and clears on an explicit `null`, and **no default is substituted
on the write path** — the one default lives where the value is consumed
(`DEFAULT_CLEAR_HOLD_SECONDS` in `alarm-lifecycle.ts`), exactly as
`defaultAlarmSeverity` does for severity.

### Open questions — the owner answers these before the first line of code

**Q1. Do the other "open alarm" readers move to `cleared_at IS NULL`?** Today
`dashboard.service.ts` (KPI `open_alarms`, per-site counts, `alarms_open` /
`alarms_critical`), `map.service.ts` (`open_alarms`, `critical_alarms`) and
`metric-catalog.service.ts` (`activeAlarmWhere`) all mean "not acknowledged".
Under decision 1 an acknowledged alarm is still active and a cleared one is
not. **Recommendation: move all three, as one mechanical unit (U12) in PR 2.**
ADR 0033 decision 1's reason — a rail that never drains — applies to a KPI
tile exactly as it does to a rail, and the metric-catalogue comment at
`:312-318` reserves the change for this column by name. The alternative
(leave them) makes the dashboard say `0 open` while the alarm centre shows the
same alarm as *acknowledged, still breaching*. Cost: three files, their
integration specs, and one comment.

**Q2. Bounds.** `clear_hold_seconds`: recommend `z.coerce.number().int()
.min(1).max(86_400).nullable().optional()` (1 s to 24 h; `0` would make
"hold" meaningless and `null` already means the default). `after_minutes`:
`1..10_080` (a week). Steps per profile: `max(10)`, `step_no` contiguous from
1 and `after_minutes` strictly increasing. Zod only, no `CHECK` — `0062`'s
precedent.

**Q3. The step-idempotency index.** `0065` adds
`notification_deliveries_channel_key_idx ON (channel_id, dedupe_key) WHERE
dedupe_key IS NOT NULL`. **Recommendation: yes, in `0065`, and do not re-open
`F3.46`'s D4** — asking `F3.46` PR 2 to widen `0064` couples two PRs' contents
for a few kilobytes of overlap on a small table. Without it each of the up to
`active-unacked × due steps × channels` reads per tick walks the channel's
ledger through `notification_deliveries_channel_time_idx`'s leading column —
fine today, not at a pilot's churn.

**Q4. A step with zero channels; a profile with zero steps.** Recommendation:
a step with no channel is **refused at the API** (400: "a step with no
channel escalates to nobody"); a profile with no steps is **allowed** (an
operator creates, then adds; mapping it is a harmless no-op).

**Q5. The admin page's field layout.** No mockup; the channels page
(`notification-channels-page.tsx`) is the §5 reference. Recommendation: the
same `MasterDataLayout` — left, the profile list (code, name, step count, and
which severities map to it); right, the form: organisation picker (locked for
a single-grant `organization_admin`, `:112-130`'s pattern), code, name, a step
table (step no. shown, "after (minutes)", a channel checklist built the way
`rule-channels-editor.tsx:160-195` builds its list, add/remove row); below the
list, a *Severity map* card with one `<select>` per live severity from
`GET /vocabularies` (`None` first) and one Save.

**Q6. Confirm D8** — profile administration is gated like the channel admin
(`canManageNotificationChannel`), not like rule authoring
(`assertOperationsWriteRole(user, "configuration")`). Recommendation: D8.

**Q7. A rate-limited step.** When an operator first maps a severity, every
long-standing unacknowledged alarm (118 on the dev database, some days old)
becomes due for every step on the next tick; the hourly ceiling
(`NOTIFY_RATE_LIMIT_PER_HOUR`, 60) sends the first 60 and records the rest as
`skipped_rate_limited` — and under decision 10's literal text those rows are
"in the ledger", so the step never sends. **Recommendation: keep the literal
reading for this row** (never send twice; the deliveries page shows why; an
operator who wants the backlog escalated raises the ceiling or acknowledges)
and record the alternative — retry `skipped_*` rows, recorded once per key in
the `F3.46` shape — as a follow-up row rather than build it here.

**Q8. Does escalation depend on the rule's `action`?** Decision 7 attaches
profiles by severity per organisation and says nothing about `notify` /
`review` / `trace_only`. Recommendation: **escalation ignores `action`** — the
severity map is the organisation's policy, and `F3.7` Q3 made `review` inert
on the raise path only. The alternative (escalate `notify` rules only) is one
predicate if the owner prefers it.

### PR 1 review corrections (security review, 2026-09-06)

- **H1** — on the event path a failed rate-limit read must return `failed`
  **without** `record()`, as D3 already does for the idempotency read; a row
  there poisoned the key for ever.
- **M2** — `dispatchToChannels` drops a channel whose `organizationId` is
  neither `null` nor `input.organizationId`, with one warn (channel code,
  organization ids). U8's profile write path must also mirror
  `setRuleChannels`' pairing refusal; the dispatch guard is the caller-
  independent floor.

## 10. Serial or parallel

**Serial, one worktree, two PRs, twelve units in the order above.** `F3.10` is
not a ⭐ enabler, so fan-out is *permitted*; the dependency graph has three
sibling sets that touch disjoint files — {U5 `alarms/`, U6 `rules/`}, {U7
`alarms/`, U8 `notifications/escalation-*`}, {U9, U10, U11 under `apps/web`,
U12 under `dashboard/`, `map/`, `dashboard-builder/`} — and each could run in
its own worktree after its predecessors merge into the branch. It is not
recommended: every unit in the second and third sets ends in an integration
suite against the **shared** Postgres the `F2.7` session also uses, and two
agents running those concurrently is the `F4.71` collision; and the units are
small enough that a cold agent's re-derivation costs more than the wall-clock
it saves. PR 1's two units are genuine siblings too, but at ~150 lines each
one dispatch after the other is cheaper than two cold starts.

**Dispatch per unit** to `implementer` with the model named in §4 and the
reason in the dispatch: Fable for U1, U2, U3, U7 (seams and the RLS surface);
Opus for U5, U6, U8, U9, U11; Sonnet for U4, U10, U12. Build inline on the
session model where a hand-off is not worth the cold start.
