## 1. Goal

Ship the first Python app, `apps/ml`: a CPU-only batch scorer that wakes hourly, reads `telemetry.point_values_1h` for **real** points only, decides readiness **per point** with step 0's thresholds, runs **one** zero-shot forecasting model (Chronos-2, falling back to Chronos-Bolt) on the points that pass, and inserts `p10/p50/p90` rows into `ml.forecasts` under a new `ml.model_runs` row per organization per run. It connects as `bms_fleet` through `DATABASE_URL_FLEET`, runs no DDL, refuses to start when the `ml` schema version it expects is absent, never rewrites a row, makes no outbound call, and exposes nothing but `GET /health` on loopback. The three `ml.*` tenant tables arrive in one Drizzle migration (`0157`). The row closes when the scorer has written forecasts for the READY WBLDC cold rooms on `bms.demosites.co.in` and nothing for `VAP_Blast_Freezer_2`, the two 33-day VAP rooms, or any simulated asset.

**Out of scope** (each named so nobody builds it by accident):
- The anomaly detector (median/MAD + Isolation Forest) and any write to `ml.anomaly_scores` — `E1.2`. The table is created here because ADR decision 4 says three tables; nothing writes it.
- The NestJS read API (`apps/api/src/ml/`), Zod contracts, any `bms_tenant` grant on `ml.*`, the Drizzle TypeScript mirror of the `ml` tables, and every screen — `E1.4` / `E1.2`. Section 14 names the seams.
- Any alarm, notification or work order from a score (advisory, decision 5). `bms.alarms` is not in the scorer's SQL allowlist, so this is held by the guard test, not by care.
- `scikit-learn`, BatteryML, RUL, covariates, fine-tuning, a GPU, MLflow, a `bms_ml` role (owed, not built), per-organization model choice, a second forecasting cadence.
- Imputation of any kind. Missing hours stay missing (Amendment 1 decision 3).
- Accuracy claims. This row proves the pipeline, not the model.

## 3. Drafter refinements (each is a call inside the ADR; veto at skim)

- **R1 — schema created by the migration, two roles in one file.** `CREATE SCHEMA IF NOT EXISTS ml AUTHORIZATION bms_owner` as `bms_app`, then one `SET ROLE bms_owner … RESET ROLE` bracket for everything else. Header states why.
- **R2 — the schema-version handshake is a comment on the schema, not a fourth table.** `COMMENT ON SCHEMA ml IS 'bms-ml-schema-version=1'`. Decision 4 says three tables; a version table would be a fourth and would need a platform-vocabulary ruling. The comment needs no grant to read (`pg_namespace`/`pg_description` are world-readable), only the owner can change it, and every later migration that changes `ml.*` re-issues it with the next integer. `apps/ml` requires `stored >= EXPECTED_ML_SCHEMA_VERSION` (additive, forward-only migrations keep an older scorer valid on a newer schema; equality would stop the scorer between a migrate and its own redeploy).
- **R3 — plain Postgres tables, no hypertable, no retention job.** "Retention follows `_1h`" means never dropped, so there is no policy to hang on a hypertable; the composite tenant FKs and the PK shapes are ordinary-table idioms; the volume (R9) is ordinary.
- **R4 — `ml.model_runs` is insert-once.** `bms_fleet` gets no `UPDATE`, so a run row is written **after** inference, in the same transaction as its forecasts: both exist or neither does. `finished_at` and `status` are therefore `NOT NULL`. A failed run is one row with `status='failed'`, `rows_written=0`, and a fixed-vocabulary `error_text` (stage + exception class name, never the exception message — a driver message can carry a DSN or row values, §9.6).
- **R5 — "one row per scoring run" is per organization per cycle.** The table carries `organization_id` under RLS, so a cycle that scores two organizations writes two run rows. `organization_id` is never trusted from Python on a score row: `ml.forecasts` rows get it in SQL from `bms.assets`, and two composite FKs — `(asset_id, organization_id) → bms.assets`, `(model_run_id, organization_id) → ml.model_runs` — make a wrong stamp a `23503`, not a leak. `bms_fleet` bypasses RLS, so the FKs are the control.
- **R6 — keys honour "never rewritten".** `ml.forecasts` PK is the ADR's `(asset_id, point_key, horizon_bucket, issued_at)` with `issued_at` = the run's `started_at` instant (not truncated), so a re-run never collides. `ml.anomaly_scores` PK is `(asset_id, bucket, detector, model_run_id)` — the ADR's logical key plus the run, otherwise a re-run for the same bucket could only overwrite (Q4).
- **R7 — forecast targets are a list of `domain/asset_type/point_key`.** Shipped default: `facility/cold_room/cold_room_temp_c` and `electrical/energy_meter/kw` (Q2). Overridable by `ML_FORECAST_TARGETS` (needed anyway to run the container against a test fixture). A PHEWB `kw` point becomes eligible on its own around 2026-12-02 through the per-point gate, with no code change.
- **R8 — per-point eligibility**, in this order, first failure wins: `no_data` → `too_few_days` (`days_with_data < 56`) → `low_coverage` (`< 0.8`, the CLI's full-span formula) → `stale` (newest bucket older than `as_of_hour − 3 h`; a dark device is device health's subject, `F3.16`) → `ready`. Two more refusals happen after the history read: `context_too_sparse` (fewer than `14 × 24 = 336` hours with data inside the context window) and `non_finite_output`. Days and coverage use the CLI's definitions over a 400-day lookback (constant), so Amendment 1's per-room table is the expected output on the demo host: 16 CHK/PORK/GOAT rooms `ready`; the two 33-day VAP rooms and `VAP_Blast_Freezer_2` `too_few_days`. PORK sits at 81.9 %, 1.9 points above the floor — it can drop out, and that is the gate working.
- **R9 — horizon 48 h, 1 h buckets, hourly cadence at HH:05, context 2,016 h.**
  - *Cadence:* hourly is the ADR's (Consequences). HH:05 because `time` is the ingest receive time since `F4.57`, so five minutes past the hour the previous hour is complete; the live branch of `_1h` serves it without waiting for the 2 h `end_offset`.
  - *Horizon:* 48 is inside Chronos-Bolt's native 64 steps and far inside Chronos-2's, so the fallback needs no config change; `limit_prediction_length=True` is passed so an over-long horizon fails loudly rather than degrading. `ML_FORECAST_HORIZON_HOURS` bounds 1–64.
  - *Context:* 2,016 h = 12 whole weeks. It fits Bolt's 2,048 limit and Chronos-2's, keeps weekly alignment, and a 56-day room supplies 1,344 h of it. `ML_CONTEXT_HOURS` bounds 336–2048.
  - *CPU time:* unmeasured. At 21 series × 2,016 points the batch is small; the budget is **one cycle ≤ 300 s at `--cpus 2`**, measured in PR 4 before the model is chosen (Q5).
  - *Volume:* 48 rows × 24 runs = 1,152 rows per point per day. 16 rooms = 18,432 rows/day; with five `kw` meters, 21 points = 24,192 rows/day ≈ 8.8 M rows/year, never dropped (Q7).
- **R10 — gaps are NaN, never a number.** The context is an hourly UTC grid from the first data hour in the window to `as_of_hour − 1 h`; an hour with no `_1h` row is NaN, which both models mask natively. No `interpolate`, `ffill`, `bfill` or `fillna` exists in `apps/ml/src`, held by a static test.
- **R11 — one cycle is one child process.** `serve` is a light parent (scheduler + health, never imports `torch`) that runs `python -m bms_ml run-once` as a subprocess each tick. Reasons: a hard timeout that actually kills a hung inference; the model's memory returns to a 7.6 GiB shared host between cycles; `serve` starts and answers `/health` in a second. The scheduler takes the cycle as an injected callable, so tests never spawn anything.
- **R12 — idempotency across restarts is a ledger read.** Before scoring an organization the scorer asks `ml.model_runs` whether a `succeeded` run with the same `(model_name, model_version, config_hash)` started at or after `as_of_hour`; if so it skips. `run-once --force` skips the check and writes new rows under a new run id — the ADR's re-run. This is a `SELECT` on `ml.model_runs`, covered by the grant and named in the guard's allowlist (Q3).
- **R13 — quantile order is enforced, not assumed.** Per bucket the three values are sorted ascending before the write (monotone rearrangement); a non-finite value refuses the point. The table CHECK rejects any NaN, infinity or crossing that gets past the code.
- **R14 — the service network is `internal: true`.** "A running scorer makes no outbound call" becomes topology: `ml` joins one internal network shared with `postgres` alone, publishes no port, and its health listener binds loopback inside the container.
- **R15 — the Python gate has two halves.** `pyproject.toml` is treated like `package.json` (added dependency entries need an ADR staged in the commit; the tool-time hook denies). `uv.lock` is generated: the tool-time hook denies any `Edit|Write|MultiEdit` of it, and the commit-time check requires an ADR when the lock gains a package **name**. A version-only lock change is not gated, which is the parity with `pnpm-lock.yaml` (ungated today).
- **R16 — the `ml` CI job is path-scoped.** `ci-scope.mjs` gains a second verdict, `ml`, true when any changed path is under `apps/ml/`, `packages/db/drizzle/`, `packages/db/src/ml-data-readiness`, or is `ci.yml` / `ci-scope.mjs` itself, and true on every doubt. A PR that touches none of those does not pay for a Python job.
- **R17 — Python naming.** Modules are `snake_case` because Python imports require it; §4.5's kebab-case rule is a TypeScript rule. Tests are `apps/ml/tests/test_*.py`; §4.6's `.spec`/`.test` split is a Vitest wrapper convention and does not translate. Both are recorded in the `chore(agents):` PR, not silently assumed.
