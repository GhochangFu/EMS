## 1. Goal, and what is out of scope

**Goal.** The stock dashboard-template catalog is keyed by section alone, so its
one `electrical` entry encodes one plant shape — a substation with an incomer, a
transformer and an HT panel. PHE WB's six sites carry a different electrical
train: two multifunction meters (`PHE-MFM-*`) and four pumps (two mains
`PHE-PUMP-M-*`, two chlorine dosing `PHE-PUMP-C-*`) per station, and after
`F3.38` the electrical template resolves for ESKOM while binding nothing at
PHE WB. This row adds a **seventh** stock entry, `electrical-metered-pumping`,
in the same `electrical` section, binding the `meter` and `pump` roles `F3.40`
shipped against the point keys those assets actually register.

Three things must land with it or the entry is decorative:

1. the twelve real-ingest point codes it binds must join a `*_POINT_KEYS` array
   in `packages/shared/src/constants.ts` — they reach `bms.point_keys` today
   only through migration `0057`'s data-derived path and `phe-pilot-seed.ts`'s
   inline registration, **both invisible to the guard that checks the catalog
   against the vocabulary**;
2. `demoRoleForAsset` must write the owner's ruling, so the roles exist to
   match;
3. PHEWB's `seedAssetGroups` pass must move to **after** `seedPheCatalog` in
   `packages/db/src/seed.ts`, because today it runs before and therefore writes
   nothing on a fresh database.

**Explicitly out of scope.**

- **The water/process vocabulary.** `flow_rate`, `ph`, `cod` and
  `dissolved_oxygen` stay on `KEYS_AWAITING_A_VOCABULARY` in
  `tests/f3.38-stock-catalog-vocabulary.test.ts`, and the `stillOutside` clock
  test stays green untouched. That is `E5.1`, blocked on the client.
- **A `dosing-pump` role, and therefore any migration.** The owner ruled both
  pump shapes take the single `pump` code. `ROLE_MIGRATION_RELS` stays at two
  entries and `roles.size === 28` does **not** move. **This row adds no SQL file
  at all.**
- **The three AIRSP/RTU-health codes** (`battery_charge_pct`,
  `network_strength`, `controller_power_status`). They are `environment` domain,
  the two `PHE-AIRSP1051M-*` assets per site stay NULL-roled, and no widget here
  binds them. They keep reaching `bms.point_keys` the way they do today.
- **The six `voltage_v*` codes join the vocabulary but no widget binds them.**
  They are part of the meter's real key set and belong in the array; authoring
  six more chart series is content nobody asked for. Stated in the array
  docblock so a reader does not read the gap as an oversight.
- **`rule-points.ts`, `control-room-bindings.ts` and `contracts/dashboard.ts`
  are not touched.** Each names its arrays explicitly; a seventh array is
  invisible to all three. See §6.
- **No `AGENTS.md` §6 edit and no `BACKLOG` ✅ mirror in this branch** — §9.10,
  separate `chore(agents):` PR.

### 3.1 The resolver decides the widget split — the row's likeliest silent defect

`DashboardTemplatesInstantiateService.outcomeOf`
(`apps/api/src/admin/dashboard-templates/dashboard-templates-instantiate.service.ts`)
tests the outcomes **in this order**:

```
roleCount === 0            -> "bound"
matchedMembers === 0       -> "unresolved"
boundPoints < candidates   -> "truncated"     <-- tested BEFORE partial
!everyBindingWhole         -> "partial"
                           -> "bound"
```

`everyBindingWhole` goes false when `resolvedForThisBinding < members.length`.
For the `pump` role, `breaker_main` matches 4 members and resolves 2. Therefore:

- On a **`value_tile`** (cap 1): matched 4, candidates 2, bound 1 → `1 < 2`
  fires first → **`truncated`**. The report then tells the reader *"the widget
  cannot hold them all — the fix is another widget"*, which is false. The truth
  is that two of the four members carry no such point. **A tile on either binary
  point hides the fact the owner accepted.**
- On a **`chart`** (cap 8): matched 4, candidates 2, bound 2 → not truncated →
  **`partial`**, with `matchedMembers 4 / boundPoints 2` making the size of the
  gap visible in the numbers as well as the word.

**Decision: the two binary pump points go on two separate charts, one binding
each.** Not one chart holding both — that reports matched 4 / bound 4 /
`partial`, where the counts read as complete and only the outcome word
disagrees. Two charts is the honest report, and the docblock says so.

The three `meter` tiles report `truncated` (2 meters into a cap-1 tile). That is
**correct and precedented** — `water-overview`'s `pump-house-tile` already does
exactly this against a role `0051` names as plural — and the remedy the outcome
names ("another widget") is genuinely the right one, which is why
`meter-current-chart` exists. State it; do not design around it.

**Closed contracts respected, each checked rather than assumed:**

- **`widgetIconSchema` is not extended.** It is `alert | clipboard | bolt | drop
  | recycle | gauge` and holds no pump icon. Electrical readings take `bolt`; the

  carry no icon at all.
- **No `unit` on a binary, and none on the power factor.** `breaker_main` and
  `chlorine_pump_on` are on/off, `UnitCode` is `NA`, `unitLabel()` returns null,
  and `UNIT_BY_KEY` spells both `""`. A unit on a binary is precisely the
  silent-wrong class f3.38's last case exists to catch. `commonConfigFields.unit`
  is `.optional()`, so omitting it is legal, not a workaround.
- **`percentUnitOnKw`.** f3.38's regex is
  `/pointKey:\s*"kw"[\s\S]{0,400}?unit:\s*"%"/` over the whole file. The only
  `pointKey: "kw"` in this entry is widget 4, followed within 400 characters by
  `unit: "kW"` and then `unit: "V"`. **This template uses `%` nowhere.** The
  window opened by `electrical-overview`'s `ht-panel-chart` `kw` now runs into
  this entry's opening docblock, which also contains no `unit: "%"`. Checked in
  both directions.
- **Cardinality.** Widgets 1-3 are `value_tile` with 0 bindings + 1 source; 4-6
  are `value_tile` with 1 binding + 0 sources — both satisfy "exactly one
  binding kind". Widget 7 is a `chart` with 3 bindings and 0 sources; 8 and 9
  are charts with 1 binding each. Widget 10 is a `table` with 1 source and 0
  bindings. Tiles use `primary`, charts `series`. Ten widgets is well under
  `MAX_DASHBOARD_WIDGETS = 40`.
- **Grid.** Every widget satisfies `gridX + gridW <= 12`; max `gridH` is 8
  against a ceiling of 24; `grid_y` has no ceiling in `0050`'s CHECK, so
  `THIRD_ROW_Y = 12` is legal.
- **No import from `packages/db`.** The entry names its point keys as string
  literals, exactly as the other six do. The docblock forbids the import because
  a repository constant must not need a database connection to load; f3.38 is
  what checks the literals against the vocabulary at test time.

**Entry docblock must state:**

- **The plant shape it serves:** a village metered-pumping station — two
  multifunction meters and four pumps per site — versus `electrical-overview`'s
  100 kVA substation train of incomer → transformer → HT/LT panel. Two shapes in
  one section is ADR 0051 decision 6's point: *"A new shape is a catalog entry,
  not a per-tenant fork."* Decision 7's per-tenant import copy is the escape
  hatch for a one-off, not the answer to a recurring shape.
- **The partial-resolution consequence, with the mechanism:** one `pump` role
  matches four members carrying two disjoint point sets. **Both binaries are on
  charts and not on tiles, and the reason is `outcomeOf`'s ordering** —

  members carry no such point. Two charts and not one, because one chart binding
  both keys reports 4 matched / 4 bound / `partial`, where the counts read as
  complete.
- **That the three `meter` tiles report `truncated` by design**, because two
  meters cannot fit a cap-1 tile, and that the remedy `truncated` names —
  another widget — is exactly what `meter-current-chart` is. Precedented by
  `water-overview`'s `pump-house-tile`. Amber here is a correct report, not a

## 5. Contract work — none, and here is why that is the answer rather than an omission

The row touches two API responses:
`GET /api/v1/admin/dashboard-templates/stock` and
`POST /api/v1/admin/dashboard-templates/:id/instantiate`. Both are **already**
§4.8 / ADR 0030 compliant — `StockDashboardTemplateDto` is
`z.infer<typeof stockDashboardTemplateDtoSchema>` and the resolution report is
`z.infer` of its own schema. **This row adds a seventh element to an existing
array and changes no schema**, so:

- No new schema is authored, therefore `z.intersection`-versus-`.merge()` and
  `.readonly()` are **N/A**. Said rather than left silent.
- **The new array widens no contract.** `packages/shared/src/contracts/dashboard.ts`
  builds one `z.enum` per **named** array. There is no all-arrays union
  anywhere. A seventh array is invisible there unless someone writes an eighth
  `z.enum`, and this row deliberately does not — nothing validates against it,
  and the runtime gates on a point key are `bms.point_keys` plus
  `assertPointKeysActive`.
- `packages/shared/src/constants.ts` is by its own docblock *"the non-contract
  half of this package"*. `tests/adr-0030-contract-derivation.test.ts` points
  **at** that file as the correct home for an `as const`-derived type.
- The catalog entry is validated by `stockDashboardTemplateDtoSchema.parse` in
  the spec **and** by `as const satisfies readonly StockDashboardTemplateDto[]`
  at compile time, so `pnpm typecheck` refuses a malformed entry before any test
  runs.

**A flattened or hand-widened schema would still typecheck, which is why this
section exists.** There is no schema change to get wrong here; the thing to
refuse is the temptation to add one.
