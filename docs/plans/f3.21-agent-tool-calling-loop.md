## 1. Goal

Replace the single-shot JSON `handleOpenAiTurn` in
`apps/api/src/admin/onboarding/onboarding-chat.service.ts` with a tool-calling
loop that runs inside `POST /api/v1/admin/onboarding/sessions/:id/chat`:
model → tool calls → model, until a final text or a cap (8 tool calls, 45 s).
Tools edit an in-memory copy of the session draft through the existing element
schemas; `propose_commit` records a proposal bound to a SHA-256 of the stored
draft; server code commits only when the next user turn is the exact phrase
`confirm commit` (or the existing Commit button). Each draft write adds a
code-written `action` message (new `role` value in the shared contract),
rendered as a small line in the web chat. OpenAI stays behind a provider port
with no new dependency; a provider error discards the turn's edits and runs
the rule-based path with a one-sentence notice; the 45 s deadline keeps
completed edits and does not fall back. One structured log line per turn, no
text.

**Out of scope** (ADR §Consequences, Deferred): templates (`F3.22`),
point-key/mapping Q&A (`F3.23`), protocol discovery (`F3.24`), per-step
confirm/rollback (`F3.25`), retrieval (`F3.26`), rule-based parity (`F3.27`), a
second provider, streaming, per-organization cost limits, any change to
`handleRuleBasedTurn`'s behaviour, any change to the Excel upload /
`PATCH draft` / `validate` / `commit` routes or the commit transaction, any
migration, the backlog close and the `chore(agents):` sweep (separate PRs).

### Q1 — where the proposal lives, the hash, the clearing rule

- **Store:** top-level `_commitProposal` on `onboarding_sessions.draft`, beside
  `_secrets`: `{ draftHash /* 64 hex */, summary, proposedAt }`. Read back with
  `commitProposalSchema.safeParse` → `null` on any mismatch (fail closed).
- **Not forgeable by a client:** `patchDraftBodySchema` parses through
  `onboardingDraftSchema`, which declares no `_commitProposal` and strips
  unknown keys. **Not forgeable by the model:** tool arguments are parsed with
  element schemas that declare no such key; `propose_commit` takes no
  arguments; `OnboardingService.chat` writes the proposal, only when the loop
  reports one, hashed on the merged draft it is about to store.
- **Hash:** `sha256(canonicalJson(withoutCommitProposal(draft)))`, hex.
  `canonicalJson` sorts object keys (jsonb does not preserve key order).
  `exceedsDepth(draft, MAX_ONBOARDING_DRAFT_DEPTH)` → `null` (never matches).
  `_secrets` is inside the hash on purpose: setting a credential after a
  proposal makes it stale.
- **Clearing:** `mergeDraft` deletes `_commitProposal` on every call; `chat`,
  `patchDraft`, `uploadExcel` and `setCredentials` all write through it. `chat`
  re-attaches only when the turn proposed. Inside the loop, a successful write
  after `propose_commit` drops the pending proposal.
- **Stale:** `draftHash(session.draft) !== proposal.draftHash` →
  `STALE_PROPOSAL_REPLY`, proposal cleared, no commit.

### Q2 — the confirm phrase

`isConfirmCommitPhrase(m) = m.trim().toLowerCase() === "confirm commit"`. Order
in `OnboardingService.chat`: `loadSession` + status gate → `looksLikeCredential`
refusal (ADR 0022) → confirm check → org lookup → `handleTurn`. The confirm path
makes no model call and runs no rule-based turn.

- No proposal → `NO_PROPOSAL_REPLY`; messages stored; draft untouched.
- Stale → `STALE_PROPOSAL_REPLY`; proposal cleared; messages stored.
- Match → `commitService.commit(jwt, sessionId)` (its own RBAC, caps,
  transaction, audit — unchanged). On success, append `user`, `action`
  (`Committed: location <name>, N RTUs, …`) and `assistant`. On
  `BadRequestException`: reply `Commit refused: <message>`, clear the proposal,
  do not rethrow. `ForbiddenException`/`NotFoundException` propagate.

### Q3 — the port, the fake, the thin adapter

```ts
export type LlmToolDefinition = { name: string; description: string; parameters: Record<string, unknown> };
export type LlmToolCall = { id: string; name: string; arguments: string };
export type LlmMessage =
  | { role: "system" | "user" | "assistant"; content: string }
  | { role: "assistant"; content: string | null; toolCalls: LlmToolCall[] }
  | { role: "tool"; toolCallId: string; content: string };
export type LlmReply =
  | { kind: "tool_calls"; calls: LlmToolCall[]; content: string | null }
  | { kind: "final"; text: string };
export interface OnboardingLlmProvider {
  isConfigured(): boolean; // reads process.env.OPENAI_API_KEY on every call
  complete(input: { messages: LlmMessage[]; tools: LlmToolDefinition[]; signal: AbortSignal }): Promise<LlmReply>;
}
export class LlmProviderError extends Error {}
export const ONBOARDING_LLM_PROVIDER = Symbol("ONBOARDING_LLM_PROVIDER");
```

`OpenAiOnboardingProvider.complete`: dynamic `import("openai")`, model
`OPENAI_MODEL ?? "gpt-4o-mini"`, `tool_choice: "auto"`, `{ signal }`; ≥1
`function` tool call → `tool_calls`, else `final` with `content ?? ""`; missing
`choices[0].message` → `LlmProviderError`; SDK rejections rethrown as-is. Under
60 lines. Specs use a `FakeLlmProvider` (scripted replies, records every
`messages` array, `behaviour: "reject"` or `"hang-until-abort"`).
`runAgentTurn` takes `{ maxToolCalls, deadlineMs }` options so a spec can drive
the deadline at 20 ms.

### Q4 — the tool registry (17 tools)

Every write parses its arguments with the matching element schema from
`onboarding.schema.ts`, so the F4.104 length bounds and the F2.23 code class
apply by construction.

| Tool | Args | Effect / result |
|---|---|---|
| `get_draft` | none | `serialiseDraftForPrompt(working)` |
| `list_point_keys` | `search?` (max 64) | catalog, optional substring filter, `echoedItems` + `moreTail` |
| `list_location_types` | none | the active types read once per turn |
| `list_protocols` | none | `getContextForOrganization` → `formatForAssistant` |
| `set_location` | `draftLocationSchema.partial().required({ name })` | `deriveLocationPatch`; inactive `type` → tool error naming the active codes; stored `type` kept when omitted |
| `add_rtu` | `draftRtuSchema.omit({ credentialsSet })` | credential walk → append; `credentialsSet: false` |
| `update_rtu` | `{ index, patch }` | credential walk on `patch.config` → shallow merge; stored `credentialsSet` kept |
| `remove_rtu`, `remove_point_key`, `remove_asset`, `remove_asset_point` | `{ index }` | splice; out of range → tool error |
| `add_point_key` | `draftPointKeySchema` | append |
| `add_asset` | `draftAssetSchema` | append |
| `map_point` | `draftAssetPointSchema` | append |
| `use_existing_point_keys` | `{ value: boolean }` | sets only `onboardingMeta.useExistingPointKeys` |
| `validate_draft` | none | `{ valid, readyToCommit, errors }` |
| `propose_commit` | none | refused unless caps pass and `readyToCommit`; else `pendingProposal = { summary }` |

Rules in code:

- **Credential refusal on `rtus[].config` at any depth** —
  `configCarriesCredential` walks with `rebuildDeep`; key visitor
  `isSecretKey(key)` (exported from `onboarding-redaction.ts`, one list for
  scrub and refusal), leaf visitor `looksLikeCredential(leaf)` for strings.
  Either → the whole call is `CREDENTIAL_TOOL_ERROR`; not applied, stored or
  logged.
- **Marker refusal** — `carriesPromptMarker(args)` → tool error.
- **After each write** — `next = mergeDraftPatch(working, patch)`;
  `draftCountProblem(next)` → tool error, write discarded. Only then
  `working = next`.
- **Forbidden properties** — no tool schema carries `_secrets`,
  `credentialsSet`, `_commitProposal`, `rtuTargetCount`, `importedFromExcel`.
- **Tool errors never throw** — unknown names and bad JSON are tool errors too.
  Results are `cutToBound(JSON.stringify(result), 8_000)` plus a fixed tail.
- **Action lines** are built from validated, applied values, never raw
  arguments or model text: `Set location …`, `Added RTU RTU-1 (mqtt)`,
  `Updated RTU …`, `Removed RTU …`, `Added point key …`, `Added asset … on RTU …`,
  `Mapped s01 → kw on asset …`, `Point keys: using the existing catalog`,
  `Proposed commit: …`, and the `Removed …` forms.

### Q5 — the deadline and the two failure classes

An `AbortController` aborts at `deadlineMs`; its `signal` goes to every
`complete`, and is checked before each model and tool call. In the `catch`:

- `signal.aborted` → `cap_time`: working draft and action lines kept,
  `STOPPED_EARLY_TIME_REPLY`, no fallback.
- otherwise → `provider_error`: `draftPatch {}`, `actionLines []`; the chat
  service runs `handleRuleBasedTurn` and prefixes `AGENT_UNAVAILABLE_NOTICE`.
  With no key, rule-based runs as now with no notice.
- `cap_calls`: the ninth tool call is not made; `STOPPED_EARLY_CALLS_REPLY`;
  edits kept.

### Q6 — prompt bounds

`buildHistory`: last 20 stored messages; drop `system`; `action` → assistant
text; each content `cutToBound(…, 2_000)`. The current message is appended
after the history. The system prompt keeps today's sentences, adds the commit
rule ("You cannot commit. Use propose_commit; the user confirms with the Commit
button or by typing `confirm commit`."), and embeds
`serialiseDraftForPrompt(draft)`.
