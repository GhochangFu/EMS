## 1. Goal

Each organization gets a **"Findings — advisory"** card above the tables on `/forecasts` and `/anomalies`. The card holds fixed fact sentences (F1–F5 for forecasts, A1–A4 for anomalies). Pure functions on the server build them from the same rows the tables show. Above the facts, an **"AI-written · advisory"** paragraph may appear. The existing LLM path writes it from pseudonymised facts only; a pure guard checks it; a new table caches it. Every failure shows facts only, with no banner. Both pages get the shared Organization + Location filter, and the tables obey it. The same card appears on the control-room organization and site pages and as a new `ml_findings` dashboard widget. Every asset a card names is a link to that asset's history page.

**Out of scope** (the amendment's "Not in this amendment"; named so nobody builds it):
- An alarm, notification, work order, report or export from a finding. The copilot chat or a copilot read tool over findings.
- Any threshold or detector change. `ANOMALY_UNUSUAL_SCORE` is imported, never restated, never changed. No accuracy figure.
- Any `apps/ml` change, Python job, queue, worker job, container, dependency or environment variable. No `ml` schema change; the marker stays `bms-ml-schema-version=3`.
- The widget in a stock template or a template surface. A new per-asset forecast or anomaly page.
- A new index (section 2.3 shows none is needed). A new per-organization switch. A background job that pre-writes paragraphs.
- Any edit to `E2.3`'s files (`apps/api/src/alarms/*` root-cause files, `alarm-details-panel.tsx`, `alarm-enrichment-wizard.tsx`, `contracts/alarm-root-cause.ts`). `alarm-location-scope.ts` is used through `AssetFilterScopeService` only.

## 3. Refinements (each is a call inside the amendment; veto at skim)

- **R-a — the paragraph code lives in `apps/api/src/ml-findings/`, with the same `ml` URL prefix.** A second controller file, `@Controller("ml")`, `@Get("findings/paragraph")`. `apps/api/src/ml/` stays read-only and its containment test stays true. The facts (reads, pure builders, the two summary routes) stay in `apps/api/src/ml/`.
- **R-b — the ML routes narrow with `AssetFilterScopeService.narrow`.** One call returns the asset ids; the SQL of the two list reads does not change. A global admin filtered to one organization then reads inside `withTenant` (row security as backstop). The two summary routes sit in their own controller file (`ml-findings.controller.ts`), so `ml.controller.ts` keeps its five routes. Two pinned handler texts change (T1.3).
- **R-c — the paragraph route takes the summary routes' four keys** (`organizationId`, `locationId`, `assetGroupId`, `assetId`) plus `kind`. The two list routes take only `organizationId` and `locationId`, as decision 8 says.
- **R-d — an empty tool list sends no `tools` and no `tool_choice`.** A small change in both adapters; a call with tools is byte-for-byte as before. The demo host is the first live proof.
- **R-e — `ResolvedLlm`'s `ready` arm gains `model: string`.** The resolver already has the value in both branches. Two typed spec fakes gain one field (`onboarding-chat-agent.spec.ts:41`, `copilot-turn.service.spec.ts:178–179`).
- **R-f — `facts_hash` is `varchar(64)` with a CHECK `~ '^[0-9a-f]{64}$'`**, the shape of `ml.model_runs.config_hash`. Same content rule, and the unique index is used for any parameter type.
- **R-g — two link builders in `@bms/shared`, used by the API; a web spec holds them equal to the web's own links.** `forecastFindingHref(assetId, pointKeys)` and `anomalyFindingHref(assetId, lastUnusualMs, asOfMs, pointKeys)` live in `contracts/ml-findings.ts`. The web renders an `href` only when it starts with `/asset-history/`.
- **R-h — the 8-line budget** (section 4.2). F2, F3, F4 are one line per point key. When more than 8 lines exist, lines are kept in this order: F1, F5 (earliest first), F2 of each key, F3 of each key, F4 of each key; the "more point types" line always keeps its place.
- **R-i — no fact names a site as its own word.** An asset is named by `assetLabelOf`, which already holds its RTU or location. So no `[S…]` placeholder and no site link is built. Say so if a line should name the site.
- **R-j — an asset has one reference per card.** On a forecast card its link charts every point key the card names for it (one key gives exactly the Forecasts table's link). On an anomaly card its link is the window around its last unusual hour with that hour's contributing points.
- **R-k — A3 does not repeat an asset that A2 already named.** The A2 line carries both numbers (hours marked by both methods, and all unusual hours).
- **R-l — A4 has two forms only.** The Baseline-only sentence when every unusual hour was marked by Baseline alone; otherwise the mixed sentence.
- **R-m — no paragraph is asked for a card with nothing to say**, and **no row is written when no provider call is made** (switch off, guided mode, cap reached). Turning the switch on then works at once.
- **R-n — the paragraph route never waits for the provider.** A miss starts the call and answers `pending`. The web asks again every 4 s while any card is `pending`, at most 6 times, then waits for the 15-minute refetch. At most 4 calls are in flight in the API process; a fifth key answers `pending` and is started by a later request.
- **R-o — the paragraph route stays in the `read` rate-limit class.** `heavy` (12 a minute) would refuse the page's own polling. The cache and the daily cap bound the provider calls.
- **R-p — fixed reasons.** `rejected`: `number_not_in_facts`, `spelled_number`, `unknown_placeholder`, `missing_weak`, `a2_not_first`, `tone`, `too_long`, `empty`, `line_break`, `url`, `markdown`, `tool_calls`. `failed`: `timeout`, `provider_auth` (401, 403), `provider_quota` (402, 429), `provider_error` (anything else). The log line holds the reason, the kind and the organization id only.
- **R-q — "on screen" means mounted.** The widget asks only while its dashboard tab is selected, and TanStack stops interval refetch in a hidden browser tab. No `IntersectionObserver`.
- **R-r — the empty line follows the filter.** "No forecast points for this organization." with no narrower key; "No forecast points in this selection." when `locationId`, `assetGroupId` or `assetId` is set. The anomaly empty line is the ADR's.
- **R-s — the prompt carries a version** (`FINDINGS_PROMPT_VERSION`), and the hash covers it, so a prompt change never serves an old paragraph.
- **R-t — a module-wiring spec for each new module edge.** CI does not boot the API and a merge deploys by itself.
- **R-u — the widget's two config keys are optional in the schema, with no `.default()`.** The builder always writes both; the renderer reads `show ?? "both"` and `paragraph ?? true`. A `.default()` would make the schema's input and output types differ (the ADR 0030 trap).

## 4. The rules, exactly

### 4.1 Words and formats

- A value: at most 2 decimals, no grouping, ASCII `-` for a negative number, then a space and the unit when the point has one (the Forecasts table's `formatValue`).
- A time: `17 Nov 14:05`, in the zone of the named asset's site (`resolveSiteTimeZone(location, organization).arithmeticZone`). F1's time uses the zone of the newest-issued point's site.
- The forecast window is the 48 whole hours from the current UTC hour. The anomaly window is `anomalyListSinceOf(undefined, now)`: the last 7 days, floored to the hour.
- Point keys are ordered by their number of points (most first), then by key. The first 3 are used.

### 4.2 Forecast facts (per organization; the current run per point, Amendment 3 C3)

| Id | Sentence (one line) |
|---|---|
| F1 | `<n> forecast points, issued at <T>; <s> stale.` (`point` for 1) |
| F2 | `<key>: coldest expected <v> at <A> (<T>); warmest <v> at <A> (<T>).` — `coldest/warmest` when the unit is `°C`, else `lowest/highest` |
| F3 | `<key>: largest change from the last 24 h is <±d> at <A>, at <T>.` — the point whose p50 is furthest from its own mean of the last 24 `_1h` hours. A point with fewer than 12 actual hours is left out; with no point left there is no F3 line for that key |
| F4 | `<key>: least certain is <A>, band <w> wide at <T>.` — the widest p90 − p10 |
| F5 | `Advisory: <A> <key> is expected to go above the limit of rule <R> (<thr>) at <T>.` · `… may go above the limit of rule <R> (<thr>) at <T> (upper band).` · `… is forecast beyond the limit of rule <R> (<thr>) from now.` — `below` and `lower band` for `lt`/`lte` |
| F_MORE | `and <N> more point types.` |
| F_NONE | R-r |

**F5 — the test.** Rules read for the forecast's own `(asset_id, point_key)`: `rule_type = 'threshold'`, `enabled`, `lifecycle_status = 'published'`, `operator` in `gt, gte, lt, lte`, `threshold_value` not null, `condition.window = 'latest'`; a rule whose `condition.unit` is set and differs from the point's unit is skipped. For each rule, over the 48 buckets in order: the first bucket where `compare(p50, operator, threshold)` is true gives *expected* (*from now* when it is bucket 0); else the first bucket where `compare(edge, …)` is true gives *may* (`edge` is p90 for `gt`/`gte`, p10 for `lt`/`lte`); else nothing. Lines are ordered earliest first, then *expected* before *may*, then asset label, then rule name. At most 3 per card. `compare` is imported from `rule-evaluation.ts`; no operator logic is written in SQL.

**The budget.** At most 8 lines (R-h). The card shows them in the table's order.

### 4.3 Anomaly facts (per organization; newest run wins, then the 0.99 line)

| Id | Sentence |
|---|---|
| A1 | `<h> unusual hours in the last 7 days, on <n> of <m> scored assets.` An hour two detectors mark counts once. *Scored assets* have any score row in the window |
| A2 | `Strongest signal: <A> — <b> hours marked by both methods, <h> unusual hours in all; last <T>; points <p1, p2, p3>.` At most 2 lines (most both-hours first); a third asset adds `and <k> more assets with marks from both methods.` to the second line |
| A3 | `<A>: <h> unusual hours, last <T>; points <p1, p2, p3>.` Up to 5 lines, most unusual hours first, then newest, then label; never an A2 asset (R-k); fewer when the 8-line budget is short |
| A4 | The amendment's two fixed sentences (R-l). Present whenever A1's `h` is above 0 |
| A_NONE | `No unusual hours in the last 7 days on <m> scored assets.` |

*Points* are the contributing points of the asset's last unusual hour, the detectors' lists joined in detector order, without repeats; the line shows the first 3, the link charts all of them.

### 4.4 Pseudonymise, hash, guard

- **Pseudonymise** (pure). Each fact line becomes text: an asset reference becomes `[A<n>]` (the card's own `A1…`), each rule name `[R<n>]`, each formatted time `[T<n>]`, numbered by first appearance. Everything else is the fixed sentence, numbers, units and point keys. A point key that does not match `^[A-Za-z0-9_.-]{1,128}$`, or a unit longer than 32 characters or holding `[`, `]` or a line break, stops the paragraph for that card (`none`, no call): free text must not leave the host.
- **Canonical text** = `v<FINDINGS_PROMPT_VERSION>\n<kind>\n` + the pseudonymised lines joined by `\n`. `facts_hash` = SHA-256 of it, hex. The organization id is part of the cache key, not of the text.
- **The prompt.** One fixed system message (the rules of decision 5 in plain words: digits only, placeholders copied as written, one paragraph, at most 600 characters, no advice beyond the facts, the word "weak" for Baseline-only marks, the strongest signal first). One user message: the kind and the pseudonymised lines. No organization name, no id, no user.
- **`checkFindingsParagraph(text, facts)`** returns `{ ok: true }` or `{ ok: false, reason }` (R-p), checked in this order: `empty`; `line_break` (`\r` or `\n`); `too_long` (over 600); `url` (`https?://` or `www.`); `markdown` (any of `*`, `` ` ``, `#`, `|`, `<`, `>`, `](`); `unknown_placeholder` (any `[…]` token that was not sent); `spelled_number` (whole words, case-folded: *one*…*twenty*, *dozen*, *half*, *twice*, *double*, *triple*, *percent*); `number_not_in_facts` (after the placeholders are removed and `−` is made `-`, every `-?\d+(\.\d+)?%?` token must equal, as a string, a token the same expression finds in the facts text that was sent); `missing_weak` (the facts hold A4's Baseline-only sentence and the text has no word `weak`); `a2_not_first` (the facts hold an A2 line and the first asset placeholder in the text is not an A2 asset's, or there is none); `tone` (*emergency, danger, dangerous, urgent, immediately, failure, failed, fault, faulty, broken, critical*).
- **Put back** (pure): the stored placeholder text is split on `\[(A|R|T)\d+\]`. `[A<n>]` becomes `{ assetRef }`; `[R<n>]` and `[T<n>]` become their text.

### 4.5 The paragraph flow, per card

1. The facts are computed again for the caller (never a hash from the browser).
2. A card with only `F_NONE` or `A_NONE`, or a failed sendable-token check → `none`.
3. Read the row `(organization, kind, hash)` inside `withTenant(organization)`. `ok` → `ok` with segments. `rejected` → `none`. `failed` younger than 30 minutes → `none`.
4. No row, or a `failed` row 30 minutes old: the switch (`organizationSwitchOn`) off → `none`; `resolveForOrganization` is `guided` → `none`; the day's count at or over 200 → `none`. None of these writes a row.
5. A call already in flight for the key, or 4 calls in flight → `pending`. Otherwise start the call and answer `pending`.
6. The call: `provider.complete({ messages, tools: [], signal: AbortSignal.timeout(15_000) })`. A `tool_calls` reply, a guard refusal → `rejected` with its reason. A timeout or any throw → `failed` with its reason (from `errorFacts`' status; never the message).
7. One `withTenant(organization)` transaction: delete the old `failed` row if this was a retry; delete the organization's rows older than 14 days; `INSERT … ON CONFLICT DO NOTHING`. Then one log line (R-p).

- **AGENTS.md changes only in the `chore(agents):` PR.**
- **Simple English** in every user-facing string, comment and PR text.

## 17. Not planned (a choice, not an oversight)

- **No index and no rewrite for the forecast run chain.** It is `E1.4a`'s read; at the demo's 16 points it costs about 50 ms (2.3). At hundreds of forecast points per organization both `GET /ml/forecasts` and the summary slow down together. That needs its own row.
- **No short-lived memo of the facts** between the summary route and the paragraph route. The paragraph route recomputes them, as the amendment rules.
- **No cap on forecast points per card.** The read is bounded by the caller's scope, as the list is.
- **No `e2e` label.** The label costs about 4 billed minutes; the module-wiring specs hold the DI claims. Say so if you want the boot proof before a merge.
- **No site name in a fact line, no `[S…]` placeholder** (R-i).
- **No admin screen that says why a paragraph is missing.** The amendment points to the organization's LLM settings page.
- **No guard against a reader who walks many filter values.** Each new scope is a new key and one call; the daily cap is the bound. A reader could use up an organization's 200 for the day; the facts stay. The security review reads this.
- **No retry inside one call.** A `failed` row is tried again after 30 minutes by a later view.
