# Lane D — `F2.15` + `F2.20` + `F2.19`: the tab family

*Plan written 2026-09-04 by `plan-architect` (Fable 5.1) from the three backlog
rows and [ADR 0038 Amendment 5](../adr/0038-template-authoring-ui.md), accepted
by the repository owner the same day (PR #305, squash `53f9468`). One pull
request — the owner ruled "four PRs by lane" on 2026-09-04 and this is lane D.
Branch `feat/F2.15-F2.20-F2.19-tab-family`.*

## 1. Goal

A stock catalog entry becomes fully readable, and a draft fully authorable, on
the tab family both the authoring page and the `F2.14` viewer share.

- **`F2.15`** — a Tier column on `PointsTab`: a `<select>` over `core` /
  `extended` / `manual` on a draft, read-only text on a frozen version. Plus the
  row's second deliverable, an `editable` gate on `details-tab.tsx`'s
  `<form onSubmit>`.
- **`F2.20`** — the alarm philosophy `<details>` renders `open` on a read-only
  template and stays collapsed on an editable one unless the row holds a
  philosophy problem.
- **`F2.19`** — `maintenance` becomes the seventh tab, read-only on the viewer
  and editable on a draft.

Build order is fixed: `F2.15` → `F2.20` → `F2.19`. `F2.19` rewrites
`template-tabs.ts` and the text-scanning guard the other two sit beside.

## 2. Out of scope

- Any file under `apps/api` or `packages/`. Both write targets have been
  accepted since before this branch.
- **Tier semantics.** Nothing at runtime may branch on `meta.tier` — no sort,
  filter, default, validation or save rule. Amendment 5 forbids it.
- Materialising `content.maintenance` into `bms.maintenance_task_templates`, and
  any link to `maintenance-schedules-panel.tsx`'s schedule templates.
- `health` and `optimisation` — no eighth tab.
- Deleting the `<details>` for `F2.20`, and the two shapes the owner rejected
  (an expand-all control, a populated `<summary>` line).
- Editing dated records: `template-tab-guard.ts:5,12`,
  `template-authoring-access.spec.ts:118`, `vitest.config.ts:363`, anything
  under `docs/plans/`, and Amendment 4's own text.

## 3. Serial or parallel

Serial, one branch, eight consecutive `implementer` units. `F2.15` and `F2.20`
touch disjoint files, but each is one small unit and both would have to merge
into the same branch `F2.19` rewrites the registry on. No unit is a ⭐ enabler.

## 4. The decisions this plan owns

### 4.1 `F2.19` builds the **editable** Maintenance tab

**This is the question Amendment 5 Part B routed here.** Its words:

> Minimum scope is read-only. A read-only Maintenance tab on the `F2.14` viewer
> is what discharges the review problem, and it is the floor this amendment
> sets. Whether the draft editor gains an editable tab in the same row is
> `F2.19`'s design question at its plan gate, not a ruling taken here.

**Ruled by the repository owner on 2026-09-04, at this plan's gate: build the
editable tab.** The owner was offered the read-only floor as an explicit
alternative — with the note that the plan is structured so the floor lands as
its own commit first, making the smaller choice cheap to take — and chose
editable. Four reasons carried it:

1. **The family has one contract, and it is `editable`.** `TemplateTabBody`
   passes that prop to every tab; on a draft the six existing tabs edit, and on
   a frozen version or the viewer they render disabled with no Save. A seventh
   tab that ignored the prop would be the one tab on an editable draft that does
   not edit, and a reader has no way to tell that from a broken tab. Decision 3's
   lifecycle rule is applied *unchanged* only if the tab honours `editable`.
2. **The read-only rendering IS the editable rendering with `disabled`.** That is
   how all six work, and it is what the viewer's enabled-field sweep is built to
   check. So the floor and the editable tab share the component and the seed; the
   marginal cost is one `lib/` form module with three precedents to copy.
3. **The same redline argument Part A already won.** A read-only tab means a
   client's redline on a plan is applied by an engineer editing catalog source;
   an editable tab means an author applies it on a draft. Amendment 5 accepted
   that argument for the tier, and `F2.19`'s row says the plans are the least
   verified content in the catalog.
4. **The write target is already validated.** `asset-templates-content.schema.ts`
   refuses anything the form could get wrong, so a form defect costs a 400 with
   the service's own sentence, never a bad row.

**What it costs.** One extra `lib/` module in the coverage denominator, one more
arm on `TemplateContentPatch` (no code — the array branch already handles it),
and the dirty path, which must be proved twice because the 42-pair count proves
nothing about this tab. The one real trap is comparator asymmetry — see §5.

### 4.2 `F2.15` — the tier is an editable select, and where the column sits

**Ruled by the owner on 2026-09-04, before the plan was written.** The owner was
offered a read-only display column as the cheaper option — the `F2.15` row
itself says "a read-only column touches neither" ADR — and chose the select,
which is why ADR 0038 Amendment 5 Part A exists at all.

The column sits **after Kind**: the tier is provenance about the point, like
`kind`, not about its wiring. The select offers `no tier` as a real option, not
a convenience — `template_points.meta` defaults to `{}`, the wire shape for that
is to omit `meta`, and a select that could not express the stored state would
silently assign a tier on the author's next save. On a read-only render the cell
is **text**, not a disabled select, because Amendment 5 says "read-only text".

### 4.3 `F2.20` — `open` by default on a read-only template

**Ruled by the owner on 2026-09-04.** Three shapes were offered; the owner chose
`open` by default when read-only and rejected an expand-all control and a
populated `<summary>` line. One expression:
`open={!editable || rowProblems.some(...)}`. Read-only covers the viewer, a
published or archived version, and a draft seen by a role that cannot author —
every case where there is no Save to protect.

### 4.4 The three label maps move to `lib/`

`maintenance-schedules-panel.tsx` holds the human labels for every category,
generation mode and priority. The Maintenance tab needs the same 23 strings, and
two copies of one vocabulary's labels is the drift this repository's own
comments warn against. They move to `apps/web/src/lib/maintenance-labels.ts`
with their `Record<Enum, string>` types intact, so a 15th category added to the
schema fails `pnpm typecheck` in the label file rather than rendering a raw code.
The panel's change is an import swap; no behaviour moves.

## 5. The traps, and how each is caught

- **`F2.15`'s submit-gate test is vacuous by default.** `details-tab.tsx` calls
  `mutate()` behind `!blocked && patch`, and on a clean form `patch` is `null`,
  so a naive "a read-only render cannot submit" case passes whether or not the
  gate exists. The case must dirty the form **while editable**, re-render
  read-only, assert no write, then re-enable and assert exactly one write.
- **The comparator.** A stored plan that omits every defaulted field must not
  read as dirty on an untouched open, or every tab click prompts about unsaved
  changes with no way out. Both sides normalise through the same payload builder.
- **The registry scan can go vacuous.** Its docblock warns that a broken
  extraction regex returns nothing and reads as compliance. The build re-runs the
  documented recipe and then mutates one entry's `id:` key to prove the scan goes
  red.
- **The third count gate is arithmetic.** `template-tab-guard.spec.ts` asserts
  the number of ordered tab pairs — `n(n-1)`, so six give 30 and seven give 42.
  Nothing in that file says "six", so a search for the count does not find it.
- **The form's bounds are a hand copy** of the API schema, because `apps/web`
  cannot import `apps/api` — the same reason `template-content-merge.ts` copies
  `WRITABLE_KEYS`.

## 7. Corrections the build made to this plan

1. **There is no resolver-fallback edit.** The plan expected an analogue of
   Amendment 4's third loop edit. `template-tabs.spec.ts:90`'s fallback list
   never contained `maintenance`, so nothing there changes. Measured, not
   assumed.
2. **`Field` puts the error text inside the `<label>`**, so a failing field's
   accessible name is not an exact string. The Maintenance tab's spec matches
   `/^Interval days/` rather than an equality.
3. **The five seeded defaults are visible in a `content` diff.**
   `maintenanceRowsFrom` seeds what the API would have defaulted, so a save
   writes `estimatedMinutes: 60`, `category: "preventive"`,
   `generationMode: "calendar"`, `priority: "medium"` and
   `safetyCritical: false` onto plans stored without them. Unchanged in effect,
   visible in a diff. `intervalDays` is deliberately not seeded — it has no
   default and is required.
4. **The copy was cross-checked against the schema it copies**, because every
   jsdom case mocks the save and the server's real `.strict()` had never seen a
   payload this form builds. Every boundary matched: `intervalDays` 1 and 730,
   `estimatedMinutes` 5 and 1440, title 3 and 255, all optionals at maximum
   length, 200 plans accepted and 201 refused, and emptied optionals omitted
   rather than sent as an empty string. **Nothing gates that copy permanently** —
   a follow-up row owes the invariant.
