## 1. Goal

Give the fleet-wide point-key catalog a per-code flag that names the key trend points of each segment, give each organization an optional per-segment override list, and expose one resolution rule — *an organization with rows for a segment uses them; otherwise the catalog default applies* — through an API read that F4.301 and F4.302 consume per site, plus an admin screen where a global admin or an organization admin edits the list for an organization. A segment is an `asset_domains.code` row (data, never code), so a segment the catalog gains later appears with no release.

**Out of scope.** No telemetry read (the strip and the Trends tab are F4.301/F4.302). No tab-to-segment map (F4.301 owns it; the DTO returns every active segment so the consumer can choose). No per-asset join (the consumer joins `asset_points.point_key` to the effective list for the asset's domain). No location-level override (design: organization). No new `ups` segment (see open question 1). No web client for the site read (one line, F4.301 adds it when it has a caller).

## 2. Calls this plan makes (the ADR 0108 decision for F4.300 records them)

| # | Call | Why |
|---|------|-----|
| C1 | **Segment = `bms.asset_domains.code`.** The override's `domain` column is an FK to it. | The only FK-backed open vocabulary (ADR 0031 A1, AGENTS §4.8 "open vocabulary → table with FK"). `point_keys.domain` is free text but agrees by seed convention (7 of 7 today); a static test pins that every `keysForDomain` domain is a seeded `asset_domains` code. |
| C2 | **Catalog flag is tri-state: `trend_default boolean NULL`.** `NULL` = undecided (the seed may fill it), `true`/`false` = decided by seed or admin. The seed writes only `WHERE trend_default IS NULL`. The DTO exposes `trendDefault: boolean` (`IS TRUE`). | A `NOT NULL DEFAULT false` column cannot tell "admin said no" from "nobody said", so every `compose up` would revert an admin's `false` — the exact class `headline_rank IS NULL` (F3.68 OQ3) and `COALESCE(unit)` (F3.39) exist to prevent. |
| C3 | **Override is replace-all per `(organization, segment)`.** `PUT …/trend-points/:domain { pointKeys: [...] }` deletes the segment's rows and inserts the body in order; `pointKeys: []` deletes them, which is "back to the catalog default". No `DELETE` route. | One predicate implements the fallback (`EXISTS` row → override). Deltas need tombstones and a merge. |
| C4 | **Cap 12 codes per segment** (`TREND_POINTS_PER_SEGMENT_MAX`), no duplicates, each code in `CATALOG_CODE_PATTERN`. Order is the body order (`sort_order` = index). | Bound every list; the strip height is F4.301's, but an unbounded body is a server cost now. |
| C5 | **Catalog flag write = global `admin` only** through the existing `PATCH /admin/point-keys/:id` (body gains `trendDefault`), plus a `BEFORE INSERT` trigger that refuses a `bms_tenant` insert with `trend_default IS NOT NULL` (the 0084 shape, a second function — 0084 is frozen). Tri-state: a tenant never sets the catalog flag, neither `true` nor `false` (a tenant `false` would be a decided value the seed never fills); an organization's choice goes in `bms.org_trend_points` (ADR 0108 §3.1). **INSERT is the only path the trigger needs to cover:** `0059_tenant_cannot_edit_point_keys.sql:51` revokes `UPDATE, DELETE ON bms.point_keys FROM bms_tenant` and its `DO $$` proof (`:65-76`) asserts the tenant keeps exactly `SELECT` and `INSERT`, so a tenant `UPDATE … SET trend_default` and an `INSERT … ON CONFLICT DO UPDATE` are refused by the privilege system before any trigger runs (0084's header states the same for `headline_rank`). U2's integration test pins this with an adjacent case. | `headline_rank` precedent (ADR 0076 d7); the tenant pool holds INSERT for onboarding. |
| C6 | **Override write gate = `isOrganizationLevelAdmin(jwt, organizationId)`**, after `requireMasterDataUser`. Audited via `MasterDataAuditService` with `action: "master.organization.trend_points.set"`, `entityType: "org_trend_points"`, `entityId: organizationId`, `organizationId` set. | Design: org admins for their organization, global admins. The move-location precedent (ADR 0098 d12) says why not `canManageOrganization`. |
| C7 | **Reads.** Site read `GET /control-room/sites/:locationId/trend-points` uses the `SiteControlRoomViewService.resolve` readable rule (global scope or the site in `scope.locations`; else 404). Admin read `GET /admin/organizations/:organizationId/trend-points` uses the C6 gate. Both run on `fleetDb` with `organization_id` in the `WHERE` (ADR 0043 A3). | Design: everyone who reads the site sees the effective list. |
| C8 | **A deactivated point key is hidden from the effective list, its override row is kept.** Reactivation restores it. The admin DTO carries `active` so the page can mark it. | Catalog rule: retire with `active=false`, never DELETE. |
| C9 | **FKs carry no `ON DELETE` clause** (`domain`, `point_key`, `updated_by`). | The `asset_domains` rule: a delete that plant still references fails loudly. Both targets are retire-only vocabularies. |
| C10 | **Admin screen = a new "Trend Points" tab under Reference Data, predicate `canEditTrendPoints` = `admin \|\| organization_admin`.** | Its own predicate (the `canManageNotificationChannels` rule in `admin-access.ts`). |
| C11 | **No `trend_rank` column.** The catalog default list orders by `headline_rank NULLS LAST, code`; an organization list orders by its own `sort_order`. ADR 0108 §3.1 records this and closes its former open item. | `headline_rank` already orders the same codes on the generated site card (ADR 0076); a second rank column would be a second ordering of one vocabulary that an admin must keep in step. |
