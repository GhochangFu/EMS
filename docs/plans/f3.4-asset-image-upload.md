# F3.4 — Image upload API + asset linkage (ADR 0066 decision 7)

**ADR:** 0066 decision 7 (and 4, 11, Amendment 1 D, Amendment 2 L-1), accepted 2026-09-15; the plan rulings below become **ADR 0066 Amendment 3**.
**Branch:** `feat/F3.4-asset-images-write-path` off `main@182fe4e6`.
**Planned:** 2026-09-16 on Fable (`plan-architect`); the three owner questions in §2 were ruled the same day.
**Serial or parallel:** **Serial, one branch, no worktrees.** F3.4 is not a ⭐ enabler, but its units chain: U3 exports the DTO mapper U4 and U5 consume; U7 (web client + gallery) is consumed by U8 and U9. U8 (admin panel) and U9 (reader gallery) are the only genuinely independent siblings — different pages, different components — but each is ~150 lines, and a cold worktree start costs more than it saves (`build-operating-model.md` §3 "cost reality"). Build hands-on, one pinned `implementer` per unit.

## 0. Goal and out of scope

**Goal.** Give `bms.asset_images` a producer and a UI: `POST /api/v1/assets/:assetId/images` (multipart, one file plus an optional caption, gated by `canManageAsset`, server-generated key, sniffed content type, server-computed `sha256`/`byte_size`, per-asset count cap, audited), `DELETE /api/v1/assets/:assetId/images/:imageId` (row in a tenant transaction, commit, then the object; an orphan is tolerated and warned), an admin "Images" side panel on `/admin/assets` (gallery + upload + delete), a read-only gallery for every `canReadAsset` reader on the location dashboard's asset table, and the F4.145 invariant row.

**Out of scope (do not build):** thumbnails/`sharp` (ADR Dependencies); presigned URLs (decision 6); `If-None-Match`/304 on the content route (the F3.3 docblock names it as a *possible* follow-up — not asked for, YAGNI); the orphan sweep (decision 11); a scoped MinIO service key (F4.144); an image on the mockups' SLD/CRAC pages; any `AGENTS.md`/`docs/roadmap.md` edit (separate `chore(agents):` PR, §9.10); any migration — `0072` is frozen and sufficient.

## 2. Rulings (routine, under the ADR) and the owner's three rulings

| # | Question | Ruling |
|---|---|---|
| R-1 | Content-type trust | **Sniff, and require agreement.** `sniffImageContentType(buffer)` returns `image/jpeg` on `FF D8 FF`, `image/png` on `89 50 4E 47 0D 0A 1A 0A`, `image/webp` on `RIFF????WEBP` (bytes 0-3 and 8-11), else `null`; a buffer under 12 bytes is `null`. The declared multer `mimetype` is parsed through `assetImageContentTypeSchema` (400 "Only JPEG, PNG or WebP images are accepted" — the declared string is client text and is not echoed); a `null` sniff is 400 "The file is not a JPEG, PNG or WebP image"; sniff ≠ declared is 400 "The file's content does not match its declared type". The **sniffed** type is stored. Routine: decision 7 makes the vocabulary a security allowlist, and an allowlist checked against a client-supplied label is not checked. |
| R-2 | put vs insert order | **Put the object first, then the row.** Decision 4 makes the orphan object the tolerable failure ("costs storage and serves nothing") and the object-less row the bad one (404 that lies, a warn on every read); decision 11 already accepts orphans. The tenant transaction never holds a connection across an S3 call (the F3.3 read-path rule). On any failure after `putObject`, `deleteObject` runs best-effort; a failed cleanup is one `warn` naming the image id and `err.name`. |
| R-3 | Per-asset count cap | **`MAX_ASSET_IMAGES_PER_ASSET = 20`** (owner, Q-3), in `packages/shared/src/contracts/asset-images.ts` (annotated `: number`). Exceeding it answers **409 Conflict** "This asset already has 20 images; delete one before uploading another" — it is a state of the resource, not a malformed body (the F4.103 `.max()` caps are 400 because they bound a body). Checked twice: a cheap fleet-pool pre-check before the put (so the common refusal costs no upload), and the authoritative count inside the tenant transaction after `SELECT id FROM bms.assets WHERE id = $1 FOR UPDATE` (serialises concurrent uploads for one asset; the asset row is visible under the GUC). |
| R-4 | sha256 / byte_size | Server-side from `file.buffer`: `createHash("sha256")`, `buffer.length`. `size`/`Content-Length` headers are never read. An empty buffer is 400 "Image file is required" (the `requireFile` precedent). A buffer over `MAX_ASSET_IMAGE_BYTES` is re-checked in the service (413, `PayloadTooLargeException`) — defence in depth, the F4.102 docblock's "each parser keeps its own byte cap". |
| R-5 | Amendment 2 L-1 re-check | **Not needed here, and the docblock says why.** L-1 asks a *grant-write* endpoint to re-check a location's organization before inserting into `user_location_access`. F3.4 writes `asset_images`, never a grant. Its tenant GUC and the row's `organization_id` both come from **the asset's own row** (`assets.organization_id`, NOT NULL), so even under a cross-organization grant the row is stamped consistently with its parent and `0072`'s `WITH CHECK` holds; the exposure L-1 names is the same one every existing asset write carries through `canManageAsset`, and it is the grant data's, not this row's. |
| R-6 | RLS path for the insert | `withTenant(tenantDb, assetOrganizationId, tx => …)` with the org resolved from `bms.assets` on `fleetDb` (the `resolveAssetOrg` shape, a private copy). Inside: `FOR UPDATE` on the asset (404 if it vanished), count, insert with `organizationId: assetOrganizationId`, `audit.write({…, organizationId}, tx)`. The integration spec proves the negative: the same insert stamped with organization B under GUC A is `42501`. Constructor order `(tenantDb, fleetDb, …)` pinned in `fleet-read-wiring.spec.ts`. |
| R-7 | UI states and error words | Both surfaces: loading "Loading images...", error "Images unavailable." (non-503) or the API's own 503 sentence via `apiErrorMessage` ("Object storage is not configured …" / "Object storage is unreachable"), empty "No images for this asset yet." Upload: 413 → "Image is too large — the limit is 10 MB." (figure computed from `MAX_ASSET_IMAGE_BYTES`); every other status → `apiErrorMessage(body)` with fallback `Upload failed (<status>).`. Client-side pre-checks disable Upload **and say why** (type, size, cap reached, no file chosen). Delete has no confirm dialog (the Deactivate precedent on the same page). |
| R-8 | OpenAPI | Nothing registered; one docblock sentence in `openapi-registry.ts` naming `AssetImagesWriteController_upload` as the sixth multipart absence. Delete: no body, no query — absent like `EscalationProfilesController_remove`. |
| R-9 | Two controllers, one prefix | `AssetImagesWriteController` (`@Controller("assets/:assetId/images")`) in its own file, so F3.3's controller scan stays untouched and the F4.102 scan gates one clean file. |
