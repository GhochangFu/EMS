## 3. Design decisions settled at this gate

1. **The tariff is resolved per asset in the read's scope, at the nearest scope, through the shipped resolver** (§10 Q4). Both reads already group `point_values_*` by `asset_id` in their `per` CTE; a second statement over the same CTE returns `(asset_id, kwh, organization_id, currency)` per asset with energy in the window (`JOIN bms.assets a JOIN bms.organizations o`, on the fleet pool both services already run on). `CalcParametersService.resolveForAssets(assetIds.map(id => ({ assetId: id, key: "energy_tariff_per_kwh" })), end)` gives each asset its nearest-scope tariff — organization row for everyone, location row where one exists, asset row where one exists — which *contains* decision 7's "organization scope, location scope where location-scoped" and adds nothing the store cannot already express. `end` is `new Date()` for the dashboard (the window ends now) and `range.end` (`endDate T23:59:59.999Z`) for the report — decision 7's "the query's end instant".
2. **Fail closed, three ways, in one pure function.** `energyCost(rows, tariffs)` in `apps/api/src/telemetry/energy-cost.ts` returns `{ indicativeCost, tariffPerKwh, currency }`: `currency` is the one distinct currency of the rows, else `null`; `tariffPerKwh` is the one distinct resolved tariff when **every** row resolved, else `null`; `indicativeCost` is `Σ kwh_i × tariff_i` rounded to 2 dp when every row resolved **and** `currency` is non-null, else `null`. No row (empty scope) → all `null`. A sum across two currencies is not a number, and a partial sum understates — both are decision 2's rule at the read ("`null`, not `0`"). **Consequence, measured:** `admin@bms.local`'s fleet-wide Energy Centre spans `ESKOM` (ZAR) and `PHEWB` (INR) — 100 and 50 assets; 7,256 `kw` rows in the trailing 24 h were all PHEWB's at measurement, the Eskom sim last wrote 2026-09-17 05:41Z — so a global admin sees the dash whenever both organizations have energy in the window. That is correct and the §4.6 claim uses `wc-admin@bms.local` (location-scoped, ESKOM). No default value anywhere: `tests/adr-0070` part (g) scans `energy-cost.ts` for `COALESCE(`, `?? 0`, `?? 1`.
3. **The DTO change, made once.** `energyCentreSummarySchema` (`contracts/operations.ts:16`) drops `indicativeCostZar`/`tariffZarPerKwh` and gains `indicativeCost: z.number().nullable()`, `tariffPerKwh: z.number().nullable()`, `currency: z.string().nullable()` — three plain keys on the existing `z.object`, **no `z.intersection`, no `.merge()`, no `.readonly()`** (`tests/adr-0030-contract-derivation.test.ts` scans for the flatteners). `energyReportPreviewSchema.summary` reuses it, so the CSV/XLSX export takes the change with no second edit. `adminOrganizationDtoSchema` (`contracts/admin.ts:21`) gains `currency: z.string()` — one line, **997 → 998 of the 1000 cap**.
4. **`DashboardModule` and `ReportsModule` import `CalcModule`**, which already exports `CalcParametersService` (`calc.module.ts:115`). The constructors take `@Inject(CalcParametersService) private readonly parameters: Pick<CalcParametersService, "resolveForAssets">`, so the seven existing `new DashboardService(pool)` / `new ReportsService(pool)` spec sites pass a two-line fake and the two new integration specs pass the real service. `CalcModule` imports only `TelemetryModule`; no cycle. The worker root (`worker.module.ts`) imports neither module — unaffected. **A green build is not a DI gate**: the API is booted in U14.
5. **Money points carry `unit: ""`** (§10 Q8) — the same spelling `pf`, `pue` and every `0/1` code use for "no unit"; a template point's unit is one static string and the currency is the organization's, shown by the tile from `organizations.currency`. The label says what it is: "Energy cost (organization currency) per hour". Rates and quantities keep their physical unit: `kg/h`, `kg`, `%`, `h`, `KL`, `kWh/kWp/day`.
6. **Every windowed formula is self-contained** — the window read is written inline in each point rather than read from a derived sibling. `E4.1b` design decision 9 dedupes reads per sweep by `inputKey(owner, windowKey)`, so three feeder formulas over `delta({kwh_total}, today)` cost one read per asset per tick, and no point inherits a sibling's `window_empty` as a `stale_input`. (`pue = {site_kw} / {it_kw}` stays as it is — it is `F2.8`'s and not touched.)
7. **The fourteen formulas** (§10 Q3, Q5, Q10, Q11), each ≤ 2 window reads and ≤ 2 parameter references, every one parsing under `v3` (U13's part (a′) is the gate, the class specs pin the text):

   `electrical-feeder` (**v2 → v3**, `sortOrder` 36–40, `calcTrigger: "scheduled"`, `calcIntervalSeconds: 60`, `formulaDialect: CALC_DIALECT_V3`, `minCoverageRatio` at `derived()`'s `null`):
   - `energy_cost_per_h` = `{kw} * $energy_tariff_per_kwh` — `""`.
   - `co2_kg_per_h` = `{kw} * $grid_carbon_factor_kgco2_per_kwh` — `kg/h`.
   - `energy_cost_today` = `delta({kwh_total}, today) * $energy_tariff_per_kwh` — `""`.
   - `co2_kg_today` = `delta({kwh_total}, today) * $grid_carbon_factor_kgco2_per_kwh` — `kg`.
   - `energy_saving_vs_baseline_pct` = `(1 - delta({kwh_total}, today) / ($energy_baseline_kwh_per_day * hours(today) / 24)) * 100` — `%` (the ADR's own prorate shape).

   `electrical-dg-set` (**v1 → v2**, `sortOrder` 38–40):
   - `downtime_h_24h` = `sum({dg_shutdown}, 24h)` — `h` (the time integral of the 0/1 trip flag; `dg_shutdown` is core).
   - `availability_pct_24h` = `(1 - avg({dg_shutdown}, 24h)) * 100` — `%`.
   - `starts_per_day` = `delta({start_count}, 24h)` — `""` (`start_count` is extended: an asset without it refuses `missing_input`, visibly).

   `electrical-solar-pv` (**v1 → v2**, `sortOrder` 26–28):
   - `co2_avoided_kg_today` = `delta({energy_total_kwh}, today) * $grid_carbon_factor_kgco2_per_kwh` — `kg`.
   - `performance_ratio_pct` = `delta({energy_total_kwh}, today) / ($installed_kwp * sum({irradiance_wm2}, today) / 1000) * 100` — `%` (`sum` of `W/m²` over hours is `Wh/m²`; `/1000` is `kWh/m²`; the tag list's "yield ÷ (irradiance × capacity)"; `irradiance_wm2` is extended).
   - `specific_yield_kwh_kwp_day` = `delta({energy_total_kwh}, 24h) / $installed_kwp` — `kWh/kWp/day`.

   `water-wtp` (**v1 → v2**, appended after its last point):
   - `kl_today` = `sum({raw_water_flow_klh}, today)` — `KL`.
   - `water_cost_today` = `sum({raw_water_flow_klh}, today) * $water_tariff_per_kl` — `""`.
   - `water_saving_vs_baseline_pct` = `(1 - sum({raw_water_flow_klh}, today) / ($water_baseline_kl_per_day * hours(today) / 24)) * 100` — `%`.

   **Expected demo state, so §4.6 does not read it as a defect:** `*_saving_vs_baseline_pct`, `performance_ratio_pct` and `specific_yield_kwh_kwp_day` are `parameter_unset` (no baseline or kWp value ships — B14); `co2_*` are `parameter_unset` until a carbon factor is entered; at the first bucketed tick after local midnight `hours(today)` is `0` and the two prorated formulas refuse `non_finite` (`evaluate.ts:7`) for one tick; a calendar window on `ESK-DECOMM-01` (the one `NULL`-zone location) refuses `timezone_unset`. All counted, none silent.
8. **The `_per_day` / `_day` names are the ADR's and mean a rolling 24 h** (§10 Q10). `starts_per_day` and `specific_yield_kwh_kwp_day` keep the code the tag list, the ledger and decision 8 all spell — one code, one meaning (ADR 0049 decision 5) — and "per day" is a rate over a trailing day, which a rolling `24h` is; `today` would be "so far today", a different quantity, and for a PV array a rolling day always holds one full diurnal cycle.
