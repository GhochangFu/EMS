## 1. Design decisions

- **D1 — fix 1 key set comes from `telemetry.point_values_1d`, not `bms.asset_points`.** One read: per `(asset_id, point_key)` of the page's assets, `max(bucket)`. The aggregate is real-time (`materialized_only = false`, migration `0027`, on all four levels), never dropped and uncompressed (14 chunks on the demo host). It is hierarchical (`1d ← 1h ← 5m ← 1m ← point_values`), so the read unions each level's real-time tail; Task 0 measured that at 5 ms planning + 5 ms execution warm. An uncatalogued key is listed because it has a bucket (the 33-vs-31 gap disappears with no catalog logic), a never-reported catalogued key is absent (as today), and each pair's newest sample is known to lie in one UTC day.
- **D2 — the newest value is a lateral `LIMIT 1` bounded to that UTC day by SQL-text timestamp literals.** Pairs are grouped by day; each group is one `UNION ALL` arm of `latest_points` with `v.time >= timestamptz '<day> 00:00:00+00' AND v.time < timestamptz '<day+1> 00:00:00+00'`. The planner sees constants and plans 1–2 chunks per arm, for a live pair and for a pair silent since October alike. This replaces a "recent bound plus unbounded fallback" design: that fallback would plan every chunk on every poll for any page with one dead key, and for every silent site (all ESKOM sites on the demo host). Task 0 M2b: the same arm with a computed bound instead of a literal planned for 374 ms; with the literal, 3.3 ms.
- **D3 — exactness rests on the aggregate being a complete record**, which the repo already keeps as a standing obligation (`0027` header): live samples are stamped at receive time (ADR 0061), and every writer of old timestamps refreshes (`telemetry-write.service.ts`, `calc-backfill.service.ts:154`, `apps/ingest/src/host/aggregate-repair.ts`). Residual: a sample written behind the watermark is invisible until its refresh (seconds to a minute); a pair whose raw rows are gone yields no row from the lateral and drops out, as in the old read. The result equals the old read's result as of the discovery statement. Task 0 M3: 0 differing rows on real data.
- **D4 — values never cross JavaScript.** Only `(asset_id, point_key, group)` go back in as three array parameters; value, unit and time are read inside the main statement, so the untouched `telemetry` CTE (`jsonb_agg … ORDER BY CASE …, point_key`) produces today's order and today's microsecond timestamps by construction.
- **D5 — fix 2 uses a literal interval built from the closed code constant** (the `GENERATED_LATEST_WINDOW_SQL` precedent, `control-room/generated-site-view.service.ts:36`), plus one named `idleTimeoutMillis` for the three pools.
- **D6 — fix 3: only the site page's list poll moves to 60 s.** It uses the list for name, organization, `energyShown` and crumbs; the other pages on the key draw live card figures from it, so their interval is their freshness (Q4). No cheaper existing source carries the ancestor chain the crumbs need.
