## 1. Goal, and what is out of scope

Give the repository its first configurable-dashboard vocabulary and persistence. This unit
ships four things and nothing else:

- **(a)** the closed widget vocabulary `radial_gauge | tank_level | value_tile | chart` as a
  `z.enum` in `packages/shared/src/contracts/`, with the per-type `config` carried by a
  `z.discriminatedUnion`;
- **(b)** three tenant-scoped tables — `bms.dashboards`, `bms.dashboard_widgets`,
  `bms.dashboard_widget_points` — created by one forward-only migration `0050` that also
  enables RLS, forces it, and writes the `tenant_isolation` policy in the same file;
- **(c)** the Drizzle declarations for those tables;
- **(d)** the opening of `TemplateDashboardView` past `featured[]`, so a template can declare
  widgets, with ADR 0019's "every referenced point key is one the template declares"
  cross-check extended to reach them on create, update **and** publish.

When this lands, `F3.1b` has a schema to serve, `F3.1c` has an enum to switch on exhaustively,
`F3.1d` has a config surface to render forms for, and `F3.1e` has a template contract to give a
tab to.

**Explicitly out of scope.** No endpoint, no controller, no service, no `DashboardsModule` —
`F3.1b` owns every route and the ADR 0017 write matrix and the audit stamping. No React
component, no `apps/web/src/lib/widget-catalog.ts` — `F3.1c` owns the renderers and ADR 0047
decision 2 puts the catalog registry with them. No builder surface, no drag-and-drop, no grid
library — `F3.1d`, and any library it needs is its own §9.4 ADR. No template *Dashboards* tab
and no amendment to ADR 0038's five-tab scan — `F3.1e`. No seed data:
`packages/db/src/*-seed.ts` is untouched, so a fresh database gets three empty tables.

Per ADR 0047 decision 6, `F3.28`, `F3.32`, `F3.2`, `F4.41` and the dark canvas are all outside
this row; the light palette is what ships. The `docs/BACKLOG.md` §5 *Reference layout language*
⚠ decision stays open and stays the owner's, and it **does not block** this row — ADR 0047
decision 6 already rules that `F3.1` ships in `TRINETRA.html:12`'s `--bg:#F2F4F7`.

## 2. The four design decisions ADR 0047 left to this build

ADR 0047 §Consequences hands four questions to `F3.1a` as "design decisions inside an approved
boundary". They are settled here, each against a constraint already in the repository. The
owner may veto any of them; none is a scope change.

### 2.1 Scope: a location, an asset group, or both — answer: two nullable columns, at most one set, both-NULL meaning organization-wide

`bms.dashboards` carries `location_id uuid REFERENCES bms.locations(id)` and
`asset_group_id uuid REFERENCES bms.asset_groups(id)`, both nullable, with a named constraint:

```sql
CONSTRAINT dashboards_scope_check CHECK (NOT (location_id IS NOT NULL AND asset_group_id IS NOT NULL))
```

Three states, all meaningful: both NULL is an organization-wide dashboard; `location_id` set is
a site dashboard; `asset_group_id` set is a plant-area dashboard.

The `CHECK` is not tidiness. `bms.asset_groups` already carries `location_id NOT NULL`
(`packages/db/src/schema/bms-schema.ts:237`), so an asset-group-scoped dashboard already
implies a location transitively — two independently-set columns can therefore *contradict each
other*, and a contradiction the database permits is one `F3.1b`'s authorization filter has to
resolve at runtime forever. ADR 0047 decision 2 lists "scope a dashboard to a location or an
asset group" among what an administrator can do, so both axes are in the approved boundary; the
`CHECK` is what stops them being set together.

Ownership is `organization_id` and nothing else. ADR 0047 decision 3 lists "ownership" among
`bms.dashboards`' column groups, and the answer is tenant ownership: **there is no `created_by`
and no per-user dashboard**. No row on the board asks for a personal dashboard, `E7.1c` already
records the actor for every mutation in `bms.audit_log`, and a second ownership axis would
force `F3.1b` to answer "can I see a dashboard I did not create" before anybody has asked the
question. If personal dashboards are ever wanted, that is one forward migration adding one
nullable column — the same standing precedent ADR 0047 decision 2 cites for reopening a closed
vocabulary.

### 2.2 URL addressing: `(organization_id, slug)` UNIQUE, addressed as `/dashboards/:slug`

`bms.dashboards.slug varchar(64) NOT NULL`, with
`CONSTRAINT dashboards_organization_slug_key UNIQUE (organization_id, slug)`.

**Do not copy `locations.slug`.** `packages/db/src/schema/bms-schema.ts:58` declares
`slug: varchar("slug", {length: 64}).notNull().unique()` — globally unique — and `assets.code`
at `:198` is globally unique the same way. Both predate multi-tenancy. Migration
`0048_channel_org_identity_and_fleet_scoped_null_check.sql` is the newest ruling on exactly
this question: under ADR 0043 Amendment 5 decision 7 it re-keyed `bms.notification_channels`
and `bms.automation_rules` from a bare global `code` to `(organization_id, code)`, *because*
the global key was the defect — "a tenant's channel or rule code no longer collides with
another tenant's". A globally-unique dashboard slug would mean the first tenant to create
`overview` takes the word from every other tenant, and the failure arrives as a `23505` in
front of an administrator with no way to resolve it. Follow `0048`.

The organization comes from the JWT on every request, so `/dashboards/:slug` resolves
unambiguously without exposing a uuid in the URL. `F3.1b` owns the route; this row owns the key
that makes the route possible. Say this in the PR body, because a reviewer who greps `slug`
finds `locations` first and will otherwise read the difference as an oversight.

### 2.3 Grid: four integer columns on the row, a fixed 12-column canvas, bounds by `CHECK`, no overlap rule

`grid_x`, `grid_y`, `grid_w`, `grid_h`, all `integer NOT NULL`, on `bms.dashboard_widgets`. Not
in `config` — ADR 0047 decision 3 puts "grid position and size" on the row and reserves
`config` for "per-widget presentation options that the *renderer alone* consumes". Position is
read by the builder, by any future export and by ordering; the line the ADR draws is "whether
anything but the renderer reads it", and position fails that test.

```sql
CONSTRAINT dashboard_widgets_grid_bounds_check CHECK (
  grid_x >= 0 AND grid_w >= 1 AND grid_x + grid_w <= 12
  AND grid_y >= 0 AND grid_h >= 1 AND grid_h <= 24
)
```

Twelve columns because it is the canvas every grid library and every CSS grid in `apps/web`
already assumes, and because a fixed column count is what makes `grid_x` comparable across
widgets at all. `grid_y` is unbounded above — a long dashboard is legitimate. `grid_h <= 24`
bounds a single tile so one widget cannot be authored a thousand rows tall.

**No overlap prevention, deliberately.** Two widgets not overlapping is a multi-row invariant,
and no row-level `CHECK` can express it; an `EXCLUDE` constraint could, and it would make every
reorder in `F3.1d` a constraint-ordering puzzle. ADR 0047 decision 1 assigns "compose, arrange"
to `F3.1d`. Stated here so `F3.1d` inherits it as a written decision rather than as an unstated
assumption it discovers by shipping overlapping tiles.

There is no `sort_order` on `dashboard_widgets`: `(grid_y, grid_x)` **is** the order, and a
second ordering column would be a third description of the same fact.

| Column | Type | Notes |

| `widget_id` | `uuid NOT NULL REFERENCES bms.dashboard_widgets(id) ON DELETE CASCADE` | |
| `point_id` | `uuid NOT NULL REFERENCES bms.asset_points(id) ON DELETE CASCADE` | see below |
| `role` | `varchar(32) NOT NULL DEFAULT 'primary'` | `dashboard_widget_points_role_check IN ('primary','series')` |
| `sort_order` | `integer NOT NULL DEFAULT 0` | ordering within a chart's series |
| `created_at` | `timestamptz NOT NULL DEFAULT now()` | |

plus `CONSTRAINT dashboard_widget_points_widget_point_role_key UNIQUE (widget_id, point_id, role)`.

**`point_id` is `ON DELETE CASCADE`, and the alternative was weighed.** ADR 0047 decision 3's
complaint about `layout jsonb` is that "a point key inside a JSON blob is not a foreign key,
and nothing tells you when it is orphaned". A foreign key gives two possible answers and both
are *known*: `RESTRICT` refuses the master-data delete, and `CASCADE` removes the binding.
`RESTRICT` is rejected because it pushes a dashboard concern into master data — an
administrator retiring a sensor would be blocked by somebody else's dashboard, with an error
naming a constraint rather than a page. `CASCADE` leaves a widget with fewer bindings, which is
a state the schema can report (`count(*) = 0` on the join) where a stale JSON id is not.

**Note for `F3.1c`:** a widget whose bindings have reached zero must render "no data bound", not
a blank rectangle — that is the same failure ADR 0047 decision 2 refuses to allow through the
vocabulary door, and it must not arrive through this one.

`role` is a closed vocabulary by §4.8's test as ADR 0032 rewrote it: what the engine needs to
know is *which slot of the renderer this point feeds*, and that is a component, not a column.
Two values, because two is what the four types need — a gauge, tank and tile read `primary`; a
chart reads N `series`. A widget's *cardinality* (a gauge takes exactly one point) is a
per-widget row count, which no row-level `CHECK` can see; it is enforced by `F3.1b`'s write
validation against `F3.1c`'s catalog, and this plan says so rather than leaving it implied.

**Indexes.** `dashboards_organization_slug_key` already leads with `organization_id`, so the
tenant-filtered list read that `E7.1i` made seekable is served by it; no second index on
`bms.dashboards`. `dashboard_widgets_dashboard_idx (dashboard_id, grid_y, grid_x)` serves the
one read `F3.1b` will make. `dashboard_widget_points_widget_idx (widget_id, sort_order)` for
the same reason. `dashboard_widget_points_point_idx (point_id)` so the `ON DELETE CASCADE` from
`bms.asset_points` does not sequential-scan, and so "which dashboards use this point" is
answerable at all. Four indexes, each named, each with a read behind it. No speculative index.

## 3. Migration mechanics — checked, not assumed

- **File:** `packages/db/drizzle/0050_configurable_dashboard_tables.sql`. Latest on disk is
  `0049_audit_log_organization_created_index.sql`, so `0050` is next. Forward-only, idempotent
  (`CREATE TABLE IF NOT EXISTS`, `CREATE INDEX IF NOT EXISTS`, `DROP POLICY IF EXISTS` before
  `CREATE POLICY`) per AGENTS.md §4.4.

- **`SET ROLE bms_owner;` … `RESET ROLE;` bracket — required, and here it is load-bearing
  rather than ceremonial.** ADR 0045 decision 6 makes it the rule for every migration authored
  after the ADR. It matters twice for this one. First, `FORCE ROW LEVEL SECURITY` requires
  table ownership. Second, and easier to miss:
  `packages/db/drizzle/0041_bms_owner_and_force_rls.sql:112-119` sets
  `ALTER DEFAULT PRIVILEGES FOR ROLE bms_owner IN SCHEMA bms GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO bms_tenant, bms_fleet`
  — and default privileges apply only to objects created by the role they name.
  `pnpm db:migrate` connects as `DATABASE_URL_SUPERUSER` (`bms_app`). So without the `SET ROLE`,
  the three tables are owned by `bms_app`, the default privileges do not fire, and the tables
  reach no pool role at all — which `0039`'s own comment warns is a failure that "surfaces one
  endpoint at a time" inside `F3.1b`, long after the migration that caused it. **With the
  `SET ROLE`, no explicit `GRANT` statement is needed and none should be written.** Say this in
  the migration header so the migration reviewer does not add a redundant grant or ask why one
  is missing. The `RESET ROLE;` is mandatory: `0041`'s own comment records that a leaked
  `SET ROLE` reaches the drizzle migrator's journal write and every later migration in the same
  run.

- **No `CREATE INDEX CONCURRENTLY`.** The repo invariant `E7.1i` established is asserted at
  `tests/e7.1i-audit-log-index.test.ts:39`. It is scoped to that one migration file, so it does
  not automatically bind `0050` — which is precisely why the new static test in Task 1
  re-asserts it for `0050`. The rule holds for the ordinary reason as well: `CONCURRENTLY`
  cannot run inside a transaction block, and the drizzle migrator wraps each file.

- **The RLS policy is the *strict* form, with no NULL branch.** All three tables have
  `organization_id NOT NULL`, so none of them has a legitimate NULL organization the way
  `users`, `notification_channels` and `audit_log` do (ADR 0043 decisions 5/7, Amendment 4).
  Copy `0047_tenant_policies_force.sql`'s §3a idiom verbatim, `USING` identical to `WITH CHECK`:

  ```sql
  DROP POLICY IF EXISTS tenant_isolation ON bms.dashboards;
  CREATE POLICY tenant_isolation ON bms.dashboards
    USING (organization_id = nullif(current_setting('app.current_organization', true), '')::uuid)
    WITH CHECK (organization_id = nullif(current_setting('app.current_organization', true), '')::uuid);
  ```

  `current_setting(..., true)` returns NULL rather than erroring when the GUC is unset, so a
  connection with no tenant fails closed and quiet. Repeat for all three tables, and pair each
  with `ALTER TABLE … ENABLE ROW LEVEL SECURITY;` and
  `ALTER TABLE … FORCE ROW LEVEL SECURITY;`. **`0048`'s Amendment 5 role-scoped NULL branch does
  not apply here** — there is no NULL case to admit.

- **`packages/db/drizzle/meta/_journal.json` is edited by hand.** Append
  `{"idx": 50, "version": "7", "when": <chosen ms>, "tag": "0050_configurable_dashboard_tables", "breakpoints": true}`.
  Choose the `when` value **once**, at authoring time, and write the same integer into the
  static test in Task 1 — `tests/e7.1i-audit-log-index.test.ts:25-31` is the precedent for
  pinning the whole entry, and a mismatched `when` is a red build with no defect under it.

- **`tests/adr-0043-tenant-columns.test.ts`'s `TENANT_TABLES` is NOT edited.** That constant is
  documented as "the 19 tenant-bearing tables `E7.1b` gives `organization_id`", and every
  assertion built on it scans migrations `0046` and `0047` specifically. Adding `dashboards` to
  it would assert that `0046` backfilled a table that did not exist in 2026-08-26 — red for the
  wrong reason. Say this in the PR body; a reviewer will look for the addition and must be told
  it was considered and rejected.

## 4. The contract — encodings, and the two constraints that force them

New file `packages/shared/src/contracts/dashboard-builder.ts`. **Not** `dashboards.ts`:
`contracts/dashboard.ts` already exists and holds the *fixed* control-room reads
(`locationDashboardDtoSchema`, `dashboardKpisSchema`), and two files one plural apart is how the
wrong one gets imported.

```
widgetTypeSchema         = z.enum(["radial_gauge", "tank_level", "value_tile", "chart"])
chartSeriesKindSchema    = z.enum(["line", "area", "bar", "scatter"])
widgetPointRoleSchema    = z.enum(["primary", "series"])
```

Four config objects, then one union discriminated on `widgetType`:

```
radialGaugeConfigSchema  — min, max, thresholds[] (value + tone), unit, decimals
tankLevelConfigSchema    — fullScale, unit, decimals, fillTone
valueTileConfigSchema    — unit, decimals, precision/abbreviate
chartConfigSchema        — series: chartSeriesKindSchema, windowMinutes, stacked, yAxisLabel, unit

dashboardWidgetSpecSchema = z.discriminatedUnion("widgetType", [
  z.object({ widgetType: z.literal("radial_gauge"), config: radialGaugeConfigSchema }),
  z.object({ widgetType: z.literal("tank_level"),   config: tankLevelConfigSchema }),
  z.object({ widgetType: z.literal("value_tile"),   config: valueTileConfigSchema }),
  z.object({ widgetType: z.literal("chart"),        config: chartConfigSchema }),
])
```

**The discriminant is `widgetType`, which is the column, and it is stored once.**
`bms.dashboard_widgets.widget_type` holds it; `config` holds only the renderer-private half.
Nothing has to reconcile a discriminant inside the JSON against the column, because there is
none inside the JSON — the union is over the pair, not over `config` alone. This is what keeps
`F3.1c`'s exhaustive `switch` (ADR 0047 decision 2) operating on the DTO directly.

**Three encoding constraints, and two of them are independent — this is the part a reviewer
will probe.**

1. `.merge()` and `.omit().extend()` are **banned in `contracts/`** by ADR 0030 Amendment 1,
   enforced as a source scan at `tests/adr-0030-contract-derivation.test.ts:133-172`. The scan
   skips lines starting with `//`, `*` or `/*`, so prose about the rule is safe; any real line
   matching the flattening patterns fails the build.
2. `z.discriminatedUnion` accepts **only `ZodObject` arms**. So `z.intersection` — the encoding
   §4.8 *prescribes* for `A & B` — cannot be used to build an arm either. Both DRY routes are
   closed at once, from two different directions.
3. The legal DRY answer is a **plain TypeScript object of field schemas, spread into each arm**:
   `const commonConfigFields = { unit: z.string().max(32).optional(), decimals: z.number().int().min(0).max(6).default(1) };`
   then `z.object({ ...commonConfigFields, min: …, max: … })`. Object-literal spread is not a
   Zod combinator, produces one flat `ZodObject`, and matches neither scan pattern. Use it, and
   put the two-constraint reason in the file docblock so the next reader does not "fix" the
   repetition with a flattening combinator.

Then the two consumers, both using the **prescribed** `z.intersection` for `A & B`:

```
dashboardWidgetDtoSchema = z.intersection(
  z.object({ id, dashboardId, organizationId, title: …nullable(), gridX, gridY, gridW, gridH,
             points: z.array(dashboardWidgetPointDtoSchema) }),
  dashboardWidgetSpecSchema,
)

dashboardDtoSchema        = z.object({ id, organizationId, slug, name, description,
                                       locationId, assetGroupId, createdAt, updatedAt,
                                       widgets: z.array(dashboardWidgetDtoSchema) })
dashboardSummaryDtoSchema = dashboardDtoSchema minus widgets — written as its own z.object,
                            NOT derived by omission, for rule 2 above
```

`(Identity) & (A | B | C | D)` distributes in TypeScript and still narrows on `widgetType`, so
the exhaustive `switch` survives the intersection. `contracts/admin.ts:273`
(`adminAssetTemplateSummaryDtoSchema`) and `contracts/dashboard.ts:105`
(`locationDashboardDtoSchema`) are the two standing precedents for `z.intersection` in this
package; `contracts/operations.ts:98` (`alarmSocketEventSchema`) is the precedent for
`z.discriminatedUnion`.

**Wiring.** Add `export * from "./dashboard-builder";` to
`packages/shared/src/contracts/index.ts`. In `packages/shared/src/index.ts`, add the type
aliases in the existing namespace style (`export type DashboardKpis = z.infer<typeof D.dashboardKpisSchema>;`
at `:79` is the shape) — `WidgetType`, `ChartSeriesKind`, `WidgetPointRole`,
`DashboardWidgetSpec`, `DashboardWidgetDto`, `DashboardDto`, `DashboardSummaryDto`, each as
`z.infer`. The ADR 0030 scan reads `index.ts` and requires every `export type X = …;` there to
contain `z.infer<`; these all do.

`.readonly()` is **not** used here. §4.8's third encoding applies to an all-`readonly` object,
and none of these is one — `telemetry-entry.ts:68` and `telemetry-import.ts:30` are the files
where it does apply, and copying it here would be a different type, not a stricter one.

## 5. Opening `TemplateDashboardView` — and the check that breaks if you only open half of it

`packages/shared/src/asset-template-content.ts:124-129` is the docblock that becomes false
("No widget types, no layout, no sizes — that is `F3.1`'s vocabulary"). ADR 0047 §Consequences
rules that this docblock change is **not** `AGENTS.md`, therefore not §9.10-gated, and **lands
with the code**.

The type becomes:

```ts
export type TemplateDashboardWidget = {
  pointKeys: string[];
  title?: string;
  gridX: number; gridY: number; gridW: number; gridH: number;
} & DashboardWidgetSpec;              // z.infer of the shared union — imported type-only

export type TemplateDashboardView = {
  featured: string[];
  widgets?: TemplateDashboardWidget[];
};
```

**The asymmetry is the point and must be written down.** A *live* dashboard binds
`bms.asset_points.id` as foreign-key rows. A *template* dashboard has no asset yet, so it binds
`template_points.point_key` **strings**, exactly as `featured[]` already does, and existence is
proved by ADR 0019's cross-check rather than by a constraint. The same widget vocabulary and
the same `config` union serve both; only the point reference differs.

`asset-template-content.ts` stays hand-written for its own half. That is the file's existing
design — `TemplateKpi`, `TemplateAlarm` and `TemplateMaintenancePlan` are all hand-written
there, with `ParsedContentMatchesDto` / `DtoMatchesParsedContent` at
`apps/api/src/admin/asset-templates/asset-templates-content.schema.ts:380-382` as the
bidirectional compensating control. The ADR 0030 scan does not reach it:
`packages/shared/src/index.ts:427` is `export type * from "./asset-template-content";`, a
re-export, not an `export type X = …` declaration. The *widest and most error-prone* half — the
four config shapes — is nonetheless derived, via the type-only import of
`DashboardWidgetSpec`. Import it from `./contracts/dashboard-builder` directly rather than from
`./contracts`, to avoid a module cycle, and keep it `import type` so the file stays type-only at
runtime.

Then in `apps/api/src/admin/asset-templates/asset-templates-content.schema.ts`:

- **`templateDashboardViewSchema` (`:262`)** gains
  `widgets: z.array(templateDashboardWidgetSchema).max(MAX_DASHBOARD_WIDGETS).optional()`. It is
  `.strict()` and stays so. Build `templateDashboardWidgetSchema` locally as
  `z.intersection(z.object({ pointKeys: z.array(pointKeyRef).min(1).max(MAX_WIDGET_POINT_KEYS), title: …, gridX…gridH }), dashboardWidgetSpecSchema)`,
  **re-exporting** the shared spec union rather than restating it — §4.8's "a vocabulary is
  declared once and everything else is derived from it", the rule
  `apps/api/src/rules/rules.schema.ts` already follows. Keeping `pointKeyRef` here rather than
  moving it to `@bms/shared` is deliberate: it is this file's character-class contract for a
  `template_points.point_key`, and moving it would drag the whole content vocabulary across a
  package boundary.
- **New bounds:** `MAX_DASHBOARD_WIDGETS = 40` per view and `MAX_WIDGET_POINT_KEYS = 8` per
  widget, declared beside the existing `MAX_DASHBOARD_VIEWS = 20` / `MAX_FEATURED_POINTS = 50`
  at `:132-133`. Note the depth budget while you are there:
  `raw → dashboards → view → widgets[] → widget → config → thresholds[] → threshold` is 8 levels
  against `MAX_CONTENT_DEPTH = 12` (`:76`). It fits, and it is worth stating because a future
  nested option would not.
- **`collectContentPointRefs` (`:390`) is the function that breaks if you forget it.** Today its
  `dashboards` branch is `refs.push(...view.featured)`. It must also push every
  `widget.pointKeys`. `findUnresolvedContentRefs` calls it, and `assertContentRefsResolve` calls
  that from **three** places in `asset-templates.service.ts` — `:165` (create), `:249` (update)
  and `:324` (publish). ADR 0019's guarantee is "checked on create, update and publish, because
  `content` and `points` are patched independently and a points patch can orphan content the
  request never mentioned". If `collectContentPointRefs` does not walk widgets, all three checks
  silently stop covering the new half, nothing in the type system says so, and ADR 0019's §3
  tier promotion is a claim rather than a fact. **This is the single highest-value assertion in
  the whole row.**
- **`ParsedContentMatchesDto` / `DtoMatchesParsedContent` (`:380-382`) will fail

**Decisions settled in this plan that the owner may veto — put in front of them once, before the
first line of code, as settled rather than as questions:**

1. **Scope is location OR asset group OR organization-wide, enforced by
   `dashboards_scope_check`** (§2.1). This is the one choice that `F3.1b`'s authorization filter
   and `F3.1d`'s builder both inherit, and reversing it after either ships is a migration plus
   two rows of rework. Recommend as written.
2. **There is no per-user dashboard ownership and no `created_by`** (§2.1). ADR 0047 decision 3
   lists "ownership" among the columns, and this plan reads that as tenant ownership. If the
   owner means personal dashboards, say so now — it is one nullable column today and a much
   larger authorization question inside `F3.1b`.
3. **`point_id` is `ON DELETE CASCADE`, not `RESTRICT`** (§2.4). The alternative makes an
   ordinary sensor retirement fail on somebody else's dashboard.

**Explicitly not blocking:** `docs/BACKLOG.md` §5's *Reference layout language* ⚠ stays open and
stays the owner's, but ADR 0047 decision 6 already rules that `F3.1` ships in the existing light
palette, and §5's own row records that the reference's component vocabulary is achievable there.
This row does not wait on it.
