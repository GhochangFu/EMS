## 1. Goal

Give a work order the depth the SOW reference layouts show. Seven things, in six small PRs:

1. A frozen human reference, `WO #ELEC-000042`, beside the uuid.
2. An SLA in whole minutes, snapshotted at create from a per-organization, per-priority policy; its state is computed on read.
3. A checklist on `bms.work_order_tasks`, copied from a reusable template.
4. Root-cause fields and a coded cause on the ticket.
5. Closure approval: `resolved` means "waiting for approval"; `POST /work-orders/:id/close` becomes the approval under a new third write class, `approval`, with four eyes and a `reject` route.
6. An append-only `bms.work_order_events` timeline any reader of the ticket may see.
7. A five-step lifecycle stepper in a new detail drawer on `/work-orders`, plus two small admin pages for SLA policies and checklist templates.

**Out of scope** (ADR 0122 "Not in this record"): mobile execution and photos (`E3.2`); a CMMS connector (`E3.3`); copying alarm enrichment into the ticket (`E3.4`); SLA breach notification, escalation, pause, business hours, response SLA; parts, labour, cost; audit hash-chaining (`F4.15`); degradation and RUL (`E1.5`); any device command; any new npm package. Also out, by this plan: an admin write route for `bms.asset_domains` (P8); a copilot read tool for cause codes or templates (P4); dropping the legacy `work_order_tasks.status` column; any AGENTS.md edit inside a feature PR.

## 3. Drafter refinements

- **R1 — one allocator, in `packages/db`.** `allocateWorkOrderReference(tx, organizationId, assetId)` is one statement: `INSERT INTO bms.work_order_counters ... ON CONFLICT (organization_id) DO UPDATE SET next_seq = next_seq + 1 RETURNING`, joined to the asset's domain prefix. The upsert takes the row lock itself, so there is no read-then-write gap and no first-row race. It lives in `packages/db/src/work-order-reference.ts`, so the seed, both API creators and the three suite fixtures call the same code. It runs last before the insert, so the lock is short. Width is `lpad(seq::text, greatest(6, length(seq::text)), '0')`: plain `lpad(..., 6)` **truncates** at seq 1,000,000 and would collide.
- **R2 — a backfill runs after `RESET ROLE`.** DDL goes inside the `SET ROLE bms_owner` bracket; data backfills go after it, as the migrator's superuser role, and the header says why. The `DO $$` block raises if any `work_orders.seq IS NULL` remains, **before** `SET NOT NULL`. Also `UNIQUE (organization_id, seq)` beside the ADR's `UNIQUE (organization_id, reference)`.
- **R3 — one create path, one projection.** New `apps/api/src/work-orders/work-order-create.ts` (`insertWorkOrder(tx, input)`: allocate, snapshot the SLA, insert; later PRs add the `created` event and the checklist copy) and `work-order-projection.ts` (the select columns and the row mapper). `WorkOrdersService` and `MaintenanceService` both use them. This also keeps `work-orders.service.ts` under the cap.
- **R4 — a field lands with its column.** The list item gains `reference`, `slaMinutes`, `slaDueAt`, `slaState` in PR 1; `checklistDone`, `checklistTotal` in PR 3; `causeCode`, `approvedAt` in PR 4. The detail schema grows the same way. Each of those PRs updates the four literals of section 2.
- **R5 — file caps.** A new contract file, `packages/shared/src/contracts/work-orders.ts`, holds every **new** response schema; `operations.ts` gains only item fields. Bodies stay in `operations-writes.ts`, as the ADR says. Types go in `packages/shared/src/types/work-orders.ts`; the four existing work-order type lines move there from `index.ts`, so `index.ts` ends two lines shorter after its two new export lines.
- **R6 — event detail is a closed shape.** `workOrderEventDetailSchema` is a `.strict()` object of optional known keys (`reason`, `origin`, `taskId`, `result`, `causeCode`, `assignedTo`), built by one function. A free-form record would let `oidcSubject` in by accident (ADR decision 7.4).
- **R7 — foreign keys.** `work_order_events.work_order_id` has **no** `ON DELETE` clause: a ticket with history cannot be deleted by a pool role. `work_order_tasks.template_item_id` is `ON DELETE SET NULL`, because a template edit replaces its items. `work_order_checklist_template_items` carries its own `organization_id` (the ADR's column list omits it; its decision 9 and AGENTS.md section 4.4 require it).
- **R8 — SLA policy API shape.** `PUT` replaces the organization's set (at most four rows; a priority left out falls back to the default). `GET` always answers four rows, each with `source: "organization" | "default"`.
- **R9 — one transition function**, `apps/api/src/work-orders/work-order-transitions.ts`, pure, holding the table below. P1–P3 hang on it.
- **R10 — a new static invariant file**, `tests/e3.1-work-order-write-gates.test.ts`, because `repo-invariants.test.ts` has one line left. It pins the gate on the two new admin controllers (PRs 1, 3) and that exactly the `close` and `reject` handlers carry `"approval"` (PR 4).
- **R11 — PR 4 carries the smallest web change that keeps the board usable**: the status wizard's root-cause step, and the Close button gated on role and status. Without it an alarm ticket could not be resolved from the web between PR 4 and PR 5.
- **R12 — stepper inputs.** A step is *reached* from the ticket's status; its *time* comes from the matching event when one exists. A ticket older than migration B has no events and still draws correctly (P10).
- **R13 — route order.** `@Get("cause-codes")` and `@Get("checklist-templates")` are declared above `@Get(":id")`.
- **R14 — prefixes for seed-born domains.** Migration A sets the prefix on whatever domain rows exist. `PACK_ASSET_DOMAINS` gains a `workOrderPrefix` (`MECH`, `FAC`, `UPS`); the seed writes it on insert and fills it where it is still NULL, never over a value. Without this a fresh database (CI, a new site) would number every UPS ticket `GEN-...` while an old one says `UPS-...`.
- **R15 — reserved, unused.** `sla_changed` stays in the events `CHECK` with no writer. `work_order_tasks.status` stays in the table and is no longer read.

## 8. Risks

1. **Concurrent reference counter.** Held by T1.4's 20-way claim. The counter row stays locked for the rest of the create transaction, so creates in one organization run one at a time. Acceptable at this volume.
2. **Backfill on a live table.** One transaction, under the `ACCESS EXCLUSIVE` lock of the first `ALTER`; the table is human-scale. The silent zero-row trap is R2 and the `DO $$` proof.
3. **Breaking `PATCH :id/status`.** A caller sending `closed` gets 400. The web wizard and the copilot already use the close route; the repository has no other caller.
4. **Operators lose close.** Intended (ADR Consequences). Between PR 4 and PR 5 an approver can approve from the board but can reject only through the API. A release note is owed.
5. **Existing `resolved` rows** have a NULL `resolved_by`, so four eyes cannot bind them; any approver may close them. Alarm tickets already `resolved` are not asked for a root cause after the fact.
6. **Copilot close card.** The wording changes; the body, and so the hash, does not. A close an operator proposed before the deploy is refused at confirm (403). `CLOSE_WORDS` (`copilot-operations-intent.ts:26`) is unchanged, so the word "approve" alone does not propose a close.
7. **File caps.** Four files are within 17 lines of 1000 (section 6).
8. **A single-administrator site** cannot close its own work (ADR, Q11).
9. **"Open work orders" counts.** `metric-catalog.service.ts:567` already leaves `resolved` out; `dashboard.service.ts` still counts it as open. Tickets now wait in `resolved` longer. No change is planned.
10. **Prefix drift between old and fresh databases** if R14 is skipped: the fresh-database check in PR 1 is what catches it.
