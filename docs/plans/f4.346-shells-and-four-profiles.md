## PR 1 — shells and the preview (web only)

Files: `apps/web/src/lib/design.ts`, `apps/web/src/layouts/app-shell.tsx`,
`apps/web/src/layouts/shells/{sidebar-shell,rail-shell,navigation-model}.tsx|ts`,
`topbar-shell.tsx` (deleted), `apps/web/src/stores/theme-store.ts`,
`apps/web/src/index.css` (the `swiss-grid` and `bento-ops` nav skins), the
shell and panel specs.

Tests first:

- **S1** `SHELL_OF_DESIGN` maps `nexus-soft`, `enterprise-flat`, `swiss-grid`,
  `bento-ops` to `sidebar` and `control-room-dark` to `rail`; no `topbar`
  value exists in the type or the source (a text scan of `apps/web/src`).
- **S2** for each of the five design systems, rendered at 1440 px (jsdom with
  a stubbed width), every visible module and admin item is a link inside one
  vertical `nav[aria-label="Modules"]`, and no element carries a horizontal
  scroller for the navigation.
- **S3** the sidebar markup fixture (`sidebar-shell-markup.spec.tsx`) is
  unchanged for `nexus-soft`: the skins are CSS only.
- **S4** the rail: a collapse button toggles text labels to codes, each code
  link keeps the full label in its accessible name, the choice persists under
  its own key (`bms-rail-collapsed`), and at ≤ `SHELL_RAIL_MAX_WIDTH` the rail
  is a 64 px slot with an overlay that closes on navigation (reuse
  `useOverlayClosesOnNavigation`). Default: expanded.
- **S5** the preview: in the Appearance panel, choosing Swiss Grid while the
  viewer's design system is `control-room-dark` renders the sidebar shell;
  Cancel restores the rail; Save keeps the saved value. `previewDesign(null)`
  clears the store's preview.
- **S6** the skins read only tokens (the DT4 and A5 gates stay green; the
  selected item in `swiss-grid` and `bento-ops` paints `ink`, not `accent`).

Build: `previewDesign` writes `preview: DesignSystem | null` to the theme
store and the attribute; `useDesignSystem` stays the saved value; a new
`useShownDesignSystem()` returns `preview ?? design` and `AppShell` reads it.

## PR 2 — four profiles (contract, web, migration)

Files: `packages/shared/src/contracts/colour-profile.ts` (+ spec),
`apps/web/src/components/appearance/labels.ts`, `apps/web/index.html` (the
boot script's allowed list), `apps/web/src/index.css` (eight blocks),
`packages/db/drizzle/0137_colour_profiles_thirteen.sql` + journal, the schema
tests, the API appearance specs.

Tests first:

- **P1** `COLOUR_PROFILES` has thirteen names in order: the nine, then
  `hmi-grey`, `moss`, `colour-safe`, `night-shift`; each has a label and a
  description.
- **P2** the A4 gate (`tests/f4.341-*` accent test) covers the four new
  profiles in light and dark and fails if any `accent*` role is within ΔE 20
  of a critical or warning role or ΔE 12 of an info role or `simulated-ink`,
  or if a series equals the accent; the 4.5:1 text pairs pass.
- **P3** every profile block defines the same 27 roles as `nexus` (the
  existing role-count gate).
- **P4** migration `0137` widens the three `colour_profile` CHECKs
  (`bms.organizations`, `bms.portal_settings`, `bms.users`) to thirteen names;
  the schema test reads the three constraints; a write of `night-shift` through
  `PUT /me/appearance` is 200, and an unknown name is 400.
- **P5** the boot script accepts the four names (`f4.341-design-boot`).
- **P6** `colour-safe`'s eight series are the Okabe-Ito / Tol members listed
  in the value table, with no orange or vermillion member.

The value table (draft accents in Amendment 3; the PR body carries the full
