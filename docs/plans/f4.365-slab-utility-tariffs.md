**Goal:** A location can be mapped to a published tariff line (billing meter, sanctioned load, month-aligned dates). The API computes that location's monthly bill (telescopic slab energy + fixed/demand + wheeling) from the billing meter's `kwh_total` or `kvah_total` delta, with kVAh estimated from kWh ÷ average `pf` when absent. The energy cost reads price a mapped location's assets at the bill's average rate instead of the flat `energy_tariff_per_kwh`. Organization admins add effective-dated revisions and custom tariffs. The catalog is the workbook's Rate Chart, imported as data.

**Architecture:** Two global catalog tables (migration A) and three tenant tables under FORCE RLS (migration B). Zod contracts and a pure `computeBill` in `packages/shared`. A new `apps/api/src/tariffs/` module: version resolver, register read, bill service, HTTP routes, and an `EnergyRateResolver` that decorates `CalcParametersService` at the two existing cost seams (`TariffResolver`, `TariffSeriesResolver`). Web: a per-location tariff page, an Admin → Tariffs screen, a Monthly bill card.

**Out of scope (ADR decision 6 and Consequences):** electricity duty, FPPAS/FAC, subsidies, ToD, PF/LF rebates, minimum charges, Gujarat telescopic demand, asset-level mapping. Also out, by this plan: editing the global catalog from the UI; a seeded demo mapping (PHEWB is a real client, ESKOM is ZAR); the calc-engine derived points `energy_cost_today|this_month|this_year` (Q7); caching of bills.

**Calculator semantics (Bill Calculator formulas, the reference):**
- Units in slab *i* = `max(0, (to_i ?? U) capped at U − (to_{i−1} ?? 0))`. `From` is display only.
- Units above a closed last slab are **not billed** (Q5).
- Wheeling is **per slab**: Σ units_i × wheeling_i.
- Highest slab reached = `max(1, count of slabs with units > 0)`; at 0 units slab 1's fixed rate still applies.
- Fixed = that slab's rate × load (kW/kVA/HP bases) or × 1 (per connection). The workbook charges a bi-monthly basis once per bill; ADR decision 6 rules half per month.

## 3. Decisions this plan makes

- **D1. Where the catalog lives.** A committed, normalised `packages/db/src/tariff-catalog.json` (the `phe-catalog.json` precedent), generated from the workbook. The workbook is not committed; the snapshot records its file name and sha256. A catalog change is a reviewed JSON diff.
- **D2. One parse, two sinks.** `pnpm --filter api tariffs:import <file> [--out <json>] [--apply]`. No flag is a dry run (validation report). `--out` writes the snapshot. `--apply` upserts into the database at `DATABASE_URL_FLEET`. `db:seed` upserts the committed snapshot on every run. Both call one function, `upsertTariffCatalog`, exported from `@bms/db`.
- **D3. Role rules (§4.4, ADR 0045).** Migration A creates the two tables inside `SET ROLE bms_owner … RESET ROLE`, writes **no rows** and **no GRANT**, and revokes `INSERT, UPDATE, DELETE` from `bms_tenant` with the `0085` proof block. The seed writes as `bms_owner` (the owner, no policy) in `seed.ts`'s pre-tenant section. `--apply` writes as `bms_fleet` (`0041` default privileges), the route every other global vocabulary write takes. `roles.ts` is untouched (`btree_gist` is already provisioned).
- **D4. Upsert.** By `(key, effective_from)`: insert or update the category, replace its slabs, never delete a category. An unchanged snapshot writes nothing.
- **D5. Audit.** Tenant writes call `MasterDataAuditService.write(…, tx)` inside the same `withTenant` transaction with the organization id stamped: `master.location_tariff.create|update|delete` (entity `location_tariff`) and `master.tariff_version.create|update|delete` (entity `org_tariff_version`, `reason` from the body). The catalog import and seed write no audit row: there is no actor, and the JSON's git history is the record.
- **D6. Authorization (§4.7).** Role always from `bms.users`.

| Route | Rule |
|---|---|
| `GET /tariffs/categories`, `GET /tariffs/lines/versions` | `JwtAuthGuard`; organization rows only for an organization in `readableOrganizationIds` (403 otherwise) |
| `GET /locations/:locationId/energy-bill` | `JwtAuthGuard`; location in `readableLocationIds` **and** billing meter in `readableAssetIds`, else one 404 sentence |
| `GET|POST|PATCH|DELETE /admin/locations/:locationId/tariffs` | `requireMasterDataUser`, then `canManageLocation` (the calc-parameters location rule) |
| `POST|PATCH|DELETE /admin/tariffs/versions` | `requireMasterDataUser`, then `isOrganizationLevelAdmin(jwt, organizationId)`; never `canManageOrganization`, which admits a `location_admin` |

- **D7. Fixed basis is a category column.** It is the one distinct non-blank basis across a key's rows, `none` when all are blank; two different non-blank bases refuse the import. Blank fixed charge is 0. Haryana DS-II becomes `per_kw_month` with slab rates 0, 0, 50, 50, which reproduces the workbook.
- **D8. Month-aligned dates.** Every `effective_from`/`effective_to` in the five tables is a `date` on day 1 (CHECK). A version or mapping applies to a month when it is in force on that month's first day, so one bill never mixes two rate sets or two mappings.
- **D9. Billed quantity.** Last minus first register sample **inside** the month window, reusing `deltaOf` (`apps/api/src/calc/calc-window-plan.ts`). This equals the existing `delta({kwh_total}, this_month)` figure. A decreasing register gives no bill.
- **D10. Cost seam.** `EnergyRateResolver` wraps `CalcParametersService`. A mapped location whose bill cannot be computed fails closed (no rate, cost `null`); it never falls back to the flat parameter. The calc engine and backfill keep `CalcParametersService`.
- **D11. Rounding.** `energyCharge`, `fixedCharge`, `wheelingCharge` are each rounded to 2 decimals once; `total` is their sum.
- **D12. Fleet reads.** The resolver and bill reads run on the fleet pool, for the reason `CalcParametersService` records (cross-organization cost reads, and the report render worker has no tenant actor). Each statement carries an organization equality (`lt.organization_id = a.organization_id`, organization rows joined on the pair's organization). Admin list reads and all writes use `withTenant`.
- **D13. Notes.** Column R goes to the slab's `notes`; category `notes` is `NULL` from the import.
- **D14. `source_url` is rendered as a link**, so every producer validates `^https?://`.
