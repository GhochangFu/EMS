## 1. Goal

Ship the five window functions and the `hours` helper in `bms-calc-v3`, end to end, so that a stored formula such as `delta({kwh}, today)` or `avg({kw}, 24h) * $energy_tariff_per_kwh` on an asset is evaluated by the scheduled sweep against the continuous aggregates (and, for `delta`, two index probes on `telemetry.point_values`), in the owning asset's location's timezone for a calendar window, writes nothing and counts `window_empty` / `timezone_unset` when it must, and stays a strict superset of `v2`. Concretely: the `window` token and two AST kinds (`window`, `hours`) behind the `v3` guard; `windowReads` on `ParseResult` bounded by `MAX_FORMULA_WINDOWS`; a pure segment planner that composes the coarsest aligned view whose watermark has passed and finer views for the remainder, never a raw range scan; a batched `CalcWindowsService` (≤ 7 statements per sweep); the host's resolve step beside `E4.1a`'s parameter step; three new refusal reasons; migration `0075` adding `bms.locations.timezone` (IANA, `varchar(64)`, nullable, no default), validated against `pg_timezone_names` on the location admin write path, seeded `Africa/Johannesburg` (Eskom demo) and `Asia/Kolkata` (PHE pilot), on the location admin form and the shared contract; the formula editor's window help, calendar warning and preview rows; and the three named guards as integration cases, each with a run mutation that reddens it.

**Out of scope, deliberately.** The stock sustainability points, the deferral-ledger promotions, the `energyTariffZar()` absorption, the DTO rename and `organizations.currency` (`E4.1c`). The `chore(agents):` sweep (already landed for ADR 0070). Backfill (ADR §9). Template KPI evaluation (`F2.33`). A window over a scope aggregate (ruling 4 — refused at parse time with its own message). A `$`/window completer in the editor (`E4.1a` Q9 deferred it; §10 Q7). A timezone on the onboarding draft (`onboarding-commit.service.ts:233` inserts locations without one; they stay `NULL` and a calendar window there refuses — recorded, not built). Sub-minute window boundaries (design decision 3).

## 3. Design decisions settled at this gate

1. **Structural superset, the `E4.1a` way.** Every window production sits behind `isV3` in the tokenizer and the parser; no `v1` or `v2` branch is edited. `limits.ts` gains `isWindowDialect(d) = d === CALC_DIALECT_V3` beside `isParameterDialect` — same truth today, a separate capability so a future `v4` decides each. Invariants part (b) widens to forbid `=== CALC_DIALECT_V3` outside the three grammar files.
2. **One new token kind, two new node kinds.** Token `window` (`text` = the literal `24h` or `today`; `position` = its first character), emitted under `v3` only: in the digit branch when an integer literal is immediately followed by one of `m|h|d` and then a non-identifier character (checked **before** the existing glued-suffix `malformed_number` rule, which keeps `24h` a `malformed_number` under `v1`/`v2` — measured, that is what the `v2` lexer says today); in the identifier branch when the text is one of `CALC_CALENDAR_WINDOWS`. Nodes: `CalcWindowFn = { kind: "window"; fn: "sum"|"avg"|"min"|"max"|"delta"; ref: CalcPointRef | CalcQualifiedRef; window: CalcWindow; position }` and `CalcHours = { kind: "hours"; window: CalcWindow; position }`, with `CalcWindow = { kind: "rolling"; minutes: number } | { kind: "calendar"; period: "today"|"this_week"|"this_month"|"this_year" }`. Two kinds, not one with a nullable `ref`, so `collectRefEntries`'s `assertNever` and `evalNode`'s TS2366 force every exhaustive consumer to decide. **The calendar words are reserved words in `v3`** (§10 Q6): the grammar has no variables, a bare identifier that is not a function is already a refusal, and `{today}` is untouched because the `{…}` branch never consults the word list.
3. **Window boundaries are minute-aligned.** The window ends at `floor_1m(bucketTimeMs(nowMs, intervalSeconds))` — for every stock interval (multiples of 60 s) exactly ADR 0037 decision 8's output timestamp; for a 10 s or 30 s interval the end is the tick's minute. A rolling start is `end − n minutes`; a calendar start comes from Postgres (decision 8). Consequence: `1m` always divides both ends, so **no aggregate window ever reads `telemetry.point_values`**; only `delta` does, with two `LIMIT 1` probes. Invariants part (e) scans for that. (§10 Q9.)
4. **The parser tells the forms apart by the token after the point reference.** `sum`/`avg`: `ident ( ref` then **`comma`** → window form, **`scope`** → the `v2` aggregate (one token of lookahead on the token array, `this.tokens[this.pos + 3]`); anything else falls into `parseAggregate` and refuses as today. `min`/`max`: `parseCall` parses the first argument as an expression; if the next two tokens are `comma`, `window` the call is the window form and the first argument must be a bare `ref` or `qref` node (`window_needs_point_reference` at the function name otherwise); else the n-ary scalar of `CALC_FUNCTION_ARITY`, unchanged. `delta` and `hours` are **not** in `CALC_FUNCTION_ARITY` (so `v1`/`v2` keep refusing them) and are parsed by `parseWindowCall` under `v3` only: `delta ( ref , window )`, `hours ( window )`. A window token anywhere else is `window_not_allowed`. `sum({kw} @site, 24h)` refuses as `window_over_aggregate` at the comma (ruling 4), naming the two-layer alternative.
5. **View selection: the coarsest aligned level whose watermark has passed, composed.** `planWindowSegments({ startMs, endMs, watermarks })` walks `1d → 1h → 5m → 1m`: at each level `L` the maximal `L`-aligned sub-interval `[ceil_L(start), floor_L(min(end, w_L)))` not yet covered becomes a segment; the head and tail it leaves go to finer levels; `1m` always finishes (its live branch covers the ≤ 2 minutes beyond `w_1m`; measured 0.7 ms for an hour of raw). Every width divides the coarser one, so the segments tile `[start, end)` exactly. Buckets are UTC-aligned (`time_bucket` without a zone in `0027`), so an IST day (18:30 UTC) is served by `5m` at its edges and `1h`/`1d` inside — decision 6's half-hour arithmetic falls out of alignment with no special case. **`1d` stays in the ladder** (§10 Q3). **The watermarks are read live once per sweep** through `_timescaledb_functions.cagg_watermark(id)` (measured callable by `bms_tenant`; ids from `_timescaledb_catalog.hypertable`, readable by `bms_tenant`), never assumed from `0027`'s offsets — measured today the `1d` watermark was `2026-09-19 00:00` against `now − 2d = 09-17 03:38`, because a manual `db:refresh-aggregates` had run (§10 Q11). Below a watermark the rows are materialized; above it the live branch — both correct; the rule only chooses cost.
6. **Semantics.** Per segment: `sum(sum_value), sum(sample_count), min(min_value), max(max_value)`; `combineSegments` gives `avg = Σsum/Σcount`, `min`, `max`, **`sum = avg × hours`** with `hours = (end − start) / 3.6e6` — never `Σsum_value` (Q6). `Σcount = 0` → `window_empty`. `delta` = last − first from two `ORDER BY time DESC/ASC LIMIT 1` probes inside `[start, end)` on `point_values_point_asset_time_idx (point_key, asset_id, time DESC)` — measured 1.5 ms over 30 days; one sample or none → `window_empty`. `hours(window)` is `(end − start)` for both kinds (§10 Q5); resolved by the host, never constant-folded (§10 Q10). The `366d` cap is enforced at **parse time** (`window_too_long`); `0h` is `malformed_window`.
7. **A window's point reference joins `refs` / `crossRefs` as the same node would bare.** `collectRefEntries` visits `node.ref`, so `{kwh}` inside `delta({kwh}, today)` lands in `refs` and `{TX_01.kw}` inside `avg({TX_01.kw}, 24h)` in `crossRefs`. Everything hanging off those lists applies unchanged: the latest-reading staleness rule (ADR decision 5), `validateFormula`'s `unknown_reference`, the api's cross-ref catalog check, membership resolution of the asset code (how the host learns the read asset for a qualified window), the dependency graph and both cycle detectors. `windowReads` is a fourth list for the host's resolve step, deduped by `windowKey`.
8. **The host learns the zone in the service's SQL, not in the definition load.** `CalcWindowsService` (a fleet read for the zone statement — `CalcParametersService`'s reason; `bms.locations` is FORCE-RLS) resolves every distinct `(owningAssetId, period)` in one statement — `unnest` joined to `bms.assets a JOIN bms.locations l` — returning `l.timezone` and `date_trunc(period, $tick AT TIME ZONE l.timezone) AT TIME ZONE l.timezone` as the start instant (measured: `'week'` in `Asia/Kolkata` at the tick → `2026-09-13 18:30 UTC`, a Monday; `'day'` → `09-18 18:30`; `'month'` → `08-31 18:30`). A `NULL` zone returns a `NULL` start → `timezone_unset`. The zone is the **owning** asset's even for a qualified reference (decision 6). No JS timezone library, no `Date` component read anywhere in the service.
9. **Batched once per sweep, ≤ 7 statements.** After membership and parameters the sweep collects every `(def, windowRead)` of every scheduled `v3` definition into `{ ownerAssetId, readAssetId, node }` (the read asset is the owner's for a `ref`, `membership.qualified.get(owner).get(code)` for a `qref`; an unresolved code is skipped here and refused as `unknown_asset_reference` by the existing cross-ref path). `resolveReads(requests, tickMs)` runs: (1) the four watermarks, (2) the calendar bounds, (3) one `unnest`-batched statement per level with ≥ 1 segment (`CROSS JOIN LATERAL` over the view — the `getLatestSamplesForPairs` shape, never `IN (unnest…)`), (4) the delta statement (two laterals). It returns `Map<string, WindowReadResult>` keyed by `inputKey(ownerAssetId, windowKey(node))`, each `{ ok: true, value } | { ok: false, reason: "window_empty" | "timezone_unset" }`. A thrown batch → every definition with `windowReads` refuses **`windows_unresolved`** (§10 Q8). Reads go through `TENANT_POOL` like `CalcInputsService` (views and raw are not policied); the zone statement through `FLEET_DRIZZLE`.
10. **Refusal order inside one formula:** parameters → local latest readings (`missing_input`/`stale_input`) → cross references → windows → `evaluate`. A meter with no sample at all is `missing_input`, as a `v1` formula over it would be; `window_empty` is what a live meter with nothing *inside the window* gets.
11. **`evaluate` gains a fifth positional map** `windows: ReadonlyMap<string, number> = EMPTY`, keyed by `windowKey(node)`; `case "window"` / `case "hours"` read it, absent → `missing_input` at the node's position. Sixteen callers compile unchanged; the scheduler and `calc-preview.ts` pass it.
12. **`MAX_FORMULA_WINDOWS = 8`** (§10 Q1, ruled 8 against the recommended 4 — symmetry with `MAX_FORMULA_CROSS_REFS` and `MAX_FORMULA_PARAM_REFS`), error `too_many_windows` at the ninth distinct read's position.
13. **`locations.timezone` is validated by an exact, case-sensitive match on `pg_timezone_names.name`** (measured: 599 rows, 70 ms — admin-rate), on create and on update when the body carries a non-null string; `null` clears; an absent key leaves it. The match is on an exact region/city name, so an exact region/city name is stored (`LIKE '%/%'`, `posix/` and `right/` excluded — PR 1 review Q1: `pg_timezone_names` also lists 46 slash-less names such as `EST`, a fixed −05:00); `Asia/Calcutta` and `Asia/Kolkata` are both exact names and both pass. The 400: `timezone must be an IANA zone name the database knows — for example Asia/Kolkata or Africa/Johannesburg — and "<value>" is not one`. Not a `CHECK` (a view cannot back one) and not `AT TIME ZONE` in a `try` (that accepts abbreviations such as `IST`, which is ambiguous). The web offers a `<datalist>` from `Intl.supportedValuesOf("timeZone")` (guarded by `typeof`), no endpoint (§10 Q13).
14. **The Eskom seed sets `Africa/Johannesburg`; the PHE pilot seed sets `Asia/Kolkata`** (§10 Q12, ruled IST against the recommended SAST — the pilot site is in India): `eskom-locations-seed.ts` and `phe-pilot-seed.ts` are update-or-insert with one `values` object each, so a re-seed (`docker compose up` re-seeds) stamps existing rows; no count changes, so the seed's verification is untouched. The migration backfills nothing (ruling 6).
15. **The calendar warning is a hint, not a problem.** `template-calc-config.ts`'s `PointGridProblem`s block a save; the ADR says the validator *warns* and cannot refuse. The warning renders as a hint line in `calculations-tab.tsx` (beside `V3_TRIGGER_LATENCY_HINT`) and in the preview panel whenever `previewWindowReads(expression, dialect)` contains a calendar window; the API adds nothing.
16. **Cagg fixture protocol for the integration spec.** A raw row inserted **behind** a level's watermark is invisible in that level until a refresh re-covers it (`0027`'s header records the delete side of the same fact). So the spec inserts every fixture row at least 3 h in the past, then `SET ROLE bms_rollup` (granted `SET TRUE` to `bms_fleet` in `roles.ts:127`; the views are owned by `bms_rollup`, measured) and `CALL refresh_continuous_aggregate` for `1m → 5m → 1h → 1d` over the **complete** buckets containing the rows — never an incomplete bucket, so no watermark moves past `floor(now)` and the stack's live data is never materialized half-full; and repeats the same after the `afterAll` delete (the `0027` standing obligation). A helper `apps/api/src/testing/cagg-materialize.ts` holds it; `tests/adr-0037` scans `apps/api/src/calc/` only.
