## 1. Goal

Author the nine classes of `docs/e5.3-derived-taglist-v1.md` as nine more `StockAssetTemplateEntry` values in a new **facility pack**, so that every organization can import a lighting zone, a fire alarm panel, an access door, an occupancy zone, a parking level, an IAQ node, a BAS gateway, a lift or an escalator through the mechanism `F2.13` built and `E5.1`/`E5.2` proved. Four things land, across two pull requests:

1. **A domain (PR 1).** `bms.asset_domains` gains its seventh row — `facility` / `Facility` / `sort_order 70` — as one more entry in `PACK_ASSET_DOMAINS` (`packages/db/src/asset-domains-seed.ts`), the module `E5.2` wrote for exactly this. `verifyHierarchySeed`'s Pass 1 count is already **derived** from that list and moves to 7 by itself; the seed spec's literal is a deliberate edit.
2. **A vocabulary (PR 1 + PR 2).** Three arrays in a **new** file `packages/shared/src/facility-point-keys.ts` (§4.5 says why not `constants.ts`): `FACILITY_CLASS_POINT_KEYS` (**91** = 89 table codes + 2 promotions), `ENVIRONMENT_CLASS_POINT_KEYS` (**13** = 11 + 2) in PR 1, `VERTICAL_TRANSPORT_CLASS_POINT_KEYS` (**102** = 99 + 3) in PR 2 — **206** codes, 206 `UNIT_BY_KEY` entries, three `keysForDomain(…)` lines, three `ARRAY_DOMAIN` entries, and every guard bound moved twice. `bms.point_keys` goes **398 → 502 → 604** on a cold start. The 11 already-seeded codes are **referenced, never redeclared** (§4.2).
3. **Nine entries.** `facility-lighting-zone`, `facility-fire-panel`, `facility-access-door`, `facility-occupancy-zone`, `facility-parking-level`, `environment-iaq-node`, `facility-bas-gateway` (PR 1); `mechanical-lift`, `mechanical-escalator` (PR 2) — **document order** (ADR 0054 decision 1), one pack index `facility.ts`, three domains, prefix = domain (decision 2). Each declares its section's rows as template points (`C` → core/required, `X` → extended/optional, `M` → manual/optional), its alarm bullets as **pair-absent philosophy rows** (decision 5), **maintenance plans** (decision 8), and **no `content.kpis`** (decision 6).
4. **Eight derived promotions, nine points.** Of the tag list's **48 distinct** named derived codes (51 mentions — §4.1; the ADR's 37 is corrected at closure), **8 are expressible** in `bms-calc-v1` over measured siblings of their own entry and are authored with real formulas (9 point instances: `occupancy_pct` is one code, two entries, two formulas — the `recovery_pct` shape). When PR 2 lands, the 2026-08-22 sheet's use-case header (hotels, data centres, townships) has building-subsystem product behind it, the SOW footer's *Data Quality* number has the gateway class it is computed from (and `data_quality_pct` itself stays deferred to the estate surface, decision 6), and the catalog stands at **27 entries**.

## 3. Serial or parallel, and the model per pass

**Serial. Two branches in sequence, one `implementer` pass at a time. Do not fan out.**

Nine classes look like nine siblings and are not, for `E5.2` §3's reason and two more. Every entry writes the same shared files — `facility.ts` (the index), `stock-catalog-deferrals.spec.ts` (`STOCK_ENTRY_CODES`, `DEFERRED_DERIVED_CODES`), `tests/f2.13` (`STOCK_ASSET_RELS`, one number per file), `facility-point-keys.ts`, `point-keys-seed.ts` — and PR 2 **depends on PR 1** twice over: `controller_comms_ok` (§3 declares it, §8a/§8b reference it) and the `facility.ts` index both lift and escalator join.
