## 0. Decisions

**D1 — Map shape; the messages are restated, not shared.**
`apps/api/src/admin/rtus/rtus-conflict.ts` gains

```ts
export type RtuUniqueConflictScope = "global" | "location";
export type RtuUniqueConflict = { readonly scope: RtuUniqueConflictScope; readonly message: string };
export const RTU_UNIQUE_CONFLICTS: ReadonlyMap<string, RtuUniqueConflict>  // four entries
export function translateRtuUniqueConflict(err: unknown): unknown           // replaces translateRtuCodeCollision
```

A `Map`, not an object literal, for the reason `onboarding-commit-conflict.ts` records (a lookup by a driver-supplied string on a plain object finds `Object.prototype` members). The guard stays narrow on both axes: `code === "23505"` **and** `typeof constraint === "string"`, then `RTU_UNIQUE_CONFLICTS.get(constraint) ?? null` → `new ConflictException(entry.message)`; anything else is returned by identity, so `throw translateRtuUniqueConflict(err)` re-throws the original object.

**Not one source with onboarding.** `COMMIT_UNIQUE_CONFLICTS` sentences are batch-phrased ("… in this draft …") and would be false on a single-resource `POST`/`PATCH`. Importing the map would also import `CommitConflictField` and the `{formErrors, fieldErrors}` 400 shape — the coupling `F4.60` refused. `F4.60` already restated the `rtuCode` sentence for this reason; the three new ones follow.

| constraint | scope | constant | message |
|---|---|---|---|
| `rtus_rtu_code_idx` | global | `RTU_CODE_TAKEN_MESSAGE` | unchanged, owner-ruled verbatim |
| `rtus_external_rtu_idx` | global | `RTU_EXTERNAL_ID_TAKEN_MESSAGE` | "That externalRtuId is already taken. Choose a different externalRtuId." |
| `rtus_mqtt_topic_idx` | global | `RTU_MQTT_TOPIC_TAKEN_MESSAGE` | "That mqttTopic is already taken. Choose a different mqttTopic." |
| `rtus_location_code_unique` | location | `RTU_LOCATION_CODE_TAKEN_MESSAGE` | "Another RTU at this location already uses that code. Choose a different code." |

**Status is 409 for all four.** `F4.60`'s reasoning is about the route shape (one resource, an identity key colliding with existing state, `deactivate` already answers 409), not the constraint.

**`rtus_location_code_unique` may name the location.** Its key is `("location_id", "code")` (migration `0016`). On `create` the caller passed `canManageLocation` for `body.locationId`; on `update` the location is `existing.locationId`, which the caller also passed, and `location_id` is not updatable (`updateRtuBodySchema` omits it). So the colliding row is always at a location the caller manages, and "at this location" discloses nothing. The sentence contains "another", which is in `CROSS_TENANT_LOCUS_WORDS`; the scan skips `scope: "location"` and a control pins the exact set of global names. The other two keys are bare-column fleet-wide partial uniques (`0016`) and take constant-only wording like `rtuCode`.

**D2 — Reachability: all six new cells are reachable through the API.** `updateRtuBodySchema = createRtuBodySchema.omit({ locationId: true }).partial()`; `update`'s `.set()` restates every column.

**D3 — Tests.** Unit on the map (one claim per `it()`), a service-level fake for the wiring negative, six integration cells against the real DB.

**D4 — Prose.** `rtus.service.ts` (the `.catch` comments) and the `rtus-conflict.ts` docblock say the three still pass through; both are rewritten. Three sites name the integration spec file, which is renamed.

**D5 — Verification layers.** Database: one probe. API: container not stale + integration suite + one live `fetch` per constraint from the logged-in SPA tab (OIDC, the human logs in). Browser: N/A with a reason and one finding (§7).
