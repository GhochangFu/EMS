## 1. Goal, and what is out of scope

**Goal.** A rule whose stored `action` is `{ type: "notify" }` sends to the
channels joined to it when its alarm **opens**, on both raise paths — the
on-demand `POST /api/v1/rules/evaluate` sweep and the streaming
`LISTEN bms_telemetry` engine — and records every attempt in
`bms.notification_deliveries`. Today `NotificationsService.dispatch` has **no
production caller** (measured: `grep -rn "\.dispatch(" apps/api/src` matches only
`notifications.service.spec.ts` and `storm-control.integration.spec.ts`; the
`apps/web` hits are CodeMirror's `view.dispatch`, unrelated). This item adds the
two callers, one pure module that decides *whether* to call, and the cache column
the streaming engine lacks. `AlarmRaiser` stays ADR 0033's sole writer of
`bms.alarms` and does not notify.

**Explicitly out of scope.**

- **No change to `NotificationsService.dispatch`'s behaviour** — dedupe, rate
  limit, transports and the ledger are `F3.8`'s and stay as built. One doc
  comment in it goes stale and is corrected (§4).
- **No widening of `AlarmRaiseRule`** (decision 9, rejected). The raiser's
  *result* is widened by two fields (D1) so the notification text is the alarm
  text by construction; the raiser's *input* and its one job are unchanged.
- **No behaviour for `review`** beyond "sends nothing" (Q3). No enum change, no
  contract change, no seed change.
- **No notification for `time_window` rules.** They never raise (`shouldRaise`
  requires `ruleType === "threshold"`), so there is no transition to key on
  (decision 7). The stale sentence in `shouldRaise`'s doc that says `F3.7` will
  read time-window matches is corrected (D4).
- **No escalation, no auto-clear** (`F3.10`), **no SMS/push** (`F3.9`), **no
  queue** (decision 1; `F4.24`).
- **No new API route and no new response contract.** The per-rule channel picker
  (Q1, Task 5) reads and writes routes `F3.8` already shipped.
- **No retention policy for `bms.notification_deliveries`.** Q2 is where its
  growth is bounded by *not writing* rows the streaming path would otherwise
  write; a retention policy would be DDL and a decision, neither of which this
  row carries.
- **The `docs/BACKLOG.md` closure row, `docs/roadmap.md:2232` and
  `AGENTS.md:2052-2053`** ("`F3.7` … is unblocked but unbuilt") — the caller's
  `chore(agents):` sweep, not this branch (§9.10).

### What `dispatch` does with what the callers give it (read, not assumed)

`dispatch(input: DispatchInput): Promise<DeliveryResult[]>` with
`DispatchInput = { ruleId, ruleCode, organizationId: string, alarmId: string | null,
severity: string | null, message: string, raised: boolean }`. It **never
rejects**: a failed `loadForRule` returns `[]`, a transport throw becomes a
`failed` row, and a failed ledger insert is logged (`record()`'s own `catch`).
No joined channel → empty array, **no row**. `raised === false` →
`skipped_deduped` row per joined channel and **no transport call**. The dedupe
key is `ruleId:alarmId|no-alarm:severity|no-severity` (`dedupe-key.ts`), so a
message-text difference never defeats it.

So, to the two questions the caller asked: **yes, the transition dedupe is a
raise-only send** — a transport is touched only when `AlarmRaiser.raise` returned
`raised: true`, which `alarms_open_per_rule_uidx` guarantees happens once per
(asset, rule) while the alarm is unacknowledged. **An on-demand
`POST /rules/evaluate` against an already-open alarm** attempts the raise, gets
`{ raised: false, alarmId: null }`, and (with Q2 as recommended) writes one
`skipped_deduped` row per joined channel and sends nothing. After an
acknowledgement, the next matching evaluation opens a new `bms.alarms` row, which
is a new transition with a new dedupe key, and that sends — by design
(`dedupe-key.ts:13-15`).

### Decisions this plan makes

**D1. `AlarmRaiseResult` gains `severity: string` and `message: string`.** Both
are computed by `raise()` before any write (`defaultAlarmSeverity`,
`composeAlarmMessage`); returning them means the notification's subject and body
are what `bms.alarms.severity` / `message` hold, by construction, and the dedupe
key carries the *defaulted* severity rather than a raw `null`. The alternative —
each caller recomputing both pure functions — leaves `alarm-raise.service.ts`
untouched but computes the same thing twice and lets the two drift. This widens
the raiser's *report*, not its *input*, so decision 9's rejection of a widened
`AlarmRaiseRule` is respected and the raiser still does not notify. Known edge:
the E7.1b org-mismatch refusal also returns `raised: false`, so on the on-demand
path it would be recorded as `skipped_deduped`; that is a diverged rule that
already logs a warning, and distinguishing it is not this row's work.

**D2. One pure module decides.** `apps/api/src/rules/rule-actions.ts` holds
`shouldNotify(action)`, `toDispatchInput(rule, raise)` and `notifyOnRaise(...)`
(the fire-and-forget call). Both call sites call `notifyOnRaise` and nothing
else, so the action vocabulary is read in exactly one place — which is also
where `review` would be given a meaning later.

**D3. Dispatch is fire-and-forget at both call sites** (decision 1): `void
notifications.dispatch(input).catch(warn)`. It is never awaited, so a hanging
SMTP server cannot delay the next rule's raise in a streaming batch or the HTTP
response of the sweep. The consequence for the tests is that a real-database
assertion polls the ledger with a bounded `until()` helper rather than awaiting
the call.

**D4. Two stale comments are corrected in the feature commits, not the sweep,
because they are code:** `notifications.service.ts:43-46` ("`dispatch` has no
production caller today") and `alarm-raise.service.ts:23-25` (a time-window
match "is a fact `F3.7`'s notification actions will read" — it is not; see out of
scope).

### Rulings (owner, 2026-09-06, all three as recommended)

### Open questions — the owner answers these before the first line of code

**Q1. Does `F3.7` ship the per-rule channel picker?** Measured: `F3.8` shipped
`GET`/`PUT /api/v1/rules/:id/notifications` and the two client functions, but no
component calls them; `bms.rule_notifications` has 0 rows; the rules card prints
`Action: notify · Operations` and the builder offers a three-option `<select>`
with no help text. Without a picker, the only way to make any rule notify is a
hand-made `PUT`, and this item's browser layer can be verified only by a `fetch`
from the SPA tab. **Recommendation: yes, include it (Task 5).** The precedent is
ADR 0041 decision 10 — the owner ruled that an item closed with its browser layer
N/A is not closed, and moved `F3.8`'s admin UI into the row for that reason.
Cost: one component with a jsdom spec, no new route, no new contract.
Alternative: a new BACKLOG row for the picker, and `F3.7`'s browser layer
verified through the `fetch` path.

**Q2. On the streaming path, does a non-transition write a `skipped_deduped`
row?** Decision 4 says every attempt writes a row; decision 7 says the send keys
on the transition. Read together for the streaming engine they mean: for every
batch in which an already-open alarm's condition still holds, one
`skipped_deduped` row per joined channel. Arithmetic at today's numbers: 5
batches/min × 118 open rules × 1 channel = **35,400 rows per hour per channel**,
into a table with no retention policy, onto a deliveries view whose default page
is 100 rows — every page would be skips. **Recommendation: the streaming path
dispatches only when `raised === true`; the on-demand path dispatches on every
attempted raise and passes `raised` through.** The on-demand sweep is one human
pressing a button, and its `skipped_deduped` rows answer "I pressed Evaluate now
— why was nobody told?", which is exactly the shape `F3.8`'s storm-control
integration test asserts. A streaming engine re-observing an open alarm every
12 seconds is not an attempt to notify anyone. Either ruling is a one-line guard
at each call site; Tasks 2 and 3 name where. If the owner rules symmetric
raise-only on both paths, delete the `skipped_deduped` assertion from Task 2's
spec and note that the status is then reachable only from `sendTest`-adjacent
paths.

**Q3. What is `review`?** Measured: accepted by `rules.schema.ts:51` and
`packages/shared/src/contracts/operations.ts:544`; narrowed by `asAction`
(`rule-mapping.ts:58-67`, default `trace_only`); rendered as an `<option>` and in
the card text; branched on by **nothing**; carried by one seeded, disabled
`time_window` rule whose description reads "prompt energy review". No ADR, no
BACKLOG row and no UI copy define it. **Recommendation: `F3.7` treats `review`
as inert — `shouldNotify` is `type === "notify"` only — and adds no behaviour or
copy.** The owner then chooses, later and outside this row: leave it; remove it
from the enum (a contract change plus the seed row); or give it a meaning under
`F3.10` escalation or a work-order action (an ADR). The only work this
recommendation needs is the predicate's negative case in Task 1's spec.
