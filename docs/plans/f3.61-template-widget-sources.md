## 1. Goal

An administrator authoring a section dashboard template can see, add and remove a widget's **named metrics** (`sources`, the metric-catalog binding of ADR 0048 decision 2) exactly as they can its role bindings today. `WidgetEditor` (`apps/web/src/components/dashboard-templates/widget-editor.tsx`) gains a **Named metric** block that mirrors `WidgetInspector`'s (`apps/web/src/components/dashboards/widget-inspector.tsx:532–573`): a list of the bound entries by catalog label, a per-row remove control, and — on the editable arm — the existing `MetricSourcePicker`, reused unchanged. The block renders only for a widget type whose `WIDGET_CATALOG[type].sources.max > 0` (a `value_tile` or a `table`), so a gauge, tank or chart shows no empty field. The two pickers are mutually exclusive on screen — the role picker hides once a metric is bound and the metric picker hides once a role is bound — and the same rule lands in the contract: `sectionTemplateWidgetIdentitySchema` refuses a widget carrying both `bindings` and `sources`, so a `PATCH` cannot store what the screen will not draw. **"Neither" stays legal**, because that is the state *Add widget* creates. Both consumers of `WidgetEditor` — the authoring detail page and the `F3.44` read-only stock viewer — show the list; only the authoring page shows the picker and the remove control. Every stock catalog entry passes the new rule unchanged (measured: 0 of 49 widgets carry both).

**Amendment 1 (owner, 2026-09-18):** the same contract also refuses what the live builder refuses and the template path never did — a source whose shape the widget type cannot draw, more sources than the type's cap, and a `table` projecting a column its bound dataset does not declare (or the same column twice). A `PATCH` can no longer store, and instantiation can no longer copy through, a widget the dashboard write path would have answered 400 for. The *minimum* is deliberately not enforced (§11.2.3): a template widget with nothing bound stays legal, as it always has for role bindings.

## 2. Out of scope

- **A `params` editor.** Every catalog entry's write schema is `z.object({}).strict()` (`METRIC_CATALOG_PARAMS_WRITE`), so any field added would be a 400 the author cannot act on, and an id in `params` is the ADR 0019 problem `tests/f3.35-metric-catalog-containment.test.ts` scans for. Add sends `params: {}` and nothing else — the inspector's own reason (`widget-inspector.tsx:94–105`).
- **A `TableColumnPicker` on a template widget, and clearing `config.columns` on remove.** §5.3 — measured, no in-scope path can put a column projection on a template widget, so a clear would be a branch that can never fire. `updateWidget`'s "never `config`" invariant stays true.
- **A widget-type selector on the template page.** *Add widget* still hardcodes `value_tile` (`dashboard-template-detail-page.tsx:200`). A `table` widget enters a draft by stock import only. Pre-existing, unchanged.
- **Enforcing a binding *minimum* on the template** (`sourcesFieldFor.min(1)` for a table, `pointsFieldFor.min(1)` for a gauge). §11.2.3 — ADR 0049 decision 6 makes an unbound widget a "No data bound." widget, never a failed import, and the remove control in Task 4 produces exactly that state.
- **Moving `eachSourceFitsTheWidget` / `noDuplicateSources` / `eachTableColumnIsDeclared` out of `dashboards.schema.ts` into `packages/shared`.** §11.2.2 — restated reading the shared records and messages, pinned by Task 1c's scan; extraction is a later refactor.
- **A catalog endpoint.** Measured: `MetricSourcePicker` fetches nothing; `catalogKeysFor` reads `METRIC_CATALOG` and `WIDGET_SOURCE_SHAPES` from `@bms/shared` at build time.
- **Changing `WidgetInspector`, `MetricSourcePicker`, `metric-catalog.ts` or `dashboard-builder-form.ts`.** All consumed as they are.
- **Renumbering `sortOrder` on remove.** The bindings arm filters without renumbering (`widget-editor.tsx:120`); the metric arm mirrors it, and instantiation reads `source.sortOrder ?? index` (`…instantiate.service.ts:258`).

## 5. The decisions

### 5.1 Mirror the inspector's block inside `WidgetEditor`; do not extract a shared "sources field"

The inspector's block is twelve lines of JSX over `DashboardWidgetRow` (`points`, `config.tableColumns`, a `Field` wrapper); the editor's rows are `SectionTemplateWidgetInput` (`bindings`, contract `config`) with its own `<span>`/`<ul>` styling. A shared component would need a props adapter on both sides for one list and one picker. The units that must not drift already exist and are reused: `MetricSourcePicker`, `metricCatalogLabel`, `WIDGET_CATALOG[type].sources`. DRY at the vocabulary, not at the JSX — the F3.44 §5.6 argument.

### 5.2 Narrow `SectionTemplateSourceInput.catalogKey` to `MetricCatalogKey`

`string` is wider than what the request schema accepts (`metricCatalogKeySchema`), and it forces a runtime narrowing at every read (`metricCatalogLabel`, `bound`). Importing the type from `@bms/shared` is what the file already does for `WidgetPointRole` and `DashboardSectionCode`; the api-client docblock's "restated, not imported" rule is about `apps/api`'s *write schema*, not shared *types*. The DTO the pages cast from already carries the narrow type, so no caller changes. A runtime guard was considered and rejected: it would make a label lookup a branch that can only ever succeed.

### 5.3 Removing a source on a template widget does **not** clear `config.columns`

Measured in §4: no in-scope path can put `columns` on a template widget (no picker on the page, no stock entry carries one, *Add widget* makes a tile). `widgetRowAfterRemovingSource`'s reason for clearing — "an author rebinds and `eachTableColumnIsDeclared` answers 400 for a change they never made" — cannot arise here, because nothing on this surface sets the field and the template write path does not even run that rule. A clear would therefore be a branch that can never fire, and it would make `updateWidget`'s "never `config`" cast comment false for a case that does not exist. The remove patch is `{ sources: filtered }` and nothing else; `widget-editor.spec.tsx` pins the absence of a `config` key in the patch so a later "helpful" clear is a deliberate change, not drift. The real gap (§2, open question 1) is the template-side cross-field rule and the copy-through at instantiation — that is a contract-and-service row, not a click-handler one.

### 5.4 The contract rule: a third issue in the existing `superRefine`, on `["sources"]`, with its own message

One node, one description — the file's own reason for not chaining `.refine`s (lines 143–159). The refinement lives on the identity schema, which cannot see `widgetType`, so `bindingExclusiveMessage(label)` cannot be fed and its wording ("a bound point") is the live dashboard's, not a template's. Message: `a widget binds asset roles or catalog sources, never both — remove one kind`. Path `["sources"]`: the arm this row adds, and the one the screen's picker fills. **"Neither" is not refused** — *Add widget* produces it, and the dashboard path's `bindingRequiredMessage` half has no template analogue. The `.describe()` after the refinement gains the third sentence (ADR 0029 Amendment 1 fact F). Because `tests/adr-0029-openapi-contract.test.ts` scans only `*.schema.ts`, the *order* of that `.describe()` has no gate in `contracts/` today; Task 1's spec asserts `sectionTemplateWidgetIdentitySchema.description` names the rule — a `.describe()` moved before the refinement leaves the outer `ZodEffects` with `description === undefined` and reddens it.

### 5.5 Where the tests live

A component spec, `widget-editor.spec.tsx`, is warranted: the cases are about the gates (cardinality, two exclusivities, the add payload, the remove payload) across three widget types, and driving them through either page would mean a stubbed template per type and a page render per claim. The precedent is `metric-source-picker.spec.tsx`. The page specs get **one case each** for what the component spec structurally cannot see — the detail page's `updateWidget` round-trip (patch → state → re-render → the *other* picker disappears) and the viewer's `editable={false}` on the new controls.

### 5.6 The second refinement node (Amendment 1)

§11.2.1 — a `superRefine` on `sectionTemplateWidgetSchema`, three rules (R4 shape, R5 cap, R7 columns), widget-key-prefixed messages built from the shared templates, `.describe()` after it naming all three. The identity node is untouched beyond Task 1.

### 5.7 Restate, read the records, pin with a scan

§11.2.2.

### 5.8 No minimum on the template

§11.2.3. The remove control's zero-source table saves; the live builder refuses it at the next `PUT` as it refuses an unresolved gauge today.

### 11.2 Decisions

**11.2.1 Where the rules live — a second `superRefine`, on `sectionTemplateWidgetSchema`.** The identity node keeps its three rules (they need only `bindings`/`sources`); the intersection node holds the three that need `widgetType` and `config`. Not on the content schema: a rule about one widget belongs on the widget, and the dashboards path put its per-widget rules on the *array* only because `z.discriminatedUnion` refuses a refined arm — a constraint an intersection does not have. Two `ZodEffects` nodes, two `.describe()`s, each after its own refinement (fact F); measured to survive (§11.1). Issue paths, widget-relative (zod prefixes `["widgets", i]` through the array):

| Rule | Condition | Path | Message |
|---|---|---|---|
| R4 shape | `!WIDGET_SOURCE_SHAPES[widgetType].includes(METRIC_CATALOG[source.catalogKey].shape)` | `["sources", j, "catalogKey"]` | `Widget "<key>": ` + `bindingShapeMessage(widgetType, catalogKey, shape)` |
| R5 cap | `sources.length > WIDGET_SOURCE_CARDINALITY[widgetType].max` | `["sources"]` | `Widget "<key>": a <widgetType> widget accepts at most <max> catalog binding(s)` — `sourcesFieldFor`'s own `.max` sentence |
| R7 columns | `widgetType === "table"`, `config.columns` non-empty, a source bound whose shape is `dataset`: each column not in `METRIC_CATALOG[key].columns`, and each repeat | `["config", "columns", c]` | `Widget "<key>": ` + `columnNotDeclaredMessage(column, catalogKey)` / `duplicateColumnMessage(column)` |

Every message is prefixed with the widget `key`, because `flatten()` collapses the path to `content:` on the wire (§11.1) — `publish()` already prefixes its own refusals this way (`Widget "${widget.key}" binds unknown catalog entry …`, service line 308). R7 keeps the dashboards path's early return when no source is bound, so it never throws on `binding.catalogKey` (the guard the correctness review proved load-bearing); "columns with no dataset" is therefore a stored-but-inert projection, refused at the live builder's next save by `sourcesFieldFor.min(1)`, and unreachable from any UI here (no column picker on templates). A chart with a source fires R4 *and* R5 on one parse — the API does the same (`.max(0)` plus the shape refinement); not deduplicated, deliberately mirrored. Duplicate source keys are not a separate rule: every `max` is 0 or 1, so a duplicate is over the cap; recorded so nobody adds `noDuplicateSources` here and calls it a fix.

**11.2.2 Reuse: restate, reading the shared records and messages; do not move the API helpers.** `eachSourceFitsTheWidget`, `noDuplicateSources` and `eachTableColumnIsDeclared` are pure over `@bms/shared` records and *could* move; `sourcesFieldFor` is a request-schema factory (ADR 0030 decision 3 keeps it in `apps/api`); `exactlyOneBindingKind` must be restated (`points` vs `bindings`, and the template has no "neither" half). Moving the three would (i) put `RefinementCtx`-shaped validators with the API's array-relative paths into the response-contract package, (ii) falsify the twelve prose sites in §11.1 that place them in `dashboards.schema.ts`, and (iii) reopen a write path with its own 600-line spec. The precedent is this file's own: the grid-fit and duplicate-binding rules restate `eachWidgetFitsTheGrid` / `noDuplicateBindings` while reading `DASHBOARD_GRID` — and `tests/f3.1d` pins that the *numbers* are read, not restated. The amendment does the same for these three: read `WIDGET_SOURCE_SHAPES`, `WIDGET_SOURCE_CARDINALITY`, `METRIC_CATALOG` and the three message templates, and pin that with Task 1c's scan. Extraction into a shared per-widget helper is a legitimate later refactor and is not this row's.

**11.2.3 The `min` is not enforced on the template — only shape, cap and columns.** Three reasons, all measured: (a) the template contract enforces no minimum for `bindings` either — an unresolved gauge is a legal, publishable, instantiable template by ADR 0049 decision 6, and a table at zero sources is the same class ("No data bound.", `dashboard-widget-data.ts:479`); (b) zero sources on a table is precisely the state Task 4's remove control produces, and refusing it on `PATCH` would turn "remove the metric, Save canvas" into a 400 that reads `content: …` with nothing more; (c) `value_tile {0,1}` — "neither" stays legal for a tile, as §1 already says, so *Add widget* keeps working. **Consequence, stated:** a freshly instantiated dashboard with a zero-binding widget of *any* type is refused by `PUT /dashboards/:id/widgets` until the author binds it — pre-existing for points, extended to a table's source by this ruling, and the renderer's reserved empty state is the intended intermediate.

**11.2.4 Divergence between an instantiated dashboard and `PUT /dashboards/:id/widgets`, after the amendment.** Matches: grid (R1 ≡ `eachWidgetFitsTheGrid`), duplicate bindings (R2 ≈ `noDuplicateBindings`, plus instantiation's own per-point dedupe), both kinds (R3 ≡ the "both" half of `exactlyOneBindingKind`), shape (R4 ≡ `eachSourceFitsTheWidget`), cap (R5 ≡ `sourcesFieldFor.max`), columns (R7 ≡ `eachTableColumnIsDeclared`, duplicates included), points cap (instantiation truncates to `WIDGET_POINT_CARDINALITY.max`), config (same `dashboardWidgetSpecSchema`; stripped before the copy), `params` (`publish()` applies `METRIC_CATALOG_PARAMS_WRITE`; only a published template instantiates). **The one remaining divergence is "neither"** (§11.2.3), recorded and intended. `dashboard-templates-instantiate.service.ts` is not in the diff.
