## Goal

A window `sum` (`sum({kw}, 24h)`, `sum({kl}, this_month)`, every rolling or calendar `sum`, stock or client-authored) refuses with a new reason `window_sparse` when the covered time of its window is below 90% of the elapsed window. Covered time is counted per segment inside the level statement `readLevel` already runs — a `1d` bucket with samples is 24 h, a `1h` bucket is 1 h, and on `5m`/`1m` each distinct clock hour that holds a non-empty bucket counts, clipped to the segment (the one-hour floor). The host treats `window_sparse` exactly as `window_empty`: no row written, `bms_api_calc_skipped_total{reason="window_sparse"}` incremented, `CalcStatusRegistry` records it. `window_empty` keeps precedence. `avg`, `min`, `max`, `delta` and `hours` are unchanged. The statement budget of seven per sweep holds.

**Out of scope (ruled, do not build):** a coverage figure of its own, proration, a per-window-kind threshold, a calc parameter for the threshold, a tile change, a label change, a stock-version bump, a migration, a contract change (`lastSkipReason` is `z.string()`), the five availability rows' silent-device exposure (decision 2, the owner's to raise), and the `chore(agents):` sweep of AGENTS.md's calculation paragraph (owed at closure, **separate PR**).

## Design (read before Task 1)

**Where the fold lives.** The amendment demands a *pure* spec of the covered-time fold, so the arithmetic cannot live only in SQL. The level statement returns **three facts per segment**, all plain aggregates in the existing `CROSS JOIN LATERAL` (one scan, one `FROM ${relation}`, no subquery, no window function, no new statement):

- `covered_units` — `count(DISTINCT time_bucket(<unit>, v.bucket)) FILTER (WHERE v.sample_count > 0)`
- `head_covered` — `coalesce(bool_or(time_bucket(<unit>, v.bucket) = time_bucket(<unit>, p.from_t)) FILTER (WHERE v.sample_count > 0), false)`
- `tail_covered` — the same against `time_bucket(<unit>, p.to_t - interval '1 millisecond')`

`<unit>` is `INTERVAL '1 day'` for the `1d` level and `INTERVAL '1 hour'` for the other three — a literal chosen in TS from a closed map beside `VIEW_NAMES`, never from the formula (the `PERIOD_UNIT` precedent). `time_bucket` on `timestamptz` with these widths is epoch-aligned in UTC, the same alignment as the `0027` views and as `LEVEL_MS` flooring in the planner, so the session `TimeZone` cannot leak in.

A pure function `coveredHoursOf(segment, facts)` in `calc-window-plan.ts` turns the facts into hours: unit width is `LEVEL_MS["1d"]` for `1d` and `HOUR_MS` otherwise; if the segment lies inside one unit, covered = `coveredUnits > 0 ? (toMs − fromMs) / HOUR_MS : 0`; else covered = `coveredUnits × unitHours − (headCovered ? (fromMs − floor(fromMs)) / HOUR_MS : 0) − (tailCovered ? (floor(toMs − 1) + unit − toMs) / HOUR_MS : 0)`. For `1d` and `1h` the segments are level-aligned, so both clips are zero by construction and only `coveredUnits` matters. `readLevel` calls it with the segment it already holds (`targets[row.idx].segment`) and stores the result as `SegmentRow.coveredHours`. `combineSegments` sums `coveredHours` over the rows and guards `sum` only — `avg`/`min`/`max` read the same rows and ignore the field.

**Fail closed.** `combineSegments` computes `fraction = covered / elapsedHours` and the **answering** branch is `fraction >= MIN_WINDOW_COVERAGE`; anything else (including `NaN`) refuses `window_sparse`. `window_empty` is decided first, on the existing `count === 0 || min === null || max === null` test.

**Two SQL traps, named so nobody rediscovers them.** `sum(DISTINCT clipped_length)` dedupes by value, not by hour — wrong. `count(*)` instead of `count(DISTINCT hour)` over-counts a `5m` segment with two buckets in one hour — the integration case S5 is built with two buckets in one hour so this mutation reddens.

**Existing sums that now depend on coverage.** W2, W2c and W8 in `calc-windows.integration.spec.ts` read `sum({kw}, 24h)` over day `D`, which holds samples in only two of its 24 hours. They stay green only because the fixture's `materializeCompleteBuckets` moves the `1d` watermark past `D`, so the day is served from `1d` at day resolution (covered 24/24). If one of them turns red after Task 2, the cause is the level that served the day, not the guard. Task 2 adds a comment on W2 saying so.
