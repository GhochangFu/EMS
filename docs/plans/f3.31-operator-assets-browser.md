## 1. Goal

Give every authenticated user a read-only `/assets` route under *Operations*
that lists the assets in their `readableAssetIds` scope as a table — Code ·
Name · Site · Domain · RTU · Source · Active — with client-side text, domain
and site filters, and a side panel per row that shows the row's columns, the
asset's health score (`GET /asset-health/assets/:id`) and the asset's `F3.2`
default dashboards as links to `/dashboards/<slug>` (`GET
/dashboards?assetId=`). To feed it, `GET /api/v1/assets` gains one `LEFT JOIN
bms.rtus` and six fields, `assetPickerRowSchema` is renamed
`assetListRowSchema` and widened, and `listDashboardsQuerySchema` gains
`assetId` (decisions 1–5, 7).

**Out of scope** (ADR 0068 decision 6 and §8): the mockup's `Set` command; a
batched per-asset health read or a band column on the list; pagination or
server-side search; alarms on the panel; asset images on the panel; the
sidebar's final position (the §5 IA decision); Load / Reading columns; any
edit, RTU-attach, points or upload affordance; any change under `packages/db`,
`admin/assets/*`, `MasterDataLayout` or `/admin/assets`; any `AGENTS.md`,
`docs/roadmap.md` or `docs/BACKLOG.md` status edit before closure.

## 2. Serial or parallel — serial, one branch, four implementer units

Not a ⭐ enabler. Units 1–3 touch disjoint files and *could* run in three
worktrees, but each is small (one contract, one join, one filter) and the
cold-start cost of three implementers exceeds what parallelism saves (§3 "cost
reality"). Recommendation: **dispatch serially on the one branch**, in the order
below. The order is forced at two points: Unit 2's API guard parses the live
rows against `assetListRowSchema`, so it needs Unit 1; Unit 4 imports the
widened `AssetRow` (Unit 1) and `fetchDashboards`'s second argument (Unit 3).
Unit 3 is independent of 1 and 2 and may be dispatched in parallel in its own
worktree if the session wants it; nothing else may.

| Unit | Task | Model | Why |
|---|---|---|---|
| 1 | contract rename + widen, web type alias, one fixture | **Sonnet** | a rename and a contract field — mechanical, compile-forced |
| 2 | `listAll` join + the API guard (scope claim) | **Opus** | a service with its integration spec; the scope assertion needs judgment about fixtures |
| 3 | `assetId` on `GET /dashboards`, tenant-pool guard, web client | **Opus** | a query filter on a 982-line service at the line cap, plus an RLS-pool proof |
| 4 | page, panel, nav, route, lib helpers, jsdom + reachability specs | **Opus** | a page with its jsdom spec |
| 5 | closure docs | **Sonnet** | doc, at close only |

## 4. Design decisions

**D1 — Contract (decision 2, rulings 2 and 3).** `envelopes.ts`:

```ts
export const assetListRowSchema = z.object({
  id: z.string(),
  code: z.string(),
  name: z.string(),
  siteName: z.string(),
  domain: z.string(),
  locationId: z.string().uuid(),
  locationName: z.string(),
  rtuId: z.string().uuid().nullable(),
  rtuDisplayName: z.string().nullable(),
  // Reported, never derived — see the docblock.
  telemetrySource: z.string().nullable(),
  active: z.boolean(),
  templateId: z.string().uuid().nullable(), // §12 Q1 — ruled in
});
export const assetListResponseSchema = z.array(assetListRowSchema);
```

Plain `z.object`, not `.strict()` (the old one was not; a strict list row would
break the picker on the first additive field). No `.merge()`, no `.extend()`, no
`z.intersection`, no `.readonly()` — nothing here is `A & B` and rows are
consumed as plain arrays. `packages/shared/src/index.ts:643` becomes
`export type AssetListRow = z.infer<typeof E.assetListRowSchema>;`. In
`apps/web/src/api/assets.ts`: `export type AssetRow = AssetListRow;` (imported
from `@bms/shared`), `fetchAssets` parses `assetListResponseSchema`. The old
names are deleted, not aliased.

**D2 — The list read (decision 2).** `listAll` keeps `innerJoin(locations)`
(an asset always has a location) and adds
`leftJoin(rtus, and(eq(assets.rtuId, rtus.id), eq(rtus.organizationId, assets.organizationId)))`
(an asset need not be wired, ADR 0018; the organization predicate is ADR 0068
ruling 7, added at the step-5 security review — G3 in its own suite). Select adds
`locationName: locations.name`, `rtuId: assets.rtuId`,
`rtuDisplayName: rtus.displayName`, `active: assets.active`,
`templateId: assets.templateId` (Q1) and
`telemetrySource: sql<string | null>\`${assets.meta}->>'telemetrySource'\``.
The `->>` form reports the stored text and `NULL` when the key is absent — the
"reported, never derived" rule of `storedSource`, in SQL, so the rows still go
out unmapped. Docblock states: why LEFT for `rtus`, why the pool stays
`fleetDb` (unchanged: the caller scopes by `assetIds` first), and that a
pre-`F4.139` row reports `null`. Route, guard and `organizationId` unchanged.

**D3 — `assetId` filter (decision 4, ruling 4).** `listDashboardsQuerySchema`
gains `assetId: z.string().uuid().optional()`; the controller destructures both
and calls `this.dashboards.list(user, organizationId, assetId)`; `list` pushes
`eq(dashboards.assetId, assetId)` beside the two organization conditions
(inside the `withOrganizationReadScope` callback, so it narrows within the
caller's organizations and can never widen — an out-of-scope id yields `[]`,
never 403). Four lines plus a two-line comment citing ADR 0068 decision 4.

**D4 — Web client.** `api/dashboards.ts`: replace `organizationQuery` with
`queryString(params: Record<string, string | undefined>)` (URLSearchParams over
the defined keys, `""` when none); `fetchDashboards(organizationId?: string, assetId?: string)`.
`fetchDashboard` keeps its behaviour through the same helper. Both existing
callers compile unchanged.

**D5 — Pure helpers in `apps/web/src/lib/asset-browser.ts`** (coverage
denominator, node specs): `filterAssetRows(rows, { query, domain, site })` —
`query` matches `code` or `name`, case-insensitive, trimmed, **not `siteName`**
(decision 1 says code and name; the site has its own filter — this is why
`filterAssetsByQuery` from `asset-picker.ts` is *not* reused);
`domain`/`site` are exact matches, `""` means all; filters compose as AND.
`siteOptions(rows)` — distinct `siteName`s sorted. `domainLabel(code, domains)`
— the vocabulary label or the bare code when the vocabulary has no row.
`noDashboardsSentence(templateId: string | null)` — `"No dashboards for this asset."`
and, when `templateId === null`, `"No dashboards for this asset — it was created by hand, so there is no template to instantiate them from."`
(Q1). `activeLabel(active)` → `"Active"` / `"Inactive"`; a null RTU or source
renders `"—"` at the call site (one literal, the em dash the repo already uses).

**D6 — Page (`apps/web/src/pages/assets-page.tsx`, export `AssetsPage`, ruling 5).**
Props `{ user: AuthUser }`; renders `AppShell` with
`kpiRibbon={<span className="text-bms-ink">Assets</span>}`; `PageHeader`
(eyebrow "Operations", title "Assets", subtitle "Every asset in your scope, with its
gateway, telemetry source and default dashboards"); no `actions`. Queries:
`["assets", "list"]` → `fetchAssets()`; `vocabulariesQueryKey` → `fetchVocabularies`
(staleTime 5 min, as `admin/assets-page.tsx:62-66`). State: `query`, `domain`,
`site`, `selectedId: string | null`. Loading / error / empty states copied from
`dashboards-page.tsx:61-72`. Filter bar: a text input (`aria-label="Filter by code or name"`),
a domain `<select>` (`aria-label="Domain"`, options from `assetDomains`, "All domains"
first) and a site `<select>` (`aria-label="Site"`, `siteOptions`). Table in a
`SectionCard`, columns in decision 1's order; the Code cell is a `<button type="button">`
whose text is the code (so a spec finds the row by `role=button, name=<code>`);
clicking it sets `selectedId`. When `selectedId` resolves to a row, render
`<AssetDetailPanel asset={row} domainLabel={…} onClose={…} />` beside the table
(the `admin/assets-page.tsx` dock layout, without reusing its component). The
docblock names the basename collision with `pages/admin/assets-page.tsx` and why
this file is not that one (Q2 of the ADR).

**D7 — Panel (`apps/web/src/components/assets/asset-detail-panel.tsx`, decision 3).**
Props `{ asset: AssetRow; domainLabel: string; onClose: () => void }`. Heading
`Asset · <code>` (the `Images · <code>` precedent); a `<dl>` of Name · Site ·
Location · Domain · RTU · Source · Active from the row — **no second asset fetch**.
Health: `useAssetHealth(asset.id)` → loading sentence, error sentence
(`"Health could not be read."` + `apiErrorMessage`), else `<AssetHealthCard title="Health" data={…} />`
— the existing card already renders absences 1–3 as distinct text and is the
DRY choice over a second renderer of `assetHealthResponseSchema`. Dashboards:
`useQuery({ queryKey: ["dashboards", "list", { assetId: asset.id }], queryFn: () => fetchDashboards(undefined, asset.id) })`
→ a `<ul>` of `<Link to={`/dashboards/${d.slug}`}>{d.name}</Link>` with
`· {d.widgetCount} widgets` beside each; empty → `noDashboardsSentence(asset.templateId)`.
A `Close` button. **No** edit, attach, points, image or delete control of any
kind (decision 3's last paragraph; the spec asserts the absence after a positive
control).

**D8 — Nav and route (decision 1, ruling 1).** `app-shell.tsx:26` gains
`{ label: "Assets", path: "/assets" },` immediately after the `Dashboards` entry.
`app.tsx` gains the `/assets` route after the `/dashboards/:slug` block, same
`accessToken && user ? <AssetsPage user={user} /> : <Navigate to="/login" replace />`
shape, **no `AdminRoute`** (decision 5). `tests/f3.31-assets-browser-reachable.test.ts`
holds both facts as a source scan, modelled on `e2.2-alarm-kb-route-gate.test.ts:85-105`.
