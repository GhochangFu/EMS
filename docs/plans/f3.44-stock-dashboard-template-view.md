## 1. Goal

An administrator can read a stock dashboard-template entry in full before deciding to import it. A **View** control beside each entry's Import button on `/admin/dashboard-templates` opens a deep-linkable page, `/admin/dashboard-templates/stock/:code`, which renders the entry's widgets exactly as the template detail page renders a canvas — the same `DashboardCanvas` preview and the same per-widget editor — with `editable={false}`, so every field is disabled and no lifecycle, save, add, remove or instantiate control renders. A header names the entry, its stock code, its section and its stock version, states that this is repository data that cannot be edited here, and — for a role that may author — carries an organization picker plus an Import button, so a reader who decides to take the entry does not go back to the list. No API, no migration, no contract change: `GET /admin/dashboard-templates/stock` already returns the whole `StockDashboardTemplateDto` with `content`, and the page reuses the list response the card already fetched.

## 2. Out of scope

- **Editing a stock entry from the screen.** ADR 0049 decision 3 — the catalog is repository data. The viewer renders no writable control and posts no `PATCH`.
- **Any change to the detail page's behaviour.** Its header, its five mutations, `InstantiateDialog` and `ResolutionReport` are untouched. Task 2 moves one private component out of the file; nothing changes inside it.
- **Any change to the card's existing Import wiring.** `dashboard-templates-page.spec.tsx` (`importCallsTheApiWithTheChosenOrganization`) is green and is this row's regression gate. The card gains one `<Link>` (and, if Q4 is ruled (a), one derived number).
- **Rendering a widget's `sources`** (metric-catalog bindings). `WidgetEditor` renders `bindings` only, today, on the authoring page too — see open question 3.
- **A per-entry read route** `GET /admin/dashboard-templates/stock/:code`. The list already carries every field.
- **A new navigation entry.** The viewer is reached from the card.
- **Making the card's Import navigate to the draft.** Measured: it does not today. See open question 2.

## 3. Serial or parallel

**Serial, one branch, two consecutive `implementer` passes.** Not a fan-out candidate: the tasks form a chain, not a star. The component move (Task 2) gates the viewer page (Task 3); the viewer's route string gates the card link (Task 4) and the reachability guard (Task 5); every task touches `apps/web`, and Tasks 4 and 5 scan or edit the same file. §3 permits fan-out only for 2+ genuinely independent siblings on non-overlapping files. There are none.

- **Pass A** — Tasks 1 and 2 (the lookup widening, the component move). Sonnet. Runs to green first.
- **Pass B** — Tasks 3, 4 and 5 (the viewer with its jsdom spec and route, the card link, the guard). Task 3 on Opus; 4 and 5 on Sonnet, or inline if too small to hand off cold.

## 5. The decisions

### 5.1 No adapter and no detail-page reuse — move `WidgetEditor` and render the canvas directly

**Decision: the viewer renders `DashboardCanvas` plus `WidgetEditor editable={false}` per widget under its own header. It never holds a `DashboardTemplateDto`, so there is no `stockEntryAsTemplate` twin and no synthetic `id` or `status`.**

F2.14 adapted because seven tab components took the row DTO and sat behind a `TemplateTabBody` seam the detail page merely hosted. Here the measurement is the opposite: the detail page is one component that fetches by id, and every one of its header controls is gated on `status`, not on `editable` — `draft` renders Publish and Delete, `published` renders Archive, Edit-this-version and Instantiate (which posts `template.id`), `archived` renders Revive. A stock entry stamped with **any** status and fed to the detail page would render at least one live mutation control against a sentinel id. The F2.14 trap was one field (`formulaFieldsAreReadOnly`); this one is the whole header. Adapting is therefore not the safe seam it was there.

What the row calls "the detail page's rendering with editing off" is, measured, `DashboardCanvas` (already shared) plus the private `WidgetEditor` plus one empty-state sentence. `WidgetEditor` reads a widget, not a template; it issues no query and no mutation; its three writable affordances sit under `{editable ? … : null}`. So the seam is the component itself: move it to `components/dashboard-templates/widget-editor.tsx` (the `TemplateTabBody` precedent, one file, no behaviour change) and let both pages import it. Duplicating a read-only twin (~40 lines) was considered and rejected: a field added to `WidgetEditor` later would not show in the viewer, and the drift would be invisible.

The `renderTile` arrow the detail page passes to `DashboardCanvas` (326–333, five lines) moves too, as a named export in the same file, so both pages draw the same tile preview.

### 5.2 Reuse `findStockEntry` by widening it to a generic

`lib/stock-template-view.ts:130` is `(items: readonly StockAssetTemplateDto[], code) => StockAssetTemplateDto | undefined`. Widen to `<T extends { code: string }>(items: readonly T[], code: string): T | undefined`. The asset page keeps compiling, the eight existing spec groups keep passing, and one new spec case pins the dashboard shape. A second `.find` in a second file was rejected: the F2.14 review made "the lookup is the validation" a tested seam on purpose.

### 5.3 A route, and there is no ordering trap today — write that down

`/admin/dashboard-templates/stock/:code` is four segments; its only sibling `/:templateId` is three. React Router v7 ranks them apart, so the F2.14 ordering rule does not apply. Declare the route immediately after `/admin/dashboard-templates/:templateId` with a comment saying exactly that, plus the rule for the future: *any four-segment `/admin/dashboard-templates/:templateId/<x>` route added later is declared **after** this one*, and the guard (Task 5) checks it.

A bare `/admin/dashboard-templates/stock` matches `:templateId`, the detail page fetches id `"stock"`, and `idParamSchema` answers 400 — the behaviour every non-uuid segment already has. Known, unchanged, out of scope (same note as F2.14 §5.2).

`:code` validation is the lookup: present in the fetched list or not-found. **Import sends the resolved `entry.code`, never the URL parameter.** The echoed code in the not-found panel is cut to 64 characters (the F2.14 security Low, applied from the start).

### 5.4 Readable by every master-data role; Import gated on `mayAuthor`

The card renders the stock list to every `AdminRoute` role and gates only Import; the server admits `location_admin` to the list. The viewer mirrors the card: no refusal branch, `stockQ` ungated, the picker and the Import button under `mayAuthor`, `orgsQ` `enabled: mayAuthor`. The reason it is right and not merely consistent: a `location_admin` may instantiate a published template (ADR 0015 §7), so "what canvas does this stock entry produce" is that role's legitimate question. This is the one place the plan departs from F2.14, and open question 1 puts it to the owner.

### 5.5 Import from the viewer lands on the new draft

The viewer's `onSuccess` invalidates `["admin", "dashboard-templates"]` and navigates to `/admin/dashboard-templates/${created.id}` — F2.14's "a reader who takes the entry does not go back to the list". The card's Import does not navigate today and is not changed (its spec is the regression gate). Open question 2.

### 5.6 DRY, considered and rejected once

Do not extract the card's import wiring into a shared hook: the card's picker lives in the `SectionCard` `actions` slot for the whole list while its Import buttons are per row, so no single component fits both layouts (the F2.14 §5.3 argument, unchanged). The units that must not drift already exist — `importAdminStockDashboardTemplate` and the draft path literal — and both call sites use both.
