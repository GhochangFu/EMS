## 1. Goal

Make a notification channel belong to a tenant instead of to nobody, and close the write-containment hole that Amendment 5 ruled on. Concretely: `bms.notification_channels` and `bms.automation_rules` re-key their identity from a global `code` to `(organization_id, code)`; `bms.notification_deliveries.organization_id` becomes `NOT NULL`; the `organization_id IS NULL OR …` disjunct in `0047`'s `tenant_isolation` `WITH CHECK` becomes role-scoped `TO bms_fleet` on `bms.users` and `bms.notification_channels` and is removed outright on `bms.notification_deliveries`, with `USING` untouched on all three; a new `AccessControlService.canManageNotificationChannel(jwt, organizationId)` replaces `assertAdmin` on the channel routes; the channel writes move off `fleetDb` onto `withTenant` (ADR 0043 decision 7, the reason the blanket `bms_tenant` DML grant in `0039:49` was ruled to stay); and the channel-list, channel-load and delivery-ledger reads gain an organization filter, because `notification_deliveries` carries alarm text and dropping the global-admin gate without a filter would let one customer's admin read another's.

**Explicitly out of scope.**

- `E7.1d` — the F3.8 admin UI split (org-scoped vs fleet-wide channel and delivery pages). `apps/web/src/lib/admin-access.ts:67-68` keeps both pages `globalAdminOnly: true` in this slice. This slice is API-side and database-side only.
- The ADR 0043 promotion sweep (AGENTS.md §2/§4/§4.7/§6 + `docs/roadmap.md` + the BACKLOG ✅ flip). Per BACKLOG §5 and AGENTS.md §9.10/§10.1 that is **one separate `chore(agents):` PR after the item's last slice**. Do not pull it into this branch.
- Narrowing `0039:49`'s blanket `GRANT … ON ALL TABLES … TO bms_tenant, bms_fleet` to a per-table matrix. Amendment 5's last consequence rules that a separate decision and a separate ADR.
- Wiring the alarm-raise path to `NotificationsService.dispatch`. **Measured, not assumed:** `dispatch` has *no production caller* today (`grep -rn "dispatch" apps/api/src` finds only comments and the method itself); only `sendTest` writes a ledger row in production. ## 2. Two decisions that block line 1 of code

Both are the human's. Neither is a preference; each changes what gets written.

### Blocker 1 — `SET NOT NULL` on deliveries breaks the existing **Send Test** button on a global channel

> **RULED by the repository owner 2026-08-27, before any implementation code: the recommended package, both halves.** An optional `organizationId` on create (omitting it still makes a fleet-wide channel, so the web UI is untouched and `E7.1d` stays out), **and** an explicit 400 on a send test against a fleet-wide channel. Tasks 5, 7 and 8 are unblocked. The two rejected readings and why are kept below as the record.
>
> **Verified against the source before the ruling, not inferred:** `sendTest` (`notifications.service.ts:216`) passes `{ ruleId: null, alarmId: null }` on all three of its `record()` calls, and `record()` (`:257-280`) builds its `values({ ruleId, alarmId, channelId, status, dedupeKey, error })` with **no `organizationId` field at all**, inside a `try/catch` that only calls `this.logger.error`. So the silent-loss failure is the current code's behaviour the moment the column is `NOT NULL`, not a hypothetical.

Amendment 5 rules that `notification_channels` **keeps** a legitimate `NULL` org ("a global channel is fleet-managed by decision 7") and, in the same ruling, that `notification_deliveries` loses its `NULL` branch because it gains `SET NOT NULL`. Those two survive together for a dispatch — a dispatch always has a rule, and `automation_rules.organization_id` is `NOT NULL` since `0047`, so the delivery inherits the rule's org even when the channel is global. They do **not** survive together for a send test: `NotificationsService.sendTest` (`apps/api/src/notifications/notifications.service.ts:216`) passes `{ ruleId: null, alarmId: null }`, so the only org available is the channel's — which is `NULL` for a global channel.

This is a live regression, not a hypothetical: `record()` (`notifications.service.ts:257-280`) wraps its insert in `try/catch` and only logs. Without an explicit refusal, pressing **Send Test** on a global channel sends the real message and writes **no ledger row**, logging one line. That is the same failure class as a cached browser bundle — it looks like it worked.

**Recommended package (one answer, not two questions):**

1. `createNotificationChannelBodySchema` gains an optional `organizationId`. Omitted by a global `admin` → a global (`NULL`-org) channel, exactly today's behaviour, so the web UI needs no change and `E7.1d` stays untouched. Supplied, or supplied implicitly for an `organization_admin` (their single writable org) → an org-scoped channel.
2. `POST /notifications/channels/:id/test` on a `NULL`-org channel returns **400** with "a fleet-wide channel has no organization to attribute the delivery to; create an org-scoped channel or wait for the E7.1d organization picker". Explicit refusal, no silent lost row.

**Alternative:** require `organizationId` on create, so no new global channels exist. That forces web work in this slice and pulls `E7.1d` forward. Not recommended.

**Do not resolve this by dropping item C.** Amendment 5 ties the deliveries branch removal to `SET NOT NULL` in the same item; dropping C turns a four-table sweep into three and is a larger deviation than a 400.

### Blocker 2 — the `audit_log` clause cannot land before `audit_log` is populated

> **RULED by the repository owner 2026-08-27: all four tables in one `0048`, one PR.** The drafting recommendation was a two-PR split and it was **rejected** — Amendment 5's *"the defect is one class with one migration"* is taken at its word, so no Amendment 6 is owed and no reader has to reconcile the ADR against a two-migration sequence.
>
> **What the ruling changes, and it is not small.** Item D (audit population + the org-scoped reader) moves from "a later PR" to **a prerequisite of `0048`**. The constraint below is unchanged and now binds inside a single branch: the audit writers must stamp an organization **before** the migration narrows the clause. So the four-table policy flip is `0048`'s **last** statement, and the population commits come **before** the migration commit. At no commit may `main` — or an intermediate checkout of this branch — hold a narrowed `audit_log` clause with writers that still write `NULL`. See §10 for the revised commit order.
>
> **Task 1's assertion 5 is now inverted.** It was written to assert `audit_log` is *not* touched by `0048` (the two-PR shape). It must now assert the `audit_log` `NULL` branch **is** present and role-scoped `TO bms_fleet`, exactly like `users` and `notification_channels`.

`0047`'s `WITH CHECK` currently admits `organization_id IS NULL` for every role. Every audit row today is written with `organization_id = NULL`, and most of them are written **on the tenant pool inside a `withTenant` transaction** — `apps/api/src/rules/rules.service.ts:171,220,404,498,947`, `work-orders.service.ts:409,511,528`, `maintenance.service.ts:432,544,669`, `alarms.service.ts:225`, `alarm-enrichment.service.ts:145`, plus `MasterDataAuditService.write` (`apps/api/src/admin/master-data-audit.service.ts:54-68`). **Counted, 2026-08-27, all three earlier figures superseded: 17 direct `insert(auditLog)` sites and 38 `.audit.write(` call sites.** "40 callers" was never measured and "27 files" was a file count; neither was the call-site number. **The plan's own starter list of direct sites was incomplete** — it named 13 and missed four: `work-orders.service.ts:364`, `rules.service.ts:284`, `master-data-audit.service.ts:61`, `channels.service.ts:459`. Verify enumerations against the source; do not inherit them from this plan.

Role-scope `audit_log`'s `NULL` branch `TO bms_fleet` before those sites stamp an org and **every one of them starts raising `new row violates row-level security policy`** — i.e. rule publish, work-order transitions, maintenance edits and alarm acknowledgement all 500. So item **D (audit population + the org-scoped reader) and the `audit_log` clause of item A are one unit and must ship together**, in that order.

There is a second edge inside the same funnel, and it is the sharpest part of D: `write(input, executor = this.db)` defaults to the **plain tenant pool with no GUC**. Stamping a real org there fails the strict check (`organization_id = current_org` where `current_org` is `NULL`). So D is not "populate a column" — it is "classify 40+17 call sites: inside a tenant transaction → stamp the tx's org; outside one → route to `fleetDb` with a named reason, or wrap in `withTenant`".

**The question for the human:** one PR or two (see §4). Both readings are defensible; the implementer must not choose silently.

## 4. Slicing — one PR or two

**Recommendation: two PRs, and ask the human to confirm before starting.**

- **PR 1 (`0048`)** — items A (for `bms.users`, `notification_channels`, `notification_deliveries`), B, C, E, F, G, H. Roughly `3–4` of the item's `6–8`, with slice 1 having already spent some.
- **PR 2 (`0049`)** — item D: `audit_log.organization_id` population across 17 direct inserts and the 40-caller `MasterDataAuditService` funnel, the `audit_log` `WITH CHECK` clause, and the org-scoped audit reader. Roughly `2–3`.

**Why the split honours Amendment 5 rather than bending it.** The amendment's stated reason for one migration is *"leaving it standing on the user table for a cycle is the worse trade"*. Under this split `bms.users`, `notification_channels` and `notification_deliveries` are all fixed in PR 1. Only `audit_log` waits, and `audit_log` is the weakest of the four: the exposure is a tenant writing a `NULL`-org row it then cannot read, with no cross-tenant read (`USING` is strict and unchanged). The split therefore preserves the amendment's own ordering of harm. It also keeps the security-critical item G — the delivery-ledger filter — from waiting behind a 57-site audit sweep.

**The alternative that satisfies both constraints literally:** one PR, one migration `0048`, with D's population as tasks 1..N and the four-table policy flip as the **last** task. Correct, literal, larger PR, and one review surface for both. If the human prefers this, the task order below is unchanged; only the commit and PR boundary moves.

**One consequence to write down if the split is taken:** PR 1 must leave `ChannelsService.audit()` (`channels.service.ts:445-467`) writing a `NULL`-org row on `fleetDb` **deliberately, with a comment naming PR 2**. Otherwise the channel audit rows become the only ones carrying an org while 5 992 others do not, and the inconsistency looks like a bug rather than a sequence.

### Task 3 — Migration `0048_channel_org_identity_and_fleet_scoped_null_check.sql`

**New file:** `packages/db/drizzle/0048_channel_org_identity_and_fleet_scoped_null_check.sql`, plus the journal entry from §3.

Shape, in this order. Every statement idempotent (`IF EXISTS` / `IF NOT EXISTS`), `SET ROLE bms_owner` first and `RESET ROLE` last.

**3a. Backfill `notification_deliveries.organization_id`, then `SET NOT NULL`.**

> **Trap, sequence it rather than discover it:** a DML `UPDATE` inside `0048` **sees nothing**. `0047` put `FORCE ROW LEVEL SECURITY` on the table and the migration runs as `bms_owner`, so the strict `USING` hides every `NULL`-org row and the `UPDATE` matches zero rows *silently*. `0046`'s per-organization loop worked only because policies did not exist yet. The mechanism is `ALTER TABLE bms.notification_deliveries NO FORCE ROW LEVEL SECURITY;` around the DML and `… FORCE ROW LEVEL SECURITY;` after it — without `FORCE`, the owner is exempt from its own table's policies. The `SET NOT NULL` itself is DDL and its validating scan is *not* filtered (`0047`'s own header states this); only the `UPDATE` needs the window.

```sql
UPDATE … SET organization_id = ar.organization_id FROM bms.automation_rules ar WHERE rule_id = ar.id AND organization_id IS NULL;
UPDATE … SET organization_id = nc.organization_id FROM bms.notification_channels nc WHERE channel_id = nc.id AND nc.organization_id IS NOT NULL AND organization_id IS NULL;
-- then a DO block that RAISEs EXCEPTION listing the offending ids if any remain
```

Abort listing the ids, matching `0046`'s fail-loud posture. **Do not delete unresolvable ledger rows** — the ledger is history and `0038`'s foreign keys exist to make history outlive configuration. The remedy belongs in the exception's `HINT`, not in the migration's behaviour. Measured: 0 rows on this database, so the abort is dormant here and exists for a populated deployment.

**3b. Re-key `notification_channels` identity.** Exact object names, read from the live catalogue rather than from the schema file:

```sql
ALTER TABLE bms.notification_channels DROP CONSTRAINT IF EXISTS notification_channels_code_key;
CREATE UNIQUE INDEX IF NOT EXISTS notification_channels_org_code_unique
  ON bms.notification_channels (organization_id, code) NULLS NOT DISTINCT;
```

It is a UNIQUE **constraint** (`notification_channels_code_key`), so it drops with `DROP CONSTRAINT`, not `DROP INDEX`. `NULLS NOT DISTINCT` is load-bearing: `organization_id` stays nullable here by Amendment 5, and a plain composite unique index treats every `NULL` as distinct, so two global channels could share a code and the "that code is taken" 409 would stop firing for exactly the fleet-managed rows. **Version-checked, not assumed:** `NULLS NOT DISTINCT` needs PG15+; local is `PostgreSQL 16.14` and `.github/workflows/ci.yml:22` pins the same `timescale/timescaledb:2.29.1-pg16`, so CI and local agree.

Follow `asset_templates`' precedent (`packages/db/drizzle/0024_asset_templates.sql:36-51`), which is the shape decision 7 names: `(organization_id, code, version)` unique plus a partial unique index, both owned by the migration.

**3c. Re-key `automation_rules` identity.**

```sql
DROP INDEX IF EXISTS bms.automation_rules_code_idx;
CREATE UNIQUE INDEX IF NOT EXISTS automation_rules_org_code_idx ON bms.automation_rules (organization_id, code);
```

Here it is a plain unique **index** created by `0008_phase5_rule_engine.sql:22` — not a constraint — and `organization_id` is `NOT NULL` since `0047`, so **no** `NULLS NOT DISTINCT` is needed. Note for the reviewer: `rules.service.ts:786` refers to this index as `automation_rules_code_unique`, a name that **does not exist** in the database; fix the comment in Task 9.

**3d. The Amendment 5 `WITH CHECK` split, three tables.** For each of `bms.users` and `bms.notification_channels`, replace the single policy with two permissive policies:

```sql
DROP POLICY IF EXISTS tenant_isolation ON bms.<t>;
CREATE POLICY tenant_isolation ON bms.<t>
  USING (organization_id = nullif(current_setting('app.current_organization', true), '')::uuid)
  WITH CHECK (organization_id = nullif(current_setting('app.current_organization', true), '')::uuid);
CREATE POLICY tenant_isolation_fleet_null ON bms.<t>
  TO bms_fleet
  USING (organization_id = nullif(current_setting('app.current_organization', true), '')::uuid)
  WITH CHECK (organization_id IS NULL
              OR organization_id = nullif(current_setting('app.current_organization', true), '')::uuid);
```

Permissive policies OR together, so the second widens `bms_fleet` alone and `USING` is unchanged for every role — which is the whole of the ruling. For `bms.notification_deliveries`, recreate `tenant_isolation` with the strict `WITH CHECK` and **add no second policy**.

Three things confirmed rather than assumed, and each deserves a comment in the file:

- **`0039`'s `password_hash` column grants are untouched.** `0048` writes no `GRANT`/`REVOKE` at all.
- **Amendment 1's `bms_auth` pre-auth read is untouched.** `auth_bootstrap_read ON bms.users FOR SELECT TO bms_auth USING (true)` and `auth_bootstrap_write … FOR UPDATE TO bms_auth USING (true) WITH CHECK (true)` (`0047:318-326`) are separate permissive policies. Narrowing the disjunct therefore cannot break login.
