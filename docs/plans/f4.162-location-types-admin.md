## Owner rulings on the plan's open questions (2026-09-27)

1. **OQ1 — the code class on create: lower snake_case.** The `F2.23` catalog class **plus** `^[a-z][a-z0-9_]*$`, matching the four seeded codes. The chat's label/code matcher folds case, so `PUMP_STATION` would silently alias `pump_station` in chat while being a distinct row. Rejected: the catalog class only.
2. **OQ2 — the retired type's label: `typeLabel` on `AdminLocationDto`** (a required contract field, one producer join, four fixture files), the `F4.157` OQ4 precedent. Rejected: showing the code.
3. **OQ3 — the validator reports an inactive stored type** (D9): `POST sessions/:id/validate` and every chat turn carry a `location.type` error and `readyToCommit: false`, so the wizard's Commit button agrees with the commit's 400. Rejected: the chat-only branch check.
4. **OQ4 — the count includes every `bms.locations` row of the type**, inactive locations included. Rejected: active locations only.

## Goal

A global `admin` lists every `bms.location_types` row (active and retired, each with its fleet-wide count of `bms.locations` rows), creates one (`code`, `label`, optional `sortOrder`; a duplicate code is a 409), renames or reorders one (`label`, `sortOrder`; a body naming `code` is a 400), and deactivates or reactivates one — on the fleet pool, in a transaction, with an org-less `master.location_type.*` audit row, the `PointKeysAdminService` / `AssetRolesAdminService` shape. A new page, `/admin/location-types`, does that in the browser and is hidden from every non-global administrator. The admin locations form shows a retired current type as "Label (retired)" and sends `type` only when the administrator changed it. Onboarding: `PATCH /admin/onboarding/sessions/:id/draft` refuses a `location.type` that is not an active code with a 400 naming the valid codes, and a draft whose stored type is retired after it was stored is treated as having no type — the validator reports it, `readyToCommit` stays false, and the chat asks "Which type of location is …?" again before the RTU step. The existing `GET /api/v1/admin/location-types` (active rows, `requireMasterDataUser`) keeps its shape and guard byte for byte. No migration.

**Out of scope.** No editable `code` (ruled). No hard delete (ruled). No refusal to deactivate a type in use (ruled). No change to the Excel path, the map, the KPI row, the Control Room, the sim, ingest, the worker or the WebSocket protocol. No `AGENTS.md` edit in the feature branch (the post-merge `chore(agents):` sweep owns the §3 layout lines for the new files). No change to `LocationsAdminService.update`'s type check (the amendment says it stays). No edit to `tests/f4.157-location-types-schema.integration.test.ts` or `tests/f4.53-fixture-reads-prefer-seeded-rows.test.ts` (the `F4.71` session holds both).

## Decisions (engineering; the ADR leaves these to the plan)

- **D1 — routes: `admin/vocabularies/location-types`**, a new controller `LocationTypesVocabularyAdminController` beside `AssetRolesAdminController` (the name differs from the existing `LocationTypesAdminController` because the registry keys on the class name). `GET` (full list with counts, **global admin**), `POST`, `PATCH :code`, `POST :code/deactivate`, `POST :code/reactivate`. Nothing under `admin/location-types` or `admin/locations` changes; the existing controller file is untouched and a static gate proves it. No `?active` query: the page filters client-side, so no query schema and no registry entry for `_list`.
- **D2 — the count** is `count(locations.id)::int` over `locationTypes LEFT JOIN locations ON locations.type = locationTypes.code`, `GROUP BY locationTypes.code` (the PK), on `fleetDb`, ordered `sortOrder, code`. All `bms.locations` rows count, inactive ones included (OQ4).
- **D3 — contracts** (ADR 0030, §4.8). `contracts/location-types.ts` gains `adminLocationTypeDtoSchema = z.object({ code, label, sortOrder: z.number().int(), active: z.boolean(), createdAt: z.string(), locationCount: z.number().int().nonnegative() })` — a **fresh plain object**, not `locationTypeDtoSchema.extend(…)` (no intersection, no `.merge()`, no `.readonly()`). `envelopes.ts`: `adminLocationTypesListResponseSchema = itemsOf(adminLocationTypeDtoSchema)`. `index.ts`: `AdminLocationTypeDto`, `AdminLocationTypesListResponse` as `z.infer`. `adminLocationDtoSchema` gains `typeLabel: z.string()` after `type` (required; the producer joins the lookup — OQ2).
- **D4 — bodies** in `admin/vocabularies/location-types.schema.ts` with the API's own `z`: `locationTypeCodeParamSchema = z.string().min(1).max(32)` (declared locally; the static gate pins it to `locationTypeCodeSchema`'s bound); `createLocationTypeBodySchema = z.object({ code: locationTypeCodeParamSchema.regex(CATALOG_CODE_PATTERN, CATALOG_CODE_MESSAGE).regex(/^[a-z][a-z0-9_]*$/, <message>), label: z.string().min(1).max(128), sortOrder: z.number().int().min(0).max(100000).optional() }).strict()`; `updateLocationTypeBodySchema = createLocationTypeBodySchema.omit({ code: true }).partial().strict()` (`.omit().partial()`, never `.omit().extend()`). `.strict()` is what refuses a body naming `code` (400 via the controller's `ZodError` → `err.flatten()`). An empty PATCH is a **400** (the `AssetRolesAdminService` choice for a new route).
- **D5 — audit.** Actions `master.location_type.create|update|deactivate|reactivate`, `entityType: "location_type"`, `entityId: null`, `organizationId: null`, `payload: { code, ...body }` (deactivate/reactivate: `{ code }`), written on `tx`.
- **D6 — invalidation.** Server: none. Browser: every mutation on the new page invalidates both `["admin", "location-types"]` (the dropdown) and the page's own key `["admin", "location-types-catalog"]`.
- **D7 — the page and its gates.** `canManageLocationTypes(role) = role === "admin"` in `admin-access.ts`; `masterDataTabs` gains `{ label: "Location Types", path: "/admin/location-types", globalAdminOnly: true }`; `adminModuleGroup` in `app-shell.tsx` gains `{ label: "Location Types", path: "/admin/location-types", globalOnly: true }`; `app.tsx` routes `/admin/location-types` inside `<AdminRoute user={user}>` exactly as `/admin/point-keys`; the page itself renders a one-line status ("Location types are managed by a global administrator.") and issues **no query** when `!canManageLocationTypes(user.role)` — fail closed at the page, because a direct URL reaches the route.
- **D8 — the locations form.** With `typeLabel` on the row: when `editing` and `editing.type` is not among `types`, the select renders one extra `<option value={editing.type}>{editing.typeLabel} (retired)</option>` first; `resolvedType` is unchanged. The PATCH payload drops `type` when `editing && resolvedType === editing.type`; a create always sends it. `updateAdminLocation`'s input type already makes `type` optional.
- **D9 — onboarding: one rule, declared in the validator.** `OnboardingValidateService.validate(draft, activeLocationTypeCodes: readonly string[])` and `inferPhase(draft, activeLocationTypeCodes)` take a **required** second parameter (an optional one at an adapter is invisible; `tsc` then names every caller). `validateCrossField`: a `location.type` that is set and not in the list pushes `{ path: "location.type", message: "Location type is not an active code; use one of: a, b, c" }` (no echo of the stored value). `inferPhase`: an inactive type keeps the phase at `"location"`. Callers: `onboarding.service.ts` `patchDraft` (`listLocationTypes()` → codes), `validate`, `uploadExcel` (reuse the codes it fetched for `parseUpload`), `onboarding-commit.service.ts:178`, and the chat. **The PATCH refusal** is a pure exported helper in `onboarding-location-type-match.ts`: `assertPatchLocationTypeIsActive(patch, vocabularies: Pick<VocabulariesService, "assertLocationType">)` — calls `assertLocationType(patch.location.type)` only when the patch names a type (a PATCH that does not name `type` on a draft whose stored type is retired must still be a 200, or the operator cannot repair the draft); `patchDraft` calls it after `loadSession` and before `mergeDraft`, so the 400 lists the codes through the existing `unknownCodeMessage`. **The chat:** `handleTurn` fetches `types` once and passes them to `handleOpenAiTurn`, `handleRuleBasedTurn` and `finalizeTurn` (the two per-branch fetches go); the rule-based location branch enters on `phase === "location" || !locationTypes.hasActiveLocationType(draft.location, types)` where `hasActiveLocationType(stored, types)` is exported from `onboarding-location-type-match.ts` and is what `resolveLocationTurn` already computes inline as `storedActive` (DRY: `resolveLocationTurn` calls it). `finalizeTurn` validates with `types.map((t) => t.code)`, so the returned `currentPhase`, `validationErrors` and `readyToCommit` agree with what the chat just asked.
- **D10 — the §4.5 split comes first, as its own commit, with no behaviour change.** New `apps/api/src/admin/onboarding/onboarding-chat-summaries.ts` exports `isEnabledMqttRtu`, `needsMqttSetup`, `mqttSetupTemplate(draft)`, `formatAssetsByRtuSummary(draft)`; the service imports them and `excelImportFollowUp` calls the functions. Gate: `git diff -w` against the base shows, in the service, only deleted lines and the import; in the new file, the moved bodies byte-identical apart from `private ` → `export function` and the removed `this.`; every existing onboarding spec green with **no spec edit** other than the prose sweep of the four docblock lines that say `this.mqttSetupTemplate`. Expected size after the move: about 790 lines.
