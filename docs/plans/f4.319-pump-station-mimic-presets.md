# F4.319 — plan: pump-station mimic presets and site template (step 3)

Written 2026-11-06 against `main` `b8cc01a` (ADR 0113 accepted and merged at `364d0c58`; F4.317
PR 4 merged on top). Scope is ADR 0113 decisions 1–9; this plan adds no scope. The owner's

## 1. Goal

The six PHEWB pump stations draw full mimics from live data. Three global code presets
(`pump_station_overview`, `pump_station_electrical`, `pump_station_environment`) bind the roles a
PHE site has; two new roles (`dosing-pump`, `rtu-controller`) and a seeded `pump-station` group
make those bindings possible; a stock site template `pump-station-standard` carries the presets
to the sites; and the seed moves the untouched `site-layout-phe-*` copies onto it.

**Out of scope** (ADR 0113 Consequences): the meaning of `breaker_main` = 1 (Q6 — state labels do
not change); the Lotapata II `battery_charge_pct` scale; layouts in templates (`F3.81`) and
shared layouts (`F3.83`); any change to `smoc-standard` or the ESKOM sites (Q8); a new node kind,
symbol, colour or table (decision 9).

## 4. Design decisions

- **D1 — the role move is one migration** (`0127`): two `asset_roles` rows, bare `ON CONFLICT DO
  NOTHING`; `UPDATE bms.asset_group_members … SET role = 'dosing-pump'` where the asset code
  starts `PHE-PUMP-C-` and `role = 'pump'`; `UPDATE … SET role = 'rtu-controller'` where the code
  starts `PHE-AIRSP1051M-` and `role IS NULL`; a `DO` block that raises if either code is
  missing. The member updates run as `bms_owner` inside the `0060` `SET ROLE` bracket.
  **FORCE RLS on `asset_group_members`:** the owner is bound by it, so the updates run with
  `row_security` handled the way the existing cross-org migrations do it (read at build time
  from the newest migration that updates a tenant table; the `migration-reviewer` checks it).
- **D2 — the seed reads the same rule.** `demoRoleForAsset`: `PHE-PUMP-C-` → `dosing-pump`,
  `PHE-PUMP-M-` → `pump`, and, before the non-electrical guard, `environment` +
  `PHE-AIRSP1051M-` → `rtu-controller`. `demoGroupCodesForAsset` adds `pump-station` for every
  `PHE-` code (after the domain group). `demoGroupName("pump-station")` = "Pump station";
  `demoGroupDescription` names ADR 0113; `demoGroupDomain("pump-station")` returns `null`
  explicitly (it would fall to NULL through the `asset_domains` sub-select anyway; explicit is
  the reading).
- **D3 — `pointKeys` on a preset node** is `readonly string[]`, optional, at most three (a
  `mimic-presets.spec.ts` case holds the cap and that each key is a seeded `bms.point_keys`
  code). `presetRoledNodes` passes `node.pointKeys ?? []`.
- **D4 — how the Overview binds `pump-station` (the F4 gap).** A planner rule, opt-in: a tab with
  `domain: null` **and** a `groupCode` binds the site's group of that code whose own domain is
  NULL (step 2 only — never a choice, never a single-candidate pick), resolved `via:
  "group_code"`. With no such group it stays the plain Overview (`group: null`, `via:
  "overview"`). `smoc-standard`'s Overview has no `groupCode`, so its plan does not change (a
  spec case holds this). The Overview mimic then names no `tabKey` and resolves through its own
  tab's group (`mimicGroupFor`, `dashboards.pure.ts:316`). New drop rule beside the F3.74 one: an
  Overview mimic with no `tabKey` on an Overview that bound no group is dropped and reported in
  `droppedCards` (`targetTabKey` = the tab's own key) — the write guard would refuse it, as it
  refuses a dangling `tabKey`. **This is a planner change the ADR did not name; the PR 3 body
  raises it for the owner.**
- **D5 — "untouched" is read from content.** For each PHEWB seed-owned location whose view row is
  `kind = 'dashboard'` and points at the copy with slug `site-layout-<slug>` stamped with a
  `smoc-standard` template: re-plan `smoc-standard` for that site in memory (the same planner and
  `omitUnboundTiles` the seed runs), and compare a fingerprint of the plan with one of the stored
  copy. The fingerprint is the sorted list of tabs (`tab_key`, `label`, `sort_order`,
  `asset_group_id`) and widgets (tab key, `widget_type`, `title`, rect, canonical `config`, the
  sorted `(point_id, role)` pairs, the sorted `(catalog_key, params)` sources), plus the
  dashboard's name, description and `stock_version` = the smoc stock version. Equal → untouched.
  Anything else (an admin edit, a removed copy, `builtin`/`generated` rows, a copy at an older
  stock shape) is left alone and logged. No stored hash, so no schema change.
- **D6 — the move is in place.** In the tenant bracket: delete the copy's tabs (widgets go by
  `ON DELETE CASCADE`, `0094`), write the `pump-station-standard` plan through the same writer a
  fresh copy uses (lifted out of `seedSiteLayouts` into `writeSiteLayoutTabs`), and set
  `template_id`, `stock_version` and `description` on the dashboard with the read values in the
  predicate; read back the counts. The view row, the dashboard id, slug and name stay. Once moved,
  the copy's template code is `pump-station-standard`, so neither the smoc upgrade chain
  (`SEEDED_COPIES_SQL` filters on `t.code`) nor the move step touches it again: idempotent.
- **D7 — a fresh PHEWB database** gets its copies straight from `pump-station-standard`
  (`seedPhewbSiteLayouts` imports it with `ensureSiteTemplate(pool, orgId, entry)`, generalised
  from the smoc-only form; `upgradeSeedSiteTemplate` stays smoc-only). PHEWB still imports
  `smoc-standard` (D5 needs it, and admins may use it).
