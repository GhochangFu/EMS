## Owner ruling (2026-09-28)

20. `meta.seedKey` is seed-owned in the API. Location POST, location PATCH and the
    onboarding commit never accept a `seedKey` from a request, and a PATCH that
    replaces `meta` keeps the stored `seedKey`. Only the seed writes it. This is
    the one `apps/api` code change in this PR (checked: no other branch or
    worktree touches `apps/api/src/admin/locations` or the onboarding commit).

## Why

The addendum 3 reviews found that the stable key could itself be written through
the admin API (security Medium-1: forge, move or wipe a key → boot stop, identity
takeover, DECOMM deactivates a live site), plus gaps in the lookup rule and its
consumers.

## 1. API: the seed key is seed-owned (ruling 20)

- `apps/api/src/admin/locations/locations.service.ts`: create strips `seedKey`
  from the incoming `meta`; update, when the body carries `meta`, strips any
  incoming `seedKey` and carries the stored `seedKey` over. One shared helper.
- `apps/api/src/admin/onboarding/onboarding-commit.service.ts` (location insert,
  ~line 259): strips `seedKey`.
- Tests (repo pattern: spec + test pair; integration where the service writes):
  POST with `meta.seedKey` → stored meta has no key; PATCH `meta: {}` on a keyed
  row → key kept; PATCH `meta: {seedKey: "x"}` → stored key unchanged; onboarding
  commit with `seedKey` → none stored. Each with its mutation.

## 2. The lookup rule (code review C2, F1)

- Adopt the key row only when it is the oldest candidate AND the only candidate
  that carries this identity's key. Otherwise the identity is ambiguous. Cases
  (d) and (e) keep their outcome.
- New case (C2): two canonical rows with the same `created_at`, the newer-id row
  given the other's key → ambiguous, no overwrite (mutation: drop the
  "only keyed" condition).
- New case (f′): an older row keyed for another identity holds B's CODE → not a
  candidate (mutation: restriction applied to the slug fallback only).

## 3. Consumers of an ambiguous identity (code review C1, C3; security Low-1, Low-2)

- RTU skip: for an ambiguous identity, every candidate whose current code is not
  the canonical code joins the skip set. Pre-key R-held case (C's key wiped in the
  transaction, code renamed, Y holds the canonical code) → no RTUs under C's code
  (mutation: ambiguous identities contribute nothing).
- Verifier view check and DECOMM-active check use the same resolution rule as the
  seed, never `candidates[0]` and never `l.code`; when the identity is ambiguous,
  the view check passes if any candidate has the view, and the DECOMM check reads
  only the resolved DECOMM row (an admin row that holds `ESK-DECOMM-01` and is
  active no longer stops the boot). Cases for both.
- `demo-users-seed.ts` finds RSMOC-WC through the resolved row, not by slug
  (ruling 17).
- Not done, recorded as residuals: writing name/coordinates on an ambiguous
  identity (the oldest candidate can be the wrong row in a slug swap); so
  `seedEskomAssets` still throws, loudly, when an ambiguous site's name was also
  changed (C4).
