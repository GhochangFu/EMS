**Row:** `F4.361` (P2) in `docs/BACKLOG.md`. Not a ⭐ enabler.
**Base:** `origin/main` `126399f`.
**ADR:** [ADR 0132](../adr/0132-alarm-and-rule-list-filters.md). No migration, no dependency.

**Goal.** `/alarms` and `/rules` each get four cascading pickers — Organization, Location (the node and its subtree), Asset group, Asset. `/alarms` also gets a Severity picker and a State dropdown (All / Active / Suppressed) that replaces the "Suppressed only" checkbox. The options come from one new read, `GET /api/v1/filter-options`, built only from what the caller can read. The alarm list gains `severity` (list only) and `assetGroupId` (list and summary). The rule list gains `organizationId`, `locationId`, `assetGroupId` and `assetId`, filtered on the server. Every parameter only narrows: an id outside the caller's scope answers an empty list, never 403. The filter lives in the URL. The cards on `/alarms` and the counters on `/rules` count the filtered rows.

**Out of scope (ADR non-goals, plus this plan's).** Saved or default filters; filters on the alarm bar, the alarms rail, reports or the Copilot; a severity filter on `/rules`; multi-select; `state=unacknowledged` on the page; any change to `RuleListItem`, `AlarmListItem`, `RulesService` or `AlarmsService` signatures; a search-as-you-type asset picker; any change to `HierarchyFilterBar` or the admin endpoints; a new e2e spec.

**Serial.** PR 1 → PR 2 → PR 3, one implementer at a time. PR 2 needs PR 1's contract and endpoint; PR 3 needs PR 2's `ScopeFilterBar` and hook.

## 2. Plan-gate questions — **ruled 2026-11-14 (owner, in chat): Q1, Q2, Q3 and Q4 all as recommended**

1. **Which asset groups a caller "reads" (decision 2).** `currentUser(jwt).scope.assetGroups` is empty for every caller whose scope comes from an organization or location grant, and for the global admin.
   - **Recommended:** a group is readable when it is one of the caller's granted groups (asset-group scope), or its `location_id` is one of the caller's readable locations (every other scope). One function decides this for the options read and for the list filters.
   - Alternative: as written — the picker is empty for most users.
2. **"Asset group narrows Asset" (decision 6) needs membership.**
   - **Recommended:** each asset-group option gains `assetIds` — its members that are in the `assets` list. One additive field; recorded as an ADR 0132 build note.
   - Alternative: the Asset picker ignores the chosen group.
3. **Device alarms under the Asset and Asset group filters.** `assetIds` already lists the comms alarm of an RTU serving that asset and the ingest-host alarm of its organization (ADR 0127 decision 14).
   - **Recommended:** `assetGroupId` behaves the same — it narrows the caller's asset scope to the group's members; no new SQL.
   - Alternative: rule alarms only under both filters (a new parameter and an ADR amendment; ~0.25 day more).
4. **A group the caller does not read, but some of whose members it does.**
   - **Recommended:** empty, as decision 5 and P2 say — checked before any read.
   - Alternative: the overlap (leaks which of its assets are in a group it cannot see).

**Effort:** about 3 days (§5), up from the row's 1–2 after the rulings widened scope.

## 3. Design decisions (no ruling needed)

| # | Decision | Why |
|---|---|---|
| D1 | New directory `apps/api/src/filter-options/` holds the options read **and** the narrowing rule. `FilterOptionsModule` exports `AssetFilterScopeService`; `AlarmsModule` and `RulesModule` import it. | The picker lists exactly what the lists accept. |
| D2 | The rule filter becomes a **narrowed asset-id array** handed to the unchanged `RulesService.listRules`. | Asset-less rules drop out; `rules.service.ts` and the Copilot do not change. |
| D3 | `AssetFilterScopeService.narrow(user, filter)` returns `readableAssetIds(user)` untouched for an empty filter, otherwise a subset of it. | One rule for both lists, one test. |
| D4 | On the alarm list `organizationId` and `locationId` stay the existing SQL predicates; only `assetGroupId` goes through `narrow` (Q3). | Keeps ADR 0130 decision 15's device-alarm rules. |
| D5 | `locationFilter` moves from `alarms.controller.ts` to `alarm-location-scope.ts` as an export; `/rules` uses it too. | "The same walk"; no third copy of P2. |
| D6 | `scopeIdQueryField` (lower-cased uuid) in `auth/asset-scope.schema.ts`; `locationIdQueryField` becomes an alias. The shipped alarm `organizationId` field is not touched. | Decision 5; no behaviour change on a shipped parameter. |
| D7 | `ruleListQuerySchema` is `.strict()`: `GET /rules?foo=1` becomes a 400. | The alarm list's rule; no caller sends a query today. |
| D8 | `severity` is a trimmed string of 1–64 characters; empty is absent; unknown code is an empty page. | Decision 3. |
| D9 | Active organizations, active locations, active assets at a listed location, every group at a listed location. `parentId` is masked again after the last filter. | No id of an unlisted node leaks. |
| D10 | Organization gates the other three pickers; a URL naming a child without its organization gets it filled in. | `HierarchyFilterBar` pattern; shared links stay valid. |
| D11 | A single organization is preselected and disabled, and is **not** written to the URL or sent. | The request stays what it is today. |
| D12 | A user's change pushes a history entry; dropping an invalid id replaces the current one. | Decision 8: Back undoes a change. |
| D13 | The list read waits for the options only when the URL carries a scope id; if options fail, the pickers are disabled with one line of text and the list runs on the URL. | No flash of an unfiltered list. |
| D14 | `fetchRules()` keeps zero arguments; new `fetchRuleList(filter)` does the work. | The nine bare `queryFn` sites. |
| D15 | Critical shows "all clear" only when no severity is chosen and State is not Suppressed. | A filtered zero is not a statement about the plant. |

## 9. Risks

1. The options read returns every readable asset (hundreds today); a few thousand would need a search-as-you-type read (an ADR amendment).
2. Scope is resolved two or three times per filtered list request; no cache added.
3. The Asset and Asset group filters list device alarms too (Q3).
4. An inactive asset cannot be picked, though its old alarms list under its org or location.
5. `GET /rules` turns strict (D7).
6. A web bundle newer than its API: `/filter-options` 404 (pickers "unavailable") and an old `/rules` ignores the query. PR 1 deploys first.
7. With an org chosen, the admin's rule read runs under that tenant instead of the fleet handle — the designed `withReadScope` path; covered by the integration spec.
8. Options are cached 5 minutes; lists are always live.
9. `/alarms` cards count loaded rows (25 a page), as today.
10. The mockup has no filter row; the bar follows `HierarchyFilterBar`'s look.
