## 1. Goal

Ship the parameter store and the `$key` reference, end to end, so that a stored `bms-calc-v3` formula such as `{kw} * $energy_tariff_per_kwh` on an asset is evaluated by the scheduled sweep against the nearest-scope parameter row valid at the tick, writes nothing and counts `parameter_unset` when no row is in scope, and so that an administrator can enter, edit and remove those rows on `/admin/calc-parameters`. Concretely: migration `0074` (`bms.calc_parameter_keys` global vocabulary seeded with the stock keys, `bms.calc_parameters` tenant table with FORCE RLS in its creating migration); a batched resolver in `apps/api/src/calc/`; `bms-calc-v3` as a third dialect that is a strict superset of `v2` by construction and by property test; a new `CalcParamRef` AST kind the host resolves before `evaluate()`; every "`v2` is scheduled-only" guard extended to `v3`; a save-time vocabulary check with an author-facing message; the admin API and screen, gated as master data (forms, not buttons); the formula editor's dialect picker and help.

**Out of scope, deliberately.** Window functions, calendar windows and `bms.locations.timezone` (`E4.1b`). Stock sustainability points, the deferral-ledger promotions, `energyTariffZar()` absorption, the DTO rename and `organizations.currency` (`E4.1c`). Any parameter **value** in the seed — ADR 0070 Context 3: no stock key ships with a value. A CRUD surface for the **keys** vocabulary — ADR decision 2 says it is "extended by `INSERT`, never by a release"; this row ships the read endpoint the picker needs and nothing else (§"Open questions" Q9 is the deferred `$` completion, not a keys editor). Template KPI evaluation (`F2.33`; a `v3` KPI expression is stored and not evaluated, as `v1`/`v2` ones are — `templateKpiSchema.dialect` already spreads `CALC_DIALECTS`, so it accepts `v3` with no edit). Backfill. A per-asset override of a parameter through the calc-override endpoint (a parameter is a row in the store, not a template field). The `chore(agents):` sweep.

## 2. Serial or parallel, and the model per unit

**Serial, hands-on, on one branch at a time, in two PRs. Never fanned out.** This is a ⭐ enabler: `E4.1b` hangs its window nodes off the tokenizer/parser/host seams this row cuts, `E4.1c` hangs its stock points and its tariff reads off the resolver's interface, and every unit below shares `limits.ts`, `ast.ts`, `calc-definition.ts` or `calc-scheduler.service.ts` with its neighbour. ## 3. Design decisions settled at this gate

The plan's own calls, each reviewable and each one line to overturn.

1. **Structural superset, as `F2.9` did it.** One tokenizer, one parser, one evaluator. In `tokenizer.ts:90` `isV2` becomes `dialect !== CALC_DIALECT` (every `v2` branch runs under `v3`) and a new `isV3 = dialect === CALC_DIALECT_V3` guards only the `$` branch; `Parser.isV2` the same. No `v1` or `v2` branch is edited. Decision 3 (`v1`/`v2` keep their meaning) is then held by construction; U3's property test is the tripwire.
2. **One new token kind, one new node kind.** Token `param` (`text` = the key **without** `$`, `position` = the `$`); node `CalcParamRef = { kind: "param"; key: string; position: number }` — a new kind on purpose (`ast.ts:42`'s reason), so `collectRefEntries`'s `assertNever` and `evalNode`'s TS2366 both force every exhaustive consumer to decide.
3. **A fourth, separate evaluator map.** `evaluate(ast, inputs, crossInputs = EMPTY, params = EMPTY)`; a `param` node reads `params.get(node.key)`, absent → `missing_input` at its position, else `finiteOrFail`. Not folded into `crossInputs` under a `p:` prefix: `crossRefKey` is the canonical key of a *cross-asset* node and the web preview keys its rows by it; a third namespace keeps the three maps' meanings one each. Every existing two- and three-argument caller compiles unchanged.
4. **`ParseResult` gains `paramRefs: string[]`** (distinct keys, first-appearance order, always `[]` under `v1`/`v2`), beside `refs` and `crossRefs`; `CalcDefinition` carries it through. `validateFormula` still checks local refs only — the vocabulary is a database read and belongs to the api (U7), exactly where `crossRefPointKeys` put the cross-asset key check.
5. **Lexical form of a key: `$` then `[A-Za-z_][A-Za-z0-9_]*`.** No `-`: `$a-b` must mean `$a - b`, so a key containing `-` could never be written. Consequently `calc_parameter_keys.code` is constrained narrower than ADR 0065's catalog class: `^[a-z][a-z0-9_]{0,63}$` — the ADR's own naming rule (*snake_case*) made mechanical. **Open question Q1.**
6. **`MAX_FORMULA_PARAM_REFS = 8`**, on the `MAX_FORMULA_CROSS_REFS` pattern, error `too_many_param_refs`. **Open question Q7.**
7. **Overlap is refused twice: a pre-read inside the write transaction for the author-facing 409, and a `btree_gist` `EXCLUDE` constraint as the race-proof backstop.** Measured: `pg_available_extensions` on the compose image lists `btree_gist` `default_version 1.7`, **not installed** (`installed_version` empty); `pg_extension` holds `plpgsql, timescaledb` only. `btree_gist` is a trusted contrib extension and the migration runs as `DATABASE_URL_SUPERUSER` (`bms_app`) before its `SET ROLE bms_owner`, so `CREATE EXTENSION IF NOT EXISTS btree_gist` needs no §9.4 dependency (ADR 0070 §Dependencies says the same). The pre-read exists because RLS suppresses a constraint violation's detail (repo memory), so the 23P01 alone cannot name the clashing dates. **Open question Q2.**
8. **The resolver is a fleet read (`FLEET_DRIZZLE`)**, for the reason `CalcScopeService` records: a cross-organization system read inside the sweep with no tenant actor (ADR 0043 Amendments 2/3). Its containment is `cp.organization_id = a.organization_id` in the statement itself, and an invariants scan holds that predicate the way ADR 0055 part (d) holds `location_id`.
9. **Batched once per sweep**, like membership: every `(assetId, key)` pair of every scheduled `v3` definition in one statement (`unnest` + `CROSS JOIN LATERAL … LIMIT 1`, the shape `getLatestSamplesForPairs` measured at 10 ms against 14 s for the `IN (unnest…)` form). `at` is the sweep's own `nowMs`. A failed read refuses every definition with `paramRefs` as **`parameters_unresolved`** — a fourth runtime reason beside the three ADR item 8 lists, mirroring `membership_unresolved`. **Open question Q4.**
10. **Nearest scope is an `ORDER BY` on nullness, not three queries**: `ORDER BY (asset_id IS NOT NULL) DESC, (location_id IS NOT NULL) DESC LIMIT 1` over rows where `[effective_from, effective_to)` contains `at`. Half-open: `effective_from <= at AND (effective_to IS NULL OR effective_to > at)`. No `COALESCE` on `value`, no fallback — the invariants scan asserts the absence.
11. **Authorization.** Read: `requireMasterDataUser` and the row's organization in `readableOrganizationIds(jwt)` (a `location_admin` may read its organization's tariff — the value is not secret inside the tenant). Write, per row scope: organization scope → `canManageOrganization`; location scope → `canManageLocation`; asset scope → `canManageAsset`. A `location_admin` writing an organization-scoped row is a 403, and the web form hides that option for the role rather than clamping it (the `F3.1d` finding). **Open question Q5.**
12. **`key`, `organizationId` and the scope are immutable on PATCH**; `value`, `effectiveFrom`, `effectiveTo` are editable. A re-scope is delete + create. Keeps the overlap rule one predicate. **Open question Q6.** Delete is a hard `DELETE` with an audit row (ending validity is an edit of `effectiveTo`). **Open question Q10.**
13. **`streaming_on_v2` keeps its name** and now fires for `v3` too (`calc-definition.ts:205` already tests `dialect !== CALC_DIALECT`). Renaming a metric label for tidiness would break every dashboard reading it; the docblock says "any scheduled-only dialect".
14. **Every `=== CALC_DIALECT_V2` gate becomes a `v1`-or-not test**, and an invariants scan forbids the literal comparison outside the three grammar files. Measured with `grep` at this gate: **23 source sites** compare to `CALC_DIALECT_V2` (§7 lists them); each one silently excludes `v3` — the override path's cycle check (`asset-point-calc-override.service.ts:221`) would skip a `v3` formula's aggregates entirely, and the migrate path (`asset-templates-migrate-calc.ts:230`) the same. Where a site needs the *cross-asset* half only, `limits.ts` exports `isCrossAssetDialect(d)` (`d !== CALC_DIALECT`); where it needs the *parameter* half, `isParameterDialect(d)` (`d === CALC_DIALECT_V3`).
15. **`formula_dialect` needs no migration.** Measured: `0035_template_point_formula.sql:31` and `0037_asset_point_calc_override.sql:45` add `formula_dialect varchar(32)` with **no `CHECK`**; ADR 0055 widened nothing either. `"bms-calc-v3"` is 11 characters.
16. **The stock keys are seeded by the migration itself** (`INSERT … ON CONFLICT DO NOTHING`, bare arbiter — the `0030`/`0051`/`0060` rule: it joins nothing `db:seed` creates), **not** by `seed.ts`. `0051`'s header says why a mirror seeding path is wrong.

#### U3 — the decision-3 property, three dialects; ADR 0070 invariants parts (a) and (c) — Sonnet, delegated

**Files**
- `packages/shared/src/calc-dsl/dialect-superset.spec.ts`: generalise `runGeneratedCorpus(rng, narrow, wide, generator)` and `runV1CorpusChecks` into a **pairwise** runner over `(v1, v2)`, `(v1, v3)`, `(v2, v3)`. The `(v1, v2)` run stays byte-identical in seed, `N`, pool and assertions. For `(v2, v3)`, the generator gains `v2` productions behind a `dialect` parameter: qualified refs `{CODE.key}` (codes from a pool inside `^[A-Za-z0-9_-]+$`), `sum`/`avg` over `@site`, `@domain('x')`, `@group('x')` — alphabet **without** `$`, so a `v2`-grammar refusal must refuse identically under `v3`.
