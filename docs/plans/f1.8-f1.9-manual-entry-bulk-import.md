# Implementation plan — F1.8 (manual time-series entry) + F1.9 (telemetry bulk import)

Wave 0 · both P0 · no `Depends` · unblocked by **ADR 0018 (accepted)**. No new
ADR is owed for scope. Four decisions in §2 are owed by the human **before the
first test is written** — they change the service signature, not just the
code.

Written by `plan-architect` on 2026-08-19, starting `F1.8`/`F1.9` together per
the human's direction to start both in parallel.

## 1. Goal

Give TRINETRA its first non-ingest write path into `telemetry.point_values`.
Today that hypertable is written only by `apps/ingest` (MQTT/simulator)
through `writeResolved` + `NOTIFY bms_telemetry`; nothing in the API can put a
number in it. **F1.8** adds an authenticated `POST` that records one (or a
handful of) hand-entered readings — the monthly meter walk, the water-quality
lab result — plus the admin screen an operator types them into. **F1.9** adds
CSV/Excel upload of historical readings with a preview-then-commit flow and a
per-row error report. Both write through **one** shared service, so
provenance, scoping, catalog validation and auditing exist in exactly one
place; and both make ADR 0018's `source_kind` real at the controller boundary.
ADR 0018's own "Risk accepted" paragraph owes a schema-level enum "when
F1.8/F1.9 expose the field to callers" — this plan pays it.

### Out of scope

- **No DDL.** `bms.asset_points` and `telemetry.point_values` are used as they
  stand. No actor column on the hypertable (OQ-4), no import-batch table
  (B2.3), no migration — so this pair does **not** take the migration lock and
  can run alongside migration-bearing work.
- **No edit or delete of a reading.** Append only.
- **No change to `apps/ingest`.** `apps/ingest/src/host/bindings.ts` filters
  `ap.source_kind = 'measured'`, so manual points are already excluded from
  the binding index. That is *verified* in step 6, not modified.
- ~~No aggregate refresh from the API.~~ **Superseded 2026-08-20, decided by
  the human.** Originally planned this way; the step-5 hardening pass found
  that without it, a backfilled row is invisible in every rollup read until
  someone remembers to run `pnpm db:refresh-aggregates` — a silent gap, not
  a documented limitation, and OQ-5 already decided a manual reading should
  behave like any other write. `TelemetryWriteService` now calls
  `refreshAggregatesFrom` after commit; see A4 point 7 for the mechanism,
  its two now-fixed failure modes, and the cost. **§10's verification
  procedure is updated to match** — it no longer asserts a backfilled range
  is absent before the manual script runs, because it isn't, by design.
- **No retirement of the 40 synthetic RTU rows** (ADR 0018 "Deferred").
- **No new npm package.** `xlsx@0.18.5` is already a dependency of `apps/api`
  (`apps/api/package.json:38`) and already parses uploads in
  `onboarding-excel.service.ts`. Nothing here is a §9.4 dependency decision.
  (Note for the security review: that pinned version carries the known
  SheetJS advisories; it is pre-existing, and this item widens its exposure
  to a second upload endpoint. Flagging, not fixing.)

## 2. Open questions — answer these before task A1

**Decided by the human, 2026-08-19:** OQ-1 → master-data roles only
(`canManageAsset`, no operator widening yet). OQ-2 → reject by default,
`conflictPolicy: "overwrite"` explicit opt-in. OQ-3 → catalog/mapping unit
wins; a disagreeing explicit unit rejects the row. OQ-5 → keep the current
default (no provenance filter in `RulesService.latestPointValue`); verify,
do not change, in step 6. Tunables kept at the proposed defaults (5 MiB
upload cap, 20 000 row cap) — no objection raised.


**OQ-1 (blocking). Who may write a reading?**
`AccessControlService.canManageAsset` calls `assertMasterDataRole`, which
admits `admin`, `organization_admin`, `location_admin` and **excludes
`operator`**. The person who walks the plant with a clipboard is an operator.
The alternative path is `assertOperationsWriteRole(jwt, "operational")`
(ADR 0017: "records what *did* happen" — `operator: { operational: true }`)
plus `canReadAsset` for scoping. *Recommendation:* ship the first cut
master-data-only (`canManageAsset`) — it adds no new authorization path and
widening later is additive. **Say it out loud that operator entry is the
likely real requirement**, and that it is an amendment to ADR 0017, not a code
tweak. This decides the service signature and every access-control assertion;
it cannot be deferred.

**OQ-2 (blocking). What happens at an existing `(time, asset_id, point_key)`?**
That triple is the primary key of `telemetry.point_values`. Ingest upserts
(`buildUpsert`). Options: reject the row, overwrite, or overwrite only on
explicit opt-in. *Recommendation:* reject by default; allow
`conflictPolicy: "overwrite"` as an explicit request field; never make
overwrite the default for an import — silently rewriting history is the one
outcome an operator cannot see. This is the `onConflict` clause and the shape
of F1.9's error report; it blocks the first insert. **Consequence
(non-blocking):** with this answer, correcting a typo means re-writing the
same timestamp with `overwrite`, and the audit log holds both entries.
Supersede-with-history would be DDL and an ADR; recorded as the default, not
asked again.

**OQ-3 (blocking). Unit precedence.** Three units exist for one reading: the
caller's optional `unit`, `bms.asset_points.unit`, and the `bms.point_keys`
catalog unit. Nothing decides what happens when the caller sends `kW` for a
point the catalog calls `kWh`. *Recommendation:* the mapping/catalog unit wins
and a **mismatch rejects the row** — storing the caller's unit silently is a
data-integrity bug that typechecks, and dropping it silently is worse. Omitted
unit is accepted and filled from the catalog. **This must live in the shared
service (A4), not in each sibling** — decided separately, the two features
will disagree invisibly.

**OQ-4 (non-blocking, but state the default).** There is no actor column on
`telemetry.point_values`. The only record of who typed a number is the
`bms.audit_log` row this plan writes, so a CSV export of the hypertable cannot
attribute a value. Attribution on the reading itself is DDL on a hypertable —
a migration and a §10 scope call, not this plan.

**OQ-5 (conditional — blocking only if the answer is "no"). Does a
hand-entered value drive the alarm engine?** `RulesService.latestPointValue`
orders by `time desc limit 1` with **no provenance filter**, so today's
default is *yes*: a manual reading at `now()` feeds threshold evaluation and
can raise or clear an alarm. Backfilled history (F1.9) sits below the latest
sample and normally cannot. Related: ADR 0027's staleness gate reads
last-seen, so a manual reading stops an ungatewayed asset looking stale —
right for a meter read by hand, wrong for a dead gateway. If the answer is
"exclude manual", that is a change to the rules query and belongs in this
pair. If it is "keep the default", nothing changes and the behaviour is
confirmed in step 6.

**Tunables the human may want to set rather than accept:** upload size cap
(proposed **5 MiB**) and row cap per file (proposed **20 000**).

## 3. Serial or parallel

**Phase A (the shared foundation) is serial and hands-on. Do not delegate
it.** It defines the interface both features hang off — §3's "⛔ do not fan
out" rule covers exactly this shape, and a subagent building it cold cannot
make the decisions in §2. It merges to `main` on its own, under the human's
step-7 gate, carrying a service that has no caller yet. That is deliberate and
has precedent here (`F2.1` shipped `assets.template_id` for `F2.2` to use).

**Phase B fans out to two worktrees.** F1.8 and F1.9 are genuinely independent
once Phase A is frozen: different controllers, services, pages and specs. Use
`superpowers:using-git-worktrees`, one branch each, each producing its own
diff for the step-5 reviewers and the human's merge.

**Four files will collide, and that is cheaper than avoiding it.** Each
sibling adds one line to `apps/api/src/admin/admin.module.ts`,
`apps/api/src/openapi/openapi-registry.ts`, `apps/web/src/App.tsx` and
`apps/web/src/lib/admin-access.ts`. Do not engineer that to zero by
pre-registering dead routes. Fix the merge order instead: **F1.8 merges
first** (it is the reference consumer of the shared core); **F1.9 rebases
onto `main` after**.

Phase A is frozen at merge. During Phase B neither worktree edits
`telemetry-write.service.ts`, `contracts/telemetry-entry.ts` or
`resolve-catalog-point-key.ts`. A sibling that needs a change there comes back
to the serial spine, and both worktrees rebase.

## 4. Facts the tasks depend on (verified, not assumed)

- `bms.asset_points` carries `UNIQUE (asset_id, point_key)`
  (`asset_points_asset_id_point_key_unique`) **and**
  `UNIQUE (asset_id, source_data_key)` (`asset_points_asset_source_key_idx`),
  both from migration `0015`. `source_data_key` is `NOT NULL`, so a mapping
  created on demand must synthesise one — and a collision on the second index
  is a real row-level failure mode.
- Migration `0023_source_axis_separation.sql` holds
  `asset_points_source_kind_check` (the four values) and
  `asset_points_source_ref_check` (`measured` ⇒ `rtu_id NOT NULL`; the other
  three ⇒ `rtu_id IS NULL`).
- `telemetry.point_values` has PK `(time, asset_id, point_key)`, a
  `point_values_value_finite_check` (migration `0031` — a range test, because
  `NaN = NaN` is true in Postgres and the `value = value` idiom is a no-op
  here), and **no foreign key on `asset_id`**: the service must prove the
  asset exists itself.
- `bms.assets.code` is **globally unique** (`assets_code_unique`, migration
  `0000`). So a bare `asset_code` in an import file resolves unambiguously —
  but it can resolve to an asset outside the caller's scope, which is the
  disclosure shape commit `962f0e4` just fixed. See B2.1.
- Raw retention is
  `add_retention_policy('telemetry.point_values', drop_after => INTERVAL '730 days')`
  in `packages/db/drizzle/0028_compression_retention.sql`.
- `packages/shared` has **no Vitest project** (`vitest.config.ts` lists
  `apps/api`, `apps/web`, `apps/ingest` and the `repo` project over
  `tests/**/*.test.ts`). A `.spec.ts` under `packages/shared/src` would never
  run. Contract-level assertions go in `tests/` (inline, per §4.6's carve-out)
  or in an `apps/api` `*.schema.spec.ts`.
- `apps/web` coverage counts `apps/web/src/lib/**` only. Page components sit
  outside the denominator, so **pure logic must be extracted into `src/lib`**
  to be testable and to count.
- `AdminModule` declares no `exports`, so `MasterDataAuditService` is
  invisible outside it. That is why the shared write service lives under
  `apps/api/src/admin/`, not `apps/api/src/telemetry/` — DI wiring, not taste.
- `auditLog.entityId` is a `uuid` column. A batch label like `"import-3"`
  throws at insert.
- `FileInterceptor("file")` in `onboarding.controller.ts` is used with **no
  options** — unbounded multer memory storage. F1.9 must pass `limits`.

### A1. The `source_kind` vocabulary in `packages/shared/src/contracts/`

ADR 0018's owed follow-up. `source_kind` is a **closed** vocabulary under
§4.8 — the engine branches on it (`bindings.ts` filters `= 'measured'`) and
its pairing with `rtu_id` is structural, not carriable as data — so `z.enum`
plus the existing CHECK is right, and ADR 0018 already ruled it. Do not
re-open it as a lookup table.

**Test first** — extend `tests/adr-0018-source-axis.test.ts` (assertions
inline per §4.6's carve-out; already named in `typecheck:tests`, so no
root-script edit):
- `pointSourceKindSchema.options` equals, as a set, the four literals parsed
  out of `asset_points_source_kind_check` in
  `packages/db/drizzle/0023_source_axis_separation.sql`. A value in one and
  not the other is exactly the drift this enum exists to prevent.
- `writableSourceKindSchema.options` is a strict subset of
  `pointSourceKindSchema.options` and does **not** contain `measured`.
- `Strict<AssetInstantiationResultDto["sourceKind"], "measured" | "unmapped">`
  is `true`, using the helper in `packages/shared/src/contracts/equality.ts`.

**Then write** `packages/shared/src/contracts/telemetry-entry.ts` (new file):
- `pointSourceKindSchema = z.enum(["measured", "manual", "computed", "unmapped"])`
- `writableSourceKindSchema = pointSourceKindSchema.extract(["manual", "unmapped"])`
  — what a caller may *ask* for. `measured` is excluded because it requires an
  `rtu_id` the API cannot supply here; admitting it would turn a 400 that
  names the options into a 500 from `asset_points_source_ref_check`.
- `telemetryEntryRowSchema` — `{ assetId, pointKey, value: z.number().finite(), unit?: string, time: ISO-8601 }`.
  Any `.refine()` is **immediately followed by `.describe()`**, in that order
  (`tests/adr-0029-openapi-contract.test.ts` scans for it; `.describe()`
  before the refinement is silently lost).
- `telemetryWriteResultDtoSchema` — `{ written, skipped, assetPointsCreated, firstTime, lastTime, batchId }`,
  all-readonly ⇒ **`.readonly()`**, not a hand-written readonly type.
- `rejectedRowDtoSchema` — `{ rowNumber, field, reason }`. Shared, because
  F1.8 takes a small batch and needs it too.
- **Encoding rules:** if any of these composes with another object type, use
  `z.intersection(...)` — never `.merge()` or `.omit().extend()`. A flattened
  schema still typechecks; the guard is a source scan in
  `tests/adr-0030-contract-derivation.test.ts`, so name it here or nobody
  catches it.
- Export from `packages/shared/src/contracts/index.ts`, and the types as
  `z.infer` (never hand-written) from `packages/shared/src/index.ts`.

Also in A1: in `packages/shared/src/contracts/admin.ts`, replace
`assetInstantiationResultDtoSchema.sourceKind`'s standalone
`z.enum(["measured", "unmapped"])` with
`pointSourceKindSchema.extract(["measured", "unmapped"])`, so the narrow
vocabulary derives from the wide one **by construction** (§4.8's rule, in the
narrow-from-wide direction). Do this **or** a subset invariant — not both.

### A3. The raw retention horizon, as a guarded constant

An import older than raw's `drop_after` succeeds, recreates a chunk, and the
next retention run deletes it — "the import worked and the data vanished four
days later". Reject those rows.

The repo has already settled *how* to hold this number. `refresh-aggregates.ts`
derives its floor from `min(range_start)` because it is a rarely-run script;
`point-aggregates.ts` holds `RETENTION_DAYS` as constants precisely because
"a read cannot query `timescaledb_information.jobs` on every call", with
`tests/adr-0025-level-selector.test.ts` as the static guard against migration
`0028`. A write endpoint is the second shape, so follow the second pattern.

**Test first:** extend `tests/adr-0024-retention-bounds.test.ts` (already in
`typecheck:tests`; it already parses `dropAfter("point_values")`) with an
assertion that `RAW_RETENTION_DAYS` in
`apps/api/src/telemetry/point-aggregates.ts` equals the parsed number. Follow
that file's own warning: a parse failure must **throw**, never return `null`
— "no policy" and "could not parse" must not be the same answer.

**Then write:** export `RAW_RETENTION_DAYS = 730` from
`apps/api/src/telemetry/point-aggregates.ts` (it already owns retention
horizons; a new module would be a third home). No new `tests/` file, so
`typecheck:tests` is unchanged — and if that changes, edit the root script in
the same commit, because a file in `tests/` is type-checked by nothing until
it is listed by hand.

### A4. `TelemetryWriteService` — the one write path

New folder `apps/api/src/admin/telemetry-entry/`, file
`telemetry-write.service.ts`, registered in `AdminModule`'s `providers` (one
line).

Freeze this interface here:

```
writeReadings(jwt, {
  rows: TelemetryEntryRow[],          // already Zod-parsed by the caller
  sourceKind: "manual" | "unmapped",  // what a mapping is CREATED with
  conflictPolicy: "reject" | "overwrite",
  auditAction: string,                // "telemetry.manual_entry" | "telemetry.import"
}): Promise<{ result: TelemetryWriteResultDto; rejected: RejectedRowDto[] }>
```

Behaviour, in this order:

1. **Validate every row in application code before any insert.** "Row-level,
   not all-or-nothing" and a batch `INSERT` are otherwise contradictory: one
   non-finite value fails the whole statement through
   `point_values_value_finite_check`. The CHECK is the backstop, never the
   error reporter.
2. Per row: the asset exists; the asset is in the caller's scope (OQ-1's
   chosen check); `time` is not in the future beyond a 60 s skew and not
   older than `now() - RAW_RETENTION_DAYS`, with the rejection message naming
   the horizon; `value` is finite; A2's catalog check passes; **the unit
   agrees with the resolved unit per OQ-3**.
3. Mapping resolution for `(assetId, pointKey)`:
   - **An existing mapping is never mutated** — not its `source_kind`, not
     its `rtu_id`, not its `unit`. A reading into a point that is already
     `measured` is legal and keeps its provenance. Write this sentence down;
     without it a worktree agent will "helpfully" rewrite a gateway-backed
     point to `unmapped`.
   - An **inactive** mapping rejects the row ("point mapping is inactive");
     it never silently reactivates.
   - **Absent ⇒ create on demand:** `rtuId: null`, `sourceKind` as requested,
     `unit` from the catalog,
     `sourceDataKey = "${sourceKind}:${pointKey}"` — `source_data_key` is
     `NOT NULL` and unique per asset, so it must be synthesised, and a
     `23505` on `asset_points_asset_source_key_idx` is a row-level rejection
     with its own reason, not a 500. Insert with
     `ON CONFLICT (asset_id, point_key) DO NOTHING`, then re-read, so two
     concurrent requests cannot both create one. *Why create rather than
     require:* ADR 0018 made `unmapped`/`manual` points first-class exactly
     so a reading can exist before a gateway does; requiring a mapping first
     would mean two trips through a different screen to record one meter
     reading, and would make F1.9 unusable for its stated purpose ("imported
     points may also land as `unmapped` before their gateway is wired").
4. Insert the accepted set into `telemetry.point_values` **in one
   transaction**, chunked, with `ON CONFLICT (time, asset_id, point_key)` per
   OQ-2.
5. Audit through `MasterDataAuditService.write` with `entityType: "asset"`
   and `entityId` = an asset **uuid** (the column is `uuid`; a batch label
   throws). For a multi-asset import write one row per asset with its
   counts, and carry a generated `batchId` uuid in `payload` to tie them
   together. `payload` holds counts, the time range, the source kind, the
   conflict policy and the first N rejected **row numbers** — never file
   contents, never cell values (§9.6).
6. **`pg_notify`, gated by each row's own timestamp — not by this plan's
   original "no notify at all".** The step-5 security review flagged that
   omitting notify entirely contradicts OQ-5's decided default ("keep
   provenance-blind, a manual reading at `now()` drives alarm evaluation
   like any other write") — with no notify, `AlarmEngineService` (which
   hears exclusively via `LISTEN bms_telemetry`, there is no second path)
   never learns of a manual entry at all. Fixed by gating on **the
   reading's own `time`, not on which endpoint wrote it**: a row within
   `NOTIFY_LIVE_WINDOW_MS` (5 minutes) of `now()` is notified, a row outside
   it is not. A live manual entry honours OQ-5; a bulk historical import's
   rows are, by construction, almost never inside that window, so this
   costs the import path nothing. **Decided by the human, 2026-08-20: keep
   it.** The plan's Out of Scope section and this point are the record of
   that decision.
   The notify payload's `time` is `new Date(row.time).toISOString()` — the
   same normalised instant the row is stored at — not the caller's raw
   string. A step-5 code review caught that the first version shipped the
   raw string: `telemetryEntryRowSchema` admits offset-less forms (an
   `<input type="datetime-local">` or a CSV cell both emit one), which
   `Date.parse` resolves against whichever process's local zone reads it —
   the API on write, the browser on receipt. Two different zones would then
   disagree about the same reading's freshness. Fixed before this ever
   shipped past hardening.
7. **The ADR 0023 continuous aggregates are refreshed after commit**, via
   `refreshAggregatesFrom(pool, earliestWrittenTime, latestWrittenTime)` —
   not mentioned in the original plan, added because a write through this
   path is otherwise invisible to `point_values_1m/_5m/_1h/_1d` until the
   next scheduled policy run. **Decided by the human, 2026-08-20: keep it.**
   The plan's Out of Scope section and §10's verification procedure are
   updated to match.
   Measured against the live database: a 3h/12h/3d/30d window (each level's
   own `start_offset`) costs 48–60 ms, acceptable inline. Three
   `refresh_continuous_aggregate` failure modes were found and fixed in
   `refreshAggregatesFrom` itself (`packages/db/src/refresh-aggregates.ts`):
   a window within about one bucket of `now()` raises `refresh window too
   small` outright; a bound landing exactly on the target row's own
   timestamp raises no error but silently fails to materialize that row's
   bucket (TimescaleDB rounds a refresh window to whole buckets — inward at
   both ends — so a bound sitting exactly on a bucket boundary rounds past
   the data it needed to cover); and, security review, the upper bound was
   originally hardcoded to `now()` regardless of the batch's own span, so a
   single row backdated near `RAW_RETENTION_DAYS` (730 days) forced a
   730-day, four-level recompute synchronously in the request — repeatable
   by any master-data user with a one-row body, a pool-exhaustion risk (the
   API pool is `max: 10`, no acquisition timeout). All three are cured by
   the same shape: both `from` and `to` carry a per-level margin, pushed in
   opposite directions, so the refreshed window is the batch's own span
   (not "batch start to whenever this request happened to run") and never
   lands exactly on a bucket boundary. See `REFRESH_MARGIN_MS`'s comment for
   the reproduction of all three. A refresh failure is logged, not thrown —
   the value is already committed, so only a rollup read lags.
8. **Two more findings from the same hardening pass, fixed:**
   - The audit-write loop was briefly keyed off which rows actually landed
     rather than which rows were attempted, so a batch where every row was
     rejected (e.g. every row hitting a `conflictPolicy: "reject"`
     collision) left **no audit trail at all** — contrary to §9.6's
     precedent that a write attempt is always recorded. Fixed to key off
     attempted rows; `rowCount` still reports what was actually written.
   - A non-master-data caller could distinguish "asset exists, forbidden"
     (403) from "asset doesn't exist" (200 with a rejection) by row order,
     since the role check ran per-row, after the existence check.
     `AccessControlService.requireMasterDataUser` is now checked once up
     front, closing the oracle and cutting ~20,000 redundant per-row role
     lookups off an F1.9-sized batch.
   **Recorded, not fixed here — Phase A's own cost, not a new one:**
   mapping creation opens one Postgres SAVEPOINT per distinct new
   `(assetId, pointKey)` pair; past roughly 64 in one batch, Postgres's
   subtransaction cache overflows and every other backend falls back to
   `pg_subtrans` for visibility checks against those rows — degraded
   performance under contention, not wrong output. A pre-check batching
   distinct pairs into one existence query would avoid most of it; left for
   whoever tunes F1.9's row-cap behaviour, since that is also where the
   20,000-row ceiling itself gets enforced (see M2 below). Similarly,
   `validateRow` running three sequential queries per row (asset lookup,
   catalog check, mapping lookup) is ~3 round trips × 20,000 rows before the
   transaction opens; batching to one query per distinct asset and one per
   distinct `(org, pointKey)` is a Phase B rewrite of `validateRow`, not a
   Phase A patch.
   Also noted, not fixed: the `telemetry-write.spec.ts` fixture cleanup
   deletes test rows from `telemetry.point_values` but not the
   `_1m/_5m/_1h/_1d` buckets the post-commit refresh (point 7) now
   materialises for them — a local dev database accumulates aggregate rows
   referencing deleted test assets across repeated runs. Does not affect
   correctness of the next run; pure hygiene, low priority.
   Separately, confirmed the same audit-write-without-`tx` hazard this pass
   fixed for telemetry-write also existed at two call sites in
   `onboarding-commit.service.ts` (`master.onboarding.commit` and
   `master.location.create`, both inside its own open transaction) —
   pre-existing, not introduced by this diff, but the same class of defect
   this pass's own new `MasterDataAuditService` docstring now documents.
   Fixed alongside these findings rather than left as a second "same shape
   elsewhere" backlog item, since the fix is identical and the file was
   already open.

**Test first** — `telemetry-write.integration.spec.ts` + `.test.ts` wrapper,

- an out-of-scope asset is refused (use the `wc-admin@bms.local` /
  `wc-hvac-admin@bms.local` fixtures from `access-fixtures-seed.ts`);
- an unknown `assetId` is refused — there is no FK to do it for us;
- a new mapping is created with `source_kind = 'manual'` and
  `rtu_id IS NULL`;
- an existing `measured` mapping is **byte-for-byte unchanged** after a write
  through it;
- the reading lands with the catalog unit; a mismatched request unit rejects
  the row (OQ-3);
- an audit row exists with the expected action and a uuid `entity_id`;
- a row older than `RAW_RETENTION_DAYS` is rejected and nothing at all is
  written;
- **the CHECK boundary, proved by direct SQL through the pool that bypasses
  the service**: `('measured', NULL)` and `('manual', <rtu>)` both raise, and
  `value = 'NaN'` raises. Driving these through the service would prove the
  Zod enum, not the constraint.
- Clean up **before and after** — a crashed run must not poison the next one
  on a shared local database. Tag every fixture with a prefix such as
  `F18-TEST-`.

### A5. Expose `sourceKind` on the asset-point DTO

Both UIs want provenance in the point picker, and this is the natural
consumer of A1's enum. **One commit, both halves:**
`apps/web/src/api/admin/asset-points.ts` validates through
`adminAssetPointDtoSchema`, and `checkResponse` **throws in dev and test**,
so a schema running ahead of the service breaks every asset-points call
locally. Add `sourceKind: pointSourceKindSchema` to the schema and the field
to `AssetPointsAdminService.mapRow` together; optionally add the column to
`apps/web/src/pages/admin/asset-points-page.tsx`.

### A4a. Other hardening findings from the step-5 review pass

Beyond notify (point 6) and the aggregate refresh (point 7), the concurrent
`code-reviewer` / `security-reviewer` / `agents-compliance-reviewer` pass
surfaced and this session fixed:

- **In-batch duplicates** (two rows sharing `(time, assetId, pointKey)`
  within one request) previously reached `ON CONFLICT DO UPDATE` twice in the
  same statement, which Postgres refuses (`21000`, aborting the whole
  transaction). Fixed with an in-batch `Map`-keyed dedup before the
  transaction opens — first occurrence wins, later ones are a normal
  rejection — mirroring `apps/ingest/src/host/normaliser.ts`'s own
  precedent.
- **A `source_data_key` collision on mapping creation** (an unrelated
  existing mapping already occupies the synthesised key) previously aborted
  the entire batch. Fixed with a nested `tx.transaction()` (Postgres
  `SAVEPOINT`) per distinct `(assetId, pointKey)` pair, so only the rows
  needing that pair are rejected.
- **A reject-policy conflict at an existing `(time, assetId, pointKey)`**
  was previously folded into an aggregate `skipped` count with no named
  entry in `rejected` — a caller could not tell which row it was. Fixed via
  `.returning()` on the insert, diffed against what was submitted.
- **Unit precedence (OQ-3) compared against the catalog unit even when a
  mapping already existed.** A mapping's own `unit` can legitimately differ
  from the catalog's (set explicitly at creation) — fixed to prefer the
  mapping's unit, falling back to the catalog's only when no mapping exists
  yet.
- **`value`/`time` were not validated against `telemetryEntryRowSchema`**
  before reaching the insert — a non-finite `value` or an unparsable `time`
  relied entirely on the database CHECK constraint as the only backstop, so
  a rejection carried no field-level reason. Fixed by running
  `telemetryEntryRowSchema.safeParse` first.
- **Deferred to Phase B, not fixed here — record, do not drop:**
  - **M2 — no cap on `input.rows.length`.** The plan's own tunable (§2,
    20 000 rows) has nowhere to live yet: `TelemetryWriteService` takes
    already-parsed rows, and the row-count ceiling belongs on the
    **controller's** request schema (`z.array(...).max(20_000)`), which
    Phase B1/B2 create. Phase A's service must not invent its own cap
    ahead of the schema that is supposed to own it.
  - **L3 — rejection reasons interpolate caller-supplied values**
    (`row.unit`, `row.pointKey`) verbatim into `RejectedRowDto.reason`.
    Not a vulnerability today — nothing logs or renders `reason` unescaped
    — but Phase B1/B2's controllers and UI must not echo it into a log line
    or a page without treating it as untrusted text.

## 7. Phase B2 — F1.9, CSV/Excel bulk import (worktree 2)

Branch `feat/f1.9-telemetry-bulk-import`. Rebases onto `main` after F1.8
merges.

**B2.1 — the parser and row validator, pure and DB-free.**
`apps/api/src/admin/telemetry-import/telemetry-import-rows.ts`:
`parseWorkbook(buffer) → { headers, rows }`, CSV and XLSX both through
`XLSX.read` (one code path, as `onboarding-excel.service.ts` already does);
header mapping for `asset_code | asset_id`, `point_key`, `value`, `unit`,
`time`; **1-based row numbers that match what the operator sees in Excel**
(header is row 1); in-file duplicate detection on
`(assetRef, pointKey, time)`; the row cap.
**`asset_code` resolution is not the parser's job.** `bms.assets.code` is
globally unique, so a code resolves unambiguously — but it can resolve to an
asset outside the caller's scope. Resolve code → uuid in the *service*, then
run the same scope check as every other row, and make the rejection message
**non-disclosing** ("no asset with that code in your scope"), so a file
cannot be used to confirm that a code exists in another organization. That is
the shape commit `962f0e4` just fixed, and `assertCollisionDisclosureIsScoped`
in the instantiate suite is the precedent for testing it.
*Test first:* `telemetry-import-rows.spec.ts` + `.test.ts` — a good CSV, a
good XLSX, a missing required header, a non-numeric value, a bad timestamp,
an in-file duplicate, an empty sheet, a workbook with no sheets, a file one
row over the cap. Keep it pure so it counts toward coverage without
`DATABASE_URL`.

**B2.2 — request schema.** `telemetry-import.schema.ts` — commit options:
`sourceKind: writableSourceKindSchema` defaulting to **`unmapped`** (per
ADR 0018, imported measured points legitimately land `unmapped` until their
gateway is wired; `manual` is the opt-in for a hand-typed sheet), plus
`conflictPolicy` and an optional scoping `organizationId`/`locationId` if
OQ-1's answer needs it. `.refine()` → `.describe()`. One registry line.

**B2.3 — service.** `telemetry-import.service.ts`: `preview(jwt, buffer, opts)`
parses and validates and writes **nothing**; `commit(jwt, buffer, opts)`
parses, validates, then calls `TelemetryWriteService.writeReadings` once with
the accepted rows. **Stateless between the two calls — the client re-posts
the same file at commit.** A persisted preview would be a new table, i.e. DDL
and an ADR, for a file that is already in the browser; put that reason in the
code comment so nobody re-derives it. Row-level, not all-or-nothing, in those
words: failing rows come back in the report, the accepted set is written in
one transaction, and a file with zero valid rows returns the report and
writes nothing.

**B2.4 — controller.** `POST /admin/telemetry/import/preview` and
`/admin/telemetry/import/commit`, with
`FileInterceptor("file", { limits: { fileSize: 5 * 1024 * 1024 } })` — the
onboarding controller passes no `limits` at all, and F1.9 invites large files
by design. A missing file gets the same `BadRequestException` shape as
onboarding.

**B2.5 — integration spec.** `telemetry-import.integration.spec.ts` +
`.test.ts`: 403 on an out-of-scope asset; **an out-of-scope `asset_code`
rejects without disclosing that the code exists**; a mixed file writes only
the good rows and reports the bad ones with their row numbers; a malformed
workbook returns 400 and writes nothing; an oversize file is refused; created
mappings carry `source_kind = 'unmapped'` with `rtu_id IS NULL`; and the
CHECK boundary again by **direct SQL through the pool**, not through the
service.

**B2.6 — web.** `apps/web/src/lib/telemetry-import-preview.ts` (pure: group
the report by reason, cap what is rendered, format the summary line) with
`.spec.ts` + `.test.ts`; `apps/web/src/api/admin/telemetry-import.ts`;
`apps/web/src/pages/admin/telemetry-import-page.tsx` — choose file → preview
table with per-row errors → explicit Commit button → result summary. Route +
nav line.

**B2.7 — docs.** Flip `F1.9`, mirror the roadmap, separate commit.

## 9. Gates this work must not break

- **Coverage is the gate most likely to fail.** `apps/api/src/**/*.ts` is
  entirely in the denominator, and the integration suites *skip* without
  `DATABASE_URL`. That is why the parser, the row validator and the request
  schemas are pure files with plain `.spec.ts`/`.test.ts` pairs. **Measure
  the final number with `DATABASE_URL` set**, or the thresholds fail for the
  wrong reason and someone is tempted to lower them. Thresholds today:
  `43.0 / 39.1 / 44.8 / 43.2`. **Never lower one to go green; never use
  `thresholds.autoUpdate`.** Re-measure at the end and raise them if the
  number rose, writing the measurement into the comment block as every
  previous item did.
- **`*.spec.ts` holds the assertions, `*.test.ts` is the wrapper** under
  `apps/**` and `packages/**`. Files under top-level `tests/` keep assertions
  **inline** and get **no** `.spec` sibling.
- **A new file in `tests/` is type-checked by nothing until it is named by
  hand in the root `typecheck:tests` script.** This plan extends two existing
  files instead; if that changes, edit the script in the same commit.
- **CI.** New suites run because they sit inside existing Vitest projects and
  CI runs `pnpm test:coverage`. No `.github/workflows/ci.yml` change is
  required — say that in the PR rather than leaving it unsaid, and if any
  suite ends up outside those projects, wire CI in the same change.
- **Never assert on a lifetime counter**, and never assert anything that only
  holds on a database with history: CI's database is created per run.
- `.refine()` immediately followed by `.describe()` in every
  `apps/api/**/*.schema.ts`.
- No `.merge()` / `.omit().extend()` anywhere in `packages/shared/src/contracts/`.
- §9.6: no file contents, cell values, emails or tokens in logs or in
  `audit_log.payload`.
