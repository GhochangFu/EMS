## 1. Goal, and what is out of scope

**Goal.** Give a published template version a way to reach assets already built
from an older version, and give one asset a way to differ from its template
without forking a version. Concretely: an additive migration puts five nullable
calc columns on `bms.asset_points`; the calc engine stops reading
`template_points` alone and instead resolves
`coalesce(asset_points.<col>, template_points.<col>)` per column after
resolving the pin; a new, audited, previewed operation moves a named set of
assets from version N to version N+1 by updating `assets.template_id`, refusing
any delta that removes or re-keys a measured point and creating `asset_points`
rows for measured additions through instantiation's own key-resolution path; a
new, audited override operation sets or clears those five columns per
`(asset, point_key)`, creating the row eagerly with `source_kind = 'computed'`
when none exists; and two browser surfaces expose the two operations —
versions/migration under the template, overrides under the asset.

**Explicitly out of scope.**

- **No backfill and no marker on history** (decision 5). Nothing recomputes
  stored values, and no column records that a series changed formula midway.
  This is a recorded, accepted hazard — do not "improve" it.
- **No follow-the-latest resolution** (Q1). The pin stays the only thing that
  decides which version an asset computes.
- **Measured removal or re-key is refused, not reconciled** (decision 3). No
  deactivation flow, no per-point prompt, no retag workflow.
- **Instantiation is unchanged** (`F2.2`). It still emits no `asset_points` row
  for a derived point. If your diff touches
  `AssetTemplateInstantiationService.planAsset` or its point insert, you have
  gone out of scope.
- **`F2.8` PUE, `F2.9` cross-asset aggregates, `F2.7` tag-mapping bulk
  editor** — untouched. `F2.7` shares `template_points.source_data_key_pattern`
  with decision 4 and **must not be built in parallel with this item**.
- **No new npm package** in any workspace. AGENTS.md §9.4 is not triggered and
  must stay untriggered.
- **No cache-invalidation mechanism** for `CalcDefinitionsService`. Its 60 s TTL
  stays; see §7.

### Q-A and Q-B — ruled 2026-08-22, both as the plan proposed

The owner confirmed both plan defaults on the day the plan was written. They are
**no longer open**; they are recorded below with the reasoning that produced
them, and with what was rejected, so a later reader does not reopen them.

Both claims were verified in source before the ruling: `sourceDataKeyVars`
appears only in the instantiate request path and in its tests — never in
`asset-templates.service.ts`, never in a seed, never persisted — and
`asset-templates.schema.ts:205` carries `domain: assetDomainCodeSchema.optional()`,
so a draft's domain is genuinely PATCHable.

**Q-A. How does a measured *addition* get its `source_data_key` at migration
time?** *Ruled: refuse if unresolvable.*

Decision 4 says "by the same path instantiation uses, so `source_data_key` is
derived from `source_data_key_pattern` exactly as at instantiation". That path
is `resolveSourceDataKey(point, entry)` in
`apps/api/src/admin/asset-templates/asset-templates-instantiate.service.ts`
(lines 498–518), and it substitutes from **`entry.sourceDataKeyVars`, supplied
in the instantiate request body**, plus the one reserved variable `asset_code`.
At migration time those variables no longer exist anywhere — they were never
persisted. So:

- pattern `SITE/{asset_code}/kW` → resolves from `assets.code` alone. Fine.
- pattern `{panel}/{asset_code}/kW` → returns `null`. For a `required` point
  instantiation *throws*.

The common case works and the general case does not.

**The ruling:** reconstruct only `asset_code` from `assets.code`; if any
**required** measured addition fails to resolve for any asset in the selected
set, refuse the entire migration before the transaction opens, naming the point
key, the asset code and the unresolved tokens; optional additions are skipped
and reported, mirroring `planAsset`'s existing discipline.

The accepted cost: **a template whose patterns use tokens beyond `asset_code`
can never be migrated** — those assets must be rebuilt. That is a real
limitation, not an oversight, and the refusal message must be explicit enough
that an operator understands rebuild is the remedy.

Rejected: (a) `POST .../migrate` accepting a per-asset `sourceDataKeyVars` map —
changes the request contract and makes the Versions UI collect, per asset per
token, what the operator already typed at instantiate time; (b) persisting
`sourceDataKeyVars` at instantiation so migration can replay them — it fixes the
root cause, but it edits `F2.2`'s instantiate path, which ADR 0039 and this plan
both put out of scope, and it back-fills nothing for assets that already exist.

**Q-B. What happens when version N+1 carries a different `domain` than version
N?** *Ruled: refuse the migration.*

`createDraftFrom` copies `domain` (line 379), but an author may `PATCH` it on
the draft. Instantiation copies `template.domain` onto `assets.domain`. After a
migration, `assets.domain` can therefore disagree with its own pin, and
`assets_domain_fk` will not notice because both values are valid domain codes.
ADR 0039 does not rule this.

**The ruling:** refuse a migration whose target version's `domain` differs from
the source version's, naming both codes. An operator who wants the
reclassification makes it deliberately, through whatever path already edits an
asset — not as a side effect of a formula migration.

Rejected: (a) updating `assets.domain` as part of the apply — it keeps asset and
pin consistent, but a domain change moves assets between plant-domain views,
rule categories (ADR 0031) and dashboards, and doing that from a screen whose
subject is formulas is exactly the silent-reclassification failure this ADR
exists to prevent; (b) migrating the pin and leaving `assets.domain` alone —
cheapest, and it lets an asset permanently disagree with the version it computes
from with no constraint catching it.

### Decisions this plan makes (not questions — do not escalate them)

**D-1. The override write path validates the *merged* result, and rejects.**

Two individually-valid layers can produce an unusable merge, and the most
likely override is exactly the one that breaks: template `scheduled` +
`calcIntervalSeconds: 300`, override sets `calcTrigger: 'streaming'` and leaves
interval NULL → the coalesce yields `streaming` + `300` →
`toActiveDefinition` (`apps/api/src/calc/calc-definition.ts` line 88) returns
`interval_on_streaming` → **the formula stops computing, as a counted skip,
with no error anywhere the author can see.** The mirror case (`streaming` →
`scheduled` with no interval) gives `missing_interval`.

Therefore: the override endpoint loads the pinned `template_points` row, applies
the proposed override, and runs the exclusivity refinement over the **merged
effective** values, rejecting with a message that names the inherited value in
conflict. Reject rather than auto-clear — auto-clearing discards a template
value silently, which is the failure class this ADR exists to prevent. This is
the faithful two-layer implementation of ADR 0039's "column-level exclusivity in
the Zod layer", not a new ruling.

**D-2. The merge join carries no `active` predicate.**

`asset_points.active` plays no part today in whether a derived formula runs —
the row need not exist at all. Filtering on it would make deactivating a point
silently stop evaluation: new, unruled and silent. Join on
`(asset_id, point_key)` only. Pin it with a test so it is a decision and not an
artefact of how the query got typed.

**D-3. The Versions view is a route, not a sixth tab.**

ADR 0038 decision 2 names **exactly five** tabs and
`tests/adr-0038-template-authoring-ui.test.ts` enforces it by scanning the
source text of `apps/web/src/lib/template-tabs.ts`. That rule protects
`content` *sections* (its reserved list is health / optimisation / dashboards /
maintenance, all content keys). A Versions view writes no `content`, so it is
not what the rule forbids — but a sixth tab still trips the gate, and the
tempting fix is to edit the expected list, which is the wrong fix.

**Build it at `/admin/asset-templates/:templateId/versions`, linked from the
detail page chrome. Do not add a tab. Do not edit
`apps/web/src/lib/template-tabs.ts`. Do not edit
`tests/adr-0038-template-authoring-ui.test.ts`.** (Informational for the human:
ADR 0039 decision 8 says "on the template detail page"; a linked route is the
reading that keeps ADR 0038 intact. No blocker.)

**D-4. The version delta keys on `point_key`, never on `template_points.id`.**

`template_points.id` is per-version and always differs, so keying on it
classifies every point as removed-and-added and refuses every migration — with a
symptom nobody diagnoses quickly. Definitions, computed over the
`kind = 'measured'` subset only: *removed* = `point_key` present in N, absent in
N+1; *re-keyed* = same `point_key`, different `source_data_key_pattern`;
*added* = absent in N, present in N+1. Derived-point differences (formula,
dialect, trigger, interval, staleness, additions, removals) are reported in the
delta and never refuse.

### U6 — Migration API *(serial)*

**Tests first.**
`apps/api/src/admin/asset-templates/asset-templates.migrate.integration.spec.ts`
\+ wrapper:

- Versions list returns every version of `(organization_id, code)`
  newest-version-first with a correct per-version asset count.
- Preview returns the delta and **writes nothing** — assert `assets.template_id`
  unchanged and no new `bms.audit_log` row.
- Apply moves `assets.template_id` for exactly the selected ids and no others.
- Apply on a delta with a measured removal → refused, response names the point
  key and the affected asset count, **and nothing was written**.
- Apply on a delta with a measured re-key → refused likewise.
- Apply with a measured **addition** → new `asset_points` rows exist with
  `source_data_key` resolved from the pattern via `asset_code`, `source_kind`
  agreeing with the asset's `rtu_id` per `asset_points_source_ref_check`.
- Q-A default: a required measured addition whose pattern has an unresolvable
  token → whole migration refused before the transaction, naming point, asset
  code and tokens.
- Q-B default: target version `domain` differs → refused, naming both codes.
- Target version not `published` → `ConflictException`. Target version belongs
  to a different `code` or org → `BadRequestException`.
- Selected asset outside the caller's writable scope → `ForbiddenException`, and
  nothing written.
- Exactly one `bms.audit_log` row per successful apply,
  `action = "master.asset_template.migrate"`, payload carrying `code`,
  `fromVersion`, `toVersion`, `assetIds`.
- **Nothing recomputes history** — stored `point_values` for a migrated asset
  are byte-identical before and after (decision 5).

**Files.**

- **Create**
  `apps/api/src/admin/asset-templates/asset-templates-migrate.service.ts`. A
  third service, not a fourth method on `AssetTemplatesAdminService` — that file
  is near AGENTS.md §4.5's 1000-line cap, and the seam is the same real one
  `AssetTemplateInstantiationService` already took (this is the second operation
  writing outside `asset_templates`/`template_points`).
  - `listVersions(jwt, id)`, `previewMigration(jwt, targetId, body)`,
    `migrate(jwt, targetId, body)`. `:id` is always the **target** version; the
    body carries `assetIds`. The source version is read per asset, so a mixed
    selection is handled honestly rather than assumed.
  - `migrate` re-runs the preview and refuses if it is not clean — never trust a
    preview the client echoes back.
  - Follow `AssetTemplateInstantiationService.instantiate`'s discipline exactly:
    **every fallible decision before the transaction opens**; the transaction
    only writes. Carry a row bound equivalent to its `MAX_POINT_ROWS` (8,000)
    for the measured-addition insert — same Postgres bind-parameter ceiling,
    same statement shape.
  - **Pass the open `tx`**: `await this.audit.write({…}, tx)`.
    `MasterDataAuditService.write`'s own docblock says this is *required* inside
    a transaction — `pg` pools at `max: 10` with no acquisition timeout, so
    asking for a second client mid-transaction can wedge every pooled client
    with nothing to break the deadlock. It also makes the audit row atomic with
    the writes it describes.
- **Create**
  `apps/api/src/admin/asset-templates/asset-templates-migrate.schema.ts` —
  `migrateAssetsBodySchema` (`assetIds`, bounded array of uuids). Parse in the
  controller and translate `ZodError` to `BadRequestException`, exactly as
  `instantiate` does.
- **Modify** `apps/api/src/admin/asset-templates/asset-templates.controller.ts`
  — `GET :id/versions`, `POST :id/migration-preview` (`@HttpCode(OK)`),
  `POST :id/migrate` (`@HttpCode(OK)` — it creates rows but its subject is a
  state change on existing assets).
- **Modify** `apps/api/src/admin/admin.module.ts` — register the provider.
- **Audit string:** `master.asset_template.migrate`,
  `entityType: "asset_template"`, `entityId` = the target version id. There is
  no central action enum, so the string is named here or it drifts.

### U7 — Override API *(serial, after U4)*

`apps/api/src/admin/asset-points/asset-point-calc-override.integration.spec.ts`

- An override on a point key the pinned template version does not declare is

## 5. Contract work — the ADR 0030 checklist for this item

This item touches API responses, so §4.8 / ADR 0030 applies in full:

- Every new response type is `z.infer<typeof …>` over a schema in
  `packages/shared/src/contracts/admin.ts`. No `export type X = { … }` in
  `packages/shared/src/index.ts`.
- **`z.intersection(a, b)`, never `.merge()` or `.omit().extend()`.** The
  override DTO is the one that will tempt you.
- `.readonly()` on any all-readonly object.
- Every `apps/web` reader passes the schema to `adminFetch` as its required
  argument. No `res.json() as Promise<T>`.
- A flattened schema typechecks and looks right. It is named here so it gets
  caught in review rather than by a red gate whose tempting fix is the wrong one.

## 9. Serial or parallel

**Mostly serial, and deliberately.**

`F2.6` is not a ⭐ enabler, so fan-out is not categorically barred. But the spine
is genuinely coupled and stays hands-on and serial:

**U1 → U2 → U3 → U4 → U6 → U7.** The migration defines the columns the contracts
describe, the contracts define what the merge selects, and the merge is the
ADR's named highest-risk change — it is in the hot path of every scheduled and
streaming evaluation, and a wrong coalesce computes a wrong number *silently
rather than failing*. **The merge is not delegated.** Neither is the migration.
U6 and U7 both edit `admin.module.ts`, so they are serial siblings rather than
parallel ones.

**Real fan-out, three units:**

- **U5 (`template-version-delta.ts` + spec)** — new files only, no overlap,
  fully specified by D-4. Hand to `implementer` (`model: sonnet`) in its own
  worktree, startable once U2 lands.
- **U8 and U9** — the two UI surfaces. Different pages, different `lib/`
  modules, different `api/admin/` clients; the only shared file is
  `apps/web/src/app.tsx`, and only U8 touches it. Own worktrees, once U6 and U7
  respectively have landed.

Each delegated unit returns a **summary** — files changed, tests added, what
failed — not a transcript.

**Cross-item constraint, carried from ADR 0039 *Consequences*: `F2.6` is not
parallel-safe with `F2.7`.** Both work the same table, and
`template_points.source_data_key_pattern` is both items' column. Do not schedule
them together.
