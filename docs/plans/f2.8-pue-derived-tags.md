## 1. Goal, and what is out of scope

**Goal.** PUE stops being a curve fitted to one number and becomes a ratio of two `bms-calc-v2` aggregates the engine computes on a site's incomer. The stock incomer entry (`electrical-feeder`) gains three derived points — `site_kw`, `it_kw`, `pue` — so any tenant that imports it gets the ratio by configuration; the ESKOM demo seed pins each site's `incoming-supply` asset to a template carrying the same three points so the running stack shows a measured number; and the API reads Σ `site_kw` / Σ `it_kw` over the incomers in scope, returning `null` where nothing is configured. All three `estimatePue()` copies and every `1` sentinel are deleted, the two contracts go nullable, and the three pages render a dash with a "not configured" hint.

**Explicitly out of scope.**

- **Authoring affordances** for `v2` (dialect selector, coverage input, `@` completion) — `F2.22`.
- **A site-level role, or PUE on every asset.** Ruling 1: the point lives on the incomer only.
- **Any change to `apps/sim`'s magnitudes** in this row's tasks — open question 1 puts that fork to the owner before Task 3; the plan is written for either answer.
- **Renaming the seeded `it-rack` group.** `IT_LOAD` is an additional group per site (ruling 2's reserved code); `it-rack` stays because `apps/web/src/lib/control-room-access.ts:40` and migration `0013` name it.
- **A freshness bound on the KPI read.** The estate `totalKw` reads the latest `kw` per asset with no age bound (`dashboard.service.ts:447-451`); the PUE read takes the same rule so the two tiles on one ribbon age the same way. The engine already refuses to *write* a stale value (ADR 0037 decision 9); the reader shows the last written one, and the ribbon's existing `Stale` badge covers the page.
- **The CSV row label `PUE estimate`.** Unchanged, because `reports.serialise.spec.ts`'s `UNCHANGED_OUTPUT` is ADR 0026's byte-level blast-radius proof and a label edit would force a re-pin for no product gain. The UI labels drop "(est.)".
- **No `AGENTS.md` edit, no `BACKLOG` ✅, no roadmap mirror on this branch** — §9.10, separate `chore(agents):` PR.

## 2. Gate record — the owner's five rulings (2026-09-05, step 2)

Quoted so a later reader finds the scope where it was set. **No ADR is owed**: no new dependency, no schema change, no new module, nothing promoted out of §6.

1. **Owner of the PUE point: the site's `incoming-supply` asset.** The electrical stock entry's incomer gains three `bms-calc-v2` derived points: `site_kw = sum({kw} @site)`, `it_kw = sum({kw} @group('IT_LOAD'))`, `pue = {site_kw} / {it_kw}`. Not a new site-level role, not a point on every asset.
2. **IT load = an asset group with the reserved code `IT_LOAD`.** `bms.asset_groups` is unique on `(location_id, code)` (migration `0010`), so the group is per site, and `@group('…')` resolves against the owner's location (`calc-scope.service.ts` header, ADR 0055 decision 9). A tenant that prefers another code edits the formula.
3. **Estate figure = kW-weighted:** Σ `site_kw` / Σ `it_kw` over the incomers in scope; one site in scope reduces to that site's own ratio; sites with no PUE point are left out of both sums.
4. **Nothing configured → `null`.** `pueEstimate` becomes nullable in both contracts (`packages/shared/src/contracts/dashboard.ts:126`, `operations.ts:20`, ADR 0030); the three pages (`dashboard-page.tsx:83`, `energy-page.tsx:130`, `reports-panel.tsx:224`) show a dash with a "not configured" hint; `reports.serialise.ts:89` writes a dash. The fitted curve `1.22 + min(0.45, totalKw / 12000)` is **deleted** from all three copies — `dashboard.service.ts:541`, `reports.service.ts:332`, `apps/web/src/lib/pue-estimate.ts:2` — no fallback, no `1.0` sentinel (the empty branches at `dashboard.service.ts:436,476,667` and `reports.service.ts:146` return `1` today).
5. **No ADR.** No new dependency, no schema change, no new module, nothing promoted out of §6. The plan quotes these rulings as its gate record; the closure row repeats them.

### 3.1 The demo formula differs from the stock formula, and where

| Point | Stock (`electrical-feeder` v2) | Demo (`BASELINE-ELECTRICAL-INCOMER`) | Why |
|---|---|---|---|
| `site_kw` | `sum({kw} @site)` | same | electrical assets emit `kw` |
| `it_kw` | `sum({kw} @group('IT_LOAD'))` | **`sum({rack_kw} @group('IT_LOAD'))`** | the sim's IT assets emit `rack_kw`, never `kw`; a stock incomer meters real IT feeders in `kw` |
| `pue` | `{site_kw} / {it_kw}` | same | — |

Both are `bms-calc-v2`, `scheduled`, `calcIntervalSeconds: 60`, `minCoverageRatio: null`, `maxInputAgeSeconds: null` (→ 300 s default). `pue` reads two derived siblings on its own asset, which `v2` admits (ADR 0055 decision 7) and the sweep resolves in the same tick through the `computedThisTick` overlay at the bucketed time (`calc-scheduler.service.ts:67-81`); 300 s > 60 s, so plan correction 60's stale-input trap does not fire.

**`minCoverageRatio: null` is a plan decision, not an owner question.** It is ADR 0055 decision 11's default (fail closed), and the ADR says relaxation is opt-in and visible. A tenant relaxes it on the imported draft; the demo runs on a simulator that keeps every member fresh.
