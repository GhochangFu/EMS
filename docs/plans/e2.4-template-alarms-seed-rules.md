## 1. Goal, and what is out of scope

**Goal.** When a published asset template is instantiated, every
`content.alarms[]` entry becomes one `bms.automation_rules` row per created
asset, written **inside the existing instantiate transaction**, with
`source = 'template_alarm'`, `action = {type: "review", target: <category>}`,
**no** `rule_notifications` row, four provenance columns
(`source_template_id`, `source_template_version`, `source_alarm_code`,
`seeded_baseline`, migration `0067`), and a derived, sanitised,
hash-on-overflow code. A proto-rule (operator + threshold) seeds
`enabled = true`; a philosophy row seeds `enabled = false` with `NULL`
operator/threshold, and the rule engine refuses to arm such a row. Two template
routes list drift (`in_sync` / `local_override` / `template_moved` /
`both_moved`) and re-apply the current published version's values to explicitly
named rules, arming a row the re-apply completes. The instantiate result and
its audit row report `ruleCount` / `disabledRuleCount`.

**Explicitly out of scope.**

- **Retro-seeding assets that already exist** (ADR Consequences). No route, no script.
- **Republish moving live rules** — never (decision 1). Re-apply is per rule and explicit only.
- **Any change to `review`'s meaning** (ADR 0041 decision 9, F3.7 Q3). `rule-actions.ts` is not edited.
- **A web page for drift/re-apply.** The two routes are API-only in this row; the SPA change is the Alarms tab banner sentence that becomes false (Q7 files the follow-up row).
- **Archive/new-draft lifecycle of seeded rules** (ADR "Deferred").
- **`rule_executions` growth** — `F3.47`, unchanged.
- **The `chore(agents):` sweep** — separate PR (§9.10); `AGENTS.md` §6 and `docs/roadmap.md` both currently say a template alarm never becomes a rule.

### Derived decisions

- **D1** Seeded row: `rule_type = 'threshold'`, `lifecycle_status = 'published'`,
  `published_at = now()`, `name = message.slice(0, 255)`, `description` =
  philosophy rendered as `Cause:` / `Impact:` / `Action:` / `Skill:` lines
  (present fields only) or `null`, `category = alarm.category ??
  DEFAULT_RULE_CATEGORY_CODE`, `condition = { window: "latest", unit? }` with
  unit = template point override ?? catalog unit, `clear_hold_seconds = null`,
  `duplicated_from_rule_id = null`.
- **D2** `seeded_baseline` stores the **resolved** values:
  `{ operator, thresholdValue, severity, category, message }`, `null` for an
  absent operator/threshold, and the defaulted category when the alarm had none.
- **D3** Code derivation exactly per decision 7, hex suffix upper-cased;
  `55 + 1 + 8 = 64`.
- **D4** Pre-check before the transaction: intra-batch duplicates and a single
  `fleetDb` select across all statuses; a hit is a 409 naming the codes. A
  `23505` inside the transaction is translated to a 409 like
  `translateAssetCodeCollision`.
- **D5** Drift list keys on the template **code** and compares against the
  **currently published** version; `current = null` when the alarm code is
  absent from it. Items are scoped to `writableLocationIds`; re-apply refuses a
  rule whose asset is outside `canManageLocation`.
- **D6** Re-apply re-stamps `source_template_id` **and**
  `source_template_version` and `seeded_baseline`; sets `enabled = true` only
  when operator and threshold were both `NULL` and are now both set; never
  disables; refuses (400, naming the rule) a rule whose alarm code the current
  version no longer carries; writes one `master.asset_template.reapply_alarms`
  audit row.
- **D7** Stored content that no longer parses at instantiate → 409 naming the
  structure-only detail, never a silent zero-rule seed.
- **D8** An alarm on a **skipped** optional point still seeds.
- **D9** Reads of `automation_rules` in the drift service run under
  `withTenant(this.tenantDb, template.organizationId, …)`.

The build chain is shared → db → api → web and a `typecheck` rebuilds all of
it, so two units running it concurrently in one worktree race on `dist/`.
**Every unit is dispatched serially into the single `E2.4` worktree.** U3 is
the seam U4 and U6 call; U4's suite is U6's fixture source, because D5's
verdicts need rows the real instantiate wrote. U6 starts only after PR 1
merges (rebase `--onto origin/main` — a squash orphans the sub-commits).

## 6. Step 6 verification, per layer

Run from the repo root, not the worktree — compose from a worktree recreates
postgres on 5432, and the override remaps it to 5433.

**Database.** The four columns exist with the FK; the index is non-unique on
`(source_template_id)`; zero seeded rows before any instantiate (no backfill).
After one instantiate: rows per alarm per asset with `source='template_alarm'`,
`action->>'type'='review'`, philosophy rows disabled with null operator; the
`rule_notifications` join returns 0; the audit row carries `ruleCount`. After
re-apply: the named rule moved, the un-named one did not. Cold start with
`down -v`, then roles → migrate → seed, then migrate again (replay no-op).

**API.** Rebuild, then `up -d api`; compare the container's `Created` time to
the commit and grep the served bundle for `template_alarm` before reading
anything from it. The two new routes as a `fetch` from the SPA tab (OIDC — no
password grant, the human signs in). `PATCH /rules/:id/enabled` → 400 on a
philosophy row, 200 on a proto. `GET /rules` → no `ResponseContractError` for
the new `source`. End to end: a manual reading above a seeded threshold →
evaluate → an alarm row and **zero** notification deliveries; a reading below →
no alarm.

**Browser** (`browser-verifier`, `javascript_tool` assertions, `find` to
locate, no screenshots): the Rule Engine lists the seeded rules with the
philosophy rows visible and disabled; toggling one shows the 400 text; the
Alarms tab banner shows the new sentence after a hard reload with a changed
asset hash. Claims already held by cheaper gates — counts, provenance,
rollback, verdicts — are **not** re-checked in the browser.

**N/A**: ingest, simulator, MQTT, Timescale aggregates. Nothing here writes
telemetry.

## 8. Concerns, recorded for the ADR amendment

- **Decision 3's update-path guard already exists** (`validateRuleDraft`), and
  `ruleUpdateBodySchema` cannot enable anything. The new code is the toggle
  guard only; the plan pins the existing refusal with a named test.
- **Decision 7's hex suffix must be upper-cased** to satisfy `ruleCodeSchema`;
  the ADR text does not say so.
- **`assertRuleCodeAvailable` excludes archived rows against a total unique
  index** — pre-existing; the seed's pre-check does not inherit it. File a row
  rather than fix it here.
- **160 review-only rules per press** — `F3.47` grows, as the ADR says.
- **No per-rule audit row on re-apply** — the ADR names only the
  template-level action; the security reviewer may ask for per-rule rows.

**Owed at the end:** `migration-reviewer` on PR 1, the four step-5 reviews on
