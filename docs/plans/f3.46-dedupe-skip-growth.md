## 1. Goal, and what is out of scope

**Goal.** `POST /api/v1/rules/evaluate` against an unchanged plant stops adding
rows to `bms.notification_deliveries`. Today every sweep writes one
`skipped_deduped` row per open-alarm rule per joined channel — 118 rows per
channel per press on the seeded database — because
`NotificationsService.dispatchToChannel` (`apps/api/src/notifications/notifications.service.ts:126-131`)
returns through `record()` before the hourly ceiling, and nothing bounds it. After
this item a refusal is **recorded once** per `(channel_id, organization_id,
dedupe_key)`: the service reads the ledger before it writes, returns the same
`{ status: "skipped_deduped", error: null }` result when the row already exists,
and writes nothing. The ledger still answers "I pressed Evaluate now — why was
nobody told?" (owner ruling Q2 on `F3.7`), once, instead of once per press. Unit B
then adds the partial index migration 0038 promised the column's first reader.

**Explicitly out of scope.**

- **No retention policy** for `bms.notification_deliveries` — the owner chose the
  other option; a retention row can be filed later if wanted.
- **No change to either raise path, the hourly ceiling, the transports, or
  `AlarmRaiser`.** `rules/rule-actions.ts`, `rules.service.ts` (994 of 1000 lines
  — §4.5) and `alarm-engine.service.ts` are untouched.
- **No unique index on `dedupe_key`, and no `UPDATE` of an existing row.** The
  ledger stays append-only; the suppression is a growth bound, not a correctness
  invariant (D3).
- **No contract change.** `dispatch` still returns one `DeliveryResult` per
  joined channel; `GET /notifications/deliveries` is unchanged.
- **No change to `sendTest`** — it passes `dedupeKey: null` and never enters the
  refusal branch.
- **The `docs/BACKLOG.md` closure row, `docs/roadmap.md:2313-2314`,
  `AGENTS.md:115` and `:427` ("a delivery row written for every attempt"), and ADR
  0041 Amendment 2** — the caller's `chore(agents):` sweep, not this branch (§8).

### What the fake database in the unit spec can and cannot see

`notifications.service.spec.ts:66-107`'s `fakeDb` answers **every** `select()`
with `from().where()` resolving `[{ count }]` and records every `insert()`. It
cannot see a `WHERE` clause (drizzle hands it an opaque SQL object), so a second
`SELECT` shape must be distinguished by its **projection**: the rate-limit read
selects `{ count }`, the new read selects `{ id }` and adds `.limit(1)`. The
fake answers existence reads from a queue of booleans in dispatch order; the
real `WHERE` is proven by the storm-control suite against Postgres.

### Decisions this plan makes

**D1. The read is one method, `hasRecordedSkip`, shaped like `isOverHourlyLimit`.**
`fleetDb.select({ id }).from(notificationDeliveries).where(and(eq(channelId),
eq(organizationId), eq(dedupeKey), eq(status, "skipped_deduped"))).limit(1)`,
`rows.length > 0`. Same connection and same reason as `isOverHourlyLimit`'s
comment (`:204-208`): a fire-and-forget read with no tenant transaction, so the
organization filter is the `WHERE`, not the GUC. The `channel_id` equality is
served today by `notification_deliveries_channel_time_idx`'s leading column; the
remaining three predicates filter that channel's rows. After Unit A a channel's
ledger holds at most one skip row per `(organization, rule, severity)` plus one
row per real transition, so each read visits at most a few hundred tuples at
today's numbers and the 118 reads of a sweep cost single-digit milliseconds. The
index (Unit B) turns each read into one probe and matters when a channel's ledger
reaches the tens of thousands — years of real transitions, or a pilot with real
alarm churn. **Unit A is safe to ship without Unit B.**

**D2. A failed read falls back to writing the row, as today, with one `warn`.**
Never a send: the refusal branch returns before the transport on every path. The
alternative — skip the write on a failed read — was rejected because it makes "the
ledger was unreadable" indistinguishable from "we already recorded this", which is
the silent-loss shape §4.6 names; and under the same outage `record()`'s own
insert fails and logs, so the ledger degrades **loudly** on both halves. The
growth under a persistent read failure is exactly today's growth, and a transient
failure costs one extra row. The `warn` carries the channel code, the rule code
and a reason only (§9.6). This mirrors `isOverHourlyLimit`'s failure branch,
which also refuses to guess in the sender's favour.

**D3. Concurrency is accepted as a growth bound, not an invariant.** Two sweeps
in flight at once (two humans, or a client looping `fetch` without awaiting)
can both read "no row" and both write. There is no unique index and this plan
adds none: the bound is "at most one row per key per concurrent sweep in the
read-write window", which is finite, versus "one per press", which is not. The
streaming engine writes no refusal rows at all, so it cannot race the sweep here.
Within one `dispatch` the channel loop is serial (`for … await`), so a dispatch
never races itself.

**D4. Unit B's index is partial: `(channel_id, dedupe_key) WHERE status =
'skipped_deduped'`.** It serves D1's read exactly (two equalities, predicate
matches), it is maintained only on skip writes — the smallest population after
Unit A — and it costs `sent`/`failed` writes nothing. `organization_id` is left
out: the rule id is inside the key and a rule has one organization, so the
heap filter on it touches at most the concurrent-sweep duplicates of D3. A full
`(channel_id, dedupe_key)` index would serve `F3.10` (escalation) reading `sent`
rows by key; per 0038's own rule that reader adds its own index when it exists.
No `CONCURRENTLY` — drizzle wraps the run in one transaction (§4.4; `0049` is
the model and `tests/e7.1i-audit-log-index.test.ts` asserts the absence there).

**D5. Two PRs.** PR 1 is Unit A and ships now. PR 2 is Unit B, written **after**
`F2.7` PR 1 has merged `0063` to `main` and this branch has rebased onto it —
not before, because `0064`'s `when` must be strictly greater than `0063`'s
(`scripts/checks/drizzle-journal.mjs:110-121`), and `0063`'s stamp does not exist
until `F2.7` authors it. Stamping `0064` first would make `0063` the out-of-order
entry and fail `F2.7`'s commit instead.

### Open questions — the owner answers these before the first line of code

**Q1. Suppression is per `(channel, organization, rule, severity)` for the life
of the ledger, not per alarm episode. Accept?** Measured: the sweep's refusal key
is `rule:no-alarm:severity` because the raiser returns `alarmId: null` on a
dedupe. Timeline: alarm A1 opens (a `sent` row keyed `rule:A1:sev`); sweep 2
writes the one skip row (`rule:no-alarm:sev`); A1 is acknowledged; the condition
still holds, so sweep 3 opens A2 (`sent`, `rule:A2:sev`); sweep 4 refuses — and
finds sweep 2's row already answers that key, so it writes nothing. The ledger
then shows the A2 episode's refusals through a skip row stamped before A2
existed. **Recommendation: accept.** The answer the row exists to give — "already
open" — is present and correct; every sweep still writes one `bms.rule_executions`
trace per rule (with `alarmId` only on a raise), so "did the sweep reach this
rule?" is answered there; and carrying the open alarm's id through the raiser's
conflict branch is a change to a raise path, which this row excludes. The
alternative — suppress only when a skip row exists within a time window — trades
the absolute bound for one skip row per key per window (118 × 24 rows per day
per channel at one hour), which is the growth the row was filed against, and
`isOverHourlyLimit`'s own comment (`:193-195`) already warns against letting
skips fill windows.

**Q2. Two PRs, with Unit B landing after `F2.7` PR 1 as `0064`?** Measured in
§2. **Recommendation: yes** (D5); PR 1 bounds the growth today, PR 2 is one
`CREATE INDEX` plus its tests, and the row flips ✅ when PR 2 merges. The
alternative is to hold PR 1 until `F2.7` PR 1 merges and ship one PR — which
parks a bounded P2 fix behind an unrelated 11–13-effort item. A second
sub-question the owner may want to rule explicitly: the index is DDL, and the
BACKLOG row names DDL as "an ADR 0041 amendment". This plan reads the index as
the discharge of a promise 0038 (decision 4's migration) already makes in its own
text, recorded in the sweep's Amendment 2 rather than gated on it. If the owner
reads it as a new decision, PR 2 waits for the amendment PR first.

/**

 * `skipped_deduped` row under this key — the refusal has been answered once
 * and is not re-recorded. Same connection and same reason as
 * `isOverHourlyLimit`: no tenant transaction, so the org filter is the WHERE.

private async hasRecordedSkip(channelId: string, organizationId: string, dedupeKey: string): Promise<boolean> {
  const rows = await this.fleetDb
    .select({ id: notificationDeliveries.id })
    .from(notificationDeliveries)
    .where(
      and(
        eq(notificationDeliveries.channelId, channelId),
        eq(notificationDeliveries.organizationId, organizationId),
        eq(notificationDeliveries.dedupeKey, dedupeKey),
        eq(notificationDeliveries.status, "skipped_deduped"),
      ),
    )
    .limit(1);
  return rows.length > 0;
}
