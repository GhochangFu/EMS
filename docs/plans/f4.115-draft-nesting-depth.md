# F4.115 — the onboarding draft's nesting depth: refuse it at the parse boundary, and make the walkers iterative

**Branch:** `F4.115-draft-nesting-depth`, cut from `origin/main` at `be2e61b9`.

**Scope gate:** taken by the owner on 2026-09-09, two rulings, recorded in §1.
Do not re-open it. **No ADR is owed:** this bounds an existing field on an
existing route and adds no dependency (§9.4), exactly as `F4.103` and `F4.104`
did.

**Serial or parallel:** serial, one engineer. The six tasks form one dependency
chain — every later task imports the module the first one creates, and tasks 3
and 4 edit files tasks 2 and 5 also read. There are no independent siblings, so
there is nothing to fan out to a worktree.

---

## 1. Goal

An onboarding draft can be stored so deeply nested that every later read of the
session throws a `RangeError` and answers 500 — **including the
`PATCH :id/draft` that would repair it**, because `mergeDraft` deep-clones the
*stored* draft before it replaces anything.

Measured inside `bms-api-1` (node v20.20.2) against the real
`patchDraftBodySchema.parse` → `mergeDraft` → jsonb write →
`redactDraftForClient` chain:

| `config` depth | PATCH body | zod | `mergeDraft` | stores | later GET / validate / chat | recovery `PATCH {rtus:[]}` |
|---|---|---|---|---|---|---|
| 1500 | 9,082 B | ok | ok | ok | ok | ok |
| 1700 | 10,282 B | ok | ok | ok | ok | ok |
| **2000** | **12,082 B** | ok | ok | **ok** | **RangeError → 500** | **RangeError → 500** |
| 2500 | 15,082 B | ok | ok | ok | RangeError | RangeError |
| 4000 | 24,082 B | ok | ok | ok | RangeError | RangeError |
| 6000 | 36,082 B | ok | ok | **RangeError** | — | — |

The JSON body limit is exactly **102,400 bytes** — confirmed live against
`bms-api-1`, where 102,400 answers `401 Missing bearer token` (the parser passed
it to the guard) and 102,401 answers `413 request entity too large`. 12 KB is
nowhere near it.

This row closes both halves, per **owner ruling 2**:

- **(a)** the draft schema refuses a body that nests deeper than the bound, so
  nothing deep is stored again and the caller gets a 400 naming the limit;
- **(b)** the three `structuredClone` calls and the recursive `scrubSecrets`
  become iterative, so a session that is *already* stored deep is readable,
  patchable back, and can still take a credential.

**Owner ruling 1** put this in its own row, built **before** `F4.107`, because it
lands in `redactDraftForClient` — a different function, a different caller set
and a different severity class from `F4.107`'s LLM forward path.

The depth walker is extracted to one module and `asset-templates-content.schema.ts`
derives from it (§4.8), while the two *limits* stay separate because their
derivations are.

### Out of scope, explicitly

- **`F4.107`.** Owner ruling 1. Do not widen either row into the other.
- **The self-limiting half.** Above ~6,000 the jsonb write itself throws, so the
  500 happens with nothing persisted. That is not the defect and needs no guard;
  the new bound sits far below it anyway.
- **Refusing prototype-pollution keys.** `asset-templates-content.schema.ts`
  refuses `__proto__`/`constructor`/`prototype` at its key schema. Doing the same
  here is the **strictness** axis, which `E7.1f`'s three-producer ruling owns
  (`onboarding.schema.ts:147-212`), not the depth axis. File it as a follow-up
  row; see §8 item 4.
- **Size and key count of `config`/`meta`.** That is `E8.5`'s axis. Depth is not
  size and neither implies the other — the same sentence `F4.104` had to write
  about `F4.103`.
- **The shared response contract.** `packages/shared/src/contracts/onboarding.ts`
  is **not** edited by this row. See task 4 for why, and read it before
  "finishing the job" there.
- **Completeness.** No `.min()`, no `.strict()`, no regex is added anywhere. A
  draft is legitimately partial until it commits (ADR 0011).

## 2. Context an engineer with no history here needs

**Five sites write `bms.onboarding_sessions.draft`**, all of them in
`onboarding.service.ts`, and **a bound on a schema binds only the producers that
parse it** — `F4.104`'s lesson, which this row must respect.

Six rows for five sites: the `chat` site at `:291` takes its patch from either
the model's `draftPatch` or `handleRuleBasedTurn`, and only the first parses
anything.

| # | Producer | Write site | Parses | Can it produce depth? |
|---|----------|-----------|--------|----------------------|
| 1 | `PATCH :id/draft` | `patchDraft`, `:336` | `patchDraftBodySchema` → `onboardingDraftSchema` | **Yes** — the body is arbitrary JSON and `config`/`meta` are `z.record(z.unknown())` |
| 2 | the model's `draftPatch` | `chat`, `:291` | `onboardingDraftSchema.safeParse` | **Yes** — the model emits JSON we `JSON.parse` |
| 3 | `uploadExcel` | `:433` | nothing | **No** — `parseRtus` writes `config: { host, port, tls, topic }`, a flat literal, and writes no `meta` at all |
| 4 | `handleRuleBasedTurn` | `chat`, `:291` | nothing | **No** — `defaultConfig` returns `{host,port,tls,topic}`, `{host,port,unitId,pollIntervalMs}` or `{}`, and writes no `meta` |
| 5 | `createSession` | `:89` | nothing | **No** — it writes the literal `{}`; nothing a caller sent reaches the column |
| 6 | `setCredentials` | `:174` | nothing of this schema | **No** — `mergeDraft(session.draft, {}, {rtuIndex, credentials})`: the patch is empty and `credentials` is `z.record(z.string().min(1).max(MAX_RTU_CREDENTIAL_CHARS))`, two levels by schema, encrypted into `_secrets` as a `{c, iv}` pair rather than written into the draft body |

Producers 3 to 6 therefore need **no guard**, and the reason is that each writes
a shape whose depth is fixed in this repository's source — **state that in the
source** rather than leaving it unsaid, because `F4.104` shipped a docblock
naming two producers when there were three, and that sentence is why the third
shipped unguarded.

Rows 5 and 6 were missing until the post-implementation review, in the one
artifact whose purpose is completeness — the same class of defect the paragraph
above describes, committed while describing it.

Why nothing catches it today: `bodyParser.json()`'s default limit is 102,400
bytes and 12 KB is nowhere near it; V8's `JSON.parse` is iterative while
`JSON.stringify`, `structuredClone` and every hand-written recursive walker are
not; and `z.record(z.unknown())` inspects keys at depth 1 and never descends, so
Zod passes any depth (measured ok at 4,000).

## 3. The four decisions this plan owes

### 3.1 Where the iterative walker lives — and yes, `asset-templates` is refactored to consume it

New module **`apps/api/src/admin/stack-safe-json.ts`**, exporting
`exceedsDepth(value, limit)` and `cloneJson(value)`. Both exist for one reason
and it belongs in one head docblock: recursion over caller-supplied JSON is the
bug it is looking for. `apps/api/src/admin/spreadsheet-guard.ts` is the precedent
for the location — a guard shared by two admin paths gets its own module at
`admin/` level — and both consumers sit under it.

`asset-templates-content.schema.ts` **is** refactored: its file-private
`exceedsDepth` is deleted and imported from the new module instead. The
extraction is a byte-identical body and signature, so the risk is small and
enumerable:

- The only call site is inside `templateContentSchema`'s `superRefine`. Nothing
  else in the repo references the symbol.
- `asset-templates-content.schema.spec.ts`'s existing depth case still exercises
  the refusal through `templateContentSchema`, so it is a live regression gate
  for the move; it must stay green untouched.
- Coverage of the function moves from that file to the new module's spec. **Do
  not lower a threshold** to absorb the shuffle (§4.6).
- `docs/adr/0019-template-content-model.md` §A documents `MAX_CONTENT_DEPTH = 12`
  and where it lives. **Do not edit the ADR** — it is a historical record; this
  repo corrects a drifted file reference in the *source*, as
  `asset-templates-content.schema.ts` already does for another stale reference.

`MAX_CONTENT_DEPTH = 12` **stays** in `asset-templates-content.schema.ts` with
its own derivation ("real content nests about five deep"). The two limits are not
the same number and must not be collapsed into one constant: **the walker is the
vocabulary, and each limit is owned by the surface that derived it.**

**Corrected by the post-implementation review: the module exports a third
symbol, and §4.8 was broken in the same commit that honoured it.** As built,
`cloneJson` here and `scrubSecrets` in `onboarding-redaction.ts` were two copies
of one walk — the same `{source, target}` frame stack, the same array branch,
the same shell-create-and-push, and a `defineOwn` byte-identical to `define` —
differing in a single `if`. This plan ruled against *fusing the two passes* in
`redactDraftForClient` (§3.3), which stands and is a behaviour argument; it never
considered *sharing the traversal*, which is a different question with the
opposite answer. The module now exports `rebuildDeep(value, isContainer,
visitKey?)`; `cloneJson` is that walk with the JSON-only predicate and no
visitor, and `scrubSecrets` is the same walk with the any-object predicate and a
visitor returning `[REDACTED]`.

The **two predicates stay two.** `cloneJson` returns a `Date` or a `Map` by
reference; the scrub descends into one and rebuilds it as `{}`, which is what the
recursive `Object.entries` form did. Nothing asserted that difference until the
review, and after the merge it was a one-word mutation, so it now has a test on
each side (`assertCloneJsonReturnsANonJsonObjectByReference`,
`assertScrubSecretsRebuildsANonJsonObject`) and a repo invariant pinning one
rebuild stack under `apps/api/src/admin/`, beside the one that pins one
`exceedsDepth`.

### 3.2 Where the onboarding refusal is checked — `onboardingDraftSchema`, not the wrapper

The original brief specified the `patchDraftBodySchema` wrapper, on the grounds
that a refusal on `onboardingDraftSchema` would also refuse a stored draft on
read and so break ruling 2b. **Read from the source, that is an overstatement,
and this plan takes the other placement.** The evidence:

- `onboarding-validate.service.ts:29-45` is a `safeParse` with an early
  `return { valid: false, errors, readyToCommit: false, suggestedPhase }`. It
  **does not throw.** A stored draft that fails the parse becomes one per-field
  wizard error — exactly the treatment already recorded for an over-long stored
  string.
- `OnboardingService.validate` returns `preview: redactDraftForClient(session.draft)`
  regardless, and `getSession` never parses the draft at all. The session stays
  **readable**.
- `patchDraft` parses the request **body** only and calls
  `mergeDraft(session.draft, draft)` with no parse of the stored value. The
  recovery PATCH stays **patchable**.
- The complete list of production consumers of the api copy is three:
  `onboarding-validate.service.ts`, `onboarding-chat.service.ts` (`.data ?? {}`),
  and `patchDraftBodySchema`. **None of them turns a parse failure into a throw.**

So ruling 2b survives this placement, and two things argue for it:

1. **Producer 2 is only covered there.** The model's `draftPatch` parses
   `onboardingDraftSchema` directly and never touches `patchDraftBodySchema`. On
   the wrapper alone, a deep patch from the model is still stored and ruling 2a
   fails for it. The residual — an over-deep model patch fails `safeParse`,
   becomes `{}` through `.data ?? {}` and the turn is silently dropped — is the
   one already ruled acceptable for that producer **and no wider**. Say so; do
   not generalise it.
2. **The depth arithmetic stays clean.** Here the value handed to `exceedsDepth`
   is the draft object, so the draft is depth 1 and the measured floor is the
   number in the constant. On the wrapper the root is the body and every number
   shifts by one.

Two consequences, written down rather than discovered:

- A `.max()` failure short-circuits the object's own `superRefine`. A draft that
  is both over-cap and too deep reports the **count** error only. Do not write an
  assertion that expects depth to be named in that case.
- The check runs *after* the fields parse, which diverges from
  `asset-templates-content.schema.ts`'s deliberate depth-first ordering. That
  ordering exists there because its `superRefine` calls `JSON.stringify` on the
  next line. Nothing in `onboardingDraftSchema`'s parse recurses or serialises —
  `z.record(z.unknown())` returns its values by reference — and Zod was measured
  depth-safe to at least 4,000. Checking after keeps the schema a plain
  `ZodObject` under one `ZodEffects` and keeps the blast radius in §5 to nothing.

The check must **not** go in the controller:
`tests/adr-0029-openapi-contract.test.ts` has an
`it("keeps body and query schemas out of the controllers")`.

### 3.3 What replaces `structuredClone` — and there are **three** sites, not two

| Site | Function | Reached by |
|---|---|---|
| `onboarding-redaction.ts:202` | `redactDraftForClient` | every `GET /sessions/:id`, `validate`, `chat`, `mapSession` |
| `onboarding-redaction.ts:267` | **`attachEncryptedCredentials`** | `POST :id/credentials`, and `uploadExcel` when the workbook carries credentials |
| `onboarding-chat.service.ts:685` | `mergeDraft` | every write path |

**Site 3 is masked by site 1 today.** `mergeDraft` clones at `:685` before it ever
reaches `attachEncryptedCredentials`, so on a deep stored draft
`POST :id/credentials` dies at `:685`. Fix `:202` and `:685` and leave `:267`
alone, and GET works, the recovery PATCH works, and `POST :id/credentials` still
answers 500 — **a green two-site fix that verification against the two routes
ruling 2b names cannot see.** This is `F4.102`'s six-echo-sites shape: count the
sites from the source, and give the third one its own assertion and its own
verification step.

All three take the same `cloneJson`. **`mergeDraft` does not get something
narrower**, and the reason is not laziness: a narrower clone copying only the
levels `mergeDraft`, `reconcileSecrets` and the credential branch actually mutate
would be a *claim* about the mutation set of three functions across two files,
and that is precisely the kind of generalising sentence four consecutive rows of
review have caught as false. `structuredClone`'s guarantee is "the caller's
object is untouched"; keep exactly that guarantee and change only how it is
computed.

**One fused clone-and-scrub pass in `redactDraftForClient` is possible and is not
taken.** The scrub there is *selective* — `location.meta`, `assets[].meta`,
`rtus[].meta` and `rtus[].config`, and nothing else — while `redactDraftForLlm`
scrubs the whole client view. Fusing would mean either carrying an "am I inside
one of the four subtrees" flag down the stack, or scrubbing everything and
changing what the client path redacts. Two iterative passes preserve today's
behaviour exactly. The cost is one extra traversal of a subtree whose depth is
now bounded; its size is not bounded and was not bounded before either, so this
is no regression (`E8.5` owns that axis).

**What an iterative clone must preserve that `structuredClone` gives for free:**

- **Key insertion order.** The response body's byte order and the jsonb text
  depend on it, and `onboarding-redaction.spec.ts` already asserts over
  `JSON.stringify` of this output. Build the shell for a container and define its
  children **in one loop over `Object.keys(source)`**, so key order is fixed at
  that moment and does not depend on the stack's LIFO order. Proved by a fixture
  whose `config` keys are deliberately non-alphabetical; the mutation is
  `Object.keys(source).reverse()`.
- **`__proto__` as an own data property.** This file has `ownBlob`/`setBlob`
  precisely because prototype keys matter here, and the reachable vector is
  `_secrets`, not a request-body `config` key: an RTU whose `code` is the literal
  `__proto__` matches `/^[A-Za-z0-9_-]+$/`, `setBlob` defines it on `_secrets`
  with `Object.defineProperty`, `JSON.stringify` emits it, jsonb stores it, and
  `JSON.parse` returns it as an own property on the next read. A clone written as
  `target[key] = child` invokes `Object.prototype`'s `__proto__` accessor: the
  key is lost and the clone is reparented. Then `reconcileSecrets`'s `ownBlob`
  returns `null`, the credential is dropped and `credentialsSet` flips false —
  the `M4`/`E8.4` class. So `cloneJson` assigns through
  `Object.defineProperty(target, key, { value, enumerable: true, writable: true, configurable: true })`,
  which is `setBlob`'s existing precedent in the same file. **For `cloneJson`
  this is a non-regression, not a fix** — `structuredClone` preserves it today.
- **The same change in `scrubSecrets` *is* a behaviour change, and it must be
  stated.** Today's `out[key] = scrubSecrets(val)` has the bug: an own
  `__proto__` inside a scrubbed subtree vanishes into the copy's prototype. The
  iterative rewrite preserves it as data. That is safe and is worth one comment:
  the output is `JSON.stringify`d to the wire, and the web's own `z.record` parse
  drops the key again on arrival, so nothing downstream is polluted — where today
  the key silently disappears and the API-side copy's prototype is caller-shaped.
- **Cycles and non-JSON values.** `structuredClone` handles cycles and clones
  `Date`/`Map`/`Set`. `cloneJson` does neither, **by contract**: every value it is
  given came from `JSON.parse` of a jsonb column or of a request body, so it is
  acyclic and holds only objects, arrays, strings, numbers, booleans and `null`.
  A value that is not a plain object or array is returned by reference. Write that
  contract in the docblock; do not add a seen-set, which would cost a `Map` per
  node to defend against an input JSON cannot express.

### 3.4 The derivation of the depth number

**Floor — 5**, measured from the shapes the shipped producers actually write,
counting the draft object itself as depth 1:

```
draft (1) → rtus (2) → rtus[i] (3) → config (4) → config.host (5)
```

- `OnboardingExcelService.parseRtus` writes `config: { host, port, tls, topic }`.
  Flat.
- `OnboardingChatService.defaultConfig` writes `{host,port,tls,topic}`,
  `{host,port,unitId,pollIntervalMs}` or `{}`. Flat.
- `buildTemplateBuffer` ships a template of 2 RTU and 3 asset data rows whose
  `config` columns become the same flat object.
- **Nothing in the repo writes a nested `meta` at all.**
- The other draft branches are shallower: `_secrets` reaches 4, `assetPoints`
  reaches 4, `location.meta`'s value would reach 4.

**Bound — `MAX_ONBOARDING_DRAFT_DEPTH = 10`.** The draft skeleton consumes four
levels before the first free-form byte, so 10 leaves a hand-written `config` or
`meta` **six levels of its own structure**, where every shipped producer uses one.
This is the same *form* of judgement `MAX_CONTENT_DEPTH = 12` records — a
measured floor plus stated headroom — and a different number because the
derivations differ: template `content` is an authoring surface a human nests by
hand, while a draft's only free-form fields are a connection config and metadata.

**Ceilings, for contrast — there are three, not two, and the third is on the
read path this row exists to unblock.** All measured inside `bms-api-1` on node
v20.20.2, the serving runtime; a figure from a dev machine's node does not
transfer, because where a recursive walk gives out moves with the platform, the
flags and the frame size.

| Ceiling | Where | After this row |
|---|---|---|
| ~2,000 | `structuredClone` in `redactDraftForClient` | **fixed** — it is `cloneJson` and walks any depth |
| **4,173** | the response's own `JSON.stringify` — returns at 4,173, throws at 4,174 | **still stands** |
| ~6,000 | the jsonb write | **still stands** |

The middle one was missing from the first pass and is the one that bounds ruling
2b: an already-stored draft stays readable **below** it and not above, and for
such a draft the failure has moved from the clone to the serialiser rather than
gone. The band is narrow because the jsonb write is the same `JSON.stringify`
call under a different caller — but **narrow is not empty**: a draft nested
between 4,174 and ~6,000 could be stored by the base code and cannot be served
by this one. Above ~6,000 nothing was ever stored, so there is nothing to serve.

Put all of it in the docblock: the bound sits twice above every shape the
product writes and two orders of magnitude below the lowest of the three, which
is what makes it a semantic bound rather than one tuned to a crash point.

## 4. The tasks, in build order

Each task is: **write the failing test first, watch it fail, then implement.**
Every assertion below names the mutation that reddens **that** assertion — §4.6
requires the mutation to redden the assertion owning the claim, not merely
something in the file.

Follow `onboarding-draft-caps.test.ts`'s shape: **one exported assert-function
per claim, one `it()` per function.** Do **not** append to
`runOnboardingRedactionTests` — it is a single `it()` over dozens of `assert`
calls, and any mutation kills it at the first one.

Two fixture rules apply to every deep test below:

- **Build a deep fixture with a loop**, never with recursion, and never
  round-trip it through `JSON.stringify` — the fixture builder and the assertion
  helper must both be iterative, or the spec throws before the code under test
  does.
- **Every `assert` message on a deep fixture is a string literal.** Interpolating
  the value would `stringify` it and throw while constructing the failure message.

### Task 1 — `apps/api/src/admin/stack-safe-json.ts` plus its spec

**Create:** `stack-safe-json.ts`, `stack-safe-json.spec.ts`, `stack-safe-json.test.ts`.

Head docblock: one reason, both functions — recursion over caller-supplied JSON
is the bug these look for; `JSON.parse` is iterative in V8 and
`JSON.stringify`/`structuredClone` are not; the two *limits* that use
`exceedsDepth` live with the surfaces that derived them and are deliberately not
here.

`exceedsDepth(value, limit)` is moved verbatim from
`asset-templates-content.schema.ts`, keeping its comment *"a recursive depth
check would be the very bug it looks for."*

`cloneJson(value)` is new. Shape: a stack of `{ source, target }` pairs; for each
pair, one loop over `Object.keys(source)` (or the array's indices) that either
defines a primitive on `target` or creates the child shell, defines it, and
pushes the pair. Object children are assigned with `Object.defineProperty`; array
elements by index.

| Assert function | Claim | Mutation that reddens *it* |
|---|---|---|
| `assertExceedsDepthCountsFromTheRoot` | `exceedsDepth(1, 1) === false`; `exceedsDepth({a:1}, 1) === true`; on a draft-shaped fixture with flat `config`, `exceedsDepth(draft, 5) === false` **and** `exceedsDepth(draft, 4) === true` | change the initial frame from `depth: 1` to `depth: 0` |
| `assertExceedsDepthIsIterative` | on a 20,000-deep chain: `exceedsDepth(chain, 20_001) === false` **returns without throwing**; and `exceedsDepth(chain, 10) === true` beside it, with a comment that it exits at depth 11 and would pass under a recursive implementation too | rewrite `exceedsDepth` recursively → the `false` assertion throws `RangeError` |
| `assertCloneJsonIsIndependentAndOrdered` | mutating `clone.rtus[0].config.host` leaves the source unchanged; `Object.keys(clone.rtus[0].config)` equals the source's order on a deliberately non-alphabetical fixture (`{topic, host, port, tls}`) | return `source` instead of a copy → independence reddens; `Object.keys(source).reverse()` → order reddens |
| `assertCloneJsonKeepsProtoAsData` | from a `_secrets` map built through `setBlob` with key `__proto__`: the clone has it as an own property, `Object.getPrototypeOf(clone._secrets) === Object.prototype`, and a bare object is unpolluted | replace `Object.defineProperty` with `target[key] = child` → the own-property assertion reddens |
| `assertCloneJsonIsIterative` | `cloneJson(chain(20_000))` returns, and the leaf value is reachable by an iterative walk of the clone | swap the body for `structuredClone` → `RangeError` |

20,000 is chosen because it is an order of magnitude above the 1,700–2,000 band
where the recursive form was measured to fail, so the mutation reddens on a
Windows dev machine, in CI and in the container alike. **It is not a claim about
where V8's limit is.**

### Task 3 — the three clone sites and `scrubSecrets` (ruling 2b)

**Modify:** `onboarding-redaction.ts` (`:202`, `:242-258`, `:267`),
`onboarding-chat.service.ts` (`:685`).

- `redactDraftForClient`: `structuredClone(draft)` → `cloneJson(draft)`.
- `attachEncryptedCredentials`: `structuredClone(draft)` → `cloneJson(draft)`.

- `scrubSecrets`: rewritten iteratively, same selective semantics — an object key
  that satisfies `isSecretKey` becomes `"[REDACTED]"` and is not descended into;
  everything else is copied; arrays keep their indices, so no index is ever

| Assert function | Claim | Mutation that reddens *it* |
|---|---|---|
| `assertRedactDraftForClientReadsADeepDraft` | on a stored draft whose `rtus[0].config` is 5,000 deep with `_secrets` present: the call returns; `_secrets` is absent; `rtus[0].credentialsSet` is a boolean; and a `password` key planted at the bottom of the chain reads `[REDACTED]` when the clone is walked iteratively | restore `structuredClone` at `:202` → `RangeError`; restore recursive `scrubSecrets` → `RangeError`; stop the scrub loop early → the `[REDACTED]` assertion reddens |
| `assertAttachEncryptedCredentialsReadsADeepDraft` | `attachEncryptedCredentials(deepDraft, 0, CT, IV)` returns and `readEncryptedCredentials` finds the blob under the RTU's code | restore `structuredClone` at `:267` → `RangeError`. **This is the only assertion that reaches site 3**; without it a two-site fix is green |
| `assertScrubSecretsKeepsKeyOrderAndProtoKey` | on a `config` with non-alphabetical keys, `Object.keys` of the scrubbed copy matches the source order; an own `__proto__` inside a scrubbed subtree survives as an own data property and does not reparent the copy | `Object.keys(...).reverse()` → order reddens; `target[key] = …` → the `__proto__` assertion reddens |

Also, in `onboarding-chat.service.spec.ts`, one exported function with its own
`it()`:

| `assertMergeDraftPatchesADeepStoredDraft` | `mergeDraft(deepStoredDraft, { rtus: [] })` returns, the result has `rtus: []`, and the deep stored object is unchanged | restore `structuredClone` at `:685` → `RangeError`; return `current` instead of a clone → the "unchanged" assertion reddens |

## 8. Open questions and gates

1. **The backlog row** was filed ahead of the build, in its own `chore(agents):`
   PR, at `P1 · Effort 2 · Wave 3 · Depends —`.
2. **The placement contradicts the original brief.** §3.2 takes
   `onboardingDraftSchema` where the brief specified `patchDraftBodySchema`, on
   the strength of `onboarding-validate.service.ts` being a non-throwing
   `safeParse` — verified in the source before this plan was accepted. The cost is
   that an already-stored deep draft's `validate` returns the depth error instead
   of its ordinary field errors, and `readyToCommit` stays false until it is
   patched. That is the same treatment `F4.104` gives an over-long stored string,
   and it is what stops a deep `config` reaching `rtu_connection_configs` at
   commit. **If a stored deep draft must remain commit-eligible, the placement
   moves back to the wrapper and producer 2 stays unguarded** — the two cannot
   both hold.
3. **`MAX_ONBOARDING_DRAFT_DEPTH = 10`** is derived in §3.4 from a measured floor
   of 5 plus stated headroom. The floor is a measurement; the headroom is a
   judgement of the same *form* as `MAX_CONTENT_DEPTH = 12`. The spec pins it in
   both directions, so moving it is a one-line change plus two spec edits.
4. **`__proto__` becomes visible where it used to vanish**, inside `scrubSecrets`'
   output. §3.3 argues this is safe and strictly better than today's silent
   reparenting. Refusing the key outright at the parse boundary is the strictness
   axis and is a **new follow-up row**, not part of this one.

**No ADR gate is owed** and none should be drafted — this row bounds an existing
field on an existing route, adds no dependency, and moves no scope. **The merge
gate is the human's.**
