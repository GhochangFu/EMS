## 1. Goal, and what is explicitly out of scope

Let an `admin` or `organization_admin` create, edit and duplicate a dashboard whose scope is one asset group — `bms.dashboards.asset_group_id` set, `location_id` and `asset_id` NULL — from the three surfaces `F3.1d` shipped: the create page, the edit page and the duplicate dialog. Today the column is reachable only by a direct API caller. `DashboardScopeFields` gains a third scope kind `assetGroup` (a radio and a select populated from `GET /admin/asset-groups`), rendered for those two roles **only** and absent from the DOM for every other role. The two callers that prefill from a source dashboard become three-way, which fixes a live defect: an asset-group dashboard is today prefilled as *"organization"*, so a rename on the edit page or a duplicate from the dialog silently produces an organization-wide dashboard.

**Explicitly out of scope.**

- **No permission moves.** `isMasterDataRole`, `isMasterDataAdmin`, `AdminRoute`, `requireMasterDataUser` and `AccessControlService.canManageDashboard` are not edited. `location_admin` does not get the option: the API's group arm refuses it (`access-control.service.ts:426-428`), and an option shown to it would be a 403 behind an enabled Save.
- **No API route, no DTO field, no migration, no dependency.** `POST /dashboards` and `PATCH /dashboards/:slug` already accept `assetGroupId` (`dashboards.schema.ts:99`); `scopeIsSingular` already counts it; `GET /admin/asset-groups` already exists (`asset-groups.controller.ts:25`) and `adminAssetGroupDtoSchema` already carries `organizationId` (`packages/shared/src/contracts/admin.ts:888`). No contract work (§4.8) — no response type changes.
- **Not the asset scope.** `assetId` stays out of the form (ADR 0067 decision 3, instantiator-only). An asset-scoped dashboard opened in the edit page still prefills as *"organization"*; that is a pre-existing gap this row records (§10 Q2) and does not fix.
- **Not `F3.63`.** Nothing routes `asset_group_admin` anywhere it cannot go today; the picker reads `GET /admin/asset-groups`, which refuses that role.
- **Not a widening of `GET /admin/asset-groups`.** The endpoint's own gate is the filter.

## 3. Task 0 — facts re-verified while planning; re-run them before the first line

**0.1 — `GET /admin/asset-groups` for `organization_admin` returns every group across all its organizations' locations.** `AssetGroupsAdminService.list` (`asset-groups.service.ts:55-108`) filters by `writableLocationIds` ∩ `writableOrganizationIds`. For `organization_admin`, `writableLocationIds` (`access-control.service.ts:183-195`) returns every location of its direct organizations, and `writableOrganizationIds` returns those organizations. So the list is complete for the role. **Settled by reading; no open question.** For `admin` both accessors return `null` (unrestricted), so the create page's list is fleet-wide.

**0.2 — the DTO carries the organization.** `adminAssetGroupDtoSchema` has `organizationId: z.string()` and `locationName: z.string().nullable()`. Choosing a group therefore DECIDES the dashboard's organization exactly as choosing a location does (`ScopeLocationOption.organizationId`, plan f3.1d §7). No derivation through the locations list is needed.

**0.3 — the seeded groups are named per location, so the option label needs the location.** `asset-groups-seed.ts:166-194` creates `Electrical`, `Hvac`, `Environment`, `IT & Rack Load`, `UPS & Battery`, `IT load (PUE)` at **every** location, unique on `(location_id, code)`. `F3.36`'s browser pass already found *"six identical `Electrical` options"* in the instantiate picker. The option text is `${name} — ${locationName}` (falls back to `name` when `locationName` is null).

**0.4 — the refusal the UI mirrors has no API assertion.** `access-control.integration.spec.ts:902-929` asserts `location_admin` on its own location (true), organization-wide (false) and a foreign organization (false). **No case feeds it a group scope.** Amendment 5's *"why not `location_admin`"* rests on `target.kind !== "location"` at line 426, which nothing pins. Unit 1 adds the case; without it the §4.6 API layer cannot honestly be called *"held by existing gates"* for this row's central claim.

**0.5 — the browser accounts.** `admin@bms.local` (global `admin`); `wc-admin@bms.local` (`location_admin`, Western Cape); `wc-hvac-admin@bms.local` (`asset_group_admin`, granted the Western Cape `hvac` group — `demo-users-seed.ts:174-203`). ## 4. The design, in one place

### 4.1 `DashboardScopeValue` widens by one arm

```ts
export type DashboardScopeValue =
  | { kind: "organization"; organizationId: string }
  | { kind: "location"; organizationId: string; locationId: string }
  | { kind: "assetGroup"; organizationId: string; assetGroupId: string };
```

### 4.2 Three pure helpers replace nine switch sites

Today the `kind` switch is written **nine times** across four files (grep `scopeChosen|kind === "location"|kind === "organization"` in `apps/web/src`): `scopeChosen` three times (`dashboard-builder-page.tsx:73`, `dashboard-builder-edit-page.tsx:117`, `duplicate-dashboard-dialog.tsx:148`), the prefill twice (`edit-page:90-94`, `dialog:107-111`), the request body three times (`builder-page:82`, `edit-page:128`, `dialog:122-125`), and the dirty check once (`edit-page:110-113`). Adding a fourth arm nine times is nine places to forget one. New module `apps/web/src/lib/dashboard-scope.ts` (the `lib/` pure-model precedent of `dashboard-duplicate.ts`):

```ts
/** Prefill from a stored dashboard. Three-way; an asset-scoped row (ADR 0067) has no form
 * representation and prefills as organization, exactly as before this row. */
export function scopeFromDashboard(dto: {
  organizationId: string; locationId: string | null; assetGroupId: string | null;
}): DashboardScopeValue;

/** True when the chosen kind has its id filled — what enables Save / Create / Duplicate. */
export function isScopeChosen(value: DashboardScopeValue): boolean;

/** The two scope columns a write body carries — exactly one non-null, or both null. */
export function scopeColumns(value: DashboardScopeValue): {
  locationId: string | null; assetGroupId: string | null;
};
```

`scopeColumns`'s return type is structurally `DuplicateDashboardTarget["scope"]` (`dashboard-duplicate.ts:66`), so the dialog passes it straight through.

The `DashboardScopeValue` type moves into this module; `dashboard-scope-fields.tsx` re-exports it (`export type { DashboardScopeValue } from "../../lib/dashboard-scope"`) so no caller's import line changes for the type alone.

### 4.3 The predicate

`apps/web/src/lib/admin-access.ts` gains `canChooseAssetGroupDashboardScope(role)` returning `role === "admin" || role === "organization_admin"`. **Its body is identical to `canCreateOrganizationWideDashboard` today, and it is deliberately a second predicate** — the file's own `canManageNotificationChannels` docblock (lines 60-64) states the rule: two predicates that answer different questions must not be collapsed, or a future change to one silently moves the other. `F3.63` is exactly that future change: it widens *this* predicate to `asset_group_admin` and must not widen the organization-wide one. The docblock says so and cites Amendment 5.

### 4.4 The PATCH body sends both scope columns explicitly (§10 Q1)

`dashboard-builder-edit-page.tsx:128-134` today sends `locationId` always and **omits** `assetGroupId`, with a comment and a spec (`savingDoesNotSendAnAssetGroupIdKey`) whose reason is *"this page has no authority to touch that column"*. After this row the page **does** render that column's control for the two roles, and the prefill is three-way, so the hazard the omission guarded — a plant-area dashboard silently widened to the tenant — no longer exists by omission but by correctness: a group source prefills as `assetGroup` and the body carries its id back. The body becomes `{ name, description, ...scopeColumns(scope) }`. Why this is safe against `DashboardsService.update`'s merged singularity guard (`dashboards.service.ts:508-548`): `scopeColumns` never returns two non-nulls, so the merged row is `{location|null, group|null, storedAssetId}`; `assetId` is never sent, so an asset-scoped row keeps it and the two sent nulls leave it singular. For a `location_admin` the page CAN load a group-scoped dashboard (the read is `getBySlug`, organization-wide, and `AdminRoute` admits the role) — **corrected at review; the first draft said the form never loads.** Two controls hold: the fields' clamp rewrites the kind the role is not offered to an unchosen location, so Save is disabled until a location is picked, and the PATCH that follows meets `update`'s **stored**-scope check (`:530`) first, which refuses the role on the group arm with a 404 — at save, not at load. The explicit `assetGroupId: null` it sends for its own location dashboard clears a column that is already null. The spec that asserted omission is **replaced**, not deleted, by the one that asserts the group id is carried (Unit 6).

### 4.5 The clamp generalises

`dashboard-scope-fields.tsx:76-80` clamps `{kind: "organization"}` to an unchosen location for a role `canOrgWide` refuses. It becomes: clamp when the value's kind is one **this role is not offered** — `(!canOrgWide && kind === "organization") || (!canGroup && kind === "assetGroup")`. An `assetGroup` value for `admin` must pass through untouched (Unit 4 has the positive control).

## 8. Step 6 verification — layers named
