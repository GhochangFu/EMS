## 1. Goal, and what is explicitly out of scope

Let the seeded `wc-hvac-admin@bms.local` (`asset_group_admin`) reach `/admin/dashboards` and `/admin/dashboards/:slug`, see the **asset-group** scope kind and nothing else, bind a point of an asset in one of its own groups, and save a dashboard whose row has `asset_group_id` set and `location_id`/`asset_id` NULL. Six surfaces refuse the role today (Amendment 6 §Q1); every one is opened **beside** the master-data boundary, gated on the predicates the API already applies to dashboards: a `DashboardAuthorRoute` on `canAuthorDashboards`, the two links following it, `canChooseAssetGroupDashboardScope` widened, the group list fed from `GET /auth/me` (whose `assetGroups` gain `organizationId`), and one new non-admin read `GET /assets/:assetId/points` gated on `canReadAsset` that feeds an asset→points chain in `PointPicker`. The second ruling (§Q2) fixes a live defect for every authoring role: an ADR 0067 asset-scoped dashboard opened in the editor prefills as *organization*; it now prefills as a fourth, read-only `asset` kind and its PATCH omits both scope columns.

**Explicitly out of scope.**

- **No master-data permission moves.** `isMasterDataRole`, `isMasterDataAdmin`, `requireMasterDataUser`, `canManageAsset`, `canManageDashboard` and `AdminRoute`'s membership are not edited. `GET /admin/locations`, `GET /admin/asset-points`, `GET /admin/asset-groups` keep refusing the role; Unit 1 pins the asset-points refusal as the positive control — **as built, Unit 1 pins all three refusals (post-merge sweep; see the note at the top).**
- **No location option for the role** (the API's group arm refuses `target.kind !== "assetGroup"`, `access-control.service.ts:463`), **no group option for `location_admin`** (Amendment 5 stands), **no organization-wide option for the role** (already enforced).
- **The create page and the duplicate dialog never offer the `asset` kind.** The instantiator stays `assetId`'s only writer. Duplicating an asset-scoped source still prefills as the source's organization (Amendment 6 §Q2, last sentence) — Unit 3 makes that an explicit fold rather than an accident of a three-way prefill.
- **`assertBoundPointsInOrganization` stays organization-wide.** The picker is the scope, the guard is the tenant (Amendment 6 §Q1 point 4).
- **No migration, no dependency, no new module.** One contract field (additive), one route on the existing `assets` module.

## 4. The design, in one place

### 4.1 The scope union splits into "chosen" and "read-only"

```ts
// apps/web/src/lib/dashboard-scope.ts
export type ChosenScopeValue =
  | { kind: "organization"; organizationId: string }
  | { kind: "location"; organizationId: string; locationId: string }
  | { kind: "assetGroup"; organizationId: string; assetGroupId: string };
/** `asset` is ADR 0067's kind: prefilled from a stored row, never chosen on a form. */
export type DashboardScopeValue = ChosenScopeValue | { kind: "asset"; organizationId: string; assetId: string };

export function scopeFromDashboard(dto: { organizationId; locationId; assetGroupId; assetId: string | null }): DashboardScopeValue; // four-way
export function scopeForDuplicate(dto): ChosenScopeValue;   // the asset arm folds to organization — Amendment 6 §Q2's last sentence, made explicit
export function isScopeChosen(value: DashboardScopeValue): boolean;          // asset: assetId !== ""
export function scopeColumns(value: ChosenScopeValue): { locationId; assetGroupId }; // body UNCHANGED, parameter narrowed
export function scopePatch(value: DashboardScopeValue): Partial<{ locationId: string | null; assetGroupId: string | null }>; // asset → {}
export function scopeChanged(value: DashboardScopeValue, stored: { locationId; assetGroupId }): boolean; // asset → false
export function scopeAssetGroupOptions(scope: AccessibleScope, organizationId?: string): ScopeAssetGroupOption[]; // /auth/me → picker options
```

**Why `scopeColumns` narrows its parameter instead of returning `undefined`s.** Three reasons. (1) `scopeColumns`'s contract is *"the two scope columns a write body carries — exactly one non-null, or both null"* and it is structurally `DuplicateDashboardTarget["scope"]`; an `asset` arm returning two `undefined`s breaks that identity, and one returning two nulls is a lie that would let a future create path silently write an organization-wide row for an asset value. (2) The PATCH must **omit** the keys, and `{ ...{ locationId: undefined } }` produces an own property whose `JSON.stringify` happens to drop — a spec that pins "absent" must pin `Object.keys`, and a helper whose output has to be post-processed is the wrong helper. (3) With the state of the create page and the dialog typed `ChosenScopeValue`, "the `asset` kind never reaches a create body" becomes a compile-time fact, not a runtime branch nobody tests. `scopePatch` is the edit page's helper; it is the only caller.

### 4.2 The option lists come from a hook, and the role decides the source

New `apps/web/src/hooks/use-dashboard-scope-options.ts`:

```ts
export function useDashboardScopeOptions(opts: { role: UserRole; organizationId?: string; enabled?: boolean }):
  { locations: readonly ScopeLocationOption[]; assetGroups: readonly ScopeAssetGroupOption[] }
```

- `locations`: `useQuery({ queryKey: ["admin", "locations", "dashboard-scope", organizationId ?? "all"], queryFn: () => fetchAdminLocations("true", organizationId), enabled: enabled && canChooseLocationDashboardScope(role) })` — the key `PointPicker` already uses for the same fetch, so the cache is shared (today three callers spell three keys for one payload).
- `assetGroups`: for `isMasterDataAdmin(role)` — `useQuery({ queryKey: adminAssetGroupsQueryKey(), queryFn: fetchAdminAssetGroups, enabled: enabled && canChooseAssetGroupDashboardScope(role) && isMasterDataAdmin(role) })`, filtered by `organizationId` when given; otherwise `scopeAssetGroupOptions(useAuthStore((s) => s.scope), organizationId)`.
- Side effect, pinned: a `location_admin` no longer issues the unread `GET /admin/asset-groups` per builder page load that F3.34's closure surfaced to the owner.

The create page keeps its own `organizationsQ`, gated `enabled: canCreateOrganizationWideDashboard(user.role)` (the edit page and the dialog synthesize that list from the dto).

### 4.3 Two predicates, not one, in `admin-access.ts`

- `canChooseAssetGroupDashboardScope` widens to `asset_group_admin` (Amendment 6 §Q1 point 2).
- **New `canChooseLocationDashboardScope(role)`**: `admin`, `organization_admin`, `location_admin`. It answers a question no predicate asks today (the Location radio is unconditional, `dashboard-scope-fields.tsx:132-146`), and the API's answer for `asset_group_admin` is a refusal (`:463`). The file's `canManageNotificationChannels` docblock rule applies: it is not `isMasterDataAdmin` even though the membership is identical today, because they answer different questions. **§11 Q3.**

### 4.4 `DashboardScopeFields` renders per role, and the clamp target follows the role

- Radios: Organization-wide behind `canOrgWide`, **Location behind `canLocation`** (new), Asset group behind `canGroup`. For `asset_group_admin` exactly one radio renders.
- The clamp (`:104-110`) generalises once more: a value whose kind the role is not offered is rewritten to the role's **first offered kind, unchosen** — `canLocation ? { kind: "location", organizationId, locationId: "" } : { kind: "assetGroup", organizationId, assetGroupId: "" }`. Without this the create page's default `{ kind: "location" }` state renders a dead form for the role (a Location select over an empty list, Save disabled forever). **An `asset` value is never clamped** and renders **no radios**: a single line *"Scoped to asset {name}. An asset-scoped dashboard keeps its scope; edit its widgets here."*, the name resolved from a new **required** prop `assets: readonly ScopeAssetOption[]` (`{ id; name }`), falling back to the id. Required, not optional: an optional parameter at an adapter is invisible to `tsc` and to fakes. The create page and the dialog pass `assets={[]}` with the one-line reason (their state type cannot hold the kind).
- `ScopeAssetGroupOption` and `ScopeAssetOption` move to `lib/dashboard-scope.ts` and are re-exported from the component (the `DashboardScopeValue` precedent, `:31-33`), so `scopeAssetGroupOptions` does not import a component from a lib.

### 4.5 The point read, API side

`GET /assets/:assetId/points` on `AssetsController` (`@Get(":assetId/points")`, beside `@Get()`), parse → `canReadAsset` → `this.assets.listPoints(id)`, in that order (the `asset-images.controller.ts` rule: a guard that throws after reading has already read). `ForbiddenException("Asset is outside your access scope")` — the asset-health/asset-images message. For a non-admin an unknown id is indistinguishable from an out-of-scope id (403 both — no existence oracle); the 404 is the service's, reached by `admin` (`readableAssetIds` null) or by any caller the guard admits: `listPoints` first reads the `assets` row and throws `NotFoundException("Asset not found")` when absent, then reads **active** points with the admin list's exact join (`assetPoints` ⋈ `assets` ⟕ `locations`, `ORDER BY point_key`) on `fleetDb` — the guard is the isolation control, the ADR 0043 shape `listAll` already records. Active only, no `?active=` parameter: the picker asks the admin route for `active=true` today and nothing else needs the inactive rows (**§11 Q2**).

The projection is **extracted, not duplicated**: `AssetPointsAdminService.mapRow` (`asset-points.service.ts:684-720`) becomes a module-level `mapAssetPointRow` in a new `apps/api/src/admin/asset-points/asset-point-row.ts`, the admin service delegates to it, and `AssetsService` imports it. A cross-boundary import of a pure function has the `assets.module.ts:3` precedent (`MasterDataAuditService`) (**§11 Q5**). The response is `{ items: AdminAssetPointDto[] }` — the existing `assetPointsListResponseSchema` (`contracts/envelopes.ts:73`); **no contract work under §4.8** beyond Unit 2's one field (a plain `z.object` key, no `.merge`/`.extend`). **As built this sentence is false (post-merge sweep): the response is the five-field `assetPointPickerRowSchema` / `assetPointPickerListResponseSchema`, two exported types — the review refused `AdminAssetPointDto` on the non-admin route; see the note at the top.**

### 4.6 `PointPicker` forks on `isMasterDataAdmin(role)`

That predicate IS the gate of both endpoints the location chain reads (`requireMasterDataUser` = the same three roles). Master-data roles: the location→points chain unchanged. Otherwise: *Asset* (`fetchAssets(organizationId)`, aria-label `Asset`, option text `${name} (${code})`) then *Add point* (`fetchAssetPoints(assetId)`, new in `api/assets.ts`, `fetch`+`withAuth`+`checkResponse` exactly as `fetchAssets`). `WidgetInspector` gains `role: UserRole` and passes it through; its two callers are the two pages (verified: no third).
