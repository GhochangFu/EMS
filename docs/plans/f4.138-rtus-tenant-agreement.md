# F4.138 — `RtusAdminService` refuses a write whose RTU organization disagrees with its location's

Branch `fix/F4.138-rtus-tenant-matches-gate`, from `31156916`. Plan by
`plan-architect` (Fable), 2026-09-27. No ADR: no migration, no schema, no
contract change, no dependency.

## Goal

`update`, `deactivate` and `reactivate` in
`apps/api/src/admin/rtus/rtus.service.ts` authorize through
`canManageLocation(jwt, existing.locationId)` — a grant derived from the
**location's** organization — but open `withTenant(tenantDb,
existing.organizationId, …)` on the **RTU's own column**. Nothing compares the
two. One private helper, `resolveAgreedOrg`, reads the location's organization,
compares it with `rtus.organization_id`, refuses before any write on a
mismatch, and returns the agreed id. All three paths call it in place of their
`existing.organizationId ?? resolveLocationOrg(...)` line, whose fallback was
dead: `rtus.organization_id` is `NOT NULL` (`bms-schema.ts:124`).

Drift is latent: `rtus.organization_id IS DISTINCT FROM
locations.organization_id` returns 0 rows on 2026-09-27.

**Out of scope.** Repairing drift; a constraint or trigger enforcing agreement
(migration, so ADR); `create` (stamps `resolveLocationOrg(body.locationId)` and
cannot drift); the pre-existing 404-before-403 ordering on an unknown id.

## Owner rulings (step 2)

1. **Refuse, do not derive.** Deriving the GUC from the location was rejected:
   the `tenant_isolation` policy on `bms.rtus` (`0047`) is `USING/WITH CHECK
   organization_id = GUC`, so a write under the location's organization would
   match 0 rows and answer 200.
2. **All three write paths**, through one shared helper.
3. **500, `InternalServerErrorException`**, message `RTU organization does not
   match its location's organization`. Precedent: `parse-stored-contract.ts`
   (ADR 0060 ruling 2) — the caller did nothing wrong and has no request to
   correct. Not 409: no API path relocates an RTU or re-stamps its
   organization, so a 409 would promise a repair the operator cannot make.
4. **One `Logger.error` line naming the RTU id only** (§9.6; the two
   organization ids are one query away). Nest's base filter does not log an
   `HttpException`, so without it a refusal leaves no server-side trace.
5. **A short-lived foreign-organization asset** in the integration fixture,
   removed in `afterAll`. Without it the "asset unchanged" claim passes with
   the guard deleted: the asset UPDATE under the drifted GUC reaches only an
   asset of that foreign organization.

## Decisions

- **The guard fires after `canManageLocation`.** A caller without the grant
  keeps the same 403; the refusal is a fact about stored data that only a
  manager of the location sees. It also keeps `resolveLocationOrg`'s docblock
  ("the caller has already passed `canManageLocation`") true.
- **`update` keeps its `.set({ organizationId })` re-stamp**: after the guard
  it is provably the location's organization.

1. **Unit pair** `rtus.service.tenant-agreement.{spec,test}.ts`, fakes only:
   per path, a drifted RTU is refused with the 500; the tenant transaction is
   never opened; a caller without the grant gets a 403 (9 cases). Red first.
2. **The helper and the three call sites.** Correct the class docblock and the

   the location again.
3. **Integration pair** `rtus.tenant-agreement.integration.{spec,test}.ts`,

   Every fixture code starts `f4-138-`.
