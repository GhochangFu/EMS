## 1. Goal, and what is explicitly out of scope

Give `content.dashboards` an authoring surface, and make the API refuse the
widget shapes that surface must never produce. Two halves:

- **Half A — the sixth tab (`apps/web`).** `dashboards` joins `TEMPLATE_TABS`
  and `TemplateTabId` in `apps/web/src/lib/template-tabs.ts`, sixth in the strip
  after Alarms. A new tab body authors the `dashboards` record: named views,
  each view's `featured[]` ordering, and each view's `widgets[]`. It writes
  through `PATCH /admin/asset-templates/:id` using the existing
  read-merge-write path. Decision 3's lifecycle rule applies unchanged —
  read-only on `published` and `archived`. Three executable gates and six prose
  sites move with it.
- **Half B — per-arm cardinality (`apps/api`).** Each of the four arms of
  `templateDashboardWidgetVariants` in
  `apps/api/src/admin/asset-templates/asset-templates-content.schema.ts` takes
  `WIDGET_POINT_CARDINALITY[type]` from `@bms/shared` instead of the shared
  `.max(MAX_WIDGET_POINT_KEYS)`. The alias is deleted. One false green is
  re-keyed.

**Explicitly out of scope.**

- **No renderer.** ADR 0047 decision 6 keeps the boundary and `F3.1c` owns the
  four widget components. This tab authors template *content*; nothing here
  draws a dashboard.
- **No `apps/web/src/lib/widget-catalog.ts`.** That file is `F3.1c`'s, named in
  its backlog row, and it does not exist yet. Creating it here collides two
  in-flight rows. Labels needed by this tab stay local — see §5.4.
- **No instantiation.** Turning template content into `bms.dashboard_widgets`
  rows is `F3.2`, a Wave 2 P1.
- **No seventh tab.** `health` and `optimisation` stay refused by
  `templateContentSchema` and stay out of the strip; `maintenance` stays
  deliberately omitted.
- **No change to `sortOrder` on the Points tab.** Amendment 4 rules it
  untouched: the two surfaces coexist, and if that proves confusing to an author
  it is a closure observation, not a ruling taken here.
- **No migration, no data fix-up, no grandfather path.** Amendment 3 §2 rules
  the stored population empty. Task 0 re-proves it; see §3.
- **No drag-and-drop and no grid-layout library.** Grid is four number inputs.
  A layout library is `F3.1d` and is §9.4-gated.
- **No new file in `tests/`.** Consequently **no `typecheck:tests` edit and no
  `.github/workflows/ci.yml` edit** — see §8.

## 2. Serial or parallel — serial, one branch, Half B first

**Serial. One branch, one PR.**

The ⭐ rule did **not** fire: `F3.1e` is not an enabler, so "never fan out an
enabler" is not what decides this. Nor does the file-collision rule decide it —
Half A touches `apps/web/**` plus `tests/adr-0038-template-authoring-ui.test.ts`,
Half B touches two files under `apps/api/src/admin/asset-templates/`, and the
two sets are disjoint.

What decides it is the fan-out *unit*. `docs/build-operating-model.md` §3's
mechanism is one git worktree per subagent, and the unit that gets a worktree is
a backlog row. Splitting one row across two worktrees produces two branches and
two diffs for one item, which spends the owner's step-7 merge gate — §1's named
scarce resource — twice, to parallelise roughly sixty lines of Half B. §3's own
cost note applies directly: a cold subagent re-deriving this context costs more
than the work it absorbs.

The halves also cannot disagree by construction, which removes the last argument
for isolating them: both read `WIDGET_POINT_CARDINALITY` from `@bms/shared`
rather than restating a number, so the tab's client-side bound and the server's
arm are the same value.

**Half B first**, for two reasons: it is the smaller unit to practise the
red-first discipline on, and once it is in, Half A's §4.6 browser pass exercises
the *tightened* arms rather than the loose ones — a gauge with two points is
refused during the live pass, not after merge.

## 3. Task 0 — prove Amendment 3's finding before writing a line of Half B

Amendment 3 §2 records, as a finding with evidence rather than as a preference,
that the set of stored rows carrying an over-bound widget is empty. It also says
what happens if that is false: *"If `F3.1e`'s build finds a widget that fails a
tightened arm **in stored `asset_templates.content`** … the finding is falsified
and the ruling must come back to the owner rather than be worked around."*

Run this **before** Task 1, not as part of §9's verification. Discovering a
failing row after the arms are tight means discarded work and, worse, invites
the one outcome the amendment forbids.

**Evidence half 1 — no seed writes the key.** Confirmed while planning; re-run
it:

```bash
grep -rn "dashboards" packages/db/src --include=*.ts
```

Expected: only `packages/db/src/schema/dashboard-schema.ts` (the three `F3.1a`
tables). No hit under any `*-seed.ts`.

**Evidence half 2 — no stored row carries an over-bound widget.** Against the
running database:

```sql
SELECT t.id, t.code, t.version, v.name AS view_name,
       w->>'widgetType' AS widget_type,
       jsonb_array_length(w->'pointKeys') AS key_count
FROM bms.asset_templates t,
     LATERAL jsonb_each(t.content->'dashboards') AS v(name, view),
     LATERAL jsonb_array_elements(COALESCE(v.view->'widgets', '[]'::jsonb)) AS w
WHERE jsonb_array_length(w->'pointKeys')
      > CASE WHEN w->>'widgetType' = 'chart' THEN 8 ELSE 1 END;
```

**Expected: zero rows.** Also run the unqualified form
(`WHERE t.content ? 'dashboards'`) and record the count, so the closure says how
large the population actually was, not only that the filtered one was empty.

**If either returns a row: STOP.** Do not widen an arm, do not add a
grandfather branch, do not exclude the row. Amendment 3's finding is falsified
and the ruling goes back to the owner. Record the row's id, code, version, view
name and widget shape verbatim in the hand-back.

Note the scope of the clause: it is about **stored content only**. A *test
fixture* that fails a tightened arm is not a falsification — several exist to be
refused on purpose, and `asset-templates-content.schema.spec.ts:441-450` is one
of them.

## 4. Half B — the arms tighten (`apps/api`)

### 4.1 The encoding

`templateWidgetIdentityFields` at `:298-305` currently spreads one `pointKeys`
bound into all four arms. Remove `pointKeys` from that object and give each arm
its own, read from the shared map:

```ts
/**
 * How many point keys one widget of this type may bind (ADR 0047 Amendment 3).
 *
 * The numbers are **not** restated here. `WIDGET_POINT_CARDINALITY` is where the
 * cardinality is declared (ADR 0047 Amendment 2 §1) and every surface derives from
 * it; an arm that hardcodes `1` re-opens the seam that amendment closed.
 */
const widgetPointKeys = (widgetType: WidgetType) =>
  z
    .array(pointKeyRef)
    .min(WIDGET_POINT_CARDINALITY[widgetType].min)
    .max(WIDGET_POINT_CARDINALITY[widgetType].max);
```

Each of the four arms then carries one added line,
`pointKeys: widgetPointKeys("radial_gauge")` and so on, beside its existing
`widgetType: z.literal("radial_gauge")`.

**Do not restructure the union.** A generic `widgetArm(type, config)` builder
that names each type once was considered and is **not** the plan: Amendment 3
authorises "each arm takes `WIDGET_POINT_CARDINALITY[type]`" and nothing more,
and rebuilding the discriminated union's shape risks `z.discriminatedUnion`'s
arm inference for no gate that is not already covered. The copy-paste hazard —
the gauge arm calling `widgetPointKeys("chart")` — is precisely what the four
per-arm tests in §4.3 exist to catch, which is the amendment's own argument for
demanding a test per arm.

**`.min(1)` stays on all four arms and that is correct.** The shared docblock's
*"`min` is an authoring rule and never a stored invariant"*
(`dashboard-builder.ts:214-218`) is about the **read** path `F3.1b`/`F3.1c`
own — a cascaded point deletion can legitimately take a live widget to zero
bindings and that must stay readable. This is an **authoring** body. Write that
sentence into the code comment so a reviewer does not flag it as a
contradiction.

  `packages/shared/src/contracts/dashboard-builder.spec.ts:216-221` asserts
  every type's `max` is at or below `MAX_WIDGET_POINTS`, and `:235-236` pins

## 5. Half A — the sixth tab (`apps/web`)

### 5.1 Where the logic goes, and why the `.tsx` cannot hold it

`apps/web/vitest.config.ts` sets `environment: "node"` over
`src/**/*.test.ts(x)`, and the root coverage gate's `include` reaches
`apps/web/src/lib/**` and **nothing above it**. A `.tsx` is therefore
unreachable by every test in this repository and invisible to the coverage gate.
ADR 0038 has already had to learn this twice — `template-tabs.ts`'s own docblock
records the move.

So:

- **`apps/web/src/lib/template-dashboard-form.ts`** — every rule. Pure functions
  over plain data: read the stored record defensively, produce editable rows,
  validate, build the payload, and answer "has this changed". No React, no JSX.
- **`apps/web/src/lib/template-dashboard-form.spec.ts`** — the assertions.
- **`apps/web/src/lib/template-dashboard-form.test.ts`** — the wrapper that
  calls the exported `run*Tests()` functions (§4.6; `tests/repo-invariants.test.ts`
  fails a `.spec` with no sibling).
- **`apps/web/src/components/asset-templates/dashboards-tab.tsx`** — wiring
  only, on the `kpis-tab.tsx` shape. No rule that could be wrong lives here.

The naming mirrors the five siblings (`template-kpi-form.ts` ↔ `kpis-tab.tsx`).

`apps/web` carries no `zod` and needs none; adding it would be a §9.4 gate this
row is not entitled to open. Types come from `@bms/shared`
(`TemplateDashboardView`, `TemplateDashboardWidget`, `WidgetType`,
`ChartSeriesKind`, `DashboardWidgetSpec`) and per-arm config narrowing comes
from `Extract<>` over the exported union — the route `F3.1c`'s row already
commits to.

### 5.2 What the tab authors, and the shape of the write

`content.dashboards` is
`Record<viewName, { featured: string[]; widgets?: TemplateDashboardWidget[] }>`
— ADR 0019 §5, at most 20 views, view name 1..64 characters.

**The trap that must be designed against, not discovered.**
`mergeTemplateContent` replaces the whole `dashboards` key. A tab that renders
one view and writes `{ [thatView]: view }` destroys every other stored view —
the silent-destruction defect Unit 6 exists to prevent, reproduced one level
down. **The tab therefore always writes the complete record.**

Affordances:

- **View list.** Every stored view, add a view by name, delete a view. **No
  rename** — a rename is delete-plus-add on a record, nothing asks for it, and a
  half-applied rename drops a view.
- **Per view, `featured[]`** — an ordered selection over the template's declared
  `point_key`s (`template.points`), with move up / move down / remove.
  `featured` is `.min(1).max(50)` and **required**, so a widgets-only view is
  not representable: the form must refuse to save a view with an empty
  `featured` and say why, rather than collect a 400.
- **Per view, `widgets[]`** — add / remove / edit, at most 40. Per widget: type
  (the four), title (optional, ≤255), `pointKeys` bounded by
  `WIDGET_POINT_CARDINALITY[type]`, four grid numbers, and the type's config.
- **Record semantics**, on the array precedent already in
  `template-content-merge.ts`: deleting the last view writes `{}`, it never
  removes the `dashboards` key. `z.record` accepts `{}` and the `<= 20` refine
  passes. "Delete this section" is a different intent and must be asked for, not
  inferred.

**Grid** is four number inputs (`gridX` 0-11, `gridY` ≥0, `gridW` 1-12, `gridH`
1-24) plus the client-side check `gridX + gridW <= 12`, which the API also
enforces at `:383-386`.

**Config, required per type** (from
`packages/shared/src/contracts/dashboard-builder.ts`): `radial_gauge`
`{ min, max }` with `max > min`; `tank_level` `{ fullScale }` positive;
`value_tile` `{}`; `chart` `{ series }`.

**The chart series picker writes the contract value, not an ECharts name, and
the mapping is exact:**

| Label shown to the author | Value written to `config.series` |
|---|---|
| Trend | `line` |
| Trend (filled) | `area` |
| Comparison bars | `bar` |
| Scatter | `scatter` |

`area` **is** a legal contract value (`chartSeriesKindSchema`,
`dashboard-builder.ts:84`). The `area` → ECharts `line` + `areaStyle`
translation is `F3.1c`'s renderer catalog, downstream of this contract. Writing
`line` where `area` belongs type-checks, saves, and stays invisible until
`F3.1c` renders — so the mapping is stated here verbatim and asserted in the
spec.

### 5.5 `mergeTemplateContent` gains a third arm

`apps/web/src/lib/template-content-merge.ts` — `TemplateContentPatch` at
`:45-47` is a union of two **array** sections and `mergeTemplateContent` at
`:111` writes `[...patch.value]`. A dashboards patch is a **record**, so both
change:

```ts
export type TemplateContentPatch =
  | { section: "kpis"; value: readonly TemplateKpi[] }
  | { section: "alarms"; value: readonly TemplateAlarm[] }
  | { section: "dashboards"; value: Readonly<Record<string, TemplateDashboardView>> };
```

The write becomes: arrays are copied as today; the record is copied key by key,
**skipping `UNSAFE_KEYS`**, for the reason the file's own docblock gives one
level up — `Object.keys` over author-typed view names, and `merged[key] = value`
must never be reached with `key === "__proto__"`, which would invoke the
prototype setter. The API refuses such a view name at `safeKeySchema` anyway;
the form must also refuse it client-side with a message naming why, so the
author is told before filling in a form.

`WRITABLE_KEYS` at `:58` already contains `"dashboards"`; nothing there changes.
Existing call sites in `kpis-tab.tsx:108` and `alarms-tab.tsx:113` keep
compiling — a union gains a member, existing arms are unaffected.

Spec additions in `template-content-merge.spec.ts`, following that file's stated
conventions: a dashboards patch preserves `kpis`, `alarms`, `maintenance` and
`someFutureKey`; writing `{}` keeps the key; the merged record does not alias
the caller's object; and a `JSON.parse('{"__proto__":…}')` view name is dropped
with `Object.hasOwn` asserted on the fixture **before** it is used, so nobody
can later "tidy" it into a literal and disarm the check.

### 5.6 The registry entry, and the traps in it

`apps/web/src/lib/template-tabs.ts`:

```ts
export type TemplateTabId =
  "details" | "points" | "calculations" | "kpis" | "alarms" | "dashboards";
```

The union must stay a **single-line** union of string literals —
`tests/adr-0038-template-authoring-ui.test.ts:144` matches
`export type TemplateTabId\s*=\s*([^;]+);` and compares the extracted names to
`EXPECTED` in order.

The array entry goes **last**, one line, one object literal, `id` first, a bare
string literal:

```ts
{ id: "dashboards", label: "Dashboards", hint: "..." },
```

The `hint` string must contain **no `{`**, **no backtick**, **no literal `...`**,
and none of `.map(`, `.concat(`, `.filter(` — `:108-111` counts `{` to get a
second reading of the tab count, and `:165` bans those constructions inside the
array block. A hint such as
`"Which points a dashboard shows, and the widgets drawn from them."` is safe.
