## 2. Diagnosis

**There is no voltage→percent curve in this repository.** The path is:

1. `decodeMqttPayload` (`packages/shared/src/ingest-adapters/mqtt-payload-format.ts`)
   with the topic's payload format. A topic that names none uses the built-in
   `thinkiot-envelope`, which reads `values.batt_volt` and runs `Number(raw)`.
   A **declarative** format could apply `value × scale + offset` here (ADR
   0116); no format in the repo's migrations (`0130`, `0135`) touches
   `batt_volt`, but one created on AWS could. AWS step 0 rules this out.
2. `resolveSamples` (`apps/ingest/src/host/normaliser.ts`): with both scale
   fields `NULL`, `scaleValue` returns the value unchanged; with no
   `eng_min` / `eng_max` there is no range test.

The ThinkIoT device already sends `batt_volt` as a **percentage**: the
reference payload in `exports/PHE-MQTT-REFERENCE.md` carries
`"batt_volt": "100.00"`, and the healthy RTUs read 89–100. So, on the built-in
format, the raw value that gives −1239.13 is **`"batt_volt": "-1239.13"`
itself**: the device made that number. This is an inference from the code and
the live metadata; nobody has looked at a raw RTU 004 frame yet (step 0).

A value that never changes for 30 days points to a fixed input on the device:
most likely its battery-sense input reads a constant (for example 0 V, open or
shorted) and the firmware's own linear voltage→% curve maps it to −1239.13.
Example only, since we cannot see the firmware: a 12 V curve with 11.40 V = 0 %
and 12.32 V = 100 % gives exactly −1239.13 % at 0 V. The site needs to check
RTU 004's battery and its sense wiring.

## 3. Fix

**Set the engineering band `eng_min 0` / `eng_max 100` on the
`battery_charge_pct` point of the `PHE-RTU-HEALTH` template.** This is what
ADR 0056 decision 4 is for: an instrument plausibility band. A scaled value
outside it is dropped and counted `outOfRange`; no row is written. Ingest reads
`coalesce(asset_points.eng_*, template_points.eng_*)`, so once the assets are on
a template version with the band, every PHE RTU gets it.

Why not the other options:

- **A decoder guard** (treat a negative `batt_volt` as empty in `mqtt.ts`)
  changes the documented decoder contract ("the value guards are the legacy
  ones verbatim", `F4.58`) and is specific to one key. It would need an ADR,
  and the band already does the job per point.
- **A hard-coded 0–100 clamp for `%` units** in the normaliser changes ADR 0056
  decision 1 ("`NULL` is a stated rule: no range test") and would *store* a
  false 0 % instead of no reading. Clamping hides a broken sensor; dropping
  shows it.
- **`quality_policy`** does not help: the device does not mark the sample bad,
  so `discard_bad` has nothing to act on.

Limits, stated so nobody expects more:

- An `asset_templates` row is one version, and ingest joins the template on
  `assets.template_id`. The band on v4 bites only after each asset is migrated
  to v4. Ingest reloads bindings every `INGEST_RELOAD_MS` (60 s); no restart.
- The 30 days of −1239.13 rows stay. They are kept on purpose as the record of
  the fault; deleting telemetry is not part of this row.
- The latest stored value stays −1239.13 until a good reading arrives. The
  rule sweep's freshness gate stops a new raise, but the open alarm must be
  closed by hand.
- A **per-asset** override (`eng_min`/`eng_max` on RTU 004's point via the
  asset-point bulk edit panel) works at once with no new version. It is the
  quick option; the template band is the standing fix for all 12.

`PHE-RTU-HEALTH` exists only on the AWS demo (made by hand on 2026-11-11, see
F4.355). No seed or migration in this repo creates it, so the repo carries no
data change. The template editor's Points tab already edits `engMin` / `engMax`
on a draft.
