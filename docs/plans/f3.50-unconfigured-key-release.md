## 1. Goal

`NotificationsService.eventDeliveryBlocked` treats any delivery row that is not
`failed` and not `skipped_rate_limited` as a final answer for an event's dedupe
key. A `skipped_unconfigured` row is therefore permanent: a channel that had no
URL, no recipients, no readable secret or no transport at all refuses one
escalation step, and after the operator fixes the configuration that step is
never sent, for the life of the ledger.

This change **keeps writing the row** — it is the operator's only signal that a
channel is misconfigured — and makes it **stop answering** once the
configuration it recorded is known to be out of date. The test is a watermark
carried on the channel: `max(channel.updatedAt, PROCESS_STARTED_AT)`. A
`skipped_unconfigured` row written at or before that instant is drawn out of the
read's sample **in SQL**; a row written after it still blocks, exactly as today.

Nothing else about decision 10 moves: `failed` still retries to
`MAX_EVENT_ATTEMPTS` (ruling Q9), `sent` and `skipped_deduped` still block for
ever, `skipped_rate_limited` is still excluded outright (Amendment 2 ruling Q2),
and the raise path is untouched.

### Explicitly out of scope

- **`F3.51`**, **`F3.52`**, **`F3.53`**, **`F3.54`** — all four filed by
  `F3.48`, none touched here.
- **Making a `cleared` message retryable.** Amendment 2 declined it for `F3.48`
  and the reason is unchanged: it needs a per-tick read over recently cleared
  alarms and a retention window nobody has chosen.
- **Routing the decision through `ChannelsService.readiness()`.** It is `async`
  and issues a `COUNT`; calling it per due step per tick is `F3.53`'s
  anti-pattern under a new name.
- **Any DDL.** No migration, no new index, no new status, no `ON UPDATE` trigger
  on `notification_channels.updated_at`.
- **Any contract or UI change** (§5, §7).
- **Retention for `bms.notification_deliveries`** — still deliberately unchosen
  (`F3.46` ruling 0).

## 2. Corrections to the design as first stated

Five. Two change the code, three change what Amendment 3 must record.

### C1 — the predicate must be `or(ne, gt)`, not `NOT (… AND …)`

Written literally in drizzle — `not(and(eq(status, …), lte(attemptedAt, …)))` —
the rendered SQL contains `"status" = $n`, and `notifications.events.spec.ts`
block 14 (`F3.48`'s own SQL-shape gate) asserts the negative:

```ts
!/"status"\s*=\s*\$\d+/.test(rendered.sql),
```

That assertion goes red. Use the De Morgan twin:

```ts
or(
  ne(notificationDeliveries.status, "skipped_unconfigured"),
  gt(notificationDeliveries.attemptedAt, unconfiguredSince),
),
```

Same predicate — `status` and `attempted_at` are both `NOT NULL`, so there is no
three-valued-logic difference — and it renders
`"status" <> $n or "attempted_at" > $m`, which block 14's three assertions all
still pass over. Leaving block 14 alone therefore buys a free gate on the *new*
clause's shape as well.

### C2 — the watermark is an API-clock value compared against DB-clock rows

`channels.service.ts:368` sets `updatedAt: new Date()` — **Node's** clock, in the
API process — so every channel that has ever been PATCHed carries an API-clock
`updated_at`. Only a never-edited channel carries the `defaultNow()` value.
`notification_deliveries.attempted_at` is always `defaultNow()`, the **database**
clock. So both halves of the watermark are API-clock values compared against
DB-clock timestamps, not just `PROCESS_STARTED_AT`. Two directions, both
residuals rather than defects:

- **API clock behind Postgres** by more than the interval between the last
  refusal and the operator's edit → the key stays blocked and nothing says so.
  Real skew is milliseconds; the real interval is minutes to hours.
- **API clock ahead** by more than the time elapsed since process start → fresh
  rows are excluded too and C3's bound weakens. Elapsed-since-process-start is
  normally large.

The integration proof must be honest about this: a psql `SET updated_at = now()`
bump exercises a DB-clock/DB-clock pairing production never produces. Bind a
Node-side `Date` instead, and say so in the block's comment.

### C3 — the growth bound is reached by the other arm, and is tighter than stated

The first draft said that within one process the step writes a fresh
`skipped_unconfigured` row per tick and that after `MAX_EVENT_ATTEMPTS` such rows
the count arm blocks the key. It never gets that far:

```ts
return rows.length >= MAX_EVENT_ATTEMPTS || rows.some((row) => row.status !== "failed");
```

`skipped_unconfigured` is not `"failed"`, so the **second** arm blocks on the
very first fresh row. The correct statement: **one fresh row per key per
process, and the next tick is already blocked.** The count arm is never reached.
That is the cost ruling Q1 accepted, reached by a different mechanism than the
rationale describes, and it means three *fresh* unconfigured rows under one key
is not a reachable state — no test may be written as if it were.

It also **strengthens** design constraint 2, in the opposite direction from
`F3.48`. Amendment 2 §3 had to concede that its mixed state was unreachable in
production and that the SQL form was preferred for exactness by construction.
Here the mixed state **is** reachable: one row accumulates per restart, so after
three restarts of a still-misconfigured channel and an eventual fix, a key
legitimately holds one `sent` row and three stale `skipped_unconfigured` rows. A
TypeScript filter over an unordered `LIMIT 3` sample can then return the three
unconfigured rows, empty itself, leave both arms false — and **re-send an event
that was already sent.**

### C4 — the five sources do not split cleanly into two classes

`webhook.transport.ts:89` spans both. `secretState: "unreadable"` comes from
`channels.service.ts:930` (the key is not configured — process) **and** from
`channels.service.ts:939/950` (the decrypt threw, or returned a non-string: a
wrong key, a rotated key, or a corrupt row — per channel, cleared by re-saving
the secret through `update()`, which bumps `updated_at`). The union is still
covered, so ruling Q1 stands; the enumeration needs the correction:

| Site | Cause | Cleared by | Watermark half |
|---|---|---|---|
| `webhook.transport.ts:94` | no `config.url` | PATCH `config` | `channel.updatedAt` |
| `email.transport.ts:82` | no recipients in `config` | PATCH `config` | `channel.updatedAt` |
| `log.transport.ts:51` via `transportFor`'s fallback | `kind` has no transport | PATCH `kind` (or a code change) | `channel.updatedAt` (or restart) |
| `log.transport.ts:51` via `transportFor`'s `smtp === null` branch, and `email.transport.ts:77` (its defensive twin) | `SMTP_HOST` unset | set the env, restart | `PROCESS_STARTED_AT` |
| `webhook.transport.ts:89` | key unset **or** wrong/rotated key **or** corrupt row | restart **or** PATCH `secret` | both halves |

### C5 — a second release trigger, now ruling Q2

`update()` sets `updatedAt: new Date()` **unconditionally**, at the top of
`values`, before any field is examined. So a purely cosmetic write — renaming a
channel, or toggling `enabled` off and on — releases every stranded key on that
channel. At ruling Q7's measured shape (52 backlogged alarms) a rename produces
up to 52 retries and 52 fresh rows inside one 30 s tick, competing for the single
hourly budget `F3.52` was filed about.

**Ruled an accepted cost (ruling Q2).** Without column-level change tracking
`update()` cannot tell a config write from a rename, and erring toward delivery
is the right direction. Amendment 3 §6(a) records it with the `F3.52`
cross-reference.

**Confirmed, and not a problem.** `update()` is the only production writer of
`bms.notification_channels` other than `create()` (`insert(notificationChannels)`
/ `update(notificationChannels)` across the repo returns
`channels.service.ts:319/321/386/392` and three integration-spec fixtures).
Secret rotation, enable/disable and kind changes all go through it. There is no
`ON UPDATE` trigger, so a DBA editing `config` directly in psql does **not**
release the key — a residual to record, not to fix here (a restart releases it
anyway).

**And the backlog row's own error:** it says `NotificationsService.readiness`. It
is `ChannelsService.readiness` (`channels.service.ts:590`).

### Task 2 — `PROCESS_STARTED_AT`

**No test of its own.** Its gate is Task 3's rendered-SQL assertions, which is
where it is observable; a "the constant is a Date" assertion would be vacuous.
Say that in Task 3's block comment rather than writing the vacuous test.

**Production**, `notifications.config.ts`, an exported module constant beside
`notificationsConfig`:

```ts
export const PROCESS_STARTED_AT = new Date();
```

**Why here.** That module already documents which notification facts are frozen
at module load: `notificationsConfig = buildConfig(process.env)` is evaluated on
the line above, and `smtp === null` is the single largest source of
`skipped_unconfigured`. The constant's meaning — "the instant the environment
snapshot this process will use was taken" — is that module's. `EmailTransport`
is confirming evidence: it decides `this.sender` **in its constructor**, so an
SMTP host appearing mid-process would not be picked up even if the config were
re-read.

- A module constant in `notifications.service.ts` also works, and is rejected
  only because the meaning is the config module's.
- **Do not put it in `NotificationsConfig`.** `buildConfig` is documented as "a
  pure function of an environment object"; a `new Date()` inside it breaks that,
  and six spec call sites would silently receive private watermarks.
- **Do not invent a provider or an injected clock.** One `Date`; Task 3's
  assertions give full testability by importing the constant.

Note in the doc comment that it is *module*-load, not literally process start. A
later import would only move the watermark later, which releases more and blocks
less — the bounded direction.

### Task 4 — the release proofs against Postgres

`storm-control.integration.spec.ts`. This is the only place a `WHERE` is real.

**Helper change:** `plantDeliveries` gains an optional `attemptedAt?: Date` and,
when present, binds it into the `INSERT` instead of letting `defaultNow()` fire.

Blocks, after the existing FG1 block:

1. **A stale row releases the key.** Plant one `skipped_unconfigured` row under a
   fresh key with `attemptedAt` an hour in the past, dispatch, assert `sent`,

3. **The block is scoped to one status — a stale `failed` row still counts.**

half of the asymmetry ruling Q-A created on the write half: Q-A special-cased the
*write* because the clear had something to lose (its only visible row); the read
has nothing to gain from a special case, so it gets none.

- **Integration gate:** `DATABASE_URL` must be set or the storm-control suite

### The three layers

**Database — applies, and it is the primary evidence.** No migration, no schema
change, no seed change, so no `roles`/`migrate`/`seed` run is needed. What is
needed: (1) `DATABASE_URL` set and the storm-control suite green — where every
new `WHERE` meets real Postgres; (2) the forced `EXPLAIN`, the ADR 0057
Amendment 2 set — `SET enable_seqscan = off;` then `EXPLAIN`, expecting
`Index Scan using notification_deliveries_channel_key_idx` with the new clause as
a residual `Filter` and **no DDL**, with `enable_seqscan = off` stated for
Amendment 2's own reason (the local ledger is nearly empty); (3) ledger
correlation after the live run, `attempted_at` against
`notification_channels.updated_at` — and other sessions redeploy this stack, so
correlate on times and pin image ids rather than trusting a bare count.

**API — N/A, with the reason.** No route, no request or response schema, no
controller and no contract change; the behaviour is entirely inside the sweep's
dispatch path. There is also no cheap way to assert it at that layer: the API is
OIDC and `curl` cannot obtain a token locally, so an HTTP-layer claim would have
to be a `fetch` from an authenticated SPA tab — for a claim with no HTTP surface.

**Browser — N/A, with the reason.** No file under `apps/web` changes. The status
vocabulary, its labels and its tones are untouched, and the deliveries page
renders a new row through paths its own spec already covers. Nothing an operator
can see is *new*; what changes is which rows appear, which is the database
layer's claim. The cached-bundle trap does not apply — no web asset is rebuilt.
No `browser-verifier` dispatch.

## 8. ADR 0057 Amendment 3 — outline

Title: **Amendment 3 — `F3.50`: an unconfigured refusal stops answering once the
configuration moves (2026-09-08)**. Amends decision 10 and Amendment 2 §5; leaves
ruling Q9, rulings Q1/Q-A of Amendment 2 and the raise path untouched.

1. **What Amendment 2 §5 held out, and why it is a different fix.** A ceiling
   refusal is a self-clearing postponement, so `F3.48` could stop writing the
   row. An unconfigured channel is a configuration fault the operator must see
   and fix, so the row is the signal and it keeps being written. What changes is
   not the write but the **read**.
2. **Ruling Q1 — the watermark is `max(channel.updatedAt, PROCESS_STARTED_AT)`.**
   The owner's rationale, recorded: the corrected five-source table from C4, with
   `webhook.transport.ts:89` spanning both classes; `ChannelsService.readiness()`
   — **not** `NotificationsService.readiness`, which the backlog row misnamed —
   is computed from static per-process facts, so readiness cannot flip inside a
   process and process start is the only boundary at which a change is
   observable, which is what makes it principled rather than a hack.
   `EmailTransport` freezing `this.sender` in its constructor is the confirming
   evidence. Cost: one retry and one row per key per API restart.
3. **The exclusion is in the SQL `WHERE`, scoped to one status against a
   timestamp.** Amendment 2 §3's argument transfers verbatim — `.limit(...)` with
   no `ORDER BY`, order-independence given as the soundness reason — and here it
   is **stronger**, because the mixed state is reachable (C3). Record the
   `or(ne, gt)` form and C1's reason for it. Record that it must **not** be a
   watermark over the whole read — that would stop a `failed` row older than the
   watermark counting toward Q9's cap, resetting it on every channel edit.
4. **No DDL, measured not assumed.** The `EXPLAIN` plan from §7, with
   `enable_seqscan = off` and its stated reason.
5. **The growth bound, corrected (C3).** One fresh row per key per process,
   blocked at the next tick by `rows.some(status !== "failed")` — the count arm
   is never reached and three fresh unconfigured rows under one key is
   unreachable. A later channel write or a restart moves the watermark past them
   and releases the key again.
6. **Accepted costs and residuals.**
   (a) **Ruling Q2 / C5** — `update()` bumps `updated_at` unconditionally, so a
   rename or an enable toggle releases every stranded key on the channel; at
   ruling Q7's measured 52-alarm shape that is 52 retries in one tick, competing
   for the single hourly budget, cross-referenced to `F3.52`.
   (b) **C2** — the watermark is an API-clock value against DB-clock rows, with
   both skew directions named.
   (c) No `ON UPDATE` trigger on `notification_channels.updated_at`, so a direct
   psql edit of `config` does not release the key until the next restart; the API
   is the only supported write path.
   (d) A key holding stale unconfigured rows and fewer than three `failed` rows
   gains a real transport attempt — the same intended effect Amendment 2 §3
   recorded for `skipped_rate_limited`.
7. **Inert for `kind: "cleared"`,** and why it is said rather than special-cased.
8. **Not fixed here:** `F3.51`, `F3.52`, `F3.53`, `F3.54`, and the ledger's
   retention (`F3.46` ruling 0).
