# F2.14 — A read-only viewer for stock asset-template catalog entries

*Backlog row `docs/BACKLOG.md` (Track B, `| F2.14 |`) · P2 · Effort **1–2** · Wave 2 · Depends `F2.13` · Branch `feat/F2.14-stock-catalog-viewer`, base `main` at `b423a50`*

*Planned 2026-09-03 by `plan-architect` (Opus) from the `F2.14` row and ADR 0052 decisions 1 and 10.*

**Gates:** no ADR is owed — the owner ruled on 2026-09-03 that the row is web-only (no API, no migration, no contract, no dependency) and said "build it". ADR 0052 decision 10 already grants the web surface; decision 1 already forbids editing catalog data from the screen. **Merge approval is still owed** to the owner at step 7.

---

## 1. Goal

An administrator can read a stock catalog entry in full before deciding to import it. A **View** control beside each entry's Import button on `/admin/asset-templates` opens a new deep-linkable page, `/admin/asset-templates/stock/:code`, which renders the entry through the **same six tab components the template detail page uses** (`DetailsTab`, `PointsTab`, `CalculationsTab`, `KpisTab`, `AlarmsTab`, `DashboardsTab`) with `editable={false}`, so every field is disabled and no save control renders. A header names the entry, its stock code and its stock version, states that this is repository data that cannot be edited here, and carries an organization picker plus an Import button, so a reader who decides to take the entry does not go back to the list. No API, no migration, no contract change: `GET /admin/asset-templates/stock` already returns the whole `StockAssetTemplateDto` with `content` and `points`, and the page reuses the list response the card already fetched.

## 2. Out of scope

- **Editing a stock entry from the screen.** ADR 0052 decision 1 — the catalog is repository data. The viewer renders no writable control and posts no `PATCH`.
- **The dashboard-template stock card's twin** (`F3.36`). Its own row if wanted — see open question 3.
- **Any change to the six tab components.** Their props, their save paths and their behaviour on the authoring page are untouched (see §5.1).
- **Any change to the stock card's existing Import wiring.** `asset-templates-page.spec.tsx` is green and is this row's regression gate for "exactly as the card's does". The card gains one `<Link>` and nothing else.
- **A tier column on the Points tab.** The Points grid renders no `meta.tier` today (measured). Adding one changes the *authoring* page for every template — see open question 2.
- **A new navigation entry.** The viewer is reached from the card, not from the admin nav.
- **`GET /admin/asset-templates/stock/:code`** — a per-entry read route. The list response already carries every field; a second route would be a second source of the same bytes.

## 3. Serial or parallel

**Serial, one branch, two consecutive `implementer` passes.** Not a fan-out candidate, and the reason is the chain rather than a star: the adapter's return type gates the viewer page, the viewer's route gates the reachability guard, and all three passes touch `apps/web`. §3 permits fan-out only for 2+ genuinely independent siblings on non-overlapping files, and this row has none. The row is not ⭐.

- **Pass A** — Task 1 (the adapter and its spec). Runs to green before pass B starts.
- **Pass B** — Tasks 2–5 (the tab-body move, the viewer, the card link, the guard).

## 5. The two decisions the row hands the plan

### 5.1 Adapt the entry (option a) — not narrow the tabs (option b)

**Decision: (a). The viewer adapts a `StockAssetTemplateDto` into the `AdminAssetTemplateDto` the tabs already take, at one tested seam in `lib/`.**

The row calls (b) "the honest one". On the measured facts it is not a narrowing at all. Every one of the six tabs calls `updateAdminAssetTemplate(template.id, …)` inside its `useMutation`, and two of them call `formulaFieldsAreReadOnly(template.status)`. A prop type that carries only the content-and-points subset **does not compile in any of the six**. So (b) is really one of two much larger changes:

- a discriminated union prop — `{ editable: true; template: AdminAssetTemplateDto; onSaved } | { editable: false; template: StockTemplateView }` — rewriting the head of all six tabs plus `TemplateTabBody`, and forcing each tab to branch before it can touch `id`; or
- a read/edit component split, six new files.

Either one widens the surface of six components totalling ~1900 lines of `.tsx`, **five of which CodeGraph reports with no covering tests**, in order to serve a read-only screen — and it charges a refactor of the authoring page to a 1–2 day viewer row. (a) is one new tested `lib/` module and **no change to any tab**.

The risk (b) exists to close — a synthetic id reaching the API — is closed structurally by (a): the mutation's only trigger in each tab is a save control rendered under `{editable ? … : null}`, and the viewer passes the literal `false`. No tab fetches by id either.

**(b) becomes the right answer the day a second read-only consumer appears. This row does not create one.** Record that sentence in the adapter's docblock.

**The one trap (a) must not step in:** the synthetic `status`. `status: "draft"` would leave the Calculations and KPIs formula editors writable behind `readOnly={formulaFieldsAreReadOnly("draft")} === false`. The adapter stamps `status: "published"` and its spec asserts the property, not the literal.

### 5.2 A route, not an in-page panel

**Decision: a route, `/admin/asset-templates/stock/:code`.**

- It is deep-linkable and shareable, which is what a catalog reference wants to be.
- It mirrors the detail page, so the tab strip's `?tab=` state comes free from `useSearchParams` + `resolveTemplateTab`. An in-page panel would either duplicate that state machine or lose the reader's tab on close.
- The card stays a summary, which is what it is good at.

**The ordering rule, and it is load-bearing:** declare the stock route **before** `/admin/asset-templates/:templateId/versions` in `app.tsx`. Both are four segments with one static and one dynamic part, so a URL matching both resolves by declaration order. The only URL that reaches the ambiguity is a stock code literally named `versions`, which the catalog does not contain — but the ordering is free and the controller already carries the same rule one layer up (`@Get("stock")` before `@Get(":id")`), so write it down rather than rely on the coincidence.

**For the reviewer who will find it:** a bare `/admin/asset-templates/stock` matches `:templateId`, the detail page fetches the id `"stock"`, and the API's `idParamSchema` (uuid) answers 400. That is the behaviour every non-uuid segment already has today. Known, unchanged, out of scope.

**On validating `:code`:** the lookup *is* the validation. The entry is either present in the already-fetched list response or it is not; an absent code renders a not-found panel. `stockCodeParamSchema` lives in `apps/api` and cannot be imported here, and a re-spelled regex would buy nothing — the code is never interpolated into a request and never rendered unescaped. **The load-bearing rule instead: Import sends the resolved `entry.code`, never the raw URL parameter.**

### 5.3 DRY, considered and rejected once

Do **not** extract the card's import wiring into a shared component or hook. The card's organization `<select>` lives in the `SectionCard` `actions` slot for the whole list while its Import buttons are per row, so no single component fits both layouts; and the detail-path literal is already inline in 5 places, so a path helper is a repo-wide refactor this row does not own. The shared units that must not drift already exist: the client function `importAdminStockAssetTemplate` and the destination `/admin/asset-templates/${created.id}`. Both call sites use both, and both specs assert the same navigation target. Touching the card's mutation would also spend this row's own regression gate.

## 6. Tasks, in build order — tests first

### Task 1 — The adapter: `stock-template-view.ts` · **model: Fable 5.1**

*Why Fable:* §2's ladder — *"the unit defines a seam other work hangs off"*. This module fixes the shape every future stock pack (`E5.1` water, `E5.2` mechanical, `E5.3` facility) hands the six tabs, and it carries the `status` trap in §5.1 where a wrong constant is invisible to the compiler and to the feeder fixture alike.

**Test first.** New `apps/web/src/lib/stock-template-view.spec.ts` with wrapper `stock-template-view.test.ts` (**no** `@vitest-environment jsdom` — this is pure logic and wants the default node environment). Assertions:

1. `capabilities(stockEntryAsTemplate(entry).status).editable` is `false`, **and** `formulaFieldsAreReadOnly(stockEntryAsTemplate(entry).status)` is `true`. Derived, never `expect(view.status).toBe("published")` — a literal assertion re-states the bug it is meant to catch. The failure message names the consequence: *"the Calculations and KPIs formula editors render writable in the read-only viewer."*
2. `adminAssetTemplateDtoSchema.parse(stockEntryAsTemplate(entry))` does not throw. This catches a runtime-shape mistake the `: AdminAssetTemplateDto` annotation cannot, and it fails loudly the day the DTO gains a field.
3. Content and points survive **by value**: `view.content` deep-equals `entry.content`; `view.points.length === entry.points.length`; `view.points[i].pointKey` / `formula` / `kind` / `required` / `sortOrder` match position for position.
4. The `meta` bridge, both branches: a point with `meta: { tier: "extended" }` becomes `meta: { tier: "extended" }`; a point with `meta` **absent** becomes `meta: null`, and `pointRowsFrom` over the result yields `meta: null` rather than throwing.
5. `description: null` survives as `null` (not `""`).
6. `view.id === STOCK_VIEW_TEMPLATE_ID`, and that constant is **not** a uuid — assert against the same `/^[0-9a-f]{8}-/i` shape the API's `idParamSchema` accepts, so a future "tidy-up" that makes it look like a real id fails here.
7. `view.version === 0`. The comment and the message say why: a catalog entry is not a row and has no row version; conflating it with `stockVersion` is exactly what ADR 0052's two-stamps-two-reasons note forbids. `stockVersion` carries the real number.
8. `findStockEntry(items, "electrical-feeder")` returns that entry; `findStockEntry(items, "nope")` returns `undefined`; `findStockEntry([], anything)` returns `undefined`.

**Then build.** New `apps/web/src/lib/stock-template-view.ts`, exporting:

- `export const STOCK_VIEW_TEMPLATE_ID = "stock-catalog-entry";` — a sentinel, deliberately not a uuid.
- `export function stockEntryAsTemplate(entry: StockAssetTemplateDto): AdminAssetTemplateDto` — `id: STOCK_VIEW_TEMPLATE_ID`, `status: "published"`, `version: 0`, `organizationId`/`organizationCode`/`organizationName` empty strings, `publishedAt`/`archivedAt` `null`, `createdAt`/`updatedAt` a fixed `new Date(0).toISOString()`, `stockCode: entry.code`, `stockVersion: entry.stockVersion`, `code`/`name`/`assetType`/`domain`/`description`/`content` straight through, and points mapped with `id: `stock:${entry.code}:${point.pointKey}``, `templateId: STOCK_VIEW_TEMPLATE_ID`, `createdAt` the same fixed epoch, `meta: point.meta ?? null`.
- `export function findStockEntry(items, code)`.

The docblock records: which five fields the tabs actually read (§4's row), why `status` is `published` and not `draft`, why the id is not a uuid, and the sentence from §5.1 about when (b) becomes right.

**Acceptance:** `pnpm --filter web test` green; `pnpm test:coverage` shows no threshold regression — this file is inside the coverage denominator (`apps/web/src/lib/**/*.ts`) and every branch above is exercised, so it must not dilute the four numbers. §4.6 forbids lowering a threshold to compensate.

### Task 3 — The viewer page and its route · **model: Opus**

*Why Opus:* the ladder names it — *"a page with its jsdom spec"*. There is judgment in the header, the not-found and pending branches, and the stable no-op callbacks.

**No `.github/workflows/ci.yml` change is needed, and this is why:** CI already runs `pnpm typecheck:tests` and `pnpm test:coverage`, and the root vitest `repo` project globs `tests/**/*.test.ts`, so the new file both runs and type-checks once it is listed. §4.6's *"wire it into ci.yml in the same change"* is satisfied by the existing wiring — stated here so it does not read as unmet.
