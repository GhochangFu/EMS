# F4.5 — plan: isolated integration databases with testcontainers (ADR 0124, Proposed)

Written 2026-11-10 against `main` at `0bc360c3`, by the agent that drafted
[ADR 0124](../adr/0124-testcontainers-integration-tests.md). **Status: plan
only. ADR 0124 is Proposed; its nine open questions were answered on
2026-11-10, each with the recommended option (ADR 0124 *Rulings*), so no unit
below changes. The build still waits for the owner to accept the ADR and say
"yes" to this plan.** No figure here was measured: the drafting
session had no Docker daemon, so PR 1 is a measured spike before anything
moves.

> **For agentic workers:** REQUIRED SUB-SKILL: use `superpowers:executing-plans`
> (or this repo's `backlog-cycle` mode `start`) to run it unit by unit. Units
> marked ⭐ are serial and hands-on — never fanned out to an `implementer`.

**Goal.** Every integration suite runs on a database and a Redis index no
concurrently running file can touch, prepared once per run from the same
`roles → migrate → seed` CI uses, without changing what any suite asserts or
the coverage denominator.

**Architecture.** A root `globalSetup` picks a mode (containers / external /
skip / refuse), starts one TimescaleDB and one Redis container through
`testcontainers` (or uses the external server), builds `bms_template`, and
`provide`s the server URLs. A root `setupFiles` entry, run in the worker before
each test file imports, copies `bms_w<VITEST_POOL_ID>` from the template once per
worker and sets `DATABASE_URL`, `DATABASE_URL_SUPERUSER`, `_FLEET`, `_AUTH`,
`_TENANT` and `REDIS_URL` for that worker. Files still on the
`NOT_YET_ISOLATED` ratchet get the single shared copy `bms_shared`.

**Tech stack.** Vitest 4.1 (`globalSetup`, `setupFiles`, `provide`/`inject`),
`testcontainers` 12.2.1 (`GenericContainer`), `pg`, the existing
`@bms/db` CLIs spawned with `tsx`.

## 1. Facts measured from the tree (`0bc360c3`)

- **318 integration files**: 255 `apps/api`, 2 `apps/ingest`, 61 `tests/`.
  `requireIntegrationDb` is used in 327 files; 185 integration files also read
  `process.env.DATABASE_URL` directly (so the env must be set **before** a file
  imports — `setupFiles`, not `beforeAll`).
- **8 files touch Redis** (`requireIntegrationRedis` / `REDIS_URL`): the two
  `queue.integration.*`, two `*.backfill.integration.test.ts` under
  `admin/asset-points`, and the gate's own spec/test.
- **13 files need MinIO, Mosquitto or Keycloak.** Those stay on CI's `docker
  run` steps; F4.5 does not containerise them.
- `resolveIntegrationRoleUrl` swaps user and password only, so a per-worker
  database name carries to every role URL. Two files name `localhost:5432/bms`,
  both in comments; none reads `current_database()` against a literal.
- Root `vitest.config.ts`: `maxWorkers: 2` (`F4.71`), projects `api`, `web`,
  `ingest`, `shared`, `db`, `repo`. No `globalSetup` and no `setupFiles` at the
  root today (only `apps/web` has a setup file).
- CI `build-and-migrate`: `services:` Timescale `2.29.1-pg16` and
  `redis:7-alpine`; steps init schemas → `db:roles` → `db:migrate` → `db:seed`
  → one `telemetry.point_values` row → `db:refresh-aggregates` → Keycloak
  provision → MinIO → Mosquitto → `pnpm test:coverage`. `docs-only-tests` runs
  `--project repo --exclude "**/*.integration.test.ts"` and is untouched.
- `docker-compose.yml` runs Postgres with `-c max_worker_processes=24` (ADR
  0024) and Redis with `--appendonly yes --maxmemory-policy noeviction`.
- `testcontainers` 12.2.1: `engines.node >= 22.22`; repo requires
  `>= 24.22.1`.
