# F4.5 — plan: isolated integration databases with testcontainers (ADR 0124, Accepted)

Written 2026-11-10 against `main` at `0bc360c3`, by the agent that drafted
[ADR 0124](../adr/0124-testcontainers-integration-tests.md). **Status: approved
2026-11-10.** ADR 0124 was accepted and the owner said "yes" to this plan in
the same message; its nine open questions were answered earlier that day, each
with the recommended option (ADR 0124 *Rulings*), so no unit below changes.
The build starts at U1, which needs a machine with Docker. No figure here was measured: the drafting
session had no Docker daemon, so PR 1 is a measured spike before anything
moves.

> **For agentic workers:** REQUIRED SUB-SKILL: use `superpowers:executing-plans`
> (or this repo's `backlog-cycle` mode `start`) to run it unit by unit. Units
> marked ⭐ are serial and hands-on — never fanned out to an `implementer`.

**Goal.** Every integration suite runs on a database and a Redis index no
concurrently running file can touch, prepared once per run from the same
`roles → migrate → seed` CI uses, without changing what any suite asserts or
the coverage denominator.

**Architecture.** A root `globalSetup` picks a mode (containers / external /
skip / refuse), starts one TimescaleDB and one Redis container through
`testcontainers` (or uses the external server), builds `bms_template`, and
`provide`s the server URLs. A root `setupFiles` entry, run in the worker before
each test file imports, copies `bms_w<VITEST_POOL_ID>` from the template once per
worker and sets `DATABASE_URL`, `DATABASE_URL_SUPERUSER`, `_FLEET`, `_AUTH`,
`_TENANT` and `REDIS_URL` for that worker. Files still on the
`NOT_YET_ISOLATED` ratchet get the single shared copy `bms_shared`.

**Tech stack.** Vitest 4.1 (`globalSetup`, `setupFiles`, `provide`/`inject`),
`testcontainers` 12.2.1 (`GenericContainer`), `pg`, the existing
`@bms/db` CLIs spawned with `tsx`.
