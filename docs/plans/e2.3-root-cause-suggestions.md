## 1. Goal

When a user opens an alarm's details panel, a new section, **"Possible causes — advisory"**, shows at most three candidate causes. A pure function, `rankRootCauseCandidates`, makes them from rows already in the database: maintenance windows, RTU communication alarms, other alarms raised shortly before, root causes operators recorded on earlier alarms of the same rule and asset, and the class philosophy. One context line may say the asset's readings were unusual in the 6 h before; it has zero weight. A new route, `GET /api/v1/alarms/:id/root-cause-suggestions`, computes this at read time. An operator may press **"Use as root cause"** to put a candidate's text into the enrichment form's root-cause field; nothing is written until the operator submits the form through the existing `PUT /alarms/:id/enrichment`.

**Out of scope** (ADR decision 11; named so nobody builds it):
- Any LLM call, prompt, provider or copilot tool. Any stored suggestion, feedback or accuracy figure.
- A table, a migration, an index, a grant, a role, an environment variable, a dependency, a process, a queue, Python code.
- Anomaly scores with weight. A new or changed threshold (`ANOMALY_UNUSUAL_SCORE` is imported, never restated).
- Suggestions on the alarm list, the rail, a notification, a work order, a report, an export or a copilot answer.
- Filling any field but `root_cause`; filling without the operator's click; a button on R5; a button for a `viewer`.
- Any change to `WizardShell`, `AlarmsController`, `AlarmDetailsService`, `ml-anomalies.*`, `device-health.*` or `maintenance-cover.*`.

## 3. Refinements (each is a call inside the ADR; veto at skim)

- **R-a — the route reuses `AlarmDetailsService.get` as its gate and as R5's source.** The 404, the scope rule and the class-philosophy join (with ADR 0059 decision 9's organization predicate) then exist once. Cost: `get`'s own reads run a second time per panel open.
- **R-b — a separate controller file.** `alarm-root-cause.controller.ts` with `@Controller("alarms")`, registered in `alarms.module.ts`. `AlarmsController` and its three hand constructions are not touched.
- **R-c — one candidate per rule row, not per database row.** R1, R2, R3, R3b and R5 give at most one candidate each, with up to 5 evidence items. R4 gives one candidate per distinct text. So three linked alarms do not fill all three places.
- **R-d — R1 counts asset and location targets only.** A window that targets only the alarm's rule did not "cover the asset" (the ADR's words).
- **R-e — R3 looks at `rule` alarms only, and never at a re-raise of the same rule on the same asset** (that is R4's population). "Same location" is the same `location_id`, not the subtree. An `rtu_comms` alarm on the asset's RTU is R2's evidence and is never also R3.
- **R-f — "before" includes the same instant** (`raised_at <= T`), because one rule sweep stamps several alarms with one `now()`. R4 is strictly earlier (`< T`).
- **R-g — the anomaly window is the six whole UTC hours that ended at or before the alarm's hour began:** `[floorHour(T) − 6 h, floorHour(T))`. The hour that holds the alarm is scored after it and partly covers minutes after it.
- **R-h — `rankRootCauseCandidates` cannot see anomaly rows.** Its input type has no anomaly member. A second pure function builds the context line. Q3's guarantee is then held by the type, by a unit test and by an integration test.
- **R-i — the wire carries no user.** No `updatedBy`, name or e-mail. No maintenance-window `reason` (free text by an admin, not in the ADR's list of quoted text).
- **R-j — the Advisory pill is the Anomalies page's** (`StatusPill label="Advisory" tone="info"`); every other element of the section uses the ink and neutral roles. A severity can carry the `info` tone (it is a column of `bms.alarm_severities`); say so if the pill should be plain ink instead.
- **R-k — the "ask before replacing" is an inline `role="alertdialog"` inside the wizard**, as `WizardShell`'s leave prompt is, not `window.confirm`. The wizard is the only place that knows the field's current text.
- **R-l — a fill marks the wizard changed** (`dirty`), so Cancel asks before it throws the text away.
- **R-m — links:** the anomaly context line links to the asset history page for its window; an R5 candidate links to `/alarm-kb`. Nothing else links (2.2).
- **R-n — a module-wiring spec for the two new classes.** CI does not boot the API and a merge deploys by itself, so a DI mistake would be found on the demo host.

## 4. The rules, exactly

`S` is the subject alarm; `T = S.raised_at`. `S` has `source = 'rule'`, an asset, its organization, a `rule_id` (may be null), and the asset's `rtu_id` (may be null) and `location_id`. All evidence rows belong to `S`'s organization.

| # | Rule id (wire) | Evidence | Strength | Title | Recency |
|---|---|---|---|---|---|
| R1 | `maintenance` | windows with `starts_at <= T` and `COALESCE(ended_at, ends_at) > T − 60 min` whose asset target is the asset, or whose location target is the asset's location or an ancestor (`windowCovers` with `ruleId: null`) | strong | `Maintenance on this asset` | `min(effective end, T)` |
| R2 | `rtu_comms` | `rtu_comms` alarms with `rtu_id` = the asset's RTU, `T − 60 min <= raised_at <= T` (pending Q1). None when the asset has no RTU | strong | `Communication or power loss at RTU <asset RTU display name>` | newest `raised_at` |
| R3 | `linked_alarm` | other `rule` alarms, `T − 30 min <= raised_at <= T`, on the same asset, or on an asset with the same non-null `rtu_id` | moderate | `Linked to "<message of the newest>"` | newest `raised_at` |
| R3b | `linked_alarm_location` | the same, on an asset with the same `location_id` and neither relation above | weak | as R3 | newest `raised_at` |
| R4 | `recorded_before` | alarms with the same `rule_id` and `asset_id`, `T − 180 d <= raised_at < T`, whose enrichment has a non-blank `root_cause`. Grouped by `root_cause.trim().toLowerCase()`. None when `rule_id` is null | moderate at 2 or more, weak at 1 | `Recorded before`; `quote` = the newest row's trimmed text; `occurrences` = the count | newest `raised_at` in the group |
| R5 | `class_cause` | `details.classPhilosophy.cause` is not null | weak | `Class cause`; `quote` = the cause | none |

- **Order:** strength (strong, moderate, weak); then recency, newest first, an undated candidate last; then the table's order; then for two R4 groups, more occurrences first, then `quote` ascending. **Cap:** the first 3 (`ROOT_CAUSE_MAX_CANDIDATES`).
- **Row caps in SQL:** R1 50 windows; R2 and R3 20 rows each; R4 50 rows. Evidence items per candidate: 5, newest first. An alarm message in a title or label is cut at 200 characters with `…`. A `quote` is never cut.
- **No candidate:** `candidates: []`. The web says "No likely cause found in the data."
- **Context (zero weight):** anomaly rows of the asset in R-g's window, newest run per hour and detector (`readAssetAnomalies` does that), kept when `score >= ANOMALY_UNUSUAL_SCORE`. One or more kept rows give one context item: the window, the count of distinct unusual hours, the distinct detectors (sorted), the distinct contributing points (sorted, first 5). None gives `context: []`.
- **A device alarm** (no asset): `candidates: []`, `context: []`, no evidence read (pending Q4).

**Contract — `packages/shared/src/contracts/alarm-root-cause.ts`:**

```ts
export const ROOT_CAUSE_MAX_CANDIDATES = 3;
export const ROOT_CAUSE_ANOMALY_LOOKBACK_HOURS = 6;
export const ROOT_CAUSE_RULES = ["maintenance", "rtu_comms", "linked_alarm", "linked_alarm_location", "recorded_before", "class_cause"] as const;
export const ROOT_CAUSE_STRENGTHS = ["strong", "moderate", "weak"] as const;
export const ROOT_CAUSE_EVIDENCE_KINDS = ["maintenance_window", "rtu_comms_alarm", "alarm", "enrichment", "class_philosophy"] as const;

rootCauseEvidenceSchema = z.object({
  kind, at: iso.nullable(), endedAt: iso.nullable(),
  alarmId: z.string().uuid().nullable(), assetId: z.string().uuid().nullable(),
  assetCode: z.string().nullable(), assetRtuName: z.string().nullable(), assetLocationName: z.string().nullable(), // ADR 0111
  label: z.string().max(300).nullable(),
});
rootCauseCandidateSchema = z.object({
  rule, strength, title: z.string().max(300), quote: z.string().nullable(),
  occurrences: z.number().int().min(1).nullable(), evidence: z.array(rootCauseEvidenceSchema).max(5),
});
rootCauseContextSchema = z.object({
  kind: z.literal("anomaly"), from: iso, to: iso, unusualHours: z.number().int().min(1),
  detectors: z.array(z.string().max(64)), contributingPoints: z.array(z.string().max(128)),
});
alarmRootCauseSuggestionsResponseSchema = z.object({
  computedAt: iso, candidates: z.array(rootCauseCandidateSchema).max(ROOT_CAUSE_MAX_CANDIDATES), context: z.array(rootCauseContextSchema),
});
```

**Encoding (§4.8 / ADR 0030), named so a reviewer checks it:** every schema is one plain `z.object`. There is no intersection and no all-readonly object, so neither `z.intersection` nor `.readonly()` applies, and none is flattened from two parts. None is `.strict()` (responses). `rule`, `strength` and the evidence `kind` are `z.enum` (the web switches on them, and strength must be a closed set of words); `detectors` are bounded strings, as `ml-anomalies.ts` has them. Types are `z.infer`, exported from this file. One `export * from "./alarm-root-cause";` line in `contracts/index.ts`. `packages/shared/src/index.ts` is not touched. **There is no number or percentage for strength anywhere in the schema.**

Evidence fields by kind: `maintenance_window` (`at` = start, `endedAt` = effective end); `rtu_comms_alarm` (`at`, `endedAt` = `cleared_at`, `alarmId`, `label` = message); `alarm` (`at`, `alarmId`, `assetId`, the three ADR 0111 label fields, `label` = message); `enrichment` (`at` = that alarm's `raised_at`, `alarmId`); `class_philosophy` (`label` = `<templateName> v<templateVersion>`). Every other field is null.

- no evidence → `[]`;

```sql
SELECT w.id AS id, (extract(epoch FROM w.starts_at) * 1000)::float8 AS starts_ms,
       (extract(epoch FROM COALESCE(w.ended_at, w.ends_at)) * 1000)::float8 AS end_ms,
       t.asset_id AS asset_id, t.location_id AS location_id
  FROM bms.maintenance_windows w
  JOIN bms.maintenance_window_targets t ON t.window_id = w.id AND t.organization_id = $org
 WHERE w.organization_id = $org
   AND w.starts_at <= $raised
   AND COALESCE(w.ended_at, w.ends_at) > $raised - interval '60 minutes'
   AND (t.asset_id = $asset OR t.location_id IS NOT NULL)
 ORDER BY w.starts_at DESC, w.id
 LIMIT 50
```

```sql
SELECT q.* FROM (
  SELECT al.id AS id, al.source AS source, al.asset_id AS asset_id, al.rule_id AS rule_id, al.message AS message,
         (extract(epoch FROM al.raised_at) * 1000)::float8 AS raised_ms,
         (extract(epoch FROM al.cleared_at) * 1000)::float8 AS cleared_ms,
         x.code AS asset_code, x.rtu_id AS asset_rtu_id, x.location_id AS asset_location_id,
         r.display_name AS asset_rtu_name, l.name AS asset_location_name,
         row_number() OVER (PARTITION BY al.source ORDER BY al.raised_at DESC, al.id DESC) AS rn
    FROM bms.alarms al
    LEFT JOIN bms.assets x ON x.id = al.asset_id AND x.organization_id = $org
    LEFT JOIN bms.rtus r ON r.id = x.rtu_id AND r.organization_id = $org
    LEFT JOIN bms.locations l ON l.id = x.location_id AND l.organization_id = $org
   WHERE al.organization_id = $org
     AND al.id <> $alarm
     AND al.raised_at >= $raised - interval '60 minutes' AND al.raised_at <= $raised
     AND (   (al.source = 'rtu_comms' AND al.rtu_id = $rtu)
          OR (al.source = 'rule' AND al.raised_at >= $raised - interval '30 minutes'
              AND (al.asset_id = $asset OR x.rtu_id = $rtu OR x.location_id = $location)))
) q
WHERE q.rn <= 20
ORDER BY q.raised_ms DESC, q.id DESC
```

## 17. Questions only the owner can rule (each has a recommended answer)

1. **R2's evidence (needed before PR 1).** The ADR's R2 says the RTU "dropped or went silent", from `readRecentDrops` and `stateOf`. In the code a "drop" is a refused sample (bad quality, out of range, unmapped key…), counted per hour, and `stateOf` knows only the present (2.2). The one stored record of silence is an `rtu_comms` alarm.
   - (a) R2 is an `rtu_comms` alarm on the asset's RTU raised in the 60 min before. Nothing else.
   - (b) (a), plus the RTU reading Offline now with its last-seen time inside the 60 min. Two more reads on every panel open, one over telemetry cadence, and it judges "now", which is wrong for an old alarm.
   - (c) (a), plus refused-sample hours shown as an extra evidence line on an R2 that already exists.
   - (d) The ADR's words: any refused-sample hour makes R2 strong. This would call a data-quality refusal "communication or power loss", which decision 2's "nothing is invented" forbids.
   **Recommended: (a).** Consequence: an RTU the ingest host does not monitor (a simulator RTU, an edge-served RTU) never gives R2.
2. **Which pool reads the evidence (needed before PR 1).** ADR decision 5 says `FLEET_DRIZZLE` with a hand-written organization predicate. AGENTS.md §4.3 says a tenant-table read defaults to `withTenant`, and that a `fleetDb` read needs a reason other than "an earlier item did it". Here the alarm's organization is known before any evidence read. **Recommended:** the evidence reads run in one `withTenant` transaction on `bms_tenant`, **and** keep every hand-written predicate. Row security is then the backstop and the predicate the second control; the anomaly read shares that transaction (it is the same organization `withReadScope([assetId])` would resolve to). The gate read stays `AlarmDetailsService.get` on the fleet pool, as today. No grant changes. If you rule the ADR's words instead, the four `bms` reads run on the fleet pool and the call site records ADR 0136 decision 5 as its reason.
3. **No index serves R3 (needed before PR 1).** Decision 5 says "served by existing indexes"; `bms.alarms` has none for a cleared alarm by time, asset or RTU. Measured: about 10 ms per 100,000 alarm rows for the scan, 147 ms at one million on one thread (2.3). Decision 4 allows no migration.
   - (a) Ship without an index. Stop rule: if the demo-host p95 (section 15, check 4) is over 150 ms, the build stops for your ruling.
   - (b) Amend the ADR now to allow one index on `bms.alarms (organization_id, raised_at)`: one more PR, a migration, `migration-reviewer`, and the `ml` CI job.
   **Recommended: (a)**, sized by check 1 of section 15. Under about 300,000 alarm rows the scan is well inside the budget.
4. **A device alarm (needed before PR 1).** Decision 5 says the caller's scope "must hold the alarm's asset", and also "exactly as `AlarmDetailsService.get` answers today". `get` admits a visible `rtu_comms` or `ingest_host` alarm, which has no asset. **Recommended:** the same visibility as `/details` (a 404 only when `/details` is a 404); a visible device alarm answers 200 with no candidate and no context; the panel does not draw the section for it, as it already draws no asset block and no form.
