## 1. Goal

Materialise every view of an asset template's `content.dashboards` into
`bms.dashboards` / `bms.dashboard_widgets` / `bms.dashboard_widget_points` rows
scoped to one asset, at two triggers: inside
`AssetTemplateInstantiationService.instantiate`'s existing `withTenant`
transaction (after the rule seed), and on demand through
`POST /admin/asset-templates/:id/default-dashboards` for every asset already
pinned to any version of that template code, skipping assets that already carry
a stamped default. `bms.dashboards` gains `asset_id` (cascade) and
`asset_template_id` (no cascade), a three-way scope check, two stamp checks and a
re-created `tenant_isolation` policy (migration `0073`). The asset scope becomes a
fourth arm in the two bodies, the two DTOs, `canManageDashboard` and
`DashboardsService.update`. All 27 stock asset-template entries gain one
`overview` view. The web gets an Asset scope badge, a *Create default dashboards*
action with its report, and `dashboardCount` in the instantiate result.

**Out of scope** (ADR 0067 decision 8 and decision 7's declines): version drift /
upgrade of stamped dashboards; deleting defaults on re-pin or archive; assets with
`template_id IS NULL`; an asset picker in the builder (`dashboard-scope-fields.tsx`
untouched); narrowing read visibility; a binding restriction on asset-scoped
dashboards; the dark canvas; `dashboard_widget_sources` rows; `templateId` on the
DTO (absent today, stays absent — §12 Q8); any edit to `AGENTS.md`,
`docs/roadmap.md` or `docs/BACKLOG.md` status before closure.

## 4. Design decisions

**D1 — Two new modules beside the ADR 0049 service, pure/impure split as
`template-alarm-rules.ts` / instantiate service.**
`apps/api/src/admin/asset-templates/asset-dashboards-plan.ts` (pure: slug, name,
tile lattice, per-view plan and report, batch bound) and
`asset-dashboards-instantiate.service.ts` (DB: writes and the backfill). The pure
half is provable against every input the content contract permits; the service
stays well under the cap.

**D2 — Slug.** `dashboardSlug(assetCode, viewName)`: each part lower-cased,
`[^a-z0-9]+` → `-`, leading/trailing `-` stripped; joined with `-`; if
`length <= 64` return `padEnd(2, "-")`; else `${joined.slice(0, 55)}-${sha256(joined).hex.slice(0, 8)}`
(55 + 1 + 8 = 64; hash over the untruncated join; lowercase hex is already in
`[a-z0-9-]`). Slicing an ASCII-only string never splits a surrogate — the
class filter has already removed every non-ASCII code point. Collision → the
409 (D6).

**D3 — Name.** `` `${asset.name} · ${viewName}` `` cut to 255 **code points**
(`Array.from(s).slice(0, 255).join("")` — `varchar(255)` counts characters and
`String.prototype.slice` splits surrogates; memory).

**D4 — Plan per view (`planView(viewName, view, pointIdByKey)`).** If
`view.widgets` is present and non-empty: one planned widget per template widget,
`title`/grid/`widgetType`/`config` verbatim, `pointRole = widgetType === "chart" ? "series" : "primary"`,
points = the keys that resolve, in key order. Else the featured fallback: tile
`i` at `gridX = (i % 4) * 3`, `gridY = Math.floor(i / 4) * 2`, `gridW 3`,
`gridH 2`, `widgetType "value_tile"`, `config {}`, `title = pointKey`, for
`i < min(featured.length, MAX_DASHBOARD_WIDGETS)`; `omittedFeatured = max(0, featured.length - 40)`.
Per-widget resolution: `widgetKey = \`${viewName}#${index}\``,
`assetRoleCodes: []`, `matchedMembers: 1`, `boundPoints`, outcome `bound` when
every key resolved, `partial` when some did, `unresolved` when none did (a widget
never has more candidates than keys, so `truncated` cannot arise per widget for
one asset; the view-level cut is `omittedFeatured` — §12 Q3). Grid numbers come
from `DASHBOARD_GRID` (`tests/f3.1d-grid-bounds-single-source.test.ts` scans this
file; `3` and `2` are not banned literals, but write them as named constants
`TILE_W = 3`, `TILE_H = 2`, `TILES_PER_ROW = DASHBOARD_GRID.columns / TILE_W`).

**D5 — Points.** Loaded once per call on the **transaction**, active rows only,
keyed `${assetId}::${pointKey}`, filtered to the assets in hand (`inArray`) and
`eq(assetPoints.organizationId, org)` — the explicit organization predicate the
`dashboard-point-scope.ts` lesson requires even on `tx`.

**D6 — Write.** Inside the caller's `tx`: per view, insert the `dashboards` row
(`organizationId`, `assetId`, `assetTemplateId: template.id`, `slug`, `name`,
`locationId/assetGroupId/templateId` NULL), then one `dashboardWidgets` insert per
planned widget with `.returning()`, then one `dashboardWidgetPoints` insert per
widget with rows. `widgetCount` and `boundPoints` in the report are **counted
from the inserted rows**, not from the plan (the F3.36 "report grades its own
work" lesson). A `23505` on `dashboards_organization_slug_key` becomes the ADR
0049 409 naming the slug; the whole transaction rolls back (both triggers).

**D7 — Hook (≤ 30 lines in the 952-line file).** Rename `parseTemplateAlarms` →
`parseTemplateContent`, returning the parsed `TemplateContentParsed`; the call
site reads `.alarms ?? []` and `.dashboards ?? {}`. After the rule insert
(`:370`) and before the audit write: `const dashboardsByCode = await this.assetDashboards.instantiateForAssets(tx, template, views, plans.map(p => ({ id, code, name })))`;
`dashboardCount` joins the audit payload and the `withTenant` return; the
per-asset DTO gains `dashboards: created.dashboardsByCode.get(code) ?? []`
(the same "unreachable `??`" argument as `seededRules`); the result gains
`dashboardCount`. `assertBatchFits` gains a fourth argument
`dashboardWidgetCount = dashboardWidgetRowsFor(views)` and calls
`assertDashboardBatchFits(assetCount, dashboardWidgetCount)` from the pure module
(`MAX_DASHBOARD_WIDGET_ROWS = 8_000`, the `MAX_POINT_ROWS` figure; the docblock
says it bounds transaction size, not bind parameters — D6 inserts per widget).

**D8 — Backfill (`backfill(jwt, templateId)`).** `fetchTemplate` on `fleetDb`;
`this.templates.assertCanAuthor(jwt, org)` **before** any status read; status
`!== "published"` → `ConflictException(draftRequiredMessage(status, "instantiated"))`
— check `TemplateDraftRequiredVerb`'s union in
`packages/shared/src/contracts/template-lifecycle.ts` for the exact verb value
and reuse `AssetTemplateInstantiationService`'s 409 sentence if the verb does not
exist; do not invent a verb. Version set: copy the six-line
`versionIds` query (`asset-templates-seeded-rules.service.ts:349-358`); do not
reach into that service. Assets: `SELECT id, code, name FROM assets WHERE organization_id = ? AND template_id IN (versionIds) AND active = true ORDER BY code`
(§12 Q4). Skip set: `SELECT DISTINCT asset_id FROM dashboards WHERE asset_template_id IN (versionIds) AND asset_id IN (assetIds)`.
The rest instantiate from `:id` in one `withTenant(org)` with one audit row
(`master.dashboard.backfill`, entity `asset_template`, payload
`{ templateCode, templateVersion, createdCount, skippedCount, assetIds }`).
Response per ADR decision 5.

**D9 — Access control asset arm.** `resolveScopeTarget` takes
`{ locationId, assetGroupId, assetId }`; returns `{kind:"asset", id}` when only
`assetId` is set, `invalid` when two or more are set, throws on all-null as
today. `admin` / `organization_admin` unchanged. `location_admin`: asset row
read on `fleetDb` (`id, organizationId, locationId`) — refuse when missing or
`organizationId !== organizationId`; then `canManageLocation(jwt, asset.locationId)`.
`asset_group_admin`: same asset-belongs check, then one query
`asset_group_members ⨝ user_asset_group_access ⨝ asset_groups` with
`eq(members.assetId, id) AND eq(access.userId, user.id) AND eq(groups.organizationId, organizationId)`
`LIMIT 1`. New private `assetBelongsToOrganization` returns the row (not a
boolean) so the location arm reads `location_id` from the same read.

**D10 — Contracts.** New file `packages/shared/src/contracts/asset-dashboards.ts`
(`admin.ts` is 950 lines): `instantiatedDashboardDtoSchema`
(`{ slug, view, widgetCount, boundPoints, omittedFeatured, resolutions: z.array(templateWidgetResolutionDtoSchema) }`,
`.readonly()` — a report nothing mutates, the `templateWidgetResolutionDtoSchema`
precedent), `defaultDashboardsBackfillOutcomeSchema = z.enum(["created", "skipped_existing"])`,
`defaultDashboardsBackfillAssetDtoSchema`, `defaultDashboardsBackfillResultDtoSchema`
(plain `z.object`; arrays inside). `admin.ts`: `instantiatedAssetDtoSchema` gains
`dashboards: z.array(instantiatedDashboardDtoSchema)`;
`assetInstantiationResultDtoSchema` gains `dashboardCount: z.number().int()`.
`dashboard-builder.ts`: both DTOs gain `assetId: z.string().uuid().nullable()`
and `assetTemplateId: z.string().uuid().nullable()` inline (they are plain
objects on purpose — the file docblock records why they are not derived). **No
`.merge()`, no `.omit().extend()`, no `z.intersection` needed** — nothing here is
`A & B`. `tests/adr-0030-contract-derivation.test.ts` scans the whole directory;
`tests/f3.1a-dashboard-schema.test.ts:376-380` scans `dashboard-builder.ts`.
Import direction: `asset-dashboards.ts` → `dashboard-templates.ts`;
`admin.ts` → `asset-dashboards.ts`; no cycle (`dashboard-templates.ts` imports
only `operations`, `template-lifecycle`, `dashboard-builder`).

**D11 — Web.** Badge: `dashboard.assetId ? "Asset" : …` first in the chain
(§12 Q1 decides whether the code follows). Detail page: a `Create default
dashboards` button beside the lifecycle actions, shown when
`template.status === "published" && mayAuthor` (`assertCanAuthor` excludes
`location_admin`; `canAuthorTemplates` is the client mirror), `useMutation` →
`createDefaultDashboardsFromAdminAssetTemplate(id)`, result rendered as a small
table (asset code · outcome · per-view `slug`, `widgetCount/boundPoints`) with a
summary line. Instantiate dialog: on success keep the dialog open, render the
summary line and a *Close* button instead of `onClose()`. Both summary sentences
come from `apps/web/src/lib/default-dashboards-report.ts` (pure, spec'd):
`instantiationSummary(result)` → `"Built 2 assets · 8 points · 3 rules · 2 dashboards"`;
`backfillSummary(result)` → `"Created dashboards for 5 assets · 3 already had one"`.

## 12. Open questions for the owner before line one, each with a recommendation

1. **Asset code on the badge.** Decision 7 says "with the asset code"; decision 2
   adds only `assetId`/`assetTemplateId` "and nothing else". The summary DTO has
   no code. *Recommend:* add `assetCode: z.string().nullable()` to
   `dashboardSummaryDtoSchema` only, filled by a `leftJoin(assets)` in
   `DashboardsService.list`; badge reads `Asset · <code>`. Else the badge says
   `Asset` alone.
2. **`widgetKey` for a template widget.** `templateWidgetResolutionDto.widgetKey`
   is required and a template widget has no key. *Recommend:* `"<view>#<index>"`,
   with `assetRoleCodes: []` and `matchedMembers: 1` (one asset).
3. **Where the view-level truncation is reported.** Decision 3 says the view's
   report says `truncated` with the omitted count, but decision 5's
   `InstantiatedDashboardDto` has no field for it and `truncated` is a per-widget
   outcome. *Recommend:* `omittedFeatured: int ≥ 0` on the view DTO; per-widget
   outcomes are `bound | partial | unresolved` only.
4. **Backfill population.** Active assets only, or every asset? *Recommend:*
   `active = true` (the instantiate path refuses inactive targets, ADR 0009).
5. **Entry count.** The catalog holds **27** entries, not 34 (ADR Context 6,
   decision 6, Q3). No scope change — every entry gains a view — but the ADR
   text is wrong and the closure should say so; correcting the ADR is the owner's.
6. **The RLS guard's role.** "On the fleet pool" cannot prove a policy refusal
   (`bms_fleet` is `BYPASSRLS`). The guard runs as `bms_tenant` (I4). Wording
   only.
7. **The instantiate dialog has no result view today**, so "beside `ruleCount`"
   has no existing surface; the plan adds a minimal one (D11) and `ruleCount`
   reaches the screen for the first time. Confirm this is wanted rather than a
   toast.
8. **`templateId` stays absent from the DTOs** while `assetTemplateId` is added.
   The asymmetry is recorded; adding `templateId` is not this row's.
9. **`stockVersion` is not bumped** for the 27 entries (ADR 0052 decision 6 makes
   a content change a release; the ADR did not rule one). *Recommend:* no bump
   here; record as a residual for the owner.
