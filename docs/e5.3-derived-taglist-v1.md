# E5.3 derived tag list v1 — facility/smart-building pack, authored from industry practice

**Status: PROVISIONAL — derived, not confirmed.** Companion to
[`e5.1-derived-taglist-v1.md`](./e5.1-derived-taglist-v1.md) and
[`e5.2-derived-taglist-v1.md`](./e5.2-derived-taglist-v1.md), same method,
same tiers. A v1 point catalog per facility asset class derived from
published practice, so the facility pack (`E5.3`) can be authored as
**template version 1** and superseded when a real BAS/fire/lighting export
lands (ADR 0015 versioning).

**Why this pack exists at P2 and not later.** The 2026-08-22 client sheet's
use-case header names hotels, data centres and townships; the SOW page-10
reference has an HVAC nav entry and a data-quality footer; the repo already
ships a control-room environment class (`temperature_c`, `humidity_pct`,
`leak_state`, `smoke_state`). The wave is unchanged (BACKLOG §8) — this
document only removes the research step from the critical path when the wave
arrives.

**Derivation basis** (recorded so v1's assumptions are auditable):

1. **ISA-5.1** letter codes where a point is an instrument; most facility
   points are *states* from a subsystem panel, marked `—`.
2. **BACnet** standard objects the subsystem gateways expose — the Life
   Safety Point / Life Safety Zone objects for fire (NEMA/BACnet SSPC-135
   fire-integration work), Analog/Binary objects for lighting and access
   gateways (zencontrol, Matrix COSEC BACnet, Advanced/Fieldserver).
3. **NFPA 72** / **IS 2189** event classes — *alarm, fault (trouble),
   supervisory, isolate (disable)* — as the fire-panel state vocabulary.
4. **DALI-2 / IEC 62386** parts 303/304 (occupancy and light sensors) and
   part 252/253 (energy and diagnostics) — the lighting-zone point set.
5. **ISHRAE IEQ Standard** and **ASHRAE 62.1** — the IAQ parameter list
   (CO₂, PM2.5, PM10, TVOC, CH₂O, temperature, RH) and the fact that CO₂ is
   a ventilation-adequacy proxy, not a pollutant limit.
6. **The repo's existing vocabulary** — `CONTROL_ROOM_ENVIRONMENT_POINT_KEYS`
   and `CONTROL_ROOM_IT_POINT_KEYS` (`rack_kw`, `rack_temp_c`, `pdu_a_status`,
   `pdu_b_status`, `pdu_util_pct`, `outlets_used`) are reused verbatim.

Per B7/B8, alarm rows carry the parameter and its *meaning* only — **no limit
numbers**.

**Tiers.** `C` = core, `X` = extended, `M` = manual (`F1.8`), `D` = derived.
Facility subsystems differ from plant instruments in one way: most "points"
are *panel states* that either exist on the gateway or do not — so `X` here
means "depends on which gateway/protocol the site has", not "depends on a
sensor being fitted".

**How the client uses this document:** strike what is not fitted, add what is
missing, correct names and units.

**Gate before this becomes template content:** the `E5.3` ADR citing this
document as v1's basis.

## 8. Vertical transport — lifts (elevators) and escalators / travelators

The hotel, data-centre and township use cases in the sheet header all run
on these. Two subclasses: **8a lift** (traction or hydraulic; drop the rows
marked *(hyd)* or *(trac)* that do not apply) and **8b escalator /
travelator**. Point sources, in order of what a site actually has:

1. **OEM cloud / API** — KONE Equipment Status API, Otis ONE, Schindler
   Ahead, TK Elevator MAX. Rich: fault codes, door cycles, ride quality.
2. **Controller gateway** — BACnet elevator objects (SSPC-135 Addendum
   *Elevator Group / Lift / Escalator* objects with `Car_Position`,
   `Car_Moving_Direction`, `Car_Door_Status`, `Car_Load`, `Passenger_Alarm`,
   `Fault_Signals`), or a Modbus/BMS-Link card (Nidec MCE, Monarch, Fuji).
3. **Dry contacts only** — the Indian default on older installations: in
   service, fault, fire mode, alarm, stuck-in-car. Three to six binaries.
4. **Retrofit IoT sensors** — accelerometer in the car, CT on the traction
   and door motors, temperature in the machine room, door-cycle counter.

The table lists the union; tier `C` is what source 3 gives, tier `X` needs
source 1, 2 or 4. **Observe-only** — no car calls, no fire recall, no
maintenance mode commands are modelled.

## Cross-cutting notes

- **Data centre rack / PDU class already exists.** `CONTROL_ROOM_IT_POINT_KEYS`
  (`rack_kw`, `rack_temp_c`, `pdu_a_status`, `pdu_b_status`, `pdu_util_pct`,
  `outlets_used`) covers the data-centre use case in the sheet header; the
  facility pack references it rather than redefining it. UPS lives in the
  electrical pack.
- **Lifts / escalators are not in the E5.3 row's text** but §8 carries them
  in v1 (owner request, 2026-09-02): hotels, data centres and townships all
  run on them, and the observe-only, counts-and-states shape is the same as
  fire and access. The `E5.3` ADR should add them to the row's class list.
- **Source tiers for §8 matter more than sensor tiers.** A dry-contact
  interface yields the `C` rows only; an OEM API or BACnet elevator objects
  yield most of `X` at once; ride-quality and door-motor rows need retrofit
  sensors. Ask the site which of the four sources it has before redlining.
- **Privacy boundary.** Access and occupancy classes carry *counts and
  states*, never identities; camera analytics deliver a number, not a frame.
  This is the §9.6 rule applied at the template layer, and it is what keeps
  these classes out of DPDP scope.
- **Fire is observe-only.** No command points are modelled; the template
  declares no writes.
- **Counts:** 227 points across eight classes (118 of them in §8); 44 core, 171 extended,
  10 manual, the rest dual-tier. Extended dominates because facility points depend on which
  gateway is fitted, not on which sensor — a site with a BACnet fire gateway
  gets all of §2 at once, a site with a relay contact gets three rows.
- **What v2 will change:** the gateway/protocol per subsystem (which fixes
  the `X` tier at once per site), the panel vendor's fault vocabulary, and
  the zone/loop → asset mapping.
