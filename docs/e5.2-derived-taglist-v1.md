# E5.2 derived tag list v1 — mechanical/utility pack, authored from industry practice

**Status: PROVISIONAL — derived, not confirmed.** Companion to
[`e5.1-derived-taglist-v1.md`](./e5.1-derived-taglist-v1.md), same method,
same tiers, same caveat: Ion Exchange's real tag list (form ref **A1**) has
not landed, so this is a v1 point catalog per asset class derived from
published practice. It exists so the mechanical/utility pack (`E5.2`) can be
authored as **template version 1** and superseded by v2 when a real fitment
schedule arrives (ADR 0015: a row *is* a version; published assets are never
touched by a later version).

**Why this pack is next after water.** The 2026-08-22 client sheet (row 4)
names chillers, compressors and HVAC explicitly, asks for chiller-health
analytics (form ref **N5**), and its framing is building-wide. Form ref
**N4** commits us to authoring KPI library v1 ourselves — chiller kW/TR and
COP, cooling-tower approach/range, kWh/KL, availability — which means the
points those KPIs need must be in the templates before the KPIs can exist.

**Derivation basis** (recorded so v1's assumptions are auditable):

1. **ISA-5.1** letter codes per point, as in E5.1; point codes keep the
   repo's `snake_case` + unit-suffix convention (`chw_supply_temp_c`).
2. **ASHRAE Guideline 36-2021** — the AHU and chiller-plant point lists its
   sequences and AFDD routines require (SAT, RAT, MAT, OAT, DSP, filter ΔP,
   damper/valve commands, CHWST/CHWRT, CW entering/leaving, plant ΔP).
3. **Project Haystack** equipment/point vocabulary — entering/leaving naming,
   `chiller`/`coolingTower`/`pump`/`ahu`/`boiler` equip conventions, kW/ton and
   COP as the chiller efficiency points.
4. **Controller register maps that ship on the equipment** — Atlas Copco
   Elektronikon (compressors: outlet pressure, element outlet temperature,
   running/loaded hours, load state), ABB ACS580 group 01 (VFDs: output
   frequency, motor current, DC bus voltage, drive temperature, fault code),
   Deep Sea / ComAp (see the electrical pack for DG).
5. **ISO 20816** (superseding ISO 10816-3) and **ANSI/HI 9.6.4** for
   pump/motor vibration velocity as the condition-monitoring point.
6. **IBR (Indian Boiler Regulations) log-sheet practice** — steam pressure,
   drum level, feedwater, flue-gas temperature and O₂ as the boiler points an
   Indian plant already records by hand.
7. **The repo's existing vocabulary** — `HVAC_POINT_KEYS` (`supply_air_temp_c`,
   `return_air_temp_c`, `fan_rpm`, `fan_speed_pct`, `chw_flow_lps`,
   `chw_supply_temp_c`, `chw_return_temp_c`, `compressor_ok`, `cooling_kw`) and
   the electrical motor points are **reused verbatim** where they fit, so the
   seeded `BASELINE-HVAC` template and the simulator do not fork.

Per B7/B8, alarm rows carry the parameter and its *meaning* only — **no limit
numbers**; values are set per site at commissioning.

**Tiers.** `C` = core: fitted in any standard design of that asset class —
low guess-risk. `X` = extended: depends on instrumentation/controller choices
— the tier the client redlines. `M` = manual/lab entry (via `F1.8`). `D` =
derived tag computed by the calc engine.

**How the client uses this document (workshop handout):** strike what is not
fitted, add what is missing, correct names and units.

**Gates before this becomes template content:** the `E5.2` ADR citing this
document as v1's basis; ADR 0019 Amendment 2 (`thresholdValue` optional) if
E5.1 has not already landed it.

## 1. Pump set — centrifugal, with motor (raw/treated water, CHW/CW, boiler feed)

The base class. Every other pack that has "a pump" (WTP intake, RO HP pump,
cooling-tower circulation, CHW primary/secondary) is this table plus the
process points already listed in that pack.

| Point code | ISA | Description | Unit | Tier |
|---|---|---|---|---|
| `pump_status` | — | Run status | 0/1 | C |
| `pump_mode` | — | Auto / manual / off selector | enum | C |
| `pump_trip` | — | Trip / fault (overload, dry-run, VFD fault) | 0/1 | C |
| `current_a` | IT | Motor current | A | C |
| `kw` | JT | Motor input power | kW | X |
| `kwh_total` | JQ | Cumulative energy | kWh | X |
| `suction_pressure_bar` | PT | Suction pressure | bar | X |
| `discharge_pressure_bar` | PT | Discharge pressure | bar | C |
| `flow_klh` | FT | Delivered flow | KL/hr | X |
| `run_hours_h` | KQ | Cumulative run hours | h | C |
| `start_count` | KQ | Cumulative starts | count | X |
| `de_bearing_temp_c` | TT | Drive-end bearing temperature | °C | X |
| `nde_bearing_temp_c` | TT | Non-drive-end bearing temperature | °C | X |
| `winding_temp_c` | TT | Motor winding temperature (RTD) | °C | X |
| `vibration_mms` | VT | Overall vibration velocity, RMS | mm/s | X |
| `seal_leak_state` | — | Mechanical seal / gland leak detect | 0/1 | X |
| `dry_run_state` | — | Dry-run protection active | 0/1 | X |
| `insulation_resistance_mohm` | — | Megger IR value (manual, periodic) | MΩ | M |

**Derived:** `head_m` D = (discharge − suction) × 10.2 · `specific_energy_kwh_kl`
D = kW ÷ flow · `duty_hours_pct` D · `starts_per_hour` D (short-cycling guard)
· `availability_pct` D (N4) · `vibration_band` D per ISO 20816 zone A–D.
**Alarms (meaning only):** pump trip · current high (overload / blocked) or
low (dry run / broken coupling) · discharge pressure low with pump running
(no flow / air lock) · bearing temperature high (lubrication / failure lead
indicator) · vibration high (imbalance, misalignment, cavitation) · seal leak
· run-hours service due · starts-per-hour high.

## 2. Motor + VFD — variable-frequency drive on any driven load

Attach to the pump, fan, blower or compressor it drives. Points come from the
drive's fieldbus register block (ABB group 01 pattern; Danfoss, Schneider and
Siemens carry the same set under other numbers).

| Point code | ISA | Description | Unit | Tier |
|---|---|---|---|---|
| `vfd_status` | — | Drive run status | 0/1 | C |
| `vfd_ready` | — | Drive ready / enabled | 0/1 | X |
| `vfd_fault` | — | Drive fault active | 0/1 | C |
| `vfd_fault_code` | — | Active fault code (vendor enum) | code | C |
| `vfd_output_freq_hz` | ST | Output frequency | Hz | C |
| `vfd_speed_ref_pct` | — | Speed reference / setpoint | % | C |
| `vfd_output_current_a` | IT | Motor current | A | C |
| `vfd_output_voltage_v` | ET | Output voltage | V | X |
| `vfd_dc_bus_v` | ET | DC bus voltage | V | X |
| `vfd_torque_pct` | — | Motor torque | % | X |
| `vfd_power_kw` | JT | Output power | kW | X |
| `vfd_kwh_total` | JQ | Cumulative energy | kWh | X |
| `vfd_heatsink_temp_c` | TT | Drive / heatsink temperature | °C | X |
| `motor_temp_c` | TT | Motor thermal model or PTC | °C | X |
| `vfd_run_hours_h` | KQ | Drive run hours | h | C |

**Derived:** `motor_load_pct` D = current ÷ rated · `energy_saving_vs_dol_kwh`
D (affinity-law estimate) · `speed_pct` D = output freq ÷ rated.
**Alarms (meaning only):** drive fault (code carried in the alarm text) ·
overcurrent · DC bus over/under-voltage (supply quality) · heatsink
temperature high (cooling / ambient) · motor temperature high · speed
reference not followed (mechanical binding).

*Redline note (`E5.2`, 2026-09-04): §2's* Derived *line names three ratios the
drive cannot compute — `motor_load_pct`, `energy_saving_vs_dol_kwh` and
`speed_pct` — because rated current, rated frequency and a DOL baseline are
nameplate attributes, not points, and a formula hardcoding a 50 Hz base
frequency would ship a wrong number on a 60 Hz site. `vfd_speed_ref_pct`
already carries the commanded speed as a percentage. v1 declares none of the
three; the workshop handout is where the client confirms whether a drive on
site can report its nameplate values on its own register block (`F2.18`).*

**Alarms (meaning only):** compressor shutdown · element outlet temperature

*Redline note (`E5.2`, 2026-09-04): `fad_m3h` stays optional (`X` tier)
because most installed compressors have no flow meter, and a required point
with a null pattern is a 400 at instantiation — v1 does not promote it to
core. Separately, the dryer travels with the machine here only because a
packaged skid ships its dew point and run status together; a separately
mounted dryer is a v2 redline candidate the client can price as its own
asset (`F2.18`).*

`cw_entering_temp_c`, `cw_leaving_temp_c`, `cw_flow_lps` and `cw_delta_t_c`
from the imported draft. The first two are core and required, so on an
air-cooled site the strike is not tidying up: left in place with no meter to
map, they refuse the draft at instantiation. The workshop handout is where
that strike happens; v1 ships all four rows because the document does not
know a given site's condenser type (`F2.18`).*

## Cross-cutting notes

- **Classes compose.** A "CHW primary pump" asset is §1 + §2; a "compressor
  house" is n × §3 + one receiver; a "chiller plant" is n × §4 + n × §1 +
  E5.1 §4 towers. Templates should carry the base class and let the asset
  group carry the composition (ADR 0031: domain from the asset, concern from
  the rule).
- **Existing keys are reused, not renamed.** `current_a`, `kw`, `kwh_total`,
  `supply_air_temp_c`, `return_air_temp_c`, `fan_rpm`, `fan_speed_pct`,
  `chw_flow_lps`, `chw_supply_temp_c`, `chw_return_temp_c`, `compressor_ok`,
  `cooling_kw` already exist in `packages/shared/src/constants.ts`; the
  seeded `BASELINE-HVAC` template and `apps/sim` keep working. New keys land
  through the same global-vocabulary path as `F3.41` (ADR 0051).
- **Every `M` row lands via `F1.8` manual entry / `F1.9` import** — megger
  values, refrigerant charge, boiler-water chemistry.
- **Per-asset electrical points** (`voltage_*`, `current_*`, `pf`) come from
  the electrical pack's feeder/meter class, not from here — a motor feeder
  in an MCC is an electrical asset that *drives* a mechanical one.
- **Counts:** 128 points across six classes (the tower is referenced, not
  counted); 54 core, 69 extended, 4 manual, the rest dual-tier — 115 distinct
  codes, 21 of them already in the global vocabulary (reused, never
  redeclared) and 94 new; with the thirteen derived codes `E5.2` promoted, 107
  keys joined `bms.point_keys` (291 → 398). The redline burden is the
  extended tier, mostly condition-monitoring sensors (bearing RTDs,
  vibration, flue O₂) that a plant may or may not have fitted.
- **What v2 will change:** fitted-instrument reality per plant, the OEM
  controller each chiller/compressor actually carries (which fixes the
  fault-code enums), and any site-specific extras. The shape — units, KPIs,
  alarm meanings — is the part practice fixes.
