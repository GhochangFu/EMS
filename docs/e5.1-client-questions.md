# E5.1 — open client questions (Ion Exchange)

**Status: sent, unanswered as of 2026-08-09.**
Blocks [`E5.1`](./BACKLOG.md) (water-treatment domain pack) and the ADR that
would promote it — **ADR 0021**, unwritten. (`0020` is free on disk but reserved
for the E8.1 encryption-at-rest retro, per ADR 0019's numbering note and
`BACKLOG.md` §5. Check `docs/adr/` before writing either — that reservation has
gone stale twice already.)

This file exists because `E5.1`'s two dependencies (`F2.1`, `E1.7`) both went
`✅` on 2026-08-05, so every re-derivation of the backlog calls it eligible. It
is not. The blocker is an unanswered client question set, which the `Depends`

## 1. The mail, verbatim

> We are planning the asset-template library for the EMS platform and are
> starting with water treatment, since that is the heart of your business.
>
> Before we commit to a design, we would rather check our assumptions with you
> than build on them. There are five questions below. Short answers to any of
> them help — and if only one gets answered, please make it question 2.
>
> For context, we have drafted a first set of templates covering RO plants,
> cooling water / cooling towers, sewage treatment plants, and softeners. We
> chose those four because they appear to match the remote-monitoring packages
> Ion Exchange Services already offers. Which leads to the first question.
>
> **1. Are those four the right place to start?** Our understanding is that
> IESL's remote monitoring covers RO plant automation, INDION Swift units,
> cooling-tower blowdown, and energy/oxygen monitoring on STPs. If that list has
> moved on, or if the first TRINETRA deployment will actually land on a
> different plant type — an ETP, a DM plant, a UF skid — we would much rather
> build that one first.
>
> **2. Could we see the tag list from one real plant?** A P&ID, an I/O schedule,
> a SCADA or PLC tag export — whatever already exists, from any single plant, of
> any type. One real example is worth more to us than a dozen assumptions: it
> tells us your naming conventions, your units, and above all which instruments
> are actually fitted rather than theoretically available. We are happy to work
> from a redacted or anonymised copy.
>
> **3. Alarm setpoints — set per site, or do you have standards?** Our reading
> is that most limits depend on the individual plant's design and its discharge
> consent, so we are planning to ship templates that specify which parameters to
> alarm on and what each one means, leaving the actual numbers to be set per
> site during commissioning. If Ion Exchange applies standard setpoints across
> plants, that changes the design and we would like to know before we build it
> rather than after.
>
> **4. For effluent and sewage plants — where does the treated water go?**
> Inland surface water, public sewer, land for irrigation, or recycle/reuse? We
> ask because the CPCB Schedule VI limits differ substantially by discharge
> route — BOD is 30 mg/L to inland surface water but 350 mg/L to a public sewer
> — so the route decides which numbers a given plant is actually held to. If
> your plants span several routes, that is useful to know too.
>
> **5. What do you call these plants internally?** We would like the platform to
> use your product names rather than generic ones. We have seen INDION FMR,
> NGPSTP and Eco MBR referenced for packaged sewage treatment; we are less
> confident about the naming on the RO, DM and softener side, and would rather
> ask than guess wrong in a customer-facing screen.

## 2. What each answer decides

| Q | Decides | Cost of guessing |
|---|---------|------------------|
| 1 | Which asset classes `E5.1` ships first | 6–8 person-weeks aimed at the wrong plant type |
| 2 | `template_points` catalog — point keys, units, which instruments exist; also seeds `F2.7`'s mapping vocabulary | A catalog of theoretically-available instruments that no real plant reports |
| 3 | Whether templates carry setpoint **numbers** or only *which parameter to alarm and what it means* | **Reopens ADR 0019** — see §3 |
| 4 | Whether packs can carry limit values at all, and which CPCB Schedule VI column applies | Limits authored against the wrong discharge route |
| 5 | Template `code` and customer-facing display names | Wrong product names on an operator's screen |

**Question 2 is the priority ask**, and the mail says so. One real tag export
settles naming conventions, units and fitted instrumentation at once — the three
things the other four questions only approximate.

## 3. Question 3 collides with a merged ADR — read before authoring alarms

[ADR 0019](./adr/0019-template-content-model.md) is **accepted and merged**, and
its `alarms[]` entry declares:

```ts
thresholdValue: number,   // required — every other soft field there is `?`
```

The mail tells the client the opposite: templates that name the parameter and
its meaning, with numbers set per site at commissioning. Under the merged
contract that template **cannot be authored** — `E5.1` would have to invent a
placeholder number per alarm, which is exactly the failure ADR 0019 was designed
to prevent ("a reserved key that is silently accepted is worse than one that
errors").

So a *"setpoints are per-site"* answer — the answer the mail expects — requires
**ADR 0019 Amendment 1** making `thresholdValue` optional or nullable. Amending
an accepted ADR is a human gate (AGENTS.md §10). The reply potentially unblocks
`E5.1` and reopens `0019` in the same breath.

In `E5.1`'s favour: the *meaning* half already has a home. `philosophy.cause` /
`.impact` / `.action` / `.skill` exists in that same schema — Anchored rather
than Bound, so `E2.1` may still rename it, but the CPCB context behind question
4 has somewhere to live today.

## 4. Provenance

The CPCB Schedule VI reasoning and the IESL product names (INDION Swift, INDION
FMR, NGPSTP, Eco MBR) were researched when the mail was drafted and exist
**nowhere else in this repository** — a `grep` for `CPCB` returns nothing. That
is the reason this file exists rather than the questions living only in a
mailbox. Treat the product names as *what we asked about*, not as verified
fact; question 5 is precisely the request to confirm them.

**When the reply lands:** record the answers here, then write ADR 0021 before
any `E5.1` code. Update the `E5.1` row in `BACKLOG.md` §2 Track B, which links
here; the critical-path note in §1 and slot 8 in §1b both point at that row.
