# F1.7 — PHE fleet measurement, 2026-08-22

The scope of `F1.7` is the answer to one question: **which of the twelve PHE
RTUs in `packages/db/src/phe-catalog.json` actually publish?** This file records
the measurement so the answer is a dated fact rather than an assumption, in the
shape the `F1.1` backlog row uses ("re-measured 2026-08-14 at 0 rows").

Repeat it with `apps/ingest/scripts/fleet-probe.mjs`. It subscribes read-only, writes
nothing, and logs key **names** and counts only — never a reading (AGENTS.md
§9.6).

```bash
node apps/ingest/scripts/fleet-probe.mjs 600
```

## Seven keys arrive with nowhere to go

The wire carries 27 distinct `values` keys. The catalog carries 21 real points
per RTU (22 rows minus `ts`, which the seed skips and deletes — migration
`0025`).

**On the wire, absent from the catalog:**
`ai1` `ai2` `di3` `di4` `do1` `do2` `s12_r02`

**In the catalog, absent from `values`:** `rssi`, published at the top level and
merged by `parsePayload`, so it is fine; and `ts`, the envelope's own timestamp.

**Lotapata I's key count varies between runs**, and the two figures in this
document are both real rather than one being a typo. It published **26** keys in
the 600 s run and **27** in the 150 s and 200 s runs; the section below records
27 for every RTU because that is what those later runs measured. Which key it
intermittently omits is not identified, and a union across cycles cannot say —
see the caveat under the absent-reading table. All 21 of its *mapped* points
land either way, so nothing here is affected.

These seven are **a catalog gap, not an ingest defect** — the vendor export is
dated 2026-06-26 and predates them. Nothing here maps them, because nobody in
this repository knows what they measure. They are concrete evidence for the
still-unanswered **A1 (tag list)** re-ask in `docs/BACKLOG.md` §8.5, and are now
tracked as **`F1.15`**.

## A key on the wire is not a reading — Salkumarhat's meters are dark

Added after the fleet was enabled, because the first three runs counted keys per
topic and never asked whether those keys carried a value. They do not always.
The probe now reports `absent=` per topic and names the keys, so this table is
reproducible rather than transcribed.

"Absent" means `null`, `""` or a value that will not coerce to a finite number
— the three cases `samplesFromPayload` skips. Every RTU below publishes the full
27 keys; the difference is entirely in which of them carry a reading.

| RTU | absent | which |
|---|---|---|
| 861736076081915 Salkumarhat I | **17** | the whole block: `s01_r01`–`s15_r01`, `s08_r02`, `s12_r02` |
| 861736076128260 Salkumarhat II | **17** | the same 17 |
| 861736076128245 Bhutnirghat II | 2 | `s12_r01`, `s12_r02` |
| the other six | 0 | — |

Measured over 150 s and 200 s runs, which agree.

**Two limits of this measurement, so the numbers are not over-read.** The probe
unions its key sets across the whole window, so a key empty in one cycle of ten
is reported exactly like a permanently dark register — `absent=17` means "was
absent at least once", not "is dark now". The Salkumarhat conclusion survives
that, because the database independently shows those 16 points with **no rows at
all** over hours, not gaps. And the accounting covers `body.values` only, so an
empty *top-level* key is invisible to it — `rssi` → `network_strength` is
published at the top level and merged by `parsePayload`, so a dark `rssi` would
not appear in the table above.

**Bhutnirghat II is the case that shows this is per-register, not per-station.**
Its two dark keys include `s12_r01`, which maps to `kwh_total` — one meter
register failing on an otherwise healthy RTU, and the reason it lands 20 of 21
points where its siblings land 21. A whole-station verdict would miss it.

So both Salkumarhat stations land **5 of their 21 mapped points**, and the 16
missing ones are precisely the mapped members of that block. The meters behind
those two RTUs are not answering; the RTU still publishes their register keys,
empty. Treating an empty reading as absent rather than as a zero is correct and
is the legacy behaviour verbatim — **the defect is that nothing reports it**,
because the drop happens in the adapter before a sample exists and so no
counter in `resolveSamples` can see it: `main.ts`'s `samples discarded` warning
cannot fire for a sample that was never built, and the log carries zero such
lines. `unmappedSourceKey` would have caught a mapping error; nothing catches
this. Tracked as **`F4.55`**.

Note that this is a **field condition surfaced by `F1.7`, not caused by it**.
The nine RTUs were on the wire in this state before anything here enabled them;
what changed is that eight more dashboards now depend on those readings.

Everything else was eliminated first: identical `source_data_key` → `point_key`
mappings to Bilsi I, all 21 rows `active` with `source_kind = 'measured'` and
`asset_points.rtu_id` matching, so `loadBindingRows` hands the adapter 21 source
keys for both stations.

## Every device keeps its own clock, and the spread is 3 h 37 m

`parsePayload` takes the envelope's `ts` verbatim and it becomes the row's
`time`. Measured on the running stack against a server at **11:41:46 UTC**, all
nine on a 60 s cadence:

| RTU | Station | skew vs server |
|---|---|---|
| 861736076128211 | Mora Nodir Kuthi II | **−3:02:36** |
| 861736076128245 | Bhutnirghat II | −0:21:34 |
| 868019069263896 | Lotapata I | +0:08:11 |
| 861736076128187 | Mora Nodir Kuthi I | +0:10:15 |
| 861736076080040 | Lotapata II | +0:11:48 |
| 861736076116638 | Bilsi I | +0:12:53 |
| 861736076081915 | Salkumarhat I | +0:15:30 |
| 861736076128260 | Salkumarhat II | +0:17:38 |
| 861736076104923 | Bhutnirghat I *(pilot)* | **+0:34:31** |

Correcting each RTU's first row by its own offset lands all nine on the same
start minute, which is what rules out a stuck clock or a retention trim. The
pilot's +34:31 matches the ~34 minutes `docs/ingest-host.md` recorded on
2026-08-06, so this is stable per device and long-standing rather than drift.

**This cost real time during the build.** A diagnostic bounded on `time > now()
- interval '15 minutes'` reported Mora Nodir Kuthi II and Bhutnirghat II as
writing nothing at all — they are the two devices lagging by more than fifteen
minutes, so the window excluded exactly the rows it was meant to find. Any
dashboard doing the same omits them the same way. Tracked as **`F4.54`**, which
also carries `F4.37`'s deferred residual naming `F1.7` as the place to clamp.
